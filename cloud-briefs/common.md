## 共通の前提(全クラウドセッション)

duocad は OCCT(OCP 7.9.3)で形を作る CAD。サーバは Python 3.14、画面は Svelte + three.js。いま全操作の応答を速くする作業の続きをしている。
あなたの担当は下の「担当」の1枝だけで、ほかの枝は別のクラウドセッションが同時に進めている。親セッション(本人の手元)が各枝の成果を、
本人の実データと保存済みの文書群(このリポジトリには無い)で確かめてから取り込む。

### 始め方
1. このセッションはリポジトリの既定のブランチ(main)から始まる。最初に `git fetch origin develop && git checkout -B cloud/perf-<名前> 4ef67570`
   (`<名前>` は担当に書いた名前)。基準はこのコミット(develop の 4ef67570)で、前の値もここで取る。
2. 先に読む: `CLAUDE.md`(コメントの規則・本人の発言を引かない規則)、`docs/PERFORMANCE.md` 6章、`docs/decisions.md` の見出しに `[速さ]` がある節、
   `docs/STATUS.md` の先頭の節「残りの高速化の調査と低リスクの修正」。
3. 依存: `uv sync --frozen`(Python 3.14 を uv が入れる)。以後 `uv run python ...` / `uv run pytest ...`。CLAUDE.md の
   `.venv/Scripts/python.exe` は本人の Windows のことなので、ここでは `uv run` でよい。
   Node の評価器(`tests/eval_*.mjs`)は Node 23.6 以上が要る。無ければ入れてよい(nvm など)。入れられなければ、そのテストが
   走らなかったことを報告に書く。

### 物差し
- `uv run python tools/bench_all_ops.py --docs part --part big --out <一時ファイル>`: 合成の部品(穴 384・485 面の板)で全 verb の
  ゴースト(preview)・確定(confirm)・配信(push)・MCP の確定(mcp)・その後の配信(mcp_push)・undo/redo とカメラの配信を測る。
  `--only <名前の一部 or verb>` で絞れる。`--profile` は cProfile(1ケースに絞って使う。全体では入れ子で落ちる)。
- 担当の着手前に必ず前の値を取り、同じ機械で後の値を取る。値は ±1〜2 割揺れるので、3回測って中央値を使う。

### 変えないもの(必ず守る)
- 形・面と辺の番号・保存形式・操作ログ・自動保存の仕様。ゴーストの待ち(打ち終わって 250 ms)とシェルの期限なしは本人の決めたことなので変えない。
- 他の枝の担当の関数。共通の関数(とくに `duocad/brep_operations.py` のブーリアンの組み立て、`kernel_meshing.py`、`view.py` の面のキャッシュ)を
  変えたくなっても、担当に書いていなければ変えずに、理由と案を報告に書く。

### 環境と資料の限界
- 本人の実データ(QR1 の STEP)、保存済み 206 文書の群、実機のブラウザは、このクラウドには無い。合成の試験に通ったことを、それらの確認の
  代わりにしない。報告の「親に確かめてほしいこと」に、何が未確認かを書く。
- `--part big` は穴の多い平面への負荷試験で、本人の部品の代わりではない。改善率を本人の部品にそのまま当てはめない。

### 測り方の条件
- 基準(4ef67570)と変更後を同じ機械で交互に測る。最初の1回(冷えた状態)と2回目以降(温まった状態)を分ける。
- 小さい部品(`--part small`)、`--part big`、担当に合わせて作った反例の形の3つで測る。時間に加えて、成功・失敗の件数、三角形の数、
  配信の大きさ、メモリ(分かる範囲で)も控える。
- 「速くならなかった」「安全に直せなかった」も有効な結果として、そのまま報告する。

### 低リスクの定義(必ず守る)
- 形(体積・面の数・面の並び)・面と辺の番号・保存形式・操作ログの再生を変えない。操作ログは面・辺の番号で対象を指すので、番号の並びが
  1つでも変わると保存済みの文書が別の形になる。
- 既存のテスト全件(`uv run pytest -q -p no:cacheprovider`)が通る。足した挙動にはテストを足す(落ちたとき何を意味するかを docstring に1〜2行)。
- 三角形の並べ方(表示の分割)が変わる変更は、三角形を使っている箇所(表示・ピック・干渉・計測・最小幅など)を全部洗い出して
  報告に書く。入れるかどうかは親が決めるので、その種の変更は別のコミットに分ける。
- 少しでも形・番号を変えうる変更や、効果が測れなかった変更は入れずに、案と測った数字だけを報告に書く。

### 書いてよい範囲と終わり方
- 書いてよいのは担当に書いたファイルと、その枝のテスト。ほかのファイルを変えたくなったら変えずに、理由を報告に書く
  (別の枝と重なると取り込みで壊れる)。`docs/` は変えない(親が書く)。
- コミットは意味の単位で分け、メッセージは日本語で何を・なぜ。コードのコメントは CLAUDE.md の4種だけ。
- 変更は、1つずつ採否を決められる小さなコミットにする。
- 最後に、リポジトリ直下の `REPORT-<名前>.md` に報告を書いて、別のコミットにする(親はこのファイルを取り込まない)。再現のコマンドと
  生の測定値(表か JSON)も入れる。報告の節:
  1. 測った内訳(前): どこに何秒。cProfile の上位など根拠つき
  2. 入れた変更: コミットごとに、何を・なぜ・前後の値(中央値)・形を変えないと言える根拠
  3. 入れなかった案: 案・測った値・入れなかった理由(リスク・効果不足・範囲外)
  4. テスト: 実行したコマンドと結果(通らなかったもの、走らせられなかったものも)
  5. 親に確かめてほしいこと(本人の実データや文書群でしか確かめられない点)
- `git push -u origin cloud/perf-<名前>` で、そのブランチだけを push して止まる。PR は出さない。develop・main には push しない。
- 認証情報を書かない。要件を変えない。本人の発言をリポジトリに引かない。
