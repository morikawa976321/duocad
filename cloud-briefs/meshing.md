## 担当: 面の分割の速さ(名前 `meshing`)

書いてよいファイル: `duocad/kernel_meshing.py`、`duocad/boundary_check.py`、`duocad/kernel.py` の三角形分割の関数(`tessellate`・`tessellate_faces`・`tessellate_reusing`・`_face_triangles` とその下請け)だけ。

分かっていること(親が手元で測った):
- `--part big` で、カメラの配信が 7〜28 秒、初回の配信が 1.7 秒かかる。
- 穴 384 個の平面1枚の分割(`IMeshTools.DiscretizeFaces`)に 0.8〜2 秒かかる。1面の中は並列にならない。角度の許容が細かいほど遅く、
  0.5 で 0.8 秒、0.3 で 1.9 秒。
- ボディ全体を `kernel_meshing.mesh_shape` で1回に分割すると、偏差 0.12 で 1.0 秒、偏差 0.012 で 1.3 秒(角度 0.5)。ところが配信の中では、
  485 面を偏差 0.0372 で分割した1回の呼び出しが 5.1 秒かかった。角度は `kernel.DEFAULT_ANGULAR_DEFLECTION` = 0.35。

調べること:
1. 配信の中の分割が単体より遅い理由。組み方、偏差と角度、同じ面を2度分割していないか、再分割の巡回(`rounds`)。
2. 穴の多い平面の分割を速くする方法。OCCT のパラメータ、平面だけ別の面分割の手法(例: `BRepMesh_DelabellaMeshAlgoFactory`)、
   重い面を別スレッドで並べて処理する、など。三角形の並べ方を変える案は、低リスクの確定扱いにしない。条件を満たすかを調べて報告し、
   別のコミットにする。満たすべき条件:
   - `kernel.tessellate` は表示のほか、STL の出力と形状最適化(ボクセル化・仕上げ)にも使われている。どこに効くかを書く。
   - `mesh_shape` は形に付いた三角形を消して書き直す(戻り値だけの変更ではない)。その副作用を調べる。
   - 穴を塞がない、領域の外を覆わない、共有する辺に隙間を作らない、重なる三角形や潰れた三角形を増やさない。これらを検査で確かめる
     (面積の和だけでは、欠けと重なりが相殺するので足りない)。
   - いまの境界検査・再分割・失敗した面の警告を保つ。許容値を後から緩めない。
   - 面の番号と、画面の三角形から CAD の面への対応、法線、鏡映した後の向きを保つ。
   - 精度や手法の違いを、キャッシュと配信の `serial` が区別する(手法を変えた三角形を古い `serial` で省いて送らない)。
   - 既存の手法のまま固定費を削る変更を先に、手法を変える変更は後に、別のコミットで。
3. Python 側の三角形の取り出し(`_face_triangles`。呼び出し1回およそ 1.5 µs が下限と前に測った)を、配列でまとめて取れないか。
4. 読み込み直後の配信がイベントループの上で走る件は、この枝の範囲外(報告に気づいたことだけ書く)。
