# duocad — AI統合（アプリ内AI・MCP・ローカルLLM）

**読むとき**: アプリ内 AI パネル・`duocad/agent/`・MCP 経路の方向を変えるとき、ローカル LLM の能力や待ち時間を見積もるとき。
仕組みの正は README §1・§4 と [../MCP.md](../MCP.md)、契約は `tests/test_agent_*.py` / `tests/test_mcp*.py`。

## ローカル LLM の実測（duocad の実ツールで）

- **Qwen3.8-27B-Q3_K_M**（Q4_K_M に置き換え済み。下記）: 5面6辺の STEP で `import_step` → `describe_predicates` を教えずに自発的に呼び、
  「全部の辺」を選ぶ述語が無い問題を `length_gt: 0` で回避して `describe_shape` の `edge_count=6` と突き合わせて検算 →
  `set_selection` → `fillet(radius=1)`。全7ターン 170秒。
- **Ornith-1.5-9B**（Q4_K_M・RTX 5060 Ti・67 tok/s）: 「XYにスケッチ→原点に直径8mmの円→X20mm×4・Y15mm×3で配列」を5手で完走
  （エラーゼロ・ID の捏造ゼロ）。40ボディ＋8スケッチ＋24パラメータから「kind=solid のうち体積最大」も正答。**9B でもエージェントの
  土台に足りる**（dGPU 無しのラップトップへの移行余地）。
- **待ち時間の分散はほぼ全部が思考**（Ornith-9B・同一の4手目を8回ずつ）: 中央値 思考ON 3.25s／OFF 1.56s、最悪 8.09s／1.66s、
  誤りは条件によらず 1/8。思考OFF は出力長がほぼ決定的（98トークン）で、このタスクでは品質の代償が見えない。事故時の
  7,468 トークン（1リクエスト120秒超）は通常の裾ではなく**縮退ループ**。サンプラは `repeat_penalty=1.0` `dry_multiplier=0.0`
  （llama-server 既定）で反復抑制が入っていない。矛盾した指示で思考が膨らみ600秒返らなかった実測もある。
- **Qwen3.8-27B-Q4_K_M を dGPU 無しのラップトップ（Core Ultra 7 255H）で**: 思考の設定 × 依頼文 × 指示文の比較、失敗の型、
  **スロット復元がハイブリッドモデルでは効かないこと**は [LOCAL_LLM_QWEN38.md](LOCAL_LLM_QWEN38.md)。

## llama-server の機構の実測（プロンプトキャッシュ・中断・スロット保存）

`python tools/llm_probe.py` で測る（台本で固定した会話を製品と同じ本文で送る）。**判定はトークン数**（処理した `prompt_n` と
再利用した `cache_n` は機種をまたいで同じになり、秒数はならない）。llama.cpp b10549・Gemma 4 12B Q4_0・`--swa-full -c 10240`・
RTX 5060 Ti（2026-10-04）。

- **固定プレフィックスは 6,676 トークン**（system 247 + ツール41個 6,429）。cold のたびに全部処理する。
- **往復ごとの再利用は `AgentLoop` の送り方で効く**: 2往復目以降の処理量は前回から伸びた分（35〜362 トークン）。**思考で増えるのは
  生成側**（1往復 19〜269、思考なしは 9〜99）。
- **ウォームアップは効く**: system + tools + `"."` を `max_tokens: 1` で先に投げると最初の依頼の処理量が 6,686 → 16 トークン。
- **キャッシュが外れる条件**（7,227 トークンの会話に1依頼足したときの処理量。何も変えなければ 203）: ツールの順序を末尾2個入れ替え
  824／先頭2個入れ替え 7,174／ツールを末尾から1個外す 748（`--cache-reuse 256` 付きで 203）／先頭から外す 6,978（同 203）／
  状態を system に毎回書き換える 7,236／状態を各依頼の末尾に付ける 268／別の会話の割り込み 7,407。ツール定義は system の直後
  （先頭から約240トークン）なので、**そこより前を触ると全部処理し直す**。`--cache-reuse` が救うのは**消えた分を詰める場合だけ**。
- **スロットを2本（`-np 2 -kvu`）にしても割り込みは防げなかった**: 短い別会話はテンプレート冒頭が一致するだけで類似度 0.214
  （既定の閾値 0.10）になり、会話のスロットへ入って 7,227 トークンを上書きした。
- **履歴の切り詰め方で総処理量が倍変わる**（18依頼、6依頼超で落とす）: 切らない 10,306／毎回1依頼ずつ滑らせる 21,191／
  半分まとめて落とす 12,447（`--cache-reuse 256` 付きなら3方式とも 10,306）。**切らないと `-c` を超えた時点で HTTP 400
  （`exceed_context_size_error`）** —— サーバは黙って詰めない。
- **非ストリーミングは、接続を閉じても生成が止まらない**（1,500 トークンの生成を3秒で閉じても止まるまで 26.9秒。待ち時間切れも
  同じ）。ストリーミングは閉じて0.22秒で止まる。**待ち時間切れや中断のあともスロットが塞がり、次の依頼が後ろで待つ。**
- **スロット保存は再起動をまたいで効く**（`--slot-save-path` ＋ `POST /slots/0?action=save|restore`）: 6,676 トークンで 119.5MB
  （KV q4_0）、保存 119ms・復元 94ms、復元後の最初の依頼の処理量は 16。
- **`timings` は非ストリーミングの応答と、ストリーミングの最終チャンクの両方に載る**（`cache_n` / `prompt_n` / `prompt_ms` /
  `predicted_n` / `predicted_ms`）。
- **スライディングウィンドウ注意を持つモデル（Gemma）は `--swa-full` なしだと、途中で食い違った時点でキャッシュが全部外れる**
  （末尾2個の入れ替え 824 → 7,413）。末尾追記・ウォームアップ・往復ごとの再利用は同じに効く。

**製品の対応**:

- **ストリーミングで受け、打ち切りで接続を閉じる**（`StreamingTransport`）。中断も合計時間上限での切断も、サーバは0.2秒で止まる。
- **ウォームアップとスロット復元**（画面が繋がると `ai_prepare` → `OpenAICompatProvider.prepare`）。スロットファイルが無い初回は
  6,676 トークンを読んで保存し（4.1秒・125MB）、以後は復元して読むのは1トークン（0.2秒）。**llama-server を
  `--slot-save-path <dir>` 付きで立てること**（無ければ読ませるだけになる）。
- **済んだ依頼は「人の発話 + AIの最終返答」へ畳む**（`AgentLoop._settle_history`）。依頼3つで新しく読んだ量は 376／194／599
  トークンで、ツール定義ぶんは使い回された。文脈あふれは `ProviderContextOverflow` で受け、古い依頼を半分捨ててやり直す
  （偽プロバイダの検査のみ、実モデルでは未確認）。
- **`timings` は往復ぶん足して `ai_result.usage` に載り**、パネルに「読み／再利用／書き」の1行が出る。
- 状態を AI へ渡す機能は、system ではなく依頼の末尾へ置く。ツールの顔ぶれと順序は会話の途中で変えない。

## 往復回数の実測（課題集）

`python tools/llm_tasks.py` で測る（板と柱の2ボディの文書に9件の依頼。本物の `AgentLoop` と道具で回し、**成否は文書の状態で
判定する**）。Gemma 4 12B Q4_0・`--temp 0.6 --top-p 0.95 --top-k 20`・思考の予算 512・各課題3回（2026-10-04）。Qwen3.8-27B では未測定。

| 版 | 成功 | 往復 | 読 | 書 | 秒 |
|---|---|---|---|---|---|
| 変更前 | 15/27 | 81.0 | 37,287 | 5,031 | 162 |
| 述語の書き方を `set_selection` の説明に載せる | 27/27 | 42.3 | 13,107 | 2,827 | 83 |
| ＋文書と選択を発話の末尾に添える（不採用） | 27/27 | 30.7 | 10,967 | 4,446 | 121 |
| ＋文書と選択を先に呼んだ結果として履歴に置く、断るときに直し方を返す（現行） | 26/27 | 26.3 | 9,664 | 1,241 | 40 |

- **変更前は選択を使う課題が全滅**: 述語の書き方がツールの説明に無く、1つのボディへ絞るキー（`body`）は `describe_predicates` にも
  載っておらず、`body_id` と書いた絞り込みは黙って捨てられて全ボディが選ばれていた。
- **状態を発話に添えると往復は減るが思考が伸びて遅くなる。** 「モデルが `describe_document` / `get_selection` を呼んで結果が返った」
  形で置くと書く量も減る（ツール結果の直後はほとんど考えずに続きを書く）。**効き方はモデルのテンプレート次第**なので別モデルでは
  測り直す。
- **反復抑制（`--dry-multiplier 0.8`）は ID の写しを壊す**: 12桁の ID を1文字落として `not_found` になる失敗が DRY ありで27試行中
  16件、なしで0件。
- **この課題集では思考は成功率を上げなかった**（思考なしで 27/27・26/27）。書く量は半分以下になる。
- 残る失敗した呼び出しは、寸法を言わない依頼を `dimension_not_given` で止める3件（狙いどおり）だけ。「箱を作る」は3回に1回、押し出しの
  結果が判定を外した（呼び出しは全部成功。原因は未調査）。
- `where` を省いた述語（「全部の辺」のつもり）は不正のまま（`tests/test_predicates.py` が固定する契約）。断るときに `"where": []` と書くよう返す。

## 「止まる」規律はプロンプトではなく実装で守る

- 以前の `agent_instructions()` は「曖昧・探索的な依頼なら止めて尋ねる」と明記していたが、**Ornith-9B は守れなかった**（「角が尖ってて
  危ないから、いい感じに処理しといて」に R1.5mm を自分で決めて `fillet` まで適用）。**このモデルは「能力の限界」では止まれるが
  「権限の限界」（やっていいか分からない）では止まれない** —— 9B クラスに「やらない判断」を期待するのは分が悪い。
- 線引き: **プロンプトで頼んでよいのは「間違えても直せること」だけ。undo でしか戻せない副作用が絡む規律は実装で止める。**
- 実装は `Param.dimension`（`catalog.py`）＋ `AgentLoop._dimensions_nobody_asked_for`（`agent/loop.py`）。止めたときの失敗コードは
  `dimension_not_given`（アプリ内AIの経路だけの語。`MCP.md`「実装のメモ」に載せ、`tests/test_doc_code_agreement.py` が一致を見る）。
  実機: 曖昧な依頼3回は適用 0/3、寸法を明示した依頼は 3/3 完走で誤発火なし。
- 散文の規範（`agent_instructions()`）が骨抜きにされていないことを文字列検査で守る試みは、QA が2ラウンド続けて素通り経路を見つけて
  打ち切った（列挙していない言い回しの矛盾は常に書き足せる）。今の `agent_instructions()` は「選択で止めるか verb まで進めるかは
  依頼の文面から AI が判断する」だけを言い（本人の決定）、検査は「固定の規則の言い回しが戻っていないこと」と「選択操作の名前が
  載っていること」だけを見る（`tests/test_agent_loop.py`）。

## MCP verb の設計原則

- **形は選択から、数値は引数から**（規則は [../MCP.md](../MCP.md) 冒頭が正）。参照の検査を MCP 層に二重で書かなくて済み、
  「述語または明示的な参照で与えられる」が `set_selection` の1箇所に集まる。
  **フィレット1回が選択→適用の2呼び出しになる代償は設計の主張であって欠陥ではない**（交互操作の一巡）。
- **公開ツールの顔ぶれの契約は `tests/test_doc_code_agreement.py`（`MCP.md` の表 ↔ `tools/list`）の一致検査だけに置く。** 同じ主張を
  別のテストや smoke へ複製すると、増減のたびに片方の更新を忘れて必ず食い違う。

## 落とし穴

- **未知の引数はプロトコルエラー**: `McpServer._call_tool` はツール本体の前に `catalog.check_arguments` でスキーマ突合し、未知キーは
  JSON-RPC のトップレベル `error`（-32602）で返す。`tests/test_mcp_verbs.py` の `call_error()`（`isError` 封筒を期待）では拾えず、
  `request()` を直接呼んで `response["error"]["code"]` を見る。**アプリ内AIの経路（`DocumentTools.call`）にも同じ検査がかかり、
  こちらは `invalid_argument` の封筒**（引数名つき）。かけていなかった頃は `radius: "12"` が1文字ずつ読まれて辺2本に半径1と2が付いた。
  任意引数の `null` も型違い（省略はキーごと落とす）。
- **MCP 起点の変更は `applied` を付けずに全接続へ配信される**（`duocad/net/ws.py` `_on_core_change`）。`applied.verb` で分岐する画面の
  挙動を実機で検査するときは、MCP ではなく本物の DOM 操作で起こす（[SMOKE_TESTING.md](SMOKE_TESTING.md)）。
- **操作ログから外した状態は、楽観ロックの版にも自分の指紋を足さないと黙って検出されなくなる**（可視性をログから外した時点で
  「AI が考えている間に人がボディを隠した」が版に現れなくなり、可視性の指紋を足して塞いだ。`DocumentTools.current_seq` は3つ組）。
  状態から導いている版（`body_revision`）は壊れず、経路（ログ）から導いている版だけが壊れる。
- **`run_coroutine_threadsafe(...).result()` をイベントループ自身のスレッドから呼ぶと必ず固まる。** `ToolsOnLoop._run_on_loop` は同じ
  スレッドなら直接呼ぶ（`net/tools_on_loop.py`）。CPU ほぼ0のまま止まったら「遅い」ではなくデッドロックを疑う。
- **AI パネルの条件付きレンダリングは DOM を消すが状態は消さない**: エンドポイント欄を `{#if}` で隠しても `baseUrlDraft` は送られ、
  サーバの防御に当たって画面操作だけでは戻れなくなった。対処は**プロバイダを切り替えた時点で打ちかけを捨てる**（`AiPanel.svelte`）。
