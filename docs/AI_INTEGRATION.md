# duocad — AI統合（アプリ内AI・MCP・ローカルLLM）

**読むとき**: アプリ内 AI パネル・`duocad/agent/`・MCP 経路の方向を変えるとき、ローカル LLM の
能力や待ち時間を見積もるとき。仕組みの正は README §1・§4 と [../MCP.md](../MCP.md)、契約は
`tests/test_agent_*.py` / `tests/test_mcp*.py`。

## ローカル LLM の実測（duocad の実ツールで）

- **Qwen3.8-27B-Q3_K_M**（llama-server・`-c 16384`）: `PC_case_feet.step`（5面6辺）で `import_step` →
  `describe_predicates` を教えずに自発的に呼ぶ → 「全部の辺」を選ぶ述語が無い問題を `length_gt: 0` で回避し
  `describe_shape` の `edge_count=6` と突き合わせて自分で検算 → `set_selection` →
  `fillet(radius=1)`。全7ターン 170秒、プロンプト 4,005→5,789 トークン。**ツール定義29個だけで 3,626 トークン
  （10,716文字）を毎ターン占める。**
- **Ornith-1.5-9B**（Q4_K_M・RTX 5060 Ti・67 tok/s）: 「XYにスケッチ→原点に直径8mmの円→X20mm×4・Y15mm×3で
  配列」を5手で完走（直径→半径の変換も正しく、エラーゼロ・ID の捏造ゼロ）。40ボディ＋8スケッチ＋24パラメータ
  （約7,800字）から「kind=solid のうち体積最大」も正答。**9B でもエージェントの土台に足りる**（dGPU 無しの
  ラップトップへの移行余地）。
- **待ち時間の分散はほぼ全部が思考**（Ornith-9B・同一の4手目を seed 違いで8回ずつ）:

  | 条件 | 中央値 | 最悪 | 生成トークン | 誤り |
  |---|---|---|---|---|
  | 思考ON（現状） | 3.25s | 8.09s | 86〜518 | 1/8 |
  | 思考OFF | 1.56s | 1.66s | 98〜105 | 1/8 |
  | 思考OFF + `tool_choice:required` | 1.53s | 1.64s | 98〜105 | 1/8 |

  思考を切ると出力長がほぼ決定的になる（8回中7回が98トークンぴったり）。精度は3条件で差が出ず、**思考OFFに
  判断品質の代償があるとは言えない**（このタスクでは）。事故時の 7,468 トークン（1リクエスト120秒超）は観測
  レンジの14倍で、通常のばらつきの裾ではなく**縮退ループ**。サンプラは `repeat_penalty=1.0` `dry_multiplier=0.0`
  （llama-server 既定）で反復抑制が1つも入っていない。矛盾した指示で思考が膨らみ600秒返らなかった実測もある
  （README §4）。

## llama-server の機構の実測（プロンプトキャッシュ・中断・スロット保存）

`python tools/llm_probe.py` で測る（台本で固定した会話を、製品と同じ本文で送る）。**判定はトークン数で行う** ——
処理した数 `prompt_n` と再利用した数 `cache_n` は機種をまたいで同じになり、秒数はならない。2026-10-04、
llama.cpp b10549・Gemma 4 12B Q4_0・`--swa-full -c 10240`・RTX 5060 Ti。**ThinkPad の秒数は未測定**（同じ
プローブを向ければ同じ表が出る）。箇条書きは機構そのものの実測で、製品の対応は節の末尾。

- **固定プレフィックスは 6,676 トークン**（system 247 + ツール41個 6,429。Gemma のトークナイザ）。cold のたびに
  これを全部処理する。
- **往復ごとの再利用は `AgentLoop` の送り方で効く。** 2往復目以降の処理量は、前回のプロンプトから伸びた分と
  一致した（35〜362 トークン）。作り直した assistant の文は毎回処理し直すが小さく、思考の有無でも変わらない
  （思考なしで +4 トークン）。**思考で増えるのは生成側**（1往復 19〜269 トークン。思考なしは 9〜99）。
- **ウォームアップは効く。** system + tools + `"."` を `max_tokens: 1` で先に投げると、最初の依頼の処理量が
  6,686 → 16 トークンになる。
- **キャッシュが外れる条件**（7,227 トークンの会話へ1依頼足したときの処理量。何も変えなければ 203）:

  | 変えたもの | 処理量 | `--cache-reuse 256` 付き |
  |---|---|---|
  | ツールの順序（末尾2個を入れ替え） | 824 | 824 |
  | ツールの順序（先頭2個を入れ替え） | 7,174 | 7,174 |
  | ツールを1個外す（末尾） | 748 | 203 |
  | ツールを1個外す（先頭） | 6,978 | 203 |
  | 状態を system に入れて毎回書き換える | 7,236 | 7,236 |
  | 状態を各依頼の末尾に付ける | 268 | 268 |
  | 別の会話が割り込む（スロット1本） | 7,407 | 7,407 |

  ツール定義は system の直後（先頭から約240トークン）に入るので、**そこより前を触ると全部処理し直す**。
  `--cache-reuse` が救うのは**消えた分を詰める場合だけ**で、書き換えと挿入は救わない。
- **スロットを2本にしても割り込みは防げなかった**（`-np 2 -kvu`）。短い別会話はテンプレート冒頭が一致するだけで
  類似度 0.214（既定の閾値 0.10）になり、会話のスロットへ入って 7,227 トークンを上書きした。逆に類似度が閾値を
  下回る大きな依頼は別スロットへ回り、元のスロットは purge された（`-kvu` の共有 KV）。
- **履歴の切り詰め方で総処理量が倍変わる**（18依頼、6依頼を超えたら落とす）: 切らない 10,306 ／ 毎回1依頼ずつ
  滑らせる 21,191 ／ 半分まとめて落とす 12,447。`--cache-reuse 256` 付きなら3方式とも 10,306。**切らないと
  `-c` を超えた時点で HTTP 400（`exceed_context_size_error`）になる** —— サーバは黙って詰めない。
- **非ストリーミングは、接続を閉じても生成が止まらない。** 1,500 トークン（29.8秒）の生成を3秒で閉じると、
  止まるまで 26.9秒（＝最後まで生成）。非ストリーミングで待つ側の待ち時間切れも同じ（26.8秒）。ストリーミングは閉じて
  0.22秒で止まる。**待ち時間切れや中断のあともスロットが塞がり、次の依頼がその後ろで待つ。**
- **スロット保存は再起動をまたいで効く**（`--slot-save-path` ＋ `POST /slots/0?action=save|restore`）。6,676
  トークンで 119.5MB（KV q4_0）、保存 119ms・復元 94ms、復元後の最初の依頼の処理量は 16。
- **`timings` は非ストリーミングの応答と、ストリーミングの最終チャンクの両方に載る**（`cache_n` / `prompt_n` /
  `prompt_ms` / `predicted_n` / `predicted_ms`）。
- **モデルの型で変わるのは「途中で食い違ったとき」だけ。** スライディングウィンドウ注意を持つモデル（Gemma）は
  `--swa-full` なしだと、食い違った時点でキャッシュが全部外れる（末尾2個の入れ替え 824 → 7,413、末尾1個を外す
  748 → 7,379、滑らせる切り詰め 21,191 → 25,234）。末尾への追記・ウォームアップ・往復ごとの再利用は同じに効く。

**製品の対応**（実モデルでの確認は上と同じ構成、2026-10-04）:

- **ストリーミングで受け、打ち切りで接続を閉じる**（`StreamingTransport`）。生成の最中に中断した場合も、合計時間の
  上限で切れた場合も、サーバは 0.2秒で止まった。
- **ウォームアップとスロット復元**（画面が繋がると `ai_prepare` → `OpenAICompatProvider.prepare`）。スロット
  ファイルが無い初回は 6,676 トークンを読んで保存し（4.1秒・125MB）、スロットを消したあとは復元して読むのは
  1トークン（0.2秒）。**llama-server を `--slot-save-path <dir>` 付きで立てること**（無ければ読ませるだけになる）。
- **済んだ依頼は「人の発話 + AIの最終返答」へ畳む**（`AgentLoop._settle_history`）。依頼を3つ続けたときに新しく
  読んだ量は 376／194／599 トークン（往復 2／2／4 回の合計）で、ツール定義ぶんは毎回使い回された。文脈あふれは
  `ProviderContextOverflow` で受け、古い依頼を半分捨ててやり直す（こちらは偽プロバイダの検査だけで、実モデルでは
  未確認）。
- **`timings` は往復ぶん足して `ai_result.usage` に載り**、パネルに「読み／再利用／書き」の1行が出る。
- 状態を AI へ渡す機能を足すときは、system ではなく依頼の末尾へ置く。ツールの顔ぶれと順序は会話の途中で変えない。

## 往復回数の実測（課題集）

`python tools/llm_tasks.py` で測る（板と柱の2ボディの文書に9件の依頼。本物の `AgentLoop` と本物の道具で回し、
**成否は文書の状態で判定する**）。往復・読んだ量・書いた量はどれも回数とトークン数なので機種をまたいで比べられる。
2026-10-04、Gemma 4 12B Q4_0・`--temp 0.6 --top-p 0.95 --top-k 20`・思考の予算 512・各課題3回。数値は9課題それぞれの
平均を足したもの（秒は RTX 5060 Ti）。**Qwen3.8-27B では未測定。**

| 版 | 成功 | 往復 | 読 | 書 | 秒 | 思考なしの 往復 / 書 / 秒 |
|---|---|---|---|---|---|---|
| 変更前 | 15/27 | 81.0 | 37,287 | 5,031 | 162 | — |
| 述語の書き方を `set_selection` の説明に載せる | 27/27 | 42.3 | 13,107 | 2,827 | 83 | 39.0 / 1,210 / 42 |
| ＋文書と選択を**発話の末尾に添える**（不採用） | 27/27 | 30.7 | 10,967 | 4,446 | 121 | 30.3 / 1,072 / 37 |
| ＋文書と選択を**先に呼んだ結果として履歴に置く**、断るときに直し方を返す（現行） | 26/27 | 26.3 | 9,664 | 1,241 | 40 | 25.0 / 910 / 32 |

- **変更前は、選択を使う課題が全滅していた**（上面を選ぶ・辺を丸める・箱を作る・続きの依頼がどれも12往復の上限まで
  `set_selection` に失敗し続ける）。述語の書き方がツールの説明に無く、1つのボディへ絞るキー（`body`）は
  `describe_predicates` にも載っておらず、`body_id` と書いた絞り込みは黙って捨てられて全ボディが選ばれていた。
- **状態を発話に添えると、往復は減るが思考が伸びて遅くなる。** 同じ内容を「モデルが `describe_document` /
  `get_selection` を呼んで結果が返った」形で置くと、往復が減ったうえで書く量も減った（ツール結果の直後は、モデルが
  ほとんど考えずに続きを書く）。**この効き方はモデルのテンプレート次第**なので、別のモデルでは測り直すこと。
- **反復抑制（`--dry-multiplier 0.8`）は ID の写しを壊す。** 12桁の ID を1文字落として `not_found` になる失敗が、
  DRY ありでは27試行中 16 件（`add_rectangle` 3・`set_visible` 13。同じ誤った ID を12回繰り返した試行もある）、
  DRY なしでは 0 件。DRY は既出の並びをもう一度書くことを罰するので、ID を正確に写す仕事と両立しない。
- **この課題集では、思考は成功率を上げなかった**（思考なしで 27/27・26/27）。書く量は思考ありの半分以下になる。
- 残っている失敗した呼び出しは、寸法を言わない依頼を `dimension_not_given` で止める3件（狙いどおりの拒否）だけ。
  「箱を作る」は3回に1回、押し出しの結果が判定を外した（呼び出しは全部成功。原因は未調査）。
- `where` を省いた述語（「全部の辺」のつもり）は不正のままにしてある（`tests/test_predicates.py` が固定している
  契約）。断るときに `"where": []` と書くよう返す。

## 「止まる」規律はプロンプトではなく実装で守る

- 以前の `agent_instructions()` は「曖昧・探索的な依頼なら止めて尋ねる」「迷ったら止める側に倒す」
  と明記していたが、**Ornith-9B は守れなかった**。「角が尖ってて危ないから、いい感じに処理しといて」に対し
  R1.5mm を自分で決めて `fillet` まで適用した。**このモデルは「能力の限界」（述語が無くて選べない）では止まれるが
  「権限の限界」（やっていいか分からない）では止まれない** —— 「進める」方向への一貫した偏りで、9B クラスに
  「やらない判断」を期待するのは分が悪い。
- 線引き: **プロンプトで頼んでよいのは「間違えても直せること」だけ。undo でしか戻せない副作用が絡む規律は
  実装で止める。** 文章は守られたか後から検証できないが、コードは検査で固定できる。
- 実装は `Param.dimension`（`catalog.py`）＋ `AgentLoop._dimensions_nobody_asked_for`（`agent/loop.py`）。
  止めたときの失敗コードは `dimension_not_given`（アプリ内AIの経路だけの語。`MCP.md`「実装のメモ」の
  語彙に載せてあり、`tests/test_doc_code_agreement.py` が `agent/loop.py` も読んで一致を見る）。
  実機: 曖昧な依頼3回は適用 **0/3**（1回はガードが fillet を阻止、2回は打ち切り）、寸法を明示した依頼は
  **3/3** 完走で誤発火なし。
- 散文の規範（`agent_instructions()`）が骨抜きにされていないことを文字列検査で守る試みは、QA が2ラウンド続けて
  素通り経路を見つけて打ち切った（列挙していない言い回しの矛盾は常に書き足せる）。原本の docstring の
  「この文を書き換える人へ」が最後の防波堤。今の `agent_instructions()` は「選択で止めるか verb まで進めるかは
  依頼の文面から AI が判断する」だけを言い、固定の規則を持たない（本人の決定）。検査は「固定の規則の言い回しが
  戻っていないこと」と「選択操作の名前が載っていること」だけを見る（`tests/test_agent_loop.py`）。

## MCP verb の設計原則

- **形は選択から、数値は引数から**（`fillet(radius)` であって `fillet(edges, radius)` ではない。面・辺・領域を
  引数で受ける verb は無い）。効き目は2つ: 参照の
  検査を MCP 層に二重で書かなくて済む／「述語または明示的な参照で与えられる」が `set_selection` の1箇所に
  集まる。**フィレット1回が選択→適用の2呼び出しになる代償は設計の主張であって欠陥ではない**（交互操作の
  一巡そのもの）。選択に出所（AIの提案か人の確定か）の区別は無く、人もAIも同じ操作で付け外しする
  （人: クリック＝`toggle_selection` / `modify_selection` / `clear_selection`、AI: 同じ3つ＋述語を書ける
  `set_selection`。`tests/test_mcp_selection.py` が両者の集合の一致を固定する）。
- **公開ツールの顔ぶれの契約は `tests/test_doc_code_agreement.py`（`MCP.md` の表 ↔ `tools/list`）の一致検査だけに置く**（部分集合では
  なく一致）。同じ主張を別のテストファイルや実機 smoke スクリプトへ複製すると、増減のたびに片方の更新を忘れて
  必ず食い違う。

## 落とし穴（実装・検査で踏んだもの）

- **未知の引数はプロトコルエラー**: `McpServer._call_tool` はツール本体を呼ぶ前に `_check_arguments` で
  スキーマ突合し、未知キーは JSON-RPC のトップレベル `error`（-32602）で返す。`tests/test_mcp_verbs.py` の
  `call_error()`（`isError` 封筒を期待）では拾えず、`request()` を直接呼んで `response["error"]["code"]` を見る。
  **アプリ内AIの経路（`DocumentTools.call`）にも同じ検査がかかり、こちらは `invalid_argument` の封筒**
  （引数名つき）で返る。かけていなかった頃は `radius: "12"` が1文字ずつ読まれて辺2本に半径1と2が付いた。
  任意引数の `null` も型違い（省略はキーごと落とす。MCP と同じ）。
- **MCP 起点の変更は `applied` を付けずに全接続へ配信される**（`duocad/net/ws.py` `_on_core_change`）。
  `applied.verb` で分岐する画面の挙動を実機で検査するときは、MCP からではなく本物の DOM 操作で起こす
  （[SMOKE_TESTING.md](SMOKE_TESTING.md)）。
- **操作ログから外した状態は、楽観ロックの版にも自分の指紋を足さないと黙って検出されなくなる。** 可視性を
  ログから外した時点で「AI が考えている間に人がボディを隠した」が版に一切現れなくなり、可視性の指紋を足して
  塞いだ（`DocumentTools.current_seq` は3つ組）。状態から導いている版（`body_revision`）は壊れず、経路（ログ）
  から導いている版だけが壊れる。
- **`run_coroutine_threadsafe(...).result()` をイベントループ自身のスレッドから呼ぶと必ず固まる。**
  `ToolsOnLoop._run_on_loop` は同じスレッドなら直接呼ぶ（`net/tools_on_loop.py`）。楽観ロックで毎ターン
  `current_seq()` を呼ぶようにした瞬間に `tests/test_agent_ws.py` の1本で顕在化し、pytest が CPU ほぼ0のまま
  数分止まった —— **プロセスが生きているのに CPU が動かないなら「遅い」ではなくデッドロックを疑う**。
- **AI パネルの条件付きレンダリングは DOM を消すが状態は消さない。** エンドポイント欄を `{#if}` で隠しても
  `baseUrlDraft` は送られ、サーバの正しい防御に当たって画面操作だけでは戻れなくなった。対処は送信時に落とすの
  ではなく**プロバイダを切り替えた時点で打ちかけを捨てる**（`AiPanel.svelte`）。
