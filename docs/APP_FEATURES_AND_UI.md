# duocad — UI機能・画面設計・viewport/CSSの落とし穴

**いつ読むか**: UIの機能追加・見た目の方針決定・viewport(3D画面)やパネルのバグ調査をするとき。

## 1. UI設計方針

- **「その瞬間に要るものだけ出す」**(2026-08-27・本人制定)。出し分けは3段: ①明確に必要なものは出す(通常モードのフィレット等) ②明確に不要なものは出さない(スケッチモードのフィレット等) ③どちらでもないものは認知負荷を上げない配置にするか開閉可能にする(保存関連エリア・ブラウザ等)。**「モード」が出し分けの主軸**で、不要側では無効化ではなく画面から消す。この方針に基づき「右サイドバーにスケッチ専用エリアが常時出ているのは違反」と判定した。
- **常設の指標(数・状態の札)を置かない**(2026-08-27・本人)。ヘッダの札4つを一度に外した際の言い分: 実物を見れば分かるものは札にしない(部品数など)/ 人の判断に使わない数は出さない(操作数など)/ 札で補わないと伝わらない見え方は見え方自体を直す(プレビュー表示の要不要) / 状態は常時光らせず人の手が要る瞬間にだけ言う(接続状態は送信失敗時にトーストで出す)。
- **接続失敗トーストは連続3回で1回だけ**(2026-08-23決定)。WebSocket(`ws://127.0.0.1:8765`)の再接続失敗を毎回トーストに出さず、`web/src/session.ts` の `CONNECT_FAILURE_NOTICE_AT` で連続3回到達時のみ1枚出し、以後は繋がるまで黙る。`WebSocket.onerror` から直接トーストを出す経路は廃止。理由: 一度も繋がっていない間は「開いていたものが切れた」という落差が生まれないため、`App.svelte`の`onStatus`が持つ落差判定だけでは無音になる。背景: サーバ起動前にタブを開きっぱなしにして「WebSocketのエラー」表示が15回連続した事故から判明。回数で切ったのは時間では切れないため。
- **FilesPanel/SelectionPanelの裁定**(本人裁定2026-08-23、一部2026-08-26撤回)。1) FilesPanelを右サイドバーから上部バーへ統合する案は**2026-08-26に撤回**、左サイドバー(`.data-panel`)への復元が決定(理由の明言なし)。2) SelectionPanel(選択パネル)は**丸ごと削除**。理由: viewportのハイライトで選択中のものが分かるため。代替: 「外す」→viewport内で該当部分をクリック、「全解除」→viewport内の空クリック(`App.svelte`の`onPick`で対応済み)、「承認する」(AI提案のcommit_selection)→明示的承認不要、そのまま操作するかAIに指示すればよい。3) **前提条件**: 頂点(vertex)はpick・highlightどちらも不可(バックエンドに頂点座標を返すクエリが無い、`mcp_server.py`に既知の未実装と明記)。SelectionPanel削除で頂点選択が人間から見えなくなるため、頂点のpick/highlightをバックエンドのクエリ新設からフルスタックで実装してから削除する、と裁定(実装順を逆にしない)。
- **画面フォントはPlemolJP Console同梱固定**(2026-08-23決定)。OS依存フォント(Consolas/Cascadia Mono/Meiryo)から、PlemolJP Console(v3.1.0、SIL OFL 1.1)の同梱・固定へ切替。Cica・HackGen Console・PlemolJP Console・UDEV Gothicの4候補を実機dev serverでプレビューして選定。ユーザーは「今後変わるかもしれないが、いったんこれで」と明言(暫定固定)。実装: `duocad/web/src/styles.css`の`@font-face`(`--font`トークン先頭、旧フォントはフォールバックとして残置)。フォント実体は`duocad/web/public/fonts/plemoljp/`(woff2、ライセンス文同梱)。
- **デバッグ表示3つを本体へ移設**(判断2026-09-05・本人、実施2026-09-06)。発端: 「デバッグ表示3点を開発フラグで本体に組み込んだ方がスマート」という本人発言。`probe_topopt/`(実験場)から本体へURLパラメータで移す。

  | フラグ | 出るもの |
  |---|---|
  | `?debug=space` | 塊(設計空間)のボクセルを薄く重ねる |
  | `?debug=anchors` | 拘束/荷重に割り当たった格子節点を色分けした球で表示 |
  | `?voxel=1` | 平滑化する前のボクセル(結果メッシュは表示だけ隠す) |

  条件: **ビルドで落とさない**(本人指示。落とすと利用者環境の問題を調べられなくなる)、**フラグ無しの画面は1ピクセルも変わらない**ことを不変条件にする、**移植先ではデモ題材に固定しない**(本人の完了条件)。根拠: probeは合成題材しか表示できないが、`?debug=space`が要るのは実物の部品で変な答えが出たときであり、そのときprobeは無力。「移す」際に満たすべきは「同じ絵が出ること」ではなく「元の道具の制限を持ってこないこと」。

## 2. 機能追加(verb)

- **mirror系verbを2つ追加**(事実・2026-09-06)。`mirror_sketch_entities`(確定選択のスケッチ図形を既存の線分1本を軸に鏡映複製)、`mirror_body`(確定選択の面/辺/頂点が属するボディを、XY/XZ/YZの3平面(原点通過)または既存ソリッドの平面な面1枚を鏡映面として鏡映複製)。どちらも**常に複製を作る**(in-place反転は無い)。実装は2段階: ①verb本体・catalog登録・MCP経路(taskbox `20260906-1100`。この時点で「既存の線分/面を鏡映基準に選ぶ」経路はUIに開けず、MCP専用のまま意図的に未決。3平面(`base_plane`)側だけUIまで通した) ②既存の線分/面をUIから選べるようにする経路(taskbox `20260906-1500`)。MCP・UI両経路から使える。
- **円弧の鏡映は始点・終点を入れ替えてから角度を映す**(実測事実・2026-09-06、`duocad/sketch.py::_mirror_arc`)。「中心+半径+`start_deg`/`end_deg`(反時計回り掃引)」の円弧表現で、軸(点A・単位方向u)に対する鏡映を実装する際、回転と同じ発想で両角度を独立に鏡映すると掃引方向の符号が壊れる(`new_end - new_start = -(end - start)`となり規約と矛盾)。正しい式: `axis_angle = atan2(u.y, u.x)`、`new_start_deg = 2*axis_angle - end_deg`、`new_end_deg = 2*axis_angle - start_deg`(=始点終点を入れ替えてから映す)。中心点は通常の点の鏡映式でよい。回転(向き保存)は`start_deg += angle`/`end_deg += angle`でよく、この非対称(回転は不要・鏡映は入れ替えが要る)が実装時に見落としやすい。`tests/test_mirror_verbs.py::test_mirroring_an_arc_keeps_its_sweep_and_flips_its_position`で確認済み。
- **数値入力欄が数式を受け付ける**(2026-09-06)。対象: コマンド引数欄・STL偏差・形状最適化の最小部材幅。実装: `web/src/expression.ts`の再帰下降パーサ(`eval`/`Function`は不使用)。ユーザーが決めたこと: 三角関数の引数は「度」(`sin(30)`は0.5、逆三角の戻り値も度。ラジアンや「度既定+ラジアン版別名」の選択肢もあったが度を選択)。関数セットは四則・単項マイナス・括弧・`sqrt`・`sin`/`cos`/`tan`に加え`pi`・`asin`/`acos`/`atan`/`atan2`・`^`(べき乗)・`abs`まで。**`hypot`・`min`・`max`・`round`・`floor`・`ceil`は明示的に除外**、`log`/`exp`/剰余も不採用。実装側の判断: 末尾のゴミを拒否(`Number.parseFloat('50mm')`が50を返すような挙動を式評価では理由付きで拒む)、入力はNFKC正規化(全角IME対策)、関数名の大小文字は区別しない。**文書パラメータの参照(`width/2`等の変数)は未実装**(`set_parameter`はMCP専用でUI側にパラメータ欄が無く、「式を保存して再評価する」という別件になるため次に伸ばすなら要検討)。

## 3. viewport/canvasの落とし穴

- **同一canvasの第2パス描画もクリックを吸う**(運用知見・2026-09-03、ビューキューブ実装で実測)。既存の`clickable(x,y)`判定(`document.elementFromPoint(...) === renderer.domElement`)は「別DOM要素の重なり」を前提にしていたが、ビューキューブのように別DOM要素を使わず同一canvasへ`setViewport`/`setScissor`で第2パス描画する実装では、その画素も`elementFromPoint`は変わらずcanvasを返す。結果、本来キューブが吸うはずのクリックがモデルのピック側へ素通りする。対応: `clickable(x,y)`の入口を1つに保ったまま、`elementFromPoint`判定の前に矩形の明示的な除外(`insideCubeRect(x,y)`)を追加(`web/src/viewport.ts`)。これにより`project*`系(`project`/`projectEdge`/`projectBasePlane`/`projectRegion`等)が自動的にキューブの矩形を候補から除外するようになった。教訓: 「クリックを吸う」原因はDOM要素の重なりだけでなく、同一canvasの複数パス描画(第2ビューポート)も同じ症状を起こす。単一のchoke pointを持つ設計なら、新種のオーバーレイが増えても条件追加だけで済む。
- **`projectPoint`はzクリップしか見ずxyクリップしない**(事実・2026-09-11)。`web/src/viewport.ts`の`projectPoint(point)`は`THREE.Vector3.project(camera)`の結果の`z`(奥行き)が`[-1,1]`内かだけを見て`null`を返す。`x`/`y`がどれだけ画面外にはみ出していても計算結果をそのまま返すため、戻り値が非nullでも実際には画面外座標であることがある。`smoke-grid-scale.mjs`はこれを踏まえ`at.x >= 0 && at.x <= rect.width && ...`を自前でチェック済み。新しいsmokeスクリプトで`projectPoint`の戻り値の有無だけで「画面に映った」と判定すると、実際には画面外座標へ`page.mouse.move`してしまい、`pointermove`がcanvasに届かず「動いたはずなのに反映されない」という原因不明の失敗になる(`20260910-1615`タスクで実際に踏み、`document.elementFromPoint`で確認)。教訓: `projectPoint`を「画面に映っているか」の判定に使うときは、必ず呼び出し側で`.viewport`の`getBoundingClientRect()`と突き合わせてx/yの範囲チェックを行う。
- **`projectFace`は視点で数十px跳ぶので測定点に使わない**(事実+修正実例・2026-08-28)。`window.__duocad.projectFace(bodyId, faceIndex)`は「最初にピックできた三角形の重心」を返す実装であり、面の代表点ではない。カメラを動かすと勝ち残る三角形が入れ替わり、同じ面でも画面座標が数十px跳ぶ。実測(画角45→60変更前後、同一面): `projectFace`は27.3px移動、面の重心(`face.centroid`)をそのまま射影すると3.5px移動。視点・画角比較の測定点には`projectPoint(face.centroid)`を使うべき。**実例**: ツールバーのボタン3つ削減でビューポート高さが変わっただけで、`acceptance.mjs`の「画角45→60度で中心付近の面は6px以内」検査が中心最寄りの面入れ替わりにより9.6px移動へ変化し3回連続で赤くなった。コアの`fitDistance`は無変更で原因は測定側。`faceScreenPoints()`を`projectPoint(face.centroid)`へ差し替えて解消(2026-08-28)。副産物: 比較に使える共通面が8〜12面から59面へ増加。検出力は`fitDistance`を一時的に画角非依存に壊して再ビルドし、修正後の検査が正しく赤くなることを確認してから復元して確認済み。
- **`projectRegion`は三角形が画面上で小さすぎると永遠にnullを返す**(落とし穴+修正・2026-09-11実測)。`web/src/viewport.ts`の`projectRegion`(領域を画面座標へ射影。三角形1つにつき4点=重心+3頂点寄せを試すサンプリング方式)は、対象の三角形が画面上で小さすぎるとどのサンプル点も当たらず恒久的にnullを返す。ズームで三角形を大きくすれば直る(実機確認: デフォルトズームで`smoke-svg.mjs`のSVG(60×40mm)の「丘」領域が該当し、何十秒ポーリングしてもnullのまま。手動ズームインで即座に成功)。**根本原因**: `lookAtSketch`(`#sketch-look`)はスケッチへ入るときの1回しか自動で呼ばれない(`App.svelte`のモード遷移effect)。`smoke-svg.mjs`は空のスケッチへ入った直後にSVGを取り込むため、そのときのフレーミングは既定倍率のままで、取り込みで図形が増えても再フレームされない。**修正**: `smoke-svg.mjs`の取り込み直後に`page.click('#sketch-look')`(+400ms待ち)を追加して`lookAtSketch`を明示的に呼び直すことで解決(3回連続PASS確認)。`viewport.ts`の`projectRegion`自体には手を入れていない。**発見の経緯**: 無関係な作業(長方形以外の交点対応・線分中点スナップ実装)中に`smoke-svg.mjs`が120秒タイムアウトするようになり、最初は円弧`start_deg`/`end_deg`異常値による無限ループを疑ったが直らず、`git stash push -- <触った5ファイル>`(パス指定)で変更を全部外して手動再現したところ変更前でも同じ不具合と判明(無関係な既存不具合)。
- **projectionヘルパのループ内DOM読み取りは13倍遅い**(解決済み・2026-09-04、duocad `49e69b4`)。`web/src/viewport.ts`の`projectRaw()`(世界座標→画面画素)が呼ばれるたびに`size()`(`container.clientWidth`/`clientHeight`)を読んでいた。この関数は矩形選択の包含判定`geometryInside()`の最内ループから頂点ごとに呼ばれる。実測(83,084頂点の矩形選択1回): 現状32.1ms → `size()`をループ外へ巻き上げのみで2.5ms(13倍速)→ 戻り値の`{x,y}`オブジェクトも作らないと2.3ms。遅さの92%はDOMプロパティ読み取りで、算術ではない。解決策: `projectRaw`/`geometryInside`/`objectInside`を`width`/`height`引数受け取り型に変更、`collectInBox`の入口で`size()`を1回だけ読んで下流へ渡す(モジュール側にキャッシュはしない。リサイズで寸法が変わるため)。実測(740x748ビューポート・27部品2835面・全体を囲む矩形、`collectInBox`全体): 中央値38.3ms→3.9ms。一般則: 画面座標へ変換するヘルパは寸法を引数で受け取るか、呼ぶ側がループの外で1回だけ読むこと。
- **深いズームのコストはface単位のカリングで削る**(実測・2026-08-30〜31)。前段: ズーム連動の可変解像度を「文書全体で1つの目標精度」にすると深いズームで破綻。実測(RTX 5060 Ti・headless Chrome・1280x860・PCケース27部品2835面): 全体表示は目標偏差0.390mmで三角形65,707・往復2.8秒、20段ズームインは目標偏差0.033mmで三角形394,975・往復5.6秒、30段ズームインは目標偏差0.010mmで三角形1,180,763・往復14.5秒(単一イベントループなのでこの間セッション全体が応答しない)。**対処**: Body単位ではなくface単位で「細かく測るか」を決め、判定は視錐台への包含とバックフェイスの2つのみ(オクルージョンは実装しないと本人決定)。実測(`web/scripts/smoke-face-culling.mjs`): 30段ズームインでカリング切り=三角形1,180,763・16.3秒、カリング入り=三角形205,534・4.0秒(**5.7分の1の三角形・4分の1の時間**)。全体表示は三角形が完全に同値。効いている仕掛け3つ(どれか1つ欠けても効果消滅): ①粗い側の精度をズームに依存させない(モデル全体が512画素に収まる引きの粗さ) ②版とキャッシュの鍵を「実効レシピ」にする(全面を粗く測るBodyの鍵に細かい側の値を入れない) ③判定は画面側(カメラを持つブラウザが判定し、サーバはface添字に従うだけ。プロトコルは`set_view_resolution`に`focus`を1つ足しただけ)。**注意点**: バックフェイスは閉じた立体の平面faceにだけ使う(開いたシェルでは裏を向いた面が実際に見え、曲面は「中央の法線」が面全体を代表しない)。**残る代償**: 細かい面と粗い面が曲線の辺を共有していると辺の折れ線が別々に作られ境目に隙間が開きうる(境目は画面の縁とシルエットなので未対応のまま)。
- **球フィットの距離式は非球体・対角外視点でFOVにより見かけが縮む**(実測・2026-09-04〜05、ビューキューブ)。透視カメラを「半径Rの球が視錐台にちょうど収まる距離」の式`distance = R / sin(fov/2)`で置くと球そのものは全FOVで見かけの大きさが不変になるが、対象が非球体(立方体等)でカメラの向きが対称軸(対角線)に正確一致していない場合、FOVを上げるほど見かけが縮む。実測: 対角±22°ずれた向き(`HOME_VIEW_OFFSET=(1,-1,0.6)`)でFOV30→90にすると、バウンディングボックス一辺が144px中118px→96pxへ約18%線形縮小。原因: 至近距離+広FOVでは、物体上の一番近い頂点がカメラ光軸から外れているほど「見かけの大きさへの寄与」が非直感的に縮む(sin/tanの非線形性と対角ズレの相互作用)。カメラが対称軸に正確一致していれば縮みは起きない(実際に対角(1,1,1)方向へスナップさせて確認、FOV90でも遜色ない見かけを保った)。実務上の指針: この式を「FOV間で見かけを揃える」目的に使うなら、①対象が球に近い/対称軸ちょうどから見ることを前提にするか、②緩い許容(縮小率0.6〜1程度)で妥協する。duocad本編カメラの`fitDistance`も同じ式を使うが、実コンテンツ(STEPインポート等)は概ね球に近い分布なので実害は出にくい。

## 4. CSSの落とし穴

- **`flex column-reverse + justify-content:flex-end`は溢れた分にスクロール不能**(実測・2026-08-14、タスクEのQA)。操作履歴パネルの`.list`(`overflow:auto; flex-direction:column-reverse; justify-content:flex-end`)をheadless Edgeで実測: 30行入れても`scrollHeight === clientHeight`(68px==68px)となり溢れた26行はスクロール到達不能(scrollTopは0固定)、見えるのはDOM末尾(視覚上の上端)の約4行のみ。一般則: スクロール容器でmain-start側に溢れたコンテンツは「到達不能オーバーフロー」になる。「新しい行を上に出したい」ならCSSで反転せず配列を逆順にして通常の`column`で描くのが正しい。検査上の教訓: 実ブラウザのsmokeテストでもテキスト/data属性だけ読んでいると見えない(この件は`smoke-files.mjs`がPASSのまま素通り)。一覧UIは「先頭以外の行に実際に到達できるか」まで見る必要がある。
- **`flex-shrink`が縦flexのリストを次の区分に溢れさせる**(落とし穴・2026-08-26実測、ブラウザパネル)。`overflow-y: auto`を持つ縦flex容器内で区分を並べたとき、区分に`min-height: 0`を置くと既定の`flex-shrink: 1`に下限が無くなり区分が中身より低く潰れる。潰れても中身は隠れない(`overflow: visible`のまま)ため、リストが枠外へ溢れて次の区分の見出しに重なる。実測(モデル29件+スケッチの2区分): 区分1は中身740pxなのに444pxまで潰れ、リストは区分の底(678px)を突き抜けて974pxまで伸び、679〜706pxにある「スケッチ」見出しと重なる。スクロールバーは出るため一見スクロールできているように見えて厄介。見分け方: 各区分の`getBoundingClientRect().height`と`scrollHeight`を並べ、食い違えば潰れている。直し方: 区分を`flex: 0 0 auto`にして中身なりの高さを保たせ、スクロールは容器が1つだけ持つ(区分ごとの独立スクロールは小さい区分まで一緒に潰れる。実測で「スケッチ」区分は見出し28px+2pxまで潰れた)。
- **素の`input`セレクタのwidth/text-alignがcheckbox/radio/rangeにも当たる**(落とし穴・2026-09-05実測)。`input { width: 7em; text-align: right; ... }`のように素の要素セレクタで打ち込み欄の作法を書くと`type=checkbox`/`radio`/`range`にも適用される。チェックボックスはwidthを無視しないため7emの箱になり、flexコンテナ内では`flex-shrink`既定値1で潰れ、潰れ方は同じ行の他要素の長さで決まるため同じ列でも行ごとに幅が変わる。実測(ボディ一覧27行): `PC_case_20251122_1`(11面)はチェックボックス幅33.4px・名前左端x=305、`_7`(6面)は39.2px/311、`_8`(181面)は27.6px/299、`_27`(90面)は26.5px/298 — 名前の左端が13px幅で左右にがたつく。打ち消す側が増えたら規則の置き場所が違う(duocadでは設定ダイアログが`#settings-ortho`/`#settings-fov`で個別に`width: auto`と打ち消しており、2箇所で打ち消していた時点でグローバル側を型で絞るのが正しかった)。正しい形は型を除外すること:
  ```css
  input[type='checkbox'], input[type='radio'], input[type='range'] {
    width: auto; flex: 0 0 auto; padding: 0; background: none; border: none;
    accent-color: var(--accent); /* 指定しないとブラウザ既定の青が出る */
  }
  ```
  `accent-color`も同じ話で、指定しないとダークテーマ中でチェックボックスだけブラウザ既定の青になり、27個並ぶと配色から外れた青の縦列ができる。
