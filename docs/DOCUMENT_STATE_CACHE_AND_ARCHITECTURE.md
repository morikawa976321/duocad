# duocad — サーバ状態・キャッシュ・verb実行・MCP/AI連携・開発運用

**いつ読むか**: サーバ側の状態管理・キャッシュ・差分配信・verb実行の一貫性を触るとき、MCP/AIループ(LLM連携)を扱うとき、開発環境やドキュメント構成を整えるとき。

## 1. 状態・キャッシュ設計

- **`state_meta()`の体積再計算問題**(【解消済み2026-08-26】)。`Server._push`は配信のたび`Session.state_meta()`を呼び、その中の`body_meta()`が全ボディぶん`query.volume()`(OCCT `BRepGProp.VolumeProperties_s`)を毎回計算していた(体積にキャッシュが無かった)。実測(`PC_case_20251122.step` 4.6MB/27ソリッド→参照+編集用で54ボディ): `state_meta()`1回=693ms(うち体積~0.97s/54体、1体平均13ms・最大83ms)、「全部非表示」(可視27体を1体ずつ`set_visible`→27回配信)はサーバ側だけで19.1秒(内訳: state_meta 18.72s / delta 0.33s / verb本体 0.00s / json 0.00s)。**原因は「配る量」と「作る値段」の取り違え**——`_push`のdocstringは出力が数KBであることを根拠に安いと見なしていたが、高いのは転送量ではなくOCCTの積分。同じ`Session`の`geometry()`は形状の同一性でキャッシュしていたのに、その規律が体積にだけ適用されていなかった。**解消**: `body_meta`に`geometry()`と同じ規律(形状の同一性`id`で判定)の`_volume_cache`を追加(コミット`56049eb`)。実測: `state_meta()`1回 693ms→1.1ms、「全非表示」27コマンド合計(サーバ側) 16.99s→0.03s。**税は全配信にかかる**: 選択変更・undo/redo・あらゆるverbの確定が同じ693msを払っていた。**倍率の出どころはUI側**: 「全非表示」(`App.svelte`の`hideAllParts`)は一括コマンドを持たず可視ボディぶん`set_visible`をWSへ1本ずつ撃つため、サーバは1コマンドごとに`_push`し**N回の配信×全N体の体積=O(N^2)回のOCC積分**になっていた(フロント側の差分更新は1メッセージO(1)なのでフロントは原因ではない)。なお`volume`はブラウザ表示には出ないがMCPの`_body_summary`が同じ`body_meta`を使うため、配信から落とすとMCPとUIの面が分裂する——キャッシュのほうが両方に効く。
- **`id(None)`を変更検出の鍵にすると版が二度と上がらない**(2026-09-05)。`DocumentView.body_revision()`は`key = (id(body.shape), body.visible, レシピ)`の変化で版を上げ、差分配信は「版が同じ=変わっていない」と判断する設計。ここに**`shape`が常に`None`である種別**(三角形メッシュのボディ。形は別フィールド`Body.mesh`が持つ)を足すと、`id(None)`は常に同じ値なのでその種別の版が二度と上がらなくなる。可視性が鍵に入っていたおかげで表示切替だけは動き、「形が変わったのに画面が更新されない」だけが残る気づきにくい壊れ方。**一般化**: 「同一性で変更を測る」鍵は、その値が入るすべての経路で非Noneであることに依存する。形の持ち方を1つ増やしたら鍵にもそのフィールドを足す(duocadでは`id(body.mesh)`を追加)。同じ形の依存がキャッシュの当たり判定(`cached[0] is body.shape`)にもあるため、**版とキャッシュは必ず同時に見ること**(片方だけ直すと版は上がるのに古いキャッシュが返る/逆になる)。検査は「表示を切り替えたら版が変わる」ではなく「新しい種別のボディで版が動くこと」を直接見る。
- **版を「経路」ではなく「状態」から導く**(2026-08-11、M3.5)。部品ごとの差分送信の契約を書いた際、同じ形の穴が経路を変えて3ラウンド連続でQAに指摘された: ①非表示が届かない(「版は形状が変わったときだけ増える」としたため`set_visible(False)`は差分で`unchanged`扱い) ②再表示が届かない(①を「可視性でも版を上げる」と直したがテストが非表示方向しか縛らず「隠したときだけ上げる」実装でも緑) ③undo/redoが届かない(②を直しても版をverb適用時だけ上げる実装だと`_undo_set_visible`経路で版が動かない)。3つとも同じ設計の帰結——イベントを数え上げる形にしている限りundo・redo・再生・将来のverbのぶんを必ず取りこぼす。**対処**: 版を状態から導く(`(形状オブジェクトの同一性, visible)`の組が変わったら版が変わる)。**一般化**: 変更通知系の仕組み(差分送信・キャッシュ無効化・再描画トリガ)は「変更イベントを列挙する設計」と「現在の状態から導出する設計」の2択であり、前者は列挙漏れが恒常的な不具合源になる。
- **非表示のボディはfillet/chamfer/extrudeの対象にできない**(承認・現状維持、2026-08-20)。`fillet`/`chamfer`/`extrude`(領域)は対象ボディを選択の外(既定=アクティブボディ)から解決するため、確定選択が生きたまま対象ボディだけ隠されると黙って変更していた。同日これを塞ぎ、対象ボディが非表示なら拒否するよう変更。副作用として「ボディを隠したまま意図的に材料を足す」操作ができなくなるが、本人が承認し現状維持と決定。根拠: 「可視性は見た目の設定ではなく、何を指せるかの定義」という既存原則の延長(PCケース27部品でピック失敗率63%の原因が「手前の部品が奥の面を隠していた」ことだった件)。**先に緩めない**方針——煩わしければ`join`モードだけ後から緩める余地はあるが、静かな事故のほうが高くつくため。
- **bodyIdはインポートごとにランダムで内容から導かれない**(事実・2026-09-04実測)。同じ`PC_case_20251122.step`(27部品)を完全に別々の2回のサーバ起動で読み込み、矩形選択(`collectInBox`)の結果を比較したところ、選ばれた面の総数は一致(2835件・27ボディ)したが`bodyId`の文字列(`body-01a54896757b`等)は2回の起動で1件も一致しなかった。**影響**: 「同じ矩形で選択結果が変わらない」ような回帰確認を別々のサーバ起動をまたいでbodyId込みで完全一致させようとすると必ず偽の差分になる。突き合わせにはbodyIdを無視し、ボディごとの面インデックス集合(ソート済み配列等)をキーにグルーピングし集合同士の一致で比べる必要がある。**同一サーバ起動内**(1回importして前後比較)ならbodyIdは変わらないのでこのグルーピングは不要——起動をまたぐ比較のときだけ注意。

## 2. サーバアーキテクチャ・通信

- **`server.py`(2170行)は2段構えで分割し、再輸出だけの薄い入口として残す**(2026-08-27承認、コード調査`docs/CODE_SURVEY_ACTIONS.md`項目3.1)。第1段=クラス境界だけで割る(振る舞いゼロ変更)、第2段=`Session`から配信側(`state`/`delta`/版/キャッシュ)を`DocumentView`として切り出す(taskbox `20260827-2330`/`-2331`)。**`duocad/server.py`自体は再輸出だけの薄い入口として残す**——`duocad.server`から名前を取っているのは`mcp_server.py`が6箇所・テストが17本で計23箇所あり、入口を残せば呼び出し側を1行も触らず分割できる(移動と呼び出し側変更を同時にやらないための措置)。verbの薄いラッパ16本の1本化(項目3.2)と`_dispatch`の表駆動化(項目3.4)は分割に混ぜない(ファイル分割で解決する問題ではなく、混ぜると後で作り直しになる)。第2段が主に狙うのは行数ではなく**キャッシュの寿命管理が1クラスに閉じること**(当時は`_replace_document`の`.clear()`5連発・`preview()`の変則・剪定がバラバラの場所にあった)。
- **同時編集を前提にしない**(2026-08-27本人決定、理由の明言なし)。コード調査の項目1.4に対する二択(「排他制御を入れる」か「単一ブラウザ前提を明記してクローズ」)で後者を選択。技術的内容: WebSocketは複数接続へ状態を配信する作りだが`Session`全体を守る排他は無い。**形状が壊れることはない**(個々のverbの適用は同期処理でawaitを挟まない)。乱れうるのは順序で、ある接続が`_push`のawaitで待っている間に別接続の操作が先に処理される(単一イベントループ内のコマンド単位のインターリーブ)。結果として操作ログや選択状態が意図と違う順序で反映されうる。前提を変えるなら`duocad/server.py`の`Server`へ排他を入れるのが先。明記箇所: `duocad/server.py`の`Server`クラスdocstringと`README.md`§5「前提にしないこと」(commit `9fac6b7`)。
- **4xxで断るときもリクエスト本文は読み切ってから返す**(運用知見・2026-08-26実測)。duocadの`/mcp`(MCPのHTTPトランスポート)で、`Origin`ヘッダを見て403を返す検査を本文を読まずに`send_error`して接続を閉じる形にしたところ、まだ本文を書いているクライアント側で`ConnectionAbortedError`になった(Windows。受信バッファに未読が残ったまま閉じるとRSTが飛ぶ)。症状がややこしいのは、拒否そのものは効いているのにクライアントからは「通信が壊れた」に見えること。対処は「検査より先に本文を読み切る」(上限で頭打ちにしてあれば読み切って安全。上限超過だけは読み捨てずに接続を閉じる)。**併せて得た検査の教訓**: このバグは1回目のpytestで緑・2回目で赤という形で出た(競合)。散発的な赤はまず実装の競合を疑う(マシン負荷で振れるものとは別物)。
- **エラーコードを分ける基準は「名前が嘘をつくか」**(設計判断・2026-08-20)。フィレット(辺を食う)を呼んだのに確定選択が面3枚、という種別の食い違いを既存の`selection_empty`で返すか専用コードを足すかで、同日の実装は「どちらも次の一手が『辺を選び直す』で同じ」として一度は分けなかった(文面だけ強化)。**本人の判断で覆し**、`selection_kind_mismatch`を7語彙目として新設。理由は語彙の数ではなく名前が嘘をつくこと——面3枚が入っている選択に`selection_empty`(選択が空)と名乗ると読む人を混乱させる。副次的利点: アプリ層が種別違いにだけ反応する余地(「この面の辺を選ぶ」等)をコードで分岐できる。**一般化**: 「次の一手が同じだから同じコードでよい」は消費者がLLMだけなら成り立つが、コードは人も画面も読むため名前が状態を正しく述べているかを先に見る。**実装の型**: 新しい例外を既存例外の派生にすると既存の`pytest.raises(既存型)`を壊さず増やせるが、判定順を入れ替えると派生が基底に吸われて新コードが死ぬため両方向をテストの対で固定する。

## 3. verb実行の設計原則

- **plan-then-writeは同じオブジェクトへの複数計画を併合しないと最後だけが勝つ**(設計知見・2026-08-30実測、`move_sketch_entities`)。「途中で落ちても半分だけ適用された状態を残さない」ため全対象の結果を先に作って検査してから書き込む形にしたが、各対象の計画が「現在の値を読む→自分の分だけ変える→**全鍵ぶんの完全な辞書**を返す」だったため、同じオブジェクトに複数の対象が掛かると後の書き込みが前の書き込みを丸ごと打ち消した(線分の両端`p0`と`p1`を選んで動かすと片方しか動かない——`p1`の計画が持つ`x0,y0`は「動かす前の値」なので先に書いた`p0`の移動が消える)。**例外もログも出ない**。ウィンドウ選択で図形をまるごと囲えば普通に踏む経路だった。**一般化**: plan-then-writeを採るなら計画の単位は「書き込みの単位(オブジェクト)」であって「入力の単位(対象)」ではない。同じオブジェクトに掛かる入力は書く前に1つの計画へ積み上げること。**検査の書き方**: 「2つ動かして両方動く」テストが要る(1つだけ動かすテストは何本あっても通り、座標比較テストでも片方が偶然同じ値になる配置では素通りする)。
- **サーバへは参照、幽霊(プレビュー)へは解決した数値**(設計判断・2026-09-06、回転軸ピック)。画面で既存図形(辺・頂点・スケッチ点)を指して引数にするUIで「参照のまま送るか座標へ潰して送るか」という分岐に対し、`move_body(mode="rotate")`の回転軸で採ったのは非対称の形: **サーバへは参照のまま送る**(`axis_edge = {body, index}`)——辺が乗る直線を厳密に出せるのはB-repを持つコアだけで、座標へ潰すと同じ解決規則がブラウザにもう1つ増える。**確定前のプレビュー(幽霊)には数値へ解決してから渡す**——プレビュー層は「解決済みの数値でしか描かない」を不変条件にしており、そこへ参照を渡すと「省略時の既定」もその層で解決したくなり、既定(重心・代表点の平均)はコアにしか無い規則なので写した瞬間に幽霊と確定結果が別の場所に出る壊れ方の芽になる。**解決に使ってよいのは「コアが既に配った数値」だけ**(テセレーションの折れ線・配信済みの頂点座標・解決済みの`params`)。近似(メッシュからの体積重心等)は使わず、使わずに描かないほうが正しい。この形は「向きの符号が両者で一致しているか」を測る責任を生む——`kernel.edge_axis`の向きと配られた折れ線の始点→終点が一致することを、立方体・穴あき・フィレット・合体・L字の直線辺83本で実測して確認(どちらも同じ`BRepAdaptor_Curve`の媒介変数の順に並ぶため)。ここが逆だと幽霊だけが逆回りに見える。

- **調査レポートの所見は正しくても対応案は実在しない場所を指しうる**(2026-08-27)。taskboxのタスクを起こす際、所見(正しかった): `Session`の`_geometry_cache`/`_edge_cache`/`_vertex_cache`/`_volume_cache`から消えたBodyのエントリが落ちない。対応案(取れなかった): 「Bodyを削除する処理(該当verbの実装箇所)でpopする」——実際には`duocad/verbs/`に削除verbは無く、`remove_body`を呼ぶのは押し出しと編集用コピーのundoハンドラで、verbs層はSessionのキャッシュを知らない(層として知るべきでもない)。正しい形は生存集合での剪定で、同じリポジトリの`sketches_state()`に既に前例があった。**一般化**: レポートの「何が起きているか」と「どこを直すか」は検証の強度が違う。前者はコードを読めば裏が取れるが、後者は書き手が実装していない以上ただの提案であり、3段階レビューを通っても提案のまま。**タスクへ落とす前に対応案の側だけ現物で裏を取る**こと(その場所は実在するか・その層はその状態に触れるか・同じ問題を既に解いている前例が無いか)。

## 5. MCP・AIループ

- **LLM待ち時間の分散はほぼ全部が思考**(実測・2026-08-23、Ornith-1.5-9B Q4_K_M・RTX 5060 Ti・62 t/s、同一4手目相当の呼び出しをseedを変えて8回×3条件)。

  | 条件 | 中央値 | 最悪 | 生成トークン | 誤り |
  |---|---|---|---|---|
  | 現状(思考ON) | 3.25s | 8.09s | 86〜518 | 1/8 |
  | 思考OFF | 1.56s | 1.66s | 98〜105 | 1/8 |
  | 思考OFF+`tool_choice:required` | 1.53s | 1.64s | 98〜105 | 1/8 |

  思考を切ると出力長がほぼ決定的(8回中7回が98トークンぴったり)——分散の出どころは思考でありツール呼び出しそのものではない。精度は3条件とも誤り1/8で有意差なし(単発観測で思考OFFがverb選択を誤ったように見えたが8試行では差にならない)。**120秒の回はこの分布では説明できない**——思考ONでも最悪518トークンだが事故時の7,468トークンは観測レンジの14倍で、通常のばらつきの裾ではなく質的に別の事象(縮退ループ)。当時のサンプラは`repeat_penalty=1.0``dry_multiplier=0.0`で反復抑制が入っていなかった(llama-server既定のまま)。
- **Ornith-1.5-9Bはllama.cppでツール呼び出しが動作**(事実・2026-08-22実測)。モデルカードはvLLM/SGLangでのツールパースしか明記していなかったが、llama.cppでも動作を確認(ローカルLLM候補選定で最大の不確定要素だった)。環境: llama-server build 10549(commit `b2e5e9b28`)、CUDA13ビルド、ornith-ai/Ornith-1.5-9B-GGUF:Q4_K_M(5.63GB単一ファイル)、RTX 5060 Ti 16GB(`-ngl 99`で全層GPU、`-c 32768`、KVはf16)。**`--jinja`が必須**(無いとツール定義が渡らない)。実測(299トークン投入/87トークン生成): 生成68.2 tok/s、プリフィル1,314 tok/s(299トークンを227ms)。このプリフィル速度なら29ツール定義込みの数千トークンプロンプトでもTTFTは1-2秒に収まる見込み。確認事項: tool_callsが正しいname/argumentsで返る、reasoning_contentに思考が分離される、finish_reasonがtool_callsになる。1ツールでの成功であり、29ツールから紛らわしい対(フィレット/チャンファー等)を選び分けられるかは別途検証が必要。
- **模擬バックエンドで測った「モデルの欠陥」は模擬の欠陥だった**(運用知見・2026-08-22)。Ornith-1.5-9Bがduocadの29ツールを扱えるかを固定応答の模擬バックエンドで測り、2つの「欠陥」を観測してあやうく誤った改修を実装しかけた。①「存在しない図形IDを捏造する」——モデルは「ID形式を推測して試します」と述べたが、原因は模擬の`describe_document`が`sketches[].entities[]`を返していなかったこと(実物は最初から全図形の`entity_id`を返す)。②「6手を超える複合操作で破綻する」——模擬では14手かけて未完了だったが、実duocadに繋いだら同じ課題を5手で完走(捏造ゼロ・エラーゼロ)。模擬が状態変化を返さないためモデルは「まだ反映されていない」と正しく読んで確認ループに入っていた(空回りはモデルの判断としてはむしろ正しい)。**教訓**: 能力の測定に模擬を使ってよいのは模擬が実物と同じ情報を返すときだけ。省略した項目はそのままモデルの失点として現れる。エージェント評価では遅くても実物に繋ぐ方を選び、模擬で出た失敗は実物で再現するまでモデルの欠陥として記録しない。
- **モデルが守れない規律は文章で頼まずコードで止める**(判断・2026-08-23)。duocadの`agent_instructions()`には「曖昧・探索的な依頼なら`propose_selection`で止めて尋ねる」「迷ったら止める側に倒す」と明記していたが、**Ornith-1.5-9Bはこれを守れず**、「角が尖ってて危ないから、いい感じに処理しといて」に対し止まらずR1.5mmを自分で決めてfilletまで適用した。観察: このモデルは「能力の限界」では止まれるが「権限の限界」では止まれない(述語が無くて選べないときは正しく停止・報告したが「やっていいか分からない」は認識できず進んだ)。**対応**: 規律を実装へ移した(`Param.dimension`の印+ループ側のガード)。実機で曖昧な依頼3回のうち1回はガードがfilletを阻止、残り2回は合計時間の打ち切りで**適用0/3**。寸法を明示した依頼は3/3完走・誤発火なし。**線引きの原則**: プロンプトで頼んでよいのは「間違えても直せること」だけ。undoでしか戻せない副作用が絡む規律は実装で止める(文章は守られたか事後検証できないが、コードは検査で固定できる)。設計上の留意: ガードは例外にせず失敗の封筒で返す(モデルはそれを読んで提案側へ回れ、往復1回増えるだけで適用してしまった形をundoで戻すより安い)。判定は厳密照合にしない(「直径8mm」から`radius: 4`を導くのは正しい導出であり、値がそのまま本文にあることを求めると普通の依頼が通らなくなる。見るのは「人が量を与えたか」だけ)。
- **部分の上限をいくつ置いても合計時間は決まらない**(実測・2026-08-23)。エージェントループで出力上限(`max_tokens`)・1リクエストの待ち(`request_timeout`)・往復数(`max_turns`)の3つを締めても、人が待つ時間は決まらなかった(前2つは1リクエストしか縛らず`max_turns`は回数しか縛らないため、待ち時間はその掛け算)。実測: 1リクエストを1024トークン(最悪16.5秒)に抑えても、曖昧な依頼で`query`ツールを堂々巡りして12往復を使い切り合計88秒。**合計時間そのものに上限を置くしかない**——duocadでは`Limits.max_total_seconds`を追加。判定を往復の境目だけに置くと実効上限は「合計+1リクエスト」になる(実測: 上限30秒に対し35.2秒)。進行中のリクエストへ渡すタイムアウトも残り時間で頭を押さえてようやく30.0秒ちょうどに収まった。併せて、予算切れによる接続タイムアウトを「プロバイダの障害」として報告しないこと(原因はこちら側の予算であって相手ではない)。
