# 楕円 verb の設計

**状態: 実装済み**（2026-10-17、develop）。楕円・円の入力の数え方、吸着、保存形式の移行を疑うときに読む。

本人の依頼（原文）:

> スケッチ用の楕円verbを作成する。円の入力が縦横2つになったバージョンというイメージ。

## 決めたこと（2026-10-17 本人）

| 論点 | 決定 |
|---|---|
| 入力の数え方 | **縦横の直径で入れる。円も直径の入力に変える**（本人: 「そういえばFusionもそうだったし」） |
| 回転角 | **`angle` を持つ。既定 0**。度・反時計回り・スケッチの X 軸基準（長方形の `angle` と同じ数え方） |
| 縦と横が等しい楕円 | **許す**（真円になるだけ） |
| 画面の入力 | **3クリック**: 中心 → 1本目の軸の端 → 2本目の軸の長さ。数値欄は 縦・横・角度 |
| 楕円弧 | **作らない** |
| SVG 取り込み | **閉じた `<ellipse>` だけ新しい楕円図形にする**。楕円弧は今のベジエ近似のまま（[svg_import.py](../duocad/svg_import.py) 冒頭） |
| 選択・測定で見せるもの | **中心・縦・横・角度・周長** |
| 円の直径の範囲 | **API(MCP)と保存まで `diameter` にする**（AI が提示した2案のうち、本人は「画面の入力だけ直径」でなく全体を選んだ）。制作データ（`duocad-data/models`）も直してよい（本人） |
| 吸着と交点 | **楕円の線上への吸着・中心と軸の端4点・楕円と直線（長方形の辺を含む）の交点を入れる。楕円と円・円弧・楕円の交点は入れない**（本人） |

「縦横」は `angle` 方向の軸と、それに直交する軸を指す。どちらが長いかの意味は持たせない（長軸・短軸ではない）。

## カーネルの罠

**OCCT の `gp_Elips` は長半径 ≥ 短半径でないと作れない**（2026-10-17 実測: `(10,5)` と `(5,5)` は通り、`(5,10)` は `Standard_ConstructionError`）。
縦の方が長い楕円は、辺にするところ（`kernel_sketch.py`）で2つを入れ替え、軸を 90° 回して渡す。

**離心率0の `gp_Elips` を `BRepOffsetAPI_MakeOffset`（包み込み）に渡すと、例外にならず access violation でプロセスごと落ちる**（長半径と短半径の差が 5e-8 以下で再現。差が 1e-7 以上なら `GeomAbs_OffsetCurve` の `ValueError`）。縦横が等しい楕円を「許す」ので、差が 1e-6 mm 以下の楕円は辺を `gp_Circ`（円）にする。保存形式は楕円のまま。

**面に貼ったスケッチの枠は左手系でありうる。** 法線に `ax3.Direction()` を使うと楕円の角度が逆に出る（sol のレビューで発見。円弧も同じ原因で逆回りになっていた: 立方体6面のうち5面で四分円の領域が閉じなかった）。
円・円弧・楕円の軸は `_curve_axis` がスケッチの X×Y から作る。直した後も開発版 models と制作データの全ファイルが同じ形に再生された（2026-10-17）。

## 保存形式（version 3）

円の `params` は `cx` / `cy` / `diameter`。**version 2 のファイルは読むときに直径へ写す**（`duocad/oplog_upgrade.py`）。
キーの位置は変えない —— `register_all` はキーの順に `d<n>` を振るので、位置を動かすと以後の名前がずれる。
円が記録される操作は `add_circle`・`import_svg`・`envelope_regions`・`delete` / `delete_items` の退避で、どれも変換の対象。
`set_parameter` を含む version 2 のファイルは断る（その名前つきの値が円の半径かは再生しないと分からない。`set_parameter` は画面にも MCP にも出していない）。

ファイルを書き換えるのは `tools/upgrade_models.py <models フォルダ> --write`（元を `<名前>.json.v2.bak` に残す）。
**書き換えたファイルは古い duocad（安定版の更新前）では開けない**（「未知の保存形式 version 3」）。開くだけなら書き換えは要らず、次の自動保存で version 3 になる。

2026-10-17 の実測: 開発版 `models/` 17件と制作データ3件を、変更前のコードと変更後のコード（version 2 のまま読む経路）で再生し、
全ボディの体積が小数6桁まで一致した。名前つきの値で変わったのは円の値だけ（2倍）。

## 吸着と交点の作り（`web/src/entityKinds.ts`）

- 線上への吸着は楕円そのものの最近点に落とす（折れ線の上に落とすと、その点を端にした線分が楕円の内側で止まり、領域が割れない）。
  解き方は D. Eberly の二分法（最近点の条件を単調な1変数の式にして解く）。ニュートン法は極端に細い楕円を強く拡大すると
  反対側の根へ飛び（直径 20×0.002 で約20mm 先へ）、初期値に戻す守りでも最近点にならなかった（sol のレビューで2回指摘）。
  論文の変数 s のままだと長軸の近くの内側の点で s + 1 が桁落ちする（(3.2, 1e-18) で 0.15mm ずれ、1e-20 で 0 除算）ので、w = s + 1 で解き、解いた点をそのまま返す。
- 折れ線の分割数は4の倍数にし、軸の端4点が必ず頂点に来るようにする。
- 楕円と線分の交点は、楕円を単位円へ写す変換（線分は線分のまま写る）で線分と円の交点に帰着させる。厳密解。
- 2点目（1本目の軸の端）を待つ間は幽霊が出ない。幽霊は「待っている点が最後の1つ」のときだけ組む作りで、円弧と同じ。

## 周長

楕円の周長に閉じた式は無い。測定では OCCT に辺の長さを測らせる（近似式を自前で持たない）。
**辺の長さの既定の積分は粗い**（2026-10-17 実測。楕円の柱の辺で、`GCPnts_AbscissaPoint.Length_s` の既定も build123d の `Edge.length` も
直径 20×10 で +0.13%、直径 40×2 で +1.74%。ベジエの辺は 1e-5、円・直線は厳密）。画面の辺・`measure`・述語の `length_lt` / `length_gt`・楕円の周長は
すべて `kernel.edge_length`（許容差 1e-9。数値積分と 1e-11 まで一致）を通す。時間は細い楕円の辺1本で 0.04ms、ベジエで 0.004ms。
実モデル（制作データの966辺・459辺）では辺の長さ全体の時間は変わらなかった（直線と円は閉じた式で解かれる）。
