## 0. このツールは何か

> **Fusion360と同等以上にモダンでシンプルなUIに、自分が実際に使う手動操作と強力なAI操作を載せ、
> 両者が同じ選択集合を交互に触れるようにしたもの。**

差別化はUIでも機能数でもなく **交互操作**（AIが集合を提案 → 人が過不足を直す → AIが操作を適用）にある。
Fusion360にも既存のコードCADにも無い。

### v1の完成条件 — 2026-08-11 に再々定義（現行）

> **v1 = いま実装済みのverbすべてを、人間とAIの両方が満足に使える状態。**（2026-08-11 本人決定）

**「実物を再現する」から「両者が全verbを使える」へ変えた。** こちらの方がこの企画の主張そのもの
（§2.1 の交互操作）に一致し、verbごとに検査できる。実物の再現は目標ではなく、その帰結として通る。

#### 「満足に使える」の操作的定義（verbごとに判定する）

| 側 | 合格条件 |
|---|---|
| **人間** | UIだけで起動でき／引数をポインティングと数値入力で与えられ／**プレビュー**があり／**Escで中断**でき／**undoで戻る** |
| **AI** | MCPツールとして呼べ／引数を**述語**または明示的な参照で与えられ／**結果と失敗が構造化して返る** |
| **交互操作** | AIが選択を提案 → **UIに提案として表示される** → 人がクリックで直す → AIが読み直して適用できる |

## 2. アーキテクチャ

```
┌── AI（MCPクライアント）──┐        ┌── 人間（アプリ層 / ブラウザ）──┐
│  述語で引数を作る          │        │  ポインティングで引数を作る      │
└───────────┬──────────────┘        └──────────────┬─────────────────┘
            │ 呼ぶ / 読む                            │ コマンド ↓ ／ イベント ↑
            └────────────────┬───────────────────────┘
                             ▼
        ┌──────────── コア（Python・唯一の真実源）────────────┐
        │  文書（ボディ木・スケッチ）／ 選択集合 ／ 操作ログ ／ undo │
        │  ── verb層（純関数） f(文書, 選択, 引数) → 新しい文書 ──  │
        │      問い合わせ : build123d ラッパ（差し替え可能）         │
        │      操作      : OCP（OCCT）＋ 由来マップ回収            │
        └────────────────────────────────────────────────────┘
```

### 外してはいけない3つ

1. **AIの経路はアプリ層を通らない。** コアはUIが無くても機能的に完全であること。
   アプリ層にしか無い機能を作った瞬間、AIから使えなくなる。**これが層分けの唯一かつ最大の存在理由。**
2. **コマンドは下り、イベントは上り。** AIが選択を書き換えたらコアがイベントを発火し、
   アプリ層がハイライトを描き直す。この上り方向が無いと交互操作が成立しない。
3. **アプリ層が落ちて失われてよいのは、途中まで入力していたコマンドだけ。**
   文書・選択・操作ログ・undo履歴はすべてコア側。これが層の責務の判定テスト。

### verbの粒度

**verb ＝ ①undo1回で消える単位 ②操作ログ1行 ③MCP1呼び出し が一致する単位。**
食い違う切り方をしたら切り方が間違っている。UIの操作手順（スケッチ開始→面選択→中心→半径→確定）は
**1つのverbを組み立てる漏斗**であって、5つのverbではない。

## 3. データモデル

### 3.1 文書

```
Document
  units          : "mm"（固定）
  bodies         : [Body]
  active_body    : BodyId
  sketches       : [Sketch]
  parameters     : { name: number }      # 名前つきの寸法値
  log            : [Operation]           # これが正。形状は導出物
```

**操作ログが唯一の正であり、形状はそこから導出されるキャッシュ。**
開くときはログから再生する（再生経路が毎回検証されるという副作用がある）。
遅くなったら最終B-repをサイドカーに置き、**ログのハッシュで無効化**する。

### 3.2 ボディ（v1から複数持つ）

```
Body
  id      : BodyId
  name    : str
  kind    : "solid" | "reference"     # reference = 読み込んだSTEP・読み取り専用
  shape   : TopoDS_Shape              # 導出物
  visible : bool
```

**v1でUIは1ボディしか見せないが、データモデルはリストで作る。**
参照STEPを読み込む時点で既に複数ボディなので、選択の余地は無い。

事後追加が高くつくのは**選択が `body_id` を持つこと**（全verb・問い合わせ層・ピッキング・MCPスキーマに波及）。
ここだけ day 1 に払う。ボディ一覧のUIは後回しでよい。

### 3.3 スケッチと領域

```
Sketch
  id       : SketchId
  plane    : PlaneRef        # 基準平面 or 面への参照（← 壊れやすい参照。由来スロット対象）
  entities : [Entity]
  regions  : [Region]        # 導出物。BRepAlgoAPI_Splitter で計算

Entity  : Line | Circle | Rectangle   （各自が名前つきの数値パラメータを持つ）
Region  : { index, area }             # 図形の配置から計算される閉領域
```

**領域は描くものではなく計算されるもの。** 実測で成立を確認済み:
円(面積1256.637)を線分で分割 → 領域 826.215 + 430.422 = 1256.637（元と一致）、
大きい方だけを押し出すと体積＝面積×高さと一致。

**注意**: パラメータを編集すると領域が分裂・合体・消失しうる。押し出していた領域が消える壊れ方をする。
§6の「黙って通さない」規律の対象。

### 3.4 パラメトリック・プリミティブ（拘束ソルバは持たない）

| | 中身 | v1 |
|---|---|---|
| 拘束ソルバ | 図形**どうし**の関係を解く（この線とあの線は平行） | **持たない** |
| パラメトリック・プリミティブ | 各図形が**自分の数値**を持つ（長方形 at (x,y) 幅w 高さh） | **これで足りる** |

「数値を打って描く／あとで値を編集する」という実際の運用は、後者だけで完全にカバーできる。
**day 1の予防**: 打った数値を図形の座標に焼き込まず、**名前つきの値として別に持つ**。
これで拘束は将来「上に重ねる層」として追加できる。

### 3.5 選択集合（交互操作の中核）

```
Selection
  items  : [ShapeRef | RegionRef]
  origin : "user" | "proposed"      # AIの提案は見た目が違い、承認操作がある

ShapeRef  : { body: BodyId, kind: "face"|"edge"|"vertex", index: int, provenance: null }
RegionRef : { sketch: SketchId, index: int, provenance: null }
```

満たすべき5条件: **永続 ／ 双方向（AIが書ける）／ 種別を保持 ／ 差分編集可能 ／ 提案と確定を区別**。

**index は現時点の添字であって、保存はしてよいが再生時に信用してはならない**（§6）。
参照IDの書式は ocp_vscode の実証済み形式（`/Group/Solid/faces/faces_6`）を借りてよい。

### 3.6 操作ログ

```
Operation
  seq        : int
  verb       : str
  args       : { ... }                # 名前つきパラメータへの参照を含む
  selection  : [ShapeRef|RegionRef]   # 実行時に解決した参照
  provenance : null                   # ★ day 1 の空スロット（§6）
```

**保存形式は JSON。SQLiteは使わない。** 理由: ①gitに載って差分が読める ②AIが履歴を全部読める
③1モデル＝1ファイルでコピー・共有が普通のファイル操作で済む。規模は数百操作で問題にならない。
これは document 指向のアプリであってデータのアプリではない（Fusionが `.f3d` を保存するのと同じ）。

## 4. 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| カーネル | **OCCT（OCP経由）** | 由来マップ（`Modified`/`Generated`/`History`）が取れる唯一の経路 |
| 問い合わせ | **build123d をラッパとして** | `Solid(shape).edges().filter_by(Axis.Z)` が1行。**インタフェース越しに使い、差し替え可能に保つ** |
| テセレーション | **ocp_tessellate** | 既に検証環境に入っている |
| コア | **Python** | OCPもMCPもPython。ビルダ文脈（`BuildPart`）は使わず生の `TopoDS_Shape` を保持する |
| 通信 | **WebSocket** | コマンド下り／イベント上りの双方向 |
| 描画 | **three.js** | |
| frontend | **Svelte 5 + TypeScript** | §4.1 参照。**2026-08-10にReactから変更** |
| CSS | **バニラ（CSS変数）** | 部品が8個程度と少なく、CADのパネルは密度が高い。**Tailwindの既定値に寄せると「よくあるWebアプリの見た目」になり、CADツールがWebアプリに見えてはいけない** |

**frontendで守るべき唯一のルール**: **canvasはフレームワークの外に置く。**
three.jsが所有するコンテナを渡し、フレームワークは二度と再描画しない。ここを外すと状態更新のたびにWebGLが壊れる。

### 4.1 frontendフレームワークの選定（2026-08-10・Reactから変更）

**当初Reactを推したが、理由が「他プロジェクトと揃う」だけで弱かった。他プロジェクト（monocore等）はWebアプリで、
これはデスクトップ級のツールであり、揃える理由になっていない。本人の「Reactは過剰」という判断は正しい。**

**過剰である根拠は、我々自身のアーキテクチャにある。**
フレームワークが元を取るのはクライアント側の状態管理だが、§2で状態を全部コアに置いた。
frontendに残るのはコマンドの途中状態（何番目の引数を集めているか・プレビュー値）だけで、これは状態機械1個。

v1の画面部品は **8個程度**: ビューポート(canvas・枠外) ／ ツールバー ／ 数値入力 ／ 操作ログ一覧 ／
選択情報 ／ パラメータ一覧 ／ ダイアログ ／ ステータスバー。

| | 判定 |
|---|---|

### 4.2 長期保守と破壊的変更（2026-08-10 調査）

10年単位で使う道具なので、依存の churn を実際に調べた。

**Svelteコアの実績**: Svelte 3(2019-04・リアクティビティ全面書き換え) → 4(2023-06・軽微) →
**5(2024-10・runes導入)**。**2026-08時点で Svelte 6 は出ていない**（5が22ヶ月継続中）。
大きい書き換えは2019と2024の**約5年間隔**で、いずれも「旧版が動かなくなる」ではなく
「書き方が変わる」（Svelte 4のコンポーネントは legacy モードで動き、`sv migrate` の移行ツールがある）。

**重要な区別**: 2026年に観測される破壊的変更は **ほぼすべて SvelteKit 側**
（SvelteKit 3.0 / remote functions / form enhance のコールバック / アダプタ）。
SvelteKit は 1.0(2022-12)→2.0(2023-12)→3.0(2026) と**ほぼ年1回のメジャー**でマイナーでも壊す。
**本プロジェクトは SvelteKit を使わない**（ルーター・SSR・アダプタ・フォームが全て不要）ので、
年1回ではなく**5年周期の側に乗る**。

**このスタックで本当にリスクが高い依存の順位**（frontendフレームワークは最下位）:

| 順 | 依存 | リスク |
|---|---|---|
| 1 | **three.js** | **semverを持たずr番号でほぼ毎月リリース。非推奨APIを定期的に削除する。**10年ではSvelteよりはるかに壊れる |
| 2 | **OCP（cadquery-ocp）** | OCCT本体は30年の実績で安定だが、**Pythonバインディングは維持者が少なく冗長性が最も低い単一障害点** |
| 3 | build123d | 小規模。ただし問い合わせ層のインタフェース越しなので差し替え可能（§6の予防4） |
| 4 | Svelte | 5年周期・部品8個・legacy互換と移行ツールあり |

**保守の実態の予想**: ローカル専用ツールなので**上げなければ壊れない**。バージョンを固定すれば
静的ファイルは動き続け、ブラウザの後方互換は極めて強い。強制力になるのは「新機能が欲しい」だけ。
したがって実際のコストは「コードが壊れる」ではなく **イディオムのずれ** —
数年後にAIが書く「今風の書き方」が手元のコードと噛み合わなくなり、**AI支援の質が落ちる**形で来る。
対処は「最も標準的で漂流しないものを選ぶ(Lit/vanilla)」か「**書き換えが1日で済む規模に surface を保つ**」の2つで、
**部品8個なら後者で足りる**。

**したがって採る予防は3つ**（M1のタスクに明記済み）:

1. **SvelteKit を使わない**（Svelte + Vite のみ）
2. **`viewport.ts` を狭いインタフェースにし、three.js の型を外に漏らさない**
   （`load` / `onPick` / `highlight` / `resize` 程度）。最も churn の激しい依存を1ファイルに閉じる
3. **バージョンを固定し、動いているものを上げない**

## 5. API / MCP 仕様

**「AIがモデルを作る」ためのAPIではなく、「AIと人間が同じ選択集合を触る」ためのAPI。**

**対象集合の指定方法は1つしかない（2026-08-20）。** 面・辺・領域を引数で受けるverbの口は、
MCPにもWebSocketにも無い —— どちらもコアの**確定選択**から取る（`duocad/selection.py` の
`require_confirmed` / `require_edges`）。引数に残るのは数値・名前・パスだけである。
それまではWebSocket側だけが添字を引数で受けており、ブラウザがコアの選択を添字へ変換して
送り返していた（同じ変換がTSとPythonに2つあった）。Bodyは選択集合の項目ではないので、
`body_id`（どのBodyへ足す／から引くか、隠すBody、複製元）は引数のまま残る。

**選択（中心）**
- `get_selection()` → 種別付きの集合
- `propose_selection(predicate | refs)` → **提案**状態で書き込む
- `modify_selection(add=[], remove=[])` → 差分編集
- `commit_selection()` / `clear_selection()`
- 述語の例: `faces where normal·Z > 0.9` / `edges where parallel_to Z and length > 20`

**問い合わせ**
- `describe_document()` → ボディ・スケッチ・パラメータの一覧
- `describe_shape(body)` → 面・辺の数、境界箱、特徴の要約
- `measure(selection)` → 面積・長さ・法線・中心

**操作**
- `apply(verb, selection, args)` → §1のverbがそのまま入る
- `set_parameter(name, value)` → 名前つき寸法の変更
- `undo()` / `redo()` — 交互操作では必須（AIの結果を1手で捨てられること）

**入出力**
- `import_step_editable(path)` → **ソリッドごとに編集可能なボディ**として追加（通常はこちら。2026-08-15）
- `import_step(path)` → 参照ボディ（読み取り専用）としてだけ追加
- `export_step(path)` / `export_stl(path, deviation)`

> **ツール名は操作ログのverb名と同じ綴りにする**（2026-08-15に徹底）。AIは `describe_document` の
> ログを読んで次の一手を決めるので、綴りが違うと対応表を推測させることになる。読み込みのツールが
> 2つあるのはこの規律の帰結で、**1つのツールが引数で2つのverbを打ち分ける形は採らない**。

**同期の要件**
- 手動操作もAI操作も**同じ操作ログに積む**
- **AIの応答待ちでUIがブロックされないこと**（手動4ステップの速さを殺さない）
- **競合**: 人間がコマンドの引数収集中にAIが選択を書き換えた場合は、
  **コマンド開始時の選択をスナップショットして使う**（単一ユーザーなのでこれで足りる）

## 7. 実測で判明した落とし穴

| 落とし穴 | 実測した内容 | 対処 |
|---|---|---|
| **OCCTのフィレットは例外を投げずに失敗する** | 20mm立方体・全辺: r=10.0 → `IsDone()=False`（例外なし）／**r=10.5 → 成功**／r=30.0 → 失敗。**半径に対して単調ですらない** | verbのラッパで**毎回 `IsDone()` を確認**し、失敗したら操作ごと捨てて人に戻す |
| **面の添字は形状変更で壊れる** | 同じ面を追跡してフィレットをかけると **i=5 → 9**。ただし穴の径変更・穴の追加・ポケット・面取りでは動かない＝**散発的に静かに間違う** | 生の添字を保存・再利用しない。由来スロット（予防2） |

| **2つの型系の同一性は保たれる** | `==` / `hash` / `set` すべて同一視。`.wrapped` 往復でも維持 | 選択集合をbuild123dオブジェクトで持ってよい |
| **STEP往復は厳密〜ほぼ厳密**（**下の訂正を必ず読むこと**） | 26面・体積 23340.849375 → 書き出し62.1KB → 読み戻し **差 0.00e+00** | 参照部品の読み込みと成果物の書き出しの両方に使える |

> **【訂正・2026-08-10実測】「STEP往復は bit-exact」は言い過ぎだった。**
> 上の差 0.00e+00 は**26面の単純な形状**での値である。M0のテスト設計中に、より複雑な
> `shelf_attachment_GD.step`（56面・体積 91018.2223598035）で同じ検証をしたところ、
> **体積差は約 7.3e-11（相対 約8e-16 ＝ IEEE double の1ULP級）で、`==` による一致は成立しなかった**。
> 同じ入力で2回やっても同じ差が再現するのでノイズではなく、**再読込で面のパラメトリック表現や
> 走査順が変わり、`GProp_GProps` の数値積分の順序が変わる**ことに由来する。
> **したがって往復の検証は `==` ではなく相対許容差（`1e-6`）で行うこと。**
> 面数（`face_count`）は往復後も厳密一致でよい。詳細は engine `step-roundtrip-volume-not-bitexact`。
| **STLは近似** | 偏差 0.2mm→30.7KB ／ 0.05mm→47.2KB ／ 0.01mm→170.6KB | 偏差を設定可能にする |
