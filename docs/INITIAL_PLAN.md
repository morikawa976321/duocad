## 企画の前提

### 呼称

**「必要最低限の機能をもったミニマルなモデリングツール」**。
「機能削減版Fusion」は使わない — Fusionと呼ぶと履歴・スケッチ拘束・アセンブリが
自動的に期待値に入り、スコープが膨張するため。

### 手動操作は一級のモード

**手動操作それ自体が一級の操作モードである。** AIへの入力手段ではない。

決定的な観察（本人の言葉）:

> 特定の面の押し出しなどは選択→押し出しを選択→数値指定→Enterの4stepですぐおわる。
> これをいちいちAIに依頼するのはむしろ時間がかかる。

これは「AIが下手だから手動が速い」ではない。**指示の情報量に対してチャネルの帯域が合っていない**
という構造的な話であり、AIの性能が上がっても解消しない。したがって
「いずれAIが賢くなれば手動は要らなくなる」という前提を置いてはならない。

### 分業の原則

| 指示の性質 | 最速のチャネル | 理由 |
|---|---|---|
| **「どれ」**を特定する（この面、この辺） | **ポインティング（手動）** | 位置情報の伝達に言語は極端に非効率 |
| **「条件を満たす全部」**（全辺、上面の外周） | **言語（AI）** | 述語1つ vs Nクリック |
| **形状そのものが未定**（大まかな形を出す） | **言語（AI）** | 手続きが長く探索的 |
| **手続きが面倒だが機械的**（一括フィレット等） | **言語（AI）** | 人間側の作業量だけが大きい |

**帰結**: 分担の境界は「作業の種類」ではなく「**対象集合をどう指定するか**」で決まる。
そしてこの境界は固定ではない — **選択集合を受け渡せるなら、1つの操作の中で分担できる。**

### 交互操作の成立条件

```
AI: 述語で候補集合を作る  →  ユーザー: 過不足をクリックで修正  →  AI: 操作を適用
```

差別化はUIでも機能数でもなく **この交互操作**にある。Fusion360にも既存のコードCADにも無い。

**成立条件は1つだけ: 選択集合が第一級の共有オブジェクトであること。** 具体的には:

1. **永続**（操作の合間に消えない。UIの一時状態ではない）
2. **双方向**（AIが読める／**AIが書ける**／ユーザーが読める／ユーザーが書ける）
3. **種別を保持**（面/辺/頂点を区別する）
4. **差分編集可能**（追加・除去。作り直しではなく）
5. **出所を区別**（AIの**提案**か、ユーザーが**確定**したものか）

データ構造上の写しは §3.5。

### Fusion360の位置づけ

| 軸 | 評価 |
|---|---|
| 手動操作 | **完璧。基準線であり下回ってはならない** |
| UI | モダン・シンプル。**これも基準線**（FreeCADはここで却下された） |
| AI操作 | 弱い。実用上「パラメータ指定でプリミティブを出す」程度 |
| 継続性 | **常に不安**（教育ライセンス失効・クラウド束縛・大企業依存・Linux非対応） |

Fusion360のAPI自体はフィーチャ生成まで含む本格的なもので「プリミティブだけ」ではない。
ただしLLMのループ前提の設計ではなく継続性の不安も変わらないので、離脱の判断は動かない。
離脱の理由6点はすべて**プラットフォーム層**。直接操作への不満はゼロで、**そこが基準線**である。

**作るべきもの**:

> **Fusion360と同等以上にモダンでシンプルなUIに、
> 「自分が実際に使う手動操作」と「強力なAI操作」を載せ、
> 両者が同じ選択集合を交互に触れるようにしたもの。**

**FreeCADは却下済み**（UIがクラシカルすぎる）。UIの様式が足切り条件として働く。
コードは全領域AIが書く。本人は「AIの解説があれば理解できる」水準。

## 0. このツールは何か

上記「作るべきもの」の定義どおり。

### 「使える」の基準

> **すべての実装済みverbを、人間とAIの両方が満足に使える状態にする。**
> これがこの企画の主張（交互操作）そのものであり、verbごとに検査できる。

#### 「満足に使える」の操作的定義（verbごとに判定する）

| 側 | 合格条件 |
|---|---|
| **人間** | UIだけで起動でき／引数をポインティングと数値入力で与えられ／**プレビュー**があり／**Escで中断**でき／**undoで戻る** |
| **AI** | MCPツールとして呼べ／引数を**述語**または明示的な参照で与えられ／**結果と失敗が構造化して返る** |
| **交互操作** | AIが選択を提案 → **UIに提案として表示される** → 人がクリックで直す → AIが読み直して適用できる |

#### 到達状況

| 操作 | コア | 人間（UI） | AI（MCP） |
|---|---|---|---|
| `sketch_create` | ✅ | **✅** | **✅** |
| `add_line` / `add_circle` / `add_rectangle` / `add_arc` | ✅ | **✅** | **✅** |
| `extrude`（領域・結合/切取/新規ボディ） | ✅ | **✅** | **✅** |
| `extrude_face` | ✅ | **✅** | **✅** |
| `fillet` / `chamfer` | ✅ | **✅** | **✅** |
| `pattern_rectangular` / `pattern_circular` | ✅ | **✅** | **✅** |
| `move_sketch_entities` / `move_body` | ✅ | **✅** | **✅** |
| `set_parameter` | ✅ | — | **✅** |
| `set_visible` | ✅ | **✅** | **✅** |
| `import_step` / `export_step` / `export_stl` | ✅ | **✅** | **✅** |
| `undo` / `redo` | ✅ | **✅** | **✅** |
| `set_preserve_bodies` / `set_exclude_bodies`（形状最適化・保持/除外ソリッド） | ✅ | **✅** | **✅** |
| `set_fixtures` / `set_loads`（形状最適化・拘束面/荷重面） | ✅ | **✅** | **✅** |

**形状最適化の4つは「プレビュー」を持たない**（`preview: 'none'`。`set_visible` と同じ位置づけ）
——集合代入するだけで形そのものは1つも変わらないので、投機実行して測る対象が無い。
確定は即座に効き、undoで戻る（`20260831-0108-duocad-optimize-mode-verbs-backend` /
`20260831-0109-duocad-optimize-mode-frontend`）。

**`set_parameter` の人間側は「作らない」と決めた欄である**（2026-08-30本人決定）。
右サイドバーのスケッチパラメータパネル（数値入力欄）を廃止し、位置の打ち直しを
**3Dの直接選択 + `move_sketch_entities` / `move_body`** へ置き換えた。半径・幅高さ・角度の
ような**寸法**の編集口は今回作らないと決めたので（押し出し済みソリッドの再計算が絡むため）、
`set_parameter` はAI（MCP）だけの操作である。受入スクリプトの `AI_ONLY` がこの欄を持つ。

**交互操作も実機で通っている**（この企画の差別化点）:
AIが述語 `parallel_to Y` で複数の辺を提案 → 画面に提案色（水色・確定は橙）で出る →
人が1本クリックして `origin` が `user` へ遷移 → AIが読み直して `fillet(1.5)` を適用できる。

## 1. スコープ

### 入れるもの

**スケッチのverb**

| verb | 引数 |
|---|---|
| `sketch_create` | 平面（基準3面）または既存ソリッドの平面状の面 |
| `add_line` | sketch, p0, p1 |
| `add_circle` | sketch, center, radius |
| `add_rectangle` | sketch, corner, width, height, angle（省略で0） |
| `add_arc` | sketch, center, radius, start_deg, end_deg |
| `pattern_rectangular` | sketch, entities, dx, dy, nx, ny |
| `pattern_circular` | sketch, entities, center, count, total_angle |
| `import_svg` | sketch, path — SVGの図形（ベジエのまま）をいま開いているスケッチへ足す |

**3Dのverb**

| verb | 引数 |
|---|---|
| `extrude` | 領域の集合, distance, mode(`join`\|`cut`\|`new`), 対象ボディ（`new` は `body_id` を受け付けない） |
| `extrude_face` | 面, distance — 既存ソリッドの面を選んで押し出す（スケッチ領域の押し出しとは別のverb） |
| `fillet` | 辺の集合, radius（辺ごとの配列も可） |
| `chamfer` | 辺の集合, distance（辺ごとの配列も可） |

**横断機能**

- **寸法の数値入力** — すべての数値引数は「名前つきの値」として保持し、後から編集すると形状が追随する
- **領域検出** — スケッチの図形群から閉領域を自動計算する（円を線で分けて片側だけ押し出す運用の土台）
- **undo / redo**
- **入出力** — STEP読み込み（読んだ時点で編集可能なボディができる）／STEP書き出し／STL書き出し

**AI側**

- MCPサーバ（§5）と、**選択集合の提案・修正・確定**

### 入れないもの

| | 理由 |
|---|---|
| 拘束ソルバ | 図形どうしの関係は現在使っていない。パラメトリック・プリミティブで足りる（§3.4） |
| ロフト・スイープ・回転 | 実測でspline面の正体がフィレットの副産物と判明しており、不要 |

## 2. アーキテクチャ

```
┌── AI（MCPクライアント）──┐        ┌── 人間（アプリ層 / ブラウザ）──┐
│  述語で引数を作る          │        │  ポインティングで引数を作る      │
└───────────┬──────────────┘        └──────────────┬─────────────────┘
            │ 呼ぶ / 読む                            │ コマンド ↓ ／ イベント ↑
            └────────────────┬───────────────────────┘
                             ▼
        ┌──────────── コア（Python・唯一の真実源）────────────┐
        │  文書（ボディ木・スケッチ）／ 選択集合 ／ 操作ログ ／ undo │
        │  ── verb層（純関数） f(文書, 選択, 引数) → 新しい文書 ──  │
        │      問い合わせ : build123d ラッパ（差し替え可能）         │
        │      操作      : OCP（OCCT）＋ 由来マップ回収            │
        └────────────────────────────────────────────────────┘
```

### 外してはいけない3つ

1. **AIの経路はアプリ層を通らない。** コアはUIが無くても機能的に完全であること。
   アプリ層にしか無い機能を作った瞬間、AIから使えなくなる。**これが層分けの唯一かつ最大の存在理由。**
2. **コマンドは下り、イベントは上り。** AIが選択を書き換えたらコアがイベントを発火し、
   アプリ層がハイライトを描き直す。この上り方向が無いと交互操作が成立しない。
3. **アプリ層が落ちて失われてよいのは、途中まで入力していたコマンドだけ。**
   文書・選択・操作ログ・undo履歴はすべてコア側。これが層の責務の判定テスト。

### verbの粒度

**verb ＝ ①undo1回で消える単位 ②操作ログ1行 ③MCP1呼び出し が一致する単位。**
食い違う切り方をしたら切り方が間違っている。UIの操作手順（スケッチ開始→面選択→中心→半径→確定）は
**1つのverbを組み立てる漏斗**であって、5つのverbではない。

**起動時にしかできない操作を作ると、それは起動オプションとして永久に残る**（2026-08-15判断・本人）。
duocadは起動時 `--step`（読んだ直後から触れる編集用ボディができる）とアプリ内「STEP読み込み」
（参照ボディだけを作り、編集には`make_editable_copy`が1ボディずつ要る）で挙動が違っていたため
`--step`を廃止できずにいた。本人の理由は「起動時にしかできないことがあるのがおかしい」であって
CLI引数を減らしたいのではない。**オプションを消すには機能の非対称を先に消すしかない**——
オプションの数はこの手の非対称の指標になる。実装はimport＋編集用コピー＋参照を隠すを
**1つのverb（ログ1行・undo1回）にする**ことが要点で、コマンド層からN回発行すると
27部品を読んだ後のCtrl+Zが最後の1個だけ戻す挙動になり、verb粒度規則に反する。

## 3. データモデル

### 3.1 文書

```
Document
  units          : "mm"（固定）
  bodies         : [Body]
  active_body    : BodyId
  sketches       : [Sketch]
  parameters     : { name: number }      # 名前つきの寸法値
  log            : [Operation]           # これが正。形状は導出物
```

**操作ログが唯一の正であり、形状はそこから導出されるキャッシュ。**
開くときはログから再生する（再生経路が毎回検証されるという副作用がある）。
遅くなったら最終B-repをサイドカーに置き、**ログのハッシュで無効化**する。

### 3.2 ボディ（複数持つ）

```
Body
  id      : BodyId
  name    : str
  kind    : "solid" | "mesh"          # 語彙の正は `duocad/document.py` の `Body`
  shape   : TopoDS_Shape              # 導出物
  visible : bool
```

**文書はボディのリストとして持つ。** STEPを読み込む時点で複数ボディになる。

選択が `body_id` を持つことは全verb・問い合わせ層・ピッキング・MCPスキーマに波及するコストであり、
ここは day 1 に払ってある（§6）。

### 3.3 スケッチと領域

```
Sketch
  id       : SketchId
  plane    : PlaneRef        # 基準平面 or 面への参照（← 壊れやすい参照。由来スロット対象）
  entities : [Entity]
  regions  : [Region]        # 導出物。BRepAlgoAPI_Splitter で計算

Entity  : Line | Circle | Rectangle | Arc | Bezier   （各自が名前つきの数値パラメータを持つ）
Region  : { index, area }             # 図形の配置から計算される閉領域
```

**領域は描くものではなく計算されるもの。** 実測で成立を確認済み:
円(面積1256.637)を線分で分割 → 領域 826.215 + 430.422 = 1256.637（元と一致）、
大きい方だけを押し出すと体積＝面積×高さと一致。

**注意**: パラメータを編集すると領域が分裂・合体・消失しうる。押し出していた領域が消える壊れ方をする。
§6の「黙って通さない」規律の対象。

**`extrude` の `new`（新規ボディ）は `body_id` を受け付けない**（行き先の無い操作に行き先を渡されたら
取り違えである）。**`join` は行き先となるボディが無ければ新規ボディとして落ちる** —— 保存済みの
操作ログはその形で再生されるため、この落ち方は残っている。

**Bezier はSVG取り込みのために持つ図形種別。** 3次ベジエで、`params` は
`x0,y0,cx1,cy1,cx2,cy2,x1,y1` の固定8キー。**これを1本ずつ作るverbは無い** ——
`import_svg` だけが作り、人もAIも直接は足せない。曲線を折れ線に落とさないのは、
落とすと押し出した側面が線分の数だけ平面に割れるためである（実測: 同じ形で面数4対130）。
**取り込んだ図形の数値は名前つきの値に登録しない**（制御点の座標は打ち直す寸法ではなく、
登録するとロゴ1枚で数千個の `d1` が並ぶ）。

### 3.4 パラメトリック・プリミティブ（拘束ソルバは持たない）

| | 中身 | 採否 |
|---|---|---|
| 拘束ソルバ | 図形**どうし**の関係を解く（この線とあの線は平行） | **持たない** |
| パラメトリック・プリミティブ | 各図形が**自分の数値**を持つ（長方形 at (x,y) 幅w 高さh 傾きa） | **これで足りる** |

「数値を打って描く／あとで値を編集する」という実際の運用は、後者だけで完全にカバーできる。
**day 1の予防**: 打った数値を図形の座標に焼き込まず、**名前つきの値として別に持つ**。
これで拘束は将来「上に重ねる層」として追加できる。

### 3.5 選択集合（交互操作の中核）

```
Selection
  items  : [ShapeRef | RegionRef]
  origin : "user" | "proposed"      # AIの提案は見た目が違い、承認操作がある

ShapeRef  : { body: BodyId, kind: "face"|"edge"|"vertex", index: int, provenance: null }
RegionRef : { sketch: SketchId, index: int, provenance: null }
```

**企画の前提「交互操作の成立条件」の5つを満たす**（`origin` が提案と確定を区別する）。

**index は現時点の添字であって、保存はしてよいが再生時に信用してはならない**（§6）。
参照IDの書式は ocp_vscode の実証済み形式（`/Group/Solid/faces/faces_6`）を借りてよい。

### 3.6 操作ログ

```
Operation
  seq        : int
  verb       : str
  args       : { ... }                # 名前つきパラメータへの参照を含む
  selection  : [ShapeRef|RegionRef]   # 実行時に解決した参照
  provenance : null                   # ★ day 1 の空スロット（§6）
```

**保存形式は JSON。SQLiteは使わない。** 理由: ①gitに載って差分が読める ②AIが履歴を全部読める
③1モデル＝1ファイルでコピー・共有が普通のファイル操作で済む。規模は数百操作で問題にならない。
これは document 指向のアプリであってデータのアプリではない（Fusionが `.f3d` を保存するのと同じ）。

## 4. 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| カーネル | **OCCT（OCP経由）** | 由来マップ（`Modified`/`Generated`/`History`）が取れる唯一の経路 |
| 問い合わせ | **build123d をラッパとして** | `Solid(shape).edges().filter_by(Axis.Z)` が1行。**インタフェース越しに使い、差し替え可能に保つ** |
| テセレーション | **ocp_tessellate** | 既に検証環境に入っている |
| コア | **Python** | OCPもMCPもPython。ビルダ文脈（`BuildPart`）は使わず生の `TopoDS_Shape` を保持する |
| 通信 | **WebSocket** | コマンド下り／イベント上りの双方向 |
| 描画 | **three.js** | |
| frontend | **Svelte 5 + TypeScript + Vite** | 状態のほとんどはコアにあり、frontendに残るのはコマンドの途中状態だけ（薄い状態機械1つ分） |
| CSS | **バニラ（CSS変数）** | 部品が8個程度と少なく、CADのパネルは密度が高い。**Tailwindの既定値に寄せると「よくあるWebアプリの見た目」になり、CADツールがWebアプリに見えてはいけない** |

**frontendで守るべき唯一のルール**: **canvasはフレームワークの外に置く。**
three.jsが所有するコンテナを渡し、フレームワークは二度と再描画しない。ここを外すと状態更新のたびにWebGLが壊れる。

**SvelteKitは使わない**（ルーター・SSR・アダプタ・フォームが不要なうえ、2026年の破壊的変更は

## 5. API / MCP 仕様

**「AIがモデルを作る」ためのAPIではなく、企画の前提どおり「AIと人間が同じ選択集合を触る」ためのAPI。**

面・辺・領域を引数で受けるverbの口は、MCPにもWebSocketにも無い —— どちらもコアの**確定選択**から取る
（`duocad/selection.py` の `require_confirmed` / `require_edges`）。引数に残るのは数値・名前・パスだけである。
Bodyは選択集合の項目ではないので、`body_id`（どのBodyへ足す／から引くか、隠すBody）は引数のまま残る。

**ツール一覧・各verbの引数・呼び方・AIがどこまで自分で進めてよいかは [../MCP.md](../MCP.md) が正。**
ここに写すと、増減のたびに2箇所を直すことになる。

**同期の要件**
- 手動操作もAI操作も**同じ操作ログに積む**
- **AIの応答待ちでUIがブロックされないこと**（手動4ステップの速さを殺さない）
- **競合**: 人間がコマンドの引数収集中にAIが選択を書き換えた場合は、
  **コマンド開始時の選択をスナップショットして使う**（単一ユーザーなのでこれで足りる）

## 7. 実測で判明した落とし穴

| 落とし穴 | 実測した内容 | 対処 |
|---|---|---|
| **OCCTのフィレットは例外を投げずに失敗する** | 20mm立方体・全辺: r=10.0 → `IsDone()=False`（例外なし）／**r=10.5 → 成功**／r=30.0 → 失敗。**半径に対して単調ですらない** | verbのラッパで**毎回 `IsDone()` を確認**し、失敗したら操作ごと捨てて人に戻す |
| **面の添字は形状変更で壊れる** | 同じ面を追跡してフィレットをかけると **i=5 → 9**。ただし穴の径変更・穴の追加・ポケット・面取りでは動かない＝**散発的に静かに間違う** | 生の添字を保存・再利用しない。由来スロット（予防2） |
| **build123d は由来を捨てている** | `Modified` / `Generated` / `BRepTools_History` への参照が**パッケージ内0件** | 操作はOCP直叩き。問い合わせだけbuild123d |
| **領域はパラメータ編集で変わる** | 線を y=5→6→7 と動かすと面積が変化（領域数と列挙順はこの範囲では安定） | 押し出し対象の領域が消えたら止めて聞く |
| **2つの型系の同一性は保たれる** | `==` / `hash` / `set` すべて同一視。`.wrapped` 往復でも維持 | 選択集合をbuild123dオブジェクトで持ってよい |
| **STEP往復は体積までは bit-exact ではない** | 26面・体積 23340.849375 の単純形状では差 0.00e+00。56面・体積 91018.2223598035 の形状では差 約7.3e-11（相対 約8e-16 ＝ IEEE doubleの1ULP級。再読込で面のパラメトリック表現や走査順が変わり、`GProp_GProps` の数値積分の順序が変わることに由来） | 比較は `==` ではなく相対許容差（`1e-6`）で行う。面数（`face_count`）は往復後も厳密一致でよい。詳細はengine `step-roundtrip-volume-not-bitexact` |
| **STLは近似** | 偏差 0.2mm→30.7KB ／ 0.05mm→47.2KB ／ 0.01mm→170.6KB | 偏差を設定可能にする |

### 背景と要件（2026-09-13移設）

#### Fusion360離脱と要件分析（2026-07-20）

- **Fusion360離脱の理由6点**（本人明示）: ①アプリが重すぎる ②使うことのない無駄な機能が多い ③クラウドに縛られる ④大企業のエコシステムに依存する ⑤大学院修了で教育ライセンスが無くなる ⑥Linuxで使えない。**全てプラットフォーム層の不満であり、直接操作（面を選んで数値指定する）というインタラクションには不満がなく、むしろ何十倍も速いと評価している**——これが「直接操作を保ちつつプラットフォームだけ捨てる」という要件の根拠になった。
- **当初(2026-07-20)の要件分析はボトルネックを空間参照(deixis)と特定していた**: 「モデルの一部を直接選択して数値指定する方が自然言語指示より何十倍も速い」（pokeca_caseで実体験）。複雑物（STL26部品構成のPCケース等）は自然言語だけでは指示しきれない。既存で足りていた部分: リアルタイム表示・ホットリロード・クリック検査は`bernhard-42/vscode-ocp-cad-viewer`(ocp_vscode)、LLM側の形状検査ループは`pzfreo/build123d-mcp`(CADGenBench 2026-06でスクリプト直書き比+27%)。自作すべき差分と位置づけられたのは「クリックした面/エッジ→壊れない意味的セレクタ式（例: `faces().sort_by(Axis.Z)[-1]`）への逆合成」——生IDはトポロジカルネーミング問題で壊れるためセレクタ式が正、という結論。STEP読み込みはOCCT系なら無償可能（ダムソリッド化の制約はあるが参照・ブーリアン用途には十分）、STLはメッシュのままなら可・B-rep編集への変換は非現実的。**この要件分析自体は2026-08-07のスコープ変更（下記）後も土台として有効という位置づけ。**

### AI/人間の分担

- **duocadのAIは（Web化しても）作業しているマシンで実行する**（2026-08-22判断）。Claudeにせよローカル LLMにせよサーバ機に置いて全端末から共用する形は採らない。効いてくること: サーバとAIが別マシンに分かれると、LLM呼び出しの接続の向きを反転させる必要がある（サーバがクライアント側のLLMを呼びに行けない）。duocadの現行実装はAgentLoopがPythonサーバ側でLLMを叩く作りなので、ここが設計上の分岐点になる。「借り物のPCでも使いたい」と組み合わせると、ローカルLLM経路は自分の端末（インストール可）でだけ成立し、借り物のPCではClaude側の経路だけが残る。

#### ローカルLLM（llama-server）運用上の罠

- **`--n-predict N`はサーバ側の上限ではなく既定値**（2026-08-23実測、llama-server build 10549）。`max_tokens`指定なしなら1024トークンで`length`終了するが、クライアントが`max_tokens: 16384`を明示すると3,520トークン返った（56秒）。出力長の保証はクライアント側の値にしか置けない。
- **`--reasoning-budget N`と`--reasoning-budget-message`で、思考付きモデルの「成功したのに空返し」が根治する**（2026-08-23実測）。症状: 推論（thinking）付きモデルは`reasoning_content`に思考を吐いてから`content`を書くため、トークン予算が足りないと思考の途中で打ち切られHTTP 200・例外なしのまま`content`が空文字で返る（`finish_reason`だけ`"length"`）。対症療法は`max_tokens`を厚く取ること（単発判定2048、エージェント用途16384 — duocadの29ツールでmax_tokens=3072だと4〜5手目で空返りして停止、16384で完走）だが、これは最悪値を捨てる代償を払う対症療法。**根治策は`--reasoning-budget N`で思考側を縛ること**（N>0で思考のトークン予算、0で即終了、既定-1は無制限）。Ornith-1.5-9Bで`--reasoning-budget 512`を実測すると思考が予算に当たっても本文は正常に返り（content 1,686文字・`finish_reason: stop`）、duocadでは`max_tokens`を16384→1024へ下げられた（実タスク20試行で打ち切り0/20・誤り0/20）。`"chat_template_kwargs": {"thinking": false}`や`"reasoning_effort": "none"`は思考を抑止できなかった（llama.cpp b9673）。**故障との判別は`finish_reason`**（正常なツール呼び出しでもcontentは空になるため、content空だけでは区別できない。正常なら`finish_reason: tool_calls`かつtool_callsあり、故障なら`finish_reason: length`）。バッチ処理での一般則: content空の応答を成功扱いしない、`finish_reason=="length"`かつcontent空を検知して警告を出す、トークン予算は思考ぶんを見込む。
- **矛盾したタスク文を渡すとQwen3系の思考が暴走し1リクエストが600秒超で返らないことがある**（2026-08-20発見、duocadのツール呼び出し検証）。症状: 「確定している選択の辺にフィレット」と指示したが実際は面3枚が確定していたケースで、モデルが確認ツールを5回繰り返して手が止まった。**文脈長の枯渇ではない**（矛盾を除いた再実行ではプロンプトは4,005→5,789トークンにしか伸びず`-c 16384`に余裕があり、全7ターン170秒で完遂。伸びるのは思考`reasoning_content`の側で、難所のターンだけ1,986字・85秒に膨らむ）。対策: エージェントループには(a)`max_tokens`の上限、(b)1リクエストの短いタイムアウト、(c)打ち切ったときに「何が矛盾していたか」を返して再指示させる経路が要る。指示の一貫性はUI側で担保する（確定済み選択の種別と、これから呼ぶverbが要求する種別を突き合わせる）。教訓: エージェントが遅いとき真っ先に疑うべきは文脈長ではなく指示の矛盾（文脈長は測れば一瞬で否定できる）。

### v1での決定

- **duocadのbboxは初回+1.6秒を払ってでも実寸を返す側（`AddOptimal`）を採る**（2026-09-07判断）。理由は本人の言葉で「29%のボディの寸法が最大9倍狂っているほうが害が大きい」。初回のコスト（27ボディの`describe_document(include_bbox=True)`で+1.6秒）は承知の上で受け入れ、「遅くなったから戻す」を後から言わないと明示。キャッシュの対象はbboxだけ（汎用の形状キャッシュにはしない）、寿命は文書の切り替えまで（グローバルな辞書1個で持つと長いセッションで古い形状が積み上がるため持たない）。実装は`Document`が`BoundingBoxCache`を1つ持つ形。

- **duocadの保存済みモデルは、開けなくなる変更のために移行スクリプトを書かずファイルごと捨ててよい**（2026-08-26判断、理由の明言なし）。verbを消すと該当操作を含む保存ログが未登録verbで例外を出し開けなくなる状況で、本人は「移行スクリプトで除去」「再生専用ハンドラだけ残す」「開けなくてよい」の3択よりさらに踏み込み「モデル自体を削除してよい」と回答。元のSTEPが手元にある限り保存済みJSONは作り直せる中間物として扱う。**`models/`のgitignoreは2026-08-27に外した**（理由: 「そこまで大したものを作れる状態ではない」。まだ個人の資産と呼べるモデルが無いので載せない理由の方が無い）。実物のモデルが溜まってきたらgitignoreへ戻す判断を再度出しうるが、捨ててよいという判断自体は変わっていない。

- **duocadのスケッチ点マーカーは、pointKeyが1個しかない種別（長方形・円・円弧）は常時表示をやめホバー/選択時だけ見せる**（2026-09-11判断）。長方形は基準コーナー1個だけがpointKeyで残り3隅は`width`/`height`/`angle`からの導出値のため、4隅のうち1つだけマーカーが出る非対称があった。技術的根拠: これらの種別は「その点だけ動かす」と「図形全体を動かす」が完全に同じ処理になっており、点は「独立に動かせる特別な場所」ではなく「たまたま名前が付いた、辺上のどこでも同じ結果になる1点」でしかない。対して線分（2点）・ベジエ（4点）は片方の点だけ動かすと形が変わるためこの理屈は当てはまらず常時表示のまま。実装は`entityHasIndependentPoints(kind)`（pointKeysが2個以上か）を追加し、`mesh.visible`だけを条件化（ピック可能な座標は変えていないため`sketchPoint`参照等の既存の使い道は保たれる）。

- **duocadのモデル表示/非表示（`set_visible`）をCtrl+Z・Ctrl+Yの対象外にし、保存にも残さないと決めた**（2026-08-26判断、理由の明言なし）。選択と同じ「セッション状態」の扱いになった。実装はverbをやめて`duocad/verbs/visibility.py`を廃止し、実体を`duocad/selection.py`へ移した（可視性は選択機構の一部という既存原則の延長）。

### 開発運用で得た知見

- **記録に残る「既知の赤・本人判断待ち」は実行時に再現するとは限らない**（2026-08-23・2026-08-26の2例）。1例目: taskbox handoverに「着手前から赤」として記録されていたacceptance.mjsのhuman4件が、FilesPanel移設タスク実行時には2回とも全緑だった（`git stash`で変更前に戻しても同条件で全緑）。一方`smoke-features.mjs`の既知赤（体積が円柱ぶん減らない）はエラーメッセージ・失敗地点まで完全一致して再現した。2例目: READMEに「本人判断待ち」と残っていた項目が、着手前の実測で両方とも緑になっていた——**解消したのはその記述を書き足したのと同じコミット自身**で、コミットメッセージには座標調整の記載があり、判断待ちとされていた分岐はその場でスクリプト側に倒して決着していたのに記述だけが更新されずに残っていた。**結論**: 既知赤の「着手前ベースライン同等」判定は、再現した場合のみ症状（エラーメッセージ・失敗箇所）の一致で行い、緑になったこと自体を問題視しない。**一般化**: 「直した」と「記録を直した」は別の作業であり後者は落ちやすい（とくに同じコミットの中で問題を直しているときは、直前に自分が書いた「未決」の記述が視界から外れる）。「既知の赤/留保」を出発点にする指示を受けたら、信じて着手せず先に1回走らせて再現を確かめる。
