# duocad — 最初期の実装計画

**立ち上げ時の計画書。企画の意図・当初のスコープ・層分け・データモデルの起点として残す** ——
いまの実装がすべてここに収まるわけではない。**いまの挙動の正はコードとテスト**（契約は各モジュールの
docstring）。MCPの口は [../MCP.md](../MCP.md)。本文と食い違うときは実装を信じる。形状最適化の記録は
[TOPOPT.md](TOPOPT.md)。

## 企画の前提

**呼称は「必要最低限の機能をもったミニマルなモデリングツール」。** 「機能削減版Fusion」は使わない ——
Fusionと呼ぶと履歴・スケッチ拘束・アセンブリが自動的に期待値に入り、スコープが膨張する。

**手動操作それ自体が一級の操作モードである。AIへの入力手段ではない。** 特定の面の押し出しは選択→
押し出し選択→数値指定→Enterの4stepで済み、これをAIに依頼する方が遅い（本人）。これは「AIが下手
だから手動が速い」ではなく、**指示の情報量に対してチャネルの帯域が合っていない**という構造的な話
であり、AIの性能が上がっても解消しない。「いずれAIが賢くなれば手動は要らなくなる」という前提は置かない。

**分業の原則** — 境界は「作業の種類」ではなく「対象集合をどう指定するか」で決まる:

| 指示の性質 | 最速のチャネル | 理由 |
|---|---|---|
| **「どれ」**を特定する（この面、この辺） | **ポインティング（手動）** | 位置情報の伝達に言語は極端に非効率 |
| **「条件を満たす全部」**（全辺、上面の外周） | **言語（AI）** | 述語1つ vs Nクリック |
| **形状そのものが未定**（大まかな形を出す） | **言語（AI）** | 手続きが長く探索的 |
| **手続きが面倒だが機械的**（一括フィレット等） | **言語（AI）** | 人間側の作業量だけが大きい |

境界は固定ではない —— 選択集合を受け渡せるなら1つの操作の中で分担できる。

**交互操作の成立条件**（Fusion360にも既存のコードCADにも無い差別化点）:

```
AI: 述語で候補集合を作る  →  ユーザー: 過不足をクリックで修正  →  AI: 操作を適用
```

条件は1つ: **選択集合が第一級の共有オブジェクトであること** —— 永続（操作の合間に消えない）・
双方向（AI/ユーザーの双方が読める・**書ける**）・種別を保持（面/辺/頂点を区別）・差分編集可能
（追加・除去。作り直しでない）・**人とAIが同じ操作で書ける**（出所を区別しない。AIの付け外しを人が見て、
よければそのまま使い、だめならAIに直させるか自分で付け外しする）。データ構造は §3.5。

**Fusion360の位置づけ**:

| 軸 | 評価 |
|---|---|
| 手動操作 | **完璧。基準線であり下回ってはならない** |
| UI | モダン・シンプル。**これも基準線**（FreeCADはここで却下された） |
| AI操作 | 弱い。実用上「パラメータ指定でプリミティブを出す」程度 |
| 継続性 | **常に不安**（教育ライセンス失効・クラウド束縛・大企業依存・Linux非対応） |

離脱の理由はすべて**プラットフォーム層**で、直接操作への不満はゼロ —— **そこが基準線**である。
**作るべきもの**: Fusion360と同等以上にモダンでシンプルなUIに「自分が実際に使う手動操作」と
「強力なAI操作」を載せ、両者が同じ選択集合を交互に触れるようにしたもの。**FreeCADは却下済み**
（UIがクラシカルすぎる。再提案しない）—— UIの様式が足切り条件として働く。コードは全領域AIが書く。

## 0. このツールは何か

> **すべての実装済みverbを、人間とAIの両方が満足に使える状態にする。**
> これがこの企画の主張（交互操作）そのものであり、verbごとに検査できる。

| 側 | 合格条件 |
|---|---|
| **人間** | UIだけで起動でき／引数をポインティングと数値入力で与えられ／**プレビュー**があり／**Escで中断**でき／**undoで戻る** |
| **AI** | MCPツールとして呼べ／引数を**述語**または明示的な参照で与えられ／**結果と失敗が構造化して返る** |
| **交互操作** | AIが選択を付け外しする → **UIに選択として表示される** → 人がクリックで直す → AIが読み直して適用できる |

**実装済みの全verbが両方の合格条件を満たしている**（verbの一覧は [../MCP.md](../MCP.md) が正）。
例外が1つ:

- **形状最適化の4つ**（`set_preserve_bodies` / `set_exclude_bodies` / `set_fixtures` / `set_loads`）は
  `preview: 'none'` —— 集合代入するだけで形は1つも変わらないので投機実行の対象が無い。確定は即座に
  効き、undoで戻る。

**`set_parameter`（寸法の打ち直し）は人にもAIにも出していない**（コアと再生用の登録だけ残す）。位置の打ち直しは
**3Dの直接選択 + `move_sketch_entities` / `move_body`** に統一している。理由は
[DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)「図形（スケッチ）の表現」。

**選択に出所（AIの提案／人の確定）の区別は持たない**（2026-10-03 本人決定。理由は
[DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)「隠したボディ・選択・可視性」）。

## 1. スコープ

**入れるもの** — スケッチ: `sketch_create` / `add_line` / `add_circle` / `add_rectangle` / `add_arc` /
`pattern_rectangular` / `pattern_circular` / `import_svg`。3D: `extrude`(領域の集合、または既存
ソリッドの同一平面の面群を `join`/`cut`/`new`) / `fillet` / `chamfer`(辺ごとの配列も可)。
各verbの引数は [../MCP.md](../MCP.md) が正。横断機能は寸法の数値入力(名前つきの値として保持し編集で
追随)・領域検出(閉領域を自動計算)・undo/redo・入出力(STEP読み書き／STL書き出し)。AI側はMCPサーバ
(§5)と選択集合の付け外し。

**入れないもの**:

| | 理由 |
|---|---|
| 拘束ソルバ | 図形どうしの関係は現在使っていない。パラメトリック・プリミティブで足りる（§3.4） |
| ロフト・スイープ・回転 | 実測でspline面の正体がフィレットの副産物と判明しており、不要 |

## 2. アーキテクチャ

```
┌── AI（MCPクライアント）──┐        ┌── 人間（アプリ層 / ブラウザ）──┐
│  述語で引数を作る          │        │  ポインティングで引数を作る      │
└───────────┬──────────────┘        └──────────────┬─────────────────┘
            │ 呼ぶ / 読む                            │ コマンド ↓ ／ イベント ↑
            └────────────────┬───────────────────────┘
                             ▼
        ┌──────────── コア（Python・唯一の真実源）────────────┐
        │  文書（ボディ木・スケッチ）／ 選択集合 ／ 操作ログ ／ undo │
        │  ── verb層（純関数） f(文書, 選択, 引数) → 新しい文書 ──  │
        │      問い合わせ : build123d ラッパ（差し替え可能）         │
        │      操作      : OCP（OCCT）＋ 由来マップ回収            │
        └────────────────────────────────────────────────────┘
```

### 外してはいけない3つ

1. **AIの経路はアプリ層を通らない。** コアはUIが無くても機能的に完全であること —— これが層分けの
   唯一かつ最大の存在理由。
2. **コマンドは下り、イベントは上り。** AIが選択を書き換えたらコアがイベントを発火し、アプリ層が
   ハイライトを描き直す。この上り方向が無いと交互操作が成立しない。
3. **アプリ層が落ちて失われてよいのは、途中まで入力していたコマンドだけ。** 文書・選択・操作ログ・
   undo履歴はすべてコア側。これが層の責務の判定テスト。

### verbの粒度

**verb ＝ ①undo1回で消える単位 ②操作ログ1行 ③MCP1呼び出し が一致する単位。** UIの操作手順
（スケッチ開始→面選択→中心→半径→確定）は**1つのverbを組み立てる漏斗**であって、5つのverbではない。

## 3. データモデル

### 3.1 文書

操作ログが唯一の正であり、形状はそこから導出されるキャッシュ。開くときはログから再生する
（再生経路が毎回検証される副作用がある）。遅くなったら最終B-repをサイドカーに置き、ログのハッシュで
無効化する。**保存形式はJSON、SQLiteは使わない** —— gitに載って差分が読める／AIが履歴を全部読める／
1モデル＝1ファイルで共有が普通のファイル操作で済む(document指向のアプリでありデータのアプリではない)。
型の定義は `duocad/document.py` / `sketch.py` / `selection.py` が正。

### 3.2 ボディ(複数持つ)

文書はボディのリストとして持つ。STEPを読み込む時点で複数ボディになる。選択が `body_id`
を持つことは全verb・問い合わせ層・ピッキング・MCPスキーマに波及するコストであり、day 1 に払ってある
(§6)。

### 3.3 スケッチと領域

**領域は描くものではなく計算されるもの**(`BRepAlgoAPI_Splitter`。実測: 円を線分で
分割した2領域の面積和が元の面積と一致し、押し出すと体積＝面積×高さと一致)。パラメータを編集すると
領域が分裂・合体・消失しうる(押し出していた領域が消える壊れ方をする。§6「黙って通さない」規律の対象)。
`plane` は基準平面または面への参照で、壊れやすい参照(由来スロットの対象)。`extrude` の `new`(新規
ボディ)は `body_id` を受け付けない(行き先の無い操作に行き先を渡されたら取り違え)。`join` は行き先が
無ければ新規ボディとして落ちる —— 保存済みの操作ログはその形で再生されるため、この落ち方は残る。
**Bezier**(3次)はSVG取り込みのために持つ図形種別で、`import_svg` だけが作り人もAIも直接は足せない。
曲線を折れ線に落とさないのは、落とすと押し出した側面が線分の数だけ平面に割れるため(実測: 同じ形で
面数4対130)。取り込んだ図形の数値は名前つきの値に登録しない(登録するとロゴ1枚で数千個の `d1` が並ぶ)。

### 3.4 パラメトリック・プリミティブ(拘束ソルバは持たない)

拘束ソルバ(図形どうしの関係を解く)は持たない。各図形が自分の数値を
持つプリミティブ(長方形 at (x,y) 幅w 高さh 傾きa)で足りる。**day 1の予防**: 打った数値を図形の座標に
焼き込まず名前つきの値として別に持つ —— 拘束は将来「上に重ねる層」として追加できる。

### 3.5 選択集合(交互操作の中核)

項目の並びだけを持つ（出所を区別しない。人とAIが同じ操作で付け外しする）。**index は現時点の添字であって、保存はしてよいが
再生時に信用してはならない**(§6)。参照IDの書式はocp_vscodeの実証済み形式(`/Group/Solid/faces/
faces_6`)を借りてよい。

### 3.6 操作ログ

1操作は `seq` / `verb` / `args`(名前つきパラメータへの参照を含む) / `selection`(実行時に
解決した参照) / `provenance`(★ day 1 の空スロット。§6)。

## 4. 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| カーネル | **OCCT（OCP経由）** | 由来マップ（`Modified`/`Generated`/`History`）が取れる唯一の経路 |
| 問い合わせ | **build123d をラッパとして** | `Solid(shape).edges().filter_by(Axis.Z)` が1行。インタフェース越しに使い差し替え可能に保つ |
| テセレーション | **ocp_tessellate** | 既に検証環境に入っている |
| コア | **Python** | OCPもMCPもPython。ビルダ文脈（`BuildPart`）は使わず生の `TopoDS_Shape` を保持する |
| 通信 | **WebSocket** | コマンド下り／イベント上りの双方向 |
| 描画 | **three.js** | |
| frontend | **Svelte 5 + TypeScript + Vite** | 状態のほとんどはコアにあり、frontendに残るのはコマンドの途中状態だけ |
| CSS | **バニラ（CSS変数）** | 部品が8個程度と少なく密度が高い。Tailwindの既定値に寄せると「よくあるWebアプリの見た目」になり、CADツールがWebアプリに見えてはいけない |

**frontendで守るべき唯一のルール**: canvasはフレームワークの外に置く。three.jsが所有するコンテナを
渡し、フレームワークは二度と再描画しない —— 外すと状態更新のたびにWebGLが壊れる。

**SvelteKitは使わない**（ルーター・SSR・アダプタ・フォームが不要なうえ、破壊的変更のほぼ全てが
SvelteKit側に集中しており、使わなければ年刻みではなく5年周期の側に乗る）。

## 5. API / MCP 仕様

**「AIがモデルを作る」ためのAPIではなく、「AIと人間が同じ選択集合を触る」ためのAPI。** 面・辺・領域
を引数で受けるverbの口はMCPにもWebSocketにも無い —— どちらもコアの**選択**から取る
(`duocad/selection.py`)。引数に残るのは数値・名前・パスだけ。
Bodyは選択集合の項目ではないので `body_id`(どのBodyへ足す／から引くか、隠すBody)は引数のまま残る。
ツール一覧・各verbの引数・呼び方は [../MCP.md](../MCP.md) が正。

**同期の要件**: 手動操作もAI操作も同じ操作ログに積む／AIの応答待ちでUIがブロックされないこと(手動
4ステップの速さを殺さない)／人間がコマンドの引数収集中にAIが選択を書き換えた場合は**コマンド開始時
の選択をスナップショットして使う**(単一ユーザーなのでこれで足りる)。

## 6. day 1 に払う予防（合計 数十行）

これを外すと後で書き直しになる。逆にこれだけ払えば「事後拡張は難しくない」が実際に正しくなる。

| # | 予防 | 外したときの代償 |
|---|---|---|
| 1 | **操作ログを最初から持つ** | undo・再生・AIの履歴読み・git差分が全部これに乗る |
| 2 | **操作の戻り値に「由来」のスロットを空で用意する** | 後付けは全操作の書き直し。取り出し方が操作ごとに違う（ブーリアンは `History()`、フィレットは `Modified()`）ので、ここが正規化の置き場所になる |
| 3 | **文書を「ボディのリスト」と定義する** | 選択が `body_id` を持つ改修は全層に波及する |
| 4 | **問い合わせ層をインタフェースにする** | verbが `build123d` を直接呼ぶと差し替えができず、記法の混在がアーキテクチャの問題になる |
| 5 | **寸法を図形に焼き込まず名前つきの値で持つ** | 「あとから値を編集して形が追随する」が成立しない |
| 6 | **失敗を黙って通さない** | §7参照。壊れたモデルが静かに残る |

**由来スロットの適用先は2つ**: 面/辺の添字 ／ 領域の同一性(スケッチを貼った面は対象外 —— 作成時点
の姿勢をスケッチへ焼き付け、以後は独立させる方式にした。`duocad/sketch.py`・`duocad/region.py` 参照)。

## 7. 実測で判明した落とし穴

| 落とし穴 | 実測した内容 | 対処 |
|---|---|---|
| **OCCTのフィレットは例外を投げずに失敗する** | 半径に対して単調でないうえ、`IsDone()` が真なのに壊れた形を返す帯がある（数値は [../README.md](../README.md)「実測で判明している技術的な地雷」が正） | verbのラッパで毎回4つの関門（`IsDone` / 空でない / 体積>0 / `BRepCheck`）を通し、落ちたら操作ごと捨てて人に戻す |
| **面の添字は形状変更で壊れる** | 同じ面を追跡してフィレットをかけると i=5 → 9。ただし穴の径変更・追加・ポケット・面取りでは動かない＝散発的に静かに間違う | 生の添字を保存・再利用しない。由来スロット（予防2） |
| **build123d は由来を捨てている** | `Modified` / `Generated` / `BRepTools_History` への参照がパッケージ内0件 | 操作はOCP直叩き。問い合わせだけbuild123d |
| **領域はパラメータ編集で変わる** | 線を動かすと面積が変化（領域数と列挙順はこの範囲では安定） | 押し出し対象の領域が消えたら止めて聞く |
| **2つの型系の同一性は保たれる** | `==` / `hash` / `set` すべて同一視。`.wrapped` 往復でも維持 | 選択集合をbuild123dオブジェクトで持ってよい |
| **STEP往復は体積までは bit-exact ではない** | 相対差は約8e-16（IEEE doubleの1ULP級。再読込で面のパラメトリック表現や走査順が変わり数値積分の順序が変わることに由来） | 比較は `==` ではなく相対許容差（`1e-6`）で行う。面数（`face_count`）は往復後も厳密一致でよい |
| **STLは近似** | 偏差と出力サイズの関係（代表値: 0.01mm→170.6KB） | 粗さを選ぶ入力は画面にもMCPにも置かない（0.01mm固定。根拠と全表は [DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)「STL書き出しの粗さ」） |

**STEPエクスポートの副次的な価値**: このツールで作りかけて、Fusion360で仕上げられる。機能が足りない
ケースに突き当たってもSTEPに吐いて続ければよく、「作ったが機能が足りなくて詰む」というこの企画最大の
リスクを構造的に消す移行の安全網になる。

## 8. 今後の拡張候補

- **拘束ソルバ** — 図形どうしの関係（平行・垂直など）を解く層。パラメトリック・プリミティブ（§3.4）
  で現状足りているため未着手。次に足すなら `python-solvespace`（実測済み・GPLv3+）
- **履歴のL4化** — 操作ログは現在L1（追記専用ログ）。押し出し距離やスケッチ寸法を後から編集する運用
  が実在するため履歴は「要る」と確定している。§6の予防（由来スロット）を払ってあるので、痛みが出た
  操作から順にL4（由来による永続命名）へ上げられる
