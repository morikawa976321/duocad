## 企画の前提

### 呼称

**「必要最低限の機能をもったミニマルなモデリングツール」**。
「機能削減版Fusion」は使わない — Fusionと呼ぶと履歴・スケッチ拘束・アセンブリが
自動的に期待値に入り、スコープが膨張するため。

### 手動操作は一級のモード

**手動操作それ自体が一級の操作モードである。** AIへの入力手段ではない。

決定的な観察（本人の言葉）:

> 特定の面の押し出しなどは選択→押し出しを選択→数値指定→Enterの4stepですぐおわる。
> これをいちいちAIに依頼するのはむしろ時間がかかる。

これは「AIが下手だから手動が速い」ではない。**指示の情報量に対してチャネルの帯域が合っていない**
という構造的な話であり、AIの性能が上がっても解消しない。したがって
「いずれAIが賢くなれば手動は要らなくなる」という前提を置いてはならない。

### 分業の原則

| 指示の性質 | 最速のチャネル | 理由 |
|---|---|---|
| **「どれ」**を特定する（この面、この辺） | **ポインティング（手動）** | 位置情報の伝達に言語は極端に非効率 |
| **「条件を満たす全部」**（全辺、上面の外周） | **言語（AI）** | 述語1つ vs Nクリック |
| **形状そのものが未定**（大まかな形を出す） | **言語（AI）** | 手続きが長く探索的 |
| **手続きが面倒だが機械的**（一括フィレット等） | **言語（AI）** | 人間側の作業量だけが大きい |

**帰結**: 分担の境界は「作業の種類」ではなく「**対象集合をどう指定するか**」で決まる。
そしてこの境界は固定ではない — **選択集合を受け渡せるなら、1つの操作の中で分担できる。**

### 交互操作の成立条件

```
AI: 述語で候補集合を作る  →  ユーザー: 過不足をクリックで修正  →  AI: 操作を適用
```

差別化はUIでも機能数でもなく **この交互操作**にある。Fusion360にも既存のコードCADにも無い。

**成立条件は1つだけ: 選択集合が第一級の共有オブジェクトであること。** 具体的には:

1. **永続**（操作の合間に消えない。UIの一時状態ではない）
2. **双方向**（AIが読める／**AIが書ける**／ユーザーが読める／ユーザーが書ける）
3. **種別を保持**（面/辺/頂点を区別する）
4. **差分編集可能**（追加・除去。作り直しではなく）
5. **出所を区別**（AIの**提案**か、ユーザーが**確定**したものか）

データ構造上の写しは §3.5。

### Fusion360の位置づけ

| 軸 | 評価 |
|---|---|
| 手動操作 | **完璧。基準線であり下回ってはならない** |
| UI | モダン・シンプル。**これも基準線**（FreeCADはここで却下された） |
| AI操作 | 弱い。実用上「パラメータ指定でプリミティブを出す」程度 |
| 継続性 | **常に不安**（教育ライセンス失効・クラウド束縛・大企業依存・Linux非対応） |

Fusion360のAPI自体はフィーチャ生成まで含む本格的なもので「プリミティブだけ」ではない。
ただしLLMのループ前提の設計ではなく継続性の不安も変わらないので、離脱の判断は動かない。
離脱の理由6点はすべて**プラットフォーム層**。直接操作への不満はゼロで、**そこが基準線**である。

**作るべきもの**:

> **Fusion360と同等以上にモダンでシンプルなUIに、
> 「自分が実際に使う手動操作」と「強力なAI操作」を載せ、
> 両者が同じ選択集合を交互に触れるようにしたもの。**

**FreeCADは却下済み**（UIがクラシカルすぎる）。UIの様式が足切り条件として働く。
コードは全領域AIが書く。本人は「AIの解説があれば理解できる」水準。

## 0. このツールは何か

上記「作るべきもの」の定義どおり。

### 「使える」の基準

> **すべての実装済みverbを、人間とAIの両方が満足に使える状態にする。**
> これがこの企画の主張（交互操作）そのものであり、verbごとに検査できる。

#### 「満足に使える」の操作的定義（verbごとに判定する）

| 側 | 合格条件 |
|---|---|
| **人間** | UIだけで起動でき／引数をポインティングと数値入力で与えられ／**プレビュー**があり／**Escで中断**でき／**undoで戻る** |
| **AI** | MCPツールとして呼べ／引数を**述語**または明示的な参照で与えられ／**結果と失敗が構造化して返る** |
| **交互操作** | AIが選択を提案 → **UIに提案として表示される** → 人がクリックで直す → AIが読み直して適用できる |

#### 到達状況

**実装済みの全verbが、人間(UI)とAI(MCP)の両方で上の合格条件を満たしている**(verbの一覧は
[../MCP.md](../MCP.md) が正。2026-09-18 に当時のverbごとの達成表を削った —— verb が増えるたびに
腐るため)。例外が2つ:

- **形状最適化の4つ(`set_preserve_bodies` / `set_exclude_bodies` / `set_fixtures` / `set_loads`)は
  「プレビュー」を持たない**(`preview: 'none'`。`set_visible` と同じ位置づけ)—— 集合代入するだけで
  形そのものは1つも変わらないので、投機実行して測る対象が無い。確定は即座に効き、undoで戻る。
- **`set_parameter` はAI(MCP)だけの操作**(2026-08-30 本人決定)。右サイドバーのスケッチパラメータ
  パネル(数値入力欄)を廃止し、位置の打ち直しを**3Dの直接選択 + `move_sketch_entities` /
  `move_body`** へ置き換えた。半径・幅高さ・角度のような**寸法**の編集口は今回作らないと決めたので
  (押し出し済みソリッドの再計算が絡むため)、この欄は AI だけが持つ。受入スクリプトの `AI_ONLY` が
  この欄を持つ。

**交互操作も実機で通っている**(この企画の差別化点): AIが述語 `parallel_to Y` で複数の辺を提案 →
画面に提案色(水色・確定は橙)で出る → 人が1本クリックして `origin` が `user` へ遷移 → AIが読み直して
`fillet(1.5)` を適用できる。

## 1. スコープ

### 入れるもの

**スケッチのverb**: `sketch_create` / `add_line` / `add_circle` / `add_rectangle` / `add_arc` /
`pattern_rectangular` / `pattern_circular` / `import_svg`(SVGの図形をベジエのまま、いま開いている
スケッチへ足す)。

**3Dのverb**: `extrude`(領域の集合を `join`/`cut`/`new`)/ `extrude_face`(既存ソリッドの面を選んで
押し出す。スケッチ領域の押し出しとは別のverb)/ `fillet` / `chamfer`(どちらも辺ごとの配列も可)。

**各verbの引数は [../MCP.md](../MCP.md) が正**(2026-09-18 に引数表を削った —— 二重管理になるため)。

**横断機能**

- **寸法の数値入力** — すべての数値引数は「名前つきの値」として保持し、後から編集すると形状が追随する
- **領域検出** — スケッチの図形群から閉領域を自動計算する(円を線で分けて片側だけ押し出す運用の土台)
- **undo / redo**
- **入出力** — STEP読み込み(読んだ時点で編集可能なボディができる)／STEP書き出し／STL書き出し

**AI側** — MCPサーバ(§5)と、**選択集合の提案・修正・確定**

### 入れないもの

| | 理由 |
|---|---|
| 拘束ソルバ | 図形どうしの関係は現在使っていない。パラメトリック・プリミティブで足りる（§3.4） |
| ロフト・スイープ・回転 | 実測でspline面の正体がフィレットの副産物と判明しており、不要 |

## 2. アーキテクチャ

```
┌── AI（MCPクライアント）──┐        ┌── 人間（アプリ層 / ブラウザ）──┐
│  述語で引数を作る          │        │  ポインティングで引数を作る      │
└───────────┬──────────────┘        └──────────────┬─────────────────┘
            │ 呼ぶ / 読む                            │ コマンド ↓ ／ イベント ↑
            └────────────────┬───────────────────────┘
                             ▼
        ┌──────────── コア（Python・唯一の真実源）────────────┐
        │  文書（ボディ木・スケッチ）／ 選択集合 ／ 操作ログ ／ undo │
        │  ── verb層（純関数） f(文書, 選択, 引数) → 新しい文書 ──  │
        │      問い合わせ : build123d ラッパ（差し替え可能）         │
        │      操作      : OCP（OCCT）＋ 由来マップ回収            │
        └────────────────────────────────────────────────────┘
```

### 外してはいけない3つ

1. **AIの経路はアプリ層を通らない。** コアはUIが無くても機能的に完全であること。
   アプリ層にしか無い機能を作った瞬間、AIから使えなくなる。**これが層分けの唯一かつ最大の存在理由。**
2. **コマンドは下り、イベントは上り。** AIが選択を書き換えたらコアがイベントを発火し、
   アプリ層がハイライトを描き直す。この上り方向が無いと交互操作が成立しない。
3. **アプリ層が落ちて失われてよいのは、途中まで入力していたコマンドだけ。**
   文書・選択・操作ログ・undo履歴はすべてコア側。これが層の責務の判定テスト。

### verbの粒度

**verb ＝ ①undo1回で消える単位 ②操作ログ1行 ③MCP1呼び出し が一致する単位。**
食い違う切り方をしたら切り方が間違っている。UIの操作手順（スケッチ開始→面選択→中心→半径→確定）は
**1つのverbを組み立てる漏斗**であって、5つのverbではない。

## 3. データモデル

### 3.1 文書

**操作ログが唯一の正であり、形状はそこから導出されるキャッシュ。** 開くときはログから再生する
(再生経路が毎回検証されるという副作用がある)。遅くなったら最終B-repをサイドカーに置き、
**ログのハッシュで無効化**する。

**保存形式は JSON。SQLiteは使わない。** 理由: ①gitに載って差分が読める ②AIが履歴を全部読める
③1モデル＝1ファイルでコピー・共有が普通のファイル操作で済む。規模は数百操作で問題にならない。
これは document 指向のアプリであってデータのアプリではない(Fusionが `.f3d` を保存するのと同じ)。

**型の定義は `duocad/document.py` / `sketch.py` / `selection.py` が正**(2026-09-18 に当時の型の
擬似コードを削った —— コードと二重になっていた)。以下に残すのは、型からは読めない決めごとだけ。

### 3.2 ボディ(複数持つ)

**文書はボディのリストとして持つ。** STEPを読み込む時点で複数ボディになる。選択が `body_id` を持つ
ことは全verb・問い合わせ層・ピッキング・MCPスキーマに波及するコストであり、day 1 に払ってある(§6)。

### 3.3 スケッチと領域

**領域は描くものではなく計算されるもの**(`BRepAlgoAPI_Splitter`)。実測で成立を確認済み: 円(面積
1256.637)を線分で分割 → 領域 826.215 + 430.422 = 1256.637(元と一致)、大きい方だけを押し出すと
体積＝面積×高さと一致。**注意**: パラメータを編集すると領域が分裂・合体・消失しうる(押し出していた
領域が消える壊れ方をする)。§6の「黙って通さない」規律の対象。

スケッチの `plane` は基準平面または面への参照で、**壊れやすい参照**(由来スロットの対象)。

**`extrude` の `new`(新規ボディ)は `body_id` を受け付けない**(行き先の無い操作に行き先を渡されたら
取り違えである)。**`join` は行き先となるボディが無ければ新規ボディとして落ちる** —— 保存済みの
操作ログはその形で再生されるため、この落ち方は残っている。

**Bezier はSVG取り込みのために持つ図形種別**(3次ベジエ)。**これを1本ずつ作るverbは無い** ——
`import_svg` だけが作り、人もAIも直接は足せない。曲線を折れ線に落とさないのは、落とすと押し出した
側面が線分の数だけ平面に割れるためである(実測: 同じ形で面数4対130)。**取り込んだ図形の数値は
名前つきの値に登録しない**(制御点の座標は打ち直す寸法ではなく、登録するとロゴ1枚で数千個の `d1` が
並ぶ)。

### 3.4 パラメトリック・プリミティブ(拘束ソルバは持たない)

拘束ソルバ(図形**どうし**の関係を解く。この線とあの線は平行)は**持たない**。各図形が**自分の数値**を
持つパラメトリック・プリミティブ(長方形 at (x,y) 幅w 高さh 傾きa)で足りる —— 「数値を打って描く／
あとで値を編集する」という実際の運用は、後者だけで完全にカバーできる。**day 1の予防**: 打った数値を
図形の座標に焼き込まず、**名前つきの値として別に持つ**。これで拘束は将来「上に重ねる層」として
追加できる。

### 3.5 選択集合(交互操作の中核)

選択は項目の並びと `origin`(`"user"` / `"proposed"`)を持ち、**`origin` が提案と確定を区別する**ことで
企画の前提「交互操作の成立条件」の5つを満たす(AIの提案は見た目が違い、承認操作がある)。

**index は現時点の添字であって、保存はしてよいが再生時に信用してはならない**(§6)。参照IDの書式は
ocp_vscode の実証済み形式(`/Group/Solid/faces/faces_6`)を借りてよい。

### 3.6 操作ログ

1操作は `seq` / `verb` / `args`(名前つきパラメータへの参照を含む)/ `selection`(実行時に解決した参照)/
**`provenance`(★ day 1 の空スロット。§6)**。

## 4. 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| カーネル | **OCCT（OCP経由）** | 由来マップ（`Modified`/`Generated`/`History`）が取れる唯一の経路 |
| 問い合わせ | **build123d をラッパとして** | `Solid(shape).edges().filter_by(Axis.Z)` が1行。**インタフェース越しに使い、差し替え可能に保つ** |
| テセレーション | **ocp_tessellate** | 既に検証環境に入っている |
| コア | **Python** | OCPもMCPもPython。ビルダ文脈（`BuildPart`）は使わず生の `TopoDS_Shape` を保持する |
| 通信 | **WebSocket** | コマンド下り／イベント上りの双方向 |
| 描画 | **three.js** | |
| frontend | **Svelte 5 + TypeScript + Vite** | 状態のほとんどはコアにあり、frontendに残るのはコマンドの途中状態だけ（薄い状態機械1つ分） |
| CSS | **バニラ（CSS変数）** | 部品が8個程度と少なく、CADのパネルは密度が高い。**Tailwindの既定値に寄せると「よくあるWebアプリの見た目」になり、CADツールがWebアプリに見えてはいけない** |

**frontendで守るべき唯一のルール**: **canvasはフレームワークの外に置く。**
three.jsが所有するコンテナを渡し、フレームワークは二度と再描画しない。ここを外すと状態更新のたびにWebGLが壊れる。

**SvelteKitは使わない**（ルーター・SSR・アダプタ・フォームが不要なうえ、2026年の破壊的変更は
ほぼ全てSvelteKit側に集中しており、使わなければ年刻みではなく5年周期の側に乗る）。

## 5. API / MCP 仕様

**「AIがモデルを作る」ためのAPIではなく、企画の前提どおり「AIと人間が同じ選択集合を触る」ためのAPI。**

面・辺・領域を引数で受けるverbの口は、MCPにもWebSocketにも無い —— どちらもコアの**確定選択**から取る
(`duocad/selection.py` の `require_confirmed` / `require_edges`)。引数に残るのは数値・名前・パスだけで
ある。Bodyは選択集合の項目ではないので、`body_id`(どのBodyへ足す／から引くか、隠すBody)は引数のまま残る。

**ツール一覧・各verbの引数・呼び方・AIがどこまで自分で進めてよいかは [../MCP.md](../MCP.md) が正。**
ここに写すと、増減のたびに2箇所を直すことになる。

**同期の要件**: 手動操作もAI操作も**同じ操作ログに積む** / **AIの応答待ちでUIがブロックされないこと**
(手動4ステップの速さを殺さない) / **競合** —— 人間がコマンドの引数収集中にAIが選択を書き換えた場合は、
**コマンド開始時の選択をスナップショットして使う**(単一ユーザーなのでこれで足りる)。

| # | 予防 | 外したときの代償 |

## 7. 実測で判明した落とし穴

| 落とし穴 | 実測した内容 | 対処 |
|---|---|---|
| **OCCTのフィレットは例外を投げずに失敗する** | 20mm立方体・全辺: r=10.0 → `IsDone()=False`（例外なし）／**r=10.5 → 成功**／r=30.0 → 失敗。**半径に対して単調ですらない** | verbのラッパで**毎回 `IsDone()` を確認**し、失敗したら操作ごと捨てて人に戻す |
| **面の添字は形状変更で壊れる** | 同じ面を追跡してフィレットをかけると **i=5 → 9**。ただし穴の径変更・穴の追加・ポケット・面取りでは動かない＝**散発的に静かに間違う** | 生の添字を保存・再利用しない。由来スロット（予防2） |
| **build123d は由来を捨てている** | `Modified` / `Generated` / `BRepTools_History` への参照が**パッケージ内0件** | 操作はOCP直叩き。問い合わせだけbuild123d |
| **領域はパラメータ編集で変わる** | 線を y=5→6→7 と動かすと面積が変化（領域数と列挙順はこの範囲では安定） | 押し出し対象の領域が消えたら止めて聞く |
| **2つの型系の同一性は保たれる** | `==` / `hash` / `set` すべて同一視。`.wrapped` 往復でも維持 | 選択集合をbuild123dオブジェクトで持ってよい |
| **STEP往復は体積までは bit-exact ではない** | 26面・体積 23340.849375 の単純形状では差 0.00e+00。56面・体積 91018.2223598035 の形状では差 約7.3e-11（相対 約8e-16 ＝ IEEE doubleの1ULP級。再読込で面のパラメトリック表現や走査順が変わり、`GProp_GProps` の数値積分の順序が変わることに由来） | 比較は `==` ではなく相対許容差（`1e-6`）で行う。面数（`face_count`）は往復後も厳密一致でよい。 |
| **STLは近似** | 偏差 0.2mm→30.7KB ／ 0.05mm→47.2KB ／ 0.01mm→170.6KB | 偏差を設定可能にする |

### STEPエクスポートの副次的な価値

**このツールで作りかけて、Fusion360で仕上げられる。**
このツールに機能が足りないケースに突き当たってもSTEPに吐いて続ければよく、
**「作ったが機能が足りなくて詰む」というこの企画最大のリスクを構造的に消す**移行の安全網になる。
