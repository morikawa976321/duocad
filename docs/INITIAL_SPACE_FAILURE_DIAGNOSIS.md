# hangerの初期合格探索失敗の原因

2026-09-17。調査対象: `8c997e9`。探索本体の変更・大規模探索の再実行はしていない。
`models/hanger_bar_attachment.json` を使って導出各段階と初期成分選別を再現した。

**修正後の結果(同日、[FIX_BINARY_SEARCH_INITIALIZATION.md](FIX_BINARY_SEARCH_INITIALIZATION.md) §9)**:
下の測定値は修正前の記録としてそのまま残す。修正後は探索へ渡す表を材料に対応付けた確定表に変え、
荷重面31は 4.8mm で 123 節点・未被覆 0・対応不能標本 0、初期全材料マスクは実FEMを含む6条件に
全合格(安全率 164.7)し、候補管理は保持マスク数が容量(48)を超えない。修正後の同じ照合は
`topopt_checks/diagnose_initial_space.py`(幾何の表と確定表の両方を段階ごとに数える)の出力
`output/initial_space_diagnosis/stages-after-fix.json`、実機記録は `output/hanger_fix_verification/`。

## 結論

設計空間導出は正常終了している。新探索が初期マスクを拒否し、直せない状態から
修復候補を大量生成してメモリ不足になる。主因は境界条件の対応付けの契約不一致、
停止条件の不足、候補配列の先行生成・無制限保持である。
旧調査の「接続性剪定が荷重面近傍を削った可能性」は今回の実測で否定された。

## なぜ導出を通り、新探索で拒否されるのか

1. `anchor.build_anchors` はCAD面の標本点から半径1セルの球内の節点へ面積を配る。
   節点が格子内かは検査するが、材料に接しているかは見ない。除外側の節点にも配り得る。
2. `design_space.connect_seeds` は `seed & mask` の所属成分を検査する。
   条件面に対応する要素の一部が同一成分に接続すればよく、全アンカー節点の被覆は保証していない。
3. 新しい `acceptance.condition_check` と `binary_search._holds_all_conditions` は
   **全アンカー節点が材料に接すること**を要求する。
4. `_build_search_conditions` は導出時のアンカー表をそのまま渡す。
   島除去前から49/108節点が未被覆なので、初期の単一成分が丸ごと `no_component` になる。

これは形状の破壊ではなく、旧アンカー生成と新しい全節点検査の接続不備。
私が作成した6条件検査・移行計画にも、従来のアンカーが最初から材料を離れて存在し得る点を
実モデルで確認していなかった不足がある。旧導出の合格を、新しい6条件の合格と読み替えることはできない。
特に導出は安全率を計算しないので、初期モデルの安全率合格も未保証である。

## なぜ探索しても直らず、メモリ不足になるのか

探索候補Mは常に設計空間Dの部分集合。したがってMに接する節点もDに接する節点の部分集合。
D全体で既に被覆できない固定アンカー節点は、削除・追加・置換のいずれでも被覆できない。
`find_initial_feasible` は全空間での保持体積は事前検査するが、このアンカー被覆の必要条件を
事前検査せず、`no_component` から候補を追加し続ける。

さらに `repair_candidates` はyieldする前に `deletes/adds/replaces` のリストを完成させる。
各候補は格子全体のbool配列コピー。`find_initial_feasible` はそれらを上限なしのdequeに積む。
`max_evaluations` は候補を取り出す回数にしか効かず、候補生成中のメモリ消費を制限しない。

全材料の初期マスクでは追加候補がなく、サイズ別の削除候補数だけで次になる。

| 要求格子サイズ | コピー1枚 | 全サイズの削除候補数 | 配列本体の合計 |
|---|---:|---:|---:|
| 4.8 mm | 123,552 byte | 54,889 | 6,781,645,728 byte（約6.8 GB） |
| 2.4 mm | 890,100 byte | 423,625 | 377,068,612,500 byte（約377 GB） |

これは候補を割り当てず、占有ブロック数から計算した量。Pythonのオブジェクトや次世代候補の
費用を含まず、実際にこの全量の確保が成功したという意味でもない。
dequeだけに上限を設けても、生成関数内で先行確保するリストの問題が残る。

## 修正対象の順序

1. 固定空間に対する境界条件の対応付けを成立させる。材料に接する節点への初期の荷重・拘束
   対応を定義し、各荷重の合力と必要なモーメント・配分精度を検証してから固定する。
   以後の探索で失われた節点を勝手に再配分しない。未被覆節点を単に捨てて合格にしてはいけない。
2. 全空間ですら被覆できない条件は、探索前に具体的な面・節点を示して停止する。
   余白拡大や探索予算追加を一般解として案内しない。
3. 候補は操作記述または遅延生成で保持する。生成中から予算・中断・キュー上限を効かせる。
4. hangerの初期モデルで6条件を実際に評価してから、体積削減の検証へ進む。

## 再現

```powershell
python topopt_checks/diagnose_initial_space.py --model models/hanger_bar_attachment.json --spacing 4.8 2.4 --out output/initial_space_diagnosis/stages.json
```

探索・FEM・メッシュ化を実行せず、導出の各マスク・荷重節点の被覆・成分選別・候補メモリ量を照合する。
