# ローカル LLM（Qwen3.8-27B）でのアプリ内 AI の実測

**読むとき**: dGPU の無いラップトップでアプリ内 AI をローカル LLM で動かすとき、思考の設定・指示文・llama-server の起動
オプションを決めるとき、AI の失敗の型を知りたいとき。仕組みの正は [AI_INTEGRATION.md](AI_INTEGRATION.md) と README §4。

測定は 2026-10-04〜10-10。同じ題材を、コードと条件を変えながら6回に分けて回した（第1〜6弾）。**各条件1回ずつ**なので、
1題ごとの合否・時間の差は揺らぎを含む。生データ（1回ごとの JSON。思考の本文・ツール呼び出しと結果・1往復ごとの timings）は
測定したマシンのセッション作業領域にあり、リポジトリには入れていない。

## 結論

| 項目 | 結論 |
|---|---|
| 量子化 | **Q4_K_M**（17.4GB）。Q3_K_M は KLD が約4倍（PPL +4.3%）で、生成は2〜3割しか速くならない（配布元の bf16 比の表） |
| 速度 | 生成 4〜6 tok/s（MTP あり）。固定プレフィックス約8,000トークンの読み込みに 95〜115 秒 |
| 思考の設定 | **xhigh は使わない**（medium と正答率が同じで2倍以上遅い）。思考なしは速いが、知識・計算の要る依頼で予測できない落ち方をする。**low と medium の優劣は測定ごとに入れ替わった**。製品の既定は low（下の節「製品の思考の設定」） |
| 指示文 | 誤差の扱いを一文書く（[#134](https://github.com/morikawa976321/duocad/issues/134)）と、low の完璧主義のループが消えた（7/8→8/8、合計 126→101 分）。medium では差が出なかった |
| 思考量の上限 | `--reasoning-budget 2048` は最悪時間とばらつきを1/3に下げたが、**行き詰まったところで打ち切られ、誤ったまま完了と報告**した。採っていない |
| スロット保存 | **Qwen3.8 では `--slot-save-path` を付けない**。復元してもキャッシュを使えず、毎回約95秒の読み直しになる（下の節） |
| 製品の上限 | `Limits()` の既定（全体30秒・12往復・1リクエスト1,024トークン）では、このマシンではどの設定でも完走しない。製品の llama-server 経路は測定と同じ上限（60往復・16,384トークン・2時間。`duocad/net/ws.py` の `AI_LIMITS`）。古い依頼を捨てる判定に残す余地は出力上限と分けて 2,048（`LOCAL_ROOM_TOKENS`。16,384 のままだと文脈長 16,384 のサーバでツールを呼ぶたびに履歴が捨てられる） |
| 残る失敗 | 台形の重心の公式の取り違え。`measure` が面・領域・ボディの重心を返し、説明で自分で計算しないよう案内するようにした（[#136](https://github.com/morikawa976321/duocad/issues/136)。効果は未測定）。思考の縮退ループのあとの空の応答は `empty_reply` として画面に出る（[#137](https://github.com/morikawa976321/duocad/issues/137)） |

## 環境

- **マシン**: Core Ultra 7 255H、内蔵 GPU Arc 140T、DDR5-5600 16GB×2（理論帯域 約90GB/s）、Windows 11
- **GPU に回せるメモリ**: 既定は物理メモリの半分（Vulkan から 18,379 MiB）。Intel Graphics Software の「共有 GPU メモリのオーバー
  ライド」を 75% にして 24,183 MiB。上限は確保ではなく「GPU が固定してよい量」なので、上げても使わない分は CPU 側に残る
- **llama.cpp**: b11378 の Windows Vulkan 版（Qwen3.8 の GGUF は b10896 以降が要る）。SYCL 版は使っていない
- **モデル**: `bartowski/Qwen3.8-27B-GGUF` の Q4_K_M（SHA256 を配布元と照合済み）

```bash
llama-server -m Qwen3.8-27B-Q4_K_M.gguf -ngl 99 -c 65536 -ctk q8_0 -ctv q8_0 -fa on -lm none -np 1 --cache-ram 0 --spec-type draft-mtp --jinja --metrics --port 8080
```

- **`-lm none`** は以前の `--no-mmap`（この版で名前が変わった）。共有メモリの機械で、ファイルの読み込みと GPU 側の重みが
  二重に見えるのを避ける
- **`--cache-ram 0`**: 既定ではホスト RAM にプロンプトキャッシュを最大 8,192 MiB 持つ。1会話なら要らず、メモリを圧迫する
- **メモリの内訳**（`-lv 4` の起動ログ）: 重み 15,942 MiB、KV はアテンション層 16/64 層だけで 32k・f16 のとき 2,048 MiB
  （1トークン 64 KiB）、再帰状態 598.5 MiB、MTP の KV 128 MiB。`-c 65536` を f16 で取るとプロセス全体で約23GB になり空きが 0.5GB
  まで落ちたので、KV を q8_0 にして 32k f16 と同じ大きさに収めた（プロセス全体で約21GB）。**起動前に空き RAM 22GB 以上**が要る
  （Docker Desktop と WSL を止めて約4GB 空いた）
- **MTP（`--spec-type draft-mtp`）**: モデル内蔵の先読み。的中率は思考なしで 65〜80%、思考ありで 45〜75%（思考の文は当たり
  にくい）。MTP なしの速度は測っていない

## 速度

| | 値 |
|---|---|
| 生成（思考なし） | 5.2〜6.2 tok/s |
| 生成（思考あり） | 4.1〜5.9 tok/s。長く考える往復ほど遅い |
| 固定プレフィックス（system + ツール定義 41〜43 個、約8,000トークン）の読み込み | 95〜115 秒 |
| 往復ごとの追加の読み込み | 数十〜数百トークン、数秒〜30秒 |
| 1往復 | 思考なしで 10〜30 秒、思考ありで 30 秒〜19 分 |

**生成速度の理論見積もり**（帯域 90GB/s ÷ 重み 17.4GB の 6〜7 割 = 3〜3.5 tok/s）より速いのは MTP の分。

## 測り方

アプリ内 AI と同じ経路で回した。`AgentLoop` に `OpenAICompatProvider` を渡し、応答はストリーミング（`StreamingTransport`）、
文書と選択は `first_look=FIRST_LOOK` で先に置き、依頼ごとに `prepare()`（画面が繋がった時点のウォームアップに当たる）を
呼ぶ。`prepare()` の時間は依頼の所要に含めない。違いは次だけ:

- **思考の設定とサンプリングを依頼ごとに送る**（製品も `seed` を除いて同じ値を送る。`duocad/agent/providers.py` の `THINKING_PAYLOAD`）。
  `chat_template_kwargs` に `enable_thinking` / `reasoning_effort`、Qwen の推奨値（思考あり temperature 1.0・top_p 0.95・
  top_k 20・min_p 0・presence_penalty 0、思考なし 0.7・0.8・20・0・1.5）、`seed=1`
- **上限を広げる**: 60往復・1リクエスト 16,384 トークン・合計2時間（第1弾は30往復・45分→2時間）
- 思考の本文はストリーミングの断片（`delta.reasoning_content`）から拾って記録する（`_assemble` は捨てる）

**採点は文書の状態だけで行う**（AI の報告は見ない）。ボディ数、体積（題材A〜Cは ±0.1%、D は ±1 mm³）、境界箱（±0.05 mm）、
**点の内外**（`export_step` した STEP を build123d で読み、`Solid.is_inside` で「ここは穴」「ここは実体」を数点確かめる。六角形の
向き・穴の位置・重心の取り違えを体積だけでは見分けられないため）。面数は D（フィレットのかけ漏れ）だけで見る —— A〜C で
面数まで見ると、同じ形を別の手順で作って底面が2枚に分かれただけの回を落とした。採点が正解を通し、典型的な誤り（外接円半径の
取り違え・向きの30°ずれ・重心を高さの中点にする・フィレットのかけ漏れ）を落とすことを、測定の前に毎回確かめた。

**有効性の確認**: 1回ごとに「依頼の所要」と「サーバの処理時間（`prompt_ms + predicted_ms` の合計）」の差を見る。差が大きい回は
PC が止まっていた（下の「測定の運用」）。

## 題材

第2弾以降は4題材 × 2依頼文。**依頼文の取り違えはどれもツールのエラーにならない**（試して直す、が効かない）ように選んだ。

| 題材 | 正確な仕様（spec） | 人間らしい言い方（human） | 正解 |
|---|---|---|---|
| A 六角ポケット（100×60×10 の板から） | 上面中央 (50,30) に対辺距離 30mm・深さ5 の正六角形。頂点を +X に | 「M20 の六角ナットがぴったり収まる凹みを深さ5で。角を板の長手方向に」 | 体積 56,102.9（外接円半径 17.32） |
| B 体積・重さから板厚 | 60×50 の板に φ20・深さ10 のポケット、掘った後の体積が 45,000mm³ | 「座ぐり後の重さがアルミ（2.7g/cm³）でちょうど121.5g」 | 板厚 15+π/3 ≈ 16.047 |
| C 台形の重心に穴 | 頂点 (0,0)-(80,0)-(60,40)-(20,40)、厚さ10、点 (40, 17.778) に φ10 貫通 | 「下底80・上底40・高さ40の等脚台形の板の重心に φ10」 | 重心の高さ 160/9 ≈ 17.78 |
| D 曲線の辺のフィレット（穴とボスのある部品から） | 穴の上下縁・ボスの上端と根元の4本に R1 | 「曲線になってる辺ぜんぶに1mmのフィレットかけといて」 | 面数 9→13 |

- **C の human は向きが2通りに読める**（「板は上(+Z)に伸ばして」を、台形の高さを +Z に取ると読んで台形を立てる回があった）。
  立てた向きでも重心が合っていれば「別解釈で正解」として数えた
- **D はどの設定でもほぼ解ける**（`kind_is: circle` 1つで4本とも選べる）。差がつかない題材
- 第1弾は T1 板・T2 穴とフィレット・T3 フランジ（ボス・中心穴・6穴の円形パターン）の3題で、寸法をすべて依頼文に書いた。

## 思考時間のばらつき

第3・4弾の low / medium（32回・373リクエスト）で、時間の偏りは2つの型だった。

- **たまの極端な長考**: 1応答の出力は中央値 260 トークンだが、**2,048 を超えた 8% の応答が生成時間の 36%**。最初の応答は中央値
  1,447 トークン
- **同じことの考え直し**: 84分かかった回は長い応答が1つも無いまま58往復し、**58回中31回で板厚の式を最初から計算し直していた**。
  `render_messages` が前の往復の `reasoning_content` を送り返さないので、モデルは往復ごとに計画を立て直す

  ただし時間のばらつきの原因は完璧主義だけではなく、medium の合計は変わらなかった

  考えて」とシステムプロンプトの先頭に1行足すが、守られない）

## プレフィックスキャッシュとスロット保存（Qwen3.8）

Qwen3.8 は Gated DeltaNet（再帰状態を持つ層）とアテンション層の**ハイブリッド**（KV を持つアテンション層は64層中16層）。再帰状態は途中まで巻き戻せない
ので、llama.cpp は読み込みの途中で状態の控え（**context checkpoint**、1つ約180MB、最大32個）を取って巻き戻す。

| 状況（固定プレフィックス 7,987 トークン） | 読んだ量 | 再利用 | 時間 |
|---|---|---|---|
| 空からウォームアップ | 7,987 | 0 | 94秒 |
| 続けて同じウォームアップ（メモリ上） | 4 | 7,983 | 3.7秒 |
| 続けて普通の依頼（メモリ上） | 18 | 7,974 | 7.1秒 |
| スロットを消して保存ファイルから復元 → ウォームアップ | 7,987 | 0 | 95秒 |
| 同 → 普通の依頼 | 7,992 | 0 | 94秒 |

- 復元の直後、サーバは `forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory)`
  を出す。**保存ファイル（435MB）には checkpoint が入らず**、ウォームアップの末尾（`"."` と生成した1トークン）から共通部分まで
  巻き戻せないため
- **`prepare()` の復元は、メモリ上にあった使えるキャッシュを上書きする**。`--slot-save-path` 付きで測った第3弾は毎回のウォーム
  アップが約96秒、外した第4弾は2回目以降 5〜19秒（切り替え直後の1回だけ約95秒）。[AI_INTEGRATION.md](AI_INTEGRATION.md) の
  スロット保存の実測は Gemma 4（SWA、`--swa-full`）のもので、モデルの型で効き方が逆になる。duocad 側の判断（ハイブリッドでは
  復元しない等）は未起票
- **PR #100 の効果**（第2弾→第3弾、思考なし）: ツールの失敗 15→3、往復 156→106、合計 56→37 分、最初の応答 約110秒→13〜37秒。
  思考ありは時間が「どれだけ考え込むか」で決まるので、合計時間は縮まらなかった
- **low と xhigh はシステムプロンプトの先頭に1行足す**ので、思考の設定を切り替えた直後の1回はプレフィックスを全部読み直す。
  medium と思考なしの切り替えならキャッシュは保たれる

## 測定の運用（次に測る人へ）

- **PC を止めない**: Claude Code のスリープ防止（`request_keep_awake`）はセッションが約5分静かになると解ける。進捗待ちの間に解け、
  画面が消えたあとモダンスタンバイ（S0 低電力アイドル。`Kernel-Power` 506「理由: Idle Timeout」）に入って2回の測定が無効になった。
  スタンバイ中は数分ごとに「AC/DC Display Burst」で画面だけ点くが、その間に起動したスリープ防止では深い待機に戻るのを止められない。
  測定と無関係に動く小さなプロセスから `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)` を
  掛け続けると、起きている間は止まらなかった（電源設定は変えない）。蓋を閉じると止まる
- **有効性は時間の差で見る**: 止まっていた回は「依頼の所要」と「サーバの処理時間」に数千秒の差が出る（サーバのログでは生成が
  途中で止まり、`cancel task` まで何も出ない）。止まっていない回の差は0〜2秒
- **重い作業と並行しない**: 並行した回は生成が 1.6 tok/s まで落ち、9回分を破棄した
- **1回の所要が2時間に届くことがある**ので、上限を短くすると打ち切りで落ちる回が混ざる。上限で落ちた回は失敗の型が違う
  （能力ではなく予算）ので、合否と分けて記録する

## 製品の思考の設定

アプリ内 AI の llama-server 経路は、AI パネルの見出しの選択で **思考なし / low / medium / サーバ任せ** を送り分ける
（[#135](https://github.com/morikawa976321/duocad/issues/135)）。値はメモリ上だけに持ち、サーバを立て直すと既定に戻る。
切り替えても会話は作り直さず、次の往復から効く（low と他の切り替えの直後は「プレフィックスキャッシュとスロット保存」の節のとおり全部を読み直す）。
「サーバ任せ」は何も送らない —— テンプレートが思考の変数を知らない他のモデルに、Qwen 向けのサンプリングを掛けないための口。

**既定は low**（2026-10-11 本人判断）。根拠にした数字:

| 思考 | 合格（第1〜6弾の通算） | 合計時間の平均 | #125 後・誤差の一文あり（第6弾） |
|---|---|---|---|
| low | 37/40 | 156分 | 8/8・101分・標準偏差 7.2分 |
| medium | 38/40 | 163分 | 7/8・155分・標準偏差 20.9分 |

通算では区別できず、最新のコードの1回では low が速く安定していた。#135 は既定を同じ条件の繰り返し（思考なし / low / medium ×
8題 × 2〜3回、約13〜20時間）で決める案だったが、本人が採らなかった:

> 既定はlow, 測定はしなくていい。消費する時間に見合わないので。
