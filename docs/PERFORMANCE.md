# duocad — 基本操作の速さ(実測と方針)

**読むとき**: 操作が重い・待ちが長いと感じたとき、速さに効く変更をする前後。ここは**実測と判断の理由**を持ち、
いまの挙動の正はコードとテスト。実測の物差しは2本:

```bash
# サーバ単体(ネットワーク無し): verb・選択・プレビュー・解像度の決め直し・自動保存・配信1回ぶんの JSON 化
.venv/Scripts/python.exe -X utf8 tools/bench_server_ops.py
# サーバ単体: 文書を変える全 verb をプレビュー → 確定 → 配信 と MCP の確定 → 配信で(6章)
.venv/Scripts/python.exe -X utf8 tools/bench_all_ops.py --step <STEP>
# ブラウザ(puppeteer・headless Chrome・実 GPU): 読み込み・フレーム間隔・往復・クリック→描画
cd web && node scripts/bench-basic-ops.mjs
```

形状演算の書き方を変えたら、保存済みの文書群を再生して形の指紋が変わらないことも確かめる(`tools/replay_fingerprint.py`)。

結果は `output/bench_basic_ops/`(git 管理外)。2026-10-16 の数値はこのデスクトップ(Core Ultra 5 245KF / RTX 5060 Ti、
Python 3.14、Node 24、headless Chrome D3D11)。**本人のメインマシンは内蔵 GPU(Intel Arc 140T)のラップトップへ移行中**なので、
描画呼び出しの数に効くものはここでの数字より大きく効く。

## 1. 1操作がどこで時間を使うか(経路)

```
人のクリック/打鍵
 → 画面: pick(レイキャスト) → WebSocket 送信(JSON テキスト)
 → サーバ(単一 asyncio ループ・全部同期): verb → 自動保存(ログ全体の JSON 書き出し) → state_meta()(全ログ+全スケッチ+選択)
     → delta(known)(版が変わったボディだけ再テセレーション) → json.dumps → 送信
 → 画面: JSON.parse → 版が変わったボディを全面作り直し(面ごとに Mesh + EdgesGeometry の LineSegments)
     → 全面の材質を塗り直す → 全スケッチを作り直す → 次の rAF で描く
```

サーバが同期で塞がっている間は、次のクリックもプレビューも `set_view_resolution` も処理されない(`duocad/net/ws.py` の
`handle` は `async for raw in connection: await self._dispatch(...)`。`_dispatch` の中で `await` が入るのは送信だけ)。

## 4. 読み取れること(方針の根拠)

1. **小さな文書では、サーバもクライアントも数 ms で、待ちは往復(10〜13 ms)と 60 Hz のフレーム待ちだけ。** ここは既に速い。
   往復の 10〜13 ms は**ブラウザの入力後スケジューリング**: node からの素の往復 0.5 ms(`modify_selection` + `ack_id` でも 0.7)、
   同じページ内の別ソケットから 0.8 ms、ところが**同じ別ソケットでも `pointerup` ハンドラの中から送ると 16.4 ms**(10 回とも
   15.3〜16.6)。入力イベントの後、Chrome は次のフレームを描き終えるまで WebSocket の受信タスクを後ろへ回す。
   サーバでもアプリの送受信経路でもないので直す対象にしない(クリックの手応えを 1 フレーム早くするには、サーバの返事を待たずに
   画面だけで先に光らせる設計変更が要るが、「選択の正はコア」に反するし 1 フレームの差は人が感じない)。
2. **大きな文書(PC ケース)では、カメラを動かすたびに 3 秒・4.5 MB。** 原因は3つが重なっている:
   (a) focus(細かく測る面の集合)が変わった部品は丸ごと測り直す(キャッシュの鍵が「ボディ × recipe」で、面単位ではない)、
   (b) 測り直しは単一ループで同期に走り、終わるまで他の操作が止まる、(c) 結果はボディ丸ごと JSON テキストで送る。
3. **フィレット系の 1 手目(辺の取り寄せ)は部品あたり 0.5〜0.7 秒で、その 97% が連なり(`blend_chains`)の計算。** 折れ線化は 13 ms。
   連なりは形にしか依存しない(偏差に依存しない)のに、辺を描くたびに計算し、キャッシュの鍵に偏差が入っている。
4. **プレビューは「verb を最初から」+「全面を細かく」で 1 回 1 秒、確定でもう 1 回同じ計算。** 打鍵のたびに 250 ms 待ってから投げ、
   古い要求はサーバ側で捨てられない(届いた順に全部走る)。カメラ由来の再配信で同じプレビューが投げ直される(`PREVIEW_REFIRE_MS`)。
5. **スケッチの領域クリックは線が増えると 2 乗で重くなる方向**(600 本で 40〜56 ms、領域検出をクリックごとに走らせ直す)。
6. **画面は面ごとに Mesh と LineSegments を持つ**(2,835 面 → 5,670 オブジェクト)。この GPU では 60 Hz に張り付いたまま
   だが、ドローコール数は内蔵 GPU で効く。材質の塗り直しは状態配信・選択・ホバーのたびに全面を舐める。
7. **固定費**: verb のたびの自動保存(4.8 MB で 20 ms、14.9 MB で 150 ms)、配信のたびの全ログ・全スケッチ(領域の三角形込み)。

方針と Issue は GitHub の `performance` ラベル: まとめ #165、個別 #166(カメラ操作)#167(辺の連なり)#168(単一ループ)#169(プレビューと確定)
#170(JSON 配信)#171(面ごとの Mesh と常時描画)#172(スケッチ)#173(自動保存)。判断の経緯は [decisions.md](decisions.md)。

### #173 自動保存を操作の応答から外す

本人の決定(issue #5「1操作ごとの自動保存、ファイルは常に今の文書の鏡」)を保つため、書く回数・書く中身・書く時点
(配る前に中身を確定)は変えず、debounce も「配信の後に書く」もしない(配信の後に書くと、落ちたとき最後の変更を
失う窓が配信の長さ = PC ケースで 150 ms 以上へ広がる)。代わりに:

- `OpLog` が大きな操作(32 KB 以上。STEP 本文・三角形)の JSON とファイルに書くバイト列を覚え、繋がずに断片の並びで
  書く(`to_file_chunks`。中身は従来とバイト一致)。費用の正体は、日本語を含む小さな操作と ASCII だけの巨大な操作を
  文字列で繋ぐと全体が1文字2〜4バイトへ広がって写し直されること、バイト列でも 14 MB の確保と写しが連結1回ごとに 5 ms
  かかること、書き込みの改行変換だった。
- 画面の操作(`Session.background_autosave()`)では中身を確定した後、書き込みだけを1本の書き手スレッドへ回し、応答・
  配信の後に待つ。ファイルに触る口は先に待つ(`_drain_writes`)。保存の状態が変わったら(失敗・回復)配り直す。

### 残り

- 読み込み直後・ズームで多くの面を新しく測るときは、OCCT の面分割(並列で効いている)と Python の三角形の取り出し(呼び出し1回あたり
  約 1.5 µs が下限)が残る。読み込みはまだループの上。

- シェルには期限を付けない(本人の決定。decisions.md)。大きな部品では数分かかって失敗することがあるが、その間も画面は止まらない。

## 7. 残りの余地の調査と低リスクの修正(2026-11-04、autopilot。STATUS.md「残りの高速化の調査と低リスクの修正」)

判断の記録は decisions.md の `[速さ]` の後半の節。

### 物差しを足した

- `tools/bench_all_ops.py --part big`: 穴 384・485 面の合成の板。リポジトリに STEP の題材が無いので、クラウドはこれで測った。
  QR1(733 面)ではゴースト 0.4 秒の操作が、この板では 4〜10 秒かかる。**穴の多い平面への負荷試験で、本人の部品の代わりではない**。

  画面と同じ三角形分割を挟んだ指紋を前後で比べる。300 本・5,744 操作で、生成はこの機械で 13 分、再生は1回 4 分。

### 穴の多い板で何が遅いか(`--part big`、基準 4ef67570)

- 穴 384 個の平面1枚の分割(`IMeshTools.DiscretizeFaces`)が 0.8〜2 秒。1面の中は並列にならず、角度の許容が細かいほど遅い。
  変わった面にこの板が入ると、ゴースト・確定後の配信が秒の単位になる。
- カメラの粗さが変わるたびに、スケッチの領域の塗りを作り直していた(穴 384 個の領域で配信1回 1.3 秒)。
- OCP は OCCT を呼んでいる間 GIL を放さない。ループの外のワーカーで分割していても、OCCT の呼び出し1回のあいだは画面のクリックも
  MCP も待つ(この板のズームで最大 59 秒。QR1 は1回の呼び出しが短いので 0.15 秒)。
- 画面の WebSocket の圧縮(permessage-deflate)が、送信のたびにループの上で 1 MB あたり約 40 ms。

### 入れなかったもの

- 離れた柱をブーリアンを掛けずにまとめる近道(60 領域の押し出し 1.4 → 0.19 秒): 一度取り込んだが、合成の文書の1本(seed 1・文書 111)で
  結果が BRepCheck で不正になり確定が断られた(順の fuse なら妥当)。fuse と同じ形だと言い切れないので取り消した。
- ブーリアンの並列(`SetRunParallel`): テストの 1,391 回と合成の 960 組で直列と同じ、ねじは 4.2 → 1.9 秒。だが下の「並列の BRepCheck」で
  OCCT の並列に非決定が見つかったので、何十回も繰り返す突き合わせを済ませるまで入れない。
- 境界の点が 1000 以上の平面を Delabella で分割する(big のズームの配信 58.7 → 4.1 秒、ピークのメモリ 5.7 → 1.0 GB): 三角形の頂点のつながりが
  変わり、形に付いた三角形分割を書き換える。形状最適化のボクセル化・仕上げなど下流の確かめが済んでいないので、別の候補にした
  (decisions.md。QR1 でも細かい粗さで 3 面が対象になる)。
- 面の分割を子プロセスへ出す(GIL を握らせない。いちばん効くが新しい子の経路で中リスク)・MCP の確定の配信をループの外へ・
  移動の undo/redo で形の物を保つ: 案として残す(decisions.md)。

### 見つけた不具合(速さとは別。直した)

  (開き直すと正しい)。6章より前からある。ブーリアンの入力から三角形分割を外して直した。
