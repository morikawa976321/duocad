# duocad — 検証設計の教訓

**読むとき**: 検査を書く・削る・「緑だから大丈夫」と言いたくなったとき、QA の指摘を受けたとき。
duocad で実際に踏んだ実例と共に書く。テスト方針（要否基準・削減の実測）は
[DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)、実機検査の作法は [SMOKE_TESTING.md](SMOKE_TESTING.md)。

## 緑を根拠にしない

- **検査を足す・直したら一度わざと壊して赤を見る。** `look()` が件数を返すのに `.sketches.length` と書いた検査は
  起動時から何も検証せず緑だった。`web/dist` を再ビルドせずに緑になった件と同じ日 —— 「緑を根拠にしない」が1日で2回。
- **「差し替えても全部緑だった」は安全の根拠にならない**(守られていないだけの可能性がある)。実装の選択肢を
  差し替えて何も動かないときは、まず**題材がその差を出せる形か**を疑う。実例(`BRepBndLib::Add`→`AddOptimal`)は
  [TOPOPT.md](TOPOPT.md)「OCCT の bbox はトリムを見ない」、索引は [CAD_LIBRARY_PITFALLS.md](CAD_LIBRARY_PITFALLS.md)。
- **新しいガード（早期リターン・キャッシュ・短絡）を足したら、その先にあった検査が到達しているかを変異で確かめる。**
  到達しなくなった検査は消えるのではなく**緑のまま無意味になる**ので件数でも失敗数でも検出できない。
  守りたい性質を直接見る検査を1本置く（副作用の連鎖に頼った検査は経路が変わると空を切る）。
- **上流の防具があると下流の防具はテストできない。** 「消えた領域を押し出させない」防具が3枚（コアの選択リセット／
  UI の `regionsStillExist`／サーバの範囲外拒否）重なっていたが、効いているのは1だけで2の枝には到達しない。
  変異検査で層を1枚ずつ剥がすとどれが効いているか測れる。「この防具にテストを書け」と言われたらまず上流に別の防具が
  無いかを疑う。到達しない防具を消すかは設計判断で、テストが書けないことは削除の理由にならない。
- **「1回のXでYを2回以上しない」型の受入条件は、Xの内部でYが呼ばれうる箇所を先に数える。** `modify_selection` は
  内部で `_coerce_refs` を add 用・remove 用の2回呼ぶ。受入例が add だけを示していたので実装者の検証も add だけを
  なぞり、同じボディが add と remove に混ざるケースで2回数えたまま「完了」と報告した（QA が指摘）。
- **fixture が均一だと、ボディをまたぐ取り違えは検出できない。** `two_bodies` / `many_bodies` が全て同一寸法の箱
  （面6・辺12・頂点8）なので、キャッシュ鍵から `body_id` を落とす変異が pytest 799件全緑で通った。
  「数えている量」自体が異なる形状（箱＋円柱）を混ぜた fixture が要る（`tests/test_face_count_once_per_body.py`）。
  鍵から `kind` を落とす変異は面数(6)と辺数(12)が違うので即座に捕まった。
- **鍵に同じ情報を重ねて置くと変異検査が吸収される。** `(kind, ref["body"], ref["kind"], index)` は `kind` と
  `ref["kind"]` が同じ値なので片方を抜いても赤くならない。鍵の要素は互いに独立な情報だけ ——
  「各要素を1つずつ抜いたとき必ず何かが赤くなるか」で確かめる。
- **緑になったテスト新設の teeth は旧コードで実際に落として確かめる。** 落ちる箇所まで見ること —— 新設 smoke の
  2節のうち落ちたのはスケッチの節だけで、ソリッドの辺の節は旧実装でも通った（「新設 smoke は旧実装で落ちる」だけを
  報告すると辺の節にも teeth があるように読める）。手順は `cp <file> 退避` → `git show HEAD:<path> > <file>` →
  ビルド＋検査 → 戻す（共有インデックスを通る `git stash` を使わない）。
- **同じ規則がコアと UI の2箇所にあった。** `origin == "proposed"` の門は設計上 `selection.confirmed_items` 1箇所で
  コメントも「唯一の場所」と書いていたが、当時の `CommandHost.svelte` の `needsCommit` が同じ判定を先回りで持っていた(その判定はいま `duocad/server.py` の `_commit_before_verb` にある)。
  サーバ側の自動 commit だけ入れて実機で叩いたら verb が1回も飛ばず、pytest も `npm run check` も緑。
  「唯一の場所」はその層の中でだけ真。規則を変えるときはその規則の文言（「承認」「proposed」）でリポジトリ全体を grep する。
  **層をまたぐ規則の変更は pytest と型検査では検出できない。**

## 変異検査の読み方

- **定義の変異検査は「その1件だけが落ちる」ことで示す。** 「連結性は6近傍」という定義を 26近傍に変えても、壁で
  断ち切った配置も隙間を空けた2島も同じく切れていると判定される。角1点だけで接する2島という**定義を分離する題材**を
  1件用意して初めて変異が検査に映る。変異は「何個落ちたか」ではなく「狙った1件だけが落ちたか」で読む。
- **変異は「狙った落ち方」をする側へずらす。** 面添字のオフセットを `+1` でずらすと範囲外エラー（範囲検査が働いただけで
  取り違えの検出力を見ていない）。`-1` なら範囲内に留まり確実に別の面になる。落ち方（例外の型・文面）まで指定して確かめる。
- **変異試験は検査と同じ前提で作ると検査の穴を継承する。** プロンプトの区間を切り出して規則の有無を見る検査に対し、
  7通りの変異が全部その区間の中だったので、区間の外に「ただし第1段の操作も必ず提案で止める」と1文足す変異が素通りした。
  変異は検査の実装を見ずに**成果物の仕様から**発想する（区間の外側での変異を先に並べる）。
- **恒等になる特殊値でテストを書くと、その項の欠落を検出できない。** `T(p)·R·T(-p)` の回転を原点を通る Z 軸で当てると
  `p=原点` で前後の平行移動が恒等になり、`T(p)` と `T(-p)` を丸ごと消しても通った。軸を非原点にし、軸上の点・離れた点・
  軸方向へずれた点、Y軸・負の角度・長さ2の向きベクトル（`.normalize()` を消す変異で赤くなる）まで足す。
  きれいな値（原点・単位行列・0・1・軸に平行）は式の一部を恒等にする値でもある。
- **解析解との比較は「その解析解が通る応力状態」しか守らない。** von Mises のせん断項の係数 3→1 の変異は、単軸引張も
  片持ち梁の曲げも（せん断成分が0なので）通り抜ける。合成量は定義単体の検査（純せん断 `sqrt(3)·τ`・静水圧 0）を別に持つ。
- **決め打ちの微小ずらしは守りにならない。** 「ずらしは効いている」の実測は既定値が効く入力しか試していなかった
  という意味でしかない。ずらし量は決定的な列にして縮退を検知したら次の候補でやり直す（乱数は決定性を失う）。
  実例は [TOPOPT.md](TOPOPT.md)「受入検査が見ているもの」`check_voxelize.py` [8]。
- **規約の定数は1箇所に畳み、口どうしの一致を検査する。** `+0.5`（セル中心）を3つの関数がそれぞれリテラルで書いていて、
  1箇所だけ壊しても受入検査8項目が全部緑（検査が使っていたのは別の口）。**受入検査が1発で全部緑のときは変異を当ててみる。**
- **例外を見る検査は `except Exception` まで受ける。** 狙った例外型だけを `except` すると、ガードを殺した変異体は下流の
  `ZeroDivisionError` で死に、検査プロセスがトレースバックで中断してどの検査が何を守っていたか1行も残らない。3分岐にする。
- **神託との照合は高速経路が決めている量と揃える**(点と中心が表面をまたげば必ず食い違う)。離散化が曖昧な帯を
  両者から除き、除いた件数も出す。実例は [TOPOPT.md](TOPOPT.md)「受入検査が見ているもの」`check_voxelize.py` [1]、
  索引は [CAD_LIBRARY_PITFALLS.md](CAD_LIBRARY_PITFALLS.md)。
- **離散点の量が一様かを格子ビンで見ると、ビン境界を跨ぐ点1個の出入りが誤差になる**。ガウス核で平滑化して同じ核で
  平滑化した真の分布と比べる。**わざと壊した対照を同じ検査に掛けて実際に落ちることまで受入検査に含める** ——
  最初の題材では対照が閾値を下回り、その題材では検査が効いていなかった。実例は [TOPOPT.md](TOPOPT.md)
  「受入検査が見ているもの」`check_anchor.py` [5]。

## 検査の設計

- **既知の未達は「期待値を正しい側で書き、留め具で留める」。** いまの誤った値を期待値に固定する（直った側が落ちる）、
  「誤っていること」を assert する（何も寸法を見ていない）は罠。pytest なら `xfail(strict=True)`、自前ランナーなら
  `check_known_gap`。後続の仕事は留め具を外すだけ。`strict=True` を付けないと成立しても黙って緑。留めてよいのは
  外す担当（後続タスク）が決まっているものだけ。
- **契約を広げるタスクは、衝突する既存の「これで全部」アサーションを自分で退役させる。** M4 が「MCP ツールはちょうど3つ」を
  固定し、F1 が28個の契約を書き、実装タスクは両方を緑にできなかった。顔ぶれの上限を決める契約は1ファイルに1つ、古い側は
  「一致」から「部分集合」へ落として回帰ガードとして残す、「存在しないもの」の例に将来実装しうる名前を使わない。
  **同じ主張は3箇所にあった** —— `smoke-mcp.mjs` にも「3つでなければ失敗」があり、pytest 全緑の後で発覚。
  テストランナーの外にある検査（smoke・CI 設定）は pytest が緑でも赤いまま残る。
- **機能を消すと、それを題材に借りていた契約の検査も消える。** 形状最適化の案5を削除するとき、14-6/14-7 は案5を題材に
  しているだけで見ている契約（空の条件面で `"result": None` を返し、受け側が構造化例外へ変換する）は案5のものではなかった。
  assert の中身が削除する関数の外を指していたら借りているだけなので、構造ごと（正常系・例外の型・変異検査）付け替える。
- **既存の契約を変えるテスト先行タスクでは、既存の実装・テストを1行も触らず、新しい契約のテストは前提の検査で
  `AssertionError` になる形にする。** 実装時に書き換えが要る既存テストを `grep` で数えて一覧にする（推測で書かない。
  レビュアーが数え直して漏れ3件を指摘した —— 影響範囲の一覧は機械的に検証できるのでレビューに出す価値が高い）。
- **突合検査は「対象外にした側」も走らせて確かめる。** `test_applied_type_sync.py` で verb ではない通知6つを除外する
  条件を書き、除外した側を実際に走らせて「`verb` キーを返さない」ことを検査に入れたので、絞り込みを緩める変異で赤くなる。
  除外を名前の列挙で書くと**その検査自身が新しい手動同期先**になる —— 宣言側のフラグから導く。
- **文書↔コードの一致検査は、走査が効いていることを先に落とす。** 「コード側の値が文書のどこかに `in` で在るか」は
  廃止項目の居座りも節ごと消えたことも検出しない。掛かり先を見出し名で決め無ければ落とす・拾えた件数が N 未満なら落とす・
  両方向で比べる・期待値を検査側に書かない（数も顔ぶれもコード側から導出し、失敗文に「直すのは文書の行」と書く）。
  **節を切る関数はコードフェンスの内側を読み飛ばす** —— ` ```powershell ` 内の `# SIMP側…` を見出しと読んで節が空になった
  （件数ガードがあったのでその場で赤くなった）。
- **性能テストで数値の推移を見せたいなら `warnings.warn()`**（pytest は通ったテストの stdout を捨てるが warnings summary は
  既定で出す）。`filterwarnings = ["error"]` のプロジェクトではカテゴリを除外する。`record_property` は junit にしか出ない。
- **状態の版は「経路」ではなく「状態」から導く。** 差分送信の版を「押し出したら上げる」「隠したら上げる」とイベントを
  数え上げる形にしていたら、非表示→再表示→undo/redo と同じ穴が経路を変えて3ラウンド続けて指摘された。
  `(形状の同一性, visible)` の組から導けば経路が増えても追随する。**QA が穴を1つ出したら、その1件を直して再 QA に出す前に
  同じ理屈で壊れる他の経路を自分で列挙して一緒に潰す**（4ラウンドで major 5・minor 7。1ラウンドの費用は件数によらない）。
  指摘が「単発の書き漏らし」か「設計の帰結」かを先に決める。
- **「コストが高いので見送った」残穴は、見送る前に実際に踏めるか1回試す。** 即適用の待ち構え中に AI が選択を書き換えると
  人が指していないのに操作が走る穴を「骨格の契約面が増える」で見送ったが、QA が差し戻して実測させたら踏めた
  （AI の選択変更だけで部品が 27→28）。配管は既に別ファイルにあり渡していないだけだった。骨格の契約面を増やすかは
  その骨格を作っているタスクで決着させるのが安い。
- **書かれた再現手順は書いた時点の実装に対する記述。** 「参照 STEP を移動しただけで rebuild の後始末が要る」は、
  STEP を埋め込んだ後は成立しない。テストを書く前にその場で一度踏む。代わりの壊し方: 矩形反復 3×2 の6番目を押し出して
  `set_parameter` で `nx` を 3→1 に落とす（値の検査は通り、再生中の `extrude` が「その添字の領域が無い」で落ちる）。
- **計測器は両側を同じ定義で固定する。** M1 の操作速度計測で自作側が `pointerdown` から、Fusion 側の手順書が
  「面に手が伸びた瞬間」からで、マウス移動時間が Fusion 側にだけ入り自作が系統的に速く見えた。入力欄に既定値があると
  「打たずに Enter」で打つ時間0の行が「速い」として記録される。自分の道具の器は意図せず有利な側にバイアスが入るので、
  区間の定義を別モデル・別人に突き合わせさせる。
- **調査コードは残さない。残すのは結果と判断**（本人 2026-09-04）。例外は**計器**（将来もう一度その測定をやるか）。
  `perf.py` は新旧を比べるタスクが依存するので残す、一度きりの調査（余白 0.25 の根拠を出した `measure_margin`）は捨てる。
  製品へ移すモジュールの中に一度きりの調査コードが住んでいることがある。
- **測定の成果物のファイル名には振った軸を全部入れ、集計側に照合の門（保存前の実物から取った SHA-256 と格子）を置く。**
  解像度が名前に無く3解像度が同じファイル名になり、上書きされた側は基準も比較対象も同じ配列を読むので `a.shape != b.shape`
  の検査を素通りした（レポートの2行が別解像度の値になった）。張り替えは「測定ごとの名前」ではなく「内容の名前」
  （`{題材}_{格子}_{SHA-256}`）。ファイルから読み直さない設計は上書きに耐える。表は生データから機械生成する。
- **「改善前 A 秒 → 改善後 B 秒」を別の時刻に測った A と B で言わない。** 同じ SIMP がセッション序盤 12.2秒、1時間の
  連続負荷後 21.2〜25.9秒（サーマルスロットリング）。その変更で1行も触っていない処理（`check_voxelize.py`）を同じ回に
  混ぜて物差しにする。境界ぎりぎりの目標は何回測って何秒だったかをそのまま書く。
- **bit-exact 基準（SHA-256）は題材を意図的に変えた回に取り直すのが正しい**（検査の弱体化ではない）。取り直すのは
  題材を変えた側だけにし、片方が変わっていないことの担保にする。**`A == B`（「既定を変えていない」）で守ると A と B の
  どちらを動かしても落ちる** —— 守りたいのが B だけなら `B == <定数>`。実例は [TOPOPT.md](TOPOPT.md)
  「既定の挙動が変わっていないことの担保」「回帰基準が動いていないことの担保」。
- **「無い」の検証は `None` と空を両方見る。終端の合格判定を「違反件数 == 0」で書かない**（母集団0件で真になる）。
  `reactions=[]` が `is None` 検証を素通りし、制約が1本も作られないまま `reaction_min=0.2` を持った無制約の結果が
  正常終了で返っていた（`max_iter=0` も同型）。「何件検証したか」を先に見る。門を外した版で新しい検査が落ちることまで確認する。
- **「この経路は通る」を途中の関数を1つだけ呼んで確かめない。** `_region_representation` を単独で呼ぶと 2.4mm で通るが、
  入口 `optimize_run.run` からは手前の門で 2秒で落ちて SIMP は1回も呼ばれない。測った値は正しく結論だけが間違い、
  それが後続タスクの完了条件に写された。途中から呼んだときは「◯◯の門は通る」と書く。高い経路でも門だけは入口から通す。
- **所見と対応案は検証の強度が違う。** コード調査レポートで「Body が消えてもキャッシュが落ちない」（正しい）に対し
  「削除 verb の実装箇所で pop する」は実在しない場所を指していた（削除 verb は無く、`remove_body` を呼ぶのは undo ハンドラ。
  正しい形は `sketches_state()` に前例がある生存集合での剪定）。タスクへ落とす前に**対応案の側だけ現物で裏を取る**
  （その場所は実在するか・その層はその状態に触れるか・同じ問題を既に解いている前例が無いか）。
- **散文の規則は検査を厚くせず「人が守る領域」に切り分ける**（[AI_INTEGRATION.md](AI_INTEGRATION.md)）。
- **「コメントしか触っていない」の証明はビルド成果物のハッシュ比較。** `dist/assets/index-*.js` / `.css` / `index.html`
  が同一バイトで、変わるのは sourcemap だけ（`sourcesContent` に原文を埋め込むため）が期待される署名。Python 側は
  docstring を取り除いた `ast.dump` を比べる（`tools/check_code_unchanged.py`）。
- **消すフォルダへの参照はフォルダ名で grep しても全部は出ない。** `probe_topopt` を消したとき、名前を書かずに
  「隔離フォルダ」と現在形で説明する節と、移設後に別ファイルと衝突する裸のファイル名（`server.py` / `web/index.html`）が
  残った。通称・特徴的なファイル名・サブフォルダ名を裸で取り直し、その場所に触れる文書は通しで読む。
  実装の差し替え（`Add`→`AddOptimal`）で文書を掃くときは**新しい名前ではなく捨てた側の名前と、その節の数値の根拠**で探す
  （「0.003秒」は `Add` の測定値だが文中に `Add` の語が無い）。
- **「N箇所塞いだ」と数を書くなら根拠になった検索式も書く。** `grep "\.shape"` に出ていたのに、呼び出しの引数の中にある
  使用（`query.describe_faces(body.shape)`）は「その関数の話」に見えて落とした（QA が9箇所目を再現）。フィールド名で引く
  のと、所有側のコレクションを舐める場所（`grep "\.bodies"`）から引くの2方向。最終的に12箇所。
- **`git stash` は使わず、パスを触るなら `git stash push -- <path>`。** 別セッションの退避物には触れない
  （A/B 計測で `viewport.ts` だけ退避し、`App.svelte` に触れずに `window` へ計測フィールドを生やした手順の成立条件は、
  フックの有無を切り替えるたび `npm run build` を挟むこと）。
