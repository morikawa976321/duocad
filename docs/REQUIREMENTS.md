## 0. 呼称

**「必要最低限の機能をもったミニマルなモデリングツール」**（2026-08-07本人決定）。
「機能削減版Fusion」は使わない — Fusionと呼ぶと履歴・スケッチ拘束・アセンブリが
自動的に期待値に入り、スコープが膨張するため。

## 1. 何が変わったか

**旧要件**: コードCADが主で、自作するのは「どこを指しているかをLLMに伝えるレイヤー」。
手動操作はAIへの入力手段という位置づけだった。

**新要件**: **手動操作それ自体が一級の操作モードである。** AIへの入力手段ではない。

決定的な観察（本人の言葉）:

> 特定の面の押し出しなどは選択→押し出しを選択→数値指定→Enterの4stepですぐおわる。
> これをいちいちAIに依頼するのはむしろ時間がかかる。

これは「AIが下手だから手動が速い」ではない。**指示の情報量に対してチャネルの帯域が合っていない**
という構造的な話であり、AIの性能が上がっても解消しない。したがって
「いずれAIが賢くなれば手動は要らなくなる」という前提を置いてはならない。

## 2. 分業の原則（仕様の中核）

| 指示の性質 | 最速のチャネル | 理由 |
|---|---|---|
| **「どれ」**を特定する（この面、この辺） | **ポインティング（手動）** | 位置情報の伝達に言語は極端に非効率 |
| **「条件を満たす全部」**（全辺、上面の外周） | **言語（AI）** | 述語1つ vs Nクリック |
| **形状そのものが未定**（大まかな形を出す） | **言語（AI）** | 手続きが長く探索的 |
| **手続きが面倒だが機械的**（一括フィレット等） | **言語（AI）** | 人間側の作業量だけが大きい |

**帰結**: 分担の境界は「作業の種類」ではなく「**対象集合をどう指定するか**」で決まる。
そしてこの境界は固定ではない — **選択集合を受け渡せるなら、1つの操作の中で分担できる。**

### 2.1 交互操作（この仕様で最も重要な要件）

```
AI: 述語で候補集合を作る  →  ユーザー: 過不足をクリックで修正  →  AI: 操作を適用
```

**成立条件は1つだけ: 選択集合が第一級の共有オブジェクトであること。** 具体的には:

1. **永続**（操作の合間に消えない。UIの一時状態ではない）
2. **双方向**（AIが読める／**AIが書ける**／ユーザーが読める／ユーザーが書ける）
3. **種別を保持**（面/辺/頂点を区別する）
4. **差分編集可能**（追加・除去。作り直しではなく）
5. **出所を区別**（AIの**提案**か、ユーザーが**確定**したものか）

### 2.2 現状の土台はこの要件を満たさない（実機確認済み）

| 要件 | ocp_vscode 4.0.1 の現状 |
|---|---|
| ユーザーの選択をAIが読む | **可**（`status()` ポーリング。往復中央値39ms） |
| **AIが選択を書く** | **不可。APIが存在しない**（`set_viewer_config` に `selected` なし、JS側に受け口なし） |
| 種別の保持 | **不可**（`faces_6` も `edges_6` も `"6"` に潰れる） |
| 提案／確定の区別 | 概念が無い |

**交互操作は ocp_vscode の上には載らない。ビューアへの改変が必須。**

## 3. Fusion360の位置づけ

| 軸 | 評価 |
|---|---|
| 手動操作 | **完璧。基準線であり下回ってはならない** |
| UI | モダン・シンプル。**これも基準線**（FreeCADはここで却下された） |
| AI操作 | 弱い。実用上「パラメータ指定でプリミティブを出す」程度 |
| 継続性 | **常に不安**（教育ライセンス失効・クラウド束縛・大企業依存・Linux非対応） |

（Fusion360のAPI自体はフィーチャ生成まで含む本格的なもので「プリミティブだけ」ではない。
ただしLLMのループ前提の設計ではなく継続性の不安も変わらないので、離脱の判断は動かない。）

**作るべきものの定義**:

> **Fusion360と同等以上にモダンでシンプルなUIに、
> 「自分が実際に使う手動操作」と「強力なAI操作」を載せ、
> 両者が同じ選択集合を交互に触れるようにしたもの。**

## 4. 3つの分岐（第2稿での状態）

| | 論点 | 状態 |
|---|---|---|
| ① | 手動操作の集合 | **決定済み** — 最小セットから始め、拡張前提で設計する |
| ② | 履歴を持つか | **判断材料を出した（§4.2）。選択は未確定** |
| ③ | 土台 | **保留** — ①②が決まってから。ただし§4.3の2条件で既にかなり絞られている |

### 4.1 決定①: 最小セットから拡張前提で設計する

**この判断は妥当。** ただし「事後拡張は難しくない」という予測は**大部分正しく、例外が短いリスト
として存在する**。区別は「**verbを足すのか、データモデルの次元を足すのか**」。

**あとから自由に足せるもの（＝verb。設計不要）**
押し出し・フィレット・面取り・穴・シェル・面移動・ブーリアン…
いずれも `f(shape, selection, params) -> shape` の形に収まるので、1個足すのは独立作業。

**あとから足すと高くつくもの（＝データモデルの次元）**

| 拡張 | 事後追加のコスト | day 1でやっておくこと |
|---|---|---|
| **履歴・再生成** | 高い | **操作ログ（§4.2 L1）を最初から持つ。ほぼ無料** |
| **由来の追跡（永続命名）** | **非常に高い（全操作の書き直し）** | **操作の戻り値に由来情報のスロットを空で用意する。1操作あたり1行** |
| **アセンブリ／コンポーネント** | 高い（選択の宛先・UIツリー・操作層すべてに波及） | **文書を「配置された物体の木」と定義する。当面は常に1個、でよい** |
| **undo/redo** | 操作ログがあれば無料 | 上の1つ目に含まれる |
| **スケッチ拘束** | 大きいが**加算的**（既存を壊さない） | 何もしなくてよい。本当に後回しでよい唯一の大物 |

**要点**: day 1で払うべきコストは合計で数十行程度。この3行の予防だけしておけば、
「事後拡張は難しくない」という予測は**実際に正しくなる**。

### 4.2 決定②: 履歴の実装コスト見積もりと中間段階

#### 実測でわかったこと（2026-08-07）

永続命名（＝履歴の最難所）が現実的かを確かめるため、**添字を実際に壊した操作**で試した:

```
基準形状の右側面      : 添字 i=5 / area 800
縦エッジにフィレット後 : 添字 i=9 / area 680   ← 添字はずれる
mk.Modified(旧面)     : 戻り 1件 → 新添字 i=9 / area 680  ← 正しく追跡できた
```

- **OCCTは由来マップ（`Modified` / `Generated` / `IsDeleted` / `BRepTools_History`）を持っており、
  この環境（OCP）から直接叩ける。永続命名の中核は約20行で動いた。**
- **ただし build123d はこれを捨てている**（`Modified`/`Generated`/`BRepTools_History` への参照が
  パッケージ内に**0件**）。**履歴を持つなら、操作層は build123d の高レベルAPIではなく
  OCP を直接叩く形になる。** これが履歴コストの本体。

> FreeCADが10年かけた話を前回持ち出したが、**あれは巨大な既存コードへの後付けの話**であり、
> 由来マップを最初から通す新規実装のコストとは別物。前回の悲観は行き過ぎだった。

#### コスト見積もり

差が出るのは**文書モデルと操作層だけ**で、ビューポート・ピッキング・コマンド層・MCP層は共通。

| 部位 | ダイレクト | 履歴あり（永続命名） |
|---|---|---|
| 文書 | 現在の形状1つ | 操作列 + 名前表 |
| 操作 | build123dを1回呼ぶ | **OCPで組み立て、由来マップを回収して名前表へ写す** |
| 再生成 | 不要 | 再生エンジン（依存・部分再生・失敗時の状態） |
| 参照解決 | 不要 | 名前解決・曖昧性処理・**参照喪失時のUX** |
| undo | 形状のスナップショット | 操作ログを巻き戻す |
| テスト | 通常 | **名前まわりは専用のテストが必須**（黙って壊れるため） |

##### build123d と OCP直接の抽象度の差（2026-08-07 実測）

同じ形状（箱60×40×20＋貫通穴r8＋縦エッジr3フィレット）を3通りで書いて測った。
**3つとも体積 43824.2481 で完全一致。**

| 書き方 | import | 本体 | 合計 | 倍率 | 由来マップ |
|---|---|---|---|---|---|
| **A** build123d 純正 | 1 | 6 | **7行** | 1.0× | 取れない |
| **B** OCP 直接 | 10 | 22 | **32行** | **4.6×** | 取れる |
| **C** ハイブリッド（問い合わせ=build123d／操作=OCP） | 3 | 9 | **12行** | **1.7×** | **取れる** |

**差がどこに集中しているか（Bの内訳）**:

| 部位 | OCP直接 | build123d | 差 |
|---|---|---|---|
| **述語による問い合わせ**（Zに平行な辺を選ぶ） | **11行** | **1行** | **ここが差のほぼ全部** |
| プリミティブ＋ブーリアン | 7行 | 3行 | 小 |
| フィレット操作そのもの | 5行 | 1行 | 小 |

**抽象度の差は「操作」ではなく「問い合わせ」に集中している。**
`TopExp_Explorer` で辺を列挙し `BRepAdaptor_Curve` で種別と方向を判定する定型が、
build123d では `.edges().filter_by(Axis.Z)` の1行になっている。

##### 推奨アーキテクチャ（実測で成立を確認）

**コアは生の `TopoDS_Shape` を保持し、build123dは「問い合わせラッパ」としてだけ使う。**
`BuildPart` のビルダ文脈は使わない — 自作の操作ログと競合するため。

```
コア:      shape = <生の TopoDS_Shape>
問い合わせ: Solid(shape).edges().filter_by(Axis.Z)      ← build123d を包むだけ
操作:      BRepFilletAPI_MakeFillet(shape) + Add + Build ← OCP。由来も回収
連鎖:      Solid(new_shape).edges()...                  ← そのまま次へ
```

実測で、この形が動くことと**操作をまたいだ連鎖・由来追跡が成立する**ことを確認済み
（上面 area 2400 → フィレット後 2392.27 を `Modified()` が1件で追跡）。

##### 上記を踏まえたコスト見積もりの訂正

- **操作層の書き直しコストは、当初の見立てより安い。** 1 verb あたり **+3〜5行**程度で、
  「全操作を書き直す恒常税」という表現は誇張だった。
- **かさむのは問い合わせ層だが、これは1回書けば済み、しかも履歴の有無に関係なく必要**
  （§5のMCPが述語を要求するため）。**履歴を持たない場合でも発生する費用なので、
  履歴のコストに数えてはいけない。**
- **よって「差分部分で4〜6倍」の内訳は、操作の書き直しではなく
  再生エンジン・名前表・参照喪失時のUX・専用テストに帰属する。**
  アプリ全体で1.5〜2倍という結論は変わらないが、根拠は上記に置き換える。

##### 実装上の注意（実測で判明）

**由来の取り出し方は操作ごとにインタフェースが違う。**
`BRepAlgoAPI_*`（ブーリアン）は `History()` を持つが、`BRepFilletAPI_MakeFillet` は持たず
`Modified()` / `Generated()` / `IsDeleted()` だけを持つ。
→ **操作ごとに由来を正規化する薄いアダプタが要る。** §4.2で「操作の戻り値に由来スロットを
用意する」と書いたのは、まさにこの正規化の置き場所である。

- **差分部分だけを比べると 4〜6倍**（内訳は上記の訂正を参照）
- **アプリ全体で見ると 1.5〜2倍**（UI側にも履歴パネル・再生失敗表示が要るため）
- **ただし本当のコスト差は工数ではなくリスク**。命名の失敗は**例外を出さず違う面を操作する**形で
  現れ、データ依存で再現しにくい。工数2倍・デバッグ難度はそれ以上、と見るのが安全。

**コストの形が重要**: この差は**アプリ全体に薄く広がっているのではなく、1つの部分系と
「1操作あたりの税」に集中している**。だから分割できる。

#### 中間は存在する（5段階）

| 段階 | 内容 | できること | 追加コスト |
|---|---|---|---|
| **L0** | 直接編集のみ | undoは形状スナップショット | — |
| **L1** | **追記専用の操作ログ** | 再生できる／AIが履歴を読める／gitに載る／undoが無料 | **ほぼゼロ。day 1で入れる** |
| **L2** | 末尾編集 | 最後のN手を取り消す・やり直す | L1があれば自明 |
| **L3** | **ベストエフォート再解決** | 手動操作時にセレクタ式を合成して記録。再生時に再解決し、**一意に決まらなければ止めて聞く** | 中 |
| **L4** | **OCCT由来マップによる永続命名** | 途中のパラメータを変えても以降が生き残る | 大（上の見積もり） |

**L3の設計目標は「常に正しい」ではなく「黙って間違えない」。** 人間がその場にいる個人用ツールなら
これで十分成立し、真の永続命名より桁違いに安い。
（なおL3は、旧「deixisレイヤー ＝ 添字→セレクタ式の逆合成」構想そのものである。）

**L4は操作ごとに足せる。** 由来を返さない操作は「ここで同一性が切れた」と記録し、
再生はそこで止まって人に聞く。だから**フィレット・面取りのような実際に壊れる操作から順に**
L4化していけばよく、一斉移行は不要。

> **重要な整理**: 「述語で集合を作る」（AIの機能）と「同じものを操作をまたいで指し続ける」
> （履歴の機能）は**別物**である。前者は履歴の有無に関係なく§5に必要。
> 旧「セレクタ式」構想はこの2つを混同していた。

#### 推奨

1. **L1を day 1 から持つ**（ほぼ無料。以降すべての土台）
2. **操作の戻り値に由来情報のスロットを空で用意する**（1操作1行。L4の後付けを可能にする唯一の予防）
3. **初期の挙動は L0+L2**（ダイレクト＋末尾編集）で出す
4. **痛みが出てから、壊れる操作から順に L4 化**する。L3は L4 が塞がった箇所の代替として使う

**この順序なら、「履歴を持つか」を今決める必要がない。** 決定②は
**「day 1で数十行の予防を払うか」だけに縮む**。払っておくことを推奨する。

### 4.3 決定③: 土台（保留。ただし2条件で既に絞られている）

最後に決めるという判断でよい。ただし**§2.2と§4.2から、土台には2つの必須条件が確定した**:

- **(a) 選択をプログラムから書き込めること**（交互操作の必須条件。ocp_vscodeは不可＝改変前提）
- **(b) OCCTのカーネルを直接叩けること**（L4を将来足すため。ラップして隠す土台は不可）

| 案 | (a) | (b) | 判定 |
|---|---|---|---|
| **B1** 自作Web UI + OCCT | 設計次第で可 | 可 | **有力**。実装量は最大だがUIの自由度も最大 |
| **B2** ocp_vscodeのビューアを改変してコマンド層を足す | **改変すれば可** | 可 | **有力**。交互操作の設計検証には最短 |
| **B3** Blender + CAD Sketcher | 可 | **不可**（メッシュ主体） | **脱落見込み** |
| **B4** Plasticity + 自作MCP | API未調査 | ほぼ不可 | **脱落見込み**（要1点調査） |

**実質 B1 か B2 の二択**。B2で交互操作を検証してからB1へ移す、が費用対効果は高い。

## 5. API/MCP の要件

**「AIがモデルを作る」ためのAPIではなく、「AIとユーザーが同じ選択集合を触る」ためのAPI**。

**選択（中心）**
- `get_selection()` → 種別付きの集合
- `propose_selection(predicate | ids)` → **提案**状態で書き込む（確定選択と見た目が違う）
- `modify_selection(add=[], remove=[])` → 差分編集
- `commit_selection()` / `clear_selection()`
- 述語の例: `faces where normal·Z > 0.9` / `edges where length > 20 and parallel_to Z`

**問い合わせ**
- `describe_shape()` → 面・辺の数、境界箱、特徴の要約
- `measure(selection)` → 面積・長さ・法線・中心

**操作**
- `apply(op, selection, params)` → 決定①の最小セットがそのままここになる
- `undo()` / `redo()` — 交互操作では必須（AIの結果を1手で捨てられること）

**同期**
- 手動操作もAI操作も**同じ操作ログに積む**
- **AIの応答待ちでUIがブロックされないこと**（手動4ステップの速さを殺さない）

### 5.1 verbの粒度（2026-08-07 追記）

#### 層を2つに分ける

UIの操作手順とverbの粒度は**別の階層であり、一致させてはならない**。

| 層 | 役割 | 例（円を描く） |
|---|---|---|
| **コマンド層**（UI） | 引数を集める状態機械。プレビューあり。Escで中断 | スケッチ開始→面を選ぶ→中心を打つ→円周上を打つ→終了 |
| **verb層**（モデルAPI ＝ MCPのツール） | 引数が揃った操作を1回適用する純関数 | `add_circle(plane, center, radius)` **1回** |

**コマンド層はverb層の引数収集器にすぎない。** 5ステップは1つのverbを組み立てるための漏斗であって、
5つのverbではない。

**この分割は §2 の分業原則の構造的表現そのもの**である — 人間はポインティングで引数を集め、
AIは言語・述語で引数を集める。**集め方が違うだけで、最後に呼ぶverbは同一**。
だから交互操作が成立する。

#### 粒度の判定規則

**verb = 次の3つが一致する単位。**

1. **1回のundoで消える単位**
2. **操作ログの1行**
3. **MCPの1呼び出し**

この3つが食い違う切り方をしたら、切り方が間違っている。

- 「面を10mm押し出す」: undoで押し出しが消える／ログ1行／`extrude(face, 10)` 1回 → **一致。1 verb**
  （UIの4ステップはverbより下の層）
- 「円を描く」: undoで円が消える（クリック1回分ではない）／ログ1行／`add_circle(...)` 1回 → **一致。1 verb**

**3つが一致しないものは、verbではなく部分系である。** スケッチがまさにこれ:
Fusionではスケッチモード内のCtrl+Zが**個々の図形**を取り消す＝**入れ子のundoスコープを持つ**。
これは「スケッチ＝図形と拘束を保持する文書の子オブジェクト」であることの証拠であり、
**1つのverbには収まらない**。§4.1で「スケッチ拘束は加算的な大物」と分類したのはこの理由による。

#### 層の責務の分界（2026-08-07 本人の確認を受けて明文化）

「UIでの操作はアプリ層が保持し、必要なものが揃ったらAPIでコアに渡す」で正しい。
ただし**3点だけ、外すと設計が崩れる**:

1. **AIの経路はアプリ層を通らない。** MCPはコアを直接叩く。
   → **コアはUIが無くても機能的に完全でなければならない。** アプリ層に「そこにしかない機能」を置いた瞬間、
   AIから使えなくなる。これが層分けの唯一かつ最大の存在理由。
2. **プレビューのため、コアは確定前にも何度も呼ばれる。** 「揃ってから1回」ではなく
   「暫定の引数で投機的に何度も呼び、捨て、最後の1回だけログに積む」。
   → verbが純関数である必要はここから来る。
3. **選択集合はアプリ層ではなくコアに置く。** §2.1の要件2（AIが選択を**書ける**こと）を満たすため。
   ここを間違えて選択をUIの状態にすると、**交互操作が原理的に不可能になる**。

**判定テスト**: 「アプリ層が落ちて再起動したとき、何が失われるべきか」
→ **途中まで入力していたコマンドだけ**。文書・選択・操作ログ・undo履歴はすべてコア側に残る。

#### スケッチは必須（2026-08-07本人決定）

> スケッチは厳密で複雑なモデリングをするための必須機能

**採用する。** 以下は「スケッチを持たない最小セット」案（下記）を退けた上での構成。

**スケッチは1つのverbではなく部分系**であり、中身は:
①スケッチ平面の参照 ②2D図形（点・線・円弧・円） ③拘束（幾何拘束＋寸法拘束）
④**拘束ソルバ** ⑤閉領域の検出（何を押し出すか） ⑥入れ子の編集セッション。

**構造上の要点**: スケッチ編集セッションは**同じアーキテクチャの入れ子インスタンス**である。
独自の文書（2D図形＋拘束）・独自の選択・独自のverb（`add_line` / `add_constraint` / `dimension`）・
独自のundoスコープを持つ。**特別扱いではなく再帰**なので、層の設計はそのまま再利用できる。

**最大の未知だった拘束ソルバは、書かなくてよい（2026-08-07実測）**:

```
python-solvespace 3.0.8 を導入し、雑に置いた4点の矩形に
 horizontal×2 / vertical×2 / distance×2 を与えて solve:
   (0,0) (31.7,2.4) (29.1,18.6) (-1.2,21.3)
     → (0,0) (60,0) (60,40) (0,40)   厳密に解けた
 寸法だけ 25×80 に変えて再解決 → (25,80)  パラメトリック駆動も成立
```

- SolveSpaceの拘束ソルバ（`slvs`）はPythonから直接使え、**約20行で動いた**。
  スケッチの最難所は既製品で埋まる。
- **ただし`dof()`の値が手計算と合わなかった**（完全定義なら0のはずが6を返す）。
  Fusionの「完全定義（青→黒）」に相当する表示を作るなら、**DOF判定の意味は要調査**。
- **ライセンスは GPLv3+**。個人利用なら問題ないが、配布・販売を考えるなら効く。
  代替は FreeCAD の `planegcs`（同じくGPL系）。回避したいなら自作が必要になる。

**残るコストは、ソルバ以外の部分**: 閉領域の検出／2Dエディタのコマンド層／
描画中の自動拘束推定（Fusionが勝手に水平・垂直を付けてくるあれ）／入れ子の選択とundo。
**ソルバが埋まったことで「未知の塊」ではなくなったが、依然として最大の部分系**である。

**決定②への波及（重要）**: スケッチは面に貼り付く。「**この面にスケッチする**」という参照は、
モデルが変わったときに**最初に壊れる種類の参照**である。
→ **スケッチを必須にしたことで、§4.2の「day 1で由来スロットを用意しておく」の価値が上がった。**

#### （参考）スケッチを持たない案 — 今回は不採用

スケッチ＋押し出しという2段構えは、**任意の輪郭を作れるようにするためのFusionの一般性の税**である。
穴・ボス・矩形ポケットのような**決まった形**なら、フィーチャ級のverbで直接作れる:

| Fusion流（スケッチ経由） | フィーチャ級verb | ユーザーの手数 |
|---|---|---|
| スケッチ開始→面選択→中心→円周→終了→押し出し→深さ→OK | `hole(face, center, diameter, depth)` | **面を選ぶ→中心を打つ→径を打つ→Enter** |

**手数は5〜8ステップから4ステップに減り、実装からはスケッチ部分系が丸ごと消える。**
これは机上の話ではなく、build123d が既にこの形（`Box` / `Hole` / `fillet` / `chamfer` が
スケッチ容器なしのフィーチャ級verb）で、検証で実際に使っている。

**この案を退けた理由**（2026-08-07本人判断）: 厳密で複雑なモデリングには任意の輪郭が要る。
ただし**フィーチャ級verbは併存させる価値がある** — 穴のような決まった形は、スケッチ経由より
手数が半分で済むため。**「スケッチが要るものはスケッチで、要らないものはフィーチャ級verbで」**が最終形。

#### 避けるべき切り方

- **細かすぎ**（UIの1ステップ = 1 verb）: `enter_sketch_mode()` `pick_plane()` `set_center()` …
  → **AIがモーダルな状態機械を人間の真似で駆動する羽目になる。** ログは再生不能、undoの粒度も壊れる。
  **MCPをUIの操作手順の写しにするのが、この設計で最もありがちで最も致命的な失敗。**
- **粗すぎ**（「ブラケットを作って」= 1 verb）: 途中結果を指せない、undoが効かない、
  交互操作の割り込み点が無くなる。

#### verbに課す2つの制約

1. **純関数であること** — `f(document, selection, params) -> new_document`。文書を破壊的に変更しない。
   これで **undoが無料**（前の文書を持つだけ）になり、**プレビューも無料**になる
   （確定前にverbを投機的に走らせて捨てる）。
2. **既存の選択を先に消費すること** — コマンド起動時、引数の収集はまず**共有選択集合**を見る。
   空のときだけユーザーに問う。**これがAI→人間の受け渡しが自然に成立する仕組み**
   （AIが選択を提案 → 人がverbを起動すると、その選択がそのまま引数になる）。
