# 当たり判定（screen pick）— 優先順位・基準平面・コスト・検査の落とし穴

**いつ読むか**: スケッチ/辺/頂点/面/領域の「掴みやすさ」を直すとき、ピックが対象を取り違える・
取れないバグを追うとき、または当たり判定がらみの実機検査（smoke/acceptance）が原因不明で
落ちたときに読む。

## ヒット優先順位（hit priority）

- ピック解決を**固定の優先順位**（例: 辺 → 領域 → 頂点 → 面）で書くと、下位の的が上位の的の
  上に**幾何的に必ず乗っている**場合、その的は一生指せない。症状は「クリックしても何も起きない」
  だけで、例外・警告は出ない（2026-09-06実測）。
  - duocadの実例: 頂点は必ず辺の端点に乗っており、`move_body` 起動中は常に辺が出ているため、
    回転中心の頂点は100%辺に取られていた。
  - **解き方は2つ、「外したときに何が起きるか」で選ぶ**:
    1. **要求中だけ順序を入れ替えるゲート**（`viewport.preferVertices(on)`）。外しても何も
       起きない（狙った的の代わりに捨てられるだけ）衝突ならこちら。
    2. **要求中だけ上位の的を画面から引っ込める**（配信そのものを止める）。外すと**共有選択が
       書き換わる**種類の衝突（素のクリック＝選択の置き換え）ではこちらが安全。副作用として
       「待ち受けに入った瞬間に上位の的が画面から消える」が起きるが、これは「いま何が指せるか」
       の表示として許容範囲。
  - 新しい的を追加するときは、既存の的の部分集合的な位置（端点・縁・中心）にいないかを先に
    確かめ、いるなら順序自体をゲートにする。

- **自動で構えられたピックが、対象を選ぶクリックを食う**（2026-09-06・鏡映UIで実測）。
  「対象は共有選択から／基準（軸・鏡映面）は別チャンネルの1ピック」型のコマンドは、引数を
  「対象→基準」の順に集めるため、対象の最小数（たいてい1）が満たされた瞬間に基準のピックが
  自動で構えられ、以後の素のクリックが全部ピックに吸われて2つ目以降の対象を選べなくなる。
  見た目は壊れず、エラーも出ない。
  - 検討した3案（duocadは3を採用・2026-09-06）:
    1. ピックを `optional` にして「指す」ボタン専用にする — 初めて使う人に基準が要ることが
       伝わらないので不採用。
    2. 対象の上限を1にする — 仕様を曲げるので不採用。
    3. **修飾キー（Shift/Ctrl）付きクリックはピックへ行かせない** — 修飾キーは既に「選択の
       トグル」の意味を持つため規則が増えない。素のクリック＝基準を指す／修飾キー付き＝対象を
       直す、と読める。既存のピック（回転軸・回転中心）にも同じ分岐でそのまま効く。

- **参照引数のピックはPickArgSpecを再利用できる**（運用知見・2026-09-06）。verbが確定選択とは
  別に「既存の図形/面への参照」を必要とするとき（`move_body` の `axis_edge`/`center_vertex`、
  `mirror_body` の `plane_face`、`mirror_sketch_entities` の `axis`）、UI側は新しい入力モードを
  設計する必要はなく、既存の `PickArgSpec`（`web/src/commands/command.ts`、対象とは別チャンネルで
  図形を1つ直接ピックする枠組み）を拡張すればよい。`mirror_body`/`mirror_sketch_entities` では
  `PickTarget` に `face`/`sketchEntity` の種別を2つ足すだけで既存経路が使えた。新設が要ったのは
  「修飾キー付きクリックをピックへ行かせない」という1点のみ。
  - 面のピックは辺と優先順位が競合するため追加の配慮（狙う種別以外を配信しない）が要る。
  - 教訓: 対象選択と衝突する参照引数を持つverbを新設するとき、「UIでの指し方は未決」と即断せず、
    まず `PickArgSpec` が使えないか確認する。

## 基準平面のピック

- **基準平面のクリックが黙って面に化ける**（duocad実機検査・2026-08-23実測）。
  `window.__duocad.projectBasePlane('XY')` は「その画素で基準平面が取れ、手前に面が無い」ことを
  確かめてから画素を返すが、ソリッドがあると返る画素は**部品の輪郭のすぐ外側**になることがあり、
  1画素ずれるだけで基準平面ではなく部品の側面に当たる。後続のアサーションは全部それで通り、
  検査は緑のままだった。
  - 対処は2つ（両方入れる価値あり）:
    1. 基準平面へ貼る手順は、ソリッドが1つも無いうちにまとめて済ませる。
    2. 貼れた平面を毎回検算する（`window.__duocad.sketches[i].frame` の `origin`/`normal` を
       見て、要求した基準平面でなければ赤にする）。
  - 一般化: 射影ヘルパが「当たることを確かめてから返す」型でも、返す点が境界すれすれなら
    クリックは別のものを取る。検査は対象側の属性で検算すること。

- **同一平面上の面ピックは最後の桁で決着していた**（2026-08-28決着済み）。`resolveHit` は面と
  基準平面を「レイ距離が近い方」で決めるが、基準平面に描いて押し出すとその面は基準平面と
  ぴったり同一平面になり、距離が同着になる。素の `<` では勝敗が浮動小数の最後の桁で決まって
  いた（`fitDistance` を数学的に同値な式へ書き換えただけでカメラ位置が7e-14ずれ、
  `smoke-files.mjs` の面が基準平面に負けて赤くなった実例あり）。
  - **決着**: `resolveHit` は画面で1画素にも満たない差を「手前」と見なさない（しきい値は
    `worldPerPixel()`、シーン寸法に依らない）。見分けが付かないところに実体のある面があるなら
    それが狙いなので、面を勝たせる。基準平面が本当に1画素より手前にあるときの挙動は変えていない。
  - 再発検査は `smoke-files.mjs` の(d)。1回クリックして面が取れても検出力は無い（同着はどちらに
    転んでもおかしくない）。**画角を45〜55で振って**カメラを視線上で動かし、丸め方の違う6通り
    すべてで面が勝つことを見る形にしてある。切り分けの決め手は「HEADと自分の版でカメラ姿勢を
    並べて出す」こと。

## ウィンドウ選択（ドラッグ矩形選択）

- **ウィンドウ選択（左ドラッグ）は領域も一緒に拾う**（実機検査`smoke-move.mjs`・2026-09-06実測）。
  `App.svelte` の `onBoxSelect` は完全包含された面・辺・頂点・領域・スケッチ図形を全部拾うため、
  長方形を囲むとその長方形が作る**領域の参照**も選択へ入る。「図形1つだけ選ばれた」の判定を
  `items.every((item) => ids.has(item.entity) && item.point === null)` と書くと領域の参照が
  `entity` を持たず必ず偽になる。**先に `item.entity !== undefined` で図形だけに絞る**こと
  （幽霊側 `ghostSources` も同じ絞り方）。完全包含された図形は `point: null`（＝図形まるごと）
  で入る。辺クリックで長方形を指す道は当たりが不安定なので、囲む方が確実。
- **選択の正はコアなので、クリック直後に読んではいけない**。クリック／ドラッグは
  `modify_selection` をサーバへ投げ、配信後に初めて `window.__duocad.selection` が変わる。
  `page.mouse.click` の直後に `page.evaluate` で読むと往復前の値が返るので、選択に関する判定は
  必ず `page.waitForFunction` で書く。
- **ドラッグ一括選択の遅さは重複判定のO(M²)だった**（解決済み・2026-09-04、duocad
  `ff503b7`/`da7d621`/`49e69b4`）。27部品2835面モデル（ビューポート740×748、headless
  Chrome/RTX 5060 Ti）の全面選択で、離してからハイライトまでの合計が **1015.6ms→65.5ms**、
  サーバ単体の `modify_selection` が **857.5ms→1.5ms** に短縮。
  - 支配項は `duocad/selection.py` の `modify_selection` にある
    `for ref in coerced_add: if not any(same_ref(existing, ref) for existing in items)`。
    `items` を線形に舐めるためM²になる（M=2835で857.5ms、うちM²ループがほぼ全部）。
  - 修正: 重複判定を鍵引きに変更（`ff503b7`）→ M=2835で47.3ms。残りの主因は
    `kernel.face_count` を参照1件ごとにやり直す `TopExp.MapShapes_s` 呼び出し（51.1ms）で、
    `_coerce_refs` を新設してボディごとに1回だけ数える形にし解消（`_face_map` 呼び出し
    2835回→27回）。`kernel.py` にキャッシュは入れていない（モジュール関数に寿命の受け皿が無く、
    戻り値が可変のOCCTマップで17箇所が使うため）。
  - 矩形サイズ別の実測（修正前→修正後）: 120px/315面 67.0ms→38.4ms、画面1/4/850面
    125.3ms→88.9ms、全面/2835面 1015.6ms→65.5ms。
  - **`_face_map` のキャッシュ欠如は主犯ではなかった**（面数1006のボディで `face_count()` 1回は
    0.063ms、M=2411でも合計35.9ms）。「安い処理をM回」より「M回の中でさらにM回舐める」方が
    桁で効いていた、という教訓。

## ピック解決のコストとしきい値

- **辺のscreen pickは全走査で足りる（broad phase不要）**（実測・2026-09-11）。当たり判定を
  world thresholdから画面上のCSS px距離へ移す際、27部品mATXケース中の面数最大ボディ
  （233面・辺645本／折れ線の点1,768、ビューポート1280×860）で計測:
  - `projectEdge`（内部で `edgeAt` を1〜7回呼ぶ上界）: 見えている辺1本を300回で
    p50 0.2ms / p95 0.7ms / 最大1.4ms。
  - 645本を1周: p50 0.2ms / p95 0.3ms / 最大1.6ms。
  - 判定基準「1フレーム16msのp95超過なら二段階化」に対し20倍以上の余裕があり、二段階化は不要と
    判断。効いているのは「1回に走査するのは選択中の1ボディぶんだけ」という設計で、部品数が
    増えても走査量は増えない。

- **「押せるのに断られる」はツールバーの出し分けでなくピックの翻訳を1箇所で畳んで消す**
  （2026-09-05決定）。メッシュボディ（面選択不可）に対する編集verbの扱いを、
  「選択に応じてツールバーのコマンド一覧を出し分ける」ではなく「ピックを選択参照へ翻訳する
  ところでメッシュだけボディ参照へ畳む」で解決。
  - 理由: コマンド一覧はモードの持ち物で `{#key mode.kind}` によりモード変更時のみ作り直す
    設計のため、選択のたびに作り直すと集めかけの引数が落ちる。畳んでおけば編集verbは選択要件を
    満たせないまま自然に確定へ到達せず、出し分けなしで「押した結果サーバに断られる」が起きない。
  - 副次効果: viewportはメッシュも1枚の面として描くため、畳まないと `kind:"face"` の参照が飛び、
    ドラッグ一括選択にメッシュが1つ混ざるだけで選択が丸ごと落ちる不具合も同時に解消した。
  - 一般化: 「操作できないもの」を入口（ボタン）側で消すより、指したものの解釈側で「指せる粒度」
    へ畳む方が状態が増えず副作用も少ない。ただし畳んでも結果が変わらない経路（duocadでは
    スケッチを貼る先。ボディ参照に畳んでも `sketch_create` は面を要求する）では畳まずに断る。

## 実機検査（オンスクリーンテスト）の落とし穴

- **対象は名指しする（「たまたま最初に指せたもの」を対象にしない）**（2026-08-28実測）。
  実機検査が操作対象を「その視点でたまたま最初に射影できたもの」で選ぶと、視点に暗黙で依存する。
  duocadのビューポートをZ-upのfront-top-rightへ変えた際、`acceptance.mjs` の
  `human/extrude_face` が押す面が`+Y`の壁から`+X`の壁（寸法も40×10→60×10相当で変化）に変わり、
  3セクション先のAI側`fillet`/`chamfer`が`IsDone is false`/`no suitable edges`で落ちた。
  原因が「視点」にあることは落ちた検査からは見えない。
  - 直し方: 対象を法線や寸法で名指しする（例: `normal[1] < -0.9` の壁）。名指しした対象が
    射影できなければ失敗にする。
  - 同種の落とし穴: 述語で集めた円い辺の「先頭」を黙って使うと、直前の操作が作った短い辺
    （例: 半径1の四半円で長さ1.57mm）を掴んでOCCTに断られる。`measure` で長さを確かめて
    一番長い辺を選ぶ形に直す（提案を確定前に検算する経路）。

- **「画面に収まる」検査は射影の在否ではなく射影された大きさで測る**（2026-08-28実測）。
  「対象を1つでも画面へ射影できたか」で書くと検出力がほぼ無い。duocadでFOVを可変にした際、
  `frameToContent` の距離式をわざと画角非依存（`diagonal * 1.2` 固定）に戻して確かめたところ、
  画角90度でシーンが本来の0.4倍にしか写らなくても検査は緑のままだった（中央付近のものはどのみち
  画面に残るため）。
  - 効いたのは射影された広がり（画面上の大きさ）を画角ごとに比べる形。**測る対象の集合を
    画角間で揃える**必要がある（射影できる面の顔ぶれが画角で増減するため、全部使うと正しい
    実装でも0.73倍などにぶれる）。3つの画角すべてで射影できた面だけで測ると0.97〜1.10倍に収まり、
    壊れた実装の0.41倍との間に十分な幅ができた。
  - 一般化: 「収まっているか」は在否ではなく寸法の問題。閾値は実測してから決め、決めた後に
    一度わざと壊して赤を見る。

- **`move_body`起動直後は辺の実データが届く前にクリックが撃ち切られる**（flake・解決済み
  2026-09-03、duocad `71aa985`）。`smoke-move.mjs` の8b節が5回中2回しか緑にならなかった原因は
  製品の不具合ではなく検査の待ち不足だった。
  - 機序: `wantsEdges` は同期的`$effect`で即座に真になるが、辺の実データはまだ無い。辺キャッシュの
    `revision`が現在のボディと不一致だと`showEdges(null, [])`で空にしてから`session.getEdges()`
    を非同期で投げる。その間`projectEdge`は全indexに`null`を返し、検査ループは待たずに次へ進み
    8本を数ミリ秒で撃ち切って1クリックも発生させずfailする（エラーは出ない）。
  - 副経路: `frameAll()`のカメラジャンプ後180msで`set_view_resolution`がサーバへ飛び、サーバは
    粗さを`body_revision`の鍵に入れる（`duocad/view.py`）ため、形が同じでも版が上がり配信で
    辺がループ途中に消えることがある。
  - 直し方（検査側が本筋）: `wantsEdges`だけでなく`projectEdge`がどれか1本でも非nullを返すまで
    待ってから撃つ。ループを最大2周（副経路対策）。失敗メッセージも「辺の実データが届かない」へ
    変更。修正後は6回連続緑（修正前は5回中2回）。
  - 製品側は現状維持でよい（版が違う辺を消すのは正しい）。ただし「起動直後は辺が指せない窓が
    ある」「視点を止めるたびに辺が取り直される」は実挙動として残る。
  - 切り分けの前提: 実機smokeが配るのは`web/dist`（ビルド成果物）なので`web/src`を触ったら
    `npm run build`を挟む。また1回の走行で結論を出さない（「毎回100%再現」と誤記録した原因は
    1回ずつの走行結果で比較したため）。

- **UIのrestyleは決め打ち座標の実機検査を黙って壊す**（2026-08-20実測）。`web/src`のUI変更
  （`478b660`「リボン+右サイドバー構成へrestyle」）で`smoke-features.mjs`/`acceptance.mjs`が
  「平面上の点(u,v)が画面の中に無い」で赤になった。検査スクリプトはモデル座標を毎回`toScreen`で
  画面座標へ射影してクリックするが、射影はビューポート矩形の外なら`null`を返す。サイドバー追加で
  3Dビューが狭くなり、モデル端の点（例: `(80,0)`）が画面外に出てクリック先を失った。
  - `npm run check`（tsc + svelte-check）もpytestもこの壊れ方を一切見ない。restyle後は必ず
    実機検査を回すこと。
  - 「カメラの余白を広げる（製品側）」か「スクリプトの座標を寄せる（検査側）」かは別問題で、
    duocadではREADME §7の留保として本人判断待ちに置かれている。

- **ビューポートを横に狭める変更はu軸（横）の可視範囲だけを削る**（実機検査実測・2026-08-27、
  左サイドバー240px復元時）。`camera.fov`（垂直）は固定で水平可視角は`aspect(=width/height)`に
  比例するため、幅だけ削るとu軸（横）が縮みv軸（縦）は変わらない（`projectSketchPoint(u,v)`実測で
  u=40が画面外でもv=-35までは可視という非対称が出た）。以前の下段バー削除（高さが増えて
  aspectが下がる）でも同方向に効いていた。
  - 教訓: ビューポートを狭める変更のたびにテスト座標を勘で詰め直さず、
    `projectSketchPoint(u, v)`を候補グリッドで呼んで実測してから座標を選ぶ。横方向が窮屈なら
    v軸（縦）へ逃がす方が安全マージンが大きい。
  - 併せて実測: `duocad/region.py`の`regions()`は`BRepAlgoAPI_Splitter`で平面をスケッチの
    辺すべて（線分・円弧のような**閉じていない曲線も含む**）で分割する。矩形の外に逃がす場所が
    無いからと線分・円弧を矩形の内側へ動かすと、内部を横切った瞬間に`extrude`が
    `ValueError: join produced an invalid shape (BRepCheck)`で壊れる。閉じた図形（円）は
    矩形の内側でも「面積を引いた穴」になるだけで安全だが、**開いた図形は矩形の外に完全に離す**
    こと。詰まった横方向の代わりに矩形の外側でまだ見えている帯（v<0など）へ逃がすのが正しい。
