## 実機smoke検査の設計

### サーバ起動・ビルド

- **実機smoke検査は`web/dist`を静的配信するため、`npm run build`を挟まないとSvelte変更前の挙動のまま緑になる**（2026-08-27実測）。`web/dist`は`.gitignore`対象のビルド成果物で、`web/src/*.svelte`を編集しても`npm run build`（`cd duocad/web && npm run build`）を挟まない限り実機には反映されない。実例: `ParametersPanel.svelte`を削除し`SketchPanel.svelte`に反復のパラメータ行を追加したタスクで、再ビルドせず`acceptance.mjs`/`smoke-files.mjs`/`smoke-regions.mjs`を実行したところ3本とも緑になったが、実際は旧コンポーネントがバンドルに残ったまま新しいDOM要素も配信されておらず、既存の別経路だけで通っていた見せかけの合格だった。`npm run check`（tsc/svelte-check）はソースを直接見るのでこの罠に引っかからないが、実機検査（puppeteer）はビルド成果物しか見ないため独立して罠にかかる。**Svelte変更後は直前に`npm run build`を実行したかを必ず確認する。**
- **duocadのサーバを手で立てて画面を触ると、リポジトリ直下の実`models/`を書き換える**（2026-09-05実際に踏んだ）。`python -m duocad.mcp_server`を手で立てると保存先はリポジトリ直下の実`models/`になる（`duocad/server.py`の`DEFAULT_MODELS_DIR`）。実機検査スクリプトは`startServer({modelsDir})`で必ず使い捨てのtempを渡しており（`web/scripts/server.mjs`に「実ブラウザ検査は必ず渡すこと」と明記）、**手で立てるときだけこの防御が外れる**。実際に踏んだ形: UIの見た目を確かめるために手でサーバを立てブラウザからテスト用のSTEP（4.6MB）を読み込み、その状態が保存経路を通って本人の作業ファイルが161KB→4.9MBになった（`git diff`で気づくまでコミット対象に紛れていた）。**手で立てるときも`--models-dir`に使い捨てを渡す**のが正しい（例: `.\.venv\Scripts\python.exe -m duocad.mcp_server --models-dir $env:TEMP\duocad-scratch`）。**stdinを閉じない**ことも併せて要る（stdioでMCPを喋るのでEOFで即終了する。`tail -f /dev/null | ...`などで開いたままにする）。もう1つの側面: 8765を掴んだサーバは複数の接続を相手にするため、手で立てたものを消し忘れると別セッションや本人のブラウザがそこへ繋いで作業を続けうる。`models/`の差分に「自分が入れた覚えのない操作」が混ざっていたら並行して誰かが触っている印なので`git checkout`を向けてはいけない。

### 座標・フィクスチャ

- **実機検査でエンティティの1点だけを動かした後、そのエンティティを「辺（図形全体）」として再選択するクリック座標を、動かす前の定数と動かした後の値を混ぜて作ると、図形が傾いた分だけ実際の中点からずれてタイムアウトする**（2026-09-11、`smoke-move.mjs`で実測。製品コードの回帰ではなくテスト自身の座標計算バグ）。機序: `move_sketch_entities`で線分の片方の端点だけをdy=10動かすと線分`(60,0)-(80,0)`は`(60,0)-(80,10)`へ傾くが、その後のクリック座標を`(LINE.x0+LINE.x1)/2`（動かす前の定数）と`moved.params.y0`（動かした後の値、実は不変で0のまま）を混ぜて作ると(70,0)を指してしまう。傾いた線分の実際の中点は(70,5)であり垂直距離で約4.5mmずれ、クリックの当たり半径（`EDGE_PICK_PIXELS`）の外になってタイムアウトする。同じ関数内に同型の中点計算が4箇所あり全部同じ理由で踏んでいた。**教訓**: エンティティを部分的に変形した後にそのエンティティへ向けてクリックを打つときは、狙い座標を必ずその時点の実パラメータ（`moved.params.x0/y0/x1/y1`等）から計算し直す。呼び出し元で最初に定義した定数と後で読んだ実測値の一部だけを混ぜて式を作ると、コンパイルも型検査もpytestも通るのに実機だけがタイムアウトで落ちる。
- **スケッチのホバースナップ導入後、実機smokeで「何もない場所」に置くつもりの座標が吸い付く落とし穴が2型ある**（2026-09-06実測）。**(a)距離型**: 当たり判定は画面ピクセルベース（`EDGE_PICK_PIXELS`=6px）を世界座標に換算した距離で、`smoke-regions.mjs`修正時の典型的なフレーミングで輪郭から4mmはスナップし5mmはスナップしない。閾値はカメラ距離に依存し絶対値としては使い回せないが「数mmは危険域」という桁感は再利用できる。fixtureは既存図形の輪郭から余裕を持って（目安10mm以上、または`window.__duocad.hoveredRef()`で実測して）離す。**(b)順序型**: 「何にも当たっていない場所」として選んだ座標が、同じスクリプトの前段が実行時に置いた線分の端点に衝突する（距離を離しても直らない）。実例: `smoke-hover.mjs`に1mmグリッドスナップの検査を足したとき、既存の検査が線分の終点として使っていた座標に近い点を選んでしまい、クリックが端点へスナップして丸めが効いていないように見える誤検出になった。新しい検査を足すときの「空き地」は、スクリプト冒頭の初期図形だけでなく同じスクリプトの前段が実行時に追加する図形・端点からも離す。**切り分け手順**: ①`page.evaluate`で実際に送られたentity paramsをダンプし意図した座標とズレていないか確認②ズレていたらクリック前のマウス移動だけで`window.__duocad.hoveredRef()`を呼び同じ当たり判定が実際のホバー機構からも得られるか確認③両方一致すれば「検査の側が前提にしていた当たり判定が変わった」と判断してよい（丸め後の値が浮動小数点誤差ぶんだけズレているのは別の当たり判定を通った証拠）。
- **キー入力除外判定で「tagName===INPUT」を全部除外すると、チェックボックスまで巻き込んで既存の実機検査が壊れる**（2026-08-23実測）。duocadの`onWindowKeydown`（Ctrl+Z/Ctrl+Yの文書undo/redo）を、Enter除外と同じ書き方（`['INPUT','TEXTAREA'].includes(target.tagName)`）に直そうとすると、パーツ一覧の可視性チェックボックス（`input type="checkbox"`）にフォーカスが残った状態でのCtrl+Zがundoしなくなり既存の実機検査が無限待ちでFAILする。原因: チェックボックスもtagNameは`INPUT`だが「打ち間違いを直す」の対象ではない。正しい判定はtagNameではなくinput typeで見る: `target?.tagName === 'TEXTAREA' || (target?.tagName === 'INPUT' && !['checkbox','radio'].includes(target.type))`。**一般化**: 「INPUT/TEXTAREAを除外」という書き方は、そのプロジェクトにcheckbox/radio型のINPUTが存在する時点で暗黙に間違っている可能性がある。既存コードの除外判定を「同じ書き方に揃える」よう指示された場合も、用途が違えば除外対象の集合まで機械的に一致させてよいとは限らない（Enterの除外は「フォーム誤送信を防ぐ」目的で全INPUTを除外して正しいが、Ctrl+Zの除外は「テキスト編集中のブラウザ標準undoを奪わない」目的なのでテキストを持たない入力要素は除外しない方が正しい）。検出経路は変更後に自分でstash/rebuildして負のコントロール（バグを再現させた版）を走らせ既存smokeが壊れることで発見した——「同じ書き方に揃えよ」という指示があっても既存の実機検査群を必ず再実行して確認する。

### 計測・ベンチマーク

- **「画面の値が変わらなくなったら落ち着き」で完了と判定する実機ベンチは、サーバが重い処理でブロックしている間を「もう何も起きない」と誤読する**（2026-08-30実測）。サーバが単一イベントループの場合、重い測り直しの最中は何も届かず、検査は「要求が出ていく前の画面」を落ち着きと読む。実例: 0.45秒の静けさで打ち切ったベンチはカリング入り・切りで同じ数値を返し（どちらも1つ前の状態）、待ちを2.5秒に伸ばすと1測定ぶん遅れた値が並び、6秒の「1通も来なければ往復0秒」という逃げ道を置いたら測りたかった16秒の沈黙が0.0秒と記録された。**正しい待ち方は受信回数を数えること**: 状態が1通届くたびに増える番号をアプリ側に生やし（`__duocad.stateEpoch`）、①手を打つ前の番号を控える→②番号が増えるまで待つ（増えなければ検査側の間違いとして落とし0秒と記録しない）→③増えなくなって一定時間（2秒）経ったら完了→④所要は最後に番号が増えた時刻までで測る。この方式で測り直すと既知の実測（三角形1,180,763・14.5秒）と一致した。**既知の値を再現できることが、ベンチが正しく測れている唯一の証拠。**
- **触ってよいファイルが1つに限られる実機A/B計測は、そのファイルにだけ一時フックを生やし`git stash push/pop`で新旧コードを切り替えて同じブラウザ検査を2回走らせれば足りる**（2026-09-04実施、`viewport.ts`単体の性能改修で`App.svelte`は禁止という制約下）。手順: ①触ってよいファイルの`return {...}`直前に`window`へ直接計測フィールドを生やす1行を足す（`App.svelte`の`__duocad`オブジェクトとは別物として共存）②修正後コード+フックで`npm run build`→実機計測→`after`記録③`git stash push -- <path>`で修正を退避しコミット済み（修正前）へ戻す④同じフックをもう一度手作業で足し`npm run build`→同じ検査を再実行→`before`記録⑤`git checkout -- <path>`でフック入り修正前ファイルを捨て`git stash pop`で本来の修正（フック無し）を復元⑥最後にフックを手で消してから最終ビルド・型検査・smokeを回す（計測用の口はコミットしない）。**成立条件**: `web/dist`は静的配信されるビルド成果物なのでフックの有無を切り替えるたびに必ず`npm run build`を挟む（挟み忘れると前回のビルドのまま計測してしまい、数値が変わらない/フックが見つからないという分かりやすい形で失敗する）。**利点**: 別セッションが`stash@{0}`を退避済みでも`stash push -- <path>`は対象パスだけを新しいstashスロットへ積むので他セッションの退避物には触れない（`stash list`で自分のスロットを確認してから`pop`/`checkout`する）。

### 実行運用・回帰の受け渡し

- **実機smokeを「触った所の周辺」だけ回して緑と報告すると、壊れたスイートは次のタスクの実行者へ渡り、自分のせいか前任のせいかの二分から始めることになる**（2026-09-06実発）。無人runnerは「自分が触った層の周辺」を検証範囲に選ぶのが合理的に見えるが、選ばなかったスイートが壊れていても誰も気づかないまま完了報告が出る。実例: あるコミット（スケッチの図形・点にホバー強調を出し吸い付いて点を置く機能）のrunは`smoke-hover`/`smoke`/`smoke-vertex`/`acceptance`を回して緑と報告したが、スケッチのクリック経路を変えたのに`smoke-regions.mjs`を回していなかった。翌タスクが実機smoke19本を全部回して失敗を踏み、自分の修正を1行無効化して同じ所で落ちることを確認→使い捨てworktreeを立てて新旧コミットで二分する作業が、本来の作業とは別に必要になった。**効く形**: 検証範囲は「触ったファイル」ではなく「スイート」で選ぶ。部分実行にするなら回さなかったスイート名を完了報告に書く（緑の範囲を偽らない）。壊れているのを見つけた側は二分して犯人のコミットを名指してから次へ渡す（「落ちている」だけを引き継ぐと次の実行者が同じ切り分けをやる）。実機smokeはCPU時間は食うが人間の時間は食わないので、削る対象として最初に選ばない。
- **`duocad/topopt/output/design_space_reference.stl`は`build_reference`の既定STL出力先なのにgit追跡下にあり、受入検査を1本走らせるだけで題材ごとの内容へ黙って上書きされる**（2026-09-10実測）。直前に別セッションが更新をコミットしていた状態で、案5削除タスクが2本の検査スクリプトを回しただけで、HEADの2,419,684バイト（hanger 2.4mm由来）が108,084バイト（検査題材のbracket由来）へ置き換わった——**検査は失敗していない、黙って上書きされる。** 受入検査を回したあとの`git status`に自分が編集していない成果物が出ていないか見る。出ていたら自分のrunが書いたものなので`git checkout -- <path>`で戻す（自分が壊した状態を元に戻すのであって他人の未コミット変更を消すのとは別）。コミットに含めない。参照を作る検査・スクリプトを新しく書くときは出力先を必ず明示的に渡す。**一般化**: 「既定の出力先を持つ関数」＋「その出力先がgit追跡下」の組み合わせは、実行するだけでリポジトリの状態が動く。追跡下にあるとセッションをまたいで成果物が消える。

## ハーネス・検査設計の一般原則

- **「途中で止めない」検査ハーネスは、走り終わったあとに合否を終了コードへ落とす処理を明示的に書かないと、失敗が何個並んでも`exit 0`で終わる**（2026-08-28、`web/scripts/acceptance.mjs`で発覚）。このスクリプトは「各操作は独立して試し、落ちても止めずに❌と理由を残す」設計で、各セクションが例外をcatchして`ok: false`を記録して次へ進むが、そのcatchが最後の1つでもあると、プロセスは正常終了する。結果、`fitDistance`や`setFov`をわざと壊しても終了コードは0のままで、呼び出し側（人・cron・無人drain）からは全緑と区別が付かなかった（画面のログには`NG`が出るので人が目で読む限りは気づけるが、気づけないのは自動化した側だけ）。**「止めない」と「合格を出さない」は別の設計判断**であり、走り終わりに記録を1回走査して終了コードを決める処理を必ず対にすること（duocadでは`failedLabels()`を足し未実行のセクションも失敗として数えるようにした）。この欠陥は新機能の検査を足そうとして初めて表面化した（足した検査をわざと壊して赤を見ようとしたら終了コードが0のままだった）——「わざと壊して赤を見る」を終了コードで確かめる習慣が無ければ見つからない。
- **`DEFAULT_RMIN == PRESET["rmin"]`のような「既定を変えていない」assertは、既定を変えるタスクが来た瞬間に必ず落ちる**（2026-09-05実発）。このassertが本当に守りたかったのは`PRESET["rmin"]`（回帰基準のρ場のSHA-256が乗っている値）のほうで既定値そのものではない。**「A == B」で守ると、AとBのどちらを動かしても落ちる** — 守りたいのがBだけなら`B == <定数>`と書く。同時に踏んだ同型の穴: 指紋（SHA-256）を採る検査が既定値に追随する引数を省略して呼んでいた。「基準はプリセットに乗っているから安全」はプリセット経路にしか当てはまらず、もう1本の指紋は既定を動かした瞬間に黙って別物になる。**指紋を採る呼び出しは、既定に追随しうる引数を全部明示すること。**
- **題材が箱・円柱・平面ばかりの検査群は「全部緑」でも守っていない**（2026-09-07実測）。duocadで`BRepBndLib::Add`を`AddOptimal`へ差し替えたとき、pytest1,029件が全部緑のまま、topopt受入検査7本のうち落ちたのは「罠が現に存在する」と主張している検査自身1件だけ（差し替えを検知したのではなく自分の前提が消えたことを報告しただけ）、7本の`MEASURED`全項目を突き合わせても動いたのはタイマーだけだった。にもかかわらず実物38ボディのうち11個（29%）でbboxが1%超ずれ最大9倍狂っていた——検査の題材が箱・円柱・平面ばかりで、そこでは両者が一致するため。**「差し替えても全部緑だった」は安全の根拠にならない。** 実装の選択肢を差し替えて何も動かないときは、まず題材がその差を出せる形かを疑う。確かめ方は変異検査（実装を1つ壊して狙った検査が実際に落ちるか）で、検査を書いた時点で1回やる（duocad`docs/TOPOPT.md`「変異検査の記録」が台帳）。対処は題材を1つ足すだけで済んだ: トリムされたトーラス片（`BRepPrimAPI_MakeTorus(100, 10, pi/6)`）を入れると同じ差し替えで狙った2件だけが落ちる。
- **機能を消すと、それを題材に借りていた契約の検査も消える**（2026-09-10）。duocadの形状最適化から案5（`derive_from_coarse_run`）を削除するとき、本人が「一部の検査は案5を題材にしているだけで、見ている契約は案5のものではない」と名指しし、別の連続値保持側（`build_reference`）の同じ契約へ付け替えることを完了条件にした。見ていた契約は「`run_topopt`は空の条件面のとき例外にせず`"result": None`で返す。受ける側は`.rho`へ触る前に自分で見て構造化された例外へ変換する」で案5とは無関係——案5と一緒に消していたら残りの検査は全部緑のまま、素の`AttributeError`へ戻る穴が復活していた。**機能を消す前に「この機能を題材にしている検査は、この機能の契約を見ているのか」を1件ずつ問う**（題材(setup)と主張(assert)が別物のことがある）。見分け方はassertの中身: 例外の型・戻り値の形・変異検査の対象が削除する関数の外を指していたら借りているだけなので付け替え先を探す。付け替えるときは構造ごと（正常系・例外の型・構造化診断・変異検査）移す（変異検査を落とすと「上げっぱなし」の実装でも緑になる）。
- **duocadのMCPサーバは未知の引数を`tools/call`実行前のスキーマ検査（`_check_arguments`）で弾き、JSON-RPCのトップレベル`error`（-32602）として返す**（2026-08-27）。`duocad/mcp_server.py`の`McpServer._call_tool`はツール本体（`DocumentTools.call`）を呼ぶ前に`_check_arguments`でスキーマ突合（必須・未知キー・型）を行う。ここで未知の引数（例: 廃止した`body_ids`を渡す）が見つかると`_RpcError(INVALID_PARAMS)`を送出し、これは`tools/call`の結果（`isError: true`の構造化封筒）ではなくJSON-RPCのトップレベル`error`（`response["error"]["code"] == -32602`）として返る。`tests/test_mcp_verbs.py`の`call_error()`ヘルパーは`assert "error" not in response`を前提にしておりこの種の失敗には使えない（使うとアサーションで落ちる）。未知引数を弾く検査は`request(server, "tools/call", {...})`を直接呼び`response["error"]["code"]`を見る必要がある。失敗の3層（プロトコルエラー/ツールのisError/成功）を書き分けるテストを書くときに踏みやすい。
- **変換のテストに「その項が恒等になる値」（原点を通る軸・単位ベクトル・正の角度のみ）を選ぶと、その項を丸ごと落とした実装でも通る**（2026-09-06、duocadの回転実装、QAが指摘）。duocadで「軸上の点まわりの回転」を`T(p)·R·T(-p)`で組み、実機検査は軸を原点を通るZ軸にして「(10,0,0)が(0,10,0)へ移る」を当てていた。テストは緑で角度符号反転の変異検査も赤くなり噛んでいるように見えたが、**`p=原点`では前後の平行移動が恒等**であり、`T(p)`と`T(-p)`を丸ごと消す変異を入れても通った（「軸の位置」という機能の中身がまるごと未検証だった）。軸を非原点（x=10を通るZ軸）にして軸上の点・軸から離れた点・軸方向へずれた点の3点を当てる形に変えたら同じ変異で赤くなった。さらに「Z軸・正の角度・単位ベクトル」だけだと軸の取り違え・符号の反転・正規化の忘れが全部素通りするのでY軸・負の角度・長さ2の向きベクトルのケースも足した（`.normalize()`を消す変異で実際に赤くなる）。**教訓**: テストの入力に選びがちな「きれいな値」（原点・単位行列・0・1・軸に平行）は式の一部を恒等にする値でもあり、恒等になった項は実装から消えていても結果に現れない。変換のテストは関わる項が全部効く値を選ぶ（原点を通さない・軸に平行でない・角度は正負両方・ベクトルは非単位）。「変異を入れたら赤くなった」はその変異についてしか語らない（落としたい欠陥の種類ごとに変異を作る）。不動点（軸上）と動く点を両方当てると恒等変換に潰れた実装も捕まる。

- **経路の途中の門を1つだけ呼んで「通る」と結論すると、その手前の門を見落とす**（2026-09-09運用知見）。実例: あるタスク本文は「hangerは2.4mmで初めて製品経路（`optimize_run.run`）を通る」という前提で2.4mmで回してSTLを残すことを完了条件にしていたが、実際には2.4mmでは`optimize_run.run`の手前の門（`_check_anchor_centroids`）で`FaceMappingError`になりSIMPは1回も呼ばれなかった。前提の出所は途中の関数（`_region_representation`）を単独で呼んだ測定で、その関数は確かに2.4mmで「0要素の領域なし」を返す（測った値は正しく、結論だけが間違っていた）。**なぜ気づけないか**: 単独で呼んだ門は本当に通るので実測ログは矛盾なく見える。前提が後続タスクの完了条件に写されると実行者は前提を疑う理由を持たない。入口から呼ぶ費用が高いほど途中から呼びたくなる。**対策**: 途中から呼んだときはノートに「入口から通したのではない」と明記する（「◯◯は通る」ではなく「◯◯の門は通る」と書く）。高い経路でも門だけは入口から通す（この例では`run()`は2秒で落ちており完走を待つ必要はまったく無かった）。
