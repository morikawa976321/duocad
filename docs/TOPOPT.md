## これは何か

**3Dのトポロジー最適化(SIMP法)の実測記録。** 計算は `duocad/topopt/`、受入検査は
`topopt_checks/`、画面と撮影は `web/` にある。以下の節は時系列なので、古い節は当時の
記録として読むこと。

出力はメッシュ止まりでよい(B-rep化はしない) —— そもそも「メッシュ → 編集可能な B-rep」の
汎用変換は OSS に存在しない(engine `no-oss-mesh-to-editable-brep`)。ただし**ボクセルの立方体
描画のままでは階段状に見える。これは描画方法が原因であって解像度が原因ではない**ので、
まず marching cubes + Taubin平滑化で滑らかな三角形メッシュに変えてから、解像度を上げる要否を
判断する(このタスクの順序)。

## 設計空間をB-repから起こす(voxelize.py)

`simp.py` の設計空間は numpy の3次元配列を直接作っているだけで、**OCCTの形状から格子を
起こす経路が無かった**。`voxelize.py` がそれを埋める(**stage1**。境界条件を面に紐づける
「面アンカー」は stage2 = `anchor.py` が担当する。下記「CADの面 → 格子の節点」)。

```python
import voxelize
from build123d import Box, Cylinder, Pos

model = voxelize.voxelize(
    Box(40, 20, 10),                       # 設計空間(TopoDS_Shape / build123d のどちらでも)
    elements_long_axis=40,                 # 最長軸方向の要素数 → 要素サイズが決まる
    keep=Pos(18, 0, 0) * Box(12, 20, 10),  # 保持領域(材料を必ず残す)。省略可
    obstacle=Pos(-10, 0, 0) * Cylinder(4, 20),  # 障害物領域(材料を入れない)。省略可
)
model.grid          # Grid(origin, spacing, shape) —— 立方体要素・ワールド軸整列
model.design        # bool (nx,ny,nz)。設計空間の占有
model.keep          # bool。**設計空間の内側に切り詰め済み**
model.obstacle      # bool。同上
model.free          # design & ~keep & ~obstacle(最適化が動かしてよい要素)
model.soup          # TriangleSoup。三角形ごとに OCCT の面添字(1始まり)を持つ
model.initial_density(0.3)  # SIMP へ渡す初期密度場(保持=1 / 障害物=0 / 外=0)
```

**セル中心規約**: `mask[i, j, k]` は要素 (i,j,k) の**中心**の値。中心のワールド座標は
`origin + spacing * (i+0.5, j+0.5, k+0.5)` で、`mesh.py` の `rho[ex]` と同じ規約。
**新しく格子と実座標を対応づけるときは必ず `Grid.centers_1d` / `Grid.centers_of` /
`Grid.center_of` を通すこと**(添字に `spacing` を直接掛けると半セルずれる。
`mesh.py` は2026-08-30にこれを踏んだ ── engine `marching-cubes-cell-center-half-offset`)。
配列の軸順 `(nx, ny, nz)` は `simp.py` の `rho` (nelx, nely, nelz) とそのまま合う。

格子の作り方: 要素サイズ = 最長辺 / `elements_long_axis`、各軸の要素数 =
`ceil(辺長 / 要素サイズ) + 2`(**周囲に1要素の余白**)、形状は格子の中央に置く。

占有判定は **`kernel.tessellate` が返す三角形群に +z のレイを飛ばして巻き数で数える**
(新規依存ゼロ。numpy だけ)。**`BRepClass3d_SolidClassifier` は本番経路に使わない** ──
1点ずつしか判定できず 100³=100万点をPythonループで回すのは非現実的なので、
`check_voxelize.py` の**神託**としてだけ使う。

守りが2つ入っている。**どちらも実測で必要だと分かったもの**で、片方では足りない:

1. **偶奇(parity)ではなく巻き数(winding)で数える。** レイが2枚の三角形の共有辺を
   ちょうど通ると同じ z に交点が2つ出る。偶奇だとその上の全域で内外が反転する
   (実測: 40×40×10 の箱で、上面の対角線が列の中心を厳密に通り **15,200 mm³ / 正解16,000**)。
   巻き数なら「入る(+1)/出る(−1)」が相殺して壊れない。
2. **レイの (x,y) を列の中心から決定的にずらし、縮退したらずらし幅を変えてやり直す。**
   格子は bbox から起こすので、軸整列した形状では面や辺が列の中心と厳密に一致する縮退が
   **系統的に**起きる。巻き数でも守れないのは**頂点に三角形が集まる点**で、円錐の頂点を
   レイが貫くと「出る」ばかりが数十回数えられる(実測: 円錐+板がずらし幅ゼロでは
   n=6〜40 の全解像度で「巻き数が0に戻らない列がある」と落ちる)。
   **ずらし幅を1つの固定値にすると守れない** —— その値にちょうど合った位置に頂点が来る
   格子を作れば必ず縮退させられる(2026-08-31のQAが実際に再現した)。なので
   `RAY_JITTER_SEQUENCE`(要素サイズの 1e-4 に素数を掛けた6通り)を順に試し、
   縮退を検知したら次のずらし幅でやり直す。**乱数は使わない**ので決定性は保たれる。
   全部だめだったときだけ例外にする。実際に使われた幅と試行回数は
   `stats["occupancy"]["jitter"]` / `["jitter_attempts"]` に出る。

**壊れた入力は黙って通さない。** 次のどれかに当たると `ValueError` で落ちる ──
(a) 三角形が取れなかった面がある、(b) 有向辺の対が揃わない(非水密な開シェル/向きの不整合)、
(c) 符号付き体積が正でない(法線が内向き)、(d) **殻(連結成分)ごとの向きが入れ子の深さと
合わない**、(e) ずらし幅を6通り試してもレイの巻き数が 0 に戻らない列がある、
(f) 保持/障害物領域が設計空間の格子とまったく重ならない、または1要素も掴めない、
(g) 保持領域と障害物領域が重なっている。開いたシェルを黙って通すと
「レイが1回しか交差しない列は全部内部」という**もっともらしいゴミ**が返る。

(d) は**総符号付き体積だけを見ても分からない壊れ方**への対処。内部空洞の殻だけを裏返すと、
総体積は正のまま(実測: 40³の箱に20³の空洞で 56,000 → 72,000 mm³)で「向きは正しい」と
判定され、**空洞が材料として埋まる**。連結成分ごとに符号付き体積を出し、
「他の殻いくつの内側にあるか」を +z のレイの巻き数で数えて、深さが偶数の殻は正・
奇数(=空洞)の殻は負でなければならない、という形で見ている
(2026-08-31のQA指摘。健全な中空の箱は殻2個・体積 [+64000, −8000]・深さ [0, 1] で通る)。

(f) を空マスクとして黙って受け入れないのは、「材料を必ず残せ」と言われた領域が1要素も
掴めないまま最適化が走ると、支えの無い構造がもっともらしく出てくるため。いちばんありそうな
原因は座標系か単位の取り違えなので、**どの領域が / どこにあって / 格子はどこか**を出して落とす。

**stage2 への引き渡し**: `model.soup` は面添字と、B-repから直に取った面ごとの
面積・重心・法線(`soup.face_props`)を捨てていない
(`soup.face_index[t]` / `soup.triangles_of_face(i)`)。`voxelize.closest_triangle(soup, points)`
が各点の最近傍三角形とその距離を厳密に返すので、`soup.face_index[tri]` で面に戻れる。
同じ格子に別のソリッドを載せたいときは `voxelize(other, grid=model.grid)`。

`closest_triangle` は最近傍点を**7候補(3頂点 / 3辺への射影 / 面への射影)の最小値**で求める。
教科書(Ericson)の領域分けを優先順位つきの上書きで書くと、**退化した三角形(2頂点が重なる)で
複数の領域が同時に真になり、後から上書きしたほうが勝って誤った距離を返す**
(2026-08-31のQA指摘。`a=b=(0,0,0), c=(5,4,4), p=(10,4,-8)` で 13.416407865 を返したが、
線分への正解は 12.638010059)。**退化三角形はOCCTの三角形分割に実際に現れる**ので
(円錐の頂点まわりで実測1枚。`shelf_attachment_7.step` では0枚)、入力で弾くのではなく
ここで正しく扱う。**stage2 は面へ戻る経路をこの関数に頼るので、ここの誤りはそのまま伝播する。**

## 塊(設計空間)と面アンカーの対象ソリッドの分離(2026-09-04)

`voxelize(shape, ...)` は**1つのソリッドに2つの役割を兼ねさせる** —— そのソリッドの占有が
`VoxelModel.design`(削る前の塊)になり、同じソリッドの三角形が `VoxelModel.soup` になって
**拘束・荷重に指定できる面はその面だけ**になる。`run_pipeline` は `void = ~design | obstacle` を
最適化へ渡すので、この経路では**材料は入力ソリッドの外へ一切出られない**(答えは必ず「元の形に
穴が開いたもの」になる)。duocad 本体では塊は利用者に見せない合成物で、拘束面・荷重面は保持
ソリッド等の**別のボディ**に付く。この2つを切り離した入口を足したのがここ。

### 塊はどこから来るか

`voxelize.model_from_design_mask(grid, design, *, anchor_shape, keep=None, obstacle=None, on_outside="raise", ...)`。
**塊は呼び出し側が渡す bool マスク**(`grid.shape` と同じかたち)で、ソリッドの占有である必要は
ない。マスクは複製して持つので、呼び出し側があとから書き換えても `VoxelModel` の中身は変わらない。
かたちが格子と違う場合・全要素 False の場合は `ValueError`(黙って全体を塊にしない)。
戻り値は既存と同じ `VoxelModel` で、`stats` は `voxelize()` と同じキーに `design_source="mask"` と
`on_outside` を足したもの。**`occupancy` キーは無い**(塊がソリッド由来でないため)。

### 面アンカーの対象はどこから来るか

`anchor_shape` から来る。`TopoDS_Shape` / build123d のオブジェクト / **既に作った `TriangleSoup`**
のいずれかを受ける。**面添字は渡したものの面の並びで決まる**ので、面を選ぶのに使った
`TriangleSoup` があるならそれをそのまま渡すこと(作り直すと面添字が食い違いうる)。
`build_anchors(soup, grid, ...)` はもともと三角形群と格子を別々に受け取っていて**下位は既に
分かれていた**。束ねていたのは `voxelize()` と `anchors_for()` の側だけで、
`anchors_for(model)` は `build_anchors(model.soup, model.grid)` のままでよい。

### はみ出しは例外

`keep` / `obstacle` は同じ格子に載せる(内部は `voxelize(..., grid=grid)` と同じ道)。
**塊からはみ出したら既定で `voxelize.OutsideDesignSpaceError`**。`ValueError` の派生なので既存の
`except ValueError` はそのまま効く。文面に「どの領域が何要素はみ出したか(領域の総要素数つき)」を
書き、`e.outside`(`{"keep": n, "obstacle": n}`)で機械からも引ける。
塊を自動で決める経路でははみ出しが普通に起こるため、既定は例外である。
切り詰めてよいときだけ `on_outside="clip"` を明示する(`stats["keep_dropped_outside"]` に件数が残る)。

### 端から端まで

`anchor.run_pipeline(shape=soup, design_mask=mask, design_grid=grid, fixed_faces=..., load_faces=...)`。
面は `int` 1つでも並びでも受ける。荷重の向きは `force`(全ての荷重面で共有する1本)か
`forces`(`load_faces` と同じ並びの、面ごとの力ベクトル[N])のどちらか一方。
`design_mask` と `design_grid` は両方渡すか両方省略する(片方だけは `ValueError`)。渡したときは
**`shape` は塊ではなく面アンカーの対象**になり、`shape` の省略は許さない。あわせて `keep` /
`obstacle`(保持ソリッド / 除外ソリッド)をどちらの経路でも渡せるようにした(どちらも同じ格子に
載り、マスク経路でははみ出しが例外になる)。省略時(既存のデモ経路)の挙動は1ビットも変えていない。
戻り値に `solid`(ρ=1 に固定した要素のマスク)と `void` を足した(既存キーは不変)。

### 実測(2026-09-04・分離の実証。`check_design_space.py` の検査4)

合成ブラケット(`demo_bracket()`: 60×24×24 の箱 + 8×8×6 の耳。bbox は x -30..30 / y -12..12 /
z -12..18)の**面はそのまま**にして、**塊だけ**を差し替える。格子は両方とも同じ
(28, 15, 18) / 要素サイズ 2.769mm。固定=面1(x=-30)、荷重=面10(耳の上面、-z へ 1.0)、
volfrac 0.3、30反復。

| 塊 | 塊の要素数 | ρ>0.5 で**ブラケットの外**に出た要素 | 30反復の所要 | 最終コンプライアンス |
|---|---|---|---|---|
| 一回り大きい箱(x -31..31 / y -13..13 / z -13..25) | 2,772 | **331** | 8.4秒 | 9.93 |
| ブラケットの占有(=旧来の `voxelize()` と同じ塊) | 1,602 | **0**(`void = ~design` により構造的に0) | 5.7秒 | 5.73 |

331 は `run_pipeline` が拘束・荷重の近傍を ρ=1 に固定した分を**除いた**数(除かないと固定分だけで
検査が自明に通ってしまう)。外に出た材料の範囲は [-29.08, -11.08, -12.23] .. [20.77, 11.08, 23.77]
で、耳の上・箱の上下いずれにも出ている。`check_design_space.py` 全体で約20秒。

## 4条件から塊(設計空間)を導出する — 案1: 外接直方体+余白(2026-09-04)

**既定の導出は2026-09-04に案5(下記「4条件から塊を導出する — 案5」)へ置き換わった。**
この節は置き換えられたあとも、(a) `derive()` 自体は案5の内部で「本番の塊(案1の箱)」を
作るのにいまも呼ばれている(案5は箱の中を削るだけで箱は作り直さない)、
(b) `margin_ratio` の既定 0.25 の根拠(下記「余白比率をどう決めたか」)、
(c) 案1のままでは解決しない限界(下記「案1の限界」、案5を試す動機そのもの)
の3点が現行の判断に効いているため、消さずに残す。

利用者は**4条件を入れてボタンを押すだけ**で、塊は最後まで見ない(engine
`topopt-design-space-never-shown-to-the-user`)。塊を見せない以上、**塊は必ず答えを含むだけ大きく
取る**必要がある。`design_space.py` はその導出を1本入れたもので、**案1(条件の点群の外接直方体+
余白)**。これは最終形ではなく、後続の「粗く1回回して膨らませる」案(案5)と比べるための
**ベースライン**である。

### 入れるものと出るもの

```python
import design_space as ds

cond  = ds.Conditions(keep=保持ソリッド, fixed_faces=拘束面の面添字, load_faces=荷重面の面添字,
                      obstacle=除外ソリッド, anchor_shape=None)   # anchor_shape 省略時は keep
# fixed_faces / load_faces は int 1つでも並びでもよい(内部でタプルへ均す)
space = ds.derive(cond, margin_ratio=0.25, elements_long_axis=40)  # → DesignSpace
out   = ds.run_topopt(space, volfrac=0.3, max_iter=60, stl_path=...)  # 端から端まで
```

`Conditions` は**4条件しか受け取らない**(設計空間ソリッドを渡す口が型に無い)。`anchor_shape` は
第5の条件ではなく「面添字が誰の面の並びのものか」の指定で、省略すると保持ソリッドになる。
`DesignSpace` は `grid` / `mask`(塊の bool 配列)/ `model`(`VoxelModel`)/ `soup`(面アンカーの
対象)/ `bbox_min`・`bbox_max`(**余白を足す前**の条件の外接直方体)/ `margin` / `stats`。

導出の手順:

1. **条件の点群** = 保持ソリッドの三角形頂点 ∪ 拘束面の三角形頂点 ∪ 荷重面の三角形頂点。
   **除外ソリッドは入れない** —— 除外は塊から引くものであって、塊を広げる理由にはならない。
2. その点群の**軸整列外接直方体**に、**最長辺 × `margin_ratio`** の余白を全軸へ足す。
3. `grid_for_bbox` で格子を起こす(既存。要素サイズ = 余白後の最長辺 / `elements_long_axis`)。
4. **塊 = 直方体の占有 − 除外ソリッドの占有。**
5. 保持ソリッドが塊に完全に含まれることを確認する(`model_from_design_mask` の
   `on_outside="raise"`)。

### 除外ソリッドを `obstacle` に渡さない(設計判断)

除外ソリッドは**塊を作る時点で引き切り**、`voxelize.model_from_design_mask` の `obstacle` には
**渡さない**。

- 塊 = 直方体 − 除外 と定義した以上、除外の領域には塊の要素が1つも無い。
  `model_from_design_mask` は `keep`/`obstacle` が塊の内側に収まることを要求するので、**同じ除外を
  `obstacle` として渡すと必ず全要素はみ出して `OutsideDesignSpaceError` になる**(検査8がこれを
  実際に突いて記録している。文面は「座標系・単位が違う」と誤誘導するので、なおさら渡さない)。
- **最適化に渡る情報は同じ。** `run_pipeline` は `void = ~design | obstacle` を作るので、除外を
  塊から引いてあれば `~design` 側で同じ要素が落ちる。
- **`on_outside="clip"` へ倒す選択はしない。** clip は「塊からはみ出した保持/除外を黙って切る」
  指定で、前タスクが入れた「はみ出しは例外」という保証をこの経路だけ骨抜きにする。塊の外の除外は
  本来ただの no-op であって、切り詰めが要る状況ではない(検査8で no-op であることを固定した)。

代わりに、**除外が保持を食っている**ケース(塊から引いた結果、保持が塊に入らなくなる)は保持の
はみ出しとして現れ、`design_space.DesignSpaceTooSmallError`(`OutsideDesignSpaceError` の派生)に
なる。文面で除外の重なりと `margin_ratio` を名指しする。

### 格子の外は誰も数えていない(前タスクのQA指摘を塞いだ)

`voxelize` のはみ出し判定は**格子の内側しか見ていない** —— 保持ソリッドが格子の外へ出た分は
`keep_dropped_outside` にも入らず例外にもならない(格子の外にはセル中心が存在しないため)。案1は
格子を条件の外接直方体から起こすので、**余白が負のときにここを踏む**。`derive` は
`model_from_design_mask` を呼ぶ前に、保持ソリッドの **B-rep の bbox** が格子のワールド箱に入って
いることを自分で見て、外れていれば `DesignSpaceTooSmallError` にする(検査9で、比率 -0.05 以下が
実際にここで落ちることを固定してある)。

もう1つ塞いだ食い違い: `run_pipeline` は保持ソリッドを**自分でもう一度**格子へ載せるので、
三角形分割の細かさが `derive` と違うと「ここで通した塊が向こうでは通らない」が起こりうる。
`derive` は格子が決まったあとに `deviation = 要素サイズ × DEFAULT_DEVIATION_RATIO` を取り直して
`run_pipeline` と揃え、`run_topopt` は**両者の保持要素が1ビットも違わないことを毎回確かめる**。

### 余白比率をどう決めたか(既定 0.25)

**これが案1の自由パラメータであり、弱点そのもの。** 利用者に見せない値なので、小さすぎると答えの
居場所を黙って削り、誰も気づけない。値は上の表から決めた:

- **比率 0.05 以下では、要求された材料がそもそも塊に入らない**(絶対体積の表。volfrac が 1 を
  超える)。相対体積のままだと「入らない」が「材料が減った」に化けて見えなくなる。
- **比率 0.10 では、最適化が置いた材料の 34.2% が塊の壁に接している** —— 形を決めているのが荷重と
  拘束ではなく**箱の壁**になっている。0.25 で 8.9%、0.40 で 3.3%。**ここで比べているのは材料比
  (表の括弧の右側)であって、塊比(左側)ではない。** 塊比は余白を広げると分母の塊が膨らむぶん
  だけ勝手に下がるので、「箱の壁が形を決めているか」の指標にならない。
- **コンプライアンスは 0.10 と 0.25 を区別しない**(材料の総体積を固定した比較で 3.14 → 3.18 →
  3.32 → 2.89 とほぼ横ばい・非単調で、0.10 のほうがむしろわずかに良い)。**この2つを分けている
  のは壁への接触だけ**(34.2% → 8.9% と 3.8 倍下がる)。0.40 まで上げても接触は 3.3% にしか
  下がらず、要素数が 2.0 倍・所要が 1.3 倍になる。
- したがって既定は **0.25**。「壊れない一番小さい値」ではなく「**答えが変わらなくなる一番小さい
  値**」に取り、そこから下げない。

**壁への接触は 0 にならない。** 箱は箱なので、どれだけ広げても答えの外周はどこかで箱に触れる
(0.50 でも 3.3% 残り、0.40 から下がらない)。案1は「塊が答えを含む」ことを**保証できない** —— これが案5(粗く1回
回して膨らませる)を試す動機である。

### 案1の限界(数字で分かったこと)

1. **姿勢依存。** 同じ部品を世界の z 軸まわりに回すだけで塊が 1.2〜1.4 倍になり、**同じ volfrac
   のまま材料が 22〜34% 増える**。軸整列の直方体を使う限り消えない。
   **余白が「最長辺 × 比率」なので単調ですらない** —— 45° では最長辺自体が縮む(63 → 55.9mm)
   ので余白も縮み、30° のほうが塊が大きくなる。「45° が最悪」と決めつけて測ると見落とす。
2. **相対体積制約だと、塊を変えるだけで別の答えが出る。** volfrac 固定の表ではコンプライアンスが
   6.57(0.10)→ 1.68(0.50)と 4 倍動くが、これは設計が良くなったのではなく**材料が 7 倍
   入っただけ**(46,805 → 326,401 mm³)。材料の総体積を固定した表では 3.14 → 2.89 とほぼ横ばい。
   **体積制約を絶対量(mm³/g)へ倒す未決の判断は、この2つの表の差がそのまま材料になる。**
3. **余白を大きくすると、要素数を固定したままでは保持ソリッドが痩せる。** `elements_long_axis`
   を 28 に固定して比率だけ上げると、保持の要素数は 0.25 で 61 → 0.6 で 26 → 1.5 で 4 と減る
   (余白が要素サイズを食うため)。**保持が 0 要素になっても「はみ出し 0」は成立してしまう**ので、
   検査6は要素数が 1 以上あることも見る。
4. **検査は「答えの居場所が残っているか」を見ていない。** 検査[5]-[9]のどれかが落ちるのは余白が
   ほぼ無くなってからで、実測では比率 -0.05 以下で「保持ソリッドが格子の外へ出ている」として
   落ちる(-0.02 でも -0.01 でも全部緑)。**比率 0.00 でも全部緑になる。** 案1の余白が小さすぎる
   ことの本当の害 —— 答えの居場所を削ること —— は検査には映らない。既定値 0.25 の根拠は検査では
   なく上の実測にある。

## 4条件から塊を導出する — 案5: 粗く1回回して膨らませる(2026-09-04)

入口は **`design_space.derive_from_coarse_run(conditions, ...)`**。案1(`derive`)と**同じ型・
同じ不変条件**の `DesignSpace` を返すので、`run_topopt(space, ...)` も表示側もそのまま受けられる。
**案1は置き換えていない** —— 並べて足してある。**2026-09-04に既定は案5へ倒した**(下記
「既定をどちらにすべきか」)。導出にこだわりのない呼び出し側が通る入口は
**`design_space.derive_default(conditions, ...)`** の1つで、案1・案5を名指しで呼ぶのは
比較の実測と受入検査だけである。

案1〜案4は**条件の位置だけ**から塊を決める(どこに材料が要るかを一切見ていない)。案5だけが
**一度解いてから決める**。

### 手順

1. **案1で粗い塊を作る**(`derive` を粗い解像度で呼ぶ。新しい箱の作り方は発明しない)。
2. 粗い塊で SIMP を短く回す(`run_topopt`)。
3. ρ を閾値で二値化し、**本番の格子へ最近傍で再サンプル**する。
4. **膨張**(mm)。
5. **4条件の要素(保持・拘束アンカー・荷重アンカー)を無条件で OR し、除外を引く。**
6. 連結性ガード(`assert_faces_connected`。6近傍)を通す。

**再サンプルの対応は物理座標で取る。** 粗い格子と本番の格子は原点も要素サイズも違う
(格子は箱に合わせて切り直されるため、要素数の比にも要素サイズの比にもならない)。添字の割り算で
済ませると別の塊になる —— 検査[11]がその2つを同じ配置で並べて見せている。

### 膨張は mm で持ち、**本番の格子**でかける(設計判断)

- **単位は mm。** 層数で持つと、格子が姿勢と余白ごとに切り直されるぶん(要素体積 62.99 →
  66.43 mm³)同じ設定が姿勢ごとに別の物理距離になる。
- **かける格子は本番側**(タスクの手順は「膨張 → 再サンプル」の順だが、**入れ替えた**)。
  理由は実測である: 粗い格子でかけると膨張の量子が粗い要素サイズ(6.75mm)になり、
  **0mm / 2mm / 4mm がすべて同じ塊(2,414 要素)になった**。mm で指定できるのに 2〜3 段階しか
  取れないなら、mm で持つ意味が無い。本番の格子なら量子は本番の要素サイズ(3.635mm)まで下がる。
- **それでも「1要素より細かくは効かない」。** 受入検査の題材(要素 6.75mm)では 4.0mm と 0.0mm が
  1要素も違わない。`bench.DESIGN_SPACE_COARSE["dilate_mm"]` が 8.0 なのはそのためである。

塊は「その量の材料がどこへ行きたいか」で決まるべきで、粗い段だけ別の量で解くと別の形の周りを

   案1の限界1(姿勢依存)に直接効く。
2. **速い。合計で 0.85倍(0°)/ 0.69倍(30°)。** 粗い段は 1.2〜1.6秒しか掛からないので、
   本番が縮んだぶんがそのまま効く。**注意: 格子は案1と同じである**(案5は案1の箱の中で塊を
   削るだけで、`nelx*nely*nelz` は変わらない)。engine `enlarging-the-box-does-not-get-cheaper-in-simp`
   のとおり ρ=0 の要素も系から消えないのに速くなるのは、**空要素が増えて CG の収束が速くなる**
   ためで、自由度が減ったからではない。
3. **コンプライアンスは同じか、わずかに良い**(3.1796 → 3.1791 / 2.9353 → 2.9249)。
   **案5が答えを削っているという証拠は出ていない。**
4. **壁に接した材料は 0° で負け、30° で勝つ**(材料比 8.8% → 9.1% / 7.9% → 7.8%)。
   `20260904-1400` は「全項目で案1以上ではない」ので据え置いたが、**2026-09-04に案5へ倒した**
   (下記「既定をどちらにすべきか」。**壁接触は代理指標**であって本命はコンプライアンス)。

### 膨張は何を守っているか(検出力の実測)

**膨張0にすると、両方の姿勢で `ZeroDivisionError` になって最適化に入れない。**

理由は構造的である。**膨張0の塊は「粗い段がその材料を置いた場所」そのもの**なので、要求した
材料は必ず塊の容量の端に張り付く(0° で 92.8%、30° でも同様、材料 50,000 mm³ に落としても
1,132 要素 = 92% で同じ)。体積目標が達成可能区間の端にあると OC の二分探索が
`(l2-l1)/(l1+l2)` で `l1 = l2 = 0` へ落ちる —— `20260904-0142` が記録した、**この変更より前から
ある性質**である。

**注意: `simp.VolumeTargetError` は出ない。** 目標(2,241 要素)は容量(2,414 要素)より小さいので
体積の口のガードは通り、**その先の OC が退化する**。「区間の中なら安全」ではない。

タスクが検出力の条件に挙げていた (a) コンプライアンスの悪化 / (b) 連結性ガードの落下は
**どちらも起きなかった**:

- (a) は起きない。膨張 4mm(塊が案1の半分)でも C は 3.1788 で案1の 3.1796 と区別が付かない。
- (b) も起きない。**最近傍の再サンプルは連結性を壊さない**(粗いセル1つが本番セルの連続した
  塊へ写り、隣り合う塊は面で接するため)。膨張0でも塊は1成分のままだった。

したがって **この膨張が守っているのは「答えの質」ではなく「要求した材料が塊に入ること」** である。
なお**閾値を 0.99 まで上げて粗い段の材料をほぼ全部落とすと、連結性ガードが落ちる**
(2成分・拘束側と荷重側が別成分)。案5の塊が切れうることは実在するので、ガードは飛ばせない ——
受入検査[11]がこれを検出力の確認に使っている。

### 既定をどちらにすべきか(2026-09-04に**案5へ倒した**)

**既定は案5**(`design_space.DEFAULT_DERIVATION = "coarse_run"`)。2026-09-04本人決定。

`20260904-1400` が据え置いたのは「比較表の**全項目**で案1以上なら倒してよい」という指示に
従ったためで、**判断は正しく実行されている。その指示のほうが粗かった**:

- **壁に接した材料の割合は代理指標**である(塊が答えを切っている疑いを測るための量)。
  案5の塊は材料の居場所に沿うぶん接触率が上がるのは当然で、「締め付けている」のか
  「ぴったり作った」のかは**この指標だけでは区別できない**。
- 区別する直接の証拠は**コンプライアンス**で、そちらは同等以上(3.1796 → 3.1791 /
  2.9353 → 2.9249)。**切られている証拠は出ていない。**

倒す根拠(数字は上の比較表):

- **姿勢依存がほぼ消える** —— 案1の塊は 0°→30° で 1.38倍、案5は 1.01倍。
- **速い** —— 合計 0.85倍(0°)/ 0.69倍(30°)。
- **塊が材料の量に追従して縮む** —— 50,000 mm³ に落とすと 5,896 → 4,406 要素(案1は 6,988 の
  まま動かない)。材料が少ないほど案5の取り分が大きい。

**倒す前に潰すことにしていた穴2つは、`20260904-1416` で両方潰した**:

1. **膨張0の `ZeroDivisionError` に体積も塊も出ない** → **OC の二分探索の退化そのものを
   `simp.VolumeTargetError`(`side="above_capacity"`)にした。** 文面に「目標 / この反復で
   到達できる最大 / 塊の容量 / その割合」が出る。**区間の内側でも落ちる** ——
   要素数で入る量でも、密度フィルタが塊の縁で目減りさせるぶん届かない配置があるため
   (実測: 容量の 98% は落ち、95% は通る)。健全な経路の計算は1ビットも変えていない
   (`check_absolute_volume.py` [4] の SHA-256 基準は取り直していない=不変)。
2. **1題材でしか測っていない** → **複数の合成条件で測った**(当時は合成4題材カタログ。2026-09-09に
   `design_space.CASES` と `perf.py` ごと削除。検証は `models/*.json` の実物モデルへ一本化)。

(engine `topopt-design-space-never-shown-to-the-user` により、どちらか一方が利用者から
見えない既定になる —— その一方が案5に決まった。)

### 入口を1つにする(`derive_default`)

**導出にこだわりのない呼び出し側は `design_space.derive_default(conditions, ...)` を通る。**
`duocad/optimize_run.py` と `safety_loop.py` がそれで、案1・案5を名指しで呼ぶのは
**比較の実測と受入検査だけ**である。こうしておかないと、既定を倒すたびに呼び出し側を
全部書き換えることになる(そして1つ書き忘れるとそこだけ取り残される)。

- **既定は `DEFAULT_DERIVATION`** の1箇所。`DERIVATIONS` が名前 → 関数の表。
- **引数は既定の導出へ素通し。** いまは案5なので `coarse_material_mm3` がそのまま届く ——
  **本番で使う材料の量が分かっているなら粗い段にも同じ量を渡すこと**(別の量で解くと
  「別の形の周り」を膨らませた塊になる)。後続の安全率の外側ループがこの引数を使う。
- **退避経路は `derive_default(..., derivation="bbox")`**。案1の挙動へ戻して比べるための口。
- 検査は `check_design_space.py` [13]。**呼び出し側が導出を名指ししていないことを
  ソースで見る検査**まで入れてある(名指しが1つ残るとそこだけ取り残されるため)。

| 検査 | 何を見るか |
|---|---|
| 13-1 | `DEFAULT_DERIVATION` が案5で、入口が返す塊に**粗い段の記録が付いている** |
| 13-2 | **案1(`derive`)が残っている**(案5より大きい塊を返す)/ 案1・案5の**既定値が1つも動いていない**(余白 0.25・長辺40 / 粗い段14要素・20反復・閾値0.3・膨張12mm) |
| 13-3 | `derivation="bbox"` で**案1へ戻せる**(退避経路)/ 知らない導出名は例外(黙って既定へ落ちない) |
| 13-4 | **`coarse_material_mm3` が粗い段まで届いている**(既定の volfrac と**はっきり違う量**を渡し、粗い段が実際にその量を出したことで見る)/ 粗い段の体積目標が排他のまま |
| 13-5 | **`safety_loop.py` が導出を名指ししていない**(ソースを読む検査。読むのは `duocad/topopt/` の中だけ) |

### 案5でも消えていないもの

- **粗い段は案1の箱の中で回す。** だから案1の余白比率は**案5にも残っている**
  (`derive_from_coarse_run(margin_ratio=...)`)。案5は箱を小さくするのではなく、
  **箱の中を削る**。
- **格子は案1と同じ**(`nelx*nely*nelz` は変わらない)。姿勢で格子が切り直されること自体は
  案5でも起きる(0° [28,18,19] / 30° [28,24,19])。**消えたのは塊の要素数の姿勢依存であって、
  格子の姿勢依存ではない。**
- **道の細さ・最適化後の材料の連結性は相変わらず見ていない**(連結性ガードの契約のまま)。
- **画面は既定の導出を通る**(2026-09-04〜。当時は実験場の `server.py`、いまは
  `duocad/optimize_run.py`)。画面はその時点での最新の最適化処理を可視化する、という方針
  なので、既定が倒れたら画面も一緒に倒れる。当時の実験場の画面
  (`probe_topopt/web/index.html`)は1行も触らずに済んだ —— 画面から見て変わったのは
  **塊が小さくなったこと**だけだった。

## 塊の中で拘束と荷重がひと続きかを検査する(連結性ガード。2026-09-04)

塊から除外ソリッドを引いた結果、**拘束面と荷重面が別々の島に落ちる**ことがある。そうなると
壁と荷重をつなぐ道が塊の中に存在しない。利用者は塊を見ない
(engine `topopt-design-space-never-shown-to-the-user`)ので、**塊の不備は利用者側からは
観測できない**。だから `design_space.derive` が**つながりを確認してから返す**。

### 連結性の定義: 6近傍(面で接する)

`scipy.ndimage.label` を `generate_binary_structure(3, 1)` で取る(`design_space.NEIGHBOURHOOD = 6`)。
**26近傍にしない。** 角1点・稜1本だけで触れている2要素が共有するのは節点1つで、それは回転を
止められないピン接合(機構)にしかならない —— 力の道として成立しないものを「つながっている」と
数えると、この検査は「切れていない」と言い張りながら宙に浮いた形を通す。検査[10]が、角1点だけで
接する2島を題材にこの定義と実装の一致を見張る(同じ 2島が 26近傍では1成分になることも
同じコードで出す)。

### 何を見て、どこで落とすか

- 対象は **塊 − 除外ソリッド**(`DesignSpace.mask` と同じもの)。
- 拘束側・荷重側の要素は `AnchorTable.element_mask([face], layers=1)`。`layers=1` は
  `anchor.run_pipeline` が ρ=1 に固定する範囲(`keep_layers` の既定)と同じ。
  **塊からはみ出したアンカー要素は落として数える** —— 道になるのは塊の中の要素だけ。
- 拘束側が乗っている連結成分の集合と荷重側のそれに**共通のラベルが1つも無ければ**
  `design_space.DesignSpaceDisconnectedError`(`ValueError` の派生)。文面には
  **成分の数・各成分の要素数・拘束側と荷重側がどの成分にいるか**が入り、例外オブジェクトの
  `components` / `fixed_labels` / `load_labels` から機械でも引ける。
- **`DesignSpaceTooSmallError` とは別の型にしてある。** あちらの文面は「`margin_ratio` を上げろ」で、
  分断には効かない直し方を指す(余白を上げても塞がれた道は開かない)。
- **アンカーの表は `run_pipeline` と同じ作り方(全面・既定の半径)で作る。** `build_anchors` の
  `faces=` で2面に絞ると稜線の規則(節点は最も面積を配った面が持つ)の競争相手が減り、
  **向こうとは別の節点集合**になる —— 同じものを見ているつもりで違うものを見ることになる。
  費用は実測 9ms(長辺22要素)。
- **保持ソリッドの連結性は見ない。** 保持が浮いていても、最適化が材料でつなぐのが正しい
  振る舞いになりうる。見るのは拘束↔荷重の1点だけ。
- **条件面のアンカーが空のときは連結性を見ない**(`skipped: empty_anchor_faces` を返す)。
  それは「要素サイズより小さい面にアンカーが付かない」という別の穴(engine
  `face-to-node-anchoring-loses-faces-smaller-than-the-cell`)で、ここで落とすと
  `empty_faces()` を見る既存の口より手前で別の例外に化ける。
- **挿入位置は `model_from_design_mask`(= 保持が塊に入っているかの確認)の後。** 前タスクの契約は
  「格子外ガードより前」と書いているが、そこからは意図的に外している。3つの位置を実際に試した:

  | 位置 | `check_design_space.py` |
  |---|---|
  | 格子外ガードより**前**(契約の指定) | **検査[9]が落ちる**(57件中1件 FAIL) |
  | 格子外ガードの後・`model_from_design_mask` の前 | 全緑 |
  | `model_from_design_mask` の後(**採用**) | 全緑 |

  **必須なのは「格子外ガードより後」の1点だけ。** 余白比率 -0.05 / -0.10 では保持ソリッドが
  格子の外へ出るが、その前に条件面のアンカー要素が塊から消えるので、前へ置くと連結性が先に
  発火し、検査[9]の梯子の verdict が「格子外」から「拘束側のアンカー要素が塊の中に1つも無い」へ
  化ける。**`model_from_design_mask` の前か後かは、いまの検査では固定されていない**(どちらも
  全緑)—— 後にしてあるのは、除外が保持を食っている配置では「保持がはみ出している」ほうが
  原因に近い診断だという判断による。
  なお**検査[6]は位置を変えても動かない**: 検査[6]の除外(`Box(10, 30, 30) @ (-30,0,0)`)は
  塊の断面を塞がないので、前へ置いても連結性は通る(実測: 1成分・拘束側の要素が63個
  除外の外に生き残る)。「上へ動かすと検査[6]が落ちる」は誤りで、2026-09-04のQA指摘を受けて
  実測し直して書き換えた。

### 切れている塊をそのまま最適化に通すと何が起きるか(実測 2026-09-04)

題材は `design_space.severed_conditions()` —— `demo_conditions()` の除外ソリッドを、2つのパッドの
間を丸ごと塞ぐ壁(厚さ10mm・塊より大きい断面)に差し替えたもの。**連結性の確認だけを迂回して**
(`assert_faces_connected` を no-op に差し替え)最後まで回した。格子は長辺22要素、60反復。

| 配置 | volfrac | 何が起きたか |
|---|---|---|
| 0° | 0.30 / 0.50 | **1反復目で `ZeroDivisionError: float division by zero`**(`simp.py:472`、体積制約の二分法 `while (l2 - l1) / (l1 + l2)`)。numpy の警告が 1,099 件(`invalid value` / `overflow in divide`)。STL は出ない |
| 0° | 0.15 | **60反復を最後まで走り、STL(88 KB)が出る。例外も警告も無し** |
| 30° | 0.15 / 0.30 / 0.50 | **60反復を最後まで走り、STL(181 KB)が出る。例外も警告も無し** |

最後まで走った2件を、つながっている系と並べる:

| | つながっている(参照) | 切れている 0° / vf 0.15 | 切れている 30° / vf 0.30 |
|---|---|---|---|
| 例外・警告 | 無し | 無し | 無し |
| 反復 | 60 | 60 | 60 |
| 塊の要素数(連結成分) | 4,254(**1**) | 3,705(**2**) | 5,205(**2**) |
| コンプライアンス 初期 → 最終 | 30.06 → **3.33** | 1,570,220 → **1,570,197** | 1,348,123 → **1,348,120** |
| 60反復での改善 | 9.0倍 | **0.0014%** | **0.0002%** |
| 達成 volfrac | 0.326 | 0.187 | 0.326 |
| 材料 | 110,022 mm³ | 54,825 mm³ | 131,827 mm³ |
| ρ>0.5 の連結成分 | **1** | **4** | **3** |
| 拘束側 / 荷重側がいる成分 | 1 / 1(**同じ**) | 1 / 2(**別**) | 1 / 2(**別**) |
| STL | 102 KB | 88 KB | 181 KB |

**結論: 検査が無いと、切れている系は2通りに壊れる。どちらも利用者には見えない。**

1. **黙って形が出る**(0°/vf 0.15、30° の全 volfrac)。例外も警告も無く、60反復を走り切り、
   体積制約も満たし、STL も出る。出てくるのは**拘束側の塊と荷重側の塊が別々に浮いた形**で、
   ρ>0.5 の材料は 3〜4 個の島に割れ、拘束側と荷重側は一度も同じ島に入らない。
   コンプライアンスは参照の**約 40 万倍**だが、**利用者はコンプライアンスを見ない**(見るのは形)。
   60反復かけて 0.001% しか下がらないのは「最適化する余地が無い」ことの表れだが、
   これも表に出ない。
2. **原因から遠い場所で落ちる**(0°/vf 0.30・0.50)。`ZeroDivisionError: float division by zero`
   で、文面には設計空間も連結性も出てこない。

**`simp` 側の拘束不足ガードがなぜ作動しないか。** 空要素も剛性の下限 `emin`(既定 1e-9)を持ち、
`simp._floating_dofs` が「空要素にしか触れない節点」を拘束側へ足すので、**荷重側の島は emin の
要素越しに固定節点へぶら下がる**。K は特異にならず、`Model._verify_solution` の残差検算も通る
(実測 max|u| = 1.58e6、コンプライアンス 1.57e6)。`emin` を 1e-12 まで下げると残差検算が
作動する(`残差 2.934e-05 > 1e-06`)ので、**この経路は emin の大きさ次第で黙る**。
**塊の分断は塊を組み立てる側でしか安く確実に検出できない。**

### 検査[10](`check_design_space.py`)

1. 正常系(案1の導出)が通り、拘束と荷重が同じ成分にいる。両側のアンカー要素が塊の中に
   実際にあることも見る(自明に通るのを防ぐ)。
2. 拘束と荷重の間を除外ソリッドで断ち切ると `DesignSpaceDisconnectedError`。文面に成分数と
   両者の成分が出ること、`DesignSpaceTooSmallError` **ではない**こと、
   **壁を外すと同じ条件が通る**こと(落とした原因が壁であることの裏取り)。
3. 塊を**直接**2つの島にして `assert_load_path` に渡すと落ちる。**隙間を埋めると通る**
   (構造的に落ちているのではないことの確認)。
4. **角1点だけで接する2島**が落ちる。同じ `element_components` を 26近傍で呼ぶと1成分に
   なることを並べて出す。
5. 片側のアンカー要素が塊の中に1つも無い場合も落ちる。

### 検査に入れなかったこと

- **保持ソリッドの連結性**(上記のとおり見るべきものではない)。
- **「道が細すぎる」の判定。** 6近傍でつながってさえいれば通る —— 幅1要素の糸でつながっている
  塊も「つながっている」と判定する。細さの妥当性は最適化の仕事であって、塊の妥当性ではない。
- **最適化後の材料の連結性。** `mesh.remove_islands` が最大連結成分だけを残す既存の処理があるが、
  それは出力の後処理で、塊の不備は直せない(上の実測がそのまま示している —— 島が残ったまま
  STL になる)。

## 拘束面・荷重面のアンカーが空のときにメッセージを出す(2026-09-05)

要素サイズより小さい面(フィレット・面取り)を拘束面・荷重面に選ぶと、`AnchorTable.empty_faces()`
に入り節点が1つも付かない。**道具(`empty_faces()`)は `20260903-2234` から既にあり、
`assert_faces_connected` も `20260903-2235` からこれを見て連結性の判定を降りている**が、
**実行経路の入口(`design_space.run_topopt` / `anchor.run_pipeline`)では誰も見ていなかった**。

### 実測: いまの経路は「黙って別の問題を解く」のではなく、既に例外で落ちていた

このタスクの前提だった記述(「荷重面が空だと荷重ゼロで解いて、もっともらしい形が出る。拘束面が
空なら `simp` の残差検算が拾うが、メッセージは『拘束不足の可能性』」)を、着手前に実測で確かめ
直したところ、**現状のコードはこの経路に該当しない**ことが分かった(推測で進めず実測に合わせる)。

`AnchorTable.node_ids`(`table.fixed_dofs` / `table.load_vector` / `table.element_mask` が
内部で通る)は `_require_nodes` を呼び、**空の面が1つでも混ざっていたら `ValueError` で落ちる**
(`20260903-2234` で入った安全策。`check_anchor.py` [6] が「黙って0にせず落ちる」ことを検査で
固定している)。したがって `anchor.run_pipeline` は `table.fixed_dofs(fixed_faces)` /
`table.load_vector(load_faces, force)` の時点で(`simp.optimize` を呼ぶ**前**に)例外を投げる ——
`simp` の残差検算まで届く前に、もっと手前で落ちていた。実測(下の合成題材、要素サイズ5mm):

```
ValueError: 指定した面に格子節点が1つも付いていない: 面7(plane, CAD面積 0.25 mm^2)。
要素サイズ 5 mm に対して面が小さすぎて、稜線の規則で隣の面が節点を全部取った可能性が高い。
解像度を上げるか、隣接する大きい面を指定すること
```

**このメッセージ自体は既に実用的**(面添字・CAD面積・要素サイズ・逃げ道1つが入っている)。
本タスクの完了条件が求めているのは (1) 例外にしない (2) 機械可読な形で返す、の2点なので、
「もっと分かりやすい例外にする」のではなく、**この例外が飛ぶ手前で立ち止まり、同じ情報+αを
返り値に積んで戻る**、という形にした。

### 実装: `run_pipeline` の入口で立ち止まる

- **`AnchorTable.empty_face_diagnosis(face_index) -> dict`** —— 空の面1つの診断。空でない面を
  渡すと例外(呼び出し側の勘違いを早く拾うため)。
  - `cad_area_mm2` / `element_size_mm`。
  - `representative_length_mm` = `√cad_area_mm2`。**近似**(正方形とみなした代表寸法。曲面や
    極端な縦横比の面では粗い)。`suggested_max_spacing_mm` に同じ値を「要素サイズをこれ以下に
    すれば節点が付く見込み」の**目安**として出す(保証ではない)。
  - `absorbed_by_faces` —— 稜線の規則(最も多く面積を配った面が持ち主)でこの面の
    `raw_node_ids`(持ち主を決める前に配った先)を実際に持っていった面。**「別の面を選ぶ」の
    具体名**。標本点が1つも節点の球に入らなかった極端に小さい面では空リストになる。
- **`AnchorTable.condition_face_diagnoses(fixed_faces, load_faces) -> list[dict]`** —— 上を
  `"side"`(`"fixed"`/`"load"`)つきでまとめる。**1枚も空でなければ `[]`**。面は
  `int` 1つでも並びでも受ける。
- **`anchor.format_condition_face_warning(diagnoses) -> str`** —— 上を1つの日本語文にする。
- `anchor.run_pipeline` は `table = build_anchors(...)` の直後、`table.fixed_dofs` /
  `table.load_vector` を呼ぶ**前**にこれを呼ぶ。1件以上あれば `stderr` に印字したうえで
  **`simp.optimize` を呼ばずに早期return**する。戻り値は
  `{"model", "table", "empty_condition_faces", "warning", "fixed_faces", "load_faces",
  "timings", "result": None, "solid": None, "void": None, "surface": None, "stl": None}`
  (最後まで走った戻り値にはこれに加えて `"load_total"`(荷重の大きさの総和[N])が入る)
  (voxelize と面アンカーはこの時点で完了しているので `model` / `table` / `timings` はある)。
  通常どおり最後まで走った戻り値では **`"empty_condition_faces"` は常に `[]`**
  (既存の呼び出し側は無視してよい。新しいキーが1つ増えただけ)。
- `design_space.run_topopt` は `anchor.run_pipeline` へ委譲しているだけなので、上の早期return
  はそのまま伝わる(保持領域の食い違いを見る事後チェックは `model` があれば動くので、
  早期returnでも変わらず効く)。加えて `space.stats["empty_condition_faces_warning"]` にも
  同じ診断を書く —— `DesignSpace` は呼び出し元がそのまま持っているので、戻り値を経由しなくても
  後から `space.stats` で見える(完了条件の「機械から拾える形」を2経路(戻り値 / `stats`)で
  満たす。`progress` コールバックは使っていない — 反復ごとの通知の口を1回だけの通知に流用すると
  意味が変わるため)。

### 逃げ道2つ(完了条件の「利用者が次に何をすればよいか」)

実測(合成題材: 40×24×10 の箱に 0.5×0.5×0.5 の突起、要素サイズ5mm。`check_anchor.py` [6] と同じ形):

```
[anchor.run_pipeline] 警告: 荷重面(面7)に格子節点が1つも付いていない: CAD面積 0.25 mm^2
(代表寸法 約0.5mm)が要素サイズ 5 mm に対して小さすぎる。このままでは荷重面の条件が最適化に
伝わらない。逃げ道: 別の面(面[3])を選ぶか、要素サイズを約0.5mm以下にする
(節点が付く保証はない目安 — 実際に付くかはその要素サイズで確認すること)。
```

- **「別の面を選ぶ」**: `absorbed_by_faces` が実際にこの面の節点を持っていった面を名指しする。
- **「要素サイズをいくつ以下にすれば付くか」**: `√cad_area_mm2` を目安として出す。**近似である
  ことをメッセージにも明記した** —— 面の縦横比が極端だと過大・過小になりうる。保証したいなら
  その要素サイズで実際に `empty_faces()` を取り直すしかない(このタスクではそこまではしない)。

### 面が小さすぎて空になる問題は、本当の解決は保留する(なぜ保留か)

**要素サイズより小さい面にも節点を付けること自体は可能**(「表の作り方」の3段目、稜線の規則の
「多数決」を曲げるか、排他をやめて重みで配るかすれば付く)。**このタスクではやらない**:

1. **排他には理由がある。** 稜線を共有すると同じ節点が「拘束されていて、かつ荷重を受ける」
   状態になり、その荷重は黙って消える(拘束された自由度に載せた荷重は解に効かない)。
   排他はこれを防ぐために置かれた規則(上「稜線の規則」節)。壊すなら代わりの守りが要る。
2. **付けても解決しない。** 節点1つに荷重を載せるのは点荷重=特異点。`20260904-0143` の実測で、
   プリセットの素の最大応力は「ρ=1 の荷重直下(点荷重の特異点)」に出ている。無理やり節点を
   付けた小さい面は、そこに応力が集中して安全率が信用できない値になる —— しかも silent。

「いずれ解きたい問題」として、この2点を次に考え直すときの出発点として残す。

## 体積目標を絶対量(mm^3)で指定する(2026-09-04)

**内部表現は絶対量、利用者の入力は安全率**という2層のうち、**内側の層**。塊を自動で導出する
ようになると、余白比率や姿勢で塊の大きさが変わり、**同じ分率でも材料の量が変わってしまう**
(下の実測では余白比率 0.10 → 0.40 で 4.56倍)。分率の口はそのまま残してある(既存の受入検査が
すべてこれを使う)。

### 口(3層とも同じ2語)

| 層 | 呼び方 |
|---|---|
| `simp.optimize` | `volfrac=` / `material_mm3=` + `element_volume_mm3=`(要素1つの体積) |
| `anchor.run_pipeline` | `volfrac=` / `material_mm3=`(要素体積は**格子から自分で決める**) |
| `design_space.run_topopt` | `volfrac=` / `material_mm3=`(そのまま `run_pipeline` へ) |

- **`volfrac` と `material_mm3` は排他**(両方渡すと `ValueError`)。どちらも省略すると
  `simp.DEFAULT_VOLFRAC`(=0.3)。
- **`optimize` は格子の寸法を知らない**(`nelx`/`nely`/`nelz` しか受け取らない)ので、
  絶対量を渡すときは `element_volume_mm3` も要る。上位2層(`run_pipeline` / `run_topopt`)は
  `voxelize.Grid.element_volume`
  から自分で決めて渡すので、**呼び出し側が `mm^3 → 要素数` を書く必要はない**
  (書くと、格子の作り方が変わったときに黙ってずれる)。
- 分率で回すときも要素体積は渡っているので、`Result.target_material_mm3` /
  `achieved_material_mm3`、`run_pipeline` の戻り値の `target_material_mm3` /
  `achieved_material_mm3` / `element_volume_mm3` はどちらの経路でも埋まる。

### 単位

- **絶対量は mm^3。材料の総体積**であって、`solid_mask`(必ず材料を残す領域)のぶんを**含む**。
- **質量(グラム)は持たない。** 密度を掛けるのは表示上の換算であって、最適化の内部表現に
  持ち込まない —— 持ち込むと「材料をどう定義するか」という別の問題が入ってくる。

### 達成不能な目標は例外(`simp.VolumeTargetError`)

達成できるのは **`[solid の体積, (solid + 動かせる要素) の体積]`** の区間だけ。この外は
`VolumeTargetError`(`ValueError` の派生)で落とす。属性 `side`(`"below_minimum"` /
`"above_capacity"`)・`shortfall_mm3`・`min_mm3` / `max_mm3` で機械から引ける。

```
体積目標 9984mm^3 は達成できない: 動かせる 830 要素と固定材料 2 要素を全部埋めても
6656mm^3 で、目標が 3328mm^3 超えている(塊を広げるか、目標を下げること)
```

**「黙って端に張り付く」わけではなかった(2026-09-04実測)。** ガードを外した状態で区間の外を
指定すると、

| 指定 | ガードが無いとどうなるか |
|---|---|
| 総体積を超える(実効分率 1.501) | OC の二分探索が退化して `ZeroDivisionError: float division by zero` |
| `solid_mask` を下回る(実効分率 -0.002) | 密度が負になり `K U = F が解けていない(残差 …)` |

どちらも落ちはするが、**文面に体積の話が1文字も出ない**(拘束不足を疑えと言ってくる)。
ガードの値打ちは「落ちること」ではなく **「どちら側にどれだけ足りないかを名指しすること」**。

**上端ちょうど(容量と等しい指定)は体積の口では弾かない** —— 数学的には達成可能だから。
ただし OC の二分探索は「動かせる要素が全部 ρ=1」で退化するので `ZeroDivisionError` になる
(`volfrac=1.0` でも同じで、**絶対量の口が入る前からある性質**)。容量の 99.9% は問題なく通る。

### 実測: 塊の大きさを変えたときの材料の量(2026-09-04)

`design_space.demo_conditions()` を余白比率だけ変えて導出し、同じ問題を2通りで解いた
(`spacing=4.0` 指定・`max_iter=5`。`check_absolute_volume.py` [2b] がそのまま走らせている)。

| 余白比率 | 格子 | 塊 | 要素体積[mm^3] | 絶対量 100,000mm^3 指定 | 分率 0.3 指定 |
|---|---|---|---|---|---|
| 0.10 | 21×12×13 | 2,050要素 | 62.994783 | **100,000.000005 mm^3** | 47,913.8 mm^3 |
| 0.40 | 30×21×22 | 10,595要素 | 66.430125 | **100,000.000016 mm^3** | 218,309.3 mm^3 |

- 絶対量なら**要素体積が違っても**(格子の切り直しで 62.99 → 66.43 mm^3)材料の量は
  相対 1.1e-10 で一致する。分率だと **4.56倍**変わる。
- 塊の大きさを変えても物理は同じなので、**変わってよいのは形であって材料の量ではない**。

### 既定の挙動が変わっていないことの担保

`check_absolute_volume.py` [4] が、**基準として採取した `simp.py` の出力**と厳密一致するかを
見る。丸めた10進ではなく **16進float と ρ 場の SHA-256** で比べる(プリセット /
パッシブ要素経路の2本。採取時に2回走らせて1ビット違わないことを確認済み)。

**題材そのものを変えたときは、基準値を取り直すのが正しい。** この検査の意味は
「この変更の前後で1ビットも変わらない」ことであって、特定の数値を守ることではない。
2026-09-04にプリセットを 40×16×16 → 20×8×8 へ縮めたときにプリセット側の4値を取り直した
(`C: 292.2307 → 15.3817` は縮める前の値。いまは `C: 440.3433 → 34.2933`)。
**パッシブ要素経路(16×8×8)は題材を変えていないので基準値もそのまま** —— 取り直したのが
「題材を変えた側だけ」であることが、検査を弱めていないことの担保になる。

## von Mises応力と最小安全率(後処理。2026-09-04)

出てきた形が「保つか」を数字で言えるようにする段(`stress.py`)。**最適化そのものには
手を入れていない。** 応力を制約に入れて最軽量を解く型(応力制約トポロジー最適化)は
**採らない**と決めてある —— 理由4点は context-engine
`safety-factor-goes-outside-the-optimizer`(制約が1本から要素数ぶんへ増える / 特異最適 /
感度が自己随伴でなくなる / **ボクセルの階段状境界では応力が最も信用できない**)。
安全率は最適化器の外側のループで実現する。ここで作ったのは「形を渡すと最小安全率が返る」
ところまでで、外側のループ(安全率 → 材料量の二分探索)は別の段。

### 口

```python
import simp, stress

result = simp.optimize(..., keep_model=True)          # Result.model に解いた Model が入る
scale = stress.UnitScale.for_model(                   # 無次元側(合力・E)は Model から読む
    result.model, element_mm=2.5, load_n=1234.0, youngs_modulus_mpa=68900.0
)
report = stress.evaluate(result.model, result.rho, scale=scale, allowable_mpa=183.3)
report.safety_factor        # 最小安全率 = 許容応力 / 代表応力
report.representative_mpa   # 代表応力[MPa](ρ>=0.5 の 99.5% 点)
report.raw_max_mpa          # 素の max[MPa]。**安全率には使わない**(下記)
report.field.von_mises      # 要素ごとの von Mises [MPa] (nelx,nely,nelz)
```

`simp.optimize` に足したのは `keep_model` の1語だけで、**数値は1ビットも変わらない**
(`check_absolute_volume.py` [4] が ρ 場の SHA-256 まで見ている)。既定は `False` ——
`Model` は `_iK`/`_jK` に**組み立てる要素数**(空要素を除いた数)×576 の添字配列を
2本持つので、要らない呼び出しに数十MBを持たせない。この口が無いと後処理側が拘束・荷重・浮いた節点の扱いを手で組み直す
ことになり、**組み直しを誤ると落ちずに違う応力が出る**。

### 変位はどこから来るか

`simp.Result` は変位を持っていない。**最終 ρ でもう一度 `Model.solve()` を呼ぶ**方を採った
(60反復に対して1回なので費用は無視できる)。`Result` に `u` を持たせなかったのは、
`rho` を後から差し替えた瞬間に `u` が黙って古くなる欄になることと、この後処理が
**`optimize` を通っていない ρ 場**(受入検査の一様な棒・片持ち梁)でも同じ口で動く必要が
あるため。`stress.evaluate(..., u=...)` で外から渡せば解き直さない。

### 応力の実単位への換算則

`simp` は **E=1.0 / 総荷重 1.0 / 要素サイズ 1** の無次元で解く(`optimize` の既定は
変えない。換算は後処理側の責任)。要素サイズ L[mm]・実荷重 F[N]・ヤング率 E[MPa] に対して:

```
sigma_real[MPa] = sigma_nd * (F / F_nd) / L^2
u_real[mm]      = u_nd     * (F / F_nd) * (E_nd / E) / L
```

**応力は E に依存しない。** 剛性は E に比例し変位は 1/E に比例するので、σ = E ε で E が
落ちる。したがって**安全率も E で動かない** —— `youngs_modulus_mpa` が効くのは変位の側
だけである(検査3が「E と荷重を同時に10倍 → 応力はちょうど10倍」で押さえている)。
剛性は要素サイズに比例する(K ~ E·L)ので、変位は L に**反比例**する。

`F_nd`(無次元側の合力)は `stress.UnitScale.for_model` が `Model.f` から読む。
手で書くと `anchor.load_vector` に `force` を渡した系で応力が黙って定数倍ずれる。

### 代表応力の規則(黙って max にしない)

**代表応力 = 「ρ >= 0.5 の要素」の von Mises の 99.5 パーセンタイル**
(`stress.DEFAULT_RHO_MIN` / `DEFAULT_PERCENTILE`)。素の max を採らない理由は2つあり、
**どちらも単独では足りない**(だから2段になっている):

1. **ρ の低い要素を落とす。** そこの応力は物理的に意味が薄い。実測(下表)では
   全要素の max が代表値の 9.8〜30.5倍まで跳ね、細分するほど大きくなる。
2. **残った母集団の上位パーセンタイルを取る。** ρ>=0.5 に絞ってもなお max は
   階段状境界の角で発散する。これは実在の応力集中ではなく離散化の産物で
   (同じ機序の偽の集中は context-engine
   `face-to-node-anchoring-loses-faces-smaller-than-the-cell` に既出)、
   **max で安全率を決めると解像度を上げるほど安全率が下がり続ける。**

要素応力は**要素中心1点**で評価する(意図した平滑化。8つの角で評価すると階段の出隅・入隅が
要素内でも尖り、拾いたくないスパイクを1段増やす)。値は SIMP の見かけの剛性 `ρ^penal·E`
ではなく **材料そのものの応力**(D は E そのまま)で、中間密度の要素はひずみが大きく出るぶん
**安全率を小さい側へ倒す**(安全側)。

母集団が空(どの要素も ρ < 閾値)なら**例外で落とす**。0 を返すと安全率が無限大になり、
「材料が1つも無い形」が最も安全という判定になる。**母集団の von Mises に非有限値
(nan / inf)が混ざっている場合も同じく落とす** —— nan は比較が常に偽になるので、
黙って通すと安全率が nan のまま「許容応力を下回っている」の判定にも引っかからない
(2026-09-04のQA指摘。`check_stress.py` [4b] が守っている)。

### 実測: 斜めに切った板(階段状境界。`check_stress.py` [4])

上端が45度で下がり幅が半分になる板を引っ張り、細い側の公称応力 F/A に対する倍率で見た
(3段の細分。`solver="direct"`):

| 格子 | 素の max | ρ>=0.5 の max | **代表(99.5%)** | 所要 |
|---|---|---|---|---|
| 24×16×2 | 12.92x | 1.538x | **1.324x** | 0.03秒 |
| 48×32×4 | 26.32x | 1.862x | **1.289x** | 1.0秒 |
| 72×48×6 | 39.72x | 2.089x | **1.304x** | 15.5秒 |

- **素の max は収束しない**(12.9 → 39.7。ρ≈0 の要素が支配している)。
- **ρ で絞ってもなお max は単調に増える**(1.54 → 2.09、+35.8%)。階段の角は細分すると
  角が細かくなるだけで、応力は下がらない。
- **代表値は動かない**(1.324 / 1.289 / 1.304。振れ幅 2.7%)。しかも公称応力より 30% 高い
  ので、**本当の応力集中(断面変化)は捨てていない**。

### 実測: 片持ち梁の曲げ(解析解 σ = M·c/I への収束。`check_stress.py` [2])

先端荷重の片持ち梁で、断面内の σ_xx を y で直線近似して外縁 y=±c へ外挿した値と
M·c/I を比べた。測る断面は**根元そのものではなく梁せい1つぶん先**に取る —— x=0 は
全自由度を固定した面で、梁理論の前提(断面が自由に反る)が成り立たない(実測: 根元の
要素は理論値を 8.5% 上回る)。

| 格子 | 外挿fiber / 理論 | 外側1層の要素中心 / 理論 | 所要 |
|---|---|---|---|
| 32×8×4 | 0.9913 (−0.87%) | 0.9911 | 0.03秒 |
| 64×16×8 | 0.9978 (−0.22%) | 0.9977 | 0.8秒 |
| 96×24×12 | 0.9990 (−0.10%) | 0.9989 | 3.4秒 |

誤差は細分でおよそ 1/4 ずつ減る(2次収束)。一様な棒の単軸引張(検査1)のほうは
**丸め誤差の水準で厳密に一致する**(最大相対誤差 3.9e-15)。

### 実測: SIMP の出力(中間密度あり。`check_stress.py` [4b])

プリセット 20×10×10 / 25反復、E=68900 MPa・荷重 1234 N・要素 2.5mm・許容 183.3 MPa:

| 量 | 値 |
|---|---|
| 素の max | 153.5 MPa |
| ρ>=0.5 の max | 153.5 MPa |
| **代表(99.5%)** | **85.77 MPa** |
| ρ の閾値を外した代表値 | 115.4 MPa(**1.346倍**) |
| 最小安全率 | 2.137 |

**ここでは素の max が ρ>=0.5 の max と一致する** —— この形の最大応力要素は ρ=1 の
荷重直下(点荷重の特異点)にあり、ρ の閾値では動かない。それでも von Mises 上位10要素の
うち8つは ρ≈1e-6 の要素で、**閾値を外すと採用する代表値が 34.6% 上がる**。
「ρ の閾値は素の max を下げるためのもの」と読むと**要らないという誤った結論**になるので、
効いているのは**代表値のほう**だと押さえておくこと。

### 留保(消えない問題)

- **この応力はボクセルFEAの上で計算するので、階段の問題は消えない。** 安全率の絶対値は
  信用せず、**同じ解像度での相対比較**と「明らかに足りない/足りている」の判定に使う。
  厳密な検証は別途まともなメッシュのFEAが要る(範囲外)。
- **99.5% と ρ>=0.5 は実測で選んだ値であって、理論値ではない。** 母集団の要素数が少ないと
  99.5% 点は max に近づく(600要素なら上位3要素)。解像度を跨いで安全率を比べるときは
  要素数も一緒に見ること(`RepresentativeStress.element_count`)。
- **点荷重・点拘束の特異点は代表値に残りうる。** 面アンカー経由(`anchor.load_vector`)なら
  荷重は面に配られるが、節点が少ない面では実質的に点荷重になる。
- **疲労・座屈・接触は見ていない。** 出るのは静的な降伏に対する安全率だけである。
- **複数荷重ケース(別シナリオ)は入れていない。** 同時にかかる複数荷重は1回の解で扱えるが、
  設計反復ごとにケース数だけ解く必要がある別シナリオは未対応。打ち消し合う荷重を1つの系に
  合成して代用してはならない。

## 幾何マルチグリッド前処理(2026-09-04)

**既定の解法を「Jacobi(対角)前処理付きCG」から「幾何マルチグリッド前処理付きCG」へ変えた。**
`simp.Model.solve` / `simp.optimize` の既定が `solver="mg"` になっている。
**`solver="cg"`(Jacobi)と `solver="direct"` は消していない** —— 片持ち梁プリセット
(`simp.PRESET`)は `"cg"` のままで、`check_absolute_volume.py` [4] の回帰基準がそれに乗っている。

### 実測の要約(2026-09-04・当時の合成題材 × 2解像度)

Jacobi → 幾何マルチグリッドで **CG反復/solve は 0.07〜0.20倍**(約7〜13倍減)。**秒/設計反復は
0.53〜0.95倍**(題材・解像度でばらつき。極端な薄板 n=30 だけ逆に遅い)。当時の測定合計は
228秒 → 177秒。コンプライアンスは4桁一致(別の近似解なのでビット一致ではない)。

**反復が10分の1でも秒は半分にしかならない。** V-cycle 1回は SpMV の **4.7〜6.3回ぶん**
の仕事があり、密度が変わるたびに各段の RAP と最粗格子の LU を組み直す。Jacobi の1反復は
SpMV 1回だけなので、**反復数の比が費用の比にはならない。**

汎用題材では反復数の伸びが O(N) に近づいた。薄板は反復数は大きく減るが、自由度が
小さく V-cycle の固定費が食い切るので**秒では勝てない**(破綻ではない)。

狭い意味の突き合わせは `check_multigrid.py` [5] で、**コンプライアンスの相対差 2.8e-12 /
rho 場の最大差 1.1e-09**(許容差 1e-6 / 1e-4)。

### 決めた3点(選択肢があるところ)

**1. 粗格子の作用素は Galerkin(`A_c = P^T A P`)。密度を粗格子へ移さない。**

`emin=1e-9` と `penal=3` で実効剛性は **10^9倍**開く。密度を算術平均で粗格子へ落とすと
空の領域が硬くなりすぎて粗格子が別の問題になり、調和平均でも最小値でも「どれだけ間違えるか」が
変わるだけである。**RAP は近似ではなく、細格子の作用素そのものを粗空間へ射影した唯一の
対称作用素**なので、移し方を選ぶ問題自体が消える。おまけに**拘束(固定DOF)と浮いた節点の
扱いが自動的に引き継がれる** —— 粗格子で境界条件を組み直さなくてよい。
代償は毎 solve の RAP の費用で、実測では **66,150自由度・非零496万で 0.08秒**(同じ solve の
`splu` が 0.04秒)。反復1回が 0.02秒台なので、**組み直しは反復5回ぶん程度**である。

**2. 平滑化は damped Jacobi(赤黒 Gauss-Seidel ではない)。**

1回あたりの効きは Gauss-Seidel に劣るが、**行列ベクトル積と要素ごとの積だけ**で書けるので
`20260904-1415`(CPU並列)がそのまま載せられる。減衰係数は
**`omega = 1 / hi`、`hi` は `λmax(D^-1 A)` の見積もり**(`_smoothing_weight`)。ここは
**前処理が対称正定値であるための十分条件 `omega < 2/λmax` を満たす必要がある**ので、
べき乗法の見積もり `lam`(下から近づく)に安全率1.2を掛けた値を使い、
**`gershgorin <= 2.4*lam` が成り立つときだけ**それを採る —— 成り立てば
`λmax <= gershgorin <= 2.4*lam = 2*hi` なので `omega < 2/λmax` が**証明できる**。
成り立たなければ Gershgorin の上界へ退避する(必ず安全側)。
**Gershgorin をそのまま使うと平滑化が弱すぎる**(実測: 真の λmax 3.1 に対して上界 5.36。
50x20x20 の実密度で 56 → 48反復の差になった)。

**3. 粗視化は軸ごとに独立。要素数が4未満の軸は間引かない(半粗視化)。**

均一ボクセル格子なので粗格子は自明(各軸2分の1)だが、**等方に間引き続けると薄板で
厚み方向が先に潰れる**。`_coarse_axis` は要素数が `min_axis_elements`(既定4)未満の軸を
そのまま残すので、**規則1つで自動的に半粗視化になる**。要素数が奇数の軸も扱える
(粗節点を 0,2,4,… と採り、端が合わなければ最後だけ幅1の粗セルにする)。
**格子寸法が2の冪になることはない**(ボクセル化が決める)ので、偶数しか扱えない実装だと
2段目でほぼ必ず止まる。最粗格子は自由度が `direct_dofs`(既定6000)を下回ったところで
`splu` で直接解く。

### 検出力(`check_multigrid.py`)

**マルチグリッド前処理が壊れていても、CG は遅くなるだけで正しい答えに収束する。**
だから「速くなった」「答えが合っている」の2つを見ても実装の正しさは示せない。
`check_multigrid.py` はそれを前提に組んである(実測値は検査の `MEASURED` 行に出る)。

| 見るもの | やり方 | 実測 |
|---|---|---|
| 補間 | 単位分割・非負・**剛体並進を厳密に再現**・列フルランク | 誤差 0.000e+00 |
| 半粗視化 | 薄い軸が間引かれないこと | 36x14x**5** → 18x7x**3** |
| **対称性** | `v^T M w` と `w^T M v` の差 | 1.5e-13(**後平滑化を0にした版は 5.0e-01** ← 検査に検出力がある) |
| 正定値性 | `v^T M v > 0` / 小格子で `M` の固有値 | 最小固有値 3.5 |
| 効き目 | 小格子で `κ(MA)` と `κ(D^-1A)` | **2.91 対 2907.6(999倍)** |
| 粗格子補正を捨てる | 反復数 | 18 → **217回(12.1倍)** |
| 平滑化を1回に減らす | 反復数 | 18 → 25回 |
| 平滑化の重みを1/5 | 反復数 | 18 → 31回 |
| 粗い段の平滑化を増やさない | 反復数 | 35 → 38回 |
| **劣化させても答えは同じ** | 変位の相対差 | どの劣化でも 1e-8 台 |
| 格子非依存 | 段数を揃えた3格子の反復数 | **21 / 19 / 18(比 1.17)**。同じ格子の Jacobi は 214 / 325 / 437(比 2.04) |
| 答えの一致 | 直接解法との変位 / `optimize` の rho 場 | 2.9e-10 / rho 最大差 1.1e-09 |

**「劣化させても答えは同じ」を検査に入れてあるのがこの表の要点**である。答えの一致は
実装の正しさの証拠にならない、ということをコードで示している。

### ウォームスタート(`x0=u0`)は残した

設計反復のあいだ前の解を初期値にする口はそのまま。**外すと反復数がどうなるか**を片持ち梁
40x16x16 の実密度(12設計反復めと11反復めの密度を使う)で測った:

| 解法 | ウォーム(前の解から) | コールド(x0=0) | 増分 |
|---|---|---|---|
| マルチグリッド | 17回 | 18回 | +6% |
| Jacobi | 493回 | 535回 | +9% |

**前処理が良くなると初期値の良さは効かなくなる**(絶対数で 1回 対 42回)。残してあるのは
害が無いからで、**`20260904-1415`(CPU並列)がここを外しても失うのは1割に満たない。**

### 費用がどこへ移ったか(並列化の当たり)

**マルチグリッドは、密度が変わるたびに各段の作用素(RAP)と最粗格子の LU を組み直す。**
片持ち梁の実密度で測ったところ、40×16×16 では solve の **46%** が組み直しだった。
**反復側だけを並列化しても、組み直しが solve の半分を占める大きさでは全体は2倍までしか
速くならない。**

- **`cg_rtol` は 1e-9 のまま。** 反復数が一桁〜数十まで落ちたので、1e-6 へ緩めて得られる
  16%(タスクの見積もり)は誤差の範囲になった。`SOLVE_RESIDUAL_TOL` の誤診の件も
  発火しないので触っていない。
- **`solver="cg"` / `"direct"` はどちらも残してある。** `check_multigrid.py` [5-6] が

## CPU並列化(2026-09-04)

**律速を測り直してから決めた**(`20260904-1414` の契約どおり)。マルチグリッド導入後の
内訳は上の「費用がどこへ移ったか」節にある実測のとおりで、**CG の反復(V-cycleの平滑化・
移送・CG自身の行列ベクトル積)が solve の 54〜84%、RAP+`splu` の組み直しが 16〜46%**
(片持ち梁の実密度・格子3点)。**組み直しはスレッド並列しない**(下記「試して効かなかったもの」)
ので、並列化するのは反復側の行列ベクトル積だけである。

### 有力な手を測った結果(実装の前に)

- **BLASのスレッド数は効かなかった。** 重い計算は疎行列演算で、BLAS(密行列)を経由する量が
  少なすぎる。
- **scipy の CSR 行列ベクトル積は GIL を解放する。** 行ブロック並列で **12スレッド3.8倍**
  (使い捨て測定)。**これが本命**。
- **RAP(疎行列×疎行列)を同じ手で並列化しても速くならない。** 結果の組み直しコストが
  並列化の利得を上回る。`splu` もスレッドプールへ切り出せない。

これらの実測から、**「疎行列×密ベクトルの積だけを行ブロックで並列化する」**方針にした。
新規パッケージは使っていない(`concurrent.futures.ThreadPoolExecutor` は標準ライブラリ)。

### 実装

- **`simp.Model.solve(..., threads=None)`** —— 既定 `None` は呼び出し時に
  `simp.PARALLEL_THREADS` を読む(`MG_DEFAULT` と同じ流儀。`simp.PARALLEL_THREADS = 1`
  を代入すれば全経路が直列に戻る)。`simp.optimize(..., threads=None)` も同じ形で
  `Model.solve` へそのまま渡る。
- **`simp.PARALLEL_THREADS`** —— 既定は**総論理コアの半分(下限1)**(このマシンでは
  14→7。**2026-09-05に `20260904-1558` で `os.cpu_count()` そのものから変更**した ——
  理由と実測は後述「既定スレッド数を総コアの半分にする」節)。
  環境変数 **`TOPOPT_THREADS`** で上書きできる(壊れた値や0以下は1へ退避する。
  `check_parallel.py` [3] が確認)。
- **並列化した箇所**は3つ、すべて「疎行列×密ベクトル」:
  1. CG 自身の `A@x`(`Model.solve` が `threads>1` のとき `kf` を
     `spla.LinearOperator` で包み、行ブロック並列 matvec を差す)。
  2. V-cycle の平滑化 `A@x`(`_vcycle` の `av`)。
  3. V-cycle の移送 `P@e` / `P.T@r`(`_vcycle` の `pv`/`ptv`)。
  RAP(`P.T @ A @ P`)と `splu` は触っていない——上の実測どおり並列化しても速くならないため。
- **`simp._BlockedMatvec`** —— 行列を行ブロックへ割り、`ThreadPoolExecutor` へ
  `submit`/`result` する。**行数がスレッド数に対して少なすぎるとき
  (`_MIN_ROWS_PER_THREAD=512` 未満/スレッド)は自動的にスレッド数を絞り、
  1スレッド相当なら `a @ x` を直に呼んでプールへ投げない**(`_effective_threads`)。
  検査で使う小さい格子(数百〜数千行)でオーバーヘッドだけが乗らないための門番。
- **`simp.parallel_matvec(a, x, threads)`** —— 公開の使い切り口。毎回ブロック分割を
  作り直すので繰り返し呼ぶ用途には向かない(`check_parallel.py` 用)。
  `Model.solve`/`_vcycle` の内部は密度が変わるたびに1回だけブロックを作って使い回す
  (`_build_blocked_levels`)。
- **`_vcycle` の後方互換**: `blocked` 引数を新設したが**既定 `None`**で、`None` のときは
  `a @ x` を直に呼ぶ以前と同じコード経路を通る。`check_multigrid.py` は `blocked` を
  渡さずに `_vcycle`/`_mg_setup` を直接呼んでいるので、**この検査の意味は1バイトも
  変えていない**(実際に46件とも変更なしで緑のまま通ることを確認済み)。
- **伝播**: `simp.optimize(threads=...)` → `anchor.run_pipeline(threads=...)` →
  `design_space.run_topopt(threads=...)`。どれも既定 `None` は `simp.optimize` へ渡さない
  (`solver=None` と同じ形)ので、**渡さなければ挙動は1ビットも変わらない契約**。

### 答えの再現性 —— 選択(a): 加算順序を固定して再現性を保つ

**行ブロックへの分割は答えを変えない。** CSR の行 `i` の内積は、その行に格納された
非零要素だけで決まり、他の行・他のスレッドの計算と独立している。行列をどう行ブロックへ
割っても、どのスレッドがどの行を計算しても、**各行の丸め誤差が発生する順序はまったく
変わらない**——変わるのは「どのスレッドが計算するか」だけで、「どういう順番で足し合わせるか」
は変わらない。CG 本体の縮約(内積・ノルム)はここでは並列化していない(小さいので律速でない。
下記「触らなかったもの」)ので、そちらの再現性もそもそも揺れない。

**したがって、この並列化は追加コストなしでビット一致を保つ。** 検査で実測した:

- `check_parallel.py` [5-1] —— `Model.solve` を `threads=1/2/3/4/8` で解いた変位が
  mg / cg どちらの解法でも**全てビット一致**(`np.array_equal`)。
- `check_parallel.py` [5-2] —— `threads=8` を5回繰り返しても毎回ビット一致
  (スレッドのスケジューリング順序に依らない)。
- `check_parallel.py` [5-3][5-4] —— `optimize(threads=1)` と `threads=8` でコンプライアンス・
  `rho` 場がビット一致(8設計反復)。
- `check_parallel.py` [5-5] —— 片持ち梁プリセット(`solver="cg"`)でも既定スレッド数
  (=14)と `threads=1` が完全一致。
- **`check_absolute_volume.py` [4] の rho 場 SHA-256 は、既定を14スレッドにした状態でも
  2本とも変更前とまったく同じ値になった。取り直していない**(この節の主題は並列化である。
  パッシブ要素経路の指紋は後日 void 除去で別途動いているので、**現行の値は
  `check_absolute_volume.py` の `BASELINES` を見ること**)。
  「答えの再現性」節で選ぶべきだった (a)/(b) の選択は、この並列化に関しては
  **選ぶまでもなく (a) が成立している**——加算順序そのものを変えていないので。

**選択(a)にした理由**: 「行を分けて計算するだけ」という並列化の形が、たまたま
決定的な reduction の条件と一致した。もし将来「複数スレッドの部分和を最後に足し合わせる」
形の並列化(縮約の並列化)を足すなら、そちらは加算順序が変わるので**改めて (a)/(b) を
選び直す必要がある**——ここで選んだ(a)は「行ブロック分割」という実装に紐づいた結論であって、
「並列化全般はいつもビット一致する」という一般則ではない。

### 検出力(退避経路の確認)

- **`threads=1` は並列化前と同じコード経路を通る**(`_build_blocked_levels(levels, 1)` が
  `None` を返し、`_vcycle` は `blocked=None` の分岐——並列化を入れる前と同一の行を実行する)。
  `check_parallel.py` [4-3] が構造そのものを確認している。
- **速度も変わらない**: 並列化を入れる前の `simp.py`(git HEAD、`20260904-1414` の成果)と
  今回の `threads=1` を同一プロセス内で突き合わせた(A/Bスクリプト、代表題材 n=30相当・
  5回のうち最良値)。**917.24ms 対 918.70ms(比 1.002倍)、答えは完全一致**。
  `check_parallel.py` [4-4] は同じ確認をより小さい格子・より緩い閾値(2倍以内)で
  受入検査に組み込んでいる(厳しい閾値にすると機械の熱状態で恒常的に落ちる検査になるため)。

### スケーリングの要約(2026-09-04・当時の合成題材 n=44)

当時の測定合計で t=1 → t=14 は **1.57倍**(t=8 なら **1.65倍**が実用上の目安)。頭打ちの主因は
RAP+splu が並列化されない **Amdahl 分**(スレッドを増やすほど組み直しの取り分が相対的に増える)。
**自由度が小さい問題では逆効果になりうる** —— 受入検査の小格子では `_effective_threads` の
門番でスレッド数が絞られる(`check_parallel.py` [7])。

### 触らなかったもの

- **CG本体の縮約(内積・ノルム)は並列化していない。** `spla.cg` が内部で計算する
  `z・r` 等は O(自由度) の仕事で、SpMV(O(非零要素数)、自由度の数百倍)に比べて
  無視できる大きさ。並列化すると縮約の順序が変わり再現性の議論が変わるので、
  律速でない場所にその複雑さを持ち込まない判断。
- **Barrier ベースの常駐ワーカー方式は試したが採用しなかった。** `ThreadPoolExecutor`
  の `submit`/`result` を `threading.Barrier` 2枚に置き換える使い捨て実験で、
  46x28x31格子・8スレッドの単発 matvec は 2.41ms → 2.09ms(**1.15倍**)という
  程度の差しか出なかった。実装が複雑になる(常駐スレッドのライフサイクル管理、
  例外時のバリア解放)わりに利得が小さいので見送った——将来もっと絞りたくなったら
  最初に検討する場所として残す。
- **RAP・`splu` の並列化は試して効かないことを実測したので触っていない**(上記「有力な手」)。
  `20260904-1414` の契約どおり。

## 安全率を入力に、材料量を二分探索する外側ループ(`safety_loop.py`。2026-09-05)

材料量は「**内部表現は絶対量(mm^3)、利用者の入力は安全率**」の2層にする、と2026-09-04に
決まっている(engine `safety-factor-goes-outside-the-optimizer`)。内側の2枚 ——
`design_space.py`(絶対量の口)と `stress.py`(応力と最小安全率)—— の上に立つ**外側の層**で、
**最適化そのものには手を入れていない**。応力制約トポロジー最適化(応力を制約に入れて最軽量を
解く型)は同ノートの理由により**採らない**。ここにあるのは「最適化を外から何度か回して
材料量を決めるループ」だけ。

### 口

```python
import design_space as ds
import safety_loop as sl

cond = ds.demo_conditions()  # load_n(荷重の実際の大きさ[N])が新設フィールド。既定1.0
result = sl.solve_for_safety_factor(
    cond,
    target_safety_factor=2.0,
    material_min_mm3=60000.0,   # 呼び出し側が決める(このprobeは「常識的な材料量」を知らない)
    material_max_mm3=300000.0,
    derivation_kwargs=dict(elements_long_axis=40),  # 既定は本番相当(重い)。検証は縮めて渡す
)
result.material_mm3      # 目標以上を満たす最小の材料量[mm^3]
result.safety_factor      # そこでの最小安全率
result.converged          # 材料量の相対幅が rel_tol 以内で止まったか
result.space               # 採用した材料量で導出した DesignSpace
result.run                 # design_space.run_topopt() の戻り値
result.report               # stress.SafetyReport
```

達成不能なら `SafetyTargetError`(`ValueError` の派生)。属性 `side` が
`"unreachable_within_max_material"`(`material_max_mm3` まで使っても届かない。`shortfall` に
不足分)か `"invalid_bound"`(`material_min_mm3`/`material_max_mm3` そのものが塊として
導出できない。元の例外を `__cause__` に連鎖)。**文面にどちら側にどれだけ足りないかが出る。**

### 塊が材料量に追従する問題 —— 案aを選んだ

`20260904-1416` で塊の導出の既定が案5(粗く1回回して膨らませる)になり、案5の塊は
**材料の居場所**から作るので、材料量が変われば塊も変わる(`derive_from_coarse_run` の
`coarse_material_mm3`)。外側のループは材料量を動かすので、これが直接ぶつかる。タスク本文が
挙げた3案のうち、**(a)二分探索の各段で塊を導出し直す**を選んだ。

**選んだ理由**: (a)は塊と材料量が常に噛み合う(塊を固定する(b)/(c)は、探索の反対側の端で
塊が締め付ける/緩すぎる)。「段ごとに塊が変わるので、安全率の変化が材料のせいか塊のせいか
切り分けられない」という(a)の弱点は、**この解像度でのコストが実測で無視できる大きさ
(1点あたり0.4〜0.5秒の導出 + 1.8〜2.8秒の最適化)だったので、切り分けを諦めてでも
噛み合わせを取った。**

**比較実測**(bracket、`elements_long_axis=14` / `coarse_elements_long_axis=12` /
`coarse_max_iter=6` / `dilate_mm=8.0` / `max_iter=20`。(c)は最大材料量(249,882mm^3)で
1回だけ塊を固定し、以後はその塊のまま材料量だけ振った):

| 材料量[mm^3] | (a) 安全率 | (c) 安全率 | 相対差 |
|---:|---:|---:|---:|
| 96,108 | 5,078.7 | 5,071.9 | 0.13% |
| 134,552 | 5,831.4 | 5,594.8 | 4.23% |
| 172,995 | 6,008.4 | 5,990.9 | 0.29% |
| 211,438 | 6,260.1 | 6,259.6 | 0.01% |
| 249,882 | 6,417.7 | 6,417.7 | 0.00%(同じ呼び出し) |

材料量が (c) の固定点(249,882mm^3)に近いほど一致し、遠いほど(特に134,552mm^3で4.2%)
ずれる —— (c)の塊は固定点向けに膨らませてあるので、それより少ない材料では塊が
「緩すぎる」側に振れる。どちらも**材料量に対して単調増加**で、二分探索そのものは両方で
成立した。(b)(=固定するだけで最大点も取らない案)は(c)の劣化版なのでここでは測っていない。

### 単調性を測る(2026-09-04実測の要約)

二分探索は「材料量を増やせば安全率が上がる」を前提にする。**これは自明ではない。**
複数の合成条件(薄板・分岐・傾けた除外穴あり等)で案a(塊を毎回導出し直す)を10点ずつ測り、
**測った範囲ではすべて単調増加**だった(`elements_long_axis=14` 前後の粗い解像度。
本番40ではない)。

発見は2点:

1. **極端な薄板題材は材料量を増やしても安全率が頭打ちになる**ことがある —— 二分探索の
   収束判定を材料量の相対幅だけに置くと評価回数を浪費する実例。`dilate_mm` が板厚に
   対して小さいときに起きる。
2. **荷重経路が分岐する題材は材料量が少ないと塊が非連結になる**ことがある
   (`DesignSpaceDisconnectedError`)。`safety_loop.py` は `"too_little"` 側に分類する。

**plate 向けの `dilate_mm` 拡大は単調性測定時だけの調整**であり、`safety_loop.py` の
既定値は変えていない。

### 探索の目標は「以上で最小」

利用者が欲しいのは「安全率がぴったり目標の形」ではなく「**目標を満たす最も軽い形**」なので、
`solve_for_safety_factor` は**目標安全率以上を満たす最小の材料量**を返す(ちょうど、ではない)。
単調なら両者は一致するが、目標をどちらに置いたかで「届かないときの扱い」が変わる ——
「以上で最小」なら「上端まで使っても届かない」だけが失敗になり、「ちょうど」だと
「オーバーシュートしたら失敗」という余分な失敗モードが増える。

### 達成不能の分類

各候補材料量の評価は3つに分類する(`safety_loop._evaluate`):

- `"ok"` —— 通常どおり安全率が出る。
- `"too_little"` —— この材料量では塊が細すぎる。`design_space.DesignSpaceDisconnectedError`
  (拘束と荷重が繋がらない)/ `design_space.DesignSpaceTooSmallError` /
  `simp.VolumeTargetError(side="below_minimum")` のいずれか。**安全率で言えば「目標に
  届かない」と同じ側として扱う**(この材料量とその下は不採用)。
- `"too_much"` —— この材料量**そのものを目標に**導出した塊でも、密度フィルタの目減りで
  材料が収まらない(`simp.VolumeTargetError(side="above_capacity")`)。安全率は測れていない
  ので、この材料量とその上は判定を保留して引き返す。

二分探索の境界(`material_min_mm3` / `material_max_mm3`)自体がこの分類に落ちた場合は
`SafetyTargetError(side="invalid_bound")` で止める(黙って範囲を書き換えない)。

### 許容応力の導出

**PETG の降伏応力 50MPa に、3Dプリントを想定した低減係数 0.8 を掛けた 40MPa を暫定で使う**
(2026-09-04本人決定)。`safety_loop.PETG_YIELD_MPA = 50.0` / `safety_loop.PRINT_DERATE = 0.8`
を別々に定義し、`DEFAULT_ALLOWABLE_MPA = PETG_YIELD_MPA * PRINT_DERATE`(40.0)を使う ——
**40 という数字だけをハードコードしない**。50 はフィラメントのデータシート級の公称値で、
実際に使う銘柄の値へ差し替えられる。

**留保**: 0.8 は積層方向(Z)には楽観的である。FDM の層間接着はふつう XY 方向の40〜60%で、
0.8 には届かない。さらにトポロジー最適化が出す形は、どの部分がどの向きに荷重を受けるかが
最適化の時点では分からないので、造形姿勢が決まるまで一つのスカラーでは異方性を代表できない。
**暫定値である。**

安全率(利用者入力)とは**二重に効く**。0.8 は材料側の低減、安全率は設計側の余裕であり、
両方掛かるのは意図どおり(片方に畳み込むと、造形法を変えたときにどちらを動かせばよいか
分からなくなる)。

### 荷重を実単位[N]で持つ(`Conditions.load_n`)

`stress.UnitScale.for_model` は `load_n`[N] を要求するが、`Conditions` はそれまで荷重の
**向き**(`force=(0,0,-1)`、`run_topopt`/`run_pipeline` の引数)しか持たず、大きさは無次元1.0
だった。`Conditions` に `load_n: float = 1.0` を足した ——**最適化そのもの(`force` の合力)は
無次元のまま変えていない**。`load_n` は `stress.UnitScale.for_model(..., load_n=conditions.load_n)`
が応力を実単位[MPa]へ換算するときにだけ参照する。`check_design_space.py` [5] の
フィールド集合の assert を更新した(5つに増えた: `keep` / `fixed_face` / `load_face` /
`obstacle` / `anchor_shape` / `load_n`。**面の2つは2026-09-07に複数形へ改名**して
`fixed_faces` / `load_faces` になっているが、口の数は6のまま)。

### `keep_model` を2層に通す

`0143` が名指しで残した配線。`anchor.run_pipeline` と `design_space.run_topopt` は
`simp.optimize` に `keep_model` を渡していなかったので、`result.model` が常に `None` で
応力を測れなかった。両方に `keep_model: bool = False`(既定)を足し、そのまま
`simp.optimize(keep_model=keep_model)` へ渡す。**数値は1ビットも変わらない**
(`check_safety_loop.py` [1] が `keep_model` の有無で `rho` が一致することを確認している)。

### 収束条件と回数上限をどう決めたか

- **`rel_tol=0.08`(材料量の相対幅8%)**: **この 8% という数に技術的な根拠は無い。**
  本人が評価回数を2回減らすために選んだ値である(2026-09-09)。`(hi-lo)/hi <= rel_tol` で
  止めるので、**返る材料量は真の最小より最大 8% 重くなりうる** —— これは停止条件から出る
  帰結であって、実測ではない。実測で動いたのは評価回数だけで、bracket・目標5,500 では
  **9回 → 7回**、材料量(143,561.920mm^3)と安全率(5529.587)はどちらも同じ値に落ちた
  (区間が同じ点を通るため。**一般に一致するわけではない**)。
- **「これ以上細かくしない理由」は別にある(8% へ緩める根拠ではない)**: この解像度
  (数百〜千要素)では、材料量が数%動くと塊の要素数が数十〜百単位で変わる(上表の
  `elements` 列参照)。数%より細かく詰めても、ボクセルの量子化と密度フィルタの目減りに
  埋もれて意味のある違いにならない。**これは下限(細かくしすぎない側)の議論**である。
  plate の頭打ち領域のように、材料量の幅だけでは収束の質を保証できない場面があることは
  実測で分かっている(上記)ので、**疑わしい題材では `result.history` を見て安全率側の
  変化幅も確認すること**。
- **`max_evaluations=15`**: 境界2回 + 二分探索。`rel_tol=0.08` まで詰めるのに必要な回数は
  `log2(1/0.08) ≈ 3.6` 回なので、境界込みで6回あれば普通は収束する。実測(上表の
  bracket、目標5,500)では**7回で収束**した。`too_little`/`too_much` を踏んで区間の詰まりが
  遅くなる場合の余裕として15のままにしてある。
- **`max_iter=40`**: `anchor.run_pipeline` の既定と揃えた。二分探索は最適化を評価回数ぶん
  回すので(`20260904-1414`/`1415` のマルチグリッド・CPU並列化が前提)素直に10倍前後
  掛かるが、**このタスクでは素直に回してよい**とタスク本文にある。粗い段で探索して最後に
  1回だけ本番、という2段構えは組んでいない(`20260904-1400` の案5と同じ機構になるので、
  必要になったらそちらと合わせて作るほうが確実)。

## 密度フィルタ半径を mm で指定する(2026-09-05)

**`rmin`(密度フィルタの半径)は要素単位である**(`simp.PRESET` の `rmin: 1.5`)。
解像度(要素サイズ)を変えると、要素単位で同じ `rmin` でも**物理的な平滑化スケールが変わる**
——40分割・要素3.85mmなら `rmin=1.5` は5.8mmの塊を平滑化するが、100分割・要素1.54mmなら
2.3mm。**細かくすると細い部材が許されるようになる = 別の設計問題を解いている。** これは
`20260904-0142`(体積目標が塊の大きさで材料量を変えていた欠陥)とまったく同じ型の欠陥で、
直し方も同じ形に揃えてある。

### 口(3層とも同じ2語)

| 層 | 呼び方 |
|---|---|
| `simp.optimize` | `rmin=`(要素単位)/ `rmin_mm=`(mm)+ `element_volume_mm3=`(要素1つの体積) |
| `anchor.run_pipeline` | `rmin=` / `rmin_mm=`(要素サイズは**格子から自分で決める**) |
| `design_space.run_topopt` | `rmin=` / `rmin_mm=`(そのまま `run_pipeline` へ) |

- **`rmin` と `rmin_mm` は排他**(両方渡すと `ValueError`)。どちらも省略すると
  `simp.DEFAULT_RMIN`。**2026-09-05に `DEFAULT_RMIN` は 1.5 → 2.5要素へ動いた**
  (下記「1要素幅のフィラメントを消す既定値を選び直した」)。**この節が下限として
  書いている 1.5要素は `simp.MIN_RMIN`(床)のほうで、そちらは動いていない。**
- **`optimize` は格子の寸法を知らない**ので、mm で渡すときは `element_volume_mm3` も要る。
  格子は立方体要素(`voxelize.Grid`)なので、その立方根が要素サイズ[mm]に厳密に一致する
  (別の値を測り直す必要はない)。上位2層(`run_pipeline` / `run_topopt`)は
  `voxelize.Grid.element_volume` から自分で決めて渡すので、**呼び出し側が
  `mm → 要素` の換算を自分で書く必要はない**(体積目標(`20260904-0142`)と同じ理由 ——
  書くと、格子の作り方が変わったときに黙ってずれる)。
- 要素単位で渡しても、要素体積が渡っていれば `Result.rmin_mm` で mm 換算が引ける
  (`target_material_mm3` と同じ役割分担)。

### 1.5要素という下限の根拠(要素サイズから決まる床。`simp.MIN_RMIN`。下回ると `simp.FilterRadiusError`)

```python
result = simp.optimize(nelx, nely, nelz, rmin_mm=2.0, element_volume_mm3=grid.element_volume)
```

要素サイズが `rmin_mm / 1.5` より大きいと、この `rmin_mm` を実現するには要素が粗すぎる
—— `simp.FilterRadiusError`(`ValueError` の派生)で落ちる。**逃げ道を2つとも数字で持つ**
(`20260904-0142` の `VolumeTargetError` と同じ形):

```
rmin_mm=3 はこの解像度(要素サイズ 3mm、最長軸 10分割)では表現できない: 換算すると 1要素で、
下限の 1.5要素に 1.5mm 足りない。**逃げ道は2つ**: (1) この rmin_mm を通すには要素サイズを
2mm 以下にする(最長軸で 15分割以上に相当)。(2) この解像度で指定できる rmin_mm の下限は 4.5mm。
```

属性 `min_rmin_mm`(逃げ道2: この解像度で指定できる下限)・`max_element_size_mm`(逃げ道1:
要素サイズをいくつ以下にすればよいか)・`min_elements_long_axis`(それが最長軸の分割数で
いくつに当たるか)・`shortfall_mm`(不足量)・`rmin_mm` / `element_size_mm`(受け取った値)
で機械から引ける。

**1.5要素という値の根拠(検出力の実測)。** `rmin` が1要素を大きく下回ると `_filter_kernel`
の半径 `r = int(ceil(rmin)) - 1` が0になり、フィルタが実質「近傍を見ない」= 未フィルタと
同じになる。未フィルタのSIMPはチェッカーボード(市松模様の密度)が出ることが知られている。
`check_filter_radius.py` [6] が片持ち梁プリセットと同じ格子(20×8×8・volfrac 0.3・20反復)
で実測(隣接要素の離散ラプラシアンの絶対値平均。市松模様で最大化・滑らかな解でほぼ0):

| `rmin` | 指標(roughness) |
|---|---|
| 1.0要素(床より下) | **1.4111** |
| 1.5要素(床 = `MIN_RMIN`) | **0.4178** |
| 2.5要素(2026-09-05からの既定) | 0.1735 |

床を境に指標が**3.4倍**跳ね上がり、半径を増やすほど単調に滑らかになる。1.5は「床を
割ったらどうなるか」を実測して**安全側に**取った値であって(1.0要素ちょうどでフィルタが
無効化する境目そのものではない)、この数字自体は `simp.MIN_RMIN` が正、実測が検査の
しきい値(1.0)の根拠。**この床の上でも1要素幅のフィラメントは出る** —— それが
「1要素幅のフィラメントを消す既定値を選び直した」節の出発点で、だから
**既定(`DEFAULT_RMIN`)を床から切り離した**。**「1.5を assert するだけの検査」にしない**ため、`FilterRadiusError`
のガードを外した(=ガードの下限を弱めた)状態で受入検査を再実行すると、この実測に基づく
6件が実際に落ちることを確認済み(ガードなしでの再実行は使い捨てスクリプトで確認。恒久的な
変異検査としては入れていない — 検査ファイル自体を書き換えないと再現できないため)。

### 回帰基準が動いていないことの担保

`check_absolute_volume.py` [4] が、**基準として採取した `simp.py` の出力**(プリセット /
パッシブ要素経路の ρ 場の SHA-256)と厳密一致するかを見ている。`rmin` の型を
`float = 1.5` から `float | None = None`(+ `DEFAULT_RMIN`)へ変えても、
`simp.PRESET["rmin"]` は変わらず明示的に `1.5` を渡すので、**この変更の前後でSHA-256は
1ビットも動いていない**(2026-09-05確認)。`volfrac`(`20260904-0142`)と同じ形の変更
(排他を判定するには既定値が値であってはいけない)。

**2026-09-05に既定を 2.5 へ動かしたとき、この検査は2箇所を直した**:
パッシブ要素経路の指紋は `simp.optimize` を `rmin` 省略で呼んでいた(=既定に追随して
いた)ので、**採取時と同じ `rmin=1.5` を明示して固定した**(値は不変)。
検査[4]の「`DEFAULT_RMIN == PRESET['rmin']`」も、既定を動かせない前提の assert だった
ので「`PRESET['rmin'] == 1.5`(回帰基準が動いていない)」+「既定値 ≧ 床」へ置き換えた。
**基準値そのものは1つも取り直していない。**

### 単位の等価性

同じ物理半径を `rmin`(要素)と `rmin_mm`(mm、同じ要素サイズへ換算した値)のどちらで渡しても
密度場は一致する(`check_filter_radius.py` [5]。`max|rho_elem - rho_mm|=0.0`)。

### 製造側の下限と目安として載せる値(2026-09-05)

**PETG / 0.4mmノズル。** 押し出し幅 0.4〜0.48mm、壁2本で 0.8mm は「形はできるが構造ではない」。
設計値が出る最小部材幅はおおむね **2〜3mm**(それ以下は層間剥離と座屈が支配)。

**密度フィルタは最小寸法を厳密には保証しない**(保証するにはロバスト定式化＋投影が要る ——
このタスクの範囲外)。目安として、出てくる部材の幅はおよそ **`rmin` 〜 2×`rmin`**。
したがって最小部材幅 2〜3mm を狙うなら **`rmin` ≈ 1.5〜2mm**。

**数値側の下限**: `rmin` ≥ 1.5要素(上の検出力の実測が根拠)。つまり **要素サイズ ≤ `rmin` / 1.5**。

実物部品(最長辺154mm)で、分割数 → 要素サイズ → `rmin`=1.5要素(数値側の下限)→
相当する最小部材幅:

| 分割数 | 要素サイズ | `rmin`=1.5要素 | 相当する最小部材幅 |
|---|---|---|---|
| 40 | 3.85mm | 5.8mm | 6〜12mm |
| 60 | 2.57mm | 3.9mm | 4〜8mm |
| 100 | 1.54mm | 2.3mm | 2〜5mm |
| 128 | 1.20mm | 1.8mm | 2〜4mm |

**mm の既定値は置いていない**(**2.0mm を既定にしない**)。理由:
2.0mmを満たすには要素サイズ ≤ 1.33mm が要り、当時の実験場のデモ(最長軸22分割)も
`design_space` の題材もそこには届かない ——既定にすると現状のデモが全部落ちる。
2.0mmは**目標**として残し、mmの口は**明示的に渡したときだけ**効く。

**要素単位の既定(`DEFAULT_RMIN`)は 2026-09-05 に 1.5 → 2.5 へ動いた。**
上の表の「`rmin`=1.5要素」列は**床**の話なので変わらないが、
**既定で回すと物理半径はその 1.67倍**(長辺40分割なら 5.9〜12.5mm)になる ——
製造の目安 1.5〜2mm からはさらに遠い。**この乖離を埋める手は解像度しかない**
(次節の段2)。

**結論(1行)**: 製造下限が解像度の要求を決める。`rmin` 2.0mm を満たすには要素サイズ
1.33mm 以下が要り、それが `20260904-1414`(マルチグリッド)/ `1415`(CPU並列)が取り組んで
いる速度の話に直結する。

### 上位2層への配線

`anchor.run_pipeline` / `design_space.run_topopt` の両方が `rmin` / `rmin_mm` を受け取り、
排他違反はボクセル化の前に弾く(`simp.check_rmin_target`。`check_volume_target` と同じ
役割分担)。`FilterRadiusError` は要素サイズが分かった後(ボクセル化後)にしか判定できない
ので、`simp.optimize` の内側(体積目標の `VolumeTargetError` と同じ位置)で上がる。

### 受入検査(`check_filter_radius.py`)

引数の形(排他・非正・要素体積の欠落) / 下限を下回ったときの `FilterRadiusError` の属性値
(手計算した期待値と一致) / 境界(ちょうど1.5要素は通り、わずか下は落ちる) / 既定の挙動
(`DEFAULT_RMIN == PRESET["rmin"]`) / 単位の等価性 / チェッカーボードの検出力(上表) /
`anchor.run_pipeline` と `design_space.run_topopt` への配線、を assert する。

## 既定スレッド数を総コアの半分にする(`simp.PARALLEL_THREADS`。2026-09-05)

**既定が全論理コア(このマシンで14)を占有していた**(`_default_thread_count()` が
`max(1, os.cpu_count() or 1)` を返していた)。**配線後は duocad 本体がユーザーのマシンで
回る**ので、最適化中に既定のまま全コアを占有すると、その間マシンが応答しなくなる
(duocad のフロントエンド自体も同じマシンで動いているため。配線前のように実験場で
計算だけを単独に回していたころは困らなかった)。これを**総コアの半分(下限1)**に変えた。

### 変更は1行

`_default_thread_count()` の最後の `return` を `max(1, os.cpu_count() or 1)` から
`max(1, (os.cpu_count() or 1) // 2)` に変えただけ(`simp.py`)。**サイズ由来の上限
(`_effective_threads` が取る `_MIN_ROWS_PER_THREAD` クランプ)との min は既に別の場所で
取れている**ので、新しい門番は足していない ——「問題サイズ由来の上限 か 総コアの半分 の
小さいほう」という規則がそのまま成立する。

このマシン(論理コア14)では、既定 `simp.PARALLEL_THREADS` は **14 → 7** になった。

### 性能でも損をしない

`20260904-1415` の実測(n=44・当時の合成題材): t=4 78.9秒 / **t=8 69.9秒** / t=14 73.5秒。
半分(=7)は最良だった t=8 のすぐ隣で、全コア(t=14)より速い側にいる。

### 明示指定は絞らない(実測で確認)

- **`TOPOPT_THREADS`** はこれまでどおりそのまま使われる(`_default_thread_count` は
  環境変数があれば先に return し、既定の計算(半分化)には触れない)。
- **`optimize(threads=N)` / `Model.solve(threads=N)` で明示した値**もそのまま使われる
  (`threads = PARALLEL_THREADS if threads is None else max(1, int(threads))` ——
  `_default_thread_count` を経由しない経路)。
- 実測: `optimize(threads=14)` で新しい既定7を上回る値を渡しても完走する。
  `--threads` 無指定では新しい既定がそのまま使われることを確認した。

### 回帰基準は動いていない(確認しただけ)

- `check_absolute_volume.py` [4] の rho 場 SHA-256 は**取り直していない**(既定を変える前と
  同じ値のまま)。**この並列化はスレッド数に関わらずビット一致する**(`20260904-1415` が
  実証済み)ので、既定値をいくつに変えても数値は1ビットも動かない。動いたらそれは別の
  不具合である。
- `check_parallel.py` [5-1]〜[5-5](ビット一致)・`check_multigrid.py`(スレッド数に依存
  しない検査)はどちらも変更なしで緑。

### 動いた検査値は1件だけ(緩めていない)

`check_parallel.py` [3-4] は「未設定なら `os.cpu_count()` を使う」という**旧い仕様の
assert**だった(`via_cpu == max(1, os.cpu_count() or 1)`)。既定の仕様そのものが
変わったので、この assert を**新しい仕様に合わせて更新した**
(`via_cpu == max(1, (os.cpu_count() or 1) // 2)`)。**これは閾値を緩めたのではなく、
検査対象の仕様変更に期待値を追随させただけ**である —— 期待するスレッド数は前より
小さくなったが、判定は「半分ちょうど」という具体的な値を要求する形のままで、
`max(1, os.cpu_count() or 1)`(旧仕様)のままでは新しい既定(7)で必ず落ちる。
**他のファイルは1つも変更していない**(新設・削除ゼロ)。

### E コアのせいだと決めつけない(先送りの理由)

`t=14` が `t=8` より遅かった原因は切り分けられていない。`20260904-1415` は熱状態と
推定しているが、もう一つ有力な説明がある —— このCPUは Intel Core Ultra(Arrow Lake)で
**P コアと E コアが混在**しており、`os.cpu_count()` は両方数える。SpMV はメモリ帯域律速
なので、E コアを足しても帯域を食い合うだけで伸びない可能性がある(t=14 の SpMV 帯域が
55〜71 GB/s と DDR5 の実力に近いこととも整合する)。**この上限は、その切り分けを先送り
するための実用的な既定であって、原因を特定したものではない**(「E コアのせいだから半分に
した」わけではない —— 測っていない)。切り分けが要るのは**本体の既定を決めるとき**で、
そのときに P コア数を数えるべきかを測って決める(`20260904-1704` の範囲)。

## CADの面 → 格子の節点(anchor.py)

`voxelize.py` が起こした格子の上に、**「ボディXの面#42」を「これらの格子節点」へ翻訳する
対応表**を載せる(**stage2「面アンカー」**)。これが無いと固定面・荷重面を指定できず、
統合時の `add_fixture` / `add_load` verb も書けない。

**ボクセルの側から境界を取り直してはいけない。** ボクセルの表面は階段状で、真のCAD面から
最大で半要素ずれる。「占有ボクセルの最も左の層」のような取り方をすると、斜面や曲面で
荷重の向きと面積が歪み、階段の角に**偽の応力集中**が出る。出てくる形は「少し悪い」のではなく
「自信を持って間違っている」。正解は**両方の表現が手元にある瞬間(=ボクセル化時)に対応を
固定し、以後はその表を引く**こと。`anchor.py` は `TriangleSoup`(面添字つきの三角形群)と
`Grid` だけを見て表を作り、**占有マスクを一切見ない**(見た瞬間に階段が混入する)。

### 契約(後続がここに依存する)

| 事項 | 決め |
|---|---|
| 節点 | 要素の**角**。要素格子 `(nx,ny,nz)` に対し節点格子は `(nx+1,ny+1,nz+1)` |
| 節点の座標 | `origin + spacing*(i,j,k)`。**要素中心の `+0.5` は付かない**(中心は `Grid.centers_of`) |
| 節点番号 | `n = i*(ny+1)*(nz+1) + j*(nz+1) + k`、自由度 `3n+{0,1,2}`。**`simp._build_edof` と一致** |
| 面と節点 | **1節点は高々1面に属する**(下記の稜線規則)。面ごとの節点集合は排他 |
| 担当面積 | 節点ごとに `mm^2` を持つ。**荷重はこの面積比で配る**(等分は禁止) |

節点番号の一致は `check_anchor.py` の検査[0]が `simp._build_edof` と全要素×8隅で突き合わせる。
**ここがずれると荷重は別の場所に入り、それでも最適化はもっともらしく収束する**ので、
他の検査が全部緑でも意味が無くなる。だから最初に置いてある。

### 表の作り方

1. 面の三角形を、辺長が `sample_ratio * spacing`(既定 0.25)以下になるまで**細分**し、
   各小三角形の重心を標本点にする。小三角形の面積は厳密に等しいので面積は分割で保存される。
   細分が要るのは、平面の面が三角形2枚で返ってくるため —— 三角形の重心だけを見ると
   40×20 の面の荷重が2点に集中する。
2. 各標本点から半径 `radius_ratio * spacing`(既定 **1.0**、引数で変更可)の球に入る節点へ、
   **テント重み** `1 - d/radius` で面積を配る。標本ごとに重みの和で正規化するので面積は保存される。
   - 既定を範囲(要素サイズの0.5〜1.0倍)の**上端**にしてあるのは、`radius >= sqrt(3)/2 * spacing`
     でないと「どの節点も球に入らない標本点」が出るため(要素の中心から最も近い節点までが
     `sqrt(3)/2 * spacing`)。そこへ落ちると最近傍1点へ全部載り、**面の置かれ方によって
     荷重が特定の節点へ集中する**(まさに避けたい失敗)。
   - 既定の `radius = spacing` では、球に入りうる節点は**その要素の8隅だけ**になり、
     重みは三線形形状関数と同じ形になる(候補の探索範囲は `_candidate_offsets` が
     半径から算術的に決める。総当たりの27近傍・64近傍は要らない)。
3. 1つの節点が複数の面の球に入りうる(稜線付近)ので、最後に**持ち主**を決める。

### 稜線の規則(明文化。黙って重複させない)

**節点の持ち主は、その節点へ最も多くの面積を配った面。同点なら面添字の小さい面**が勝つ
(決定的にするため)。したがって:

- 面ごとの節点集合は**排他**。`table.node_ids([面A, 面B])` は素直に連結してよい。
- 他面に取られた節点へ配った面積は**捨てる**(再正規化しない)。捨てた割合は
  `FaceAnchor.leak_ratio`。担当面積の合計を「その面が実際に受け持っている面積」に
  保ちたいため。捨てた分は隣の面が受け持っている。
- 荷重は「その面の節点の担当面積の比」で配るので、捨てた分があっても**指定した総荷重は
  厳密に保存される**(比の正規化で吸収される。実測の相対誤差 2.3e-16)。
- **圧力(`pressure_vector`)の合力は、捨てた面積から独立している。** `p × 面積` が合力
  そのものなので、担当面積から出すと捨てたぶんがそのまま不足する(実測: 要素サイズ
  2.5mm で 11.7%、1.25mm で 4.5%)。**合力は `FaceAnchor.cad_area`(B-repから取った
  真の面積)から出し、その総量を担当面積の重みで按分する。** 配り方は変えていない。

重みを割って両方に配る案(節点を共有する)は採らなかった —— 固定面と荷重面が稜線を
共有していると、同じ節点が「拘束されていて、かつ荷重を受ける」ことになり、
**その荷重は黙って消える**(拘束DOFの荷重は解に効かない)。排他なら少なくとも
どちらか一方には必ず効く。

**この規則の帰結として、要素サイズより小さい面(フィレット・面取り・小さな段差)は
節点が1つも付かず空になる**。実測では 231面のSTEPを要素サイズ 1.54mm で割ると 22面が空。
`table.empty_faces()` で見えるようにしてあり、空の面を名指しして荷重・拘束を作ろうとすると
**黙って「荷重0」「拘束なし」を返さず落ちる**(そのまま通すと、拘束の無い系が最適化に入る)。

### 使い方

```python
model = voxelize.voxelize(shape, 32)                      # stage1
table = anchor.build_anchors(model.soup, model.grid)      # stage2
fixed_dofs = table.fixed_dofs(face_a)                     # 面 → 拘束する自由度
load = table.load_vector(face_b, (0, 0, -1000))           # 面 → 荷重ベクトル(合計は厳密に一致)
keep = table.element_mask([face_a, face_b], layers=1)     # 荷重・拘束の近傍(非設計領域)
result = simp.optimize(*model.grid.shape, fixed_dofs=fixed_dofs, load=load,
                       void_mask=~model.design, solid_mask=keep & model.design)
```

`table.pressure_vector(face, p)` は圧力(面法線の逆向き)を載せる口。合力ではなく
面の向きの分布で決まるので、`load_vector` とは意味が違う。

### SIMP側に足した口(既定の挙動は1ビットも変えていない)

`simp.optimize` / `simp.Model` に足した引数。**境界条件・パッシブ要素の4つが `None` の
ときの挙動は追加前と完全に同じ**(旧版と新版で `rho` がビット単位で一致することを確認済み)。
`keep_model` は数値に一切触らない(既定 `False`)。

| 引数 | 意味 |
|---|---|
| `fixed_dofs` | 片持ち梁の既定の拘束を置き換える。空だと `ValueError`(剛体運動が止まらない) |
| `load` | 既定の荷重ベクトルを置き換える。**自由な自由度に1つも載っていなければ `ValueError`** |
| (共通) | 解いたあと `K U = F` を残差で検算し、通らなければ**拘束不足を名指しして落とす**。`fixed_dofs=[0]` のような拘束不足は「非空で範囲内」の検査を通ってしまい、CGが収束しないまま **max\|u\| = 1.2e16 の有限値**が返って、最適化はそれを信じて進んだ末に OC 更新の `ZeroDivisionError` で落ちていた(原因から遠い場所で落ちるのが最悪) |
| `void_mask` | ρ=0 に固定する要素(設計空間の外・障害物領域) |
| `solid_mask` | ρ=1 に固定する要素(保持領域・荷重や拘束の近傍) |
| `keep_model` | `True` にすると `Result.model` に**実際に解いた `Model`** が入る(既定 `False`)。応力の後処理(`stress.py`)が拘束・荷重・浮いた節点の扱いを手で組み直さずに済ませるための口。**組み直しを誤ると落ちずに違う応力が出る** |

- **パッシブ要素は密度フィルタの「後」で上書きする。** 設計変数だけを固定して物理密度を
  上書きしないと、フィルタが設計空間の外へ密度をにじませる(実測: `rmin=1.5` で設計空間の
  外の要素が ρ=0.29 になった)。にじんだぶんは marching cubes がそのまま形にするので、
  **CADの設計空間からはみ出した形**が出てくる。上書きに合わせて感度も `live` で刈るので、
  連鎖律は上書き後の定義と厳密に一致する。
- **体積制約は動かせる要素だけに掛ける**(目標体積 = `volfrac × 可動要素数 + ρ=1固定の要素数`)。
  そうしないと、設計空間の外の空要素を「もう十分軽い」と数えて、設計空間の中がほとんど
  埋まったまま止まる。
- **空要素にしか接していない節点は拘束側へ寄せて系から外す**。剛性 `emin=1e-9` でしか
  繋がっていない浮いた自由度を残すと K がほぼ特異になり、CGが収束しない。この追加は
  `Model(extra_fixed_dofs=...)` という**別の引数**で行う ——
  `fixed_dofs` に混ぜると、**`void_mask` だけを渡して拘束は既定のままにしたい呼び出しで、
  片持ち梁の拘束が黙って消える**(2026-08-31の自己レビューで見つけて直した欠陥。
  受入検査[0]が「既定の拘束が全部残っている」を見る)。
- **荷重が全部拘束DOFに落ちていたら `ValueError`。** 固定面と荷重面が節点を共有していると
  そうなり、「変位ゼロ・コンプライアンスゼロ」で**荷重を掛けたつもりで何も掛かっていない**
  最適化がもっともらしく収束する。

## メッシュ化(marching cubes + Taubin平滑化)

`mesh.py` が持つパイプライン。**この順序で、段を飛ばさない**:

0. **ガウシアン平滑化+保持/除外の塗り直し**(`smooth_density`。2026-09-05追加。
   詳細は次節「密度場側のガウシアン平滑化」)—— 密度場の**コピー**を
   `scipy.ndimage.gaussian_filter` で均し、`keep_mask` / `zero_mask` を渡されていれば
   平滑化の**後**に保持=1・除外/設計空間外=0へ塗り直す。既定で有効(σ=1要素)。
1. **浮島の除去** — `scipy.ndimage.label` で二値化した場の最大連結成分を求め、それ以外の
   領域を**連続場のほうで**ゼロに塗る(`remove_islands`)。二値化した配列そのものは
   後段(marching cubes)へ渡さない。**段0の出力に対して行う**ので、塗り直しで
   本体から浮いた保持ソリッドは浮島として消える(想定: 保持ソリッドは通常、荷重伝達の
   ため本体と連結している)。
2. **ゼロの縁を1層足す**(`pad_field` = `np.pad(rho, 1)`)。材料が設計空間の端に接していると
   そこだけメッシュが開き、水密でない STL になる。
3. **marching cubes**(`run_marching_cubes`、`skimage.measure.marching_cubes`)——
   **連続値の密度場をそのまま渡す。二値化しない。** 二値化すると全ての辺の両端が
   0/1になり、線形補間が必ず中点(0.5)に落ちて半セルずれた階段が戻ってくる。
   この経路の価値の全ては「補間によって面の位置が要素サイズより細かく決まる」ことに
   あるので、ここを間違えると marching cubes を使う意味が消える
   (`check_mesh.py` の検査5がこれを機械で見張る)。`level`(等値の太さ)は定数で
   埋め込まず引数(既定0.5)。
4. **Taubin平滑化**(`taubin_smooth`)—— **自前実装**(`pyvista` / `vtk` / `pymeshlab` は
   使わない)。頂点隣接をscipyの疎行列で1度作り、離散ラプラシアン `L = D^-1 A - I` を
   λ→μの2段で適用する(λ=0.5・μ=-0.53が既定、すべて引数)。反復数は**2026-09-05に
   30→12へ減らした**(次節参照)。`|μ| > λ` が本質的な条件で、破ると通過帯域周波数が
   負になりただのLaplacianへ退化して形が縮む(`laplacian_smooth` はこの比較専用に
   残してある)。
5. **STL書き出し**(`write_stl`)—— 自前のバイナリSTLライタ(依存追加なし)。
   `output/optimized.stl` に書く。

## 密度場側のガウシアン平滑化 + 保持/除外の塗り直し(2026-09-05)

**この節が選んだ値(σ=1.0要素・Taubin反復 12→30)は、同日の後続節
「1要素幅のフィラメントを消す既定値を選び直した」で反転された** —— 現在の既定は
`DEFAULT_SMOOTH_SIGMA=0.0` / `DEFAULT_ITERS=30`(「現在の正」節)。この節は
導入の動機と、σの値に関わらずいまも効いている仕組み(「保持/除外の塗り直し」。
下記、独立した機能)の記録として残す。**この節だけを読んで現在の既定を判断しないこと。**

### 動機: メッシュ側の低域通過(Taubin)は中周波に効率が悪い

marching cubes の出力に**中周波のうねり**(山と谷)が残り、Taubin をかけても目立ったまま、
という問題が2026-09-05に画像で確認された。原因は伝達関数の計算で分かった。

Taubin(λ|μ)の1反復の伝達関数は `f(k) = (1-λk)(1-μk)`(`k`は空間周波数、`k=0`が一定・
`k=2`が最も細かいナイキスト周波数)。既定値(λ=0.5・μ=-0.53)で `n`反復後は `f(k)^n`:

| k | 意味 | `f(k)` | 30反復後 |
|---|---|---|---|
| ≈0.25 | うねりの周期が要素サイズの~8倍(中周波) | 0.991 | **76%残る** |
| ≈0.5 | うねりの周期が要素サイズの~4倍 | 0.949 | **21%残る** |
| ≥1.0 | marching cubesの階段状ファセット(高周波) | 0.765 | **0.03%まで落ちる** |

**目に見えているうねりは中周波で、メッシュ側の低域通過(Taubin)では反復数をいくら増やしても
効率が悪い。** 密度場を規則格子の上で均してから等値面を切れば、三角形が作られる**前**に
うねりを消せるので marching cubes が最初から滑らかな面を切り、かつ marching cubes の
不規則な頂点間隔に由来する病理(一様重みラプラシアンが密な側へ引っ張る)も避けられる。
**最適化の答えは変えない** —— ρ のコピーを均すだけなので、コンプライアンス・安全率・
最適化そのものの体積目標は1ビットも動かない。

**山と谷の中間を通ってよい**(低域通過)という判断で、モルフォロジーのクロージング
(膨張→収縮。「山を通る」包絡線)は検討したが実装していない(本人判断・2026-09-05)。

### 調整値は2つとも未検証の決め打ちだった(そして同じ日に測って両方動かした)

| 定数 | 値 | 根拠 |
|---|---|---|
| `mesh.DEFAULT_SMOOTH_SIGMA`(ガウシアンのσ) | **1.0要素** | **無い**(未検証) |
| `mesh.DEFAULT_ITERS`(Taubin反復数) | 30 → **12** | **無い**(未検証。`0.765^12≈3.8%`まで
  落ちれば格子ファセットは取れる、という概算のみ) |
| `mesh.DEFAULT_LAMBDA` / `DEFAULT_MU` / `DEFAULT_LEVEL` | 変更なし(0.5 / −0.53 / 0.5) | 既存の実測どおり |

この設計はここまで「なんとなくの既定を置かない」を原則にしてきた(案1の `margin_ratio=0.25`
は姿勢・材料比の実測、案5の `dilate_mm=12.0` は検出力の実測、`rmin=1.5要素` は
チェッカーボードの実測が根拠)。**σとTaubin反復数(12)の2つだけがこの原則の例外**で、
本人が「探索も比較表も作らず、この値のまま採用してよい」と明示した(2026-09-05)。

**その2つは同じ日(2026-09-05)に実測で決め直した** —— σ=1.0 → **0.0(切る)**、
Taubin反復数 12 → **30**。根拠は次節「1要素幅のフィラメントを消す既定値を選び直した」の
段3・段4にある。**この節の残りは「なぜガウシアンを入れたか」の記録として読むこと**
(口は残してあるので `smooth_sigma=` を明示すれば今でも効く)。

### 保持/除外の塗り直し(パッシブ要素と同型の問題)

ぼかすと保持ソリッド・除外ソリッド・設計空間の外がすべて壊れる —— 保持は角が丸まって
食い込まれ、除外・設計空間の外は隣の材料がにじみ込む。**先例がそのまま使える**:
「密度フィルタのパッシブ要素は、フィルタの**後**で物理密度を上書きする」
(下記「SIMP側に足した口」参照。設計変数だけを固定して物理密度を上書きしないと、
フィルタが設計空間の外へ密度をにじませる)。**同型の問題なので、同じ手当てをもう一段
入れた**: `smooth_density(rho, sigma, keep_mask, zero_mask)` はガウシアンを掛けた**後**に
`keep_mask`→ρ=1・`zero_mask`→ρ=0へ塗り直す。

`mesh.build_surface(rho, ...)` はρしか受け取っていなかったので、`keep_mask` / `zero_mask`
(`rho`と同じ形のbool配列)を受け取る口を足した。**マスクを渡さなければ塗り直しはしない**
(ガウシアンは既定で有効なまま)—— `mesh.py`のCLIと`check_mesh.py`本体の題材(片持ち梁)は
保持・除外の概念を持たないので、この経路にあたる。

**`duocad.topopt.anchor.run_pipeline` が実際に塗り直すマスク**は、`simp.optimize` へ
`solid_mask`/`void_mask`として渡したのと**同じ**変数(`solid` = 保持ソリッド+アンカー材料、
`void` = 設計空間の外∪除外)。これらは最適化中すでに物理密度を強制されている領域なので、
段0で同じマスクを再適用するのは「もともと1/0だった値を、ガウシアンがにじませた後に
元へ戻す」だけの操作になる。`design_space.run_topopt` → `anchor.run_pipeline` →
`mesh.build_surface` という既存の呼び出し経路に載るので、**新しい引数を上位2層
(`design_space.run_topopt` / `duocad/optimize_run.py`)へは足していない**。

## 1要素幅のフィラメントを消す既定値を選び直した(2026-09-05)

### 症状と含意

`20260904-1650` の比較(傾けた題材・真横。当時撮った画像は削除済み)で、除外トンネルの縁に
**迷路状の細い筋**が出ていた。幅はほぼ1要素で、構造部材ではなく**チェッカーボード**
(密度フィルタが防ぐべき数値アーティファクト)である。

**含意は見た目ではなく正しさである。** 筋が数値アーティファクトなら、それが担っていた
荷重も架空であり、コンプライアンスと安全率が一部フィクションになる(安全率のループが
材料量を決めた根拠にも効く)。**ガウシアン平滑化(σ=1要素)はこれを溶かして隠していた**
—— σ を上げる方向は証拠を消すだけなので採らない。

原因は `rmin` である。**1.5要素は「チェッカーボードが出ない値」ではなく「フィルタが
無効化する境目(1.0要素)から安全側に取った床」**であり(`20260904-1557`)、その床の上でも
題材によっては筋が残る。**このタスクで初めて、既定を床から切り離して測って決めた。**

### 測った指標(既にあるものだけ。新しい指標は作っていない)

| 指標 | 出どころ | 何を見るか |
|---|---|---|
| roughness | `check_filter_radius._checkerboard_roughness` と同じ式(隣接6近傍の離散ラプラシアンの絶対値平均) | チェッカーボードの直接測定。**設計要素だけで平均する**(塊の外の ρ=0 が混ざると塊の大きさで薄まる) |
| 壁厚 | `mesh.min_wall_thickness` | **頂点ごとの分布**を取り、「壁厚が1要素未満の頂点が全頂点の何割か」を見る(下記) |
| 体積の乖離 | `check_mesh.py` 検査2 と同じ式 | 書き出す形と解析した形の乖離 |
| コンプライアンス | `simp.Result.history[-1]` | **代償**(半径を上げれば必ず悪くなる) |
| 中間密度 | 0.1<ρ<0.9 の要素数 / 設計要素数 | 灰色の残り |
| 秒 | 壁時計 | **代償** |

**`min_wall_thickness` が返す最小値そのものでは、この問題を弁別できない。** 例として
傾けた題材では `rmin=1.5`(筋あり)で 0.0133要素、
`rmin=2.5`(筋なし)で 0.0797要素 —— どちらも「1要素幅よりはるかに薄い」値で、
**どちらが壊れているかを言えない**。**下側の裾(分布)を取ると弁別できる**:

| 傾けた題材(σ=0) | 最小値[要素] | 壁厚の5%点[要素] | 壁厚<1要素の頂点(全頂点比) |
|---|---|---|---|
| `rmin=1.5` | 0.0133 | 0.260 | **17.29%** |
| `rmin=2.5` | 0.0797 | 0.895 | **0.79%** |

**測り方(2026-09-04)**: 複数の合成条件を `derive_default`(案5)で
導出 → `volfrac=0.3` / `max_iter=40`。**ガウシアンは切って(σ=0)測る。**

### 段1: `rmin` を要素単位で振った結論

複数の合成条件(薄板・傾けた除外穴あり等を含む)で測った結果:

1. **1要素幅の筋が出るのは薄板系と傾けた題材だけ。** 汎用ブラケット系は `rmin=1.5` でも 0%。
   **1題材だけで確かめて終わりにできない。**
2. **薄板は `rmin=2.0` で消えるが、傾けた題材は 2.0 でも 6.78% 残る。** 全条件を満たす
   最小は **2.5要素**。
3. **roughness は題材をまたいで比べられない。** 合否は壁厚<1要素の頂点割合(しきい値2%)で取る。
4. **`rmin` を上げすぎると逆に悪化する**(極端な薄板で `rmin=4.0` など)。

### 段2: 解像度との交換(これが本当の問い)

「`rmin` を要素単位で上げる」と「解像度を上げて `rmin_mm` を物理的に保つ」は、どちらも
**フィルタの実効半径を要素単位で 1.5 より上げる**。違うのは**物理半径**で、前者は上がり
(細い部材が作れなくなる)、後者は据え置きになる。

**物理半径は題材ごとに「長辺40要素での1.5要素」に固定した**(`rmin_mm` で渡す)。

**結論**: **既定の解像度(長辺40要素)で筋を消す手は `rmin` を要素単位で上げることしかない。**
解像度を上げる価値は別のところにある —— 同じ物理半径でより良い形が出ることと、
製造の目安(`rmin` 1.5〜2mm)へ物理半径を近づけられること。筋を出さないために要素単位で
2.5 要ると分かったので、`rmin_mm=2.0` を満たしつつ筋も出さない解像度はさらに高くなる
(要素サイズ ≤ 0.8mm 程度)。

### 段3: ガウシアン平滑化はまだ要るか(`rmin=2.5`・長辺40要素・Taubin 12反復で σ を振る)

**要らない。既定を切る**(`mesh.DEFAULT_SMOOTH_SIGMA` 1.0 → **0.0**。`smooth_sigma=` 口は残す)。
`rmin=2.5` で筋は σ=0 の時点で消えている。σ を上げると薄板で体積乖離が 15% を超え、
傾けた題材では筋の割合が増える。**σ=1 が下げるのは roughness だけ**で、それは `rmin` で
得られる。

**副産物: `check_mesh.py` 検査2 の許容差を 12% → 5% へ戻せる**(上記)。
**「応力・安全率は平滑化前の場で評価している」という留保も既定では消える** —— σ=0 なら
評価した場と marching cubes へ渡す場が(保持/除外の塗り直しを除いて)同一になる。

### 段4: Taubin の反復数(σ=0 に戻したので、格子ファセットを取る仕事が戻ってくる)

`check_mesh.py` と同じ題材(片持ち梁 35×14×14・15反復)で σ=0 固定・反復数だけを振った実測:

| 反復数 | `f(k=1)^n`(格子ファセットの残り) | Taubinの体積変化 | 最小肉厚 前→後 | 比 |
|---|---|---|---|---|
| 0 | 100% | 0.0000% | 0.2350 → 0.2350 | 1.000 |
| 6 | 20.0% | −0.1901% | 0.2350 → 0.4091 | 1.741 |
| 12(2026-09-05午前の既定) | 4.02% | −0.2108% | 0.2350 → 0.4599 | 1.957 |
| 20 | 0.47% | −0.1487% | 0.2350 → 0.4556 | 1.939 |
| **30(採用)** | **0.03%** | **−0.0030%** | 0.2350 → 0.4917 | 2.093 |
| 45 | 0.001% | +0.2903% | 0.2350 → 0.5003 | 2.129 |

**`mesh.DEFAULT_ITERS` を 12 → 30 へ戻す。** 12 にしたのは「ガウシアンが中周波を
引き受けたので Taubin は格子ファセットだけ取ればよい」という理由だった(`20260904-1650`)。
**その理由が消えたので値も戻す。** 費用は無視できる(メッシュ化の段は全体で10〜20ms)、
縮みも 0.003% で 12反復(0.21%)より小さい。

**中周波(k≈0.25〜0.5)は Taubin では取れないままである** —— 30反復でも
`f(0.25)^30 = 0.761` / `f(0.5)^30 = 0.206` しか落ちない。**そこは `rmin` を上げたことで
密度場側が滑らかになったぶんで対処している**(段1の roughness が題材ごとに 0.43〜0.61倍)。
**ガウシアンで消していたのは「見えなくする」であって「滑らかにする」ではなかった**、
というのがこのタスクの結論である。

### 選んだ既定値と根拠

**選び方は2段階**(単一のスコアを作らない):

1. **正しさの条件で絞る** —— **複数の合成条件すべてで、壁厚が1要素未満の頂点が全頂点の 2% 以下**
   (測定分布の 0〜1% 群と 7〜17% 群の間に隙間があり、2% はその内側)。
2. **その中でコンプライアンスが最小のもの** —— `rmin` に対して単調増加なので、条件を満たす
   最小の `rmin` が答えになる。

| 定数 | 旧 | 新 | 根拠 |
|---|---|---|---|
| `simp.DEFAULT_RMIN` | 1.5要素 | **2.5要素** | 段1。全合成条件が正しさの条件を満たす最小 |
| `mesh.DEFAULT_SMOOTH_SIGMA` | 1.0要素 | **0.0(切る)** | 段3 |
| `mesh.DEFAULT_ITERS` | 12 | **30** | 段4 |
| `simp.MIN_RMIN`(**新設**) | — | 1.5要素 | 床。`20260904-1557` の実測がそのまま根拠。**既定と分離した** |
| `simp.PRESET["rmin"]` | 1.5 | **1.5(不変)** | 回帰基準。`check_absolute_volume.py` [4] の ρ 場の SHA-256 が乗っている |

**床(`MIN_RMIN`)と既定(`DEFAULT_RMIN`)を分離したのがこのタスクの構造上の変更である。**
1つの定数が兼ねていると、既定を上げた瞬間に `rmin_mm` の受理範囲(`FilterRadiusError` の
境界)と `optimize_run.resolution_limits` が要求する解像度まで黙って動く。床が守っている
のは「これより下はフィルタが壊れる」で、その根拠(`check_filter_radius.py` [6] の
1.0 対 1.5 の実測)は**今回1ビットも動かしていない**。

**床のほうを 1.5 のままにしてよいのか、という問いは残っている。** このタスクの実測は
「1.5要素でも題材によっては1要素幅の筋が出る」ことを示したので、床を上げるべきという
議論はできる。**しかし上げると、いま通っている `rmin_mm` の指定が例外になり、
`optimize_run.resolution_limits` がUIへ要求する解像度が跳ね上がる** —— 本人の判断が要る
範囲なので手を付けていない。

  前後は全部 `IN`。±0.0001mm ずらした点も `OUT`、±0.1mm ずらすと全点 `IN`。

## 受入検査の通し時間(2026-09-04)

**方針: 配線が終わるまで、解像度と反復数は検証が速い側に倒す。性能と品質を詰めるのは配線の後**
(2026-09-04本人指示)。ここを「本番相当にすべきでは」と揺り戻さないための記録である。
検査の題材の大きさは **`bench.py` 1箇所**(と、片持ち梁そのものは `simp.PRESET`)にまとめてある。

`voxelize.occupancy` のレイのずらしは、格子が粗くなると**飛び飛びの解像度で縮退する**
(「レイのずらしを6通り試したがすべて縮退した」で `derive` が落ちる)。実測:

- `check_design_space.py` の `CASE1_LONG_AXIS`: **12 と 16 で落ちる**。13/14/15/17/18/20/22 は通る → **14** を採った。

- `check_design_space.py` の `LONG_AXIS`: 14 で拘束面と荷重面が同じ節点を掴み `simp.Model` が
  「荷重が自由な自由度に載っていない」で落ちる。16 は通るが余裕を見て **18**。

**「小さいほど危ない」ではないので、1点で試して通ったら採る、をやらないこと。**
通る値の帯を確かめて、その真ん中を採ってある。

### OCCT の bbox はトリムを見ない(2026-09-07)

`BRepBndLib::Add` は**面のトリムを見ず、下地のサーフェス全体で囲む**。トリムされたトーラス面はドーナツ丸ごとで囲まれるので、曲がったバーの一部のような
形では bbox が実寸から大きく外れる。実測(`models/hanger_bar_attachment.json` の
`hanger_bar_attatchment_7`。トーラス6枚+平面2枚・体積 17,034mm^3):

| 測り方 | 辺の長さ [mm] |
|---|---|
| `BRepBndLib::Add`(トリムを見ない) | **482.8 x 252.1 x 252.1** |
| `BRepBndLib::AddOptimal`(トリムを見る) | 35.0 x 36.6 x 36.6 |
| 三角形分割(deviation 0.05) | 35.0 x 36.6 x 36.6 |

**x で約14倍。** `derive` の格子外ガードがこれを使っていたため、格子に収まっている保持を
「格子の外へ出ている」と落としていた。しかもエラー文は `margin_ratio` を上げろと言うが、
**上げても直らない**(実寸の14倍を覆う余白にすると要素サイズが使い物にならなくなる)。

**円柱・平面だけの部品では両者はほとんど一致する**(同じ文書の他の3ボディは 18.6 対 17.2mm
= 弦が円の内側に来るぶんだけ)。**曲面の種類によって壊れ方が変わるので気づきにくい。**

`kernel.bounding_box` と `voxelize._shape_bbox` は**両方とも `AddOptimal`** で取る
(2026-09-07)。`check_design_space.py` [9] と `check_voxelize.py` [10]、
`tests/test_kernel_bbox.py` が、どちらの bbox も三角形分割の節点と一致することを固定する。

**`AddOptimal` は繰り返しても速くならない**(OCCTは内部で結果を持たない。実測: 11ボディで
`Add` 0.09ms 対 `AddOptimal` 178ms = 約2000倍)。そこで繰り返し呼ぶ経路は
`kernel.BoundingBoxCache` に載せてある —— `Document` が1つ持ち(`document.bbox_cache`)、
文書を差し替えると `Document` ごと捨てられる。実測(`models/hanger_bar_attachment.json`、
`optimize_run.resolution_limits` の定常状態の中央値):

| 測り方 | 1回あたり |
|---|---|
| `Add`(差し替え前) | 0.56ms |
| `AddOptimal` + キャッシュ | 0.50ms |
| `AddOptimal` キャッシュ無し | **145ms** |

**初回のコストは消えない**(キャッシュは1つも減らさない)。実測: 11ボディの
`describe_document(include_bbox=True)` が初回 190ms・2回目 7.5ms。29%のボディの寸法が
最大9倍狂っているほうが害が大きい、という判断でこれを受け入れてある(2026-09-07 ユーザー決定)。

**`TopoDS_Shape` は `hash` が一致しても `__eq__` が False を返す**ので、素の `dict` や
`lru_cache` は**1回も当たらない**(遅いままメモリだけ増え、動いてはいるので気づかない)。
鍵は `IsSame` で引く(`kernel._ShapeKey`)。**`IsSame` は Orientation を見ない**ため、
この同一性を bbox 以外へ流用すると静かに壊れる。

## 受入検査が見ているもの

**走らせ方は `readme.md` §3「形状最適化の受入検査」にある。** ここに書くのは、各 `check_*.py` が何を守っているか。

どれも最後の行が `OK:` で、終了コードが 0 なら合格。

`check_simp.py` が見ているもの:

1. **要素剛性行列** — 対称 / 半正定値 / 剛体モードがちょうど6本 / **パッチ試験**
   (一様ひずみ・せん断のひずみエネルギーが弾性論の値と 1e-10 相対で一致、剛体運動のエネルギーが0)。
   B行列・D行列・ヤコビアン・局所節点順のどれが狂っても落ちる。
2. **全体系** — `K U = F` の残差 / 拘束DOFが0 / **コンプライアンス = F・U** / 荷重と拘束がz対称。
   要素→全体のDOF写像の誤りを捕まえる。
3. **(a)** 体積分率が目標の ±1% 以内 /
   **(b)** コンプライアンスが減少し(最終 < 初期)、終盤10反復の変動が1%未満 /
   **(c)** 密度場がz対称(CG解法で 1e-6 以内、直接解法で 1e-9 以内)。

`check_mesh.py` が見ているもの:

1. **水密** — すべての辺がちょうど2枚の三角形に共有される。孤立頂点・縮退三角形が無い。
2. **体積の一致** — marching cubes直後(段0のガウシアン平滑化+塗り直しを経た後)の
   メッシュ体積が `sum(rho_clean) × 要素体積` と一定範囲内(12%。2026-09-05に5%から
   広げた — 上の「密度場側のガウシアン平滑化」節)で一致する(等値0.5の面としてまともか)。
3. **Taubinが体積を保つ** — 平滑化の前後で体積変化が5%以内。
4. **Taubinが素のLaplacianより縮まない** — 同じ反復数・同じ開始点で素のLaplacianを回し、
   Laplacianのほうが明確に大きく縮むことを確認する
   (「Taubinと名乗っているが実はLaplacian」の検出)。
5. **補間が効いている(先に二値化していない)** — marching cubesが辺上に置いた頂点の
   内分比の分布の標準偏差が0でないことを見る(二値化した場を渡すと厳密に0になる)。
6. **最小肉厚** — 平滑化の後も、最小肉厚が平滑化前の50%を下回らない
   (細い部材を食っていないこと)。
7. **STLの往復** — 書き出したSTLを `build123d.Mesher().read()` で読み戻し、三角形数(=面数、
   facetedB-rep)と体積が一致する。
8. **座標系の整合(セル中心規約)** — 既知の位置に置いた合成密度場で、面のバウンディング
   ボックスが期待どおりの位置にあるかを見る。1〜7はどれも並進不変(体積・水密性・
   分布の形は位置のズレでは変わらない)なので、**全軸を一律に半セルずらす**類のバグを
   検出できない(2026-08-30、QAが実データで発見した不具合。下記「設計上の決定」参照)。
9. **面の向き(巻き順が外向き)** — 閉曲面の向きは「全部外向き」か「全部内向き」の2通り
   しかないので、(a)向きが全面で一貫している(共有辺を2枚の三角形が必ず逆向きにたどる
   ＝同じ有向辺が2度現れない)ことと、(b)発散定理の符号付き体積が正であること、で確定する。
   (a)だけだと全体反転を、(b)だけだと一部反転の打ち消し合いを見逃す。**閾値は無い。**
   1〜8で巻き順を見るのは検査7だけで、それは**STL経路しか通らない**ため、`mr.faces` を
   直接使う消費者(当時は実験場の `server.py` → three.js描画。いまは
   `duocad/optimize_run.py`→`add_mesh_body`→`web/src/viewport.ts`)が内向きのまま残る事故を捕まえられなかった
   (2026-09-02発見。下記「設計上の決定」の巻き順の項)。
10. **保持/除外の塗り直し**(2026-09-05追加) — 合成密度場(本体ブロック+保持スパイク+
    除外の穴)にσ=3.0(極端値)のガウシアン平滑化+塗り直しを掛け、(a)段0の出力の場で
    保持=1・除外=0が厳密に保たれる、(b)できたメッシュを`voxelize.occupancy`で焼き直し、
    保持マスクの要素がすべて内側・除外マスクの要素に材料が1つも入っていない、
    (c)この合成場でも水密・面の向きが保たれる、を見る。詳細は上の「密度場側の
    ガウシアン平滑化」節。

`check_voxelize.py` が見ているもの(合成ソリッドだけで、私物STEPには依存しない):

1. **OCCT の神託との一致** — `BRepClass3d_SolidClassifier` の判定と高速経路が一致する。
   合成6形状 × (無作為に選んだ要素2,000個 + 表面の近くに偏らせた要素2,000個)。
   比べるのは**要素の中心**であって任意の点ではない —— 高速経路が決めているのは中心の
   内外なので、任意の点を要素の占有と比べると「中心と点が表面をまたぐ」だけで不一致になる
   (最初にそれをやって4.9%の偽の不一致を出した)。**表面から要素サイズの5%以内の中心は
   集計から除く**(三角形分割の弦誤差=2%より大きく取ってある)。除いた件数も表示する。
2. **既知形状の体積が収束する** — 円筒と傾けた箱で、格子に対する形状の位置を
   **サブセル単位でずらした10通りの平均誤差**が解像度とともに単調に減る。
   1つの解像度の1点の誤差では駄目 —— 実測で円筒の相対誤差は n=16 で 0.4%、n=24 で 3.5% と
   **増える**(位置をずらして平均すると n=8→64 で 3.9%→0.2% と単調に減る)。
3. **貫通穴が埋まらない** — 穴のある板で、穴の内側が1要素も占有されない。
   かつ実体側は隙間なく埋まる(「全部空」で通らないように両側を見る)。
4. **壊れた入力で黙って通らない** — 開いたシェル / 向きを裏返した面を含むシェル /
   裏返したソリッド / **内部空洞の殻だけを裏返した中空の箱** /
   (`inspect_soup` を通さずに)閉じていない三角形群を `occupancy` へ直接、
   の5種で `ValueError` になる。健全な入力(ただの箱・**健全な中空の箱**)が通ることも
   併せて見る(「常に落ちる」実装で緑にならないように)。
5. **保持/障害物マスクが設計空間の内側に収まる** — 外へはみ出した分が捨てられ、
   捨てた件数が報告され、`free` と `initial_density` が整合し、保持と障害物が重なったら落ちる。
   **設計空間とまったく重ならない領域**は、どの領域が/どこにあって/格子はどこかが分かる
   文言で拒否される。
6. **決定性** — 同じ入力で2回呼ぶと格子もマスクも完全に一致する。加えて
   **同じ形状オブジェクトを使い回して(別解像度を挟んで)も**三角形群まで一致する
   (2026-08-31にここで欠陥を発見。下記「設計上の決定」参照)。
7. **セル中心規約の整合** — 辺長が要素サイズの整数倍の軸整列の箱は、**どの解像度でも
   体積が厳密に一致する**(幅 L の区間に入るセル中心の数は、L が要素サイズの整数倍なら
   位置によらず L/h 個)。原点や中心の取り方が半セルずれれば必ず崩れる。あわせて
   占有要素の中心の範囲・`Grid` の3つの口の一致・添字との往復を見る。
   1〜6はどれも半セルの平行移動に鈍感なので、これを別に置いている。
   さらに **B-rep の bbox に対して**1要素以上の余白があること(三角形分割の bbox から
   格子を作り直すと1要素を割る)と、**原点から 1e10 mm 離しても符号付き体積が桁落ちしない**
   ことを見る。
8. **縮退したレイでも壊れない** — 上面の対角線が列の中心を厳密に通る箱で、レイのずらしを
   切っても体積が厳密に一致する(巻き数で数えていることの確認。偶奇だと5%低く出る)。
   併せて円錐で、ずらしのほうが実際に効いていることと、**既定のずらし幅にちょうど合わせた
   格子でもやり直しで最終的に成功する**ことを見る。
9. **表面までの最短距離(`closest_triangle`)** — stage2 が面へ戻る経路。退化した三角形での
   反例(上記)/ 三角形上を細かく標本化した参照値との突き合わせ(自前 ≤ 参照、差は標本の
   刻み以内)/ 三角形の重心から `face_index` で元の面へ戻れること、の3つ。
10. **トリムされた曲面のソリッドの bbox が実寸を返す** — `_shape_bbox` の6面が、三角形分割の
    箱をすべて包み(切り落としが無い)、その外へ弦誤差(0.2mm)より大きくは膨らまないこと。
    題材は箱・円筒に加えて**トリムされたトーラス片**(`BRepPrimAPI_MakeTorus(100, 10, pi/6)`)。
    箱・円柱・平面だけでは `BRepBndLib` の `Add` と `AddOptimal` が一致してしまい、
    bbox の取り方を変えても検査が1件も動かない。トーラス片の膨らみは実測 0.011mm
    (`Add` に戻すと 9.063mm になって落ちる)。`tests/test_kernel_bbox.py` が
    `kernel.bounding_box` 側で同じ役をする。

`check_anchor.py` が見ているもの(合成ソリッドだけで、私物STEPには依存しない):

0. **節点番号と境界条件の口の契約** — `NodeGrid` の通し番号・自由度番号が
   `simp._build_edof` と一致する(全要素×8隅で突き合わせ)。節点座標に半セルのずれが
   無いこと、要素中心とはちょうど半セル離れていることも見る。**ここがずれると荷重は
   別の場所に入り、それでも最適化はもっともらしく収束する**ので、1〜7が全部緑でも
   意味が無い。だから最初に置いてある。あわせて、**`void_mask` だけを渡した `optimize` が
   既定の拘束を明示した場合と `rho` ビット単位で一致する**こと(`Model` を直に組んで
   `fixed` の包含関係を見るだけでは、`optimize` が拘束を置き換える回帰を素通りする ——
   置き換えていたのは `optimize` なので、そこを通らない検査には意味が無い)と、
   **拘束不足(1自由度だけ拘束)が拘束不足と名指しした例外で落ちる**ことを見る。
1. **総荷重の保存** — 単一面 / 斜め方向 / 2面同時、解像度16と32で、節点荷重の合計が
   指定値と一致する(相対1e-12。実測 2.3e-16)。荷重が載った節点がその面の節点集合と
   厳密に一致することも見る(取りこぼし・はみ出しなし)。あわせて**圧力の合力が
   `p × cad_area` と一致する**(稜線で捨てた面積に依らない。修正前のコードに当てると
   11.7% / 4.5% ずれて実際に落ちることを確認済み)。
2. **解像度非依存** — 傾けた箱の平面と半円柱の曲面で、担当面積の相対誤差と重心の誤差が
   **解像度4倍で半分以下**になる。3解像度ぶんを全部出す(中間が単調とは限らないため。
   下記の実測表)。
3. **面の取り違えが無い** — 板の上面と側面で節点集合が排他、それぞれの重心が正しい面の側、
   **全面について「自分の面の三角形から殻の半径以内」**(1面でも取り違えると落ちる)。
4. **法線が合っている** — 傾けた平面で CAD 法線と厳密に一致(dot = 1.0)し、
   **節点の位置だけから主成分分析で出した面の向き**とも一致する(法線を三角形から
   引き継いだのではない証拠)。曲面は面積重み平均どうしで一致し、半円柱の平均法線の
   大きさが解析値 `2/pi` の2%以内。
5. **偽の集中が出ていない** — (a) どの節点も要素1個ぶん `h^2` の1.5倍を超えて担当しない
   (実測 1.00〜1.01)。(b) 荷重密度をガウス核(σ=2h)で平滑化して、同じ核で平滑化した
   真の面積分布と比べたとき、面の内側でのずれが1.5%以下(実測 0.5〜0.6%)。
   **(b) は面積重みを外した対照(節点で等分)を同じ検査に掛け、実際に落ちることまで
   確認する**(実測 3.4% / 3.5%。検査が効いている証拠)。
6. **稜線の扱いが宣言どおり** — 全面の節点集合が互いに排他、競合した節点(実測288個)が
   すべて「最も多く配った面」へ行っている、どの面も自分の三角形の総面積を超えて担当しない。
   帰結として**要素サイズより小さい面は節点が空になる**ことと、そのとき荷重・拘束の口が
   黙って0を返さず落ちることを見る。
7. **端から端まで** — 合成ブラケットで「ソリッド → ボクセル化 → 面アンカーで固定/荷重 →
   SIMP → marching cubes → STL」が繋がり、`check_simp.py` と同じ基準(目標体積±1% /
   コンプライアンス減少 / 終盤10反復の変動1%未満)を満たす。設計空間の外に材料が
   残っていないこと、荷重・拘束の近傍が ρ=1 に固定されていること、STLの三角形数と
   ファイルサイズが面と一致することも見る。

## 設計上の決定(実測に基づく)

- **線形方程式は CG(Jacobi前処理・前回解でウォームスタート)で解く。** 直接解法は
  40×16×16 で 1回 7.1秒(`spsolve`) / 6.3秒(`splu` + MMD_AT_PLUS_A)かかり、60反復で7分を超える。
  CG は同じ格子で 1.9〜2.1秒/反復。**当時のタスク既定の格子 40×16×16 を落とさずに済んだのは
  このため**(2026-09-04にプリセット自体を 20×8×8 へ縮めたが、この選択は変えていない —— CG が
  効かなくなるのは格子を上げたときで、下げたときではない)。
- **CG の許容は `rtol = 1e-9`。** 1e-6 だと z対称性の相対誤差が 60反復で 1.7e-07 まで育ち、
  完了条件(c)の 1e-6 に対して余裕が6倍しかない。1e-9 にすると 1.0e-09 まで下がり、
  **所要は13%しか増えない**。合否が丸め誤差の積み上がりで揺れる状態にしない。
- **体積の二分探索は「フィルタ後の密度」の総和で判定する。** 設計変数 `x` の総和で判定すると
  境界付近で目標からずれる。これで最終体積分率が 0.300000 に乗る。
- **カメラは外接球の半径と視野角から距離を出す。** 「最大辺 × 係数」の目分量だと
  40×16×16(当時のプリセット)が画面の1/6にしか映らなかった。
- **marching cubesの頂点座標は角(0,0,0)基準のまま書き出す**(STLは角基準のほうが
  スライサ・3Dプリンタのビルドプレート原点と相性がよい)。**画面側だけ**、ボクセル描画の
  中心原点規約(`ex+0.5-nelx/2`)に合わせて平行移動する(当時は実験場の `server.py` の
  `_build_mesh_payload`。いまは `duocad/optimize_run.py` の `_mesh_to_world`)。`nelx`/`nely`/`nelz` が偶数なのでこの平行移動は整数量になる
  (2026-08-30、平行移動を忘れて完了時に形状がバウンディングボックスからずれて
  描かれる不具合を実機確認で発見・修正した)。
- **`rho[ex]` はセル `ex` の中心の値であり、パディング除去のオフセットはそれを踏まえる
  必要がある。** `marching_cubes` は配列の添字 `i` をそのまま `i*spacing` の位置とみなすが、
  パッド済み配列の添字 `i` は元のセル `ex = i - pad_width` の**中心**を表すので、
  正しいオフセットは `(pad_width - 0.5) * spacing` である。**`pad_width * spacing`
  (0.5要素分だけ大きい値)を引くと、面が設計空間に対して全軸一律に半要素ずれる**
  (2026-08-30、QAが `mesh.py:94-96` で指摘・実測で確認して修正。40mmの模型では
  目視で気づけない大きさなので実機スクリーンショットの比較では検出できず、
  既存7項目の受入検査もどれも並進不変で検出できなかった。**検査8(座標系の整合)を
  新設**し、既知の位置に置いた合成密度場のバウンディングボックスで機械的に見張る)。
  この修正に伴い、**`check_mesh.py` の検査5(内分比)は`mesh.build_surface`内部で
  オフセット適用前(marching cubes直後の生座標、整数格子点のまま)に計算した値を使う
  よう改めた** —— オフセット後の座標(半要素ずれた基準)で計算すると、整数格子点の
  前提が崩れて軸判定が丸ごと反転し、常に0.5という誤った結果になる。
  engine `marching-cubes-cell-center-half-offset`。
- **巻き順は `run_marching_cubes` で `faces[:, (0,2,1)]` へ入れ替える(生成側で直す)。**
  `skimage.measure.marching_cubes` が返す巻き順は `(v1-v0)x(v2-v0)` を外向き法線とする
  一般的な規約(STL/OCCT/three.js)に対して逆向き(実測: 単純な立方体で発散定理の
  符号付き体積が負になる)。直さずにSTLへ書き出すと `build123d.Mesher().read()` で
  読み戻した体積の**符号だけ**反転する(2026-08-30実測: 期待+3022.0が-3022.0)。
  **当初はこれをSTL書き出しの直前で直していたが、2026-09-02に取りやめた** ——
  巻き順に依存する消費者はSTLだけではなく、当時は実験場の `server.py` の
  `_build_mesh_payload` が `mr.faces` をそのままブラウザへ送り、実験場の画面
  (`probe_topopt/web/index.html`)が `computeVertexNormals()` で巻き順から法線を導いていた(いまは `duocad/optimize_run.py` →
  `add_mesh_body` → `web/src/viewport.ts` が同じ経路である)。書き出し1箇所で直す形だと**ブラウザ表示だけが内向き法線の
  まま残り**(実測: 面の100%が内向き)、`MeshLambertMaterial` の既定 `side: FrontSide` が
  手前の面を間引くので奥の内壁が見えていた。生成側で直せば消費者が増えても漏れない。
  engine `winding-fix-at-export-only-leaks-to-other-consumers`。
- **最小肉厚は「法線がほぼ逆向きな近傍点との距離」で近似する**(3Dプリントの薄肉検出で
  よく使われる考え方。真の肉厚計算はレイキャストが要り複雑なため)。この近似は
  marching cubes直後の階段状メッシュでは局所ノイズを厚みとして誤検出し**実際より薄く**
  出る。そのため「平滑化後 ≥ 平滑化前」に振れるのが正常(実測比4.27)——
  閾値50%はこの前提で「著しい縮退(パラメータ誤り等)だけを検出する」ための安全側の値で、
  `|μ|>λ` を破るような致命的な劣化(実測: 反復1000回で比0.945まで低下)は検出できる。
- **要素サイズ=1mmと仮定する**(`mesh.DEFAULT_SPACING=(1,1,1)`)。SIMP側に他の物理スケールの
  定義が無く、既存のボクセル描画(`BoxGeometry(1,1,1)`)も1要素=1単位の規約なので、それに
  合わせた。実寸を変えたいときはこの1点(`spacing`)を差し替えればよい。

- **格子を決めるための bbox は `BRepBndLib.AddOptimal_s(shape, box, False, False)` で取る**
  (第3引数が `useTriangulation`、第4引数が `useShapeTolerance`)。`Add_s` にすると
  面のトリムを見ない(上記「OCCT の bbox はトリムを見ない」)。`useTriangulation` を
  `True` にすると、形状に**既に付いている三角形分割**があればそれを使う。OCCT は
  三角形分割を形状に貼り付けたままにするので、同じ形状オブジェクトに2回ボクセル化をかけると
  「1回目=素の幾何の bbox / 2回目以降=前回の三角形分割の bbox」と値が変わり、
  そこから決まる要素サイズ・分割の細かさ・三角形群まで変わる。2026-08-31に実測で発見:
  実物STEPで三角形数が呼ぶたびに 62,264 → 62,168 → 62,138 と動いた(`Cylinder(10,30)` でも
  1回目312枚・2回目以降308枚)。**BRepMesh 自体は deviation を固定すれば決定的**なので、
  非決定性の源は分割器ではなく bbox の取り方だった。**`AddOptimal` はトリム曲線を実際に
  評価するので遅い**(実測: `models/` の実物ボディ1つで 18〜60ms)。`voxelize` と
  `design_space.derive` は1回の導出につき数回しか呼ばないのでそのまま呼んでいる ——
  繰り返し呼ぶ `kernel.bounding_box` 側だけが `BoundingBoxCache` を通る。
- **占有判定は偶奇ではなく巻き数で数え、そのうえでレイをずらし、縮退したらずらし幅を
  変えてやり直す。** 3つとも要る。巻き数だけだと円錐の頂点(三角形が数十枚集まる点)を
  レイが貫いたときに守れず、ずらしだけだと共有辺の二重計上で列がまるごと反転し、
  ずらし幅が**固定**だとその値に合わせた格子を作られたときに守れない(2026-08-31のQAが
  実際に再現した)。やり直しは決定的な列(素数倍の6通り)で、乱数は使わない。
- **最近傍点は7候補の最小値で求める(領域分けの優先順位では求めない)。** 教科書の
  領域分けは分岐が排他であることを前提にしていて、退化した三角形では複数の領域が同時に
  真になり、後から上書きしたほうが勝って誤った距離を返す。**退化三角形はOCCTの三角形分割に
  実際に現れる**(円錐の頂点まわりで実測1枚)ので、入力で弾くのではなくここで正しく扱う。
  stage2 は面へ戻る経路をこの関数に頼るので、ここの誤りはそのまま伝播する。
- **符号付き体積は基準点(bboxの中心)を引いてから三重積を取る。** 絶対座標のまま足すと
  原点から遠いソリッドで桁落ちする(実測: 原点から 1e8 mm の 40×20×10 の箱で 8,000 が
  7,957.33 になった)。薄い形なら符号が反転して、健全な形状を「法線が内向き」と誤って
  拒否する。体積は平行移動に対して不変なので、これは数値の都合だけの操作。
  **殻ごとに測るときの基準点は、その殻自身の点から取る**(soup 全体の bbox 中心を使うと、
  離れた位置にある小さな殻で桁落ちが戻ってくる。実測: 原点の中空箱と 1e7 mm 先に置いた
  傾けた4mm角の箱の compound で、小箱の体積が 64 ではなく 3,542.34 になった。
  軸整列した箱だと三重積が偶然きれいに相殺するので、この検査には傾けた小箱を使う)。
- **向きの検査は殻(連結成分)ごとに行う。** 総符号付き体積だけを見ると、内部空洞の殻だけを
  裏返した入力が正のまま通り、空洞が材料として埋まる。連結成分ごとの符号付き体積と、
  「他の殻いくつの内側にあるか」(+z のレイの巻き数で数える)の偶奇を突き合わせる。
- **占有はセル中心の1点サンプルで、部分体積(占有率)は持たない。** SIMPは全要素が
  同形状であることに依存していて、境界の要素だけ体積を変える口が無い。境界の表現を
  細かくしたいときは解像度を上げる(所要は要素数に比例するので stage1 側は律速にならない
  —— 効くのは SIMP 側で、engine `simp-cost-scales-with-fourth-power-of-resolution`)。

## 設計と画面（`duocad/optimize_run.py`）

条件を置く4 verb（`set_preserve_bodies` / `set_exclude_bodies` / `set_fixtures` / `set_loads`）の
**続き**が `duocad/optimize_run.py` である。verbは1本も足していない —— 結果を文書へ入れる口は
既存の `add_mesh_body` だけで、**元のボディは1つも消さず・形も差し替えない**
（最適化は編集ではなく「条件から新しい形を1つ作る」操作）。

```
Session.optimize_conditions()     4条件がそろって走らせられるか（足りないものを名指しする）
Session.optimize_resolution(rmin_mm=...)   要素サイズの上限・下限・既定と予想時間
Session.run_optimization(...)     端から端まで走らせ、結果をメッシュボディとして足す（重い）
Session.cancel_optimization()     走っている最適化に降りるよう伝える（旗を立てるだけ）
```

**要素サイズの上限＝「これより粗いと間違う」**を2つの要求の min で決める:

- **最小部材幅から** — `rmin_mm / simp.MIN_RMIN`
- **条件面から** — `sqrt(CAD面積)`。**利用者に聞かない**。`anchor.empty_face_diagnosis` の
  `suggested_max_spacing_mm` と同じ式で、**近似であって保証ではない**（正方形とみなした
  代表寸法なので、曲面や極端な縦横比の面では過大にも過小にもなる）

**要素サイズの下限は暫定の固定値**（総要素数 `MAX_ELEMENTS`）で、**メモリの安全域ではない**
——ピークを決めるのは箱の要素数ではなく**組み立てに載る要素数（塊。空要素は外れる）**であり、
この定数は箱の数を数えている（実測は `optimize_run.MAX_ELEMENTS` のコメント）。**既定は上限側**
（＝条件と最小部材幅を満たす、最も粗くて安い設定）で、**時間は制約にしない** ——
予想時間は帰結として出るだけ。

**保持・除外ソリッドからは上限を厳密に計算できない**（細い通路の表現に必要な要素サイズは
中心軸変換に近い話で、バウンディングボックスや体積では取りこぼす）。だから**ボクセル化した
あとに数えて通知する** —— 保持/除外を**1つずつ**格子へ載せ、0要素なら最適化を回さずに
`state == "unrepresented_regions"` で戻る（合計で見ると、大きい保持ソリッド1つで小さいほうの
消失が隠れる）。空の条件面と同じ通知の形を使う。

**許容応力は固定**（根拠は本書「許容応力の導出」）。duocad 側でも材料を選ばせない。値は
`optimize_run.allowable_stress()` から引ける。利用者が入れるのは**目標安全率**で、
そこから材料量を二分探索する（`safety_loop.solve_for_safety_factor`）。

**この版の制限**:

- **荷重は「同時にかかる1つの荷重系」だけ**。拘束面・荷重面は何枚でもよく、荷重の大きさ[N]と
  向きは**面ごとに違ってよい**（面Aへ鉛直下向き50N、面Bへ法線方向20N、が同時に成立する）。
  扱えないのは**別シナリオ＝複数荷重ケース**（「あるときは面A、別のときは面B」）で、
  これは合成すると**どちらの単独荷重にも耐えない形**が出るため、表現できないままにしてある。
- **保持ソリッドは1つ以上必須**（塊は保持ソリッドと条件面から起こす）。
- **メッシュボディは保持・除外に指定できない**（README §4「ボディの種別」の名指しの線）。

**面の対応がこの配線でいちばん壊れやすい。** duocad は面を `(body_id, 1始まりの添字)` で持ち、
`duocad.topopt` は `TriangleSoup` の面添字で持つ。どちらも `kernel._face_map` の数え方なので
**同じ形状を渡すかぎり一致する**が、条件面が複数のボディに散ると `kernel.make_compound` で
1つにまとめるため `face_count` の累積ぶんずれる。**ずれても例外は出ない**（荷重が別の面に入り、
最適化はもっともらしく収束する）ので、網を2枚張ってある:

1. `_verify_face_mapping` — まとめた形の側で測り直した指紋（面積・法線・**重心**）が、ボディ
   単体で測った指紋と一致するか。**重心を外すと同形の別ボディを取り違えても通る。**
2. `_check_anchor_centroids` — 実際にできた面アンカーの節点の重心が、条件面の重心の近くにあるか。

同じ性格の門がもう1つある: **結果メッシュの頂点は要素添字空間（`spacing=(1,1,1)`・セル中心規約）
で返る**ので、`grid.origin + verts * grid.spacing` でワールド[mm]へ直す（`_mesh_to_world`）。
忘れると原点付近に縮んだメッシュが黙って入るだけなので、`_check_mesh_placement` が毎回見る。

### 画面から走らせる（`web/src/OptimizePanel.svelte`）

WebSocketには**4つの口**を開けてある（`catalog` の `category="protocol"` ＝ verbではない。
応答は状態配信ではなく専用のイベント `optimize_conditions` / `optimize_resolution` /
`optimize_status` / `optimize_progress` / `optimize_result` / `optimize_error`）。
**MCPには開けていない** —— 数分かかる同期の呼び出しをツールとして出すと、進捗も中断も
運べないまま呼び出し側がタイムアウトする。AIから走らせたくなったら、まず**進捗と中断を
MCPで運ぶ形**を決めること。**`add_mesh_body` は `ws="none"` のまま**でよい（画面が三角形を
作る操作は無く、結果は `run_optimization` がサーバの中で入れる）。

**重い処理は `asyncio.to_thread` で回す。** `_dispatch` の中で待つと、`handle()` が1接続を
直列に処理する以上、**同じ接続から届く `cancel_optimization` が読めなくなる**（＝止める手段が
無くなる）。`_ai_start` と同じ形である。

**解像度は「既定＝粗い側の端。細かくする方向にだけ動く目盛り」**。
両端の性質が違うからで、**粗い側の端は「正しさ」の境界**（割ると条件面から節点が消え、最小
部材幅が表現できない。しかも silent）、**細かい側の端は「都合」の境界**（遅い・落ちる、それだけ）
である。目盛りの実体は `resolution_limits()["steps"]`（等比で6段。添字0が上限側＝既定）で、
**段はサーバが作る** —— 要素数の数え方（余白比率とパッド）を画面が持つと必ずずれる。
各段に予想時間が付くが、**時間は入力にしない** —— 時間から解像度を逆算すると、利用者が
知らないうちに最小部材幅と条件面の要求を割り、しかも割ったことは画面から見えない。
画面には**「2〜3倍の幅で読む値」であることを添えて**出す（係数が 1.05e-4〜2.82e-4 に散り、
熱状態だけで1.7倍振れる）。

**通知はトーストとパネルの二重に出す。** トースト（`Toast.svelte`）は8秒で消える設計なので、
「荷重面に格子節点が付かなかった」「保持ソリッドがこの解像度では表現できていない」のような
**結果が信用できないという意味の文**を流すと見落とす。パネルの `#optimize-notice` は
**次に走らせるまで残る**（トーストは気づかせる役、パネルは読み返す役）。**中断はエラー扱いに
しない** —— 人がそう言った結果なので赤い札を出さず、「文書は変わっていない」だけを残す。

**実行中は画面の操作を止める**: verbの行（`CommandHost` の `busy`）・
最小部材幅・解像度・「抜ける」を無効にする。止めないと、走っている最中に条件を編集できて
**結果と条件が食い違う**（`run_optimization` は入口で読んだ条件のまま最後まで走る）。
**MCP／アプリ内AIからの編集は止めていない** —— 止めるには全verbの入口に門が要り、範囲を
広げすぎる。1人が1つのブラウザで開く前提（README §4「前提にしないこと」）の内側の割り切りである。

**パネルはビューポート左のブラウザと同じ列（左端・同じ幅）の下端に出す。** 位置の決め手は
見た目ではなく**画面に新しい帯を取らないこと**である —— `viewport.project()` は
`clickable(x, y)` で「浮いているパネルに覆われていないか」を見ており、ブラウザの右へ
幅320pxの帯を足した版では**左のボディの面が1枚も指せなくなった**
（`smoke-optimize-mode.mjs` が検出）。条件を置くのはこのモードの仕事そのものなので、
モデルを覆う位置には置けない。`SettingsDialog` がブラウザの右へ出るのは、開いている時間が
短い一時的なダイアログだからで、出しっぱなしのパネルは同じ扱いにできない。

**結果は積み上がる**（置き換えない）。名前は `optimized` / `optimized-2` / … で、
何度走らせても前の結果は残る。要らなくなったものは選んで削除する（メッシュボディは
`delete` だけが通る）。

**メッシュボディのピックはボディ選択へ畳む**（`App.svelte` の `pickedRef`）。viewport は
メッシュも1枚の面として描くので、素直に翻訳すると `kind:"face"` の参照が飛び、コアの
`select_face` が断る —— **ドラッグの一括選択は1回でまとめて送るので、画面を囲んだドラッグに
メッシュが1つ入っているだけで選択が丸ごと落ちる**。畳んでおけば「クリックしても何も
起きない」も起きず、しかも**編集verbは自然に押せないまま**になる（`move_body` / `fillet` /
`chamfer` / 領域押し出しはどれも選択の種別にボディを持たないので、ボディ参照では確定に
到達しない）。**ツールバーは選択で出し分けない** —— コマンドの一覧はモードの持ち物であり、
選択のたびに作り直すと集めかけの引数が落ちる。「押せるのに断られる」を消しているのは
**この畳み込み1本**である。スケッチを貼る先だけは畳まずに断る（ボディ参照にしても
`sketch_create` は面を要求するので、押した結果が変わらないまま理由だけが消える）。

### 開発用のデバッグ表示（URLパラメータ）

**答えがおかしいときに「塊が悪いのか最適化が悪いのか」を切り分ける道具**（`web/src/debugFlags.ts`）。

| 付けるもの | 出るもの |
|---|---|
| `?debug=space` | **塊（設計空間）**のボクセルを薄く重ねる |
| `?debug=anchors` | **拘束/荷重に割り当たった格子節点**を色分けした球で（固定=緑シアン / 荷重=橙赤） |
| `?voxel=1` | **平滑化する前のボクセル**。結果のメッシュボディは表示だけ隠す |

`?debug=space,anchors` のように**まとめて指定できる**。走らせたときにだけ材料が生まれるので、
**実行を押すまでは何も出ない**（塊と節点は実行の数秒後、密度場は走り切ったあと）。

- **ビルドで落とさない。** 落とすと利用者の環境で起きた問題を調べられなくなる。
  代わりに **フラグが無いときの画面は1ピクセルも変わらない**（`smoke-optimize-debug.mjs` の[1]と、
  既存の実機smokeが番人）。
- **デモ題材に固定されていない。** 材料は**いま走らせた最適化そのもの**から来る。
- **塊は既定では見せない。** フラグの下でだけ出る。
- **画面にフラグの状態は出さない**（出すとフラグ無しの画面と差ができる）。確かめるのは
  `location.search` と `window.__duocad.optimizeDebugCounts()`。
- 実物の部品は要素数が桁で大きくなりうるので、**上限（15万立方体）を超えたら軸方向に間引く**。
  間引いたことは `optimizeDebugCounts().spaceStride` に出る（黙って切り捨てない）。

配線は `duocad/optimize_run.py` の `_DebugSink` →（`run_optimization` の `debug` で頼んだときだけ）
`optimize_debug` イベント → `web/src/viewport.ts` の `setOptimizeDebug`。
**頼まなければサーバは配列を1本も作らない**（既定の実行の費用は1ビットも増えない）。

## duocad 本体への配線(2026-09-05)

**4条件を置いた duocad の文書から、実際にメッシュボディが出るまで**を繋いだ
(`duocad/optimize_run.py`。設計と口は上「設計と画面」が正)。
ここに書くのは実測だけである。

### 受入検査 `check_optimize_wiring.py` が見ているもの

**この1本だけが本物を回す**(`tests/test_optimize_backend.py` は SIMP を1回も回さない ——
pytest を重くしないため)。題材は離れた2つのパッド(拘束側 10x40x40 / 荷重側 10x40x10 を
50mm 離して置く)で、**条件面が別々のボディに載る**ので面添字をまとめる経路を必ず通る。

1. **端から端まで** — `state == "done"`、ボディが1つだけ増え、それがメッシュボディで、
   **元のボディは1つも消えず・形も差し替わらない**(`is` で見る)。戻り値が素の値だけで
   できている(`json.dumps` が通る)ことも見る —— 画面はこれをそのままWebSocketへ載せる。
2. **結果メッシュの位置** — ワールド[mm]で格子の箱の中にあり、拘束側と荷重側の両方の
   パッドに届いている。**要素添字空間のまま入れると原点付近に縮む**ので、広がりが
   要素サイズの4倍を超えることも見る。
3. **荷重・拘束が選んだ面に入っている** — 面アンカーの節点の重心と条件面の重心の距離。
   **面添字の取り違えは例外を出さない**(荷重が別の場所に入り、最適化はもっともらしく
   収束する)ので、実際に走らせた結果で突き合わせる。
4. **進捗** — 設計反復ごと(`phase="optimize"`)と候補材料量ごと(`phase="search"`)の2段。
5. **中断** — 進捗の途中で旗を立てると `OptimizeCancelled` になり、文書は1ビットも変わらない。
6. **応力を測る経路** — `keep_model` が通っているので安全率が出る。許容応力 40MPa の導出も見る。
7. **事後検出** — この解像度で1要素も掴めない保持ソリッドがあると `simp` を呼ぶ前に戻る。
8. **条件面からの要求要素サイズ** — `optimize_run._face_max_spacing_mm` と
   `anchor.empty_face_diagnosis` の `suggested_max_spacing_mm` が同じ値になる。

### 実測(2026-09-05・検証用に縮めた設定)

| 項目 | 値 |
|---|---|
| 端から端まで(要素4.04mm・格子 28x21x21・塊 6,179要素・6反復 × 3評価) | **10.9秒** |
| 出た三角形 | 2,848枚 |
| 面アンカーの重心と条件面の重心の距離 | 拘束 0.58mm / 荷重 0.18mm(許容 12.1mm = 3要素) |
| 中断(進捗3件目で旗を立てる) | 2.7秒で降りる |
| 事後検出で早期returnするまで | 0.1秒 |

**この秒数は本番の設定ではない。** 既定(`max_iter=40` / `max_evaluations=15`)のままだと
同じ格子でも数分になる(`optimize_run.estimate_seconds` の見当は 561秒)。

### 予想時間の係数の作り方

`estimate_seconds` は `粗い段の固定費 + 設計反復 × 格子要素数 × 係数` を候補材料量の数だけ
掛ける。係数 1.8e-4 [秒/(要素・反復)] は2026-09-04の実測の中央付近で、
**実際には 1.05e-4〜2.82e-4 に散る**(秒は格子要素数の 1.05乗〜2.03乗で伸びるので線形では
収まらない)。熱状態の 1.7倍も乗るので、**返るのは 2〜3倍の幅で読む値**である。

## 制限(承知のうえで残しているもの)

- **画面から面を選べない。** `?debug=anchors` は合成ブラケットの決め打ちで、
  「クリックした面を固定面にする」UIは入っていない。境界条件UIと非同期ジョブ化は
  「難しいが解決可能」として本タスクの範囲外(2026-08-29のスコープ確定)。
  ただし**面添字を受け取る側の口は全部揃っている**(`fixed_dofs` / `load_vector` /
  `pressure_vector` / `element_mask`)ので、残るのは verb の配線だけ。
- **ブラウザで回せる条件は `demo_conditions()` の決め打ち1組だけ。** 2026-09-04に
  「最適化を実行」ボタンは `design_space.run_topopt()`(4条件から塊を導出して面アンカーで
  境界条件を入れる経路)へ繋がったので、**画面と計算は同じ `DesignSpace` を見ている**。
  残っているのは「画面で条件を作る/差し替える」ほうで、条件そのものはサーバ側の
  決め打ちのままである。
- **要素サイズより小さい面には節点が付かない**(稜線の規則の帰結)。実物STEPを
  要素サイズ 1.54mm で割ると 231面中22面が空になる。`table.empty_faces()` で見える。
  **2026-09-05に実行経路の入口(`design_space.run_topopt` / `anchor.run_pipeline`)で
  メッセージが出るようにした**(上「拘束面・荷重面のアンカーが空のときにメッセージを出す」)
  —— 面添字・要素サイズ・CAD面積・逃げ道2つ(別の面を選ぶ/要素サイズをいくつ以下にするか)。
  **多数決の規則を曲げて小さい面にも節点を付ける、という本当の解決はまだしていない**
  (同節「本当の解決は保留する」に理由)。
- **担当面積は真の面積より数%小さい**(稜線で隣の面に取られたぶんを再正規化しない設計)。
  `load_vector` の総和は正規化で、`pressure_vector` の合力は `cad_area` から出すことで、
  どちらもこの差から独立にしてある。**残るのは「担当面積を『面の面積』としてそのまま
  使ったとき数%低く出る」ことだけ**で、面の面積が要るなら `FaceAnchor.cad_area` を使うこと。
- **案1(外接直方体+余白)は「塊が答えを含む」ことを保証できない。** 余白は自由パラメータで、
  最適化が置いた材料は既定の 0.25 でも 8.9% が塊の壁に接している(0.50 でも 3.3%)。姿勢を
  変えると塊が 1.2〜1.4 倍に膨らみ、相対体積制約のままだと材料の量まで変わる。
  **2026-09-04に既定は案5へ倒した**ので、案1は比較のベースラインと退避経路として残っている。
  **案5も「塊が答えを含む」ことを保証はしない**(保証しているのは「粗い段の答えの周り
  `dilate_mm` mm と4条件の要素が入っていること」だけ)。
- **体積目標の絶対量(mm^3)は口だけで、画面はまだ分率で回している。** 当時の実験場の
  `DEMO_VOLFRAC=0.3` は変えていない —— 利用者の入力(安全率)から材料の量を作る外側のループは
  別タスク。**画面を絶対量へ倒すときはスクショの撮り直しが付いてくる**という当時の制約は、
  実験場を消した2026-09-05に消えた(いまの画面は `duocad/optimize_run.py` を通り、撮影は
  `web/scripts/shoot-topopt.mjs` が引数で受ける)。
- **達成可能区間の端ちょうどは解けない。** 体積の口は「容量と等しい絶対量」を通すが、
  OC の二分探索が退化する。**その退化は `simp.VolumeTargetError`
  (`side="above_capacity"`)で落ちる**。文面に目標・
  この反復で到達できる最大・塊の容量・その割合が出る。**区間の内側でも落ちることがある**
  —— 密度フィルタが塊の縁で目減りさせるので、実測では容量の 98% は落ち 95% は通る
  (塊の形で変わるので、この境目を定数として持ち出さないこと)。
- **つながり検査は入った**(2026-09-04・`20260903-2235`。上の「塊の中で拘束と荷重がひと続きかを
  検査する」)。ただし見るのは**拘束↔荷重の道が有るか無いか**だけで、**道の細さは見ない** ——
  幅1要素の糸でつながっている塊も通る。
- **反復ごとの配信は間引いていない**(60反復 × 約35KB で足りている)。
- 60反復では収束判定(change < 1%)に届かず、反復上限で止まる。コンプライアンスは
  終盤10反復で 0.161%(縮める前は 0.113%)しか動いていないので、実用上は収束しているとみなしてよい。
- **解像度は上げていない**(2026-09-04以降は 20×8×8。むしろ下げた。上の「受入検査の通し時間」)。ボクセル描画の
  階段状の見た目は描画方法が原因で解像度が原因ではないことは今回のmarching cubes導入で
  実証できたので、解像度を上げる要否は別途判断できる状態になっている
  (engine `simp-cost-scales-with-fourth-power-of-resolution`: 線形解像度を2倍にすると
  SIMP側の所要が16倍になる)。

## 連続値保持の既定値をどう決めたか(参照 容量の8%・10反復 / k 2.0 / 回廊)

**すべて実測で決めてある**(案5・案1の既定と同じ扱い)。題材は `models/hanger_bar_attachment.json`
(要素 5.333mm・案1の箱 98,606要素・容量 15.25e6mm^3)と `demo_conditions`(bracket)。
**「正解」は案1(絞らない箱)で最後まで回した ρ >= 0.5** で、絞り方の良し悪しはそれをどれだけ
覆うか(被覆)で測る。

### 参照 run の材料量(`REFERENCE_MATERIAL_RATIO = 0.08`)

参照を作るときの材料量 M0 が、対象の材料量 M より**多い**と壊れる。hanger:

| M0/M | M0 → M | 被覆(k=1.5) | 被覆(k=2.0) | 被覆(k=2.5) |
|---|---|---|---|---|
| 1.6 | 1.6e6 → 1.0e6 | 100% | 100% | 100% |
| 2.9 | 2.9e6 → 1.0e6 | 88.83% | 95.54% | 100% |
| 5.1 | 5.1e6 → 1.0e6 | 48.58%(未連結) | 75.32%(未連結) | 83.55%(未連結) |
| 8.4 | 8.4e6 → 1.0e6 | 4.28%(未連結) | 12.58%(未連結) | 31.92%(未連結) |

**M0 <= M の方向は k>=1.5 で常に 100%。壊れるのは M0 > M の方向だけ。** 原因は ρ の飽和で、
材料が多い解は箱の半分以上が ρ>0.7(hanger の上端で中央値 0.7377)になり、順位が同点だらけに
なって情報を持たない。**だから薄い側へ倒す。** 安全帯の実測は volfrac 0.066〜0.105。

**k を上げても M0 の誤りは直らない**(M0=8.4e6 → M=1.0e6 は k=3.0 でも 56%)。ただし未連結
として検出はできる。

### 順位の付け方(距離が主キー・ρ が副キー)

3つ比べた。**ひずみエネルギー `u_e^T k0 u_e` は原理的に使えない** —— 収束した解では solid 内の
エネルギー密度がほぼ一様で、単位剛性の値は void で最大になる(emin 媒質が巨大に変形する)ので、
上位から取ると void を先に取る。**自分自身の構造すら 8.72% しか取れない。** ρ^p を掛けた真の
感度にしても、今度は solid 内が一様になって順位が作れない。

| 順位の場 | M0=1.0e6 → M=1.0e6 | M0=1.0e6 → M=8.387e6 (k=1.25/1.5) |
|---|---|---|
| ρ のみ | 100% | 87.03 / 94.14% |
| ひずみエネルギー | **8.72%** | 93.66 / 99.22% |
| **ρ + 距離(採用)** | 100% | **97.66 / 99.88%** |

収束した ρ はほぼ二値なので、ρ だけで並べると `ρ>=0.5` を取り切った先が同点だらけになる。
距離を主キーにすると「構造をまず取り、そこから同心に膨らませる」順になる —— **これは案5の
膨張と同じ操作で、膨らませる量が定数(`COARSE_DILATE_MM`)から材料量と k に変わったもの。**

**同じく1回の線形解析で済ませる案(中身の詰まった箱の応力で順位を付ける)も測って落とした。**
答えの近傍で被覆 47.6〜60.4% かつ未連結。ESO(下位を削って解き直す)を3回挟むと 53.5〜65.5% へ
改善するので、原因は「材料の再配置を経ていない場だから」で確定する —— 目標体積まで削って
解き直せば当たるが、それはトポロジー最適化そのものであり、この方向は SIMP に収束する。

### 参照 run の反復数(`REFERENCE_MAX_ITER = 10`)

| 反復 | 秒 | 被覆 k=1.5(M=1.0/1.6/2.9/5.1/8.39e6) |
|---|---|---|
| 10 | 91.5 | 100 / 100 / 100 / 99.98 / 99.97% |
| 20 | 169.4 | 100 / 100 / 100 / 99.99 / 99.90% |
| 40 | 323.3 | 100 / 100 / 100 / 100 / 99.87% |

**差が無いので 3.5倍速い側を採った。**

### k(`K = 2.0`)

**被覆だけで決めると 1.5 になるが、それでは密度フィルタが体積目標に届かない。** bracket
(案1 3,336要素)で材料量と k を振ると:

| 材料 | k=1.5 | k=1.75 | k=2.0 | k=2.5 |
|---|---|---|---|---|
| 52,786 | **VolumeTargetError**(充填率67%・塊751要素) | OK 57% | OK 50% | OK 40% |
| 70,382 | OK 67%(塊1,001要素) | OK 57% | OK 50% | OK 40% |

**同じ充填率 67% でも塊が 751要素なら落ち、1,001要素なら通る** —— 効いているのは充填率
そのものより塊の絶対の大きさ(`rmin` が要素単位で効くため)。1.75 も通ったが落ちた 67% との
隔たりが1段しかないので、2.0(充填率 50%)を採った。

壁に接した材料の割合(案5の既定を決めたときと同じ代理指標)でも 2.0 が良い。hanger:

| M | 案1(下限) | 案5(粗20) | k=1.5 | k=2.0 |
|---|---|---|---|---|
| 1.0e6 | 5.37% | **14.00%**(箱比12.9%) | 5.38%(箱比9.8%) | **5.37%**(箱比13.1%) |
| 1.6e6 | 4.28% | 7.10% | 5.38% | 4.28% |
| 8.39e6 | 4.51% | 4.70% | 4.70% | 4.51% |

**k=2.0 は壁接触率が案1と完全に一致し、塊の大きさは案5とほぼ同じ**(箱比 13.1% 対 12.9%)で
ありながら、被覆は 93.27% → 100%。**案5が答えの近傍で答えを押しつぶしていた**のは、膨張が
絶対距離 12mm で部品の大きさに追随しないためである(hanger の実効 k は 1.36〜2.35 で、
案5の既定を決めた根拠②「材料は塊の容量の4割以下」= k>=2.5 を満たしていなかった)。

### 回廊(`Reference.corridor`)と痩せすぎの検出

**材料量ごとに「繋がるまで k を上げる」作りは採らなかった。** 繋がった時点で止めると塊が
材料量について単調でなくなり(bracket 20要素で 45%→2,927要素 / 50%→2,502要素)、外側の
二分探索が前提にしている単調性が崩れて安全率が 5522 → 3893 と逆行する。代わりに
**参照ごとに1回だけ「拘束と荷重を繋ぐのに要る順位の先頭からの最小本数」を二分探索で求め**、
どの材料量でもそこまでは必ず取る。連結性が構造的に保証され、塊は単調になる。

`REFERENCE_MATERIAL_RATIO` を容量の分率で持つと**部品によっては痩せすぎる**(8% は hanger の
答えが容量の約8%にあったから当たった値)。bracket 9,386要素では 8% で参照の solid が 578要素・
2成分にちぎれ、**回廊が案1の 71.2%** になった(12% なら1成分・回廊 7.9%)。
**痩せすぎは回廊の大きさで検出できる**ので、`REFERENCE_MAX_CORRIDOR`(0.40)を超えたら
`REFERENCE_RETRY_GROWTH`(1.6)倍して取り直す。**下げる側へは動かさない** —— 薄いほうが
安全側で、濃い側は上の表のとおり崖である。
