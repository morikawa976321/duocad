# 形状最適化の CG を GPU で解く

形状探索の FEM の線形求解(ヤコビ前処理つき CG)を、NVIDIA の GPU で解く経路。**既定は CPU** で、使う機械だけ人が有効にする。
判断の議論は morikawa976321/duocad#104。検証のスクリプトと生の結果(JSON)は git の履歴の `gpu_feasibility/`(コミット 7fffb24 まで)にある。

- 実寸 2.0mm の探索 1 本で 2.3〜2.6 倍(デスクトップ、RTX 5060 Ti。下の「実測」の表 2)。
- **解・反復数は CPU の `scipy.sparse.linalg.cg` とビット一致する。** 探索の試行と採用形状も変わらない。途中で CPU に戻っても結果は同じ。
- 直接解法に回る小さい系(`solver="auto"` の `direct`)は対象外。

## 有効にする

画面の「設定」(ヘッダーの「設定」ボタン)の3つ目、**「GPU で計算する」にチェックを入れる**。次に準備する計算から効き、
走っている最適化の途中で切り替えても答えは変わらない(秒だけが変わる)。

- 選んだ値はこの clone の設定ファイル `duocad_settings.json`(リポジトリ直下・未追跡。`duocad/local_settings.py`)に残り、
  サーバを立て直しても続く。安定版と開発版は別の clone なので別の値になる。
- **GPU の部品(CuPy と CUDA ランタイムの wheel、約 2GB)が入っていなければ**、設定の下に「GPU の部品を入れる(約 2GB・再起動)」
  ボタンが出る(安定版だけ)。押すとサーバが `tools/stable/update.ps1 -InstallGpu` を起こして落ち、`uv sync --frozen --extra gpu`
  だけを走らせて立ち直る(取り込みとビルドはしない。main に新しいコミットが無くても使える)。失敗したら extra なしで同期し直して
  CPU の構成に戻す。開発版では手で `uv sync --extra gpu` を走らせる。
- 以後の更新(`update.ps1`)は、その版が extra gpu を持ち、かつ設定が gpu か CuPy が入っているときに `--extra gpu` を付ける。
  **extra を付けない `uv sync` は入っている CuPy を消す**ので、GPU を切っても部品は入れたままにする(切り直すたびに入れ直さない)。
- 設定の下の1行が今の状態を言う: CPU で解いている/GPU の名前/部品が入っていない/使えない理由(CPU で解いている)。
- コードから使うなら `fem.FEM_DEVICE = "gpu"`、1 回だけなら `Model.prepare(..., device="gpu")`。

GPU の無い機械(ThinkPad P14s Gen 6 等)では選ばない。選んでも、最初の solve で CPU に戻ってそのプロセスでは以後試さない。

## CPU に戻る条件と記録

`gpu` のとき、次のどれかで **CPU が初期値から解き直す**(途中の解は渡さない。渡すとビット一致が崩れる)。

| 理由(`gpu_fallback` の頭) | 中身 | 以後 GPU を試すか |
|---|---|---|
| `cupy:` | CuPy を読めない・GPU が無い | 試さない |
| `openblas-threads:` | numpy 同梱 OpenBLAS のスレッド数を読めない | 試さない |
| `startup-check:` | 起動時に小さい系を CPU と GPU の CG で解き、ビットが合わない(scipy の行列積・更新の番人) | 試さない |
| `dot-mismatch:` | その長さの内積が `np.dot` とビット一致しない(numpy・OpenBLAS の番人。長さとスレッド数ごとに 1 回検査) | 他の長さは試す |
| `vram:` | VRAM が足りない | 試す |
| `residual:` | 収束したのに残差検算に通らない | 試す |
| `gpu-error:` | それ以外の CUDA の例外 | 試さない |

GPU の CG が収束しない(`not-converged:`)ときだけは CPU の CG を経ず、直接解法(`spsolve`)へ回す。ビット一致なので CPU の CG も
同じ反復で収束せず、CPU だけで解いたときの「CG が収束しない → 直接解法」と同じ道になる。以後も GPU を試す。

- 戻るたびに `RuntimeWarning` を出す。
- 実行記録の `linear-solve` に `device_requested` / `device`(実際に解いた方)/ `gpu_fallback`(理由。戻らなければ null)が残る。
  `fem.collect_solve_stats()` は `gpu_solves` / `gpu_fallbacks` を数える。**`gpu_fallbacks` が 0 でない実行は、CPU と GPU の秒が混ざっている**
  (`wall_seconds` で手法どうしを比べる集計では分ける)。実行記録の `environment` には `fem_device`(その時点の設定)が残る。
- 解き終わるたびに VRAM をドライバへ返す(Unity・ローカル LLM と 16GB を分け合うため)。

## ビット一致の範囲

保証するのは「**同じ機械・同じ numpy/scipy で、GPU の ON/OFF が結果を変えない**」ことだけ。

- 内積の足し順は OpenBLAS のスレッド数(既定は論理プロセッサ数)と実行時カーネルで決まる。**機械をまたぐ一致は CPU 同士でも元々無い。**
- numpy・scipy を上げると自己検査に落ちて CPU に戻ることがある(結果は変わらず、速度だけ戻る)。版は `uv.lock` で固定してあり、
  上げるときは GPU のある機械で `tests/test_fem_gpu.py` を回す。
- 確認した組み合わせ: numpy 2.4.6(OpenBLAS 0.3.31)・scipy 1.17.1・cupy-cuda13x 14.2.0、Python 3.11 と 3.14、Core Ultra 5 245KF。

## 方針(2026-10-10 本人決定)

Claude・Codex(gpt-6-astra)・Fable の3者で詰めた案を本人が了承した。

- **CPU と GPU の両経路を持ち、既定は CPU。** GPU への完全移行はしない —— ThinkPad P14s Gen 6 は Intel 内蔵 GPU だけで CuPy(CUDA)が
  動かず、メイン機はいずれそちらへ移る。ビット一致の基準とテストにも CPU の経路が要る。
- **使えるからといって自動で GPU にしない。** 利用者1人・機械2台で自動判定が守る相手がいない一方、VRAM を Unity・ローカル LLM と
  分け合うので、黙って数 GB を取る既定は他の作業を壊しうる。低性能の GPU で CPU より遅くなる問題も、既定が CPU なら起きない。
- **Intel 内蔵 GPU 向けの経路は作らない。** CG はメモリ帯域律速で、内蔵 GPU は CPU と同じメモリを使う。ビット一致も作り直しになる。
- 着手の判断線は「実寸の探索で GPU が探索全体 1.5 倍以上なら、GPU の配線を候補生成(`peel`)の高速化より先に」(測る前に決めた)。
  実測は 2.26 倍と 2.59 倍で、線を越えた。

## 実測(デスクトップ: Core Ultra 5 245KF・RTX 5060 Ti 16GB、2026-10-10)

**CG 単体**(07 の最終形マスクから製品の組立コードで作った保存済み 8 行列、自由度 3.3 万〜49 万。Python 3.14・numpy 2.4.6・scipy 1.17.1・
cupy-cuda13x 14.2.0。CPU は製品と同じ形〈ヤコビ前処理・rtol 1e-9・行列ベクトル積 7 スレッド〉、GPU はビット一致版〈準備込み〉):
**GPU は CPU の 4.4 倍(3.3 万自由度・5.6 秒→1.3 秒)〜8.5 倍(36 万自由度・44.2 秒→5.2 秒)、49 万自由度で 61.1 秒→7.5 秒。8 行列すべてビット一致。**
CPU の CG は 1 反復・非ゼロ 1 個あたり 0.46〜0.53 ns。VRAM は 49 万自由度で約 1.8GB(CuPy のメモリプール)。
ビット一致を捨てた最速の方式(cuSPARSE)でも CPU の 9〜12 倍(2026-10-04、換算)で、ビット一致版との差は小さい。
組立と切り出しは 49 万自由度でも 2 秒未満で、GPU に載せる意味は無い。5 万自由度以下は直接解法(1 秒弱)に回るので対象外。

**実寸 2.0mm の探索 1 本**(hanger・設計空間 64 万セル・step 0.2、プロファイラなし、製品の既定 7 スレッド):

| 条件 | 評価 | CPU 版 | GPU 版 | 倍率 | CPU 版の内訳(線形求解 / 候補生成 / それ以外) | GPU 版の内訳 |
|---|---|---|---|---|---|---|
| 2000N・最小幅 10mm | 14 | 1,581 秒 | 701 秒 | **2.26** | 937 / 497 / 147 | 126 / 423 / 152 |
| 200N・最小幅 5mm | 28 | 1,683 秒 | 651 秒 | **2.59** | 1,241 / 260 / 182 | 178 / 291 / 182 |

- 両条件とも、試行の履歴(マスクのハッシュ・合否・安全率)、CG の反復数の列、採用形状が CPU 版と一致した。
  全設計空間(自由な自由度 約 201 万)の CG もビット一致で解けた(最初の評価の GPU の CG は 18 秒)。
  製品の配線(`fem.FEM_DEVICE = "gpu"`)で 2000N の探索を回し直しても一致した(Python 3.11 の CPU 版と 3.14 の GPU 版)。
- 2.0mm では低荷重(200N)でも線形求解が CPU 版の 74% を占めた(4.8mm・4.0mm の探索では候補生成が 7 割強だった。docs/TOPOPT_SPEED.md)。
- **GPU 版では候補生成が探索の 45〜60% になり、次の律速はそこ**(docs/TOPOPT_SPEED.md「候補生成と評価の固定費」)。
- プロセスのホスト RAM のピークは CPU 版 12.1GB・GPU 版 13.4GB。

## 採らなかった CPU 側の候補: 剛体モード付きの AMG 前処理

GPU の無い機械で CPU の CG を速くする候補として測った(本人の指示、2026-10-10)。上の 8 行列・rtol 1e-9 で、前処理をヤコビから
平滑化集約 AMG(pyamg 5.3.0、近零空間に剛体モード 6 本、3×3 ブロック、V サイクル 1 スレッド)に替えた。

- 反復は 50〜70 分の 1 になるが、V サイクル 1 回がヤコビの CG の約 20 反復ぶん重く、**合計は 1.8〜2.7 倍**(準備込み。49 万自由度で 59.7 秒→7.3+19.6 秒)。
  剛体モードなし(並進のみ)では 0.8〜1.3 倍で効かない。
- 解の差はヤコビの解に対して相対 1e-11 前後。**ビットは一致しない**(採ると過去の台帳と比べられなくなる)。
- **設定に敏感**(36 万自由度で): 強さの閾値 0.05 で 3.1 倍、**閾値 0.1 ではヤコビより遅い**(76.9 秒)。平滑化をヤコビ系にすると 33〜38 秒、延長の平滑化を外すと 39 秒。
- **pyamg 5.3.0 には Python 3.14 の Windows wheel が無い**(3.13 まで。ソースからのビルドには Visual Studio が要る)。
- 100 万自由度超と、探索に組み込んだ秒は測っていない。線形求解の割合(59〜74%)に 2〜3 倍を当てはめると探索全体で 1.4〜1.9 倍の見込み(換算)。
- 扱い: GPU の無い機械(ThinkPad)が計算の主になる前に、台帳の基準を切り替えてよい時点の候補として再検討する。

## まだ分かっていないこと

- 200 万自由度級の CG の VRAM の量(解けることは確認済み)。
- GPU を他の作業(Unity・ローカル LLM)と同時に重く使ったときの秒。
- ThinkPad での CPU の CG の秒(2026-10-10 本人判断で見送り)。

## テスト

`tests/test_fem_gpu.py`。CPU へ戻る経路は GPU が無くても走る。ビット一致と探索の一致は、CuPy と GPU がある環境でだけ走る
(開発用チェックアウトで回すなら `uv sync --extra gpu`)。
