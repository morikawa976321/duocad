# 形状最適化 — 更新則 OC と MMA の比較（制約は体積1本のまま）

**この文書の役割:** `simp.optimize(update="oc"|"mma")` を**同じ題材・同じ格子・同じ材料量**で回し、
**答え（形・硬さ・材料量）と費用（反復数・1反復の秒数・合計）を並べた実測**。
**制約を1本も足していない状態**での比較であり、「MMA を既定に倒してよいか」の判断材料である。
**採否は本人が決める** —— 本書は数値と実行者の推奨まで。

## 結論（先に）

**答えは実用上同じで、費用は MMA のほうが安い。ただし「同じ答えに何反復で着くか」は OC が速い。**

1. **形と硬さは区別できない。** hanger 2.4mm・40反復で、自由要素の
   **98.6〜99.6% が同じ側**（ρ>=0.5）に落ちる。食い違うのは輪郭1層で、
   材料要素の 4.4〜4.7%・自由要素あたりの平均 |Δρ| は 0.005〜0.014。
   最終コンプライアンスの差は **-0.38%（材料10%）/ +0.008%（材料30%）** で符号すら一定しない。
2. **達成材料量も同じ。** MMA は体積を**上限**として扱うので目標へ下から寄るが、
   その下振れは相対 **-1.3e-05 〜 -2.3e-05**（OC は等式なので 1e-12）。
   mm^3 でいえば 452,360.3 に対し 452,350.1 —— 10mm^3 の差。
3. **1反復は MMA のほうが 7〜15% 安い。** hanger 2.4mm・`threads=7` の中央値で
   38.29→35.49秒（材料10%）、32.82→28.46秒（材料30%）。
   **同じ OC の計算を2時間空けて測り直して合計 0.4% 差だったので、この規模の秒数は
   そのまま読んでよい**（小さい題材の秒数は ±16% 動く。下の「秒数をどこまで信じてよいか」）。
   理由は**更新則そのものの秒数**にはっきり出ている: **OC 7.87〜8.48秒（1反復の 20〜25%）に対し
   MMA 0.91〜1.01秒（3%）**。OC の乗数二分探索は各段で密度フィルタ `_physical` を掛け直すが、
   MMA の双対二分探索は**フィルタを掛けない**閉じた式である。
4. **しかし反復数では OC が速い。** 両者が届く共通のコンプライアンス（悪い側の最終値 +1%）へ
   到達するのに、**OC 9〜20反復に対し MMA 25〜29反復**（時間で 1.4〜2.9倍）。
   MMA は序盤の歩みが遅く、終盤で追いつく。**40反復固定なら差は消えるが、
   反復数を削る方向の短縮案（[TOPOPT_SPEED.md](TOPOPT_SPEED.md)）とは相性が悪い。**
5. **この序盤の遅さは定数1本で半分になる。** `MMA_ASYMPTOTE_INIT`（初期漸近線の半幅）を
   文献の標準値 0.5 から **1.0** へ広げると、hanger 材料30% で共通目標への到達が
   **25→17反復**、一致率 0.9858→**0.9946**、コンプライアンスは OC より**良い側**へ
   （+0.008% → **-0.058%**）動き、合計秒も 1321→**1212秒**（OC 比 0.918）になった。
   **既定値はこの題材で校正した数字ではない**（taskbox `20260910-1312` の契約 ④）。

### 実行者の推奨: **条件付きで「倒してよい」（止める材料は出なかった）**

- **反力制約を入れる段（taskbox 1314 以降）へ進むのに、費用の面からの反対材料は無い。**
  制約が2本以上になれば OC は使えないので選択の余地が無いが、「MMA は遅いから別の道を探す」
  必要が**無い**ことが数字で確かめられた。1反復は 7〜15% 安く、答えは同じである。
- **`DEFAULT_UPDATE` を倒すなら、`MMA_ASYMPTOTE_INIT` を 1.0 にしてから倒すこと。**
  既定の 0.5 のままだと、40反復固定という前提の外（早期停止・反復数削減）へ出た瞬間に
  OC に負ける。1.0 にすると hanger 材料30% では**測ったすべての軸で OC 以上**になった
  （形・硬さ・材料量・秒数）。**ただし校正したのは demo30 の3点と hanger の1点だけ**で、
  この1本以外（`move` / `SHRINK` / `GROW` / `ALBEFA`）は触っていない。
- **急いで倒す理由は無い。** 制約が1本のうちは OC でも困らない。
  **既定の切り替えは、制約を足す変更と一緒に（それが必要になったときに）行うのが安い**
  —— そのほうが、下の2つの副作用を同じ変更の中で始末できる。
- **費用以外に、倒すと変わることが2つある**（taskbox `20260910-1312` の契約 ②③）。
  - `safety_loop._evaluate` の3分類のうち **`too_much` の作られ方が消える**
    （MMA は `VolumeTargetError(above_capacity)` を上げない）。
  - `rho.sum() == target_volume` を前提にした比較・検査に**相対許容が要る**（上記2の下振れ）。

## 測り方

`update` は `run_topopt` / `run_pipeline` へ通っていない（`optimize` の引数として増やしただけ）。
そこで `anchor.run_pipeline` が `simp.optimize` へ渡す引数を**そのまま横取りし**
（`_capture_optimize_kwargs`）、その同じ引数で `simp.optimize(update="oc")` と
`simp.optimize(update="mma")` を1つの process で続けて呼ぶ。格子・境界条件・パッシブ要素
（`void_mask`/`solid_mask`）・フィルタ半径・材料量は**同一物**である。
自分で境界条件を組み直すと、製品が解いている問題とは別の問題を測ることになる。

- **`change_tol=0.0` を明示する。** MMA は漸近線が歩幅を殺すので `Iteration.change` の意味が
  OC と違い、既定 `change_tol=0.01` のままでは「どちらが速いか」が**停止条件の差**に化ける。
  反復数は `max_iter` で揃え、収束は履歴から事後に判定する。
- **収束反復の定義**: 最終コンプライアンスからの相対距離が `tol` の内側に入り、
  **以降ずっと内側に留まる**最初の反復（1% と 0.1% の2本）。「初めて内側へ入った反復」では
  ないのは、コンプライアンスが途中で下から突き抜けて戻るため。
- **一致率はパッシブ要素を除いた自由要素で読む。** 箱の外側の空要素を入れると、両方 0 で
  一致するぶんだけ水増しされる（hanger は 359,656 箱要素のうち 37,272 が空）。
  ρ>=0.5 の集合の IoU も併記する。
- **更新則そのものの費用を分離する。** `simp.UPDATES` のクラスを派生クラスで包んで `step()` の
  秒数だけを積む（数値は変わらない）。1反復の大半は CG（`model.solve`）で、そこは OC と MMA で
  同じコードなので、費用差が出るなら `step()` に出る。
- **`threads` は固定する。** demo（小格子）は `threads=1` —— 格子が小さいと並列の当たり外れが
  1反復の秒数に乗って更新則の費用が見えなくなる。hanger は `threads=7`（= この機械の
  `simp.PARALLEL_THREADS`。本番経路と同じ値）。

### 秒数をどこまで信じてよいか（**題材の大きさで別物**）

同じ OC の計算を時間を空けて2回測った（どちらも**ビット単位に同じ答え**を返している）。

|---|---|---|---|
| demo30・`threads=1`・1反復≒1秒 | 0.929 / 0.925 / 0.948秒 | 0.776 / 0.781 / 0.968秒 | **-16% / -16% / +2%** |

## 問いへの答え

**形と硬さは実用上区別できるか** —— できない。自由要素の 98.6〜99.6% が同じ側に落ち、
食い違うのは輪郭1層（材料要素の 4.4〜4.7%）。コンプライアンス差は -0.38% 〜 +0.008% で、
**どちらが良いかは題材と材料量で入れ替わる**。marching cubes と平滑化を通した後の形として、
この差を意味のある違いとして扱う根拠は無い。

**MMA は OC より遅いか** —— **遅くない。**同じ反復数なら MMA のほうが安い
（実測した 8ケースすべてで合計秒が小さい）。**hanger 2.4mm では 1反復の中央値が
38.29→35.49秒 / 32.82→28.46秒**で、この規模の秒数は再測定で 0.4% しか動かない。
demo 規模の倍率（0.883〜0.983）は壁時計が ±16% 動くので向きだけを読むこと。

**それは反復数か、1反復の重さか** —— **1反復は MMA が軽い**（更新則の step が
7.87〜8.48秒 → 0.91〜1.01秒。OC は乗数二分探索の各段で密度フィルタを掛け直すが、
MMA の双対二分探索はフィルタを掛けない）。**反復数は OC が少ない**（共通目標へ
OC 9〜20 に対し MMA 25〜29）。**40反復固定という現在の前提では前者が効いて MMA が安く、
反復数を削るなら後者が効いて OC が安い。**

なお **step の差（1反復あたり約7秒）がそのまま合計の差になっていない**。
hanger 材料10% では 1反復の中央値の差が 2.8秒しかない —— **MMA のほうが step 以外
（大半は CG）に時間が掛かっている**ということで、密度場が違えば CG の反復数も違うのだから
不思議ではない。**「更新則を軽くしたぶんがそのまま浮く」とは考えないこと。**

**MMA 固有の調整で改善の余地があるか、それとも本質的か** —— **余地がある。本質ではない。**
唯一の弱点だった序盤の遅さは、**初期漸近線の半幅 `MMA_ASYMPTOTE_INIT` を 0.5 から 1.0 へ
広げるだけで、小さい題材では消え、hanger では半分になる**
（下表は demo30・100反復・共通目標への到達反復）:

| ケース | oc | mma 既定(0.5) | mma 0.2 | **mma 1.0** |
|---|---|---|---|---|
| demo30 10% | 24 | 19 | 20 | 20 |
| demo30 20% | 40 | 22 | 25 | **19** |
| demo30 40% | 8 | **12** | 17（悪化） | **9** |

最終コンプライアンスは3本とも実質同じ（材料40% で -0.028% → -0.034%）。
**狭める側（0.2）は悪化する**ので、効いているのは「序盤の歩幅」である。
初期漸近線が広いほど部分問題は線形に近づき、1歩目は移動限界だけで決まる
—— つまり OC の1歩目と同じ大きさになる。既定の 0.5 は文献の標準値そのままで、
**この題材で選び直した数字ではない**（taskbox `20260910-1312` の契約 ④）。

**hanger 2.4mm・材料30% でも同じ向きに効く**（上の「定数を1本振ると弱点が半分になる」）:
共通目標への到達 25→17反復、一致率 0.9858→0.9946、コンプライアンスは OC を上回った。
**ただし OC の 9反復には届かない** —— 序盤の遅さは**縮むが消えない**。

**振ったのは1本だけ**である。移動限界 `move`（OC と共有・0.2）、
`MMA_ASYMPTOTE_SHRINK/GROW`（0.7 / 1.2）、`MMA_ALBEFA`（0.1）は触っていない。
**制約を足す段へ進む前に定数を確定させる必要は無い** —— 序盤の歩幅は
「同じ答えにいつ着くか」を動かすだけで、着く先（形・硬さ・材料量）を動かさない。

## 自前実装にした理由（ライセンスと形。2026-09-10 本人決定）

出回っている実装のライセンス: `mmapy`（PyPI）と `GCMMA-MMA-Python`（GitHub。TO 界隈の事実上の標準）は
Svanberg の MATLAB（`mmasub.m` / `subsolv.m`）の翻訳で **GPLv3**。NLopt の `LD_MMA` は Steven Johnson が
論文から独立に実装したもので実装自体は MIT（ライブラリ全体は LGPL）—— GPL 系譜の外にある唯一の実装。
著作権が守るのはコードという表現であってアルゴリズムではないので、論文から独立に実装すれば GPL の
制約は及ばないが、GPL のコードを見て書き写すと派生物になる。配布方針が未定のうちは GPL を取り込まない、
が判断（MMA の特許状況は未確認）。

**ライセンス以前に形が合わない。** `mmasub()` は部分問題ソルバで、反復ごとに1回呼ぶと新しい設計変数が
返る（既存の更新則をそのまま差し替えられる）。NLopt は最適化器で、目的関数を渡すと NLopt が呼び返す ——
ループを NLopt が持つので、反復ごとの進捗配信・中断・パッシブ要素の上書き・履歴を全部その流儀へ
作り直すことになる。duocad では `simp.optimize` がループを持ち、外側（`safety_loop` / `optimize_run`）が
そこへ進捗と中断を刺しているので、NLopt は形が合わない。
