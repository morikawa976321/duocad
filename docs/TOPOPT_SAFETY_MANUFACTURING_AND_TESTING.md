# duocad — 安全率探索・製造要件・テスト設計の落とし穴

**いつ読むか**: 構造解析(安全率探索・SIMPトポロジー最適化)の実測や製造要件を扱うとき、検査・受入テストの設計をするとき、一般的な開発運用の落とし穴を確認したいとき。

## 1. hanger実測(唯一の実物モデル)

- **`hanger_bar_attachment.json`が製品経路を通る要素サイズは4.4mm/4.8mmだけだった**(実測・2026-09-08〜09、`45e3ab3`門1修正前)。製品の経路(`optimize_run.run`)には門が2つ: ①`_check_anchor_centroids`(荷重面がトーラスなので細かいほど落ちる) ②`_region_representation`(保持/除外ソリッドが0要素だと`state="unrepresented_regions"`を返しsimpを呼ばずに戻る。`0 < n < 8`は警告して続行)。要素サイズ別の可否: 2.4/2.8/3.2/3.6/4.0mmは門1で落ちる、4.2mmは通るが門2(`_10`が0)で落ちる、4.3mmは門1で落ちる(12.951>12.925)、**4.4mmは両方通り走る**、4.6mmは門2(`_8`/`_9`/`_10`が0)で落ちる、**4.8mmは両方通り走る**、5.333mmは門2(`_10`が0)で落ちる、既定13.264mmは保持1つ・除外6つが0。**門2は要素サイズに対して単調でない**(4.2mmで0だった領域が4.4mmで1になり4.6mmでまた0になる——格子の原点と刻みが要素サイズごとに引き直され、薄い部品(最小辺5.00mm、保持`_1`/`_2`/`_3`と除外`_8`/`_9`/`_10`が5.2×5.0×5.2mm級)にセル中心が入るかどうかが偶然で決まるため)。「N mm以下なら通る」という書き方はできない。`MAX_ELEMENTS`は2026-09-08に120,000→2,000,000へ上げた(`4b9d2e2`)。**門1は2026-09-09に修正**(`d3b1229`、閾値は緩めず比べる相手を面の面積重心に変更)、同日**2.4mmで`optimize_run.run`を入口から完走**(門1の距離は荷重面0.055mm・拘束面0.173mm、許容7.223mm。門2は0要素の領域なしで通過)。未決(2026-09-09時点): 門2の非単調性への対応(事前検出を緩めるかモデル側条件を選び直すか)は本人判断待ち。
- **hangerの作業解像度は2.4mmと決定**(判断・2026-09-08、完走確認2026-09-09)。決めたこと: ①`optimize_run.MAX_ELEMENTS`を120,000→2,000,000(`4b9d2e2`、これで2.4mmが`[下限2.065mm, 上限13.264mm]`に入り指定可能になった) ②hangerの作業解像度は2.4mm(箱1,173,276/塊610,384、コードは変えず`element_size_mm=2.4`を明示的に渡す。**2026-09-09に製品経路(`optimize_run.run`)で完走**)。**決めなかったこと**: 既定の決め方(文書ごとに導出し「いちばん粗い(=条件面が許す上限)」を採る。hangerでは13.264mm)を2.4mm固定に変える案は不採用——2.4mmはhanger固有の事情(薄い部品が5.00mm)から出た数字で他部品へ持ち出す根拠が無く、絶対値の固定は部品の大きさに追随しない(10mm角の部品なら4要素、500mmの部品なら200要素跨ぐ)。原因に直接対応するなら「保持・除外の最小辺がN要素跨ぐ大きさ」のような規則(hangerだと自動で約1.7mmが選ばれる)だが、実測が溜まる前に規則を決めない。**代償**: 完走の実測(2026-09-09・void除去済み・材料量範囲`[54233, 87036]`に絞った再開分)は箱1,096,894要素/採用材料70,634.5mm^3(容量の0.46%)/最小安全率2.024(目標2.0)/最終の塊11,368要素/三角形10,236枚、**評価5回で3.57時間・峰25.9GB**。範囲を絞らない初回は評価10回目で落ちるまでに5.7時間(下記「低材料側の残差失敗」参照)——**範囲を絞らない完走は8時間級**と見ておくこと。`MAX_ELEMENTS`はもうメモリの安全域ではない(上限いっぱいの200万要素は現行実装で約46GBとなりこの機械では走らない。「実物が通るための政策上の上限」として読むこと。実用の目安は120万要素前後)。
- **hangerの形が初めて出た**(実測・2026-09-09、taskbox `20260909-0518`)。成果物は`duocad/models/`(`.gitignore`対象なのでコミットされない)。**4.4mm(製品の経路)**: `state="done"`/`converged=True`/9評価/`rel_tol=0.08`/40反復。安全率**156.758**(目標2.0)/収束材料量**1,315,866.508mm^3**/三角形14,580。格子43x76x60=196,080箱(実spacing 4.4247mm)、最大の評価で塊137,683。全体2,107秒(35.1分)。組立112.93/solve 861.68/mg_setup 166.18(うちsplu 8.00・RAP+平滑化158.18)/slice 27.25秒。CG 19,394反復/366 solve(平均53.0・最大144)。ピーク+3,767MB・スワップ無し。面アンカーの門は余裕0.15mmで通っている(実測13.120mm/許容13.274mm。距離はほぼ一定で許容だけが要素サイズで動くので、この解像度は崖っぷち)。探索の途中で`too_little`を3回踏み、うち2回は`DesignSpaceDisconnectedError`(拘束と荷重が繋がらない、材料1,186,138mm^3と1,056,410mm^3)——収束値1,315,867のすぐ下に不連結の崖がある。**2.4mm(製品の経路ではない、単発)**: 製品の経路を通らないため`design_space.run_topopt`を直接呼び、材料量を4.4mmの収束値に固定して40反復1回回した(安全率探索ではない)。格子78x138x109=1,173,276箱(実spacing 2.4076mm)/塊172,310/自由度3,623,730(自由567,246・拘束3,056,484)/nnz 43,235,469/`_iK`+`_jK` 794.0MB。全体2,484秒(41.4分)。組立60.57/solve 1,035.88/mg_setup 84.95/slice 14.53秒。CG 7,763反復/40 solve(平均194.1)。ピーク+4,970MB・スワップ無し。安全率**154.701**(4.4mmの156.758と1.3%差)/三角形50,244。自由度の84%が拘束側に回っている(3,056,484/3,623,730、`_floating_dofs`が「空要素にしか接していない節点」を外すためで、塊が箱の15%しかない構成でこれが効く)。
- **安全率探索は低材料側の残差失敗で落ちていた**(実測・2026-09-09、修正2026-09-11時点)。hangerを2.4mm(案1の箱1,096,894要素)で端から端まで回すと**10回目の評価で`simp.SolveResidualError`が上まで抜け、5.7時間ぶんの評価を捨てて落ちた**(材料8.704e4mm^3→安全率3.183(通る)、材料5.423e4mm^3→SolveResidualError。自由度3,623,730のうち残ったのは43,161/残差2.93e-5>1e-6/max|u| 8.24e7)。機序: 材料量が小さいほどρが下限に張り付き`_floating_dofs`がほとんどの節点を拘束側へ回す。残った系は小さいが悪条件でCG/多重格子が`SOLVE_RESIDUAL_TOL`(1e-6)に届かない。`safety_loop._evaluate`は`VolumeTargetError`と設計空間の例外しか分類しておらず残差検算の失敗は素通しだった(`SolveResidualError`を型として分けた2026-09-09より前は素の`ValueError`)。**`too_little`に分類するのが正しい**(材料が足りない側の現れなので`lo`を立てて探索を続ければよい、duocad `4f81f6b`)。拘束不足の握りつぶしにはならない(本当に拘束が足りなければ上端の評価が同じ例外で落ち`SafetyTargetError(side="invalid_bound")`として原因を連鎖したまま上がる)。**受入検査では見つからなかった**——`check_safety_loop.py`はbracket 20要素(案1 3,336要素)で探索を最後まで回すが、低密度の悪条件は要素数が多いほど出るため再現しない(参照runが14要素の格子で残差検算を通らなかった件も同じ理由で本番では起きない)。**本番解像度で1回通すまで見つからない種類の失敗がある。**

## 2. 安全率探索の設計判断

- **収束幅`DEFAULT_REL_TOL`を0.02→0.08へ**(判断・2026-09-09)。`duocad/topopt/safety_loop.py`の定数を書き換えるだけで、引数で渡す口は作らない(`OptimizeOptions`に`rel_tol`は無く`optimize_run.run`も`solve_for_safety_factor`へ渡さない——その配線は今回作らない)。理由は**評価回数を2回減らすため**(二分探索は1評価ごとに区間を半分にするので`log2(0.08/0.02) = 2`)。**8%という値そのものに技術的根拠は無い**(欠落ではなく事実。`docs/TOPOPT.md`にもそう書く)。既存の`rel_tol=0.02`の論拠(「2%より細かく詰めてもボクセルの量子化と密度フィルタの目減りに埋もれる」)は「これ以上細かくしない理由=下限」の話であり、緩める根拠に転用してはならない。**承知している代償**: 停止条件が`(hi-lo)/hi <= rel_tol`なので返る材料量は真の最小より最大8%重くなりうる(停止条件からの帰結であって実測ではない)。安全率は目標以上のままなので形は使えるが、この設定で出した結果を「最小材料の解」として扱わないこと。
- **安全率外側ループは二分探索の候補材料量ごとに塊を導出し直す方式を採用**(判断・2026-09-05)。`probe_topopt`の塊の導出(案5`derive_from_coarse_run`)は材料の居場所から塊を作るため材料量が変われば塊も変わる。安全率を入力に材料量を二分探索する外側ループ(`safety_loop.py`)で塊の扱いに3案あった: (a)二分探索の各段で塊を導出し直す(塊と材料量が常に噛み合うが「安全率の変化が材料のせいか塊のせいか」を厳密には切り分けられない) (b)一度だけ導出して固定(安いが塊と材料量が噛み合わない) (c)探索範囲の上端で一度導出して固定((b)よりまし、塊が最大なので少ない材料も含む見込みがあるが包含は保証されない)。**(a)を選択**——理由はcheck-scale解像度(数百〜千要素)での実測コストが1点あたり導出0.4〜0.5秒+最適化1.8〜2.8秒と無視できる大きさで、切り分けの明快さより噛み合わせの正しさを優先できたため。(a)と(c)を同じ題材(bracket)で比較実測すると、材料量が(c)の固定点に近いほど安全率が一致(差0.01〜0.13%)、遠いほどずれる(最大4.23%、(c)の塊は固定点向けに膨らませてあるのでそれより少ない材料では塊が「緩すぎる」側に振れる)。**一般化**: 「材料量(や他の設計変数)に追従して形状/離散化そのものが変わる系で、その変数を外側ループが振るとき」は、内側の離散化・領域決定を候補値ごとに作り直すコストが実際にどれだけ無視できるかを測ってから決めること(コストが安ければ噛み合わせを優先してよいが、高い場合(本番解像度など)は別の判断になりうる——本番解像度(elements_long_axis=40)でのコスト比較は未実施)。
- **配線が終わるまで検査は「題材を縮める」で削る**(判断・2026-09-04本人指示)。本人指示: 「パフォーマンスを詰めるのは一番最後(配線も終わった後)でいい。まずは時間がかかるor品質が低い、でいい。検証効率を高めるためにいまは要素数も反復数も十分すくなめで。細かい変数の調整は配線のあと」。`probe_topopt`の受入検査7本で実行: 通し661秒→110〜120秒、検査項目284件は増減なし。**削る単位は「検査の題材の大きさ」であって「検査の数」ではない**(題材の大きさは`bench.py`と`simp.PRESET`の1箇所に集約——各検査が自前の格子を持つと縮めるたびに6ファイルを直すことになる)。**縮めてよいかどうかは「わざと壊したときに落ちるか」で決める**——落ちなくなったものはその検査だけ元の大きさを残し理由を数字で書く。実際に残った4件: marching cubesの体積誤差は要素サイズで決まる(20×8×8で9.19%、閾値5%を割る)、面アンカーの「面積重みを外した対照が落ちる」は解像度32でしか安定しない(24で1.03%、閾値1.5%)、応力の「ρ≥0.5のmaxが代表値の1.5倍以上」は16×8×8で1.18倍に落ちる、片持ち梁の「終盤10反復の変動が1%未満」は30反復で2.47%になる(格子だけ縮め反復数は据え置き)。**閾値を緩めて通すのは禁じ手**(閾値が守っていた回帰(等高面の位置ずれ・偽の集中・素のmaxへの退行)が素通りする。速さのために検出力を売らない)。

## 3. 面アンカー・製造要件

- **要素サイズより小さい面には節点が1つも付かない**(実測+修正・2026-08-31〜2026-09-05)。`probe_topopt`のstage2「面アンカー」(CADの面→格子節点の対応表)で、1節点を1面に排他割り当てする規則(最も多く面積を配った面が独占)を採ると要素サイズより小さい面には節点が1つも付かない。実測: 231面のSTEP(`shelf_attachment_7.step`)を要素サイズ1.54mmで割ると22面が空、2.57mmでは30面が空。帰結: そういう面は固定面・荷重面に指定できない(UIは「この面はこの解像度では指定できない」と言えなければならない)。空の面を黙って「荷重0」「拘束なし」に変換してはいけない(拘束の無い系や荷重の無い系がそのまま最適化に入りもっともらしい形が出る)。もう1つの実測: 担当面積は稜線で隣の面に取られるぶん真の面積より数%小さい(合成ブラケットの24×24の面で10.7%、8×8の面で11.8%、要素サイズ1.875mm。面が小さいほど大きい。誤差は要素サイズに比例して減るが1段の解像度比較では単調にならない)。**続報(2026-09-03〜05)**: 空の面は黙って通らなくなった——`AnchorTable.node_ids`(`fixed_dofs`/`load_vector`/`element_mask`が内部で通る)は`_require_nodes`を呼び、節点が1つも付かない面が混ざっていたら`ValueError`で落ちる(2026-09-03、taskbox `20260903-2234`)。`anchor.run_pipeline`はこれを`simp.optimize`より前に呼ぶのでsimpの残差検算まで届く前に落ちる(実測: `ValueError: 指定した面に格子節点が1つも付いていない: 面7(plane, CAD面積0.25mm^2)。要素サイズ5mmに対して面が小さすぎて…`)。解像度をどこまで上げるべきかは下記「製造下限」が決める。
- **小さい面に節点を付ける改修は解決にならない**(判断・2026-09-04、当面は通知のみ)。「どうやって小さい面を節点に紐づけるのか」を検討し**紐づけない**という結論。**なぜ空になるのか**: 面→節点の表は3段(`probe_topopt/anchor.py`)——①面を細分して標本点を作る(面積は保存)②各標本点から半径`radius_ratio×要素サイズ`(既定1.0)の球に入る節点へテント重みで面積を配る③1節点は高々1面、持ち主は「最も多く面積を配った面」(同点は面添字の小さい方)。小さい面も節点に面積は配っているが3段目の多数決で隣の大きい面が勝つ——だから「付ける」こと自体は多数決の規則を曲げるか排他をやめるかで技術的には可能。**それでもやらない理由2つ**: ①排他には理由がある(稜線を共有すると同じ節点が「拘束されていて、かつ荷重を受ける」状態になり、その荷重は黙って消える。排他は「黙って消える」を防ぐ規則で、壊すなら代わりの守りが要る)②付けても解決しない(節点1つに荷重を載せるのは点荷重=特異点。`20260904-0143`の実測でプリセットの素の最大応力は「ρ=1の荷重直下(点荷重の特異点)」に出ており、無理やり節点を付けた小さい面はそこに応力が集中して安全率が信用できない値になる——しかもそれはsilentである)。**当面の措置(2026-09-04本人判断)**: 例外にせずメッセージを出すだけ(当初は実行経路の入口で落とす案だったが本人が通知に留めると判断。「いずれ解きたい問題ではある」とのこと)。道具は既にある(`AnchorTable.empty_faces()`)し受入検査も見ている。`design_space.assert_faces_connected`は空の条件面を見つけると意図的に判定を降りる(そこで落とすと原因が別の例外に化けるため)——足りないのは実行経路の入口だけだった。
- **「解像度をどこまで上げるべきか」は製造下限が決めている**(判断・2026-09-04〜05)。密度フィルタ半径`rmin`は要素単位(既定1.5要素)で、しかも`anchor.run_pipeline`/`design_space.run_topopt`から渡す口が無い——解像度を変えると物理的な平滑化スケールが変わり別の設計問題を解いていることになる(格子単位で持っている量は格子が変わった瞬間に物理を変える、という型)。実物部品(最長辺154mm)での対応: 分割数40→要素サイズ3.85mm→`rmin`(1.5要素)5.8mm→相当する最小部材幅6〜12mm、分割60→2.57mm→3.9mm→4〜8mm、分割100→1.54mm→2.3mm→2〜5mm、分割128→1.20mm→1.8mm→2〜4mm。**2つの下限が挟み撃ちにする**: 製造側(PETG/0.4mmノズル。壁2本の0.8mmは「形はできるが構造ではない」。設計値が出る最小部材幅はおおむね2〜3mm→`rmin`≈1.5〜2mmを狙う)と数値側(`rmin`が1要素を下回るとフィルタが効かずチェッカーボードが出る→`rmin`≥1.5要素、つまり要素サイズ≤`rmin`/1.5)。**いまの分割40はフィルタが製造下限よりはるかに粗い**(2mmの部材が作れるプリンタに対し最適化は6mmより細い部材を出せない=製造能力を使い切っていない)。`rmin` 2.0mmを満たすには要素サイズ≤1.33mmが要り154mmの部品なら116分割以上(現状で1.8時間を超える領域)——速度の話は製造要求から逆算された必要条件であり単なる快適さの問題ではない。**採った形(2026-09-04本人了承)**: 値を1つ固定するのではなく両方の下限を明示して破ったら数字で教える。`rmin`をmmで指定する口を作る(要素単位の口は残す・排他)。既定は要素単位1.5のまま2.0mmを既定にしない(現状のデモが全部落ちるため。デモは最長軸22分割で要素サイズが1.33mmに遠く及ばない。2.0mmはREADMEの目標値)。下限を破ったら例外にし逃げ道を2つとも数値で言う(要素サイズをいくつ以下にするか/この解像度で指定できる`rmin`の下限はいくつか)。
- **「合力を指定して比で配る」荷重は面積の欠損を正規化で隠す**(2026-08-31)。CAD面→格子節点の対応表(面アンカー)で稜線の規則により担当面積の合計は真の面積より数%小さい(実測: 要素サイズ2.5mmで11.7%、1.25mmで4.5%)。`load_vector(face, 合力)`は指定した合力を担当面積の比で配るのでこの欠損は正規化で吸収されて完全に消える(実測の相対誤差2.3e-16)。一方`pressure_vector(face, p)`は`p×面積`が合力そのものなので欠損がそのまま合力不足になり、粗い格子ほど大きいため解像度を上げると黙って合力が増える(=結果が解像度に依存する)。**教訓**: 「正規化してから配る」量と「掛け算で決まる」量を同じ中間データから作るとき、前者だけを検査すると後者の誤りが見えない(前者は正規化があるので中間データがどれだけ狂っていても検査は緑になる)。直し方は中間データを変えることではなく(担当面積は「実際に受け持っている面積」で正しい)、掛け算の側だけを真の値から出すこと(総量はB-repの面積から出し、配り方(重み)は担当面積のまま按分する)。
- **解いた系と目的値の総和範囲は必ず揃える**(運用知見・2026-09-09)。duocadのvoid除去で`Model.assemble`をactive要素だけにしたとき`Model.compliance`は全要素で足したままだった。変更前はKが空要素をeminで含んでいたので`c == F・U`が厳密に成り立っていたが、除去後は`c = F・U + (解いた系に無いemin媒質のひずみエネルギー)`になった(実測の相対差2.5e-07/1.3e-06、題材による)。**なぜ検査で捕まらなかったか**: `check_simp.py`[2]は`c == F・U`を1e-8相対でassertしているが全件緑だった——[2]が使うのは`void_mask`を渡さない片持ち梁で`active_mask`が`None`なので等式が今も厳密に成り立つ(検査は存在したのに壊れた経路にだけ届いていなかった)。「同じ不変条件をassertしている検査があるか」ではなく「その検査は自分が変えた経路を通るか」を見ること。新しい経路を足したら既存の不変条件の検査も新しい経路ぶん足す。**直し方**: 目的値の側をactiveに揃えた(`c`だけactiveで足し`ce`は感度に使うので全要素ぶん返す)。「ずれることをdocstringに書いて残す」案は不採用——ずれは2.5e-07で許容の内側だが目的値は解いた系のものであるべきで放置すると以後の全利用者(随伴の検算・matrix-free・エネルギーを使う収束判定)がこの項を継ぐため。費用が測れて小さいことを先に確認(`c`は`history`にしか入らずOC更新は`ce`から作る`dc`を使う(空要素は`x_phys**(penal-1)`と`live`で消える)のでρは1ビットも動かないと予測でき実際にビット一致(SHA-256・体積とも)。動いたのは`c_first`/`c_last`だけ。判定表「コンプライアンス相対1e-3以内」に対し1.2e-06)。「念のため直す」と「直す費用を測ってから直す」は別物——基準値の取り直しを伴う変更は先に「何が動かないか」を予測して確かめてから入れると判定が事後の追認にならない。

## 4. テスト設計の一般原則

- **「無い」の検証はNoneと空を両方見る**(落とし穴・2026-09-11、composer-2.5指摘)。duocadの反力下限制約(`simp.optimize(reactions=..., reaction_min=ε)`)で、`reaction_min`を渡すときは`reactions`も要るという検証が`reactions is None`だけを見ていた。`reactions=[]`は通り、グループが空なので契約検査(`_check_reaction_groups`)は`if groups:`で呼ばれず、反復中も`if groups:`が偽で制約が1本も作られず、終端の検査は「下限を満たさない取付点」を数えるので0件→合格。結果`reaction_min=0.2`を持ったまま無制約の`Result`が正常終了として返っていた(同型の穴が`max_iter=0`(反復が1回も回らず測定が0件)にもあった)。**教訓2つ**: ①「無い」の検証はNoneと空を両方見る(0件だと何もしないのが自然な機能では0件が黙って無効化になる) ②終端の合格判定を「違反件数==0」で書かない(母集団が0件のときに真になる。「何件検証したか」を先に見る=`if not measured: raise`)。検出できたのは指摘を受けて門を外した版で再現を試したから——修正したうえで「門を外すと新しい検査が落ちる」ことまで確認しないと検査が欠陥を固定できていない可能性が残る。
- **観測用ヘルパーの値の形の取り違えは緑のまま何も検証しない**(落とし穴・2026-08-27実測)。状態を覗く`look()`が`sketches`を件数(数値)で返しているのに呼び出し側が`.sketches.length`と書いていた。`undefined !== undefined`は常に偽なのでその検査は起動時から何も検証しないまま緑だった(2項目該当)。比較を直したうえで「件数が数値で来ること」を先に落とすガードを追加。**一般化**: 観測用ヘルパー(`look()`/`snapshot()`等)は返す値の形が変わりやすく、型検査の無いスクリプトでは形の取り違えが赤ではなく緑になって表面化しない。検査を足す・直したときは一度わざと壊して赤くなることを確かめるか、少なくとも比較している値を出力して形を確認する。緑になったこと自体は検査が働いている証拠にならない。
- **ガード付き検査の直後に無条件`ok()`を書くと未検査分岐が隠れる**(2026-08-30、`smoke-clip-planes.mjs`)。`if (条件が成立するときだけ検査する) { ...fail()... }`の直後に無条件で`ok('...')`を書くと、条件不成立の回でも「検査した・通った」と表示される。実際に踏んだ例: `if (nearEdge > 0 && !(near <= nearEdge)) fail(...)`のガード自体は正しい(カメラが外接球の内側にいるときは近側クリップを判定できないので判定しないこと自体は正しい設計)が、直後の`ok('外接球の近端はnearより奥')`が無条件だったため`nearEdge`が負(検査対象外)の実行でも同じ「OK」が出て、この検査が一度もその分岐を通っていないことに誰も気づけなかった(QAが実際に走らせてログの数値を読むまで発覚せず)。**教訓**: ガードで守られた検査には`ok()`もガードの中に入れ、ガード外側(スキップ時)には別の文言(「検査対象外」等)を出す。検査の合否と「検査したこと自体」を同じ1行の`ok()`で済ませない。**副次的な設計事実**: near/farの「外接球containment」検査はnear側とfar側が互いに鏡像で、同じカメラ姿勢では片方しか検査できない(文書全体がカメラの外側にある姿勢を作るには内容がその後縮む(undoで消して小さな形だけ残す)+実カメラがその小さな形の外側・近くまで実際に寄る、の両方が要る。`frameAll()`等の明示的な再フレーミングは検査したい「自動追随の欠落」自体を迂回してしまうので使えない)。
- **既知の未達は期待値を正しい側で書きxfailで留める**(運用知見・2026-09-07)。「いまの実装は間違っているが直すのは次のタスク」という状態で検査を先に置くとき、書き方は3通りあり2つは罠になる: ①いまの(誤った)値を期待値に固定する(差し替えで落ちるが直った側が「落ちた」と言われ、誤った値が正として文書化される) ②「誤っていること」をassertする(罠の存在の主張。実装が直ると落ちるが何も寸法を見ていないので、直った以外の理由で罠が消えても同じ赤になり区別がつかない) ③**期待値を正しい側で書き「既知の未達」として留める**(pytestなら`@pytest.mark.xfail(strict=True, reason=...)`、自前検査なら「成立したら不合格にする」ヘルパ(duocad `topopt_checks/check_voxelize.py`の`check_known_gap`)。合否には数えないが成立するようになると落ちて知らせる)。③を採ると後続タスクの仕事は「期待値の書き換え」ではなく留め具を外すだけになり、期待値そのものは動かない。留め具の`reason`に「直したらこれを外せ」と書いておくと落ちた人がその場で何をすべきか分かる。**xfailは「いつか直す」の墓場にしない**——`strict=True`を必ず付ける(付けないと成立しても黙って緑になる)。留めてよいのは外す担当が決まっている(後続タスクが積まれている)ものだけ。
- **変異検査は「狙った1件だけが落ちたか」で読む**(2026-09-04〜05)。`probe_topopt`の連結性ガード(taskbox `20260903-2235`)で、「連結性は6近傍で判定する」という定義が実装と一致していることを検査で示すには定義を変異させたときに落ちる検査が実在することを見る必要があった。当てた変異3つ: 呼び出し自体を外す→正常系+断ち切り配置が落ちる(ガードが経路に繋がっている)、判定の本体を外す→断ち切り+直接入力3件が落ちる(判定そのものが効いている)、**定義を6近傍→26近傍に変える→角1点で接する2島の1件だけが落ちる**(定義が実装と一致している)。要点は3つ目——壁で断ち切った配置も隙間を空けた2島も6近傍でも26近傍でも同じく「切れている」と判定されるため定義の変異を検出できない。角1点だけで接する2島という定義を分離する題材を1件用意して初めて変異が検査に映る。**一般化**: 「AとBのどちらの定義を採ったか」を検査で固定したいなら、AとBで答えが変わる入力を題材にしなければならない。**同型(2026-09-05)**: 複数ボディをcompoundにまとめたときの面添字対応(オフセット=先行ボディの`face_count`の累積)を検査するとき、わざとオフセットをずらす変異を`+1`で入れたところcompoundの最後の面をまたいで`face index out of range: 13 (1..12)`になり「別の面を掴んだ」ではなく「添字が無い」で落ちた(範囲検査が働いただけで取り違えの検出力を1件も見ていない)。**-1側でずらすこと**(添字1は必ず存在するので範囲内に留まりかつ確実に別の面になる)。「壊したら落ちる」を見せる変異検査は落ち方まで指定して(例外の型・文面の一部)確かめないと意図と違う安全網に助けられて緑になる。
- **ハード・ビニングは分布の一様性検査に使えない**(2026-08-31)。離散点(格子節点)に載った量が空間的に一様かを検査するとき、面を格子状のビンに切って「ビンごとの合計vs真の面積」で比べるとビン境界を跨ぐ点1個の出入りがそのまま誤差になる。実測(`probe_topopt`の面アンカー): 3要素幅のビン(1ビンあたり約9節点)で±27%のばらつきが出て、正しい実装と明らかに間違った実装(面積重みを外した等分)が区別できなかった。**直し方**: ガウス核(σ=2要素)で平滑化し同じ核で平滑化した真の分布と比べる(分子と分母で縁の効果と曲率の効果が相殺し残るのは「配り方の偏り」だけになる)。同じ題材で正しい実装0.5〜0.6%/等分の対照3.4〜3.5%と6倍離れた。副産物の作法: わざと壊した対照(面積重みを外した等分)を同じ検査に掛けて実際に落ちることまで受入検査に含める(閾値が緩すぎて何も検査していない状態を防げる。実際、最初に選んだ題材(円筒・要素サイズを粗く)では対照が1.03%しか出ず閾値1.5%を下回り、その題材ではその検査は効いていないと分かった)。
- **規約の定数は1箇所に畳み口どうしの一致を検査する**(運用知見・2026-08-31、変異検査で発見)。同じ規約(例: 「要素の値はセルの中心のもの」=添字に+0.5)を複数の関数がそれぞれリテラルで書いていると1箇所だけ壊しても受入検査が緑のまま通る。実例(`probe_topopt/voxelize.py` stage1、2026-08-31): `Grid.centers_1d`/`Grid.centers_of`/占有判定のレイ生成がそれぞれ`+0.5`を書いており、変異検査で`centers_1d`の+0.5だけを+1.0に壊したところ8項目の受入検査が全部緑のまま通った(検査が使っていたのは別の口だった)。対処は2つセット: ①規約を1つの名前付き定数にしすべての口がそれを参照する(`CELL_CENTER_OFFSET = 0.5`。占有判定のレイも自前で座標を作らず`Grid`経由にする)②口どうしが同じ値を返すことを受入検査で照合する(`centers_1d`と`centers_of`と`center_of`の3つを突き合わせる。定数を1つにしても参照箇所を1つ壊す変異は残るため)。一般に**受入検査が全部緑で1発で通ったときは変異を当ててみる**。
- **測定成果物のファイル名には振った軸を全部入れる**(落とし穴・2026-09-08)。比較測定のハーネスが密度場を`rho_{題材}_{条件}_{ラベル}.npy`で書き出していたが解像度が名前に入っておらず、同じ題材の3解像度が同じファイル名になり後から回した解像度が前のを上書きした。集計側は「格子が違えば比較不能」を`a.shape != b.shape`で見ていたが上書きされた側は基準も比較対象も同じ配列を読むので形が一致し検査を素通りする(結果、レポートの2行が「5.37mm同士を比べた値を8.19mmの行に書く」状態になった、QAで発覚)。**教訓2つ**: ①測定の成果物のファイル名にはそのrunで振った軸を全部入れる(格子そのもの`25x42x34`を入れると軸名を考えなくて済む)②集計側に照合の門を置く(測定JSONに保存前の実物から取ったSHA-256と格子を書いておき読むときに突き合わせる。合わなければ同じdigestの配列を探し無ければ落とす。形の一致だけを見る検査は上書き事故に対して検出力ゼロ)。**続き**: 張り替えるときは「測定ごとの名前」ではなく「内容の名前」にする(`{題材}_{格子}_{中身のSHA-256}`にすれば共有は共有のまま別物は必ず別名になる)。成果物をファイルから読み直さない設計はこの事故に耐える(三角形数は書き出し前のオブジェクトから数えていたので数字は無傷だった)。表を手で書くと別の測定点の数字を書き写す(表は生データから機械生成するほうがよい)。取り違えを疑ったときの決め手はdigestだった(記録側(JSON)は保存前の実物から取っていたので実ファイルと突き合わせるだけで6/21本の取り違えが機械的に確定)。
- **PNGバイト列の単純比較でWebGL描画の変化を機械検査できる**(2026-09-04、ビューキューブFOV検査で採用)。「見た目が変わったか」を機械検査するのに`pixelmatch`/`pngjs`等の画像diffライブラリを新規に足さなくても、`page.screenshot({clip, encoding:'binary'})`が返すPNGバイト列を単純に1バイトずつ比較した不一致数で近似できる。やり方: ①同一カメラ・同一設定で2回連続スクリーンショットを撮り「制御群」の差分バイト数を測る(Chrome headlessの描画+PNGエンコードは同一入力に対して決定論的なので理論値は0)②比較したい条件(FOV違い等)の差分バイト数を測る③制御群の数倍(実測で0バイト対2995バイトと歴然差)を閾値にする。利点: 依存を増やさない・実装が数行・「変わったか」の有無検出だけなら画素単位の精密diffは不要。欠点: 「どれだけ・どこが」変わったかは分からない(変化量の大小比較には向かず、その場合は画素decodeが要る)。`web/scripts/acceptance.mjs`(ビューキューブがFOVに追従する検査)で採用。
- **散文の規則は検査を厚くせず「人が守る領域」に切り分ける**(判断・2026-08-22)。duocadのAIの行動規範(`duocad/catalog.py`の`agent_instructions()`。MCPの`initialize.instructions`とアプリ内AIパネルのシステムプロンプトが同じ文を読む、同一性はテストで固定)が骨抜きにされていないかを文字列検査で守ろうとした。QAが2ラウンド続けて素通りの経路を発見(1回目「重要句の有無しか見ていない」、2回目「区間を切り出したが終端句より後ろを見ていない」)。区画を4つに割り「止まれと読める語は第2段の中にしか置けない」という不変条件へ作り直して13通りの変異を落としたが、列挙していない言い回しの矛盾は常に書き足せることが実測で残った(素通り例: 「ユーザーへ問い合わせてから進むこと。」「実行の前にユーザーに聞くこと。」)。**判断**: 語を追い足すのをやめ、原本のdocstringに「この文を書き換える人への注意書き」を置き検査ではなく人が守る領域として切り分けた。**なぜ危険側に倒れないかを先に確かめること**: 規範を骨抜きにする変更をしてもコアが何も止めないので実行時に異常が出ない点が怖い——散文を検査から外すときは外した先に別の防具(コア側の門)があるかを必ず確認する。**一般則**: 散文の意味は文字列検査で固定できない(検査は「重要句が消えた」までしか見られず「意味を打ち消す1文が足された」は原理的に追い切れない)。パターンを増やす方向は盲点を厚くするだけで投資対効果が反転する。

## 5. 一般的な開発運用の落とし穴

- **同じリポジトリ内でも行末はファイルごとに違う**(運用知見・2026-08-27、2026-09-05〜06補強)。duocadは`core.autocrlf=true`でgitのblobは全てLFだが作業ツリーの行末は混在(ツールが直接書いたファイル(`web/src/viewport.ts`等)はLF、checkoutを経たファイル(`web/src/App.svelte`・`web/src/viewCube.ts`等)はCRLF)。`git diff`も`git status`も差分を出さないので目視では分からない。`.gitattributes`が無い環境では書いたツールごとに違う行末が入る。**踏んだ形**: ①複数行の完全一致置換が0件で落ちる(2026-08-27。片方で通った置換をそのまま隣のファイルに当てて0件)②変異検査が逆の結論を出す(2026-09-05。置換対象を複数行の`\n`文字列で指定したが作業ツリーはCRLFなので置換は0件で終わりファイルは無傷のままテストが走り「変異を入れたのに緑」という逆の結論になった。Pythonの`open(..., encoding="utf-8")`はユニバーサル改行で`\n`に見えるが`newline=""`で読めば`\r\n`が入っている)③`git checkout -- <path>`が1ファイルだけCRLFで書き戻す(2026-09-06。LFだったファイルを巻き戻すとそのファイルだけCRLFになり、行を配列にして切り貼りするスクリプト(`line == '}'`のような完全一致)が`'}\r'`になって落ちる)。**守り方**: 複数行にまたがる完全一致置換の前にそのファイルの行末を見る。文字列置換は必ず件数をassertする(`assert s.count(old) == 1`)。行末を変えたくないなら`newline=""`で読み書きし`\r\n`↔`\n`の正規化を1箇所に閉じる(`newline="\n"`で保存すると作業ツリーだけLFになり、gitは正規化するので差分は正しく出るが並行セッションの差分表示や他ツールが汚れる)。変異チェックで「緑のまま」が出たらテストを疑う前に変異が入ったかを確かめる(`git diff`で1行でも変わっているか見る)。検出は`python -c "d=open(p,'rb').read(); print(d.count(b'\r\n'), d.count(b'\n'))"`。`git checkout`の直後は`\r\n`→`\n`へ戻してから作業を続ける。
- **生のNULバイトを1つ書くとgitがファイルをバイナリ扱いする**(落とし穴・2026-08-15実測)。`web/src/viewport.ts`に面の強調でキーを突き合わせる区切りとして生のNULバイトが2個書かれていた(エスケープ表記ではなく文字そのもの)。実行時は正しく動く(JSの文字列はNULを含められる)が、道具の側が壊れる: gitがNULを見てバイナリと判定(先頭8000バイトの走査、`git ls-files --eol`が`i/-text`)、その結果`git diff`も`git blame`も効かず`git log -p`は「Binary files differ」しか出さない、`core.autocrlf`の正規化も止まる(他ファイルはgitがLFへ直すがこのファイルだけ書いたツールの改行がそのまま格納される)。しかもこのファイルはリポジトリで最もchurnの激しいファイル(three.jsの囲い)で、差分が読めない状態が5日以上続いていたが動作には出ないため誰も気づかなかった。**直し方**: Unicodeのエスケープ表記へ置き換える(実行時の値は同じ)——これでテキストに戻りdiff・blame・改行の正規化が全て効くようになる。**見つけ方**: `git ls-files --eol`に`i/-text`が出ているテキストファイルを疑う。`git diff --stat`と`git diff --ignore-all-space --stat`が桁違いなのも同じ兆候。
- **実装を差し替えたとき嘘になるドキュメントは新しい名前でgrepしても出てこない**(運用知見・2026-09-07)。duocadで`BRepBndLib::Add`を`AddOptimal`へ差し替えたとき`grep AddOptimal`では見つからないのに嘘になった記述が2種類あった: ①捨てた側の名前で書かれている記述(「ガードは`_shape_bbox_trimmed`へ移した」。`grep _shape_bbox_trimmed`で出る)②速さの根拠として置いてあった実測値(「`False`は実物STEP(231面)で0.003秒」。`Add`の測定値だが文中に`Add`の語が無く、差し替えで実測が3桁変わったのにgrepのどの語にも引っかからない)。**対処**: 実装の差し替えでドキュメントを掃くときは「新しい名前」ではなく「捨てた側の名前」と「その節に書いてある数値の根拠」で探す。数値は「何を測ったものか」を書いておくと差し替えのときに掃ける(逆に書いていないと誰も直せないまま嘘が残る)。
