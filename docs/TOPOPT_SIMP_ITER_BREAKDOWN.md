# SIMP 1反復の時間内訳（hanger 2.4mm）

**この文書の役割:** `simp.optimize` の**設計反復1回**に何秒掛かり、塊を小さくしても下がらない理由と、
秒数の主な寄与先をまとめたもの。**実測の正**は `duocad/topopt/output/simp_convergence_hanger_2.4mm.json`
と `topopt_checks/profile_simp_iter_breakdown.py` の出力。

---

## 現象

`models/hanger_bar_attachment.json`・要素サイズ **2.4mm**・連続値保持（既定導出）で SIMP を回すと、
**材料量を下げて塊を小さくしても、1反復あたりの秒数は大きくは下がらない**。

本番経路（`optimize_run.run()` → `safety_loop` → `run_topopt`）は `threads` を渡さないので、
`simp.PARALLEL_THREADS`（この機械では **7** = 論理コア14の半分）で動く。
その条件下では **おおよそ 30〜35秒/反復** が床と観測される。

`topopt_checks/measure_simp_convergence.py` は並列測定の公平性のため **`threads=1`** 固定で回す。
同じ題材・同じ格子でも **1反復はおおよそ 100〜130秒** になり、本番の 3〜4倍遅い
（並列は matvec だけ効き、RAP/`splu` は直列のまま —— [TOPOPT.md](TOPOPT.md)「CPU並列化」）。

## 1反復で何をしているか

```
simp.optimize() の for it in 1..max_iter:
  ├─ model.solve(x_phys)          … K組立 + mg_setup + CG/V-cycle  （最大）
  ├─ model.compliance()           … 小さい
  ├─ 感度 dc, dv
  ├─ _filter_conv ×2 (dcn, dvn)   … 全格子 (nelx×nely×nelz)
  └─ OC 体積制約の二分探索
       └─ 各ステップ: _physical(xnew) → _filter_conv … 全格子
  └─ x_phys = _physical(x)        … また全格子
```

コード: `duocad/topopt/simp.py` の `optimize`（設計反復ループ）、`Model.solve`、`_filter_conv`。

## 塊を小さくしても秒数が下がらない理由

### 1. 格子サイズは材料量と無関係

連続値保持では、探索中のすべての評価が **同じ `reference.base.grid`**（案1の外接直方体）を使う。
`void_mask` で塊の外を空要素にするだけで、**配列の形状は常に 78×138×109**。

密度フィルタ `_filter_conv` は **常に全箱要素**に畳み込む。塊が 144k 要素でも 1.17M 箱の
コストは変わらない。

### 2. 線形方程式の規模もほぼ一定

節点自由度は **約 3,624,000**（hanger 2.4mm 実測。材料量を変えても同オーダー）。
空要素にしか接していない節点は `extra_fixed_dofs` で拘束に回すが、
**自由 DOF の桁は縮まない**。

塊が小さいと `active_mask` で **K の非零の数**は減るが、CG/V-cycle は格子全体の
前処理構造を使うため、秒数は **下がるが線形には下がらない**（実測: 塊7.6倍で秒2.7倍）。

### 3. 毎反復 MG の組み直し

マルチグリッドは **密度が変わるたびに** 各段の RAP と最粗格子の LU を組み直す
（`simp._mg_setup`）。これはスレッド並列化できない（[TOPOPT.md](TOPOPT.md) 実測）。
全塊プロファイルでは solve の **約8%** が `mg_setup` 単体。

### 4. 体積制約 OC がフィルタを繰り返す

OC 更新の二分探索（`while (l2-l1)/(l1+l2) > 1e-9`）の**各ステップ**で
`_physical()` → 全格子フィルタ。塊の大きさに依存せず、**反復あたりの呼び出し回数**が効く。

## 秒数の見積もりとの関係

`optimize_run.SECONDS_PER_ELEMENT_ITERATION = 1.8e-4` は
「秒 / (格子要素数 × 設計反復)」の桁取り用係数（[TOPOPT.md](TOPOPT.md)「予想時間の係数の作り方」）。

最小塊 144,790 要素 × 1.8e-4 ≈ **26秒/反復**（threads=1 の solve 寄与の見積もり）。
実測平均 125秒には OC・フィルタ多回・MG 組み直し・CG 反復数が上乗せされる。
本番 7 スレッドでは matvec 部分が短縮され、**床 30〜35秒** 付近に落ち着く。

## 短縮の当たり所（1反復の中身に対して）

[TOPOPT_SPEED.md](TOPOPT_SPEED.md) の外側ループ短縮と併せて、**1反復を軽くする**候補:

| 優先 | 案 | 効き | 難度 |
|---|---|---|---|
| 1 | **格子を粗くする**（2.4mm → 4.4mm 等） | 箱要素数が桁で減る。SIMP は解像度に強依存 | 画面・契約 |
| 2 | **MG setup の再利用**（密度変化が小さい反復では RAP/LU をスキップ） | solve の数〜十数% | 中 |
| 3 | **OC 二分探索のフィルタ回数削減**（初期値・打ち切り・フィルタ結果の再利用） | 数秒〜十数秒/反復 | 中 |
| 4 | **`threads` の調整** | 半コア付近が最良（[TOPOPT.md](TOPOPT.md)）。RAP は効かない | 低 |
| 5 | `cg_rtol` 緩和 | 全体 ~16% 程度。精度トレードオフ | 低（未着手） |

**効きが小さいもの:** mesh/STL（評価の 0.01%）、`build_anchors`（0.5%）——
[TOPOPT_SPEED.md](TOPOPT_SPEED.md) の内訳表どおり。

案3 の大きさは実測してある: `hanger_test.json` 2.4mm（322,384要素・`threads=7`）で
**OC の二分探索は 1反復あたり 7.87〜8.36秒＝1反復の 20〜25%**。
**MMA の更新則ならこれが 0.93〜1.01秒（3%）になる**（フィルタを掛け直さないため）——
[TOPOPT_MMA_VS_OC.md](TOPOPT_MMA_VS_OC.md)。

## 移設ノート（context-engineから、2026-09-12）

### 3D SIMPはウォームスタートしたCGで解く(2026-08-29実測)

`probe_topopt`実測(numpy 2.4.6/scipy 1.17.1、片持ち梁・volfrac 0.3・penal 3・rmin 1.5)。格子40x16x16(10,240要素/35,547 DOF)の1反復所要: `spsolve` 7.1秒、`splu`(`permc_spec='MMD_AT_PLUS_A'`)6.3秒、**CG+対角(Jacobi)前処理+前回のUをx0に渡す 1.4〜2.1秒**(CG内部200〜300反復)。直接解法だと60反復で7分超だがCGなら約2分。ウォームスタートが効くのは密度がゆっくりしか変わらないため。

**`rtol`は1e-9にする(1e-6では足りない)**。荷重・拘束をz対称に置いたときの密度場の対称性検査(相対誤差1e-6以内)で、rtol=1e-6だと60反復での非対称さが1.7e-07(許容1e-6に対し余裕6倍)まで育つのに対し、rtol=1e-9では1.0e-09に収まる(所要は+13%だけ)。CGの停止判定は内積の丸めが解法ごとに違う経路を通るため対称な問題でも解は厳密には対称にならず反復を重ねるほどずれが育つ。コンプライアンスの値はrtol 1e-6と1e-9で一致(15.7709) — 締めて損をするのは速度だけ。

### 性能測定はCG反復数を第一の物差しにする(2026-09-04〜10実測)

同一セッション内で同じ設定を撮り直すと、**CG反復数は8回のsolveが1つ残らず一致**(コンプライアンスも下6桁まで同じ)する一方、**秒は1.00〜1.16倍振れる**(4題材で1.10/1.00/1.09/1.16)。したがって前処理・解法の改良はCG反復数の差で主張し、秒は補助にする。秒を出すときは1回の実行内の設計反復から分布を取り**中央値**(1反復目はx0=0からの求解で極端に遅いため平均は歪む。実測7.26秒対中央値4.93秒)を使い、最小〜最大を併記して、その幅より小さい差を「速くなった」と言わない。

**時間を空けると壁時計は最大15%動く(2026-09-10実測)**。ビット単位に同じ答えを返す同じ計算を20:02と22:22に測ると、1反復秒の中央値が-16%/-16%/+2%動いた(threads=1・1反復1秒前後の規模)。322k要素・threads=7・1反復30秒規模では2回の測定が32.8秒/33.0秒で揃った。**小さい題材の壁時計比較は±15%の幅で読み、倍率を1回の実測から書かない — 向き(どちらが小さいか)が複数ケースで揃っているかを見る。** 同じrun内の内訳(ある関数が1反復の何%を占めるか)はこの幅を受けない。並列化は秒に出て反復数には出ない、マルチグリッドは反復数に出る — 両方の欄を出さないとどちらが効いたか切り分けられない。

### COO→CSCの位置表はsearchsortedで作る(2026-09-08実測)

疎パターン固定・`data`だけ更新する組み立て(COO→CSC)で、COOの各項がCSCの`data`のどこへ行くかの表`pos`の作り方(duocad・hangerの剛性行列で実測): `np.lexsort((rows,cols))`(従来)は8.19mmで0.430秒/+196.5MB、5.37mmで1.262秒/+834.6MB。**`searchsorted`(COO側を分割)**は8.19mmで0.600秒/+77.2MB、5.37mmで2.034秒/+296.0MB。**鍵**: CSCの(列,行)は全体として昇順に並んでいるので「列×ndof+行」を鍵に1本の`np.searchsorted`で引ける(列ごとの切り出し不要)。一時領域が「項数×8バイト」から「非零数×8バイト」へ落ちる(比はZ/E=非零数÷項数、3次元8節点要素の連続した塊なら0.44前後)。COO側をチャンクに切ると探索の一時が「分割幅×8バイト」に固定される。**代償は構築時間1.4〜1.6倍だが設計反復40回に対し構築は1回なので全体では0.3〜0.6%** — 一時領域を取るほうが得。`pos`はint32で持てる(非零数が2^31未満なら)。足し込みは`np.bincount(pos, weights=vals, minlength=nnz)`の1パスが速い(整列済み並びへ`vals[order]`で並べ替えてから`np.add.reduceat`する書き方はdoubleのランダムアクセスコピーぶん遅い)。

### matrix-freeのK·vは3条件が全部揃わないと疎matvecに勝てない(2026-09-08実測)

duocad SIMPでKを作らずK_ff·vを計算する実装を4通り測定(hanger 5.37mm・active 34,910・自由度118,083・nnz 8.83M)。「要素ブロック+触る自由度の帯だけ返す」が7スレッドで1.567ms・12スレッドで1.406ms、対して疎(本番の`_BlockedMatvec`)は7スレッドで2.210ms・12スレッドで1.879ms。**3つとも要る、1つ欠けると本番より遅い**: (1)gatherもscatterも選択行列(疎行列×密ベクトル)で書く — numpyのインデクシング(`ve[idx]`/`np.bincount`)はGILを握ったままなのでスレッドで割っても速くならないが、scipyのCSR行列ベクトル積はC実装でGILを解放する(並列化の唯一の入口)。(2)要素ブロックへ割る(行列を持たないので行ブロック分割`_BlockedMatvec`は使えない)。(3)各ブロックが返すのは「そのブロックが触る自由度の帯」だけにする(自由度数ぶんのベクトルをスレッド数だけ作って足し合わせると集約自体が律速になる。12スレッドで3.92ms対1.41ms)。密度はscatter側の値へ畳み込む(密度が変わるたびに作り直す必要がある)。

4測定点での最終比(matrix-free/疎、それぞれ最良スレッド数)は**0.67〜0.92でmatrix-freeのほうが速い**。メモリは選択行列2本11.3MB対疎56.9MB(`kf` 28.5MB+`_BlockedMatvec`の行ブロック写し28.4MB)で5.0倍少ない(hanger 8.19mm)。数値は疎との相対差5.6e-16〜1.0e-15。**ただし本番へ採用したのはvoid除去だけで、matrix-freeは導入していない。**

### マルチグリッドの段数チューニングは一様密度で当たりを取ってはいけない(2026-09-04実測)

幾何マルチグリッド前処理の既定値(段数・平滑化回数・最粗格子の大きさ)を**一様密度`rho=0.5`で測って決めようとして1時間溶かした**。同じ片持ち梁32x16x16で階層の段数だけを変えたCG反復数: 一様密度では1段14/2段16/3段17/4段18(段を増やしてもほぼ増えない=教科書どおり効く)。**設計反復を12回まわした実密度では1段17/2段33/3段53/4段69**(段ごとに1.5〜2倍に劣化)。効き方を決めているのはSIMPの`emin=1e-9`と`penal=3`が作る10^9倍の剛性差で、これは設計が二値へ寄ってから出てくる。一様密度には剛性差が無いため粗格子が細格子と同じ問題になり何をしても効いてしまう。**教訓: 前処理・反復解法の当たりを「解きやすい入力」で取ってはいけない** — 当たり取りの入力は本番と同じ条件数でなければ順位そのものが入れ替わる(上の表は「深いほど良い」と「浅いほど良い」で結論が逆になる)。

関連する一般則: マルチグリッド前処理は壊れていてもCGは正しい答えに収束する(遅くなるだけ)ので「答えが合っている」は実装の正しさの証拠にならない。部品を意図的に劣化させて反復数が増えることを検査に入れる必要がある(実測で粗格子補正を捨てると18→217回になった。増えないならその部品は最初から効いていない)。

### void要素を組み立てから外すとCG反復数が題材によって増減する(2026-09-08実測)

void要素(ρ=0固定)を組み立てから外すと、`_floating_dofs`が既に浮いた節点を拘束へ回しているため**未知数は1つも減らず最終形状も同じ**(5測定点でρ>=0.5の一致率100.0000%・コンプライアンス相対差3e-6〜3e-5)。しかし**Kそのものは変わる**(emin媒質の寄与が消える)ためCGの反復数が動く: bracket n=40で20.9→24.9回/solve(+19%)、hanger 5.37mmで35.0→36.5回(+4%)、hanger 8.19mm/6.59mm/tilted n=40は変化なし、hanger rmin=8mmの完全な安全率探索(447 solve)は16,145→15,263回(合計、-5.5%)。**符号が題材で変わる** — bracketでは反復数の増加が組み立ての節約をほぼ食い潰し、全体は98.2%(他の題材は79〜85%)にしかならなかった。**「void除去は数値的に無害」は形の話であって費用の話ではない** — 組み立て方を変える案を評価するときは秒数だけでなくCG反復数を必ず並べて見ること。
