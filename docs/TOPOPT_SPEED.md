## 背景：1回の「形状最適化実行」で何に時間が掛かるか

画面で実行ボタンを1回押すと `optimize_run.run()` が走る。重い部分はほぼすべて
**安全率 → 材料量の探索**（`safety_loop`）である。

```
optimize_run.run()
  ├─ 事前チェック（案1 bbox 導出・条件面・保持/除外） … 数秒未満
  ├─ safety_loop
  │    ├─ 参照 run（1回・10反復）           … 全体の ~4%
  │    └─ 材料量探索（典型6評価 × 40反復）   … 全体の ~96%
  └─ メッシュ化 + add_mesh_body              … 数秒未満
```

`estimate_seconds()` のモデル（`optimize_run.py`）:

- 1評価 ≒ `DEFAULT_MAX_ITER`(40) × 格子要素数 × 係数
- 参照 run ≒ `REFERENCE_MAX_ITER`(10) × 格子要素数 × 係数
- 典型合計 ≒ 参照 + 6 × 1評価（`TYPICAL_EVALUATIONS = 6`）

実測。**題材と要素サイズを必ず添えて読むこと** —— 比率（参照 ~4% / 探索 ~96%）は解像度に
依らないが、**秒数は解像度で1桁変わる**。

`hanger_bar_attachment.json` / **要素サイズ 5.333mm**（98,606要素）:

| 内訳 | 秒（目安） | 比率 |
|---|---|---|
| 参照 run（10反復） | 91.5 | ~4% |
| 6評価 × 本番 SIMP（40反復） | ~1,940 | ~96% |
| **合計** | ~2,030（34分） | 100% |

**本番の作業解像度は 2.4mm であり、そこでは合計が時間単位になる**（2026-09-10 実測）:

| 題材 / 要素サイズ | 箱内要素 | 1反復 | 峰メモリ | 探索1回（参照+8〜10評価） |
|---|---|---|---|---|
| `hanger_test` / **2.4mm**（検証用） | 322,384 | 45.5秒 | 8.3GB | **3〜5時間** |
| `hanger_bar_attachment` / 2.4mm | 1,096,894 | 159.8秒 | 26.1GB | **8時間級** |

**検証は `hanger_test` の 2.4mm を使う**（本人決定 2026-09-10。同じ部品を密集させたもので、
条件の構成は同一・箱が3.4倍小さい）。

1評価の中身（[TOPOPT.md](TOPOPT.md)「端から端まで1回の内訳」）:

| 段 | 割合 |
|---|---|
| `simp.optimize` | **99.5%** |
| `build_anchors` | 0.5% |
| marching cubes + Taubin | 0.01% |

**結論:** 短縮の主戦場は **探索の評価回数を減らす** ことと、**各評価の SIMP 反復数を減らす**
こと。mesh/STL・derive 単体の削減は副次。

## 現状の探索アルゴリズム

入口: `safety_loop.solve_for_safety_factor`（`duocad/topopt/safety_loop.py`）。

### 探しているもの

利用者入力は**目標安全率**。内部では**材料量[mm³]** を動かす。

> **目標安全率以上を満たす最小の材料量**（「ぴったり目標」ではない）

数学的には `f(m) = safety_factor(m) − target` について、括り `[material_min, material_max]` 内で
`f(m) ≥ 0` となる**最小の m** を求める。上端は `f(hi) ≥ 0` が保証される。

### 手順（現状）

1. **参照 run を1回**（連続値保持の ρ。探索全体で使い回す）
2. **上端 `material_max` を評価** —— 届かなければ `SafetyTargetError`
3. **下端 `material_min` を評価** —— ここで既に目標を満たせば **探索本体はスキップ**
4. **探索本体** —— 次の候補材料量の決め方は `searcher`（既定は括り付きの補間。下記「実装済み A」。
   `"bisection"` なら `mid = (lo + hi) / 2`）。**括りの更新は探索器に依らない**:
   - `ok` かつ `sf ≥ target` → `hi = mid`、best 更新
   - `ok` かつ `sf < target` → `lo = mid`
   - `too_little` → `lo = mid`
   - `too_much` → `hi = mid`
5. 停止: `(hi − lo) / hi ≤ rel_tol`（既定 **0.08**）または `max_evaluations`（既定 **15**）

### 現状のパラメータ（[TOPOPT.md](TOPOPT.md)「収束条件と回数上限」）

| パラメータ | 既定 | 備考 |
|---|---|---|
| `rel_tol` | 0.08 | **技術的根拠は無い**。評価回数を2回減らすために選んだ（9→7回の実測。**2026-09-09 のコードでの値** —— 同じ題材の 2026-09-12 は6回） |
| `max_evaluations` | 15 | 境界2 + 探索本体。8% までなら典型6回で足りる余裕 |
| `DEFAULT_MAX_ITER` | 40 | 各評価の SIMP 反復数 |
| `REFERENCE_MAX_ITER` | 10 | 参照 run のみ |

### 前提と罠

- **材料量 ↑ → 安全率 ↑** を前提（単調性）。合成題材では実測済みだが**理論保証はない**
  （plate の頭打ち、非連結など —— [TOPOPT.md](TOPOPT.md)「単調性を測る」）。
- 評価後の **`safety_factor` は次候補の決定に使う**（既定の補間。`searcher="bisection"` では
  符号しか見ない）。
- 塊は材料量で離散化される（連続値保持）。`rel_tol` より細かく詰めても意味が薄い、という
  議論も [TOPOPT.md](TOPOPT.md) にある。

## 実装済み A：探索アルゴリズム（二分 → 括り付き補間）

**2026-09-12 実装。既定は `safety_loop.solve_for_safety_factor(searcher="illinois")`。**
結論を先に書く（数字は下記「実測」）:

| 何を狙ったか | bracket 題材でどうなったか |
|---|---|
| 評価回数を 1〜2 減らす | **減らなかった** —— 4つの目標のうち3つで同数、1つで **+1** |
| 採用材料量・安全率を悪化させない | 採用材料量は**常に 1.2〜2.7% 軽い**（契約は「目標以上で最小」なので改善側）。安全率は両者とも目標以上 |

### 動機（実装前の見立て）と、その誤り

見立て: 上端の安全率が目標の数百〜数千倍（bracket 実測で 5529 vs 目標 2.0 など）のとき、
**中点評価はまだ sf ≫ target** になり、高材料量の SIMP を無駄に回す。評価ごとに
`report.safety_factor` は取れているのに**捨てている**、というもの。

**この見立ては bracket では成立しない。** 括りの下端（塊容量の 15% = 52,786mm³）の安全率が
**1,832.55** あるので、目標がそれ以下なら**下端の評価でそのまま採用されて探索本体に入らない**
（上の「手順（現状）」の3。評価2回で終わる）。「5529 vs 目標 2.0」はまさにこの場合で、
**二分は1回も無駄を踏んでいない**。探索本体に入るのは目標が `sf(下端)` と `sf(上端)` の間に
あるときだけである。

**したがって「上端の sf が目標の何倍か」は無駄の指標にならない。** 効くのは
**`sf(上端) / sf(下端)`**（括りの中で安全率が何倍動くか）で、bracket ではこれが **3.3倍**しかない。

### 前提: 安全率の偏りは補間を歪めない（2026-09-12 実測）

**この案は安全率の「大きさ」を使う。** いまの二分は**符号**しか使っていないので、
「安全率が信用できるか」はこの案で初めて前提になる。そして
[TOPOPT.md](TOPOPT.md)「40反復では収束していない」のとおり、**`DEFAULT_MAX_ITER`(40) の
安全率は収束していない**。

`hanger_test` 2.412mm・`PICK_RATIO=0.08`(塊 25,791要素)で、材料量3点をそれぞれ120反復
回し、**同じ run の40反復時点と120反復時点**で安全率を測った（別 run を並べるとばらつきが
混ざる。40反復時点の ρ は `run_topopt(progress=...)` で控える）:

| 材料[mm³] | 充填率 | sf(40) | sf(120) | 比 | C比 |
|---|---|---|---|---|---|
| 45,000 | 12.4% | 0.7593 | 0.8106 | **0.9367** | 1.0597 |
| 70,634.5 | 19.5% | 2.6049 | 2.6548 | **0.9812** | 1.0250 |
| 110,000 | 30.4% | 4.8213 | 4.9519 | **0.9736** | 1.0163 |

**比は一定ではない（開き 4.74%）。** 痩せた側ほど偏りが大きく（6.3% 対 1.9〜2.6%）、
しかも**単調ではない**（中央がいちばん小さい）。安全率は常に低く出る＝**保守側**。

それでも**補間の提案位置はほとんど動かない**。上の括り `[45,000, 110,000]` で計算すると:

| 目標 sf | 真値(120反復)での提案 | 40反復での提案 | ずれ |
|---|---|---|---|
| 1.0 | 47,973 | 48,852 | +1.4% |
| 2.0 | 63,668 | 64,854 | **+1.9%** |
| 4.0 | 95,059 | 96,858 | +1.9% |

**括りの約2%、しかも材料が多い側（保守側）へ倒れる。** 停止条件 `rel_tol = 0.08` の
**4分の1**なので、評価が1回増えることもほとんどない。

機序: 偏りは `sf_lo` だけでなく `sf_hi` にも乗り、**絶対値では高い側のほうが大きく下がる**
（0.1306 対 0.0513）ので、分子 `target − sf_lo` と分母 `sf_hi − sf_lo` の歪みが部分的に
打ち消し合う。**「痩せた端の偏りが最大だから補間が壊れる」は誤り** —— 比ではなく差で効くので、
絶対値の大きい端の寄与が勝つ。

**したがって「偏りがあるからこの案を薄める」方向の設計変更は要らない。**

### 採用したアルゴリズム: Regula Falsi + Illinois ハイブリッド

**Regula Falsi（割線法）:** 括り `[lo, hi]` と両端の `(sf_lo, sf_hi)` から、
sf が target になる材料量を線形補間する。

```
m_next = lo + (hi − lo) × (target − sf_lo) / (sf_hi − sf_lo)
```

- 目標から遠い → **lo 側に大きく寄る**（二分より早く「軽い側」を探せる）
- 近い → **小さく動く**（細かく詰める）

**Illinois:** Regula Falsi で同じ端点だけが更新され続けるとき、
その側の sf を半分にずらして二分に近い挙動へ落とす（粘り対策）。

**実装（`safety_loop._propose_material`）:**

1. 端点2回の評価は従来どおり（`proposed_by="bound"`）
2. 以降は上の式で提案し、**`[lo + 0.15×(hi−lo), lo + 0.85×(hi−lo)]` にクリップ**する
   （`lo` 極近傍への張り付きの緩和。比率 15/85 は経験値で、実測で調整する足場は下の表）
3. Illinois は、**同じ端点が続けて据え置かれた回数 k に対し、その端点の `f = sf − target` を
   `2^(k−1)` 分の1**にする。**`too_little` / `too_much` で括りが動いたときは数え直す** ——
   安全率が測れていない更新は「割線が粘っている」証拠ではなく、数えたままにすると
   復帰後の1手が材料の多い側へ強く引かれる（探しているのは最小の材料量である）
4. 次のいずれかなら **その回だけ二分** `(lo+hi)/2` に落ちる。理由は
   `SafetyLoopStep.fallback_reason` に残る:

| `fallback_reason` | 条件 |
|---|---|
| `unmeasured_endpoint` | 端点の安全率が測れていない —— **`too_little` / `too_much` の直後**。括りは `lo=mid` / `hi=mid` で更新されるが sf は計測不能で、古い `sf_lo` / `sf_hi` を使うと**括りの外へ提案が飛ぶ**。下端が `too_little` で括りに入った場合も同じ |
| `degenerate_slope` | `sf_hi − sf_lo` が極小（除算が不安定） |
| `at_bracket_edge` | 提案が `lo` / `hi` と実質同じ（再評価になる） |
| `already_evaluated` | 履歴と同じ材料量（振動） |

5. **`too_little` / `too_much` に擬似 sf（例: 0）を返して補間に使わない** —— 非連結境界で sf が
   不連続ジャンプし、補間が非連結側に引きずられる（下記「採用しない」）
6. 停止条件は **`rel_tol` on 材料量幅**のまま。**この実装では動かしていない** —— 探索器と停止条件を
   同時に変えると、回数が動いた理由がどちらか分からなくなる。**Dual Criteria**（下記 B0'）は未着手

**呼び出し側が見るもの**（`result.history` の各 `SafetyLoopStep`）:
`proposed_by`（`"bound"` / `"illinois"` / `"bisection"`）・`fallback_reason`・`clipped`。
`optimize_run.run()` が返す `history` にも同じ3つが載るので、**実行が終わったあとでも
「補間が効いたのか二分に落ちていたのか」を追える**。
**`searcher="bisection"` で従来の二分に戻せる**（受入と実測の基準線。既定は `"illinois"`）。

### 採用しない: `too_little` / `too_much` でも安全率を返す

FEA が解けない（`DesignSpaceDisconnectedError`）か、体積目標に届かない（`VolumeTargetError`）評価に
擬似 sf を載せても、**単調性と物理対応が壊れる**だけ。例外分類して括りだけ更新する現行契約を維持する。

### 使わない方がよいもの

| 手法 | 理由 |
|---|---|
| ニュートン法 | `f'(m)` が無い。1評価 = フル SIMP |
| 括りなし secant | 範囲外・`too_much` 処理が崩れる |
| Brent 法 | 堅牢だが評価回数削減より安定性優先。ここでは得が薄い |

### 実測（2026-09-12）

**環境:** Windows 11 / 論理コア14 / 物理メモリ 31.7GB / Python 3.11.15 / numpy 2.4.6。
8ケース（4目標 × 2探索器）を**1プロセスで逐次**に回した（同時に重い処理は走らせていない）。

**題材:** bracket（`design_space.demo_conditions`）/ `elements_long_axis=20`（`bench.SAFETY_LOOP`）/
塊容量 **351,910mm³** / 括り **[52,786, 246,337]mm³**（容量の 15%〜70%。`check_safety_loop.py` [3] と同じ）/
各評価の SIMP 反復 **20** / `rel_tol=0.08` / `max_evaluations=15` / クリップ **0.15〜0.85**。
塊は候補ごとに導出し直すので要素数は 1,487（下端）〜3,336（上端）。

**生データ:** `duocad/topopt/output/safety_search.json`（8ケース・全55評価の材料量・分類・安全率・
`proposed_by` / `fallback_reason` / `clipped` ・経過秒）。取り直しは
`.\.venv\Scripts\python.exe topopt_checks\measure_safety_search.py`。

**括りの端の安全率:** `sf(52,786) = 1,832.55` / `sf(246,337) = 6,026.28`。
**目標は探索本体に入る範囲でしか振れない**ので、この4つがこの題材で取れる全部である。

| 目標 sf | 上端/目標 | 評価回数 二分 → Illinois | 採用材料量 二分 → Illinois [mm³] | 差 | 安全率 二分 / Illinois |
|---|---|---|---|---|---|
| 3,500 | 1.72 | **8 → 8** | 70,932 → 69,869 | **−1.50%** | 3,750.5 / 3,578.4 |
| 4,500 | 1.34 | **7 → 8** | 107,223 → 105,492 | **−1.61%** | 4,623.2 / 4,568.5 |
| 5,500 | 1.10 | **6 → 6** | 197,949 → 192,627 | **−2.69%** | 5,793.5 / 5,640.4 |
| 5,900 | 1.02 | **6 → 6** | 210,046 → 207,487 | **−1.22%** | 5,965.6 / 5,960.8 |
| **合計** | | **27 → 28** | | | |

**フォールバックは1回も発火していない**（8ケース・全55評価）。4条件のどれにも当たらなかった
＝ この括りでは `too_little` / `too_much` が出ず、割線の分母も退化しなかったということで、
**「フォールバックしっぱなしで利得が出ない」ではない**。
**クリップ（0.15/0.85）は Illinois 側で 6回**当たった（目標 3,500 で1回・5,500 で3回・5,900 で2回）。
1つの solve（参照 run + 6〜8評価）は 33〜39秒。

#### なぜ評価回数が減らなかったか

**安全率は材料量に対して凹である。** 実測の傾き `Δsf / Δ材料` は
**0.106 → 0.023 → 0.017 → 0.011 → 0.005** と **22倍**変わる。端点を結ぶ直線（割線）は
常に真の曲線の**下**を通るので、割線が目標に当たる位置は**真の答えより材料の多い側**に出る。
結果として Illinois は**上からだけ**括りを詰める（目標 4,500 では
175,895 → 144,050 → 113,782 → 91,778 と4手かけて初めて目標の下へ抜けた）。
Illinois の減衰は同じ端点が**2回続けて**据え置かれてから効くので、そこで取り返す 1〜2手ぶんが、
二分が毎回きっかり半分に割る速さとほぼ相殺する。

**利得が出たのは回数ではなく答えの質だった。** 契約は「目標以上を満たす**最小**」なので、
同じ評価回数で 1.2〜2.7% 軽い材料量を返すのは改善である（`rel_tol = 0.08` の 15〜34%ぶん）。

#### 次に手を付けるなら

- **`log(m)` 軸での補間**（もとは下の「オプション」だった案）。上の凹みは対数軸で目に見えて
  小さくなる —— `Δsf / Δln(m)` は **6,488 → 1,952 → 2,114 → 1,869 → 1,065** で、
  最大/最小が **6.1倍**（線形軸は 22倍）、中央の3区間は 1,869〜2,114 の **1.13倍**に収まる。
  **未実測。**
- **`sf(上端)/sf(下端)` が桁で違う題材では未検証。** bracket は 3.3倍、hanger 級でも
  上の「前提」の表で 6.3倍（0.76〜4.82）しかない。**案Aが想定していた regime の題材を
  まだ持っていない**ので、本来の想定は机上のままである。
- **評価回数を減らしたいなら停止条件の側**（`rel_tol` / B0' Dual Criteria）。上の実測は
  「探索器だけを替えても回数は減らない」ことを示している。

## 実装時の受入の考え方

1. **採用材料量・安全率** — bracket 等の固定題材で、旧二分と **同程度またはより軽い** 材料量
   （悪化しないこと）。完全一致はボクセル量子化で要求しない。
2. **評価回数** — **減ることを当てにしない。** bracket の実測（「実装済み A」）では4つの目標の
   うち3つが同数・1つが **+1** だった。受入で見るのは「**二分より増えないこと**」を固定の1点
   （`check_safety_loop.py` [8]・目標 5,500）で、**全ての目標で増えないという主張ではない**。
   他の題材では `measure_safety_search.py` で測り直すこと。
3. **単調性が怪しい題材** — plate 等で `history` を見て安全率が逆行していないこと
   （[TOPOPT.md](TOPOPT.md) の留保どおり）。
4. **契約** — 探索目標は「以上で最小」のまま。`SafetyTargetError` / `too_little` / `too_much`
   の **3分類そのものは変えない**。Dual Criteria を入れる場合は **許容超過幅（例: 2%）** を
   仕様に明記。
   **※ MMA へ倒すときは「分類の作られ方」が変わる**（taskbox `20260910-1315`）——
   いまの `too_much` は `VolumeTargetError(side="above_capacity")`、すなわち **OC の
   ラグランジュ乗数の二分探索が退化したとき**に出る。MMA では体積が不等式制約になるので
   同じ出方をしない。**A が先に入っている（2026-09-12）。** 1315 が `too_much` の作られ方を
   変えるときに守るのは、**安全率を返さない評価では `f_lo` / `f_hi` を `None` にする**という
   一点である —— 分類の名前が同じでもこの配線を外すと、`_propose_material` が古い安全率で
   **括りの外へ提案する**（3分類そのものは保たれるので、本書の案は生き残る）。
5. **B5** — 最終 ρ に対する solve が走ること。`u` の再利用は **`u0` 経由のみ**（完全省略禁止）。
6. **Illinois** — `too_little` / `too_much` 直後に割線法を使わないこと（二分フォールバック）。

## 移設ノート（context-engineから、2026-09-12）

### 組み立て方式のメモリ比は「どこを測るか」で別物になる(2026-09-08実測)

疎パターン固定案(`pos`を持つ)とvoid除去だけの案のメモリ比: **組み立てのピークだけ**で測ると1.34倍(`pos`と構築の一時領域がそのまま比に出る)。**実行全体のピークRSS**(導出→40反復のsolve→メッシュ化)で測ると**1.035〜1.063倍**(5測定点。hanger 3解像度+bracket+tilted)。理由はsolve側のほうが大きいため — マルチグリッドの`_BlockedMatvec`は行列の約2倍を持ち、各段の作用素と`splu`も乗るので`pos`(21〜80MB)はそこに埋もれる。**「案Aは案Bよりメモリを食う」を組み立てのピークだけで言わないこと。** 実行全体のピークには385MB前後の固定の床(Python・OCCT・条件の三角形分割・塊の導出まで)があるため、ピークRSSのスケーリング指数も1を大きく下回る(N^0.60〜0.76)。床を引いた増分で取り直すとN^1.00〜1.10になり、行列の非零数の伸び(ほぼ線形)と揃う。

### 完走時間の引き算による費用見積もりは2,500倍外れた(2026-09-11実測)

「1評価36.6分−純SIMP24.1分=12.5分は塊の導出に払っている」という見積もりを立て、それを根拠に「塊を探索の中で1回だけ作る」最適化をタスク要件に入れたが、**実測するとその導出(`derive_from_reference`)は0.3秒だった**(hanger_bar_attachment・要素2.412mm・案1 1,096,894要素)。案1の塊を起こし直す`derive`と回廊の二分探索2本を足しても4.9秒 — **見積もりは2,500倍ずれていた**。36.6分と24.1分の残差にはメッシュ化・STL書き出し・応力評価など名前を付けていない工程が全部入っており、塊の導出はそのごく一部にすぎなかった。入れた最適化自体は無害だったが、「12.5分を省く」と信じて設計判断(控えを1件だけ持つ・キャッシュキーの設計)に重みを掛けたぶんは余計な複雑さとして残っている。**教訓: 完走時間の引き算で費用を特定の工程に帰属させる前に、その工程を単体で実測すること。**

### void除去をmainへ採用(2026-09-09決定)

4条件の比較(`mf/reports/topopt-assembly-strategies-comparison.md`)を受け、**条件2(void除去。`void_mask`のパッシブ要素を組み立てから外し`_iK`/`_jK`もactive要素ぶんしか確保しない)をmainへ入れる**と決定。切り替えフラグは残さない(比較用の`ASSEMBLY_STRATEGY`は持ち込まない)。**条件3(パターン固定)と条件4(matrix-free)は入れない**(実装はブランチ`topopt-assembly-comparison`にだけ残す)。比較の途中でAIが「条件3が条件2を支配するので条件2を落としてよい」と2度提案したがどちらも成立しなかった — 条件2と条件3は支配関係に無く、**メモリなら条件2・大きい問題の速度なら条件3**(組立時間が約6.5秒=全体の10%強を超えると条件3が勝つ)。本人は最も安く最も確実に効く条件2だけを採った。main投入後の実測は全体75.9%・ピークRSS49.7%(ブランチ実装とρがビット一致)。

### 設計空間(箱)を大きく取っても費用は下がらない、むしろ悪化する(2026-09-03〜05実測)

体積制約が絶対量なら材料の総量は固定されるので答えはほとんど変わらないが、**費用は下がらない** — SIMPが下げるのは密度だけで要素は格子に残り、毎反復すべての要素が剛性行列に入り全自由度が線形方程式に入る(要素を実際に系から外すアクティブセットの仕組みは無い)。むしろ悪化しうる: 「空要素にしか接していない節点は剛性eminでしか繋がらない浮いた自由度なのでK がほぼ特異になりCGが収束しない」という`_floating_dofs`のガードは`void_mask`から反復に入る前に一度だけ計算され、**最適化の途中でρが0になった領域はこの網にかからない**。

費用の外挿(部品60.1×154.0×100.6mm・60反復): 部品ぴったり(1.54mm・254k要素)1.8時間に対し、2倍の箱(同じ要素サイズ・2.04M要素)29時間、3倍の箱(6.88M要素)147時間。箱を大きくしたまま要素サイズを粗くする(6.16mm)と2倍の箱で7分・3倍の箱で34分に収まる。メモリも壁になる(264k自由度で1.57GB実測があるので、2倍の箱・同じ要素サイズは600万自由度で30GB級、このPCのRAM31.7GB)。**結論: でかい箱は要素が粗いときだけ払える** — 「大部分は勝手に削れるだろう」が成り立つのは粗い格子で1回回してから細かく仕上げる多重解像度の1段目そのものであり、多重解像度は「でかい箱案」の対案ではなくそれを払える形にしたもの。未検証のリスク: 絶対量とでかい箱を組み合わせると初期密度が極端に低くなり(箱が100倍なら初期ρは1/100)、荷重経路が最初から存在しない状態からのスタートで局所解に落ちる恐れがある(未実測)。逆向きの実測として、同じ格子のまま塊だけ縮めると自由度は減らないのに0.66倍に速くなる(空要素が増えてCGの収束が速くなるため)。

### hanger 2.4mmの費用は塊を縮めても頭打ちになる(2026-09-09実測)

`models/hanger_bar_attachment.json`(要素2.408mm・案1の箱1,096,894要素・容量15,307,281mm³・14スレッド34GB機、既定は連続値保持k=2.0)の1反復秒数(組立約98秒を除く): 材料8.419e6mm³(塊=箱)で136.5秒、4.220e6で68.8秒、2.121e6で52.8秒、1.071e6で44.2秒、5.463e5で37.9秒、2.839e5で40.5秒、1.526e5で35.4秒、8.704e4で33.6秒。**塊が小さくなっても34秒あたりで頭打ちになる**(材料量を半分にしても費用は2〜3割しか下がらない)。「要素数^1.30」で外挿すると小さい側で2倍近く外す(実測36.8分に対し予想21分)。床がある理由は未確認だが、連立方程式と多重格子の階層が**塊ではなく格子全体**(78×138×109)の上に組まれているためと見られる。峰メモリ26.1GB(事前の単発測定22.4GBに対し、探索を通すと3.7GB増える)。参照run(10反復・箱いっぱい)+上端評価(40反復)で7,256秒=2.02時間。

**安全率の曲線(目標2.0)は単調だが傾きが大きく揺れる**(材料量[mm³]→最小安全率: 8.419e6→650.19、4.220e6→435.21(前点比0.669)、2.121e6→284.14(0.653)、1.071e6→185.18(0.652)、5.463e5→106.53(0.575)、2.839e5→13.48(**0.127**)、1.526e5→6.71(0.498)、8.704e4→3.18(0.474))。**2点から外挿して交差点を当てようとすると必ず外す** — 実際650→435の2点から「答えは範囲の下端より2桁下」と読んだが、実際の交差は5.4e4〜8.7e4mm³(容量の0.35〜0.57%)だった。代表応力が「ρ>=0.5の要素の上位99.5%点」で位相が変わると跳ぶためと見られる。

### hanger_testは費用測定に使えるが病理の再現には使えない(2026-09-10〜11実測)

`models/hanger_test.json`は`hanger_bar_attachment.json`と条件構成が同一(拘束面3・荷重面1・保持ソリッド4・除外ソリッド7、保持の体積もほぼ同じ17,603 vs 18,558mm³)だが**外接直方体が3.2倍小さい**(容量4,655,592 vs 15,249,793mm³)。本人決定(2026-09-10、明言: 「同じ部品を使っているがより密集させることで速度を高めている。検証では何度も回すのでこちらを」)で検証用の実物モデルとした。

**限界(2026-09-11実測): 病理の再現には使えない。** `hanger_bar_attachment`を2.4mmで完走させると保持ソリッド(5mm厚の円盤)が浮き島になって`mesh.remove_islands`に消える病理が出るが、**`hanger_test`ではこの病理が1度も再現しない**(反力の内訳、荷重の合力を1としたときの各拘束面の受け持ち): hanger_test 5.319mm・材料10%で0.993/0.993/1.895(保持4/4生存)、5.319mm・30%で0.973/0.973/1.903(4/4)、3.989mm・30%で0.984/0.984/1.927(4/4)、2.412mm(本番)・30%で0.981/0.981/1.917(4/4)。対してhanger_bar_attachment 5.281mm・30%は0.842/0.842/1.668(9/9生存だが受け持ちの偏りが小さい)。**部品の配置を変えると取付点と荷重の距離関係が変わり荷重経路の選び方も変わる** — 速い代替題材は費用の測定には使えても病理の再現には使えないことがある。2026-09-11の追加実測で病理の引き金は「外接直方体に空きが多いこと」と判明し、箱を縮めたhanger_testは構造上これを出せないと確定した。**塊の導出に関する回帰の判定はhanger_bar_attachmentでしか止められない**が、比較の計測(pを振る等)には引き続きhanger_testを使う。

### 性能作業を配線の前へ繰り上げた判断(2026-09-04)

当初方針(第1段): 「パフォーマンスを詰めるのは一番最後(配線も終わった後)でいい」。しかし[[four-thirds-cost-law-is-the-jacobi-preconditioner]]の実測(費用の4/3乗は前処理の性質でマルチグリッドで指数ごと落ちる)が出た後、方針を訂正(第2段・本人明言): 「マルチグリッド化とCPU並列化を配線前にやる。どちらのタスクでもどれくらい高速化したかを調べるところまでをタスクとする。なお検証材料がいまブラケットの一つしかないので、これを3つ追加し4つにしてから着手してほしい」。順序は(1)検証セットを3つ追加→(2)マルチグリッド→(3)CPU並列化。**教訓**: 「性能は後でよい」は性能が定数倍の話であるうちは正しいが、指数(費用の伸び方そのもの)が変わるなら別 — 変数の微調整と費用の伸び方を変える作業を同じ「性能」の箱に入れない。測る前に順序を決めない(第1段は測定前、第2段は測定後の方針転換)。効果の測定までをタスクに含めるという指定が明示的にあった(実装だけ入れて「速くなったはず」で終わらせない)。題材が1つでは効果を測れないという理由づけを本人が先に出している。

### 環境依存で揺れる性能テストは閾値でなく注意書きで凌ぐ(2026-08-14判断・現在は対象テスト自体が削除済み)

`duocad/tests/test_incremental_update.py`の性能テスト(1000ms閾値)がコード無変更のままマシンの混雑で超過した(単独5回で942/961/973/1076/1164ms)。**選択: 閾値を上げる・テストを消すはしない、いったん放置する。** 対処として、無人drainが「性能回帰」と誤診しないための注意書きをテストのdocstringと`duocad/tests/README.md`の2箇所に追加(内容: 「この1本だけが赤いなら負荷。コードを直さず閾値も上げず、報告に負荷由来と書いて進める」)。理由: 実害は測定値そのものではなく赤が狼少年化して本物の性能回帰を見落とすこと。**このテストは2026-08-22に私物STEP依存として削除済みで、duocadのkernel時間の回帰を機械で見る手段は現在ひとつも無い**(根治案が必要なら合成形状で測り直すところから)。一般化として今も有効: 環境依存で揺れるテストは閾値をいじるより「揺れることを失敗の現場に書く」ほうが安い(閾値を緩めると測っている意味が消えるが、注意書きは測定を保ったまま誤診だけを防ぐ)。

### 予想時間は本番実測より2〜4倍長い側へ外れる(2026-09-05実測)、係数は実測へ寄せない判断

`optimize_run.estimate_seconds()`が返す予想時間は実測より2〜4倍長い側へ外れる。実測例: 12mm立方体2つ・48mm離し・rmin 6mm・4,225要素で予想191秒に対し実測46〜60秒。係数`SECONDS_PER_ELEMENT_ITERATION=1.8e-4`は実測の1.05e-4〜2.82e-4の中央付近から取ってあり、加えて安全率の二分探索が典型6回まで回る想定になっている(実際は早く収束すると評価回数が減る)。**係数を実測へ寄せて直さないという判断をした**: そもそも2〜3倍の幅で読む値だと`estimate["accuracy"]`にもコードにも書いてある。下振れ(予想より早く終わる)は害が小さいが上振れ側で外すと「10分と言われて30分待たされる」になり体験としてより悪い。題材依存が大きく1つの題材へ合わせると別の題材で逆へ外れる。画面(`OptimizePanel.svelte`)には幅であることを添えて出している。

| ピークRSS | +2,590MB | +1,287MB | 49.7% |
