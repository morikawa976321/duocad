# duocad — 画面と操作の判断

**読むとき**: パネル・ツールバー・コマンドの振る舞い・スケッチ入力・見た目を変えるとき。
3Dビューの内側（カメラ・ピック・グリッド・深度）は [VIEWPORT.md](VIEWPORT.md)。
操作手順・キー割当・ボタン文言の正は各コンポーネントのコメント（README §2）。ここに書くのは
**なぜそうしたか**と、コードから読めない判断だけ。

## 方針（README §0 の設計原則の下にあるもの）

- **常設の指標を置かない**（本人 2026-08-27。ヘッダの札を4つ一度に外したときの言い分）:
  実物を見れば分かるものに札を作らない（部品数は「ブラウザを見ればわかる」）／人の判断に使わない数は出さない
  （操作数）／札で補わないと伝わらない見え方は見え方の側を直す（プレビュー中の印は「プレビュー表示が
  いらないような設計を目指そう」）／状態は常時光らせず、人の手が要る瞬間に言う（接続状態は、操作したのに
  送れなかったときにトースト）。ヘッダ最上段は「どのファイル」と「書けているか」だけ。
- **既定状態は「見ているだけ」**（本人判断。2026-08-22 の逆の決定を覆した）。既定コマンドを常時構えさせない。
  押し出しが1手増えるのは承知のうえ。「通常モードにも『選ぶ』コマンドを新設して既定にする」案はボタンが増えるので却下。
  **確定に成功したら自動で無起動へ戻す**（本人 2026-08-31。連続作図・連続フィレットの操作性を失うのを承知で
  全 verb 共通。`set_parameter` / `import_step` / `undo` / `redo` は `CommandHost` を経由しないので対象外）。
  戻すのは**サーバの確認（`client_op` の一致）が返ってから** —— 楽観的発火と同時に落とすと、失敗応答で
  入力欄を復元しても欄自体が DOM から消えている（OCCT のフィレットは限界半径で失敗しうるので「打ち直す」が必須の流れ）。
- **現段階の duocad は複数パーツ運用を最適化しない**（本人 2026-08-23。パーツ一覧の pick 列と「選択したものだけ表示」を
  削除した理由）。「10や20の複数パーツを扱えるほどリッチな状態ではなく、現段階で考える必要のない懸念」。
- **一度決めたら触らない設定は設定ダイアログ1枚に平らに並べる。** スキーマ駆動・カテゴリ・タブのような
  「設定の仕組み」は作らない。作業中に切り替えるものはその場のパネル。見ながら決める設定（FOV）のために
  覆わない・暗くしない・即座に効く（「適用」ボタンを挟まない）。
- **プレビュー（確定前の幽霊）はつけられる操作には基本的にすべてつける**（本人 2026-09-05）。`move_body` の
  「幽霊は本体と重なって見分けが付かない」という旧判断は覆した（移動量が0でなければ別の場所に描ける）。
  方式は**ブラウザだけで描くローカル**（`preview: 'local'`）で、サーバの投機実行は増やしていない ——
  位置や図形しか変わらない verb は投機実行しても「形が変わった Body」が返らず応答が常に空になる。
- **モーダルを使わない。** 設定ダイアログは `show()`（非モーダル）。`showModal()` は背後を inert にして
  「見ながら回して確かめる」を殺す。フォーカストラップは戻さない。
- **既定の透視は30度、UIは正投影/透視の2値**（本人 2026-09-04）。30/40/50 の間に実用上の差が無く 90 は使う角度では
  ない。距離補正で見かけの大きさを保つので体感のパースは `tan(fov/2)` で動き（30→0.268 / 45→0.414 / 90→1.0）、
  30 vs 50 が弁別できない＝1.74×が閾値を下回る。**「実用上の差が無い」は「弁別できない」ではない**
  （本人が明示的に訂正）—— 30と45には見た目の差がある。刻んで選ばせる作業上の理由が無いという意味で、
  「体感が変わらないなら20度まで下げる」と読み違えてはいけない。内部 API（`setFov` / `isSelectableFov`）は
  0 または 30〜90 を受け付けたまま —— `smoke-files.mjs` の45〜55度スイープ（共平面ピックの回帰検査）が
  UI から到達できない値を使っている。

## パネルの配置

- **左サイドバー＝ファイルパネル（開閉可）、ビューポート左上に浮くブラウザ（モデル/スケッチ）、右サイドバー＝AI パネルだけ（開閉可）。**
  Fusion 360 に寄せた（本人 2026-08-23）。ブラウザは「モデル」「スケッチ」の2区分をフラットに並べる —— 区分の
  見出しだけ先に立ててあり、入れ子のツリー化とコンストラクションを足すときに一覧を作り直さないため。
- **ファイルパネルは左サイドバーが正**（2026-08-23 に一度ツールバーへ統合したが 2026-08-26 に本人が戻した）。
  **左サイドバーの既定は開いた状態** —— 畳んだ既定にすると `smoke-files.mjs` が `#file-name-input` を押せない。
  パネル内の「編集中のファイル名」と「ファイル」ラベルはヘッダと重複するので削除し、どれを開いているかは
  一覧の当該行を光らせる（`.files-row.active`）。モデルが空のとき左パネルの中央が大きく空く件は「いったん放置」（本人）。
- **STEP 読み込みはツールバーの verb、STEP/STL 書き出しはファイルパネル。** 線は「文書を変えるか」
  （本人「STEP読み込みはそもそもファイルバーじゃなくて通常モードの上部に出るべきだった」）。
- **常設パネルを足すときは画面に新しい帯を取らない。** 形状最適化の実行パネル（320px）をブラウザの右へ足したら
  その帯の下のボディが1面も指せなくなり `smoke-optimize-mode.mjs` が落ちた。ブラウザと同じ列の下端へ移して解決。
  一時的なダイアログは別の帯へ出してよい。**モードのあいだ出しっぱなしのパネルは、モデルを覆う位置に置けない。**
- **選択パネル・操作履歴パネル・パーツ一覧の pick 列は削除済み。** 履歴の行クリックで一括 undo はコアの
  機能追加になるので見送り。「承認する」ボタンは不要 —— そのまま操作するか AI に指示すればよい。
- **右サイドバーは AI 専用。** スケッチモードの残存部分（見出し・「正面から見る」・「抜ける」）はコマンドツールバー側へ移した。
- **断面はブラウザの「原点」の下の「断面」グループ**（issue #6、2026-09-16。提案8点を本人が一括採用）。チェックで入れ、
  入れている間だけ平面・位置・反転の操作子を出す。verb ではないのでツールバーに置かず、AI（MCP）にも出さない。キー割当は無い。
  **代償は、切っていない間もブラウザが見出し1行ぶん縦に伸びること**（モデルを覆う面積が増える）。実機検査2本
  （`smoke-regions.mjs` の領域クリック、`acceptance.mjs` の右ドラッグ）の始点がブラウザの下に入って落ちたので、
  どちらもブラウザを畳んでから押す形にした。
  - **平面（XY / XZ / YZ）はパネルのボタンで選ぶ。** README §0 原則1（viewport で指せるものにボタンを作らない）とは緊張するが、
    基準平面のピックはスケッチの貼る先待ちの間だけ生きる経路で、大きいモデルでは原点が埋まって指せない。
  - **状態はその場限り**（文書にも localStorage にも載せない。文書を開く・新規にすると切らない状態に戻る）。原点表示と違い
    「一度決めたら触らない設定」ではない。スケッチ・形状最適化のモードに入っても切ったまま。
  - 入れた瞬間・平面を替えた瞬間の位置は、表示中のボディ（幽霊を含む）の外接箱の中心。反転なしで消すのは
    **ホームビューのカメラ側**（XY は +Z、YZ は +X、XZ は −Y。`HOME_VIEW_OFFSET` の符号から導く）。
  - 位置の欄は他の数値欄と同じく数式を受け付ける。評価に失敗したら打った式を欄に残し、理由はトースト。
  - 平面は枠線だけで塗らず、クリックを吸わない。掴めるのは法線方向の矢印だけ（板全体を掴む形は、板の画素でモデルが
    指せなくなる）。矢印は切られる側を向く（反転すると向きも変わる）。
  - 切り口は1色（基本色より暗い `SECTION_CAP_COLOR`）で、選択色には追従しない。
- **新規ボタン**（`new_document`）は確認ダイアログを挟まない —— 一覧のクリック1つで別の文書へ移れる（未保存の編集が消える）
  のに空の文書へ移るときだけ確認を挟むと挙動が割れる。**AI には開けない**（`mcp=False`）: 今の文書を丸ごと捨てて
  undo でも戻せない操作なので、捨てる判断は人がする。

## コマンド層

- **点から導ける寸法欄は how に数えない**（`fromPoints`。README §0 原則3）。空欄なら集めた点から導き、打てば
  それが勝つ。確定に使う引数を `built ?? ghostBuilt` にすると「始点だけ置いて寸法を打って Enter」と
  「角をクリックして寸法を打って Enter」が同じ経路で通る。代償は**層をまたぐ契約が1本増える**こと ——
  プレースホルダに出す「いまマウスが指している値」は確定用の引数から名前で引くので、UI の欄名がサーバへ送る
  引数名と一致しない寸法（線分の長さ・角度は `p0`/`p1` へ畳む）は追従しない。
- **対象とは別に「既存の図形/面への参照」を引数で受ける verb**（`move_body.axis_edge` / `center_vertex`、
  `mirror_body.plane_face`、`mirror_sketch_entities.axis`）は `PickArgSpec` に乗せる。新設時に「UI での指し方は未決」と
  即断せず、まず `PickArgSpec`（`commands/command.ts`）が使えないか確認する。必須のピックは対象の最小数が満たされた
  瞬間に構えられ素のクリックを全部吸うので、**修飾キー付きクリックはピックへ行かせない**（修飾キーは既に
  「選択のトグル」の意味を持つので規則が増えない）。ピックを `optional` にする案は必須の引数が「(任意)」と出て
  基準が要ることが伝わらない、対象の上限を1にする案は仕様を曲げる、ので採らなかった。
- **モードは verb の上位次元**（[DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)）。`App.svelte` のモードはタグ付きユニオン
  1変数（`idle` / `sketch-pending` / `sketch` / `optimize`）で、不正状態が表現できない。**モードに紐づく状態の掃除は
  「出口」ではなく「入口」に置く** —— 出口は増えないが入口（再開・直接切り替え・undo での復帰）は後から増える。
  ブラウザのスケッチ名クリックで A から B へ直接移る道が「A の図形を選んだまま B へ入れる」抜け道になっていた。
- **確定前の幽霊が無関係な再配信で消えたまま戻らない**（2026-09-06、未解決）。カメラを動かすと可変解像度が
  `set_view_resolution` を送り、形が変わっていなくても状態が配信し直され（[VIEWPORT.md](VIEWPORT.md)）、
  `viewport.update()` が幽霊を消す。幽霊は引数が変わらないと描き直されない（`CommandHost` の `previewedKey`）。
  塞ぐなら「最後のローカルプレビュー要求を控えて `viewport.update()` の後に描き直す」形になるが、
  `preview: 'local'` の全 verb の挙動が変わる。実機検査は「状態配信が止まるまで待ってから打つ」で避けている。
- **`move_*` の空欄の軸を 0 として扱う判断（本人 2026-09-04）はコードに入っていない**（`NumberArgSpec.default`
  は無い）。入れるなら**この2 verb の dx/dy/dz だけに絞る** —— 半径・距離・個数のような「空欄＝まだ決めていない」
  引数に黙って 0 を埋めると壊れるので、汎用の既定値ではなく個別 opt-in にする。
- **数値欄は数式を受け付ける**（`web/src/expression.ts`。2026-09-06）。三角関数の引数と逆三角の戻り値は**度**
  （本人選択）。関数セットは四則・単項マイナス・括弧・`^`・`sqrt`・`abs`・`pi`・`sin/cos/tan`・`asin/acos/atan/atan2` で、
  **`hypot` / `min` / `max` / `round` / `floor` / `ceil` は本人が明示的に除外**（`log` / `exp` / 剰余も無し）。
  文書パラメータの参照（`width/2`）は入れていない —— `set_parameter` は MCP 専用で UI にパラメータ欄が無く、
  「式を保存して再評価する」話になる。次に伸ばすならここ。

## スケッチ入力（本人判断 2026-09-06、Fusion に揃える）

- **寸法はもう1つの点で決まる**（長方形＝対角、円＝円周の1点、円弧＝下記）。数値欄は残し、空欄ならマウス追従・
  打てばそれが勝つ。長方形・円は2クリック、円弧は3クリックで確定（Enter を押さない）。verb の契約は変えず UI 層で閉じる。
- **円弧は「始点 → 終点 → 円弧上の1点」の3クリック（中心は入力しない）。** 中心から始める形は「円と線分で代用できる」
  ので採らない。3点目を中心にする案は Fusion を再確認して円弧上の点へ変えた。技術的にも中心は弦の垂直二等分線上
  にしか置けず自由度が1つしか残らないので、「膨らむ向き」と「劣弧/優弧」を同時にマウスで選べない。
- **線分には長さ・角度の数値欄**（dx/dy ではない。Fusion の線ツールに合わせた。角度は度・反時計回り・X軸から）。
- **スナップ3段**（描く verb が点を待っている間）: 既存の点マーカー → 既存の図形の線（線上へ落とす）→ **1mm グリッドの
  交点へ丸める**。1mm は `gridScale.ts` の `TIERS` の最小段で絶対値固定。**マウスだけでは非整数の座標が置けないのは
  意図した挙動**。端数が要るなら寸法を打つ。**スナップを切る修飾キーも、ズームで刻みを変える仕組みも作らない**
  （視点に依存すると同じ操作が違う結果になる）。スナップは拘束ではない（吸い付いた先を動かしても付いていかない）。
- **スケッチの図形・点にはホバー強調を出し、描く verb が点を待っている間も出す**（2026-08-27 の「既存の選択ゲートに従う」
  の例外）。スナップが入ることで強調の意味が「クリックすれば選べる」から「**クリックすればここに乗る**」に変わり、
  どちらの状態でも予告として正しいので出し分けない。ソリッドの頂点は対象外のまま。
- **長方形の残り3隅（導出値）と図形をまたぐ交点（線分・円・円弧。ベジエは対象外）は本物の点と同格に吸着し □ で示す**、
  **線分の中点は点と辺の間の優先度で直交ティックを出す**（本人 2026-09-11）。交点は `SketchEntityHit.snapAt`
  （厳密座標）で運ぶ —— 片方の図形への射影に任せると連続的な最近傍点になり交点からずれる。
  `SKETCH_HANDLE_PIXELS` は 5→7（「点は辺より小さくしておく」という旧設計は撤回。点は辺より先に試すパスなので
  半径が辺の当たり半径を超えても辺の掴みやすさは構造的に壊れない）。
- **pointKey が1個しかない種別（rectangle / circle / arc）は点マーカーを選択中・ホバー中だけ出す。**
  これらでは「その点だけ動かす」と「図形全体を動かす」が同じ処理（`_moved_params`）なので、点は独立に動かせる
  特別な場所ではない。線分（2点）・ベジエ（4点）は片方だけ動かすと形が変わるので常時出す。
- **スケッチ開始は「ボタン → 貼る先をクリック」の2手**（基準平面も任意の面も同じ操作。Enter を挟まない）。
  対象の指し方が2つ（平面ボタン / 面を選んでからボタン）あると重複するので、ポインティング1つに寄せた。
- **スケッチを抜けたら入る前の視点へ戻す**（本人。4案中）。「全体が入る視点へ戻す」「『全体』ボタンを戻す」
  「直さない」は退けた。**再フレーミングを通常編集（押し出し・フィレット）へは広げない**（2026-08-23 の「全体」
  ボタン削除は撤回していない）。`open_document` は再フレームする、`new_document` はしない（合わせる内容が無い）。
- 選択の修飾キー: **Shift も Ctrl も「トグル」に統一**（本人「間違えたらもう一回クリックすればいいので、除外専用は
  実質無意味」）。無修飾は置き換え。形状最適化の集合代入 verb（保持/除外/拘束面）だけは素クリックもトグル
  （既存の割り当てが選択状態で現れるので、足すのに Ctrl が要るのをやめたい）。
- **スケッチモードの「選ぶ」ボタンは人向けの画面から外す**（人は直接クリックで選べるので重複）。コマンド定義・
  既定コマンド・Esc/確定後に戻る挙動は AI 用にそのまま残す（`CommandDef.hidden`）。

## 見た目

- **文字の大きさは2段だけ**（`--fs` 13px＝本文と操作子、`--fs-meta` 11px＝添える情報）。直す前は 11/12/13 が
  混在し、決めていたのは役割ではなく「そのファイルで誰かが font-size を書いたか」だった。差が8%では階層は伝わらず
  不揃いだけが見える。**ラベルであることは色（`--dim`）で言い、大きさでは言わない。**
- **操作子は線ではなく面で見せる。** `--line` は区画境界専用、打ち込む欄は凹み（`--input-bg`）、押すものは出っぱり
  （`--control-bg`）。読み札（`span.tag`）と押せる札（`button.tag`）も分けた。**枠は常に 1px ぶん確保して色だけ変える**
  —— 太らせたり消したりすると行高が動き、ビューポートの実寸（＝カメラのアスペクト）が動く。
- **区画境界の視認性**（本人 2026-08-23。第一希望は境界線を目立たせる、背景コントラストは第二希望）: `--line` を
  明度 30%→40%、`EDGE_COLOR` を `0x20262d`→`0x3f4a56`。境界線とパネル地の RGB 差が約2倍になり、地の明度差を
  広げる第二段は不要と判断。**border の無い flex 帯の中の区切り線は `position:absolute` の疑似要素で足す**
  （`.toolbar` は `flex:0 0 auto` なので border/padding で高さを増やすとビューポートの実寸を直接圧迫する。
  疑似要素は通常フローの高さに数えられず、`.viewport` の矩形が変更前後で一致することを実測）。
- **ホバー強調は新しい色を足さず明度を上げる**（選択済みにも同じ明度アップ。本人「ルールが単純になる」）。
  色相が「誰の選択か」（user=橙 / proposed=水色）、明度が「今カーソルの下にあるか」。第一段の裁定（2026-08-27）:
