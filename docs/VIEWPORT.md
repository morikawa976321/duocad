# duocad — 3Dビューポート（カメラ・ピック・グリッド・深度）

**読むとき**: `web/src/viewport.ts` とその兄弟（`planeGrid.ts` / `gridScale.ts` / `viewCube*.ts` /
`faceCulling.ts` / `screenPick.ts`）を変えるとき。当たり判定は screen 半径[px]で揃える
（正は `web/src/screenPick.ts` と `web/scripts/smoke-screen-pick.mjs`）。
実装の詳細はコードのコメントが正で、ここは**判断の理由と実測**。

## 不変条件「見えるもの＝指せるもの」と深度の規約

three.js の線のレイキャストは面による遮蔽を見ないので、見た目だけ隠すと「見えない辺が選ばれる」になる。
本当の不変条件は深度ではなく**見えるもの＝指せるもの**で、z-fighting が起きないのはその副産物。
判定は「そのオブジェクトはピック対象か」の一問:

- **A群（ピック対象）** — 辺・領域・スケッチの線と点。`depthTest:false` ＋ `depthWrite:false` ＋ renderOrder の階段。
  実体を透過するのは欠点ではなく仕様。
- **B群（装飾。ピック対象でない）** — 床グリッド・面グリッド・原点ギズモ。深度検査あり・書き込みなし ＋
  **クリップ空間の深度バイアス**でカメラ側へ寄せる（`planeGrid.ts`）。裏側は正しく隠れ、共平面でも争わない。
- **C群（実体）** — 何も指定しない。

基準平面のグリッドはスケッチ対象待ちのときだけピック対象になるが**表示は常に B群**（ピックは別経路のレイ検査）。
**使わないと決めたもの**: 法線方向へのワールドオフセット（ズームで破綻するうえ、ジオメトリを動かすので描画と
レイ検査がずれる）。`polygonOffset`（WebGL は `POLYGON_OFFSET_FILL` しか持たず線に効かないので、面と線で機構が
割れる）。`renderer.reversedDepthBuffer`（three 0.185.1 に実体はあるが `@types/three` の型に無く、深度の向きと
範囲を変えるので B群の自前 `gl_FragDepth` が黙って壊れる）。ビューキューブは同一 canvas の第2パスで
`clearDepth()` してから描くのでこの規約の外側。

## カメラ

- **Z-up 右手系**（X右/Y奥/Z上。Fusion・Blender・Cura と同じ）。カーネルは元から Z-up で、ビューアだけ
  three.js 既定の Y-up だった（床に見えていたのは XZ、基準地面 XY が壁のように立ち、XY にスケッチして +Z へ
  押し出すと手前左へ伸びた）。直したのはカメラの up だけで、ジオメトリに回転や軸入替は無い。
- **near/far は初回フレーミングから分離して常時引き直す**（`updateClipPlanes`）。`frameToContent` が姿勢と
  視錐台の2つを兼ねて `framed` フラグで1回しか走らなかったため、最初に届いた形の大きさで視錐台が固定され、
  後から入れた大きな STEP（対角約640mm）は画面外へ出るのではなく**平面で削られて**見えた（引けば引くほど
  切れる）。「初回だけでよいもの（姿勢）」と「常時追随すべきもの（視錐台）」を同じ一発フラグに相乗りさせない。
- **カメラを動かすと、見ているボディ自身が配り直される。** 版の鍵 `body_recipe` に目標精度と面単位の `focus`
  （視錐台に入り正面を向く面の集合）が入っているので、回すと `focus` が変わり**形が1ミリも変わっていなくても
  版が上がって再テセレーションが配信される**（板1つ・右ドラッグ 140×60px で約500ms後に revision 2→3）。
  **「この配信で形が変わったか」をブラウザ側から判定する口は無い** —— `applied === null` も使えない（MCP 起点の
  変更と形状最適化の完了配信がどちらも `applied=None` で本物の形を配る）。
- **減衰つきのカメラは正確には止まらない。** `enableDamping` は指数で近づくので位置も四元数も下位桁が動き続け、
  姿勢の一致を「止まった」の条件にすると門が二度と開かない（可変解像度が採り直されなくなった）。閾値で見る。
  しかも**閾値は画面の画素で決める**（位置は `worldPerPixel * 0.5`、向きは四元数内積 `1-1e-7`、倍率は相対差）。
- **`fitDistance` を経由しない距離の決め打ちを残さない。** 起動時カメラ位置だけが `diagonal * 1.2` を独自に持って
  おり、旧既定 FOV=45 で `fitDistance` と偶然 0.6% 一致していたため気づかれず、既定を 30 に変えたとき 55% ずれて
  `smoke-move.mjs` が「辺をクリックで選べない」という原因を名指ししない形で落ちた。既定値を変える前に
  `grep -rn "diagonal \* [0-9]"` のような独自再計算が無いか確認する。
- **球にちょうど収まる距離 `R / sin(fov/2)` は、球でない凸体を対角からずれた向きで見ると FOV が大きいほど縮む**
  （ビューキューブ: 対角±22°ずれで FOV 30→90 のとき一辺 118px→96px、約18%）。対称軸ちょうどから見れば縮まない。
  本編の `fitDistance` も同じ式だが、実コンテンツは概ね球に近いので実害が出にくい。UI の FOV が 2値になったことで
  90 が選べなくなり実用上は解消。

## ピック

- **面と基準平面はレイ距離で競うが、1画素にも満たない差を「手前」と見なさない**（`worldPerPixel` 閾値）。
  基準平面に描いて押し出した面は基準平面と厳密に同一平面で、素の `<` では勝敗が浮動小数の最後の桁で決まって
  いた（`fitDistance` を数学的に同値な式へ書き換えただけでカメラ位置が 7e-14 ずれ、`smoke-files` が赤くなった）。
  **切り分けの決め手は HEAD と自分の版でカメラ姿勢を並べて出すこと** —— 最後の桁だけ違えばこの同着。
- **基準平面の当たり範囲をモデルに追随させると、原点をまたいだ向こう側の面が指せなくなる。** ホームビューの
  カメラは特定の象限（`HOME_VIEW_OFFSET` の符号）にあり、反対側にある面へのレイは必ず先に座標平面をくぐる。
  解析的には正しいオクルージョン判定であり、バグではないので、実機検査ではクリック対象をカメラと同じ象限の
  部品から選ぶ（[SMOKE_TESTING.md](SMOKE_TESTING.md)）。内容への追随は描画からは切り離し、ピック範囲と near/far
  の下限にだけ残した。
- **固定の優先順位の下では、上位の的に常に乗っている下位の的は一生指せない**（頂点は必ず辺の端点にあり、辺が先。
  `move_body` 起動中は辺が常に出ているので回転中心の頂点は 100% 辺に取られた。症状は「クリックしても何も起きない」
  だけ）。解き方は2つで「外したときに何が起きるか」で選ぶ: 要求している間だけ順序を入れ替えるゲート
  （`preferVertices`。外しても何も起きないならこれ）／要求している間だけ上位の的を画面から引っ込める（外すと
  共有選択が書き換わる種類の衝突ではこちら）。
- **`clickable(x,y)` が単一の choke point。** 浮かせた DOM パネルは `elementFromPoint` で判定できる
  （`pointer-events:none` のトーストは覆っていても吸わないので自動的にすり抜ける）が、**同一 canvas の第2パス
  （ビューキューブ）は `elementFromPoint` が canvas を返し続ける**ので矩形の明示的な除外を足した。新しい種類の
  「吸うオーバーレイ」が増えたらここへ条件を足すだけで、ピック・矩形選択開始・ホバー予告の全部に波及する。
- **ホバーのキャッシュは「ポインタ＋カメラ」の鍵では不足。** 当たるものはポインタも視点も動かないまま変わる
  （ゲートの開閉・選択によるマーカーの増減・プレビューで本物を隠した/戻した・寸法変更）。「何が指せるか」を
  変える側が増やす**世代番号**を鍵に混ぜる。無効化は参照を捨てるだけでなく材質を戻すところまで。
- **辺の screen pick は全走査で足りる**（27部品の最大ボディ 233面・辺645本・折れ線の点1,768、1280×860）:
  見えている辺1本を300回で p50 0.2ms / p95 0.7ms、645本を1周して p95 0.3ms / 最大 1.6ms。基準「1フレーム16ms の
  p95 超過なら二段階化」に20倍以上の余裕。効いているのは「1回に走査するのは1ボディぶんだけ」。
- **`projectRegion` は三角形あたり4点（重心＋各頂点へ寄せた3点）を試し、実際のクリックと同じ判定を通す。**
  スケッチの点・辺を選べるようにしてピックを点→辺→領域にしたら、ベジエの制御点（曲線から離れて領域の内側にも
  立つ）が重心の5画素以内に来て候補が尽きた。「その画素で本当にそれが取れるか」を答えるヘルパは、ピックの
  優先順位を1つ足すたびに検算の条件も足さないと嘘をつき始める。

## グリッド（本人判断）

- **刻みは 1mm / 10mm / 100mm の3段固定。** 分割数10で内容から刻みを導く旧方式はモデルが大きかろうと小さかろうと
  同じ見え方になり、画面から縮尺が失われていた。段の不透明度は画面上の線間隔[px]だけから決まる1本の規則
  （目安 1.5px で 0・6px で 1）で、**連続フェードにすればヒステリシスは要らない**。判定は必ず投影後の px
  （FOV は 0 もあるのでカメラ距離では正投影で破綻）。
- **無限グリッドは「指せる範囲」で切る。** 基準3平面を同時に出すとビューポート全体が白い線で埋まった。その平面が
  指せるときだけピック範囲（±extent）で切り、装飾だけのときは無限でよい —— 指せる範囲の外まで描くと
  「見えているのに指せない」面積が生まれる。
- **ピック範囲の枠はワールド原点を含める**（本人「普通は原点付近にモデリングするので問題ない」）。代償: 原点から
  400mm 離れた 60mm 角の箱で枠が 600mm 角。面グリッドは `includeOrigin:false` で面自身の範囲が正
  （`extentFor()` は `BASE_EXTENT`=100mm を下限に持つので、面のスケールで再利用すると 40×20mm の面に 100mm が
  返る。`snap125()` を直接呼ぶ）。
- **格子の u=0 / v=0 の線は無条件に抜く。** 3平面を同時に出すと X軸(赤)・Y軸(緑)が消えた —— 格子の v=0 線が軸と
  完全に一致し、後から描いた灰色が色付きの軸を上書きする。描く順序では「どれかの軸が必ず負ける」。

## 可変解像度と面カリング（RTX 5060 Ti・headless Chrome・1280×860・PCケース 27部品2835面の実測）

文書全体で1つの目標精度（画面誤差 0.35 画素から導く）は深いズームで破綻する:

| 視点 | 1画素 | 目標偏差 | 三角形 | 測り直しの往復 |
|---|---|---|---|---|
| 全体 | 1.11mm | 0.390mm | 65,707 | 2.8秒 |
| 20段ズームイン | 0.095mm | 0.033mm | 394,975 | 5.6秒 |
| 30段ズームイン | 0.028mm | 0.010mm | 1,180,763 | 14.5秒 |

画面に出ていない部品まで同じ細かさで測るのが効いている（サーバは単一イベントループなので、この間セッション
全体が応答しない）。**相対下限 `DEVIATION_MIN_RELATIVE` を上げて誤魔化さない**（大きなモデルの小さな造作へ
寄ったとき角が見え、可変解像度の目的そのものを壊す）。

対処は **face 単位の視錐台＋バックフェイス**（オクルージョンは実装しないと本人決定）:

| 視点 | カリング | 三角形 | 細かく測った面 | 往復 |
|---|---|---|---|---|
| 全体 | 切 | 65,707 | 2835/2835 | 2.1秒 |
| 全体 | 入 | 65,707 | 1906/2835 | 1.8秒 |
| 30段 | 切 | 1,180,763 | 2835/2835 | 16.3秒 |
| 30段 | 入 | 205,534 | 231/2835 | 4.0秒 |

効いている仕掛けは3つで、どれか1つ欠けると効果が消える: (1) 粗い側の精度をズームに依存させない（画面外の Body の
「測り方」が変わると版が上がり全部配り直す）(2) 版とキャッシュの鍵を「実効レシピ」にする（全面を粗く測る Body
の鍵に細かい側の値を入れない）(3) 判定は画面側（カメラを持つのはブラウザだけ。プロトコルは `set_view_resolution`
に `focus` を1つ足しただけ）。**バックフェイスは閉じた立体の平面 face にだけ使う**（開いたシェルは裏が本当に
見える。曲面は「中央の法線」が面を代表しない）。残る代償: 細かい面と粗い面が曲線の辺を共有すると境目に隙間が
開きうる（画面の縁とシルエットなので塞がずに置いてある）。

## ビューキューブ（本人採用）

- 方向認識の問題（「軸と面の識別が難しい」「スケッチ中にどの面をどの向きで見ているか分からない」）への対策は
  **ビューキューブ1つで打ち止め**（本人「それ一つでほとんどの問題が片付くから」）。26領域（6面+12辺+8角。
  14領域への簡素化案は退けた）。表示 ON/OFF は作らない。ドラッグ自由回転は Pointer Lock（本編の右ドラッグには
  効かせない）。
- 見送った残り3件: スケッチのタグに面名・法線／正対時の `camera.up` を人間規則で固定／照明をワールド固定の
  キー＋フィル。**照明だけはキューブと守備範囲が重ならない**（ヘッドライトはどの向きの面もカメラを向いた分
  だけ明るくするので、平行な面・浅い段差・面取りとフィレットの区別は視点の手当てでは原理的に良くならない）。
  本人はこれも承知で「実際に使って困るかを見る」順序を採った。
- **投影は本編の FOV に追従**（本編がパースならキューブもパース。弱める案は採らない）。透視の距離は
  `R / sin(fov/2)`（R=√3）。素朴に「半幅 1.8 を画角で割る」と FOV 90 で手前の角が near に食われて消える。
  near/far はカメラ距離から導いて引き直す。
- **スケッチ中にキューブが天地逆になった原因**は `lookAtSketch` が `camera.up` にスケッチ平面の v 軸を焼いて
  いたこと。`OrbitControls` は生成時の up を `_quat` へ一度だけ焼き込むので、回転軸（常に Z）と `camera.up` を
  写すキューブの見た目が食い違う。`upForDirection`（真上・真下付近だけ ±Y）を `lookAtSketch` にも使う。
  任意面へのスケッチのときだけ挙動が変わる。

## 調査の順序

**ビューポートの見た目異常（グリッド・軸線が変なところで切れる等）は、グリッドやカメラのロジックを疑う前に、
クライアント（dev サーバ・ブラウザタブ）が複数同時に立っていないかを先に確認する**（near/far でもグリッドの
bounds でもなく、新旧複数のクライアントが同時に立っていたのが原因だった）。
