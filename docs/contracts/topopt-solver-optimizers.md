# 形状最適化のソルバ・性能の契約

形状最適化（`duocad/topopt/`）の線形解法・CPU並列化・性能測定の、**ソースを読んでも分からない不変条件・依存禁止・罠**を作業タスクの契約から分野別に蒸留した文書。
**いまの挙動の正はコードとテスト**（実測は [../TOPOPT.md](../TOPOPT.md)・[../TOPOPT_SPEED.md](../TOPOPT_SPEED.md)）。ここは、そこに無い契約だけを持つ。
出典: 節末尾の括弧のタスクID（先頭の `2026MMDD-HHMM-topopt-` は省略）。

## 現状の要約（読む前に）

- 製品の探索は二値探索（`binary_search.py` / `acceptance.py`）。線形解法は `fem.py`（既定 `"cg"`、`"auto"` で `"direct"` / `"cg"` を選ぶ。[../TOPOPT.md](../TOPOPT.md)「線形解法とCPU並列化」）。
- 扱う範囲: CPU並列化（`fem.PARALLEL_THREADS` / `_BlockedMatvec` / `parallel_matvec`）、解の計測口（`fem.collect_solve_stats`）、反力の荷重釣り合い確認（`fem.load_resultant` / `fem.reaction_forces`）、線形解法・性能測定に共通の罠。

## 線形解法の計測口（fem.collect_solve_stats）

- **`fem.collect_solve_stats()`（contextmanager）が、その文脈で `Model.solve` が積んだ `solves` / `cg_iterations` / `cg_iterations_each` / `assemble_seconds` / `slice_seconds` / `solve_seconds` / `fallbacks` / `direct_solves` を返す。** 器の鍵は `new_solve_stats()` が1か所に持つ。入れ子にしない（後勝ち）。
- **`_SOLVE_STATS` が None のとき `spla.cg` に callback を渡さない**（渡すと本番経路の費用が変わる）。反復数を数える処理は**解法と同じ場所**（`Model.solve` の中の `counter`）に置き、外から `cg` を差し替えて数える方式にしない（差し替えた瞬間に数え口が外れ、反復数が黙って 0 になる）。解法を差し替えたら反復数を `_SOLVE_STATS` へ積む処理も一緒に移す。計測側が「CG反復が1回も数えられていない」で落ちるのは数え忘れの合図。

(benchmark-set-four-cases / multigrid-preconditioner, 2026-09-04)

## CPU並列化とスレッド数（fem.py）

- **並列化したのは「疎行列×密ベクトル」だけ**（CG 自身の `A@x`）。BLAS のスレッド数（`OMP_NUM_THREADS` 等を 1→14）は有意差なし（疎行列演算が BLAS を経由しない）。BLAS 経由の重い密行列演算が増えたら測り直す。
- **疎×疎の積と `splu` は並列化しても速くならない。** 行ブロックに割って `A@P` を投げても `sp.vstack` の再結合費用が利得を食い、**1スレッドでも単発呼びの約2倍遅い**。scipy の版が変われば結果が変わりうるので並列化前に測り直す。
- **行ブロック分割はビット一致を保証する**（CSR の行 i の内積は行 i の非零要素だけで決まる）。`threads=1/2/3/4/8` で変位が1ビットも変わらない（`topopt_checks/check_parallel.py`）。縮約を並列化する形に変えるなら選び直し。
- **`threads<=1` は並列化前と同一のコード経路**（CG に生の `kf` を渡す）。`PARALLEL_THREADS=1` で直列に戻す運用の前提（A/B 実測 1.002倍、誤差内）。壊さないこと。
- **`_MIN_ROWS_PER_THREAD=512`** は検査で使う小さい格子（数百行）でオーバーヘッドだけが乗らないための値で、理論値ではない。変えるなら小さい格子でも遅くならないことを検査で見る。`_effective_threads` が行数に応じてスレッド数を絞る。
- **既定スレッド数は `max(1, os.cpu_count()//2)`**（`_default_thread_count`。論理コア14のこのマシンで7）。環境変数 `TOPOPT_THREADS` は import 時に1回だけ読み、壊れた値・0以下は1（半分化の**前**に return するので影響を受けない）。明示指定（`TOPOPT_THREADS` / `threads=N`）は絞らない（`threads=14` が全コアで動く）。比率が契約で、絶対値7はこのマシン固有。旧仕様（`os.cpu_count()` そのもの）は上書きされた。既定を変えても数値は動かない（`check_parallel.py` [3-4] は「ちょうど半分」の判定を保って期待値を追随させた）。
- **「14スレッドで最速」に依存しない。** n=44・4題材の合計で t=8 が 69.9秒、t=14 が 73.5秒（tilted は t=14 で中央値が悪化）。**半分（7）は t=8 の隣というだけで最速の実測点ではない。** 「Eコアのせいで半分にした」も未測定（Arrow Lake の P/E 混在は仮説で未実証）。P コア数を数えるべきかは別途測って決める。
- **並列化が効くかは題材の種類でなく自由度の大きさで決まる。** 自由度 14,256 で 0.77倍（遅くなる）、35,250 で 1.53倍。倍率を書くときは**測定時のスレッド数**を併記する。
- 罠: **反復数のベンチを一様乱数密度で取ると桁が狂う。** `rng.uniform(0.05,1.0)` は普通に収束するが、`rho<0.3→1.0 else 0.02` のような二値に近い極端な密度は CG が 1000回超（実測 1216回）。速度比較には前者を使う。
- 罠: **`ThreadPoolExecutor` の cProfile は `lock.acquire` の tottime に惑わされる**（`future.result()` が他スレッドの計算待ちも算入）。壁時計の before/after で判断する。
- 罠: **Barrier ベースの常駐ワーカーは単発 matvec で 1.15倍止まり**（46x28x31 格子・8スレッド）。複雑化に見合わず不採用（試作スクリプトは残っていない）。
- 罠: `git status` が触っていないファイル（`stress.py`）を modified と出すが `git diff` は空、という現象が並行セッション下で出る。diff が空なら触らず、ステージにも入れない。

## 線形解法の数値の罠（共通）

- **CG の前処理は対称正定値でなければならない。** 前後の平滑化回数が違う・制限が `P^T` でない・減衰係数が大きすぎる、のいずれでも `v^T M v` が負になりうる（重み 5.0 で負を実測）。検査用の口だからと上限を外さない。（multigrid-preconditioner, 2026-09-04）
- 反復法（べき乗法など）の開始ベクトルは**固定ベクトル**にする。乱数にすると出力の SHA-256 を見る回帰検査が毎回落ちる。（multigrid-preconditioner, 2026-09-04）
- **`np.union1d` / `np.setdiff1d` を自由度に使わない。** ndof 3.6M で合わせて 8.0秒/反復（setdiff1d 6.32 + union1d 1.66）。真偽マスクで 0.013秒。（dynamic-active-set, 2026-09-12）
- **`spla.cg` は再帰残差で「収束」と返しても真の残差が大きく乖離することがある。** 保持ソリッド(ρ=1)と背景(低充填率)のコントラストが極端な場（0.77% で 2.2e6 倍）では真の残差が約3000倍あった（`SolveResidualError` 残差 2.963e-06・max|u| 1.739e+06）。真の残差の検算を外さない。対処の候補は真の残差での再スタート・対角スケーリング。（dynamic-active-set, 2026-09-12）

## 性能測定の流儀（共通）

- **物差しの第一は `CG反復/solve`、秒は補助。** 同条件の撮り直しで反復数は完全一致・コンプライアンスも下6桁一致、秒は同一セッション内でも 1.00〜1.16倍振れた。**この幅より小さい秒の差を「速くなった」と言わない。** 秒の主張は幅つきで書く。
- **スケーリング則は1題材の直線から外挿しない。** 題材4つで秒/設計反復は格子要素数の 1.05乗〜2.03乗、CG反復数は DOF の 0.41〜0.45乗。薄板が 2.03乗なのは、行列（非零99万）がキャッシュに載る大きさから外れて実効帯域が落ちる（27.4→16.9 GB/s）ため。
- **条件数は大きさでなく形で決まる。** 薄板は DOF 14,256 で CG 477反復、塊状は DOF 47,817 で 296反復。コンプライアンスを題材どうしで比べない（材料量も荷重も塊の大きさも違う）。
- 受入検査用と性能測定用の大きさを1つにまとめない（受入は速さが命、性能は大きさが要る）。
- 題材設計の罠: 薄板は低解像度だと保持パッドの中心を1つも通らず落ちる（`voxelize.occupancy` のレイ縮退は解像度に対して単調でない）。薄板の荷重面は節点が1つしか付かず実質点荷重になりうる。「拘束DOFが多い=多点支持」ではない。

(benchmark-set-four-cases / multigrid-preconditioner, 2026-09-04)

## 測定・運用の罠（共通）

- **小さい題材の壁時計は信用しない。** 1反復1秒規模で、ビット単位に同じ計算の1反復中央値が2時間空けた再測定で -16% / -16% / +2% 動いた。秒の倍率を語ってよいのは1反復が数十秒の規模だけ。（mma-vs-oc-measure, 2026-09-10）
- 罠: **`TaskStop` で止めたバックグラウンドの bash が子スクリプトを生かしたまま残り**、67分後に2本目の実測を暴発させてログを切り詰め、70秒間 CPU を奪った。止めた後に `Get-CimInstance Win32_Process` の CreationDate で孤児を確認する。待ち合わせはラッパーに書かず、先行が終わってから自分で次を起動する。（mma-vs-oc-measure, 2026-09-10）
- 罠: **Windows で python の標準出力をファイルへリダイレクトすると cp932 になる。** 完了マーカーを日本語で grep する待ち合わせは永久に成立しない。マーカーは ASCII にする。（mma-vs-oc-measure, 2026-09-10）
- 罠: 計測スクリプトは走行の最後に JSON を書く形だと、途中で止めると生データが残らず、**先に書いた文書だけが実在しないパスを指したまま残る**。`--merge` で段ごとに積み、長い段は分けて回す。（reaction-constraint, 2026-09-10）

## 反力（荷重釣り合い確認）

- `fem.load_resultant(f) -> (3,)`（荷重ベクトル→合力）と `fem.reaction_forces(model, rho, penal, u) -> (3,)`（拘束自由度全体の反力の合力 `R=(K u - f)|_fixed` の軸ごとの合計）。**荷重釣り合い（合計が荷重合力の符号反転）の確認にだけ使う。**（reaction-constraint, 2026-09-10）
