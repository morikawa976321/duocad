## Issue の粒度(AIの判断 2026-10-16)

- 前提(記録済みの本人の基準。docs/DESIGN_DECISIONS.md「開発の進め方」): 不満は issue にせず、issue は「1件ずつでは直せない構造的な作業」にだけ使う。
- 決めた: 今回は本人が「適切な粒度で Issue 化」と明示したので Issue を立てる。粒度は**層とデータ経路の単位**(例: 「面ごとの Mesh を1ボディ1 Mesh にまとめる」「テセレーションをイベントループから外す」)にし、1 Issue が1回の対話で終わる見込みのもの(数値1つの変更など)は Issue にせず、まとめ Issue の箇条書きに入れる。
- 各 Issue に「実測(今の数値)」「原因の場所(file:line)」「方針」「効いたかを測る物差し(再現コマンド)」を書く。

## Issue の切り方(astra の意見と AI の判断 2026-10-16)

AI(親)の案: 8 件(①カメラ操作の丸ごと測り直し ②辺の連なり ③単一ループの塞がり ④プレビューと確定の二重計算 ⑤JSON 配信のバイナリ化 ⑥面ごとの Mesh と常時描画 ⑦スケッチの領域検出と作り直し ⑧固定費のまとめ)。問いは「粒度・順位・見落とし・継ぎはぎ・物差し」。

astra の意見(要旨):
- ①③⑤は別 Issue のまま(仕事量・応答性・表現コストは互いの改善後も独立して残る)。統合するのはプロトコルを一括置換しなければ成立しないと確認された場合だけ。
- ⑧は解体。自動保存は独立した「保存を操作の待ち時間から外す」Issue に、スケッチの配信は⑦に、全ログ配信・`face_count`・往復 10 ms の調査は関連 Issue の作業項目へ。
- ③から保存を外し、④とは「投機結果の採用・失効の契約」を共有する。`Session.preview` は共有文書を一時変更して巻き戻すので、そのまま別スレッドへ移せない。
- ②はキャッシュだけでは初回 0.5 秒が消えない。「初回の辺表示」と「再取得」のどちらを狙うか明記する。全部品の前計算は 26 部品で 5 秒なので標準案にしない。
- ⑥の「1 Mesh なら速い」は要注意: three.js は材質配列だと group ごとに描画項目になる。物差しは draw call 数。BVH は測ってからの候補。
- 多世代キャッシュ自体は継ぎはぎではない(鍵・容量・破棄条件が統一されていれば)。
- 順位は⑥①、次に③④で同意。着手順は②と⑦の領域キャッシュを先行させてよい(独立して効果を確認しやすい)。
- 画面からの往復 10 ms はまだ経路固有の固定費と断定できない(計測の対応づけが粗い)。`measure()` は rAF 後にさらに 1 フレーム待つので 85〜120 ms をすべて実アプリの描画待ちとは扱えない。
- 物差しには、コミット・モデル・環境・開始終了点・冷/温・反復分布を書く。① 再計算面数と bytes、② 初回/再取得、③ 重処理中の入力待ち、④ verb 実行回数、⑤ 符号化/解析時間、⑥ draw calls・静止 CPU・操作中フレーム時間、⑦ 領域計算/再構築回数。目標値は実測値と区別し、非目標・依存先・不変条件も書く。

AI(親)の判断: 上をすべて採用する。⑧は解体して「自動保存を待ち時間から外す」を独立 Issue にし、残りの小粒は関連 Issue の作業項目へ。②は「初回表示から連なりの計算を外し、クリックした辺だけ遅延計算して形ごとにキャッシュ」と目標を定める。⑥の物差しは draw call 数と静止時 CPU/フレーム。往復 10 ms は node から同じ `modify_selection` を打って切り分けたうえで、該当 Issue の調査項目に書く。全体を見渡すまとめ Issue を 1 件足す(順位・依存・物差しの表)。

### #167 連なりは指した辺の分だけ取り寄せる(AIの判断)

- 決めた: 折れ線から連なりを外し、ホバー・クリック・矩形の辺の分だけ `get_edge_chains` で求める。連なり未着の

- 捨てた: 折れ線を先に返して全辺の連なりを後から押し出す案(計算量が変わらず、ボディを替えるたびにループが 0.5 秒塞がる)。
  連なりの規則を Python で書き直す案(OCCT の内部規則の写しになり、版で黙ってずれる。`Add` そのものを答えにする)。

### #173 保存は配る前に確定し、書き込みだけを後ろへ(AIの判断)

- 決めた: debounce も「配信の後に書く」もしない。Issue の方針 (a) は「配信してから書く」だったが、そうすると落ちたとき最後の
  変更を失う窓が配信の長さ(PC ケースのフィレット後で 150 ms 以上)へ広がり、本人の決定(issue #5。Issue 本文の「数百 ms の窓は
  本人に確認してから広げる」)に触れる。中身は配る前に確定し(JSON 化を 117 → 4 ms に縮めた)、ファイルへの書き込みだけを書き手
  スレッドへ回す。窓は従来どおり「書き込みが終わるまで」。
- (b) の `saved` の3値は入れない: 書き込み中を画面に出す必要が無い(応答を待たせていない)。
- 覆る条件: 本人が「数百 ms の窓は構わない」と言ったとき(配信の後に書けば JSON 化の 4 ms も応答から外れる)。

### #168 プレビューはスレッドで、写しの上で(AIの判断)

- 決めた: プレビューだけをワーカースレッドへ出す。入力の形は深い写しにして渡す(錠で直列にする案より単純で、ループ側の
  テセレーションと競合しない)。写しの上の結果は元の形の結果として覚え直す(#169 の使い回しを保つ)。
- 捨てた: プロセスへ出す案。往復(最大 85 ms・中央値 54 ms)を 50 ms 未満へ縮める差のために、形の受け渡し(BRep の文字列化)と別プロセスの寿命管理を
  持ち込むことになる。テセレーションもスレッドへ出す案: 文書を変える verb と配信の順序・版(`_send_locks`)の契約を
  スレッドへまたがせることになり、#166 で測り直しの量そのものを減らす方を先にする。
- 覆る条件: 本人が「プレビュー中のクリックの手応えが遅い」と言ったとき(プロセス分離を検討する)。

### #166 面単位のキャッシュで、同じ細かさの面の境目の小さな隙間を許す(AIの判断)

- 決めた: 面の三角形を測り方ごとに面単位で覚え、足りない面だけを測る(回転で細かく測る面が入れ替わっても、入れ替わった面だけ)。
  別々の回に測った面どうしの境目には、同じ細かさでも分割の食い違いによる隙間が残りうる(sol の再現 0.000255 mm。上限は偏差の
  2倍程度。偏差が画素から決まっている間は 1 画素未満で、面の境目には境界線を描くので見えない)。偏差が下限に張り付く深いズーム
  (sol の再現: 1 画素 1e-6 mm で 40 画素)では1画素を超えうるので、細かく測る面の組は同じ回に測ったものだけで組む。
- 捨てた: 「同じ測り方の面の組に1つでも足りない面があれば組ごと測り直す」をいつも行う案。隙間は消えるが、回転で細かく測る面が
  入れ替わるたびに組ごと測り直すので、回転の往復が 1.0 秒から元の 2.2 秒へ戻る。
- 覆る条件: 断面の切り口や画面で境目のすき間(点状の抜け)が見えると本人が言ったとき。

### #170 状態とプレビューは1枚のバイナリフレーム、型付き配列は写す(AIの判断)

- 決めた: `[u32 ヘッダ長][JSON ヘッダ][float32/uint32 の生バイト]` を1枚で送る(`duocad/net/wire.py`)。三角形だけを生バイトにし、
  残りは JSON のまま。画面は読んだ数の並びを型付き配列へ写す(`web/src/wire.ts`)。
- 捨てた: JSON のテキストフレームの直後に生バイトのフレームを送る2枚組。1つの接続へは状態の配信とプレビュー・辺などの応答が
  別々の非同期処理から送られ、2枚の間に別のフレームが割り込むと対応が崩れる(1枚なら対応付けが要らない)。
- 捨てた: フレームの `ArrayBuffer` のビューをそのまま使う(写しを省く)。省かれて使い回される面が1つでも残る限りフレーム全体を
  手放せない。写しは PC ケースの初回 2.8 MB で数 ms。
- 実測で分かったこと: 受信ハンドラの大半は解析ではなく作り直しだった(PC ケースの初回 186 ms のうち JSON.parse は 9.5 ms)。
  バイナリ化で効いたのは流れる量(6.1 MB → 2.8 MB)とサーバの直列化(json.dumps 72〜77 ms → 20 ms)。
- 覆る条件: 画面以外のクライアント(テキストしか読めないもの)が状態の配信を読むようになったとき。

### #166 #170 接続が持っているものを省く: 面は通し番号、ログは共通の先頭、スケッチは中身の一致(AIの判断)

- 決めた: 接続ごとに送り届けたものを覚え(`wire.Delivered`。記録は送信成功の後)、同じものを省く。面はサーバが測るたびに振る
  通し番号(`serial`)が前回と同じなら三角形を省く。操作ログは前回と同じ先頭を省いて末尾だけ送る。スケッチは前回送ったものと
  中身が一致すれば省く。画面は前回の写しで埋め戻し、埋め戻せなければ繋ぎ直す(両側とも忘れて全部を送り直す)。
- 捨てた: スケッチの版(`revision`。#172)で省く。版は描くもの(枠・領域・展開した図形)が変わったときだけ上がり、名前・可視・
  寸法の名前は入っていないので、名前を変えても画面に届かない。中身の比較は、領域の配列がキャッシュの同じ物なので速い。
- 捨てた: 画面が測り方ごとに面を複数持つ(ズームの行き来で送り直さない)。画面の写しは各ボディの今の面だけにした。
  ズームアウトで元の段へ戻ると、サーバは測らない(18 ms)が三角形は送り直す(PC ケースで 2.0 MB)。
- 覆る条件: ズームの行き来の送り直しが重いと本人が言ったとき(画面の写しを多世代にする)。
