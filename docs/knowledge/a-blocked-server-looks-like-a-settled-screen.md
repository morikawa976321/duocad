性能の前後比較を実機ブラウザで測るとき、**「画面に届いた値が変わらなくなったら落ち着き」を
完了条件にしてはいけない**。サーバが単一イベントループなら、重い測り直しの最中は
**何も届かない** —— これは「もう何も起きない」と見分けが付かず、検査は
**要求が出ていく前の画面**を落ち着きと読む。

2026-08-30、duocadで実際にこう読んだ。0.45秒の静けさで打ち切ったベンチは、カリング入りと
切りで**まったく同じ数値**を返した(どちらも1つ前の状態を読んでいた)。待ちを2.5秒へ
伸ばすと今度は**1測定ぶん遅れた値**が並び、入りの結果が切りの欄に出た。さらに
「1通も来なければ往復0秒」という逃げ道を6秒で置いたら、**測りたかった16秒の沈黙**が
そこに落ちて0.0秒と記録された。

正しい待ち方は**受信回数を数えること**。状態が1通届くたびに増える番号をアプリ側に生やし
(`__duocad.stateEpoch`)、

1. 手を打つ前の番号を控える
2. 番号が増えるまで待つ(増えなければ**検査側の間違い**として落とす。0秒と記録しない)
3. 増えなくなって一定時間(2秒)経ったら完了
4. 所要は**最後に番号が増えた時刻**までで測る

こうして測り直したら、カリング切りの値が事前に別経路で測ってあった実測
(三角形1,180,763・14.5秒)と一致した。**既知の値を再現できることが、ベンチが正しく
測れている唯一の証拠**になる。
