# ミニマルなモデリングツール v1 の技術決定

計画書全文は `mf/duocad/docs/IMPLEMENTATION_PLAN.md`。ここは判断とその理由だけ。

## 決定

- **土台は Python コア + ブラウザ frontend**。OCP・MCP・モダンUIの3つが同じ答えを指したため。
  ocp_vscode は**改変対象ではなく参考書**（あれはビューアであってエディタではない）。
- **frontend は Svelte 5 + TypeScript**（2026-08-10。当初のReact推奨を本人の「過剰では」で見直し撤回した）。
  **AI側の当初の理由「他プロジェクトと揃う」が弱かった** — 他プロジェクトはWebアプリで、これはデスクトップ級のツール。
  過剰である根拠は**自分たちのアーキテクチャ側にあった**: 状態を全部コアに置いたので、
  frontendに残る状態はコマンドの途中状態だけ。画面部品も8個程度。
  **フレームワークが元を取るのはクライアント状態管理であり、その理由を設計時点で消していた。**
  **守るルールは1つ、canvasはフレームワークの外に置く。**
  なお**寿命の観点を当初見落としていた** — 10年使う道具なので、変化の激しいReactより
  Svelte、さらに陳腐化しないWeb標準(Lit/vanilla)の方が有利。決め手は技術的優劣でなく
  「2年後に自分が読み返して分かるか」。
- **CSSはバニラ（CSS変数）。Tailwindを使わない。** 部品が10〜15個と少なくCADのパネルは密度が高いこと、
  そして **Tailwindの既定値に寄せると「よくあるWebアプリの見た目」になり、CADツールがWebアプリに見えてはいけない**ため。
  [[freecad-rejected-classical-ui]] の足切り条件と同根の判断。
- **保存はJSONの操作ログ。SQLiteは使わない。** ①gitに載って差分が読める ②AIが履歴を全部読める
  ③1モデル＝1ファイル。**document指向のアプリであってデータのアプリではない**（Fusionが `.f3d` を保存するのと同じ）。
  monocore（Supabase）からの類推が働きやすい場面だが、種類が違う。
- **複数ボディはv1のデータモデルに入れる**（UIは1ボディ分だけ）。**参照STEPを読み込む時点で既に複数ボディ**なので
  選択の余地が無い。高くつくのは「選択が `body_id` を持つ」改修で、これが全層に波及する。
- **単位は mm 固定。**
- **STEPエクスポートも必須**（本人指摘）。最近のスライサーがSTEP読み込みを既定にしているため。
  加えて副次的価値として、**このツールで作りかけてFusionで仕上げられる＝移行の安全網になる**
  （「機能が足りなくて詰む」というこの企画最大のリスクを構造的に消す）。

## v1の受入テストを実物に固定した

**`shelf_attachment_GD.step` をFusionなしで再現すること。**
面の構成を実測して選んだ（56面 = 平面34 + 穴22、トーラス0・円錐0・spline0）ので、
**verb 6個で届くことが分かっている**。到達点が自分で印刷した部品なので「作ったが使えない」が構造的に起きない。

**（注・2026-08-11判明）** このファイルは実際には「板に22穴」の1部品ではなく**17個の独立ソリッド（ネジ・スペーサー類の参照部品）**で、面種別からの読み取りが誤っていた — 経緯と教訓は [[full-cylinder-is-not-always-a-hole]]。
v1.1は積層プレート（フィレット・面取りが要る）、v1.2はPCケース（円弧）。

## 7つ目のverb `extrude_face` を承認（2026-08-10）

承認された6個の中に、本人の速度ベンチマークである「既存の面を選んで押し出す」が入っていなかった。
受入テストはスケッチ＋押し出しだけで作れるので厳密には不要だが、
**これが無いと「手動のほうが速い」という企画の前提を実測できない**ため追加。M1の検証はこのverbで行う。
