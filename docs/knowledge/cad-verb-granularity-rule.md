# verbの粒度: 3つが一致する単位で切る

[[cad-migration-scope-shifted-to-app]] の自作モデリングツールで、
「Fusionの円を描く5ステップをどう分割するか」という問いへの設計解。

## 層を2つに分ける

- **コマンド層（UI）**: 引数を集める状態機械。プレビューとEsc中断を持つ
- **verb層（モデルAPI ＝ MCPのツール）**: 引数が揃った操作を1回適用する純関数

**UIの操作手順とverbの粒度は別階層であり、一致させてはならない。**
円を描く5ステップは1つのverb `add_circle(plane, center, radius)` を組み立てる漏斗にすぎない。

**この分割は分業原則（[[cad-manual-ai-division-principle]]）の構造的表現そのもの** —
人間はポインティングで、AIは述語で引数を集める。**集め方が違うだけで呼ぶverbは同一**だから交互操作が成立する。

## 判定規則

**verb = 次の3つが一致する単位**: ①1回のundoで消える単位 ②操作ログの1行 ③MCPの1呼び出し。
食い違う切り方をしたら切り方が間違っている。

**3つが一致しないものはverbではなく部分系**である。スケッチがその例 —
スケッチモード内のCtrl+Zは個々の図形を取り消す＝**入れ子のundoスコープを持つ**ので、1verbに収まらない。

## 避けるべき切り方

- **細かすぎ（UIの1ステップ=1verb）**: AIがモーダルな状態機械を人間の真似で駆動する羽目になり、
  ログは再生不能、undoの粒度も壊れる。**MCPをUIの操作手順の写しにするのが最もありがちで最も致命的な失敗。**
- **粗すぎ（「ブラケットを作って」=1verb）**: 途中結果を指せず、交互操作の割り込み点が消える。

## verbに課す2つの制約

1. **純関数** `f(document, selection, params) -> new_document`。破壊的変更をしない。
   → **undoもプレビューも無料になる**（プレビュー＝確定前に投機実行して捨てる）
2. **既存の選択を先に消費する**。引数収集はまず共有選択集合を見て、空のときだけ人に問う。
   → **AI→人間の受け渡しがこれで自然に成立する**

## 派生する判断: 最小セットではスケッチを持たない（同日撤回）

**この派生判断は2026-08-07に本人により退けられた** — スケッチは厳密で複雑なモデリングに必須（[[sketch-mandatory-solver-is-off-the-shelf]]）。フィーチャ級verbは併存させる価値があるため以下の理由付けは生きているが、「持たない」という結論の方は無効。

スケッチ＋押し出しの2段構えは「任意の輪郭を作れるようにするための一般性の税」。
穴・ボス・矩形ポケットのような決まった形なら**フィーチャ級のverbで直接作れ、
手数は5〜8ステップから4ステップへ減り、実装からスケッチ部分系が丸ごと消える**。
build123d が既にこの形（`Box`/`Hole`/`fillet`/`chamfer` にスケッチ容器が無い）で、実例として機能する。
スケッチが要るのは非円・非矩形・拘束付きの輪郭だけなので、必要になってから加算的に足す。
