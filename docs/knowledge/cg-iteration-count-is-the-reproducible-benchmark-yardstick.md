# 反復解法の基準線は「秒」ではなく「CG反復数」で取る

2026-09-04 `probe_topopt` で4題材 × 2解像度の性能基準線を取ったときの実測。**同じセッション内で
同じ設定を撮り直した**ところ:

- **CG反復数は8回の solve が1つ残らず一致**した(`[356,338,303,300,303,253,223,290]` が2回とも同じ)。
  コンプライアンスも下6桁まで同じ。
- **秒は 1.00〜1.16倍振れた**(4題材で 1.10 / 1.00 / 1.09 / 1.16)。日をまたぐと
  [[benchmark-seconds-swing-with-thermal-state]] のとおり 1.2〜1.7倍。

だから前処理・解法の改良は **CG反復数の差で主張し、秒は補助**にする。秒を出すときは
**1回の実行の中の設計反復から分布を取り(中央値)、最小〜最大を併記**して、
**その幅より小さい差を「速くなった」と言わない**。全体を3回回すより安くて再現性が高い。

**平均ではなく中央値**にするのは、1反復目だけ `x0=0` から解くぶん極端に遅いため
(実測 7.26秒 対 中央値 4.93秒)。平均だと反復数を変えただけで値が動く。

## 時間を空けると壁時計は15%動く(2026-09-10実測)

duocadのSIMPで**ビット単位に同じ答えを返す同じ計算**を2026-09-10の20:02と22:22に測った。1反復の秒数の中央値は 20:02: 0.929 / 0.925 / 0.948秒(3ケース)、22:22: 0.776 / 0.781 / 0.968秒 → **-16% / -16% / +2%**。機械は空いていて、走らせたのは同じスクリプトだけ。`threads=1`・1反復1秒前後の規模である(322k要素・`threads=7`・1反復30秒の規模では、2回の測定が32.8秒と33.0秒で揃った)。

- **小さい題材の壁時計比較は±15%の幅で読む。** 「MMAはOCより12%速い」のような倍率を1回の実測から書かない。**向き(どちらが小さいか)が複数ケースで揃っているかを見る。**
- **同じrunの中の内訳(ある関数が1反復の何%を占めるか)はこの幅を受けない。** 費用を語るときは、まずrun内の内訳を計る道具を用意するほうが強い。

対になる注意: **並列化は秒に出て反復数には出ない。マルチグリッドは反復数に出る。**
両方の欄を出さないと、どちらが効いたか切り分けられない。
