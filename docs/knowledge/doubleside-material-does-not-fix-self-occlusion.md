# `side: THREE.DoubleSide` は自己遮蔽を直さない

probe_topopt(taskbox `20260903-2304`)で、塊(パッド)の軸整列な1面(拘束面)を単色で塗る
実装をしたところ、既定のカメラ視点からその面の画素が実測でほぼ0だった。

**最初に疑って外れた原因**: バックフェースカリング(カメラから見て裏向きの三角形を
描かない)。`MeshLambertMaterial({ side: THREE.DoubleSide })` に変えても症状は変わらなかった。

**実際の原因**: 幾何学的な自己遮蔽。カメラは塊(パッド)の正面(+x側)を向いており、
問題の面は塊の背面(-x側、法線が外向きに-xを指す軸整列面)にあった。同じ塊の**手前にある
他の面**(側面・正面)が不透明に描かれているため、背面の面はカリング設定に関係なく
そもそも視線が届かない。バックフェースカリング対策とはメカニズムが別物 —— 前者は
「単一の三角形をどちらの向きから見ても描くか」、後者は「そもそも別の不透明物体に
隠れて見えないか」で、`side` パラメータが効くのは前者だけ。

**直し方はカメラの向きを変えること**(または遮る側のジオメトリに穴を開けるなど、
視線が実際に届く構成にすること)。`side: THREE.DoubleSide` は無害だが無意味だった。

## 検出漏れの二次被害(検査への影響)

この面を検出する画素判定(色のチャンネル比較)を「そこそこ緩い」閾値で書いたところ、
**表示/非表示を切り替えても画素数が変化しなかった**(=その面を1枚も検出できていない)。
にもかかわらず閾値を満たす画素が数千個あったのは、**半透明の境界線ヘルパー
(`#5577aa`、背景と混ざって拘束面の色に近い暗さになっていた)を誤検出していたため**。
集計値だけを見ると「そこそこの数が出ている」ので気づきにくい。

1色ずつ実際に非表示にして画素数が実際に0近くまで落ちることを確認する変異検査
(`probe.setVisible(role, false)` のような穴をコードに仕込む)を実装して初めて発覚した。

[[fit-to-screen-tests-need-projected-size-not-visibility]] — いずれも「集計だけの検査は
見えていないものを見逃す」という同型の教訓。
