# duocadの深度・重ね順の規約

面グリッド・床グリッドの追加でz-fightingが複数箇所に出る見込みになったため、ツール全体の規約を
決めた。**本人が「ベストと思われるルールを決めてよい」と委任し、以下をこちらで決定した**(2026-09-03)。

## 出発点 — 既にある不変条件

duocadのオーバーレイは既に全て `depthTest: false` ＋ `renderOrder` の階段で描かれており
(グリッド-1 / ソリッド0 / 最適化1 / 辺10 / 領域11 / スケッチ線12 / スケッチ点13)、
その論拠が `web/src/viewport.ts` の辺のマテリアル定義にコメントとして残っている:
**three.jsの線のレイキャストは面による遮蔽を見ないので、見た目だけ隠すと「見えない辺が選ばれる」
になる。** つまり本当の不変条件は深度ではなく **「見えるもの＝指せるもの」** であり、
z-fightingが起きないのはその副産物にすぎない。規約はこの既存の論理の一般化として書く。

## 規約 — 判定は「そのオブジェクトはピック対象か」の一問

- **A群(ピック対象)** — 辺・領域・スケッチの線と点。
  `depthTest: false` ＋ `depthWrite: false` ＋ renderOrderの階段。実体を透過するのは欠点ではなく、
  「見えないものが指せる」を防ぐための仕様である。
- **B群(純粋な装飾。ピック対象でない)** — 床グリッド・面グリッド・将来の補助線。
  **深度検査あり・深度書き込みなし ＋ クリップ空間の深度バイアス**でカメラ側へ寄せる
  (`onBeforeCompile` で `gl_Position.z -= BIAS * gl_Position.w;`)。裏側は正しく隠れ、
  共平面でも争わない。バイアスは層番号 × 単位量で、単位は 1e-4 程度から実測で詰める。
- **C群(実体)** — 何も指定しない。

基準平面のグリッドは、スケッチ対象待ちのときだけピック対象になるが、**表示は常にB群に置く**。
ピックは別経路のレイ検査が担っており、表示の深度とは既に独立して動いている
([[duocad-base-planes-lose-to-solids-by-depth]])。状態によって群を切り替える方が複雑になる。

## 使わないと決めたもの

- **法線方向へのワールドオフセットは禁止**。ズームで破綻する(引くと足りず寄ると浮きが見える)うえ、
  **ジオメトリを実際に動かすので描画とレイ検査がズレる**。1画素未満の差で面と基準平面の勝敗を
  決めている([[duocad-coplanar-base-plane-pick-is-decided-by-the-last-bits]])世界へ、意図的な
  ズレを持ち込むことになる。**描画のズレをピック側に持ち込まない**ことが本規約の必須条件である。
- **`polygonOffset` は使わない**。WebGLは `POLYGON_OFFSET_FILL` しか持たず**線に効かない**ので、
  面と線で機構が割れる。統一ルールにならない。

## 併記事項

- **renderOrderは名前付き定数表を1箇所に置き、生の数値をコード中に書かない**。現状の
  -1/0/1/10〜13は番号自体が意味を持たずコメントで補われており、層が増えるたび全部を読み直す形に
  なっている。
- **深度精度の改善は別軸**。完全な同一平面はどんな精度でも決着しないので共平面問題の代替には
  ならないが、「近いが同一ではない平面」の争いには効く。near/farの常時引き直しは既に入っている
  ([[duocad-clip-planes-decoupled-from-initial-framing]])。残る候補だった `renderer.reversedDepthBuffer`
  は **2026-09-03に不採用と決めた** — three.js 0.185.1 に実体はあるが `@types/three` 0.185.4 の型に
  無くTSから渡せず、かつ**深度の向きと範囲の規約を変えるのでB群の自前 `gl_FragDepth` が黙って壊れる**。
  「安い保険」ではない。
- ビューキューブは同一canvasの第2パスで `clearDepth()` してから描くので、**本規約の外側**
  (独立した深度空間)になる。
