taskbox handoverに「着手前から赤・本人判断待ち」として記録されていた acceptance.mjs の human
4件（add_circle / add_arc / pattern_rectangular / pattern_circular）が、2026-08-23の
FilesPanel移設タスク実行時には**2回とも全緑**だった。念のため `git stash` で変更前のコードに
戻して同条件で実行しても同じく全緑で、変更が直したわけでもなかった。

一方 `smoke-features.mjs` の既知赤（体積が円柱ぶん減らず「穴が開かない」）は、変更前後で
**エラーメッセージ・失敗地点まで完全一致**して再現した。

結論: acceptance.mjs の該当4項目は実行タイミング依存で緑/赤が入れ替わる（原因未特定。人手クリック
座標のタイミングやOCCTの非決定的な面挙動が疑わしいが未調査）。**既知赤の「着手前ベースライン同等」
判定は、再現した場合のみ症状(エラーメッセージ・失敗箇所)の一致で行い、緑になったこと自体を問題視
しない**（handoverの既知赤リストは「その回に赤だった」記録であって「常に赤で確定している」保証では
ない）。次にこの4項目に触れるタスクは、赤か緑かどちらが出ても驚かないこと。

## 2例目(2026-08-26): 記録した本人が同じコミットで直していた

duocadのREADMEに「`smoke-features.mjs` と `acceptance.mjs` が赤。製品側の穴かスクリプトの脆さかは
**本人判断待ち**」と残っていた項目を、指示を受けて着手する前に実測したところ、**両方とも緑**だった
(`smoke-features` PASS、`acceptance` は人間19/19・AI19/19)。

**解消したのは、その記述を書き足したのと同じコミット `7363c76` 自身**である。コミットメッセージには
「画面外に出た smoke-features.mjs の座標2箇所を調整した」と書いてあり、**判断待ちとされていた分岐は
その場でスクリプト側に倒して決着していた**。記述だけが更新されずに残った。

一般化: **「直した」と「記録を直した」は別の作業**であり、後者は落ちやすい。とくに
**同じコミットの中で問題を直しているとき**は、直前に自分が書いた「未決」の記述が視界から外れる。
「既知の赤/留保」を出発点にする指示を受けたら、**信じて着手せず先に1回走らせて再現を確かめる**。
