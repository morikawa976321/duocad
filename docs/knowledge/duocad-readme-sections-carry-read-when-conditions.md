# duocad/README.md の各節に「読むとき」条件を付けた

`duocad/README.md`(778行/61KB)冒頭の文書地図は、`IMPLEMENTATION_PLAN.md`=仕様確認時、`REQUIREMENTS.md`=背景確認時、`MCP.md`=AI操作時、`docs/TOPOPT.md`=数字の根拠を辿るとき、と条件を明示して無条件依存を避けている。一方 `duocad/CLAUDE.md` は「入口はREADME.md」とだけ言い、README自身の§2 UIチートシート〜§4 アーキテクチャ(約400行)には条件が無かった。結果、UI入力統一のような狭いタスクでも778行全体を読む方向に誘導されていた([[taskbox-runner-protocol-references-oversized-files]] と同じ調査で発見)。

2026-09-06に、§2(UIチートシート)・§3(自動検査の走らせ方)には見出し直後に1行、§4(アーキテクチャ)は内部に8小節あるので小節ごとの「読むとき」一覧を追加した(duocad `159a40f`)。

**教訓: 「読むとき」条件は狭めすぎると新しい除外事故を作る。** 当初案の§3「手動QAのシナリオ(①〜⑬)のみ」は事実誤認(①〜⑬は実ブラウザの自動smokeで、節にはpytest・受入検査も含む)、§4の「frontend(`web/`) — ファイル配置を変更するとき」は狭すぎて、発端だった「UI入力統一」タスク自体が除外される誤りだった(実節の実体はファイル役割表とcanvas/three.jsの不変条件で、`web/` を触る実装全般が読むべきもの)。「`web/` 配下のコードを変更するとき」に広げて修正(`f2482e7`)。どちらも別セッションのモデルに独立レビューさせて見つかった。
