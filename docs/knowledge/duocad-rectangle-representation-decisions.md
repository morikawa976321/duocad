# duocadの長方形: 1図形のまま、角度を持つ

2026-09-06に本人が決めた2件。同じ制約(拘束ソルバが無い)から出ている。

## 1. 長方形は1つの図形のまま据え置く

Fusionは長方形を「4本の線分+拘束」で持ち、辺単位で削除・移動できる。duocadは長方形を1つの図形(`x`/`y`/`width`/`height`)として持っているので同じことができない。検討の結果、本人は**当面そのまま(現状維持)**を選んだ。辺単位で触りたくなったときに**分解verbを足すかもしれない**、という位置づけ。

判断の材料になった事実:

- duocadは**拘束ソルバを持たない**(`duocad/parameters.py` の冒頭が明言)。4本の線分にすると長方形を保つ仕組みが無くなり、隅を動かすと片方の線の端点だけが動いて角が割れる。
- `add_rectangle` は4個の名前つき値を作る。4本の線分だと端点座標8個になり、`set_parameter` で「幅を50」が引けなくなる。これは拘束ソルバの代わりにduocadが持っている唯一のパラメトリックな口。
- `rectangle` を名指しするコードは187箇所・テストは31ファイル。
- 長方形→4本の線分の分解コードは既にコアに2本ある(`_rotate_rectangle` の回転コピーと `_mirror_rectangle` の斜め軸鏡映)。分解verbはそれを角度0で呼ぶだけになるので実装は小さい。

## 2. `params` に `angle`(度・反時計回り)を足す

長方形は軸平行しか表せず、回転すると4本の線分に化けていた。本人が引っかかったのは「**円形反復すると参照元と複製で構成が違う**」という気持ち悪さ。調べると症状はもう1つあり、**斜めの軸で長方形を鏡映すると ValueError で失敗する**(`duocad/verbs/mirror_sketch.py`)。

この変更は**機能追加ではなく、欠けている数値を埋めるもの**という位置づけ:

- `EntityKindOps` の `rotate`/`mirror` が種別をまたぐ `List[dict]` を返しているのは、コード自身のコメントによれば**長方形のこの1ケースのためだけ**。角度を持たせるとその一般化の理由が消え、分解関数2本も消える。
- `duocad/parameters.py` が「拘束ソルバは持たない。各図形が自分の名前つき数値を持つだけ」と宣言しており、角度はまさにその数値。Fusionが長方形に角度を持たないのは拘束があるからで、拘束の無いduocadが真似る理由は無い。

移行コストがほぼ無いのは、**文書の保存形式が操作ログだから**(verbと引数の列を再生する)。`add_rectangle` に既定0の引数を足せば、古いファイルは同じ結果に再生される。ただし再生した個体はキーを持たないままなので、[[adding-a-param-key-to-a-shape-breaks-old-entities]] の3箇所が壊れる。

## 実装済み(2026-09-06・taskbox `20260906-1442`)

- 回転・鏡映した長方形は常に `kind == "rectangle"` のまま(4隅の座標集合で検算。`angle` の値そのものは基準の角の取り方に自由度があるため期待値にしない)。
- `EntityKindOps.rotate` / `.mirror` の戻り値は `List[dict]` から `Dict[str, float]` 1つに狭まった(長方形が種別を変える経路が無くなったため)。
- 鏡映verb([[duocad-mirror-verbs-added]])側にあった長方形用の ValueError・フォールバック処理は不要になった。
- 実装時に踏んだ「旧文書はキーが少ない」型の壊れ方は [[adding-a-param-key-to-a-shape-breaks-old-entities]] のとおり。duocadの長方形を触る変更をするときは常にこれを疑うこと。
