# duocadのスケッチ: 点を置くときのスナップ3段とホバー強調

2026-09-06に本人が決めた。

## スナップ3段

描くverbが点の入力を待っている間:

1. 既存の点マーカー → その座標そのもの
2. 既存の図形の線 → その線の上へ落とした座標
3. どちらにも当たっていない → **1mmグリッドの交点へ丸める**

1mmは `web/src/gridScale.ts` の `TIERS = [1, 10, 100]` の最小段で、**絶対値で固定**(視点でも内容の大きさでも変わらない。[[duocad-grid-three-tier-fixed-steps]])。スケッチ平面にもこの格子が描かれているので、frameの (u,v) を丸めるだけで見えている線の交点に一致する。

**結果としてマウスだけでは非整数の座標が置けなくなるが、これは意図した挙動**。端数が要るときは寸法を打つ([[duocad-sketch-dimensions-follow-the-mouse]])か、既存の図形へ吸い寄せる。**スナップを切る修飾キーも、ズームで刻みを変える仕組みも作らない** —— 挙動が視点に依存すると同じ操作が違う結果になるため。

## ホバー強調

- スケッチの図形・点にも**マウスホバーの強調**を出す。
- **描くverbが点を待っている間もホバー強調を出す**(本人決定)。2026-08-27の裁定6「既存の選択ゲートに従う」([[duocad-hover-prehighlight-decisions]])に照らすと「クリックしても選択されないのだから光らせない」になりそうだが、スナップが入ることで**強調の意味が変わる** ——「クリックすれば選べる」ではなく「**クリックすればここに乗る**」。どちらの状態でも予告として正しいので出し分けない。
- 2026-08-27に点を見送った理由2つは、スケッチの点には当てはまらない: スケッチの点マーカーは常に描かれているし(`picked` は材質を選ぶだけ)、`move_sketch_entities` が点・辺を対象に取るverbとして2026-08-30に入った。**ソリッドの頂点は対象外のまま。**

**このスナップは拘束ではない** —— duocadは拘束ソルバを持たない([[duocad-rectangle-representation-decisions]] と同じ制約)。作られるのは「たまたま同じ座標」で、吸い付いた先の図形を後から動かしても付いていかない。

実機smokeのfixtureがこのスナップで壊れる件は [[smoke-fixture-points-must-clear-snap-targets]]。

## 見た目の角(2026-09-11)

`pointKeys`(独立に動かせる点。`move_sketch_entities` の対象)に無い頂点 —— 長方形の
残り3隅([[duocad-rectangle-representation-decisions]] が言う「基準の角1つだけ」の
残り)のような、`width`/`height`/`angle` からの導出値だが幾何的には角そのもの ——
は、以前はスナップ3段の「線」扱いになり×表示だった。`snap()` は隣接するどちらの辺
から来ても同じ角へ厳密にクランプするので実際の精度は点と変わらず、**表示だけ**が
不統一だった(基準コーナーだけ特別に見える)。

`web/src/entityKinds.ts` の `EntityKindSpec.visualCorners` で、pointKeysとは別に
「見た目だけの角」を種別ごとに宣言できるようにし、長方形は4隅すべてを返すようにした。
円・円弧には追加していない(曲線上のサンプル点まで角扱いすると誤って□が出るため)。
`hit.point` の意味・`move_sketch_entities` の対象は変えていない —— 変えたのは
`sketchCursorOverlay.ts` の □/× 表示の分類だけ(ここまでは表示だけの対応)。

**同日中に本人から「優先順位も点と同格にして」と追加指示があり、当たり判定
(`sketchEntityAt`)側も直した。** それまでは表示が□でも内部的には今も「辺」パス
(`EDGE_PICK_PIXELS`)のままで、角のすぐ近くに別図形の辺があると、それが角より
画面上で近ければそちらが勝つ非対称が残っていた(点は必ず辺に優先するのに、角は
優先しないという食い違い)。`viewport.ts` に `sketchCornerAt` を新設し、点パスと
辺パスの間に挿し込んで `entityVisualCorners` を本物の点と同じ半径
(`SKETCH_HANDLE_PIXELS`)・同じ優先度で拾うようにした。返す `point` は常に
null(独立参照は持たない)なので、選択やmove_sketch_entitiesの対象は変わらない。
「角のすぐ近くにより近い別図形の辺があっても角が勝つ」ことをアドホックな検査
スクリプトで実測確認済み(コミットには残していない)。

## 図形をまたぐ交点(2026-09-11)

続けて本人から「長方形以外でも線分の交点には点と同じ優先順位で吸着させたい」と
要望があり、自己の角と同じ理屈を**異なる図形どうしの交点**(線分どうし・長方形の辺
どうし)へ広げた。`entityKinds.ts` に `EntityKindSpec.segments`(直線区間)を追加し、
`sketchIntersections()` が全図形ペアの交点を線形代数で列挙する。この時点では曲線
(circle/arc/bezier)は対象外だった(数値的な求根が要ると判断)が、**同日中に本人から
「円や円弧も含めて」と追加指示があり、直後の節でcircle/arcへ広げている**(閉じた式で
解けると分かったため。ベジエだけは今も対象外)。
`viewport.ts` の `sketchCornerAt` が、自己の角と交点を**同じ候補集合**に混ぜて
`pickNearestWithinRadius` へ渡すので、優先度もradiusも完全に同格になる。

**この段になって、スナップされる座標そのものを直す必要が出た**: 交点は2つの図形に
またがるが、`SketchEntityHit` は `entityId` を1つしか持てない。片方の図形自身への
射影(`snapToSketchEntity`)に任せると、連続的な最近傍点になるだけでほぼ確実に
交点からずれる(自己の角がこれまで問題にならなかったのは、隣接するどちらの辺へ
射影しても同じ角へクランプされるという偶然の一致でしかなかった)。`SketchEntityHit`
に `snapAt`(厳密座標)を追加し、`sketchCornerAt` が角・交点の両方でこれを立てる
ようにして、`viewport.ts`(`snappedSketchUv`)・`App.svelte`(`snappedPlanePoint`)
の両方の当たり判定経路で「`snapAt` があればそのまま使い、自己への射影を呼ばない」
よう揃えた。この設計変更で、旧方式(`isEntityCorner`: 確定後の座標を自己の角の
座標と比較して判定)は不要になり削除した —— `hit.snapAt` の有無を見るだけで
角・交点の判定と分類の両方が同時に片付く。

## 円・円弧の交点/線分の中点/点の半径(2026-09-11)

同日中に本人から3件追加指示があった: (1)「円や円弧も含めて交点は吸着点として
扱ってほしい」(2)「既存線分の中点に重なったとき、直交する短い線分を表示したい。
半径は点と同じ・優先順位は点と線の間」(3)「点の吸着半径を少しだけ大きく」。

**(1)** `EntityKindSpec.segments`(直線区間限定)を`intersectables`という判別共用体
(`segment`/`circle`/`arc`)へ一般化。線分×円・円×円・線分×円弧・円×円弧・円弧×円弧の
交点はどれも閉じた式(2次方程式・円と円の交点公式)で解け、数値求根は要らないと
判明した(ベジエだけは今も対象外)。`angleWithinArc`(交点が弧の範囲内か)と、
既存の `clampAngleToArc`(`snap()` が使う)を、反復加算のwhileループから `%` による
定数時間の正規化へ書き換えた —— SVG取り込み由来の円弧は `start_deg`/`end_deg` が
0〜360の前提から外れることがあり(実機で `start_deg:270,end_deg:0` を確認)、
whileループ版はそこで極端に遅くなりうる。**ただしこれは念のための頑丈化であり、
実際に踏んだ不具合の原因ではなかった** —— `smoke-svg.mjs` が別の場所でハングした
件を最初はこの円弧角度が原因と疑ったが、`git stash` で今回の変更を全部外しても
同じ箇所で同じように失敗することを確認し、無関係な既存不具合(`viewport.ts` の
`projectRegion` が小さすぎる三角形をサンプリングし損ねる)と判明した。切り分けの
経緯・再現条件は [[duocad-region-projection-fails-on-tiny-triangles]]。

**(2)** `viewport.ts` に `sketchMidpointAt` を新設。直線区間の中点を、本物の点・角/
交点より1段低いが辺よりは高い、新しい優先度階層で拾う(`sketchEntityAt` の点パス→
角/交点パス→**中点パス**→辺パスの順)。半径は点と同じ `SKETCH_HANDLE_PIXELS` を
共用。`SketchEntityHit` に `midpoint`(真偽)と `snapDirection`((u,v)空間の単位
ベクトル)を追加し、カーソル強調(`sketchCursorOverlay.ts`)が線分と直交する短い
ティックを描けるようにした —— 画面上の角度は `viewport.ts` 側で2点を射影して
求める(このファイル自身はthree.jsを知らない)。ブラウザでの実測で、円と円の
交点・線分の中点それぞれ `hoveredRef().snapAt` が解析値と厳密一致し、分類
(□/ティック)も優先度どおりになることを確認した。

**(3)** `SKETCH_HANDLE_PIXELS` を5→7へ拡大。**「点は辺より小さくしておく」という
旧来の設計コメントは撤回**した —— 点(と角・交点)は辺より優先度が高い(距離に
関わらず先に試すパスが違う)ので、半径が辺の当たり半径(`EDGE_PICK_PIXELS=6`)を
超えても辺の掴みやすさが構造的に壊れるわけではない、という理由づけに変えた。
