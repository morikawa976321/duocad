# 破壊的変更はSvelteコアではなくSvelteKitに集中している

duocad（自作モデリングツール）のfrontend選定で、10年使う前提の churn を調べた結果。

## Svelteコアの実績

- Svelte 3(2019-04) リアクティビティの全面書き換え → 4(2023-06) 軽微 → **5(2024-10) runes導入**
- **2026-08時点で Svelte 6 は出ていない**（5が22ヶ月継続中）
- 大きい書き換えは **約5年間隔**。いずれも「旧版が動かなくなる」ではなく「書き方が変わる」で、
  legacyモードと `sv migrate` の移行ツールがある

## 重要な区別

**2026年に観測される破壊的変更はほぼ全て SvelteKit 側**（SvelteKit 3.0 / remote functions /
form enhance のコールバック / アダプタ）。SvelteKit は 1.0(2022-12)→2.0(2023-12)→3.0(2026) と
**ほぼ年1回のメジャー**でマイナーでも壊す。

→ **ルーター・SSR・アダプタ・フォームが要らないなら SvelteKit を入れないだけで churn の大半を回避できる。**
「Svelteは変化が激しい」という一般的な印象は、実際にはSvelteKitの評判を借りている可能性が高い。

## 一般化できる判断（フレームワーク選定全般）

- **フレームワークの churn を心配する前に、依存の順位を数えること。** duocadの場合、実際に危険な順は
  ①**three.js**（semverを持たずr番号で毎月リリース・非推奨APIを定期削除）
  ②**言語バインディング**（OCP等は維持者が少なく冗長性が最も低い）
  ③小規模ライブラリ ④フレームワーク。**フレームワークは最下位だった。**
- **ローカル専用ツールは上げなければ壊れない。** バージョン固定＋静的ファイルなら動き続ける。
  したがって実コストは「壊れる」ではなく **イディオムのずれ** — 次の大きな版が出た後にAIが書く「今風の書き方」が
  手元のコードと噛み合わず、**AI支援の質が落ちる**形で来る。
- 対処は「最も標準的で漂流しないものを選ぶ」か「**書き換えが1日で済む規模に surface を保つ**」の2択。
  部品が10個以下なら後者で足りる。

**How to apply**: 長寿命の個人ツールで技術選定するとき、①メタフレームワークを外せないか検討する
②churnの激しい依存を1ファイルの狭いインタフェースに閉じる ③バージョンを固定する。
