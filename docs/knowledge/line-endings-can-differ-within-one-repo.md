# 同じリポジトリ内でも行末はファイルごとに違う(duocad)

duocadは `core.autocrlf=true` で、gitのblobは全てLFだが**作業ツリーの行末は混在している**: ツールが直接書いたファイル(`web/src/viewport.ts` など)はLF、checkoutを経たファイル(`web/src/App.svelte`・`web/src/viewCube.ts` など)はCRLF。`git diff` も `git status` も差分を出さないので目視では分からない。「リポジトリ単位で行末は揃っている」という推定は成り立たず、`.gitattributes` が無い環境では書いたツールごとに違う行末が入る。

## 踏んだ形

1. **複数行の完全一致置換が0件で落ちる**(2026-08-27)。片方で通った置換をそのまま隣のファイルに当てて0件。1行だけの置換は行末を含まないので起きず、同じセッションの中で成功例と失敗例が混ざるのがさらに紛らわしい。
2. **変異検査が逆の結論を出す**(2026-09-05)。実装を1箇所わざと壊してテストが赤くなるか見る手順で、置換対象を複数行の `\n` 文字列で指定した。作業ツリーはCRLFなので**置換は0件で終わり、ファイルは無傷のままテストが走った**。結果は「変異を入れたのに緑」——素直に読むと「このテストは何も見ていない」という**逆の結論**になり、正しく噛んでいるテストを書き直すところだった。Pythonの `open(..., encoding="utf-8")` はユニバーサル改行で読むと `\n` に見えるが、`newline=""` で読めば `\r\n` が入っている。
3. **`git checkout -- <path>` が1ファイルだけCRLFで書き戻す**(2026-09-06)。LFだったファイルを巻き戻すとそのファイルだけCRLFになり、行を配列にして切り貼りするスクリプト(`line == '}'` のような完全一致)が `'}\r'` になって落ちる。落ち方は「なぜかアサーションだけが失敗する」で、中身は1文字も変わっていないので目視では見つからない。

## 守り方

- 複数行にまたがる完全一致置換をする前に、そのファイルの行末を見る。文字列置換は**必ず件数をassertする**(`assert s.count(old) == 1`)。件数を見ていれば「0件でした」が即座に出る。
- 行末を変えたくないなら `newline=""` で読み書きし、`\r\n` ↔ `\n` の正規化を1箇所に閉じる。**`newline="\n"` で保存すると作業ツリーだけLFになる** —— gitは正規化するので差分は正しく出るが、並行セッションの差分表示や他ツールが汚れる。
- 変異チェックで「緑のまま」が出たら、**テストを疑う前に変異が入ったかを確かめる**(`git diff` で1行でも変わっているか見る)。
- 検出は `python -c "d=open(p,'rb').read(); print(d.count(b'\r\n'), d.count(b'\n'))"`。`grep -c $'\r$'` はGit Bashで当てにならない([[bash-tool-grep-cr-false-positive-on-lf-files]])。
- `git checkout` の直後は `\r\n` → `\n` へ戻してから作業を続ける。
