比較測定のハーネスが密度場を `rho_{題材}_{条件}_{ラベル}.npy` で書き出していた。
**解像度が名前に入っていなかった**ので、同じ題材の3解像度が同じファイル名になり、
後から回した解像度が前のを上書きした。集計側は「格子が違えば比較不能」を
`a.shape != b.shape` で見ていたが、**上書きされた側は基準も比較対象も同じ配列を
読むので形が一致し、検査を素通りする**。結果、レポートの2行が
「5.37mm 同士を比べた値を 8.19mm の行に書く」状態になった(QAで発覚)。

**教訓は2つ:**

1. **測定の成果物のファイル名には、その run で振った軸を全部入れる。** 「題材 × 条件」だけ
   入れて「解像度」を落とすのは、振った軸が3本あるのに名前が2本しか区別しないということ。
   格子そのもの(`25x42x34`)を入れると軸名を考えなくて済む。
2. **集計側に照合の門を置く。** 測定JSONに**保存前の実物から取った SHA-256 と格子**を書いておき、
   読むときに突き合わせる。合わなければ同じ digest の配列を探し、無ければ**落とす**。
   形の一致だけを見る検査は、上書き事故に対して**検出力ゼロ**である。

**続き(同日・2回目の指摘で分かったこと):**

- **張り替えるときは「測定ごとの名前」ではなく「内容の名前」にする。** 測定ごとの名前へ直そうと
  したら、**同じ値を出す複数の測定(反復違い・パラメータ振り・取り直し)が1つの実体を取り合って
  同じ穴を作り直した**。`{題材}_{格子}_{中身のSHA-256}` にすれば、共有は共有のまま別物は必ず別名になる。
- **成果物をファイルから読み直さない設計は、この事故に耐える。** 同じ測定は STL も上書きしていたが、
  三角形数は書き出し前のオブジェクトから数えていたので数字は無傷だった。
  **「ファイルへ書いてから読み直して数える」実装だったら、そのまま嘘になっていた。**
- **表を手で書くと、別の測定点の数字を書き写す。** 欠測を埋めるために足した表で実際にやった。
  **表は生データから機械生成する**(集計スクリプトの関数にする)ほうが、書き写しの機会そのものが消える。

**取り違えを疑ったときの決め手は digest だった。** 記録側(JSON)は保存前の実物から取って
いたので、実ファイルと突き合わせるだけで6/21本の取り違えが機械的に確定した。
測り直した6本の digest が記録値と全部一致したので、**時間・メモリの表(別測定)とρの対応も
保たれている**ことまで言えた。**「保存したものの指紋を、保存とは別に記録しておく」**が効いた。
