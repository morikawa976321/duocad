# `move_body` 起動中、辺をクリックで選べない(解決済み・検査側の待ち不足だった)

`web/scripts/smoke-move.mjs` の8b節が `move_body を起動しても辺を1本もクリックで選べない` で
落ちていた(同じビルドで5回中2回緑・3回赤)。**2026-09-03に原因を特定して直した。製品の不具合ではなく、
検査の待ちが足りなかった。**

## 機序(主経路)

1. 検査は `frameAll()` でカメラをジャンプさせた直後に `#move-body` を押し、
   **`window.__duocad.wantsEdges === true` だけを待って**辺の射影に入る。
2. `wantsEdges` は `CommandHost` の同期的な `$effect` で立つので**即座に真**になる。
   **しかし辺の実データはまだ無い。**
3. `App.svelte` は辺のキャッシュの `revision` が今のボディの `revision` と一致するときだけ
   `showEdges` する。一致しなければ **`showEdges(null, [])` で辺を空にしてから
   `session.getEdges()` を非同期で投げる**(WS往復)。
4. その間 `edgeBodyId === null` なので、`projectEdge` は先頭の
   `if (edgeBodyId !== bodyId) return null` で**全インデックスに対して即 null** を返す。
5. 検査のループは null なら**待たずに次へ進む**(`continue`)。8本を数ミリ秒で撃ち切り、
   **クリックを1回も発生させないまま** fail する。**エラーは1つも出ない**
   (「取れるものが無かった」だけの静かな失敗)。

flakeなのは、非同期フェッチが間に合うかどうかのレースだからである。キャッシュが当たれば
同期的に `showEdges` されて緑になる。

## 副経路(同じ症状を作るもう1つの道)

`frameAll()` のカメラジャンプが可変解像度を誘発する。動きが止まって180ms後に
`set_view_resolution` がサーバへ飛び、**サーバは粗さを `body_revision` の鍵に入れている**
(`duocad/view.py`)ので、**形が同じでも版が上がって `changed` に載る**。届いた配信で
`viewport.update()` の `if (entry.bodyId === edgeBodyId) clearEdges()` が走り、
**ループの途中で辺が消える**。

## 直し方(2026-09-03に実施・`duocad 71aa985`)

- **検査側(これが本筋)**: `wantsEdges` だけでなく**辺の実データが届くまで待つ** ——
  `projectEdge` がどれか1本でも非nullを返すまで待ってから撃つ。加えて**ループを最大2周**
  する(下の副経路で、撃っている最中に全indexがnullへ落ちうるため)。
  失敗メッセージも「辺を1本もクリックで選べない」から**「辺の実データが届かない」**へ変え、
  次に踏んだ人にとって原因が近くなるようにした。**修正後は6回連続で緑**(修正前は5回中2回)。
- **製品側は現状維持でよい。** 版が違う辺を消すのは正しい(古い添字は別の辺を指す)し、
  `edgesAsked` で取り直しは走る。ただし**「起動直後は辺が指せない窓がある」「視点を止める
  たびに辺が取り直される」のは実挙動として残る**ので、実使用で「選ぼうとした瞬間に外れる」
  が起きうる。検査を素直に書くには `edgesReady` 相当の穴があるとよい。

## 切り分けるときの前提(この件で二度、判断を誤った)

**実機smokeが配るのは `web/dist`**(ビルド成果物)なので、`web/src` を触ったら
`npm run build` を挟まないと古い束を検査する。加えて**1回の走行で結論を出さない** ——
当初「毎回100%再現する決定的な失敗」と記録したのは、走行1回ずつの結果で
`git stash` 比較を判断したためで、誤りだった。
