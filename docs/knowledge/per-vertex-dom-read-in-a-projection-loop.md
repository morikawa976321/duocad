**解決済み**(duocad `49e69b4`)。`projectRaw` / `geometryInside` / `objectInside` が
`width`/`height` を引数で受け取る形に変え、`collectInBox` の入口で `size()` を1回だけ
読んで下流へ渡すようにした。モジュール側にはキャッシュしていない(リサイズで寸法が
変わるため。関連ノート参照)。実測(同じ740x748ビューポート・27部品2835面・画面全体を
囲む矩形、collectInBox 全体を計測): **中央値38.3ms → 3.9ms**。同じ矩形で選択される
面集合が前後で一致することも確認済み(27ボディの面インデックス集合が同一)。

以下は解決前に実測した記録(踏んだ経緯として残す)。

duocadの `web/src/viewport.ts` の `projectRaw()`(世界座標→画面画素)が、**呼ばれるたびに
`size()` を呼んで `container.clientWidth` / `clientHeight` を読んでいた**。この関数は
矩形選択の包含判定 `geometryInside()` の**最内ループから頂点ごとに**呼ばれる。

**実測**(83,084頂点を射影する矩形選択1回):

- 現状(頂点ごとに `size()`) = **32.1ms**
- `size()` をループ外へ巻き上げただけ = **2.5ms**(13倍速い)
- さらに戻り値の `{x,y}` オブジェクトも作らない = 2.3ms

つまり**遅さの92%は射影の算術ではなくDOMプロパティの読み取り**であり、
オブジェクト割付(2.5→2.3ms)はほとんど効かない。矩形の幅と高さはループの間ずっと
不変なので、巻き上げは結果を1ビットも変えない。

**気づきにくい理由**: 単発クリックのピックも同じ `projectRaw` を通るが、そちらは
1頂点なので体感に出ない。**「1回あたり0.36マイクロ秒」が数万回に掛かって初めて見える**。
型検査も単体テストも通り、コードを読んでも「レイアウト読み取り」だと意識しにくい
(`size()` という名前が算術のように見える)。

一般則として、**画面座標へ変換するヘルパは寸法を引数で受け取るか、呼ぶ側が
ループの外で1回だけ読む**こと。
