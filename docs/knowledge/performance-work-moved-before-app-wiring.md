# 性能は配線の後、から「マルチグリッドとCPU並列だけは配線の前」へ

2026-09-04、同じ日のうちに方針が2段で動いた。

**第1段(訂正前)**: 「パフォーマンスを詰めるのは一番最後(配線も終わった後)でいい。まずは、
時間がかかるor品質が低い、でいい。検証効率を高めるために、いまは要素数も反復数も十分すくなめで。
細かい変数の調整は配線のあと」

**第2段(訂正後)**: 「方針を少し訂正し、**マルチグリッド化とCPU並列化を配線前にやる**。
どちらのタスクでも**どれくらい高速化したかを調べるところまでをタスクとする**。
なお、**検証材料がいまブラケットの一つしかないので、これを3つ追加し4つにしてから**それら二つに
着手してほしい」

順序は **(1)検証セットを3つ追加 → (2)マルチグリッド → (3)CPU並列化**。

## なぜ2段になったか

第1段のあと、[[four-thirds-cost-law-is-the-jacobi-preconditioner]] の実測が出た。
**費用の4/3乗は前処理の性質であって、マルチグリッドで指数ごと落ちる**と分かったので、
「配線の後の細かい調整」ではなく**土台の性質**に変わった。GPUの話から入って、
GPUが3番目の手だと分かった流れでもある。

## この判断の形が示していること

- **「性能は後」は、性能が定数倍の話であるうちは正しい。指数が変わるなら別。**
  変数の微調整と、費用の伸び方そのものを変える作業を、同じ「性能」の箱に入れない。
- **測る前に順序を決めない。** 第1段は測定前、第2段は測定後。実測1回で方針が変わった。
- **効果の測定までをタスクに含める**という指定が明示的にあった。実装だけ入れて
  「速くなったはず」で終わらせない。
- **題材が1つでは効果を測れない**という理由づけを本人が先に出している。1題材で速くなっても
  一般に効いたことにならない。
