# 画面は、いま動いている最適化経路を映す

duocad `probe_topopt` のビューアについて本人が指示した: **その時点での最新の最適化処理を
可視化する。** 計算側の入口が変わったら、画面もそこへ追随させる。

## なぜ規則として要るか

2026-09-04に実際に起きかけた: 表示タスク(`20260903-2304`)は、塊の自動導出タスク
(`20260903-2234`)より**前**に書かれたため、ボタンの接続先を `anchor.run_pipeline()` と
名指ししていた。2234 が入った後の正しい入口は `design_space.run_topopt()` で、
`run_pipeline()` を既定引数で呼ぶと **`design_mask=None` の旧経路**に入る。

そのまま実装されていたら:

- 画面には新しい4条件が出る
- しかし解いているのは「ブラケットの中を削る」旧問題
- 材料は入力ソリッドの外へ出られない

**見た目が正しいのに中身が古い、という食い違いは画面からは観測できない。** 絵は正しく描かれる
ので、誰も気づかない。タスクを積んだ順序と完了した順序がずれると普通に起こる。

## 含意

- タスクファイルは書いた時点の実装を前提にしている。**着手時に入口が変わっていないか確認する**
  (先行タスクが後から入る構成では、名指しした関数名が失効しうる)。
- 表示と計算は**同じオブジェクトを共有する**。表示用と計算用で導出を2回走らせると、
  余白や格子のわずかな違いで別の問題を見せることになる。
- 開発用の可視化は消さない。塊を利用者に見せないのは本体の UX
  ([[topopt-needs-no-design-space-input]])だが、**見せないことと見ないことは別**で、
  probe には切り替えで残す。答えがおかしいときに「塊が悪いのか最適化が悪いのか」を
  切り分ける手段がゼロだと詰まる。
