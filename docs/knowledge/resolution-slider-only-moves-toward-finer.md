# 解像度のスライダーは細かくする方向にだけ動く

duocad の形状最適化で解像度(要素サイズ)を利用者にどう選ばせるかを2026-09-04に検討した。本人の案は
「上下の制約を決めて、その範囲で自由に設定できるUI」。**範囲を出すことには合意したが、「範囲内で自由」ではなく
「既定＝粗い側の端。細かくする方向にだけ動かす」を採った**(本人了承。2026-09-05に `OptimizePanel.svelte` として実装)。

理由は**両端の性質が違う**こと:

- **粗い側の端は「正しさ」の境界** —— 割ると条件面から格子節点が消え、最小部材幅が表現できない。しかも **silent**
  (例外は出ず、もっともらしい形が返る)。
- **細かい側の端は「都合」の境界** —— 割っても間違いはしない。遅い・落ちる、それだけ。

**同じスライダーの両端として並べると、この非対称が見えなくなる。** さらに「範囲内ならどれでも同じように正しい」
わけでもない —— 細かくすれば体積誤差(±5%振れる)も応力の母集団も安全率も動く。**細かいほど良く、粗いのは妥協**
というのが実態である。

## 採った形

- **既定は粗い側の端**(条件と最小部材幅を満たす、最も安い設定)。最速で「正しい」答えが出る。
- **スライダーは細かくする方向にだけ動く。** 粗い側の端を越える操作を用意しない。
- 細かくして得られるものを言葉で示す(STLの滑らかさ・応力の信頼性・体積精度)。払うのは時間とメモリ。
- **時間は入力にしない。各点の予想時間を帰結として表示する。** 時間から解像度を逆算すると、利用者が知らないうちに
  正しさの境界を割る —— しかも割ったことは画面から見えない。予想時間の当たり方は [[topopt-time-estimate-overshoots-actual]]。

## 一般化

**入力にしてよいのは「何が欲しいか」であって、「どれだけ待てるか」ではない。** 後者を入力にすると、システムは黙って
正しさを削って要求に合わせる。この形は「片側だけが silent に間違う」設定一般に効く(もう一方の端が遅さ・メモリの
ような可視の代償でしかないとき)。

なお**粗い側の端は事前に計算し切れない** —— 最小部材幅と条件面からの要求は出せるが、保持・除外ソリッドの形状からの
要求(細い通路を表現できるか)は中心軸変換に近い話で近似しかない。**事前計算+事後検出の二段構え**にする
(事後検出の一例: [[occupancy-raises-when-no-grid-column-hits-the-shape]])。事前の1本で決め切ろうとすると必ず取りこぼす。
