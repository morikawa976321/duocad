# scipyのCSR行列ベクトル積はGILを解放するが疎×疎の積は同じ手が効かない

duocadのprobe_topopt(トポロジー最適化solver)をCPU並列化するタスクで実測した。

- **疎行列×密ベクトル(SpMV)**: `scipy.sparse.csr_matrix.__matmul__` は内部でGILを解放する。
  行列を行ブロックへ分割し、`concurrent.futures.ThreadPoolExecutor` の `submit`/`result` で
  各ブロックの `block @ x` を投げると、実際にマルチコアで速くなる。実測: 自由度128,064・
  非零978万の行列で、12スレッド 3.8倍(6.66ms → 1.75ms、永続プール使用時)。
- **疎行列×疎行列(sparse@sparse。例: Galerkin射影 `P.T @ A @ P`)**: 同じ「行ブロックへ割って
  ThreadPoolExecutorへ投げる」手法を適用すると、**1スレッドでも単一呼び出しの約2倍遅く、
  14スレッドでも単一呼び出しより遅い**(実測)。各ブロックの積の結果を `sp.vstack` で
  再結合するコストが並列化の利得を上回るため。疎行列積は出力の非零パターンが行ごとに
  不定なので、単純な行分割+再結合が向かない。
- **BLASのスレッド数環境変数(`OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS`)は
  疎行列演算が支配的なコードには効かない**(1→14スレッドで有意差なし、実測)。BLASは密行列
  演算の経路にしか効かないため、疎行列ベースの数値計算では最初に試す価値が低い。

**再利用できる判断**: 疎行列を含む数値計算をCPU並列化するとき、まず「疎行列×密ベクトル」を
探して、それだけを行ブロック並列にする。「疎行列×疎行列」は同じ発想が通用しないので、
実測せずに勾配的に広げないこと。

**副産物**: 行ブロックへの分割は行 `i` の内積の計算順序を変えないので、CSR行列ベクトル積の
並列化は**スレッド数に関わらずビット一致する**(浮動小数の加算順序が変わらない)。
数値再現性(rho場のSHA-256等)を維持したまま並列化したい場面で使える性質。
