# 巻き順の是正を書き出し1箇所に閉じると、後から増えた消費者に漏れる

`skimage.measure.marching_cubes` の巻き順がSTL/OCCT規約と逆である事実は
[[marching-cubes-winding-is-inward-for-stl-occt]] に記録済み。当初そのノートは
「直すのは書き出し1箇所だけで足りる」と結論していたが、**以下の実測でその結論は失効し、生成側で直す方針へ改めた**(2026-09-02)。

duocad `probe_topopt` で実測(単純な直方体の密度場、10x8x6):

- `mesh.build_surface` が返す `faces` は、符号付き体積 `sum(v0・(v1×v2))/6` が **-89.667**。
  `cross(v1-v0, v2-v0)` が外向きな三角形の割合は **0.0**(全数が内向き)。
  `mesh.vertex_normals` も全数が内向き。
- `mesh.write_stl` は書き出し直前に `faces[:, (0,2,1)]` へ入れ替えるので、
  STLだけは正しい(読み戻すと **+89.667**、記録法線が外向きな割合 1.0)。
- ところが `server.py` の `_build_mesh_payload` は `mr.faces` を**そのまま**
  ブラウザへ送り、`web/index.html` が `geometry.computeVertexNormals()` で
  巻き順から法線を導く。**ブラウザ表示だけが内向き法線のまま**になっている。

一般化: **「規約の是正を出力直前に置く」対策は、その配列の消費者が1つのうちは正しいが、
消費者が増えた瞬間に静かに壊れる。**是正は生成側(ここでは `run_marching_cubes`)で
行い、内部表現を最初から規約に合わせるほうが、消費者の増加に対して安全。

検査が拾えなかった理由: `check_mesh.py` の8検査のうち巻き順を見るのは検査7だけで、
それは**STL経路しか通らない**(書き出したSTLを `build123d.Mesher` で読み戻し、
符号付き体積を `abs` 体積と比べるので、STLが裏返れば相対誤差が約2.0になって落ちる)。
残る7検査は巻き順に鈍感である(体積は `abs()`、水密性は辺の共有数、隣接行列は無向、
最小肉厚は法線の内積なので全体反転で不変)。**`mr.faces` を直接使う側 —— ブラウザへ
送る経路 —— の向きを見る検査は1つも無い。**「規約の是正が出力直前にある」形は、
検査もその出力の後ろにしか置けないので、他の消費者を構造的に守れない。
