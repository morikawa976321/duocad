# topopt FEM の GPU 高速化 — 中間結論(2026-10-04)

計画と各段階の数値は [ROADMAP.md](ROADMAP.md)(結果は 10章)。ここは採用/見送りを決めるための材料だけを置く。
**CPU の CG の秒は測っていない**(本人指示)。下の「CPU 換算」は製品の実行記録から出した値で、実測ではない。

## 分かったこと

1. **GPU で解いても、解を CPU 版とビット一致させられる。**
   行列ベクトル積・内積・ベクトル更新を CPU と同じ順序と丸めで行う CG を作り、8 行列(3.3万〜49万自由度)で確認した。
   探索 2 本(4.8mm 格子、16 評価と 80 評価)でも、試行の履歴と採用形状が CPU 版と一致した。
   「GPU 化で数値が変わり、過去の結果と形状を比較できなくなる」という懸念は、この方式では生じない。
2. **CG 単体は CPU 換算の 7〜9.5 倍**(10万〜49万自由度、準備込み)。36万自由度・3,551 反復が 4.8 秒。
   ビット一致を捨てた最速の方式(cuSPARSE)は 9〜12 倍で、差は小さい。
3. **探索全体の倍率は探索の種類で変わる。CG が時間の大半を占める探索(荷重が高く太い形)で 3 倍弱、
   細い形を多数評価する探索(荷重が低い)ではそれより小さい。**
   - 1 評価(`acceptance.inspect`)あたり: 2.0mm 格子で CPU 換算 24〜51 秒 → 9〜12 秒(2.6〜4.2 倍)。CG 以外が 6〜7 秒ある。
   - 製品の実行記録 1 本(1.875mm・1000N・64 評価)への当てはめ: 線形求解 2,771 秒を 7〜8.5 で割ると、
     探索 3,869 秒 → 約 1,420〜1,490 秒(2.6〜2.7 倍)。
   - 細い形の探索では、候補生成(`peel`)が CG より大きい(下の「探索のどこに時間がかかっているか」)。
     ここは GPU では縮まない。
4. **組立はボトルネックではない。** 49万自由度でも組立と切り出しで 2 秒未満。GPU に載せる意味は無い。
5. **細い形(5万自由度以下)では GPU の出番は無い。** 製品は直接解法(1 秒弱)に回しており、GPU の CG はそれより遅い。

## 探索のどこに時間がかかっているか(2026-10-05 追加)

探索 1 本を cProfile にかけた(`results/s8_search_profile_*.json`。hanger・200N・最小幅 10mm、CG は GPU のビット一致版)。
プロファイラは関数呼び出しの多い箇所を重く見せるので、秒は割合を見るために使う(4.8mm の探索はプロファイラなしで 176 秒、ありで 267 秒)。

| 項目 | 4.8mm(設計空間 4.7万セル・80 評価) | 4.0mm(7.8万セル・63 評価) |
|---|---|---|
| 候補生成 `binary_search.peel`(最小幅の判定を含む) | 195 秒(73%)・1 評価 2.4 秒 | 313 秒(78%)・1 評価 5.0 秒 |
| 評価 `acceptance.inspect` | 65 秒(24%) | 81 秒(20%) |
| 　うち線形求解(直接解法と GPU の CG) | 16 秒 | 19 秒 |
| 　うち `np.setdiff1d` | 13 秒 | 21 秒 |
| 　うち保持・除外の判定 `region_check` | 24 秒 | 19 秒 |
| 最初の全材料の評価 `find_initial_feasible` | 11 秒 | 17 秒 |

- この 2 本は細い形に収束し、評価の 8 割が直接解法に回る探索。**候補生成が 7 割強を占め、CG はほとんど効いていない。**
- 候補生成の中身は、1 手ごとに小さい窓へ `scipy.ndimage` の侵食・膨張・ラベリングを呼ぶ処理で、1 本の探索で
  侵食 100〜130 万回、ラベリング 38〜54 万回。1 回は数十マイクロ秒で、回数が費用になっている。
- 1 評価あたりの候補生成は、設計空間が 1.66 倍になると 2.0 倍になった。2.0mm 格子(64万セル)での値は未実測。
- 荷重が高い探索では比率が逆になる。`docs/TOPOPT_STOP_RULE.md` §11 の実測(hanger 1.875mm・1000N・m=4、64 評価)では
  総時間 64.7 分のうち `peel` は 351 秒(9%)で、FEM が 1 回 37 秒。

07 の grid(step20、28 本、`07_grid.json`)の秒を荷重で分けると次のとおりで、細い形を多数評価する側(200N・500N)が 6 割を占める。

| 荷重 | 探索 | 評価(FEM 回数) | 秒の合計 | 1 評価あたり |
|---|---|---|---|---|
| 200N | 4 本 | 421 | 18,600(30%) | 44 秒 |
| 500N | 8 本 | 339 | 18,552(30%) | 55 秒 |
| 1000N | 8 本 | 163 | 12,558(20%) | 77 秒 |
| 2000N | 8 本 | 132 | 12,148(20%) | 92 秒 |

07 は 1 評価の内訳を記録していないので、2.0mm 級の格子で CG・候補生成・その他がそれぞれ何秒かは分からない。
**GPU の効果を 07〜10 の日数に直すには、実寸の探索 1 本で「CG / 候補生成 / それ以外」の秒を取る必要がある**(07 の完了後)。

## 採用した場合に払うもの

| 項目 | 内容 |
|---|---|
| 依存 | CuPy と CUDA ランタイム(pip の wheel、約 1.5GB)。システムへの CUDA Toolkit は不要 |
| VRAM | 49万自由度で 2.5GB(実測)。全設計空間(200万自由度級)は未実測。Unity 等と 16GB を分け合う |
| 足し順への依存 | 内積のビット一致は numpy 同梱の OpenBLAS の実装(0.3.31・Haswell カーネル)に合わせてある。numpy や CPU が変わると合わなくなりうる |
| 上の対処 | 使う前に `np.dot` との一致を自己検査し、合わなければ CPU の CG に戻す。**戻しても結果は同じ**なので、GPU が使えない夜も探索は止まらず結果も変わらない |
| 製品への配線 | `fem.PreparedSystem.solve` の CG の呼び出しに GPU の経路を足す(本検証の範囲外) |

## 07〜10 への当てはめ

- 荷重が高く太い形の探索(1000N・2000N)は 3 倍弱(実行記録への当てはめ 2.6〜2.7 倍)。
  荷重が低く細い形を多数評価する探索(200N・500N)は、候補生成の秒が分からないので倍率を出せない。3 倍より小さいことだけは言える。
  07 の grid ではこの後者が秒の 6 割を占めるので、**全体を「N ÷ 3 日」と見積もるのは楽観的**。
  08〜10 は規模の見積もりが文書に無いので、日数は出していない。
- **結果がビット一致するので、タスクの途中で解法を替えても結果の比較可能性は崩れない。** 変わるのは `wall_seconds` の記録だけ
  (手法間で秒を比べる集計は、GPU に替えた前後で分ける必要がある)。
- ただし 07 に効かせるには、稼働中のタスクが使うコードを変えることになる。本検証では触れていない。

## GPU と独立に効く CPU 側の改善(製品コードの変更。本検証の範囲外)

**候補生成(`peel`)**: 細い形の探索では最大の項目(上の表)。2026-09-24 に大域の数え直しを局所判定へ置き換え済みで、
残っているのは小さい窓への呼び出しの回数そのもの。余地は 2 つある。

- `docs/TOPOPT_STOP_RULE.md` §11 が「まだ入れていない」としている、同じ形状での歩き直しの記憶。
- 1 手ごとの窓の判定を、Python から `scipy.ndimage` を何度も呼ぶ形でなく、1 つのコンパイルされた処理にまとめる。
  判定は真偽と整数だけなので、手の採否が現行と一致することを厳密に検査できる。どれだけ縮むかは未実測。

**評価(`acceptance.inspect`)の固定費**: CG を GPU に載せると、1 評価の半分以上が CG 以外になる。
内訳(2.0mm 格子、1 評価あたり)は次のとおりで、いずれも形の大きさではなく格子の大きさで決まる。

| 箇所 | 秒 | 中身 |
|---|---|---|
| `acceptance.safety_check` の `np.setdiff1d(fixed, floating)` | 約 3.2 | 格子全体の自由度(470万)を相手にした集合演算。`fixed` は 234 個しかないので、ブール配列で引けば 0.007 秒(morikawa976321/duocad#103) |
| `fem.Model.compliance` | 約 1.0 | 全要素の einsum |
| `fem.Model.__init__` の `_build_edof` | 約 0.8 | 格子が同じなら毎回同じ表を作り直している |
| 組立と切り出し | 0.3〜1.9 | 形の大きさに比例(10万〜49万自由度) |

これらを削ると、GPU なしでも 1 評価が数秒縮み、GPU ありなら倍率が上がる(36万自由度で 3.7〜4.2 倍 → `setdiff1d` を無くすと 5 倍前後)。
結果の値は変わらない種類の変更だが、確認は別途要る。

**探索の最初にだけかかる費用**: 1 回目の評価は 2 回目以降より 17〜25 秒長い(2.0〜2.4mm。保持・除外の前計算など)。
同じ模型・同じ格子の探索を何十本も回すときは、探索をまたいで使い回せる可能性がある(中身は未調査)。

## 本人の判断が要る点

1. **見送りライン S_min**(未決)。Claude の提案は探索1本の壁時計で 1.5 倍。太い形の探索(3 倍弱)はこれを上回る見込み。
   細い形を多数評価する探索が上回るかは、候補生成の秒を実寸で測るまで分からない。
2. **採用の作業(製品コードへの配線)に進むか。** 進むなら、07〜10 のどこから切り替えるかも決める。
3. **CPU ベースラインをいつ取るか。** 取るまで倍率は換算値のまま。07 の完了後に、全設計空間の帯と過去ケースの再現と一緒に取るのが自然。
