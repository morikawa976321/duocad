# topopt FEM の GPU 高速化 — 実現可能性検証ロードマップ

**状態: 2026-10-04 に本人が実施を了承(7章)。CPU ベースラインの取得は見送り。見送りライン S_min は未決。
段階0〜6 のうち 07 の稼働中にできる分は実施済み(10章)。判断材料のまとめは [CONCLUSION.md](CONCLUSION.md)。**

## 1. この検証が答える問い

形状探索(`binary_search.find_best_feasible`)の FEM 評価を GPU に載せると、**探索1本の壁時計がどれだけ縮むか**。
縮むとして、**結果の再現性と、CPU 版の過去の結果との比較可能性を保てるか**。

- やること: このフォルダ内の独立スクリプトによる計測と、採用/見送りの判断材料の整理。
- やらないこと: 製品コード(`duocad/topopt/` 等)の変更、製品既定への採用、push。

## 3. 判定の物差し

### 速度

探索1本の壁時計の短縮率を S とする。

    S = 1 / (1 − p + p / s)

p は GPU に載せる部分が探索の壁時計に占める比(段階1で実測)、s はその部分の倍率(段階3・5で実測、転送込み)。
s をいくら上げても S は 1 / (1 − p) を超えない。

**見送りライン S_min は本人が決める値。** Claude の提案は **1.5 倍**。これは実測から出た値ではなく、
採用時に払うもの(製品への配線、GPU 依存の追加、過去結果との比較可能性の再確認)に見合う最低線として Claude が置いた値である。
各段階の撤退条件は「その時点の実測から計算した S の上限が S_min を下回る」に統一する。

### 再現性

同じ入力で解がビット一致するか。CPU の現行はスレッド数に関わらず一致する。

### 同等性

**閾値を先に置かない。** CPU 版自身が持つばらつき(cg と direct の差、1e-13 ノイズを混ぜたときの最終指標の幅)を実測し、
GPU と CPU の差がその内側か外側かで判定する。許容基準は実測の表を見てから提案し、本人の合意で確定する。

## 4. 段階

各段階の成果物は `results/` に JSON と短い要約で残し、段階の終わりに本書の「結果」欄へ結論を1〜3行で書く。

### 段階0: 環境の構築と動作確認

- **測ること**: 検証用 venv(`gpu_feasibility/.venv`、Python 3.11)に GPU ライブラリを入れ、次を確認する。
  (a) GPU を認識する。(b) 倍精度 CSR の行列ベクトル積が CPU と丸め誤差の桁で一致する。
  (c) `cupyx.scipy.sparse.linalg.cg` に `M=` を渡して小さな対称正定値の系が `rtol=1e-9` で収束する。
  (d) 製品の `.venv` が導入の前後で変わっていない(パッケージ一覧の差分なし)。
- **導入するもの**: 第一候補は PyPI の `cupy-cuda13x` と、それが要求する CUDA ランタイムの wheel。合計は 1〜3GB の見込み(実サイズは導入時に記録)。
  動かなければ第二候補の `cupy-cuda12x`、第三候補の PyTorch(CUDA 12.8 以降のビルド)を試す。システムへの CUDA Toolkit のインストールは行わない。
- **合格**: (a)〜(d) がすべて成り立つ。
- **次へ進む条件**: 合格。
- **撤退条件**: どの候補でも倍精度 CSR の行列ベクトル積が動かない。

### 段階1: 時間の内訳の出し直し

- **測ること**: 1評価の壁時計を「組立・切り出し・CG・後処理(応力と判定)・その他」に分けた比。
  - 07 の最終形マスク(`07_masks/`、読み取り専用)と、それを n 層膨らませた形(探索序盤の太い形の代わり)を入力に、
    製品の評価経路を `collect_solve_stats` 付きで呼ぶ。自由度 3万〜40万級を 6〜8 点。
  - 自由度ごとの重みは 2章(a)の実行記録と 07 の台帳から置く。07 の軌道そのものは記録が無いので、重みは近似であると明記する。
- **出すもの**: 帯ごとの p_cg・p_組立・p_切り出し・p_その他と、重み付きの合成値。
  S の上限を 2 通り出す — CG だけ GPU に載せる場合 1/(1 − p_cg)、組立と切り出しも載せる場合 1/(1 − p_cg − p_組立 − p_切り出し)。
- **合格**: 判定はしない(以後の段階の重みを決める段階)。
- **次へ進む条件**: 後者の上限 ≥ S_min。
- **撤退条件**: 後者の上限 < S_min(線形代数を全部 GPU に載せても届かない)。
- **制約**: 全設計空間(120万〜240万自由度)は組立にホスト RAM 7GB 以上が要るため、07 の稼働中は測れない。
  この帯は既存の実行記録の値で代用し、代用であることを明記する。

### 段階2: 計測用行列セットと CPU ベースライン

- **作るもの**: 段階1 と同じ形から、製品の組立コードで K_ff(CSR)・右辺・対角を作り `data/` に保存する(git には載せない)。
  行列ごとに自由度・nnz・nnz/自由度・材料セル数を記録する。
- **測ること**: 同じ行列に対する現行 CG(ヤコビ前処理、`rtol=1e-9`、製品と同じ行ブロック並列)の秒・反復数・最終残差・常駐メモリ。
  スレッド数は 1・7・12。各 3 回。直接解法の領域(5万以下)では `spsolve` の秒も取る(GPU の比較相手になるため)。
- **合格**: 1反復・非ゼロ1個あたりの秒が 2章(a)の 0.41〜0.48 ns と整合する(整合しなければ競合の影響として条件と併記)。
- **次へ進む条件**: 行列セットと基準値がそろう。
- **撤退条件**: なし。
- **扱い**: 07 と CPU・メモリ帯域を奪い合うので、絶対値ではなく同一条件の相対比較として使い、条件(07 の稼働、空き RAM)を結果に書く。

### 段階3: GPU での CG(最小実験)

- **測ること**: 段階2 の各行列について、
  - 転送の秒(ホスト→GPU の行列と右辺、GPU→ホストの解)
  - CG の秒・反復数・最終残差(残差は製品と同じ式で CPU 側で検算)・VRAM のピーク
  - 2 通りの実装: `cupyx.scipy.sparse.linalg.cg` をそのまま使う版と、scipy の CG と同じ漸化式を CuPy で書いた版
- **出すもの**: 自由度ごとの倍率 s(転送込み・抜き)、s = 1 になる損益分岐の自由度、5万以下での直接解法との比較。
  段階1 の重みで合成した S(CG だけ GPU に載せた場合)。
- **合格**: 合成した S ≥ S_min、かつ全行列で残差検算(≤ 1e-6)を通る。
- **次へ進む条件**: 合格なら段階4へ。不合格でも段階1 の「組立まで載せた上限」が S_min 以上なら、段階5a を先に行う。
- **撤退条件**: 組立まで載せた上限に段階3 の実測 s を入れた S が S_min に届かない。
- **見るべき異常**: 同じ算法・同じ前処理なので反復数は CPU とほぼ同数のはず。大きく違えば実装か精度の問題として先に原因を調べる。

### 段階4: 再現性と、解のレベルでの同等性

- **4a 再現性**: 同じ行列・同じ右辺を、同一プロセス内で 10 回、プロセスを分けて 10 回解き、解のビット一致を確認する。
  - **合格**: すべてビット一致。
  - **不合格のとき**: 決定的な行列ベクトル積(cuSPARSE の決定的な算法、または足す順序を固定した自作カーネル)で再試験する。
    それでも一致しなければ「GPU 版は再実行で同じ探索結果を再現できない」を結論に明記し、扱いは本人判断とする(撤退条件にはしない)。
- **4b 解のレベルの差**: 各行列で GPU の解・CPU の cg の解・基準解(直接解法が可能なサイズは `spsolve`、不可能なサイズは `rtol=1e-12` の CPU cg)を比べる。
  変位の最大相対差、コンプライアンス、最大応力、安全率(後処理は製品の関数を CPU で呼ぶ)。
  - **物差し**: 同じ行列での「CPU の cg と基準解の差」。
  - **出すもの**: 差の表と、許容基準の提案。
- **次へ進む条件**: 4a の結果が確定し、4b の許容基準に本人が合意する。
- **撤退条件**: GPU の解が残差検算を通らない、または安全率の差が CPU の cg と direct の差(実測)を桁で上回り、原因を除けない。

### 段階5: 追加の手段(条件付き)

段階3 の結果で要否を決める。段階3 の S が十分なら 5b・5c は行わない。

- **5a 組立を無くす/GPU に載せる**: CG が速くなった後、組立と切り出しが残りの時間のどれだけを占めるかで要否が決まる。
  - 案1: 行列を組まず、要素ごとの演算で K·x を GPU 上で直接計算する(格子が規則的で要素剛性が共通であることを使う)。組立と切り出しが不要になり、ホストの COO(07 のピーク 7〜17GB の主因と見ている。段階1 で確認)も要らない。
  - 案2: COO→CSR の組立を GPU で行う。全設計空間では COO だけで数 GB の VRAM を使うので、空き 10.8GB に収まるかを先に計算する。
  - **測ること**: 1反復の秒(CSR 版との比)、準備の秒(組立との比)、VRAM、4a と同じ再現性試験。
  - **合格**: 段階3 の構成より S が上がり、再現性が 4a と同じ水準で成り立つ。
- **5b 前処理の代替**: 反復数は数千に達しているので、減らせれば CPU・GPU の両方に効く。ただし算法が変わるので解の差は広がる。
  候補は GPU に向くもの(節点ごとの 3×3 ブロックヤコビ、多項式前処理)と、`cupyx` の不完全分解。AmgX は Windows で pip から入らないので対象外。
  - **測ること**: 反復数・1反復の秒・準備の秒・合計秒、4b と同じ差の表。
  - **合格**: ヤコビより合計秒が減り、4b の許容基準を満たす。
- **5c GPU の直接解法(cuDSS)**: 10万〜30万自由度の帯で CG が伸びない場合だけ試す。VRAM に収まる自由度の上限を先に測る。
- **撤退条件**: 5a〜5c を足しても S が S_min に届かない。

### 段階6: 探索のレベルでの同等性

GPU の解法を探索に通すと、最終指標が CPU 版のばらつきの内側に収まるかを見る。
GPU 解法は**検証プロセスの中でだけ**実行時に差し替える(製品のファイルは変更しない)。

- **6a 小さい題材(07 の稼働中に実施可)**: ホスト RAM が 1GB 程度で済む粗い格子の hanger で、
  - CPU 版(ノイズなし)1 本、CPU 版に 1e-13 相当のノイズを混ぜたもの 10 本、GPU 版を 4a の結果に応じて 1 本または複数本。
  - 比べるもの: 最終の材料セル数(体積)、安全率、合否、評価回数。
  - **合格**: GPU 版の最終指標が、CPU ノイズ群の最小〜最大の範囲に入る。
- **6b 過去ケースの再現(07 の完了後)**: 04〜07 から軽い 1〜2 ケース(候補は 2.4mm・2000N、16 solve 前後)を GPU 版で再実行し、台帳の値と比べる。
  7GB 以上のホスト RAM が要るため、07 と同時には走らせない。
  - **合格**: 最終指標の差が 6a で測った CPU ノイズ群の幅の内側。
- **限界**: 10 本は分布の裾を見るには少ない。範囲に入ることは「区別できない」ことを示すだけで、同一であることは示さない。
- **撤退条件**: GPU 版の最終指標が CPU ノイズ群から系統的に外れ(合否が変わる、安全率が目標を割る)、原因を除けない。

### 段階7: 全体効果の見積もりと結論

- **出すもの**(`CONCLUSION.md`):
  - 探索1本の短縮率 S(実測の p と s から。格子別・荷重別)。
  - 07〜10 への当てはめ。08〜10 は規模の見積もりが文書に無いので、S を比で示し、日数は 07 の実績から換算した参考値とする。
  - 採用/見送りの材料: 速度、再現性、同等性、払うもの(GPU 依存、Unity 等との VRAM の取り合い、過去結果との比較の扱い)、採用する場合に必要な作業(本検証の範囲外)。
- **見送りを推奨する条件**: S < S_min、または再現性・同等性のどちらかが本人の許容に入らない。

## 6. 先に見えているリスク

1. **効果が届くのは早くて 08 以降。** 07 は稼働中で、製品コードを変えない本検証の結果は 07 には使えない。08〜10 で使うには、検証の後に採用の作業(範囲外)が要る。
   また 07〜10 の途中で解法を替えると、タスク間の比較に解法の違いが混ざる。
2. **CG だけでは頭打ちになる。** CG が探索の 72% なら、CG を無限に速くしても S は約 3.6 倍で止まる。それ以上は組立を無くす必要がある(段階5a)。
3. **GPU の行列ベクトル積が実行ごとにビット一致しない可能性がある。** 探索は 1e-13 の差で採用形状が変わるので、一致しなければ GPU 版は同じ入力で同じ形を再現できなくなる(段階4a)。
4. **コンシューマ GPU の倍精度演算は遅い**(約 0.4 TFLOPS)。行列ベクトル積はメモリ帯域で決まるので影響は小さい見込みだが、演算の多い案(段階5a の案1)では上限になりうる。
5. **全設計空間の行列は 07 の稼働中に作れない。** 秒の約半分を占めうる帯(100万自由度超)の直接比較は 07 の完了後になる。

## 10. 結果(2026-10-04)

数値の出所は `results/` の JSON。**CPU の CG の秒はどれも実測ではない**(本人指示で測っていない)。
「CPU 換算」は 2章(a)の 0.41〜0.48 ns に、GPU で数えた反復数と nnz を掛けた値(7 スレッド相当)。

### 段階0 — 合格

`cupy-cuda13x` 14.2.0 と CUDA 13 のランタイム wheel(検証用 venv 全体で 1.9GB)で RTX 5060 Ti(compute capability 12.0)を認識。
倍精度 CSR の積は CPU と相対 2.4e-16 で一致、ヤコビ前処理 CG は CPU と同じ 241 反復で収束。製品の `.venv` は導入前後で差分なし。
CuPy 14 の `cg` の引数名は `tol` ではなく `rtol`。

### 段階3・4・5d — GPU の CG(`s3_gpu_cg.json`・`s4_*.json`・`s5_*.json`)

3 つの方式を測った。

- **cuSPARSE 版**: CuPy 付属の `cg`。行列ベクトル積は cuSPARSE。解は CPU と 1e-11〜1e-13 の相対差で違う。
- **積だけ GPU**: scipy の `cg` をそのまま使い、行列ベクトル積だけを GPU の自作カーネルに差し替える。
- **ビット一致版**: 行列ベクトル積・内積・ベクトル更新のすべてを GPU で、CPU と同じ順序と丸めで行う。

- 3.3万自由度は製品では直接解法(約 0.85 秒)に回る領域で、GPU の対象外。
- 全方式・全行列で残差検算(≤ 1e-6)を通り、相対残差は 1e-9 前後。
- VRAM は 49万自由度のビット一致版で 2.5GB。

**再現性(4a)**: cuSPARSE 版を含む GPU の CG 4 種は、同一プロセス 10 回と別プロセスで解がすべてビット一致(3 行列)。
ロードマップの「プロセスを分けて 10 回」は 2 プロセスに減らした。

**CPU とのビット一致(5d)**: 次の 3 つをそろえると、GPU の解は CPU の `scipy.sparse.linalg.cg` の解とビット一致した。

1. 行列ベクトル積: 1 行を 1 スレッドが列番号の昇順に足し、積と和を融合しない(scipy の CSR の積と同じ順序)。
2. 内積: OpenBLAS の ddot の足し順をなぞる(スレッド数ぶんの区間 → AVX2 の 16 本の累算器 → 決まった順でたたむ)。
   8 通りの候補のうち 1 通りだけが、長さ 17〜244万の 14 通りすべてで `np.dot` と一致した(`s5_bitexact_dot.json`)。
   OpenBLAS のスレッド数 1・3・7・14 で一致を確認。
3. ベクトル更新と前処理: 積と和を融合しない要素ごとの演算。

- 6 行列は CPU の解(1 スレッドで計算)とハッシュが一致。残り 2 行列は「積だけ GPU」(6 行列で CPU と一致を確認済み)の解と一致。反復数も全行列で CPU と同じ。
- **前提**: 足し順は numpy 同梱の OpenBLAS(0.3.31・実行時カーネル Haswell)の実装に依存する。numpy・CPU が変われば合わなくなりうるので、
  使う前に `np.dot` との一致を自己検査し、合わなければ CPU の CG に戻す(戻しても結果は同じ)。

### 段階6 — 探索での一致(`s6_search_*.json`)

`binary_search.find_best_feasible` を、CPU の CG(4 スレッド)と GPU のビット一致版で 1 本ずつ走らせた。hanger・4.8mm 格子・最小幅 10mm。

|---|---|---|---|---|---|---|
| 1000N | 16(16 / 0) | 一致 | 一致(4,307 セル) | 一致 | 56.2 → 9.2 | 90.2 → 42.8 |
