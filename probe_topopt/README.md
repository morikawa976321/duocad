### カメラの向き(踏み抜いた罠)

**`demo_conditions()` の拘束面(固定側パッドの x 最小面、法線 `(-1,0,0)`)は軸整列の平面**
なので、カメラの向きが十分 `-x` を向いていないと、隣接する面(同じパッドの側面)の陰に
隠れてほぼ画面に出ない。**旧来の視点(`(0.72, 0.45, 0.86)`)では拘束面の画素がほぼ0だった**
(実測: どの `?debug=anchors` 用の視点でも拘束面ぶんの画素が変化しなかった)。
`web/index.html` の `fitCamera()` の向きを `(-0.75, 0.5, 0.6)` へ変えて解決した。
**`MeshLambertMaterial` を両面描画(`side: THREE.DoubleSide`)にしただけでは直らない** ——
これはバックフェースカリングの問題ではなく、**同じ塊(パッド)の他の面に幾何学的に
遮られている**ことが原因(オブジェクトの奥にある面は、カリング設定に関係なくそもそも
視線が届かない)。塊を利用者に回転させて見る前提の以上、少なくとも既定視点では
4色とも一定の画素数が出る向きを選ぶ必要がある。

## これは何か

duocad 本体に一切手を入れずに、**3Dのトポロジー最適化(SIMP法)が正しく動くことを実証する**
ための隔離フォルダ。本体への統合はこのフォルダの範囲外。

出力はメッシュ止まりでよい(B-rep化はしない) —— そもそも「メッシュ → 編集可能な B-rep」の
汎用変換は OSS に存在しない(engine `no-oss-mesh-to-editable-brep`)。ただし**ボクセルの立方体
描画のままでは階段状に見える。これは描画方法が原因であって解像度が原因ではない**ので、
まず marching cubes + Taubin平滑化で滑らかな三角形メッシュに変えてから、解像度を上げる要否を
判断する(このタスクの順序)。

## 設計空間をB-repから起こす(voxelize.py)

`simp.py` の設計空間は numpy の3次元配列を直接作っているだけで、**OCCTの形状から格子を
起こす経路が無かった**。`voxelize.py` がそれを埋める(**stage1**。境界条件を面に紐づける
「面アンカー」は stage2 = `anchor.py` が担当する。下記「CADの面 → 格子の節点」)。

```python
import voxelize
from build123d import Box, Cylinder, Pos

model = voxelize.voxelize(
    Box(40, 20, 10),                       # 設計空間(TopoDS_Shape / build123d のどちらでも)
    elements_long_axis=40,                 # 最長軸方向の要素数 → 要素サイズが決まる
    keep=Pos(18, 0, 0) * Box(12, 20, 10),  # 保持領域(材料を必ず残す)。省略可
    obstacle=Pos(-10, 0, 0) * Cylinder(4, 20),  # 障害物領域(材料を入れない)。省略可
)
model.grid          # Grid(origin, spacing, shape) —— 立方体要素・ワールド軸整列
model.design        # bool (nx,ny,nz)。設計空間の占有
model.keep          # bool。**設計空間の内側に切り詰め済み**
model.obstacle      # bool。同上
model.free          # design & ~keep & ~obstacle(最適化が動かしてよい要素)
model.soup          # TriangleSoup。三角形ごとに OCCT の面添字(1始まり)を持つ
model.initial_density(0.3)  # SIMP へ渡す初期密度場(保持=1 / 障害物=0 / 外=0)
```

**セル中心規約**: `mask[i, j, k]` は要素 (i,j,k) の**中心**の値。中心のワールド座標は
`origin + spacing * (i+0.5, j+0.5, k+0.5)` で、`mesh.py` の `rho[ex]` と同じ規約。
**新しく格子と実座標を対応づけるときは必ず `Grid.centers_1d` / `Grid.centers_of` /
`Grid.center_of` を通すこと**(添字に `spacing` を直接掛けると半セルずれる。
`mesh.py` は2026-08-30にこれを踏んだ ── engine `marching-cubes-cell-center-half-offset`)。
配列の軸順 `(nx, ny, nz)` は `simp.py` の `rho` (nelx, nely, nelz) とそのまま合う。

格子の作り方: 要素サイズ = 最長辺 / `elements_long_axis`、各軸の要素数 =
`ceil(辺長 / 要素サイズ) + 2`(**周囲に1要素の余白**)、形状は格子の中央に置く。

占有判定は **`kernel.tessellate` が返す三角形群に +z のレイを飛ばして巻き数で数える**
(新規依存ゼロ。numpy だけ)。**`BRepClass3d_SolidClassifier` は本番経路に使わない** ──
1点ずつしか判定できず 100³=100万点をPythonループで回すのは非現実的なので、
`check_voxelize.py` の**神託**としてだけ使う。

守りが2つ入っている。**どちらも実測で必要だと分かったもの**で、片方では足りない:

1. **偶奇(parity)ではなく巻き数(winding)で数える。** レイが2枚の三角形の共有辺を
   ちょうど通ると同じ z に交点が2つ出る。偶奇だとその上の全域で内外が反転する
   (実測: 40×40×10 の箱で、上面の対角線が列の中心を厳密に通り **15,200 mm³ / 正解16,000**)。
   巻き数なら「入る(+1)/出る(−1)」が相殺して壊れない。
2. **レイの (x,y) を列の中心から決定的にずらし、縮退したらずらし幅を変えてやり直す。**
   格子は bbox から起こすので、軸整列した形状では面や辺が列の中心と厳密に一致する縮退が
   **系統的に**起きる。巻き数でも守れないのは**頂点に三角形が集まる点**で、円錐の頂点を
   レイが貫くと「出る」ばかりが数十回数えられる(実測: 円錐+板がずらし幅ゼロでは
   n=6〜40 の全解像度で「巻き数が0に戻らない列がある」と落ちる)。
   **ずらし幅を1つの固定値にすると守れない** —— その値にちょうど合った位置に頂点が来る
   格子を作れば必ず縮退させられる(2026-08-31のQAが実際に再現した)。なので
   `RAY_JITTER_SEQUENCE`(要素サイズの 1e-4 に素数を掛けた6通り)を順に試し、
   縮退を検知したら次のずらし幅でやり直す。**乱数は使わない**ので決定性は保たれる。
   全部だめだったときだけ例外にする。実際に使われた幅と試行回数は
   `stats["occupancy"]["jitter"]` / `["jitter_attempts"]` に出る。

**壊れた入力は黙って通さない。** 次のどれかに当たると `ValueError` で落ちる ──
(a) 三角形が取れなかった面がある、(b) 有向辺の対が揃わない(非水密な開シェル/向きの不整合)、
(c) 符号付き体積が正でない(法線が内向き)、(d) **殻(連結成分)ごとの向きが入れ子の深さと
合わない**、(e) ずらし幅を6通り試してもレイの巻き数が 0 に戻らない列がある、
(f) 保持/障害物領域が設計空間の格子とまったく重ならない、または1要素も掴めない、
(g) 保持領域と障害物領域が重なっている。開いたシェルを黙って通すと
「レイが1回しか交差しない列は全部内部」という**もっともらしいゴミ**が返る。

(d) は**総符号付き体積だけを見ても分からない壊れ方**への対処。内部空洞の殻だけを裏返すと、
総体積は正のまま(実測: 40³の箱に20³の空洞で 56,000 → 72,000 mm³)で「向きは正しい」と
判定され、**空洞が材料として埋まる**。連結成分ごとに符号付き体積を出し、
「他の殻いくつの内側にあるか」を +z のレイの巻き数で数えて、深さが偶数の殻は正・
奇数(=空洞)の殻は負でなければならない、という形で見ている
(2026-08-31のQA指摘。健全な中空の箱は殻2個・体積 [+64000, −8000]・深さ [0, 1] で通る)。

(f) を空マスクとして黙って受け入れないのは、「材料を必ず残せ」と言われた領域が1要素も
掴めないまま最適化が走ると、支えの無い構造がもっともらしく出てくるため。いちばんありそうな
原因は座標系か単位の取り違えなので、**どの領域が / どこにあって / 格子はどこか**を出して落とす。

**stage2 への引き渡し**: `model.soup` は面添字と、B-repから直に取った面ごとの
面積・重心・法線(`soup.face_props`)を捨てていない
(`soup.face_index[t]` / `soup.triangles_of_face(i)`)。`voxelize.closest_triangle(soup, points)`
が各点の最近傍三角形とその距離を厳密に返すので、`soup.face_index[tri]` で面に戻れる。
同じ格子に別のソリッドを載せたいときは `voxelize(other, grid=model.grid)`。

`closest_triangle` は最近傍点を**7候補(3頂点 / 3辺への射影 / 面への射影)の最小値**で求める。
教科書(Ericson)の領域分けを優先順位つきの上書きで書くと、**退化した三角形(2頂点が重なる)で
複数の領域が同時に真になり、後から上書きしたほうが勝って誤った距離を返す**
(2026-08-31のQA指摘。`a=b=(0,0,0), c=(5,4,4), p=(10,4,-8)` で 13.416407865 を返したが、
線分への正解は 12.638010059)。**退化三角形はOCCTの三角形分割に実際に現れる**ので
(円錐の頂点まわりで実測1枚。`shelf_attachment_7.step` では0枚)、入力で弾くのではなく
ここで正しく扱う。**stage2 は面へ戻る経路をこの関数に頼るので、ここの誤りはそのまま伝播する。**

## 塊(設計空間)と面アンカーの対象ソリッドの分離(2026-09-04)

`voxelize(shape, ...)` は**1つのソリッドに2つの役割を兼ねさせる** —— そのソリッドの占有が
`VoxelModel.design`(削る前の塊)になり、同じソリッドの三角形が `VoxelModel.soup` になって
**拘束・荷重に指定できる面はその面だけ**になる。`run_pipeline` は `void = ~design | obstacle` を
最適化へ渡すので、この経路では**材料は入力ソリッドの外へ一切出られない**(答えは必ず「元の形に
穴が開いたもの」になる)。duocad 本体では塊は利用者に見せない合成物で、拘束面・荷重面は保持
ソリッド等の**別のボディ**に付く。この2つを切り離した入口を足したのがここ。

### 塊はどこから来るか

`voxelize.model_from_design_mask(grid, design, *, anchor_shape, keep=None, obstacle=None, on_outside="raise", ...)`。
**塊は呼び出し側が渡す bool マスク**(`grid.shape` と同じかたち)で、ソリッドの占有である必要は
ない。マスクは複製して持つので、呼び出し側があとから書き換えても `VoxelModel` の中身は変わらない。
かたちが格子と違う場合・全要素 False の場合は `ValueError`(黙って全体を塊にしない)。
戻り値は既存と同じ `VoxelModel` で、`stats` は `voxelize()` と同じキーに `design_source="mask"` と
`on_outside` を足したもの。**`occupancy` キーは無い**(塊がソリッド由来でないため)。

### 面アンカーの対象はどこから来るか

`anchor_shape` から来る。`TopoDS_Shape` / build123d のオブジェクト / **既に作った `TriangleSoup`**
のいずれかを受ける。**面添字は渡したものの面の並びで決まる**ので、面を選ぶのに使った
`TriangleSoup` があるならそれをそのまま渡すこと(作り直すと面添字が食い違いうる)。
`build_anchors(soup, grid, ...)` はもともと三角形群と格子を別々に受け取っていて**下位は既に
分かれていた**。束ねていたのは `voxelize()` と `anchors_for()` の側だけで、
`anchors_for(model)` は `build_anchors(model.soup, model.grid)` のままでよい。

### はみ出しは例外

`keep` / `obstacle` は同じ格子に載せる(内部は `voxelize(..., grid=grid)` と同じ道)。
**塊からはみ出したら既定で `voxelize.OutsideDesignSpaceError`**。`ValueError` の派生なので既存の
`except ValueError` はそのまま効く。文面に「どの領域が何要素はみ出したか(領域の総要素数つき)」を
書き、`e.outside`(`{"keep": n, "obstacle": n}`)で機械からも引ける。旧経路 `voxelize()` は
`keep & design` で黙って切り詰め、件数は `stats["keep_dropped_outside"]` に残るだけだった。
**塊を自動で決めるようになるとはみ出しは普通に起こる**ので、新しい入口では既定を例外にした。
切り詰めてよいと分かっているときだけ `on_outside="clip"` を明示する(結果は旧経路と一致する)。

### 端から端まで

`anchor.run_pipeline(shape=soup, design_mask=mask, design_grid=grid, fixed_face=..., load_face=...)`。
`design_mask` と `design_grid` は両方渡すか両方省略する(片方だけは `ValueError`)。渡したときは
**`shape` は塊ではなく面アンカーの対象**になり、`shape` の省略は許さない。あわせて `keep` /
`obstacle`(保持ソリッド / 除外ソリッド)をどちらの経路でも渡せるようにした(どちらも同じ格子に
載り、マスク経路でははみ出しが例外になる)。省略時(既存のデモ経路)の挙動は1ビットも変えていない。
戻り値に `solid`(ρ=1 に固定した要素のマスク)と `void` を足した(既存キーは不変)。

### まだやっていないこと

**塊をどのロジックで決めるか(箱・凸包・カプセル・粗く回す等)は未着手。** ここでやったのは分離
だけで、下の検査4で使う「一回り大きい箱」は**分離を実証するための足場**であって、採用した導出
ロジックではない。4条件(保持ソリッド・除外ソリッド・拘束面・荷重面)から塊を導く経路は後続
タスクで入れる。

### 実測(2026-09-04・分離の実証。`check_design_space.py` の検査4)

合成ブラケット(`demo_bracket()`: 60×24×24 の箱 + 8×8×6 の耳。bbox は x -30..30 / y -12..12 /
z -12..18)の**面はそのまま**にして、**塊だけ**を差し替える。格子は両方とも同じ

## 4条件から塊(設計空間)を導出する — 案1: 外接直方体+余白(2026-09-04)

利用者は**4条件を入れてボタンを押すだけ**で、塊は最後まで見ない(engine
`topopt-design-space-never-shown-to-the-user`)。塊を見せない以上、**塊は必ず答えを含むだけ大きく
取る**必要がある。`design_space.py` はその導出を1本入れたもので、**案1(条件の点群の外接直方体+
余白)**。これは最終形ではなく、後続の「粗く1回回して膨らませる」案(案5)と比べるための
**ベースライン**である。

### 入れるものと出るもの

```python
import design_space as ds

cond  = ds.Conditions(keep=保持ソリッド, fixed_face=拘束面の面添字, load_face=荷重面の面添字,
                      obstacle=除外ソリッド, anchor_shape=None)   # anchor_shape 省略時は keep
space = ds.derive(cond, margin_ratio=0.25, elements_long_axis=40)  # → DesignSpace
out   = ds.run_topopt(space, volfrac=0.3, max_iter=60, stl_path=...)  # 端から端まで
```

`Conditions` は**4条件しか受け取らない**(設計空間ソリッドを渡す口が型に無い)。`anchor_shape` は
第5の条件ではなく「面添字が誰の面の並びのものか」の指定で、省略すると保持ソリッドになる。
`DesignSpace` は `grid` / `mask`(塊の bool 配列)/ `model`(`VoxelModel`)/ `soup`(面アンカーの
対象)/ `bbox_min`・`bbox_max`(**余白を足す前**の条件の外接直方体)/ `margin` / `stats`。

導出の手順:

1. **条件の点群** = 保持ソリッドの三角形頂点 ∪ 拘束面の三角形頂点 ∪ 荷重面の三角形頂点。
   **除外ソリッドは入れない** —— 除外は塊から引くものであって、塊を広げる理由にはならない。
2. その点群の**軸整列外接直方体**に、**最長辺 × `margin_ratio`** の余白を全軸へ足す。
3. `grid_for_bbox` で格子を起こす(既存。要素サイズ = 余白後の最長辺 / `elements_long_axis`)。
4. **塊 = 直方体の占有 − 除外ソリッドの占有。**
5. 保持ソリッドが塊に完全に含まれることを確認する(`model_from_design_mask` の
   `on_outside="raise"`)。

### 除外ソリッドを `obstacle` に渡さない(設計判断)

除外ソリッドは**塊を作る時点で引き切り**、`voxelize.model_from_design_mask` の `obstacle` には
**渡さない**。

- 塊 = 直方体 − 除外 と定義した以上、除外の領域には塊の要素が1つも無い。
  `model_from_design_mask` は `keep`/`obstacle` が塊の内側に収まることを要求するので、**同じ除外を
  `obstacle` として渡すと必ず全要素はみ出して `OutsideDesignSpaceError` になる**(検査8がこれを
  実際に突いて記録している。文面は「座標系・単位が違う」と誤誘導するので、なおさら渡さない)。
- **最適化に渡る情報は同じ。** `run_pipeline` は `void = ~design | obstacle` を作るので、除外を
  塊から引いてあれば `~design` 側で同じ要素が落ちる。
- **`on_outside="clip"` へ倒す選択はしない。** clip は「塊からはみ出した保持/除外を黙って切る」
  指定で、前タスクが入れた「はみ出しは例外」という保証をこの経路だけ骨抜きにする。塊の外の除外は
  本来ただの no-op であって、切り詰めが要る状況ではない(検査8で no-op であることを固定した)。

代わりに、**除外が保持を食っている**ケース(塊から引いた結果、保持が塊に入らなくなる)は保持の
はみ出しとして現れ、`design_space.DesignSpaceTooSmallError`(`OutsideDesignSpaceError` の派生)に
なる。文面で除外の重なりと `margin_ratio` を名指しする。

### 格子の外は誰も数えていない(前タスクのQA指摘を塞いだ)

`voxelize` のはみ出し判定は**格子の内側しか見ていない** —— 保持ソリッドが格子の外へ出た分は
`keep_dropped_outside` にも入らず例外にもならない(格子の外にはセル中心が存在しないため)。案1は
格子を条件の外接直方体から起こすので、**余白が負のときにここを踏む**。`derive` は
`model_from_design_mask` を呼ぶ前に、保持ソリッドの **B-rep の bbox** が格子のワールド箱に入って
いることを自分で見て、外れていれば `DesignSpaceTooSmallError` にする(検査9で、比率 -0.05 以下が
実際にここで落ちることを固定してある)。

もう1つ塞いだ食い違い: `run_pipeline` は保持ソリッドを**自分でもう一度**格子へ載せるので、
三角形分割の細かさが `derive` と違うと「ここで通した塊が向こうでは通らない」が起こりうる。
`derive` は格子が決まったあとに `deviation = 要素サイズ × DEFAULT_DEVIATION_RATIO` を取り直して
`run_pipeline` と揃え、`run_topopt` は**両者の保持要素が1ビットも違わないことを毎回確かめる**。

### 余白比率をどう決めたか(既定 0.25)

**これが案1の自由パラメータであり、弱点そのもの。** 利用者に見せない値なので、小さすぎると答えの
居場所を黙って削り、誰も気づけない。値は上の表から決めた:

- **比率 0.05 以下では、要求された材料がそもそも塊に入らない**(絶対体積の表。volfrac が 1 を
  超える)。相対体積のままだと「入らない」が「材料が減った」に化けて見えなくなる。
- **比率 0.10 では、最適化が置いた材料の 34.2% が塊の壁に接している** —— 形を決めているのが荷重と
  拘束ではなく**箱の壁**になっている。0.25 で 8.9%、0.40 で 3.3%。**ここで比べているのは材料比
  (表の括弧の右側)であって、塊比(左側)ではない。** 塊比は余白を広げると分母の塊が膨らむぶん
  だけ勝手に下がるので、「箱の壁が形を決めているか」の指標にならない。
- **コンプライアンスは 0.10 と 0.25 を区別しない**(材料の総体積を固定した比較で 3.14 → 3.18 →
  3.32 → 2.89 とほぼ横ばい・非単調で、0.10 のほうがむしろわずかに良い)。**この2つを分けている
  のは壁への接触だけ**(34.2% → 8.9% と 3.8 倍下がる)。0.40 まで上げても接触は 3.3% にしか
  下がらず、要素数が 2.0 倍・所要が 1.3 倍になる。
- したがって既定は **0.25**。「壊れない一番小さい値」ではなく「**答えが変わらなくなる一番小さい
  値**」に取り、そこから下げない。

**壁への接触は 0 にならない。** 箱は箱なので、どれだけ広げても答えの外周はどこかで箱に触れる
(0.50 でも 3.3% 残り、0.40 から下がらない)。案1は「塊が答えを含む」ことを**保証できない** —— これが案5(粗く1回
回して膨らませる)を試す動機である。

### 案1の限界(数字で分かったこと)

1. **姿勢依存。** 同じ部品を世界の z 軸まわりに回すだけで塊が 1.2〜1.4 倍になり、**同じ volfrac
   のまま材料が 22〜34% 増える**。軸整列の直方体を使う限り消えない。
   **余白が「最長辺 × 比率」なので単調ですらない** —— 45° では最長辺自体が縮む(63 → 55.9mm)
   ので余白も縮み、30° のほうが塊が大きくなる。「45° が最悪」と決めつけて測ると見落とす。
2. **相対体積制約だと、塊を変えるだけで別の答えが出る。** volfrac 固定の表ではコンプライアンスが
   6.57(0.10)→ 1.68(0.50)と 4 倍動くが、これは設計が良くなったのではなく**材料が 7 倍
   入っただけ**(46,805 → 326,401 mm³)。材料の総体積を固定した表では 3.14 → 2.89 とほぼ横ばい。
   **体積制約を絶対量(mm³/g)へ倒す未決の判断は、この2つの表の差がそのまま材料になる。**
3. **余白を大きくすると、要素数を固定したままでは保持ソリッドが痩せる。** `elements_long_axis`
   を 28 に固定して比率だけ上げると、保持の要素数は 0.25 で 61 → 0.6 で 26 → 1.5 で 4 と減る
   (余白が要素サイズを食うため)。**保持が 0 要素になっても「はみ出し 0」は成立してしまう**ので、
   検査6は要素数が 1 以上あることも見る。
4. **検査は「答えの居場所が残っているか」を見ていない。** 検査[5]-[9]のどれかが落ちるのは余白が
   ほぼ無くなってからで、実測では比率 -0.05 以下で「保持ソリッドが格子の外へ出ている」として
   落ちる(-0.02 でも -0.01 でも全部緑)。**比率 0.00 でも全部緑になる。** 案1の余白が小さすぎる
   ことの本当の害 —— 答えの居場所を削ること —— は検査には映らない。既定値 0.25 の根拠は検査では
   なく上の実測にある。

## 4条件から塊を導出する — 案5: 粗く1回回して膨らませる(2026-09-04)

入口は **`design_space.derive_from_coarse_run(conditions, ...)`**。案1(`derive`)と**同じ型・
同じ不変条件**の `DesignSpace` を返すので、`run_topopt(space, ...)` も表示側もそのまま受けられる。
**案1は置き換えていない** —— 並べて足しただけで、既定は案1のままである(理由は下記「既定をどちらに
すべきか」)。

案1〜案4は**条件の位置だけ**から塊を決める(どこに材料が要るかを一切見ていない)。案5だけが
**一度解いてから決める**。

### 手順

1. **案1で粗い塊を作る**(`derive` を粗い解像度で呼ぶ。新しい箱の作り方は発明しない)。
2. 粗い塊で SIMP を短く回す(`run_topopt`)。
3. ρ を閾値で二値化し、**本番の格子へ最近傍で再サンプル**する。
4. **膨張**(mm)。
5. **4条件の要素(保持・拘束アンカー・荷重アンカー)を無条件で OR し、除外を引く。**
6. 連結性ガード(`assert_faces_connected`。6近傍)を通す。

**再サンプルの対応は物理座標で取る。** 粗い格子と本番の格子は原点も要素サイズも違う
(格子は箱に合わせて切り直されるため、要素数の比にも要素サイズの比にもならない)。添字の割り算で
済ませると別の塊になる —— 検査[11]がその2つを同じ配置で並べて見せている。

### 膨張は mm で持ち、**本番の格子**でかける(設計判断)

- **単位は mm。** 層数で持つと、格子が姿勢と余白ごとに切り直されるぶん(要素体積 62.99 →
  66.43 mm³)同じ設定が姿勢ごとに別の物理距離になる。
- **かける格子は本番側**(タスクの手順は「膨張 → 再サンプル」の順だが、**入れ替えた**)。
  理由は実測である: 粗い格子でかけると膨張の量子が粗い要素サイズ(6.75mm)になり、
  **0mm / 2mm / 4mm がすべて同じ塊(2,414 要素)になった**。mm で指定できるのに 2〜3 段階しか
  取れないなら、mm で持つ意味が無い。本番の格子なら量子は本番の要素サイズ(3.635mm)まで下がる。
- **それでも「1要素より細かくは効かない」。** 受入検査の題材(要素 6.75mm)では 4.0mm と 0.0mm が
  1要素も違わない。`bench.DESIGN_SPACE_COARSE["dilate_mm"]` が 8.0 なのはそのためである。

### 膨張は何を守っているか(検出力の実測)

**膨張0にすると、両方の姿勢で `ZeroDivisionError` になって最適化に入れない。**

理由は構造的である。**膨張0の塊は「粗い段がその材料を置いた場所」そのもの**なので、要求した
材料は必ず塊の容量の端に張り付く(0° で 92.8%、30° でも同様、材料 50,000 mm³ に落としても
1,132 要素 = 92% で同じ)。体積目標が達成可能区間の端にあると OC の二分探索が
`(l2-l1)/(l1+l2)` で `l1 = l2 = 0` へ落ちる —— `20260904-0142` が記録した、**この変更より前から
ある性質**である。

**注意: `simp.VolumeTargetError` は出ない。** 目標(2,241 要素)は容量(2,414 要素)より小さいので
体積の口のガードは通り、**その先の OC が退化する**。「区間の中なら安全」ではない。

タスクが検出力の条件に挙げていた (a) コンプライアンスの悪化 / (b) 連結性ガードの落下は
**どちらも起きなかった**:

- (a) は起きない。膨張 4mm(塊が案1の半分)でも C は 3.1788 で案1の 3.1796 と区別が付かない。
- (b) も起きない。**最近傍の再サンプルは連結性を壊さない**(粗いセル1つが本番セルの連続した
  塊へ写り、隣り合う塊は面で接するため)。膨張0でも塊は1成分のままだった。

したがって **この膨張が守っているのは「答えの質」ではなく「要求した材料が塊に入ること」** である。
なお**閾値を 0.99 まで上げて粗い段の材料をほぼ全部落とすと、連結性ガードが落ちる**
(2成分・拘束側と荷重側が別成分)。案5の塊が切れうることは実在するので、ガードは飛ばせない ——
受入検査[11]がこれを検出力の確認に使っている。

### 既定をどちらにすべきか(このタスクの判断)

**このタスクでは既定を案1のまま据え置いた。** 比較表の全項目で案5が案1以上ではない
—— 0° の壁に接した材料だけが 8.8% → 9.1% と負けている。

**判断としては、案5へ倒すのが妥当だと考える。** 根拠:

- 負けている唯一の項目は 0.3 ポイントで、**同じ指標が 30° では逆に勝っている**(7.9% → 7.8%)。
  材料を 50,000 mm³ に落とすと 0° でも勝つ(4.51% → 4.50%)。**姿勢と材料量を跨いで一貫して
  負けている項目は無い。**
- 案5は**案1の弱点をどちらも消す**: 姿勢依存(1.38倍 → 1.01倍)と、余白比率という
  利用者に見えない自由パラメータの効き(案5にも閾値と膨張があるが、**閾値は既定の膨張では
  ほとんど効かない**)。
- 速い(0.85倍 / 0.69倍)。

**倒す前に潰すべき穴が2つある**(だからこのタスクでは倒していない):

1. **膨張0の `ZeroDivisionError` は文面に体積も塊も出ない。** 案5を既定にするなら、
   「材料が塊の容量に対して大きすぎる」を**名指しで**落とす口が要る
   (`simp.VolumeTargetError` は区間の内側では黙る)。
2. **1つの題材(`demo_conditions`)でしか測っていない。** 姿勢は2つ振ったが、条件の配置は1つ。
   engine `voxelize-ray-degeneracy-is-not-monotonic-in-resolution` と同じで、
   **1点で通ったから採る、をやらない。**

(engine `topopt-design-space-never-shown-to-the-user` により、最終的にはどちらか一方が
利用者から見えない既定になる。)

### 案5でも消えていないもの

- **粗い段は案1の箱の中で回す。** だから案1の余白比率は**案5にも残っている**
  (`derive_from_coarse_run(margin_ratio=...)`)。案5は箱を小さくするのではなく、
  **箱の中を削る**。
- **格子は案1と同じ**(`nelx*nely*nelz` は変わらない)。姿勢で格子が切り直されること自体は
  案5でも起きる(0° [28,18,19] / 30° [28,24,19])。**消えたのは塊の要素数の姿勢依存であって、
  格子の姿勢依存ではない。**
- **道の細さ・最適化後の材料の連結性は相変わらず見ていない**(連結性ガードの契約のまま)。
- **`server.py` / `web/index.html` は案1のまま。** 画面を案5へ倒すのは既定が決まってから
  (`shot.mjs` の反復数の期待値と `screenshots/` の撮り直しが付いてくる)。

## 塊の中で拘束と荷重がひと続きかを検査する(連結性ガード。2026-09-04)

塊から除外ソリッドを引いた結果、**拘束面と荷重面が別々の島に落ちる**ことがある。そうなると
壁と荷重をつなぐ道が塊の中に存在しない。利用者は塊を見ない
(engine `topopt-design-space-never-shown-to-the-user`)ので、**塊の不備は利用者側からは
観測できない**。だから `design_space.derive` が**つながりを確認してから返す**。

### 連結性の定義: 6近傍(面で接する)

`scipy.ndimage.label` を `generate_binary_structure(3, 1)` で取る(`design_space.NEIGHBOURHOOD = 6`)。
**26近傍にしない。** 角1点・稜1本だけで触れている2要素が共有するのは節点1つで、それは回転を
止められないピン接合(機構)にしかならない —— 力の道として成立しないものを「つながっている」と
数えると、この検査は「切れていない」と言い張りながら宙に浮いた形を通す。検査[10]が、角1点だけで
接する2島を題材にこの定義と実装の一致を見張る(同じ 2島が 26近傍では1成分になることも
同じコードで出す)。

### 何を見て、どこで落とすか

- 対象は **塊 − 除外ソリッド**(`DesignSpace.mask` と同じもの)。
- 拘束側・荷重側の要素は `AnchorTable.element_mask([face], layers=1)`。`layers=1` は
  `anchor.run_pipeline` が ρ=1 に固定する範囲(`keep_layers` の既定)と同じ。
  **塊からはみ出したアンカー要素は落として数える** —— 道になるのは塊の中の要素だけ。
- 拘束側が乗っている連結成分の集合と荷重側のそれに**共通のラベルが1つも無ければ**
  `design_space.DesignSpaceDisconnectedError`(`ValueError` の派生)。文面には
  **成分の数・各成分の要素数・拘束側と荷重側がどの成分にいるか**が入り、例外オブジェクトの
  `components` / `fixed_labels` / `load_labels` から機械でも引ける。
- **`DesignSpaceTooSmallError` とは別の型にしてある。** あちらの文面は「`margin_ratio` を上げろ」で、
  分断には効かない直し方を指す(余白を上げても塞がれた道は開かない)。
- **アンカーの表は `run_pipeline` と同じ作り方(全面・既定の半径)で作る。** `build_anchors` の
  `faces=` で2面に絞ると稜線の規則(節点は最も面積を配った面が持つ)の競争相手が減り、
  **向こうとは別の節点集合**になる —— 同じものを見ているつもりで違うものを見ることになる。
  費用は実測 9ms(長辺22要素)。
- **保持ソリッドの連結性は見ない。** 保持が浮いていても、最適化が材料でつなぐのが正しい
  振る舞いになりうる。見るのは拘束↔荷重の1点だけ。
- **条件面のアンカーが空のときは連結性を見ない**(`skipped: empty_anchor_faces` を返す)。
  それは「要素サイズより小さい面にアンカーが付かない」という別の穴(engine
  `face-to-node-anchoring-loses-faces-smaller-than-the-cell`)で、ここで落とすと
  `empty_faces()` を見る既存の口より手前で別の例外に化ける。
- **挿入位置は `model_from_design_mask`(= 保持が塊に入っているかの確認)の後。** 前タスクの契約は
  「格子外ガードより前」と書いているが、そこからは意図的に外している。3つの位置を実際に試した:

  | 位置 | `check_design_space.py` |
  |---|---|
  | 格子外ガードより**前**(契約の指定) | **検査[9]が落ちる**(57件中1件 FAIL) |
  | 格子外ガードの後・`model_from_design_mask` の前 | 全緑 |
  | `model_from_design_mask` の後(**採用**) | 全緑 |

  **必須なのは「格子外ガードより後」の1点だけ。** 余白比率 -0.05 / -0.10 では保持ソリッドが
  格子の外へ出るが、その前に条件面のアンカー要素が塊から消えるので、前へ置くと連結性が先に
  発火し、検査[9]の梯子の verdict が「格子外」から「拘束側のアンカー要素が塊の中に1つも無い」へ
  化ける。**`model_from_design_mask` の前か後かは、いまの検査では固定されていない**(どちらも
  全緑)—— 後にしてあるのは、除外が保持を食っている配置では「保持がはみ出している」ほうが
  原因に近い診断だという判断による。
  なお**検査[6]は位置を変えても動かない**: 検査[6]の除外(`Box(10, 30, 30) @ (-30,0,0)`)は
  塊の断面を塞がないので、前へ置いても連結性は通る(実測: 1成分・拘束側の要素が63個
  除外の外に生き残る)。「上へ動かすと検査[6]が落ちる」は誤りで、2026-09-04のQA指摘を受けて
  実測し直して書き換えた。

### 切れている塊をそのまま最適化に通すと何が起きるか(実測 2026-09-04)

題材は `design_space.severed_conditions()` —— `demo_conditions()` の除外ソリッドを、2つのパッドの
間を丸ごと塞ぐ壁(厚さ10mm・塊より大きい断面)に差し替えたもの。**連結性の確認だけを迂回して**
(`assert_faces_connected` を no-op に差し替え)最後まで回した。格子は長辺22要素、60反復。

| 配置 | volfrac | 何が起きたか |
|---|---|---|
| 0° | 0.30 / 0.50 | **1反復目で `ZeroDivisionError: float division by zero`**(`simp.py:472`、体積制約の二分法 `while (l2 - l1) / (l1 + l2)`)。numpy の警告が 1,099 件(`invalid value` / `overflow in divide`)。STL は出ない |
| 0° | 0.15 | **60反復を最後まで走り、STL(88 KB)が出る。例外も警告も無し** |
| 30° | 0.15 / 0.30 / 0.50 | **60反復を最後まで走り、STL(181 KB)が出る。例外も警告も無し** |

最後まで走った2件を、つながっている系と並べる:

| | つながっている(参照) | 切れている 0° / vf 0.15 | 切れている 30° / vf 0.30 |
|---|---|---|---|
| 例外・警告 | 無し | 無し | 無し |
| 反復 | 60 | 60 | 60 |
| 塊の要素数(連結成分) | 4,254(**1**) | 3,705(**2**) | 5,205(**2**) |
| コンプライアンス 初期 → 最終 | 30.06 → **3.33** | 1,570,220 → **1,570,197** | 1,348,123 → **1,348,120** |
| 60反復での改善 | 9.0倍 | **0.0014%** | **0.0002%** |
| 達成 volfrac | 0.326 | 0.187 | 0.326 |
| 材料 | 110,022 mm³ | 54,825 mm³ | 131,827 mm³ |
| ρ>0.5 の連結成分 | **1** | **4** | **3** |
| 拘束側 / 荷重側がいる成分 | 1 / 1(**同じ**) | 1 / 2(**別**) | 1 / 2(**別**) |
| STL | 102 KB | 88 KB | 181 KB |

**結論: 検査が無いと、切れている系は2通りに壊れる。どちらも利用者には見えない。**

1. **黙って形が出る**(0°/vf 0.15、30° の全 volfrac)。例外も警告も無く、60反復を走り切り、
   体積制約も満たし、STL も出る。出てくるのは**拘束側の塊と荷重側の塊が別々に浮いた形**で、
   ρ>0.5 の材料は 3〜4 個の島に割れ、拘束側と荷重側は一度も同じ島に入らない。
   コンプライアンスは参照の**約 40 万倍**だが、**利用者はコンプライアンスを見ない**(見るのは形)。
   60反復かけて 0.001% しか下がらないのは「最適化する余地が無い」ことの表れだが、
   これも表に出ない。
2. **原因から遠い場所で落ちる**(0°/vf 0.30・0.50)。`ZeroDivisionError: float division by zero`
   で、文面には設計空間も連結性も出てこない。

**`simp` 側の拘束不足ガードがなぜ作動しないか。** 空要素も剛性の下限 `emin`(既定 1e-9)を持ち、
`simp._floating_dofs` が「空要素にしか触れない節点」を拘束側へ足すので、**荷重側の島は emin の
要素越しに固定節点へぶら下がる**。K は特異にならず、`Model._verify_solution` の残差検算も通る
(実測 max|u| = 1.58e6、コンプライアンス 1.57e6)。`emin` を 1e-12 まで下げると残差検算が
作動する(`残差 2.934e-05 > 1e-06`)ので、**この経路は emin の大きさ次第で黙る**。
**塊の分断は塊を組み立てる側でしか安く確実に検出できない。**

### 検査[10](`check_design_space.py`)

1. 正常系(案1の導出)が通り、拘束と荷重が同じ成分にいる。両側のアンカー要素が塊の中に
   実際にあることも見る(自明に通るのを防ぐ)。
2. 拘束と荷重の間を除外ソリッドで断ち切ると `DesignSpaceDisconnectedError`。文面に成分数と
   両者の成分が出ること、`DesignSpaceTooSmallError` **ではない**こと、
   **壁を外すと同じ条件が通る**こと(落とした原因が壁であることの裏取り)。
3. 塊を**直接**2つの島にして `assert_load_path` に渡すと落ちる。**隙間を埋めると通る**
   (構造的に落ちているのではないことの確認)。
4. **角1点だけで接する2島**が落ちる。同じ `element_components` を 26近傍で呼ぶと1成分に
   なることを並べて出す。
5. 片側のアンカー要素が塊の中に1つも無い場合も落ちる。

### 検査に入れなかったこと

- **保持ソリッドの連結性**(上記のとおり見るべきものではない)。
- **「道が細すぎる」の判定。** 6近傍でつながってさえいれば通る —— 幅1要素の糸でつながっている
  塊も「つながっている」と判定する。細さの妥当性は最適化の仕事であって、塊の妥当性ではない。
- **最適化後の材料の連結性。** `mesh.remove_islands` が最大連結成分だけを残す既存の処理があるが、
  それは出力の後処理で、塊の不備は直せない(上の実測がそのまま示している —— 島が残ったまま
  STL になる)。

## 体積目標を絶対量(mm^3)で指定する(2026-09-04)

**内部表現は絶対量、利用者の入力は安全率**という2層のうち、**内側の層**。塊を自動で導出する
ようになると、余白比率や姿勢で塊の大きさが変わり、**同じ分率でも材料の量が変わってしまう**
(下の実測では余白比率 0.10 → 0.40 で 4.56倍)。分率の口はそのまま残してある(既存の受入検査が
すべてこれを使う)。

### 口(3層とも同じ2語)

| 層 | 呼び方 |
|---|---|
| `simp.optimize` | `volfrac=` / `material_mm3=` + `element_volume_mm3=`(要素1つの体積) |
| `anchor.run_pipeline` | `volfrac=` / `material_mm3=`(要素体積は**格子から自分で決める**) |
| `design_space.run_topopt` | `volfrac=` / `material_mm3=`(そのまま `run_pipeline` へ) |

- **`volfrac` と `material_mm3` は排他**(両方渡すと `ValueError`)。どちらも省略すると
  `simp.DEFAULT_VOLFRAC`(=0.3)。
- **`optimize` は格子の寸法を知らない**(`nelx`/`nely`/`nelz` しか受け取らない)ので、
  絶対量を渡すときは `element_volume_mm3` も要る。上位2層(`run_pipeline` / `run_topopt`)は
  `voxelize.Grid.element_volume`
  から自分で決めて渡すので、**呼び出し側が `mm^3 → 要素数` を書く必要はない**
  (書くと、格子の作り方が変わったときに黙ってずれる)。
- 分率で回すときも要素体積は渡っているので、`Result.target_material_mm3` /
  `achieved_material_mm3`、`run_pipeline` の戻り値の `target_material_mm3` /
  `achieved_material_mm3` / `element_volume_mm3` はどちらの経路でも埋まる。

### 単位

- **絶対量は mm^3。材料の総体積**であって、`solid_mask`(必ず材料を残す領域)のぶんを**含む**。
- **質量(グラム)は持たない。** 密度を掛けるのは表示上の換算であって、最適化の内部表現に
  持ち込まない —— 持ち込むと「材料をどう定義するか」という別の問題が入ってくる。

### 達成不能な目標は例外(`simp.VolumeTargetError`)

達成できるのは **`[solid の体積, (solid + 動かせる要素) の体積]`** の区間だけ。この外は
`VolumeTargetError`(`ValueError` の派生)で落とす。属性 `side`(`"below_minimum"` /
`"above_capacity"`)・`shortfall_mm3`・`min_mm3` / `max_mm3` で機械から引ける。

```
体積目標 9984mm^3 は達成できない: 動かせる 830 要素と固定材料 2 要素を全部埋めても
6656mm^3 で、目標が 3328mm^3 超えている(塊を広げるか、目標を下げること)
```

**「黙って端に張り付く」わけではなかった(2026-09-04実測)。** ガードを外した状態で区間の外を
指定すると、

| 指定 | ガードが無いとどうなるか |
|---|---|
| 総体積を超える(実効分率 1.501) | OC の二分探索が退化して `ZeroDivisionError: float division by zero` |
| `solid_mask` を下回る(実効分率 -0.002) | 密度が負になり `K U = F が解けていない(残差 …)` |

どちらも落ちはするが、**文面に体積の話が1文字も出ない**(拘束不足を疑えと言ってくる)。
ガードの値打ちは「落ちること」ではなく **「どちら側にどれだけ足りないかを名指しすること」**。

**上端ちょうど(容量と等しい指定)は体積の口では弾かない** —— 数学的には達成可能だから。
ただし OC の二分探索は「動かせる要素が全部 ρ=1」で退化するので `ZeroDivisionError` になる
(`volfrac=1.0` でも同じで、**絶対量の口が入る前からある性質**)。容量の 99.9% は問題なく通る。

### 実測: 塊の大きさを変えたときの材料の量(2026-09-04)

`design_space.demo_conditions()` を余白比率だけ変えて導出し、同じ問題を2通りで解いた
(`spacing=4.0` 指定・`max_iter=5`。`check_absolute_volume.py` [2b] がそのまま走らせている)。

| 余白比率 | 格子 | 塊 | 要素体積[mm^3] | 絶対量 100,000mm^3 指定 | 分率 0.3 指定 |
|---|---|---|---|---|---|
| 0.10 | 21×12×13 | 2,050要素 | 62.994783 | **100,000.000005 mm^3** | 47,913.8 mm^3 |
| 0.40 | 30×21×22 | 10,595要素 | 66.430125 | **100,000.000016 mm^3** | 218,309.3 mm^3 |

- 絶対量なら**要素体積が違っても**(格子の切り直しで 62.99 → 66.43 mm^3)材料の量は
  相対 1.1e-10 で一致する。分率だと **4.56倍**変わる。
- 塊の大きさを変えても物理は同じなので、**変わってよいのは形であって材料の量ではない**。

### 既定の挙動が変わっていないことの担保

`check_absolute_volume.py` [4] が、**基準として採取した `simp.py` の出力**と厳密一致するかを
見る。丸めた10進ではなく **16進float と ρ 場の SHA-256** で比べる(プリセット /
パッシブ要素経路の2本。採取時に2回走らせて1ビット違わないことを確認済み)。

**題材そのものを変えたときは、基準値を取り直すのが正しい。** この検査の意味は
「この変更の前後で1ビットも変わらない」ことであって、特定の数値を守ることではない。
2026-09-04にプリセットを 40×16×16 → 20×8×8 へ縮めたときにプリセット側の4値を取り直した
(`C: 292.2307 → 15.3817` は縮める前の値。いまは `C: 440.3433 → 34.2933`)。
**パッシブ要素経路(16×8×8)は題材を変えていないので基準値もそのまま** —— 取り直したのが
「題材を変えた側だけ」であることが、検査を弱めていないことの担保になる。

## von Mises応力と最小安全率(後処理。2026-09-04)

出てきた形が「保つか」を数字で言えるようにする段(`stress.py`)。**最適化そのものには
手を入れていない。** 応力を制約に入れて最軽量を解く型(応力制約トポロジー最適化)は
**採らない**と決めてある —— 理由4点は context-engine
`safety-factor-goes-outside-the-optimizer`(制約が1本から要素数ぶんへ増える / 特異最適 /
感度が自己随伴でなくなる / **ボクセルの階段状境界では応力が最も信用できない**)。
安全率は最適化器の外側のループで実現する。ここで作ったのは「形を渡すと最小安全率が返る」
ところまでで、外側のループ(安全率 → 材料量の二分探索)は別の段。

### 口

```python
import simp, stress

result = simp.optimize(..., keep_model=True)          # Result.model に解いた Model が入る
scale = stress.UnitScale.for_model(                   # 無次元側(合力・E)は Model から読む
    result.model, element_mm=2.5, load_n=1234.0, youngs_modulus_mpa=68900.0
)
report = stress.evaluate(result.model, result.rho, scale=scale, allowable_mpa=183.3)
report.safety_factor        # 最小安全率 = 許容応力 / 代表応力
report.representative_mpa   # 代表応力[MPa](ρ>=0.5 の 99.5% 点)
report.raw_max_mpa          # 素の max[MPa]。**安全率には使わない**(下記)
report.field.von_mises      # 要素ごとの von Mises [MPa] (nelx,nely,nelz)
```

`simp.optimize` に足したのは `keep_model` の1語だけで、**数値は1ビットも変わらない**
(`check_absolute_volume.py` [4] が ρ 場の SHA-256 まで見ている)。既定は `False` ——
`Model` は `_iK`/`_jK` に要素数×576 の添字配列を2本持つので、要らない呼び出しに
数十MBを持たせない。この口が無いと後処理側が拘束・荷重・浮いた節点の扱いを手で組み直す
ことになり、**組み直しを誤ると落ちずに違う応力が出る**。

### 変位はどこから来るか

`simp.Result` は変位を持っていない。**最終 ρ でもう一度 `Model.solve()` を呼ぶ**方を採った
(60反復に対して1回なので費用は無視できる)。`Result` に `u` を持たせなかったのは、
`rho` を後から差し替えた瞬間に `u` が黙って古くなる欄になることと、この後処理が
**`optimize` を通っていない ρ 場**(受入検査の一様な棒・片持ち梁)でも同じ口で動く必要が
あるため。`stress.evaluate(..., u=...)` で外から渡せば解き直さない。

### 応力の実単位への換算則

`simp` は **E=1.0 / 総荷重 1.0 / 要素サイズ 1** の無次元で解く(`optimize` の既定は
変えない。換算は後処理側の責任)。要素サイズ L[mm]・実荷重 F[N]・ヤング率 E[MPa] に対して:

```
sigma_real[MPa] = sigma_nd * (F / F_nd) / L^2
u_real[mm]      = u_nd     * (F / F_nd) * (E_nd / E) / L
```

**応力は E に依存しない。** 剛性は E に比例し変位は 1/E に比例するので、σ = E ε で E が
落ちる。したがって**安全率も E で動かない** —— `youngs_modulus_mpa` が効くのは変位の側
だけである(検査3が「E と荷重を同時に10倍 → 応力はちょうど10倍」で押さえている)。
剛性は要素サイズに比例する(K ~ E·L)ので、変位は L に**反比例**する。

`F_nd`(無次元側の合力)は `stress.UnitScale.for_model` が `Model.f` から読む。
手で書くと `anchor.load_vector` に `force` を渡した系で応力が黙って定数倍ずれる。

### 代表応力の規則(黙って max にしない)

**代表応力 = 「ρ >= 0.5 の要素」の von Mises の 99.5 パーセンタイル**
(`stress.DEFAULT_RHO_MIN` / `DEFAULT_PERCENTILE`)。素の max を採らない理由は2つあり、
**どちらも単独では足りない**(だから2段になっている):

1. **ρ の低い要素を落とす。** そこの応力は物理的に意味が薄い。実測(下表)では
   全要素の max が代表値の 9.8〜30.5倍まで跳ね、細分するほど大きくなる。
2. **残った母集団の上位パーセンタイルを取る。** ρ>=0.5 に絞ってもなお max は
   階段状境界の角で発散する。これは実在の応力集中ではなく離散化の産物で
   (同じ機序の偽の集中は context-engine
   `face-to-node-anchoring-loses-faces-smaller-than-the-cell` に既出)、
   **max で安全率を決めると解像度を上げるほど安全率が下がり続ける。**

要素応力は**要素中心1点**で評価する(意図した平滑化。8つの角で評価すると階段の出隅・入隅が
要素内でも尖り、拾いたくないスパイクを1段増やす)。値は SIMP の見かけの剛性 `ρ^penal·E`
ではなく **材料そのものの応力**(D は E そのまま)で、中間密度の要素はひずみが大きく出るぶん
**安全率を小さい側へ倒す**(安全側)。

母集団が空(どの要素も ρ < 閾値)なら**例外で落とす**。0 を返すと安全率が無限大になり、
「材料が1つも無い形」が最も安全という判定になる。**母集団の von Mises に非有限値
(nan / inf)が混ざっている場合も同じく落とす** —— nan は比較が常に偽になるので、
黙って通すと安全率が nan のまま「許容応力を下回っている」の判定にも引っかからない
(2026-09-04のQA指摘。`check_stress.py` [4b] が守っている)。

### 実測: 斜めに切った板(階段状境界。`check_stress.py` [4])

上端が45度で下がり幅が半分になる板を引っ張り、細い側の公称応力 F/A に対する倍率で見た
(3段の細分。`solver="direct"`):

| 格子 | 素の max | ρ>=0.5 の max | **代表(99.5%)** | 所要 |
|---|---|---|---|---|
| 24×16×2 | 12.92x | 1.538x | **1.324x** | 0.03秒 |
| 48×32×4 | 26.32x | 1.862x | **1.289x** | 1.0秒 |
| 72×48×6 | 39.72x | 2.089x | **1.304x** | 15.5秒 |

- **素の max は収束しない**(12.9 → 39.7。ρ≈0 の要素が支配している)。
- **ρ で絞ってもなお max は単調に増える**(1.54 → 2.09、+35.8%)。階段の角は細分すると
  角が細かくなるだけで、応力は下がらない。
- **代表値は動かない**(1.324 / 1.289 / 1.304。振れ幅 2.7%)。しかも公称応力より 30% 高い
  ので、**本当の応力集中(断面変化)は捨てていない**。

### 実測: 片持ち梁の曲げ(解析解 σ = M·c/I への収束。`check_stress.py` [2])

先端荷重の片持ち梁で、断面内の σ_xx を y で直線近似して外縁 y=±c へ外挿した値と
M·c/I を比べた。測る断面は**根元そのものではなく梁せい1つぶん先**に取る —— x=0 は
全自由度を固定した面で、梁理論の前提(断面が自由に反る)が成り立たない(実測: 根元の
要素は理論値を 8.5% 上回る)。

| 格子 | 外挿fiber / 理論 | 外側1層の要素中心 / 理論 | 所要 |
|---|---|---|---|
| 32×8×4 | 0.9913 (−0.87%) | 0.9911 | 0.03秒 |
| 64×16×8 | 0.9978 (−0.22%) | 0.9977 | 0.8秒 |
| 96×24×12 | 0.9990 (−0.10%) | 0.9989 | 3.4秒 |

誤差は細分でおよそ 1/4 ずつ減る(2次収束)。一様な棒の単軸引張(検査1)のほうは
**丸め誤差の水準で厳密に一致する**(最大相対誤差 3.9e-15)。

### 実測: SIMP の出力(中間密度あり。`check_stress.py` [4b])

プリセット 20×10×10 / 25反復、E=68900 MPa・荷重 1234 N・要素 2.5mm・許容 183.3 MPa:

| 量 | 値 |
|---|---|
| 素の max | 153.5 MPa |
| ρ>=0.5 の max | 153.5 MPa |
| **代表(99.5%)** | **85.77 MPa** |
| ρ の閾値を外した代表値 | 115.4 MPa(**1.346倍**) |
| 最小安全率 | 2.137 |

**ここでは素の max が ρ>=0.5 の max と一致する** —— この形の最大応力要素は ρ=1 の
荷重直下(点荷重の特異点)にあり、ρ の閾値では動かない。それでも von Mises 上位10要素の
うち8つは ρ≈1e-6 の要素で、**閾値を外すと採用する代表値が 34.6% 上がる**。
「ρ の閾値は素の max を下げるためのもの」と読むと**要らないという誤った結論**になるので、
効いているのは**代表値のほう**だと押さえておくこと。

### 留保(消えない問題)

- **この応力はボクセルFEAの上で計算するので、階段の問題は消えない。** 安全率の絶対値は
  信用せず、**同じ解像度での相対比較**と「明らかに足りない/足りている」の判定に使う。
  厳密な検証は別途まともなメッシュのFEAが要る(範囲外)。
- **99.5% と ρ>=0.5 は実測で選んだ値であって、理論値ではない。** 母集団の要素数が少ないと
  99.5% 点は max に近づく(600要素なら上位3要素)。解像度を跨いで安全率を比べるときは
  要素数も一緒に見ること(`RepresentativeStress.element_count`)。
- **点荷重・点拘束の特異点は代表値に残りうる。** 面アンカー経由(`anchor.load_vector`)なら
  荷重は面に配られるが、節点が少ない面では実質的に点荷重になる。
- **疲労・座屈・接触は見ていない。** 出るのは静的な降伏に対する安全率だけである。

### 題材(4つ)と、何を覆うために居るか

文字列は `design_space.CASES[...].covers` が正で、`check_design_space.py` [12-6] が
**この README に同じ文字列があること**を確かめている(片方だけ直すと落ちる)。

| | 題材 | 余白比率 | 姿勢 | 力 | 覆う性質 |
|---|---|---|---|---|---|
| ① | `bracket`(`demo_conditions`) | 0.25 | 0° | (0,0,-1) | 汎用。保持2つ・除外1つ(円柱)・拘束1面・荷重1面。既定の余白比率のまま |

**余白比率が題材ごとに違うのは題材の性質のため**であって、揃え忘れではない。余白は
「条件の点群の最長辺 × 比率」なので、②を既定の 0.25 のままにすると長辺 182mm に対して
余白が 45mm 付き、**厚み 12mm の板が厚さ 100mm の塊になって薄板でなくなる。**

**③で「拘束2箇所・荷重2箇所を、別々の面添字・別々の力の向きで」は入れられなかった。**
`Conditions` は `fixed_face` / `load_face` を **int で1つずつ**しか持たず、`run_pipeline` は
力を1本のベクトルでしか受けない。フィールドを増やすと `check_design_space.py` の検査[5]
(`Conditions` のフィールド集合そのものを assert している。`20260903-2234` の契約)が落ちる。
代わりに **1枚の U 字面**(中央に上へ抜ける切り欠きを入れた C 形パッドの x 最小面)で支持を
2本の脚に分けてある —— 塊の上半分では拘束アンカーの要素が**6近傍で2成分**に分かれることを
[12-5] が解像度 14/16/18/20/30/44 で確かめている(他の3題材は1成分)。**力の向きを2つにする
のは `Conditions` の型を変えないと無理**で、それは本人の判断が要る(下記「残っている判断」)。

### 基準線の取り方(後続2タスクはここに従う)

秒数はこの機械では熱状態で **1.2〜1.7倍振れる**(engine
`benchmark-seconds-swing-with-thermal-state`)。だから物差しの順位を決めてある:

1. **`CG反復/solve` が第一の物差し。** 同じセッションで n=30 の4題材を撮り直したところ、
   **8回の solve の反復数が1つ残らず一致した**(`[356,338,303,300,303,253,223,290]` など)。
   コンプライアンスも下6桁まで同じ。**機械の状態に依らないので、ここの差は本物である。**
2. **秒は「設計反復あたりの中央値」で見る。** 1回の実行に設計反復が8回あるので、1回
   走らせるだけで分布が取れる。**平均ではなく中央値**にしてあるのは、1反復目だけ `x0=0`
   から解くぶん極端に遅いため(bracket n=44 で 7.26秒 対 中央値 4.93秒)。
3. **同じセッション内で撮り直しても秒は 1.00〜1.16倍振れた**(実測。n=30 の4題材で
   bracket 1.10x / plate 1.00x / branching 1.09x / tilted 1.16x)。**この幅より小さい差を
   「速くなった」と言わない。** 表には最小〜最大も併記してある。
4. **繰り返しは「1回の実行 × 8設計反復」で足りる。** 同じ設定で全体を3回回すのは、n=44 が
   1回5分かかるので割に合わない。**分布は実行の中から取る。**
5. **マルチグリッドは `CG反復/solve` を減らし、並列化は「秒/設計反復」を縮める。**
   別々の欄に出るので、**両方あって初めてどちらが効いたか切り分けられる。**
6. **新旧は必ず同じセッションで測る。** 別の日の秒数どうしを比べない。`--baseline` は
   そのためにある。

### この基準線から読めること(後続2タスクの当たり)

- **CG が solve の 89〜95%、solve が設計反復の 93〜98%。** つまり**設計反復の 8〜9割が CG**
  であり、CG を速くしない限り全体は速くならない。組立は 4.6〜9.1%、スライスは 1% 前後で、
  ここを削っても上限が1割しかない。
- **反復数を DOF^(1/3) で割ると題材が2群に割れる。** bracket 8.2〜8.9 / branching 9.2〜9.9 に対し、
  **plate 19.7〜21.8 / tilted 17.2〜18.7 と2倍以上悪い。** 薄板は極端なアスペクト比で、斜め姿勢は
  除外が塊の中央を貫くぶん条件数が悪い。**マルチグリッドの効きを見るならこの2つが本番。**
- **反復数の伸びは4題材とも DOF の 0.41〜0.45乗**(教科書の対角前処理は 1/3乗)。
  線寸法でいうと n^1.10〜1.20。**1題材だけで測ると 1/3乗に見えるが、4題材ではそうならない。**
- **秒/設計反復の伸びは題材ごとに格子要素数の 1.05乗〜2.03乗とばらつく。**
  薄板が 2.03乗なのは、n=30 の行列(非零 99万)がキャッシュに載っていて n=44(254万)で
  外れるため —— 同じ表の実効帯域が 27.4 → 16.9 GB/s に落ちている。
  2026-09-04の対話セッションが未コミットで出した「合計 ∝ N^(4/3)」は**片持ち梁1題材の
  1本の直線から出た数字**であり、**4題材では成り立たない**(この README に載っていた
  わけではない。持ち込むときは題材ごとに測り直すこと)。
- **薄板は厚み方向が n=30 で5要素・n=44 で7要素**(格子はそれぞれ 7 と 9。外側1層は
  `grid_for_bbox` の pad)。**幾何マルチグリッドで2段粗くすると厚みが1要素になる。**
  ②を入れてあるのはここを踏ませるためである。

### 受入検査は別の題材で回す(巻き込まれないようにしてある)

**性能測定と受入検査で同じ大きさを共有しない。** 受入検査は速さが命(7本で 100〜141秒)、
性能測定は大きさが要る。共有すると、検証を速くするたびに性能の基準線が黙って別物になる。

- 受入検査が使う大きさの正は **`bench.py`**。4題材の通し検査は
  `bench.DESIGN_SPACE_FOUR_CASES`(長辺 **16** 要素・6反復)で、`check_design_space.py` [12]
  が回す。**下限は 14** —— 13 まで落とすと薄板の保持パッド(厚み12mm)に対して要素が 15.4mm に
  なり、`model_from_design_mask` が「保持領域が1要素も掴めなかった」で落ちる。
  `voxelize.occupancy` のレイ縮退は解像度に対して単調でないので、下限ぎりぎりを採らずに 16 に
  してある。
- 性能測定が使う大きさの正は **`perf.py`**(`RESOLUTIONS = (30, 44)` / `MAX_ITER = 8` /
  `VOLFRAC = 0.3`)。[12-7] が **`min(perf.RESOLUTIONS) > bench.DESIGN_SPACE_FOUR_CASES` を
  機械で確かめている**ので、受入検査を縮めた側が性能の基準線を巻き込むことはない。
- **既定を n=50 ではなく n=44 にしてあるのは、測り直しの費用のため。** n=50 は**動く**
  (実測: `tilted` n=50 は格子 52x44x35 / DOF 257,580 / CG反復 1215.0 / 23.566秒per設計反復 /
  1題材だけで226秒)が、4題材だと1回およそ10分かかり、後続タスクが何度も撮り直すには重い。
  n=44 でも DOF は n=30 の 2.8倍あって伸びの指数は取れているので、既定はそちらにした。
  **最終的な数字が要るときは `--resolutions 30 50` を渡す。**

### 4題材とも端から端まで通ることの検査(`check_design_space.py` [12])

**「4つ通った」だけでは足りない。** 同じ性質の題材を4つ並べても全部通るので、
覆っている性質が実際に違うことまで数字で見る。

| 検査 | 何を見るか |
|---|---|
| 12-1 | 表に4題材あり、①が**既存の `demo_conditions` をそのまま指している**(足すのであって置き換えではない) |
| 12-2 | 4題材とも連結性ガードを通り、拘束側と荷重側が共通の連結成分にいる |
| 12-3 | 条件面のアンカーが空でない(`empty_faces()` に入らない・拘束DOF>0・荷重節点>0) |
| 12-4 | `derive` → ガード → `run_topopt` → STL が通り、**条件のどのソリッドにも入っていない空間に材料が出る** |
| 12-5 | 4題材の格子の形がすべて違う / **薄板だけアスペクト比が突出**(3.60 対 1.38〜1.50)/ **多点支持だけ拘束アンカーが2成分**(他は1成分)/ **斜め姿勢の除外だけが塊を大きく削る**(580要素 対 0〜12) |
| 12-6 | 4題材の「覆う性質」の1行が**この README にそのまま**ある |
| 12-7 | 性能の基準線が2段以上の解像度で測られ、その解像度が受入検査より大きい |

`perf.py` 側にも門番がある: **条件面のアンカーが空なら測らずに落とす**(空のまま回すと、
条件が消えた別の問題を測ることになり、しかも最適化はもっともらしく収束する)、
**CG の反復数が1つも数えられていなければ落とす**(解法を差し替えたときに 0 が表へ出て
「反復が減った」と読めてしまう)。

### 残っている判断(本人向け)

- **`Conditions` に「複数の拘束面・複数の荷重(向き付き)」を入れるか。** 型は
  `anchor.AnchorTable.fixed_dofs` / `load_vector` が既に `Iterable[int]` を受け、
  `load_vector` には `out=` があるので**下の層はもう複数に対応している**。塞いでいるのは
  `Conditions` のフィールドの型(int)と `run_pipeline(force=...)` が1本しかないことの2点だけ。
  入れると③が本来の「拘束2箇所・荷重2箇所で向きが違う」になるが、
  **`check_design_space.py` 検査[5]が `Conditions` のフィールド集合を固定している**ので、
  そこを緩める判断が要る(`20260903-2234` の契約が「設計空間ソリッドを渡す口を作らせない」
  ための門番として置いたもの)。

| tilted n=44 | 180,480 | 1055.8 → **142.6** | **0.14x** | 10.770 → 9.077 | 0.84x |

8行の合計は **228.2秒 → 177.3秒(0.78x)**。

**秒の倍率をそのまま読まないこと。** 同じセッション内でも秒は 1.00〜1.16倍振れる(基準線の
取り方3)。この幅を差し引くと、**はっきり速くなったと言えるのは大きい側の4行**
(bracket n=30 0.76x / branching n=30 0.81x / bracket n=44 0.57x / branching n=44 0.53x)で、
**plate n=30 は逆に遅くなり、tilted n=30・plate n=44 は差が無い。**
一方 **CG反復数は機械の状態に依らない**ので、0.07〜0.20x はすべて本物である。

**なぜ反復が10分の1でも秒は半分にしかならないか。** V-cycle 1回が行列ベクトル積 6〜8回ぶん
あり、さらに**密度が変わるたびに各段の作用素(RAP)と最粗格子の LU を組み直す**からである。
Jacobi の1反復は行列ベクトル積1回でしかない。**反復数の比が費用の比になるわけではない。**

### 決めた3点(選択肢があるところ)

**1. 粗格子の作用素は Galerkin(`A_c = P^T A P`)。密度を粗格子へ移さない。**

`emin=1e-9` と `penal=3` で実効剛性は **10^9倍**開く。密度を算術平均で粗格子へ落とすと
空の領域が硬くなりすぎて粗格子が別の問題になり、調和平均でも最小値でも「どれだけ間違えるか」が
変わるだけである。**RAP は近似ではなく、細格子の作用素そのものを粗空間へ射影した唯一の
対称作用素**なので、移し方を選ぶ問題自体が消える。おまけに**拘束(固定DOF)と浮いた節点の
扱いが自動的に引き継がれる** —— 粗格子で境界条件を組み直さなくてよい。
代償は毎 solve の RAP の費用で、実測では **66,150自由度・非零496万で 0.08秒**(同じ solve の
`splu` が 0.04秒)。反復1回が 0.02秒台なので、**組み直しは反復5回ぶん程度**である。

**2. 平滑化は damped Jacobi(赤黒 Gauss-Seidel ではない)。**

1回あたりの効きは Gauss-Seidel に劣るが、**行列ベクトル積と要素ごとの積だけ**で書けるので
`20260904-1415`(CPU並列)がそのまま載せられる。減衰係数は
**`omega = 1 / hi`、`hi` は `λmax(D^-1 A)` の見積もり**(`_smoothing_weight`)。ここは
**前処理が対称正定値であるための十分条件 `omega < 2/λmax` を満たす必要がある**ので、
べき乗法の見積もり `lam`(下から近づく)に安全率1.2を掛けた値を使い、
**`gershgorin <= 2.4*lam` が成り立つときだけ**それを採る —— 成り立てば
`λmax <= gershgorin <= 2.4*lam = 2*hi` なので `omega < 2/λmax` が**証明できる**。
成り立たなければ Gershgorin の上界へ退避する(必ず安全側)。
**Gershgorin をそのまま使うと平滑化が弱すぎる**(実測: 真の λmax 3.1 に対して上界 5.36。
50x20x20 の実密度で 56 → 48反復の差になった)。

**3. 粗視化は軸ごとに独立。要素数が4未満の軸は間引かない(半粗視化)。**

均一ボクセル格子なので粗格子は自明(各軸2分の1)だが、**等方に間引き続けると薄板で
厚み方向が先に潰れる**。`_coarse_axis` は要素数が `min_axis_elements`(既定4)未満の軸を
そのまま残すので、**規則1つで自動的に半粗視化になる**。要素数が奇数の軸も扱える
(粗節点を 0,2,4,… と採り、端が合わなければ最後だけ幅1の粗セルにする)。
**格子寸法が2の冪になることはない**(ボクセル化が決める)ので、偶数しか扱えない実装だと
2段目でほぼ必ず止まる。最粗格子は自由度が `direct_dofs`(既定6000)を下回ったところで
`splu` で直接解く。

### 薄板(粗視化が一番効かない形)はどうなったか

**半粗視化が要ると判断して実装した。** 数字は3つある。

- **薄板の格子は n=30 で 32x17x7、n=44 で 46x24x9。** 等方に2段間引くと厚みが
  **7 → 4 → 2**(n=30)になる。`min_axis_elements=4` は「粗格子でも各軸に2要素以上残す」規則で、
  実際には**自由度が 6000 を切るほうが先に来る**ので薄板は1段で止まっている(上の表)。
- **反復数は 477.0 → 96.8(n=30)・715.9 → 98.5(n=44)。** 4.9〜7.3倍減っており、
  **薄板だけ落ちていない、という失敗にはなっていない。** しかも**伸びの指数は 0.448 → 0.020**で
  4題材の中で**いちばんきれいに格子非依存になった**。
- **ただし秒では勝っていない**(n=30 で 1.37倍遅く、n=44 は差なし)。薄板は自由度が
  他の3題材の3〜5分の1しかなく、**V-cycle 1回の費用増が反復数の減りを食い切る大きさ**である。
  `check_multigrid.py` の薄い格子(36x14x5)でも同じで、反復数は厚い格子と同水準(21回)に
  収まっている。**薄板で破綻してはいないが、薄板は速くなってもいない。**

### 検出力(`check_multigrid.py`。46件)

**マルチグリッド前処理が壊れていても、CG は遅くなるだけで正しい答えに収束する。**
だから「速くなった」「答えが合っている」の2つを見ても実装の正しさは示せない。
`check_multigrid.py` はそれを前提に組んである(実測値は検査の `MEASURED` 行に出る)。

### ウォームスタート(`x0=u0`)は残した

設計反復のあいだ前の解を初期値にする口はそのまま。**外すと反復数がどうなるか**を片持ち梁
40x16x16 の実密度(12設計反復めと11反復めの密度を使う)で測った:

| 解法 | ウォーム(前の解から) | コールド(x0=0) | 増分 |
|---|---|---|---|
| マルチグリッド | 17回 | 18回 | +6% |
| Jacobi | 493回 | 535回 | +9% |

**前処理が良くなると初期値の良さは効かなくなる**(絶対数で 1回 対 42回)。残してあるのは
害が無いからで、**`20260904-1415`(CPU並列)がここを外しても失うのは1割に満たない。**

### 費用がどこへ移ったか(並列化の当たり)

**マルチグリッドは、密度が変わるたびに各段の作用素(RAP)と最粗格子の LU を組み直す。**
これは `solve` の内数で、`perf.py` の内訳表に「うち前処理の組み直し」として出る(Jacobi では 0)。
片持ち梁の実密度で測った実測:

| 格子 | 自由度 | CG反復 | solve[秒] | うち組み直し |
|---|---|---|---|---|
| 20x8x8 | 4,860 | 21 | 0.032 | 40% |
| 40x16x16 | 34,680 | 17 | 0.562 | **46%** |
| 60x24x24 | 112,500 | 34 | 2.023 | 16% |

**反復側だけを並列化しても、組み直しが solve の半分を占める大きさでは全体は2倍までしか
速くならない。** `20260904-1415` はここを見てから当たりを決めること
(RAP は `scipy` の疎行列積、`splu` は SuperLU で、**どちらもスレッド並列していない**)。

### 触らなかったもの

- **`cg_rtol` は 1e-9 のまま。** 反復数が一桁〜数十まで落ちたので、1e-6 へ緩めて得られる
  16%(タスクの見積もり)は誤差の範囲になった。`SOLVE_RESIDUAL_TOL` の誤診の件も
  発火しないので触っていない。
- **`solver="cg"` / `"direct"` はどちらも残してある。** `check_multigrid.py` [5-6] が
  3つとも解けることを見ている。

## CADの面 → 格子の節点(anchor.py)

`voxelize.py` が起こした格子の上に、**「ボディXの面#42」を「これらの格子節点」へ翻訳する
対応表**を載せる(**stage2「面アンカー」**)。これが無いと固定面・荷重面を指定できず、
統合時の `add_fixture` / `add_load` verb も書けない。

**ボクセルの側から境界を取り直してはいけない。** ボクセルの表面は階段状で、真のCAD面から
最大で半要素ずれる。「占有ボクセルの最も左の層」のような取り方をすると、斜面や曲面で
荷重の向きと面積が歪み、階段の角に**偽の応力集中**が出る。出てくる形は「少し悪い」のではなく
「自信を持って間違っている」。正解は**両方の表現が手元にある瞬間(=ボクセル化時)に対応を
固定し、以後はその表を引く**こと。`anchor.py` は `TriangleSoup`(面添字つきの三角形群)と
`Grid` だけを見て表を作り、**占有マスクを一切見ない**(見た瞬間に階段が混入する)。

### 契約(後続がここに依存する)

| 事項 | 決め |
|---|---|
| 節点 | 要素の**角**。要素格子 `(nx,ny,nz)` に対し節点格子は `(nx+1,ny+1,nz+1)` |
| 節点の座標 | `origin + spacing*(i,j,k)`。**要素中心の `+0.5` は付かない**(中心は `Grid.centers_of`) |
| 節点番号 | `n = i*(ny+1)*(nz+1) + j*(nz+1) + k`、自由度 `3n+{0,1,2}`。**`simp._build_edof` と一致** |
| 面と節点 | **1節点は高々1面に属する**(下記の稜線規則)。面ごとの節点集合は排他 |
| 担当面積 | 節点ごとに `mm^2` を持つ。**荷重はこの面積比で配る**(等分は禁止) |

節点番号の一致は `check_anchor.py` の検査[0]が `simp._build_edof` と全要素×8隅で突き合わせる。
**ここがずれると荷重は別の場所に入り、それでも最適化はもっともらしく収束する**ので、
他の検査が全部緑でも意味が無くなる。だから最初に置いてある。

### 表の作り方

1. 面の三角形を、辺長が `sample_ratio * spacing`(既定 0.25)以下になるまで**細分**し、
   各小三角形の重心を標本点にする。小三角形の面積は厳密に等しいので面積は分割で保存される。
   細分が要るのは、平面の面が三角形2枚で返ってくるため —— 三角形の重心だけを見ると
   40×20 の面の荷重が2点に集中する。
2. 各標本点から半径 `radius_ratio * spacing`(既定 **1.0**、引数で変更可)の球に入る節点へ、
   **テント重み** `1 - d/radius` で面積を配る。標本ごとに重みの和で正規化するので面積は保存される。
   - 既定を範囲(要素サイズの0.5〜1.0倍)の**上端**にしてあるのは、`radius >= sqrt(3)/2 * spacing`
     でないと「どの節点も球に入らない標本点」が出るため(要素の中心から最も近い節点までが
     `sqrt(3)/2 * spacing`)。そこへ落ちると最近傍1点へ全部載り、**面の置かれ方によって
     荷重が特定の節点へ集中する**(まさに避けたい失敗)。
   - 既定の `radius = spacing` では、球に入りうる節点は**その要素の8隅だけ**になり、
     重みは三線形形状関数と同じ形になる(候補の探索範囲は `_candidate_offsets` が
     半径から算術的に決める。総当たりの27近傍・64近傍は要らない)。
3. 1つの節点が複数の面の球に入りうる(稜線付近)ので、最後に**持ち主**を決める。

### 稜線の規則(明文化。黙って重複させない)

**節点の持ち主は、その節点へ最も多くの面積を配った面。同点なら面添字の小さい面**が勝つ
(決定的にするため)。したがって:

- 面ごとの節点集合は**排他**。`table.node_ids([面A, 面B])` は素直に連結してよい。
- 他面に取られた節点へ配った面積は**捨てる**(再正規化しない)。捨てた割合は
  `FaceAnchor.leak_ratio`。担当面積の合計を「その面が実際に受け持っている面積」に
  保ちたいため。捨てた分は隣の面が受け持っている。
- 荷重は「その面の節点の担当面積の比」で配るので、捨てた分があっても**指定した総荷重は
  厳密に保存される**(比の正規化で吸収される。実測の相対誤差 2.3e-16)。
- **圧力(`pressure_vector`)の合力は、捨てた面積から独立している。** `p × 面積` が合力
  そのものなので、担当面積から出すと捨てたぶんがそのまま不足する(実測: 要素サイズ
  2.5mm で 11.7%、1.25mm で 4.5%)。**合力は `FaceAnchor.cad_area`(B-repから取った
  真の面積)から出し、その総量を担当面積の重みで按分する。** 配り方は変えていない。

重みを割って両方に配る案(節点を共有する)は採らなかった —— 固定面と荷重面が稜線を
共有していると、同じ節点が「拘束されていて、かつ荷重を受ける」ことになり、
**その荷重は黙って消える**(拘束DOFの荷重は解に効かない)。排他なら少なくとも
どちらか一方には必ず効く。

**この規則の帰結として、要素サイズより小さい面(フィレット・面取り・小さな段差)は
節点が1つも付かず空になる**。実測では 231面のSTEPを要素サイズ 1.54mm で割ると 22面が空。
`table.empty_faces()` で見えるようにしてあり、空の面を名指しして荷重・拘束を作ろうとすると
**黙って「荷重0」「拘束なし」を返さず落ちる**(そのまま通すと、拘束の無い系が最適化に入る)。

### 使い方

```python
model = voxelize.voxelize(shape, 32)                      # stage1
table = anchor.build_anchors(model.soup, model.grid)      # stage2
fixed_dofs = table.fixed_dofs(face_a)                     # 面 → 拘束する自由度
load = table.load_vector(face_b, (0, 0, -1000))           # 面 → 荷重ベクトル(合計は厳密に一致)
keep = table.element_mask([face_a, face_b], layers=1)     # 荷重・拘束の近傍(非設計領域)
result = simp.optimize(*model.grid.shape, fixed_dofs=fixed_dofs, load=load,
                       void_mask=~model.design, solid_mask=keep & model.design)
```

`table.pressure_vector(face, p)` は圧力(面法線の逆向き)を載せる口。合力ではなく
面の向きの分布で決まるので、`load_vector` とは意味が違う。

### SIMP側に足した口(既定の挙動は1ビットも変えていない)

`simp.optimize` / `simp.Model` に足した引数。**境界条件・パッシブ要素の4つが `None` の
ときの挙動は追加前と完全に同じ**(旧版と新版で `rho` がビット単位で一致することを確認済み)。
`keep_model` は数値に一切触らない(既定 `False`)。

| 引数 | 意味 |
|---|---|
| `fixed_dofs` | 片持ち梁の既定の拘束を置き換える。空だと `ValueError`(剛体運動が止まらない) |
| `load` | 既定の荷重ベクトルを置き換える。**自由な自由度に1つも載っていなければ `ValueError`** |
| (共通) | 解いたあと `K U = F` を残差で検算し、通らなければ**拘束不足を名指しして落とす**。`fixed_dofs=[0]` のような拘束不足は「非空で範囲内」の検査を通ってしまい、CGが収束しないまま **max\|u\| = 1.2e16 の有限値**が返って、最適化はそれを信じて進んだ末に OC 更新の `ZeroDivisionError` で落ちていた(原因から遠い場所で落ちるのが最悪) |
| `void_mask` | ρ=0 に固定する要素(設計空間の外・障害物領域) |
| `solid_mask` | ρ=1 に固定する要素(保持領域・荷重や拘束の近傍) |
| `keep_model` | `True` にすると `Result.model` に**実際に解いた `Model`** が入る(既定 `False`)。応力の後処理(`stress.py`)が拘束・荷重・浮いた節点の扱いを手で組み直さずに済ませるための口。**組み直しを誤ると落ちずに違う応力が出る** |

- **パッシブ要素は密度フィルタの「後」で上書きする。** 設計変数だけを固定して物理密度を
  上書きしないと、フィルタが設計空間の外へ密度をにじませる(実測: `rmin=1.5` で設計空間の
  外の要素が ρ=0.29 になった)。にじんだぶんは marching cubes がそのまま形にするので、
  **CADの設計空間からはみ出した形**が出てくる。上書きに合わせて感度も `live` で刈るので、
  連鎖律は上書き後の定義と厳密に一致する。
- **体積制約は動かせる要素だけに掛ける**(目標体積 = `volfrac × 可動要素数 + ρ=1固定の要素数`)。
  そうしないと、設計空間の外の空要素を「もう十分軽い」と数えて、設計空間の中がほとんど
  埋まったまま止まる。
- **空要素にしか接していない節点は拘束側へ寄せて系から外す**。剛性 `emin=1e-9` でしか
  繋がっていない浮いた自由度を残すと K がほぼ特異になり、CGが収束しない。この追加は
  `Model(extra_fixed_dofs=...)` という**別の引数**で行う ——
  `fixed_dofs` に混ぜると、**`void_mask` だけを渡して拘束は既定のままにしたい呼び出しで、
  片持ち梁の拘束が黙って消える**(2026-08-31の自己レビューで見つけて直した欠陥。
  受入検査[0]が「既定の拘束が全部残っている」を見る)。
- **荷重が全部拘束DOFに落ちていたら `ValueError`。** 固定面と荷重面が節点を共有していると
  そうなり、「変位ゼロ・コンプライアンスゼロ」で**荷重を掛けたつもりで何も掛かっていない**
  最適化がもっともらしく収束する。

## メッシュ化(marching cubes + Taubin平滑化)

`mesh.py` が持つパイプライン。**この順序で、段を飛ばさない**:

1. **浮島の除去** — `scipy.ndimage.label` で二値化した場の最大連結成分を求め、それ以外の
   領域を**連続場のほうで**ゼロに塗る(`remove_islands`)。二値化した配列そのものは
   後段(marching cubes)へ渡さない。
2. **ゼロの縁を1層足す**(`pad_field` = `np.pad(rho, 1)`)。材料が設計空間の端に接していると
   そこだけメッシュが開き、水密でない STL になる。
3. **marching cubes**(`run_marching_cubes`、`skimage.measure.marching_cubes`)——
   **連続値の密度場をそのまま渡す。二値化しない。** 二値化すると全ての辺の両端が
   0/1になり、線形補間が必ず中点(0.5)に落ちて半セルずれた階段が戻ってくる。
   この経路の価値の全ては「補間によって面の位置が要素サイズより細かく決まる」ことに
   あるので、ここを間違えると marching cubes を使う意味が消える
   (`check_mesh.py` の検査5がこれを機械で見張る)。`level`(等値の太さ)は定数で
   埋め込まず引数(既定0.5)。
4. **Taubin平滑化**(`taubin_smooth`)—— **自前実装**(`pyvista` / `vtk` / `pymeshlab` は
   使わない)。頂点隣接をscipyの疎行列で1度作り、離散ラプラシアン `L = D^-1 A - I` を
   λ→μの2段で適用する(λ=0.5・μ=-0.53・30反復が既定、すべて引数)。`|μ| > λ` が
   本質的な条件で、破ると通過帯域周波数が負になりただのLaplacianへ退化して形が縮む
   (`laplacian_smooth` はこの比較専用に残してある)。
5. **STL書き出し**(`write_stl`)—— 自前のバイナリSTLライタ(依存追加なし)。
   `output/optimized.stl` に書く。

**新規依存は `scikit-image` の1つだけ**(marching cubesのため)。duocadの`.venv`へ:


## 設計上の決定(実測に基づく)

- **線形方程式は CG(Jacobi前処理・前回解でウォームスタート)で解く。** 直接解法は
  40×16×16 で 1回 7.1秒(`spsolve`) / 6.3秒(`splu` + MMD_AT_PLUS_A)かかり、60反復で7分を超える。
  CG は同じ格子で 1.9〜2.1秒/反復。**当時のタスク既定の格子 40×16×16 を落とさずに済んだのは
  このため**(2026-09-04にプリセット自体を 20×8×8 へ縮めたが、この選択は変えていない —— CG が
  効かなくなるのは格子を上げたときで、下げたときではない)。
- **CG の許容は `rtol = 1e-9`。** 1e-6 だと z対称性の相対誤差が 60反復で 1.7e-07 まで育ち、
  完了条件(c)の 1e-6 に対して余裕が6倍しかない。1e-9 にすると 1.0e-09 まで下がり、
  **所要は13%しか増えない**。合否が丸め誤差の積み上がりで揺れる状態にしない。
- **体積の二分探索は「フィルタ後の密度」の総和で判定する。** 設計変数 `x` の総和で判定すると
  境界付近で目標からずれる。これで最終体積分率が 0.300000 に乗る。
- **カメラは外接球の半径と視野角から距離を出す。** 「最大辺 × 係数」の目分量だと
  40×16×16(当時のプリセット)が画面の1/6にしか映らなかった。
- **marching cubesの頂点座標は角(0,0,0)基準のまま書き出す**(STLは角基準のほうが
  スライサ・3Dプリンタのビルドプレート原点と相性がよい)。**画面側だけ**、ボクセル描画の
  中心原点規約(`ex+0.5-nelx/2`)に合わせて `server.py` の `_build_mesh_payload` で
  平行移動する。`nelx`/`nely`/`nelz` が偶数なのでこの平行移動は整数量になる
  (2026-08-30、平行移動を忘れて完了時に形状がバウンディングボックスからずれて
  描かれる不具合を実機確認で発見・修正した)。
- **`rho[ex]` はセル `ex` の中心の値であり、パディング除去のオフセットはそれを踏まえる
  必要がある。** `marching_cubes` は配列の添字 `i` をそのまま `i*spacing` の位置とみなすが、
  パッド済み配列の添字 `i` は元のセル `ex = i - pad_width` の**中心**を表すので、
  正しいオフセットは `(pad_width - 0.5) * spacing` である。**`pad_width * spacing`
  (0.5要素分だけ大きい値)を引くと、面が設計空間に対して全軸一律に半要素ずれる**
  (2026-08-30、QAが `mesh.py:94-96` で指摘・実測で確認して修正。40mmの模型では
  目視で気づけない大きさなので実機スクリーンショットの比較では検出できず、
  既存7項目の受入検査もどれも並進不変で検出できなかった。**検査8(座標系の整合)を
  新設**し、既知の位置に置いた合成密度場のバウンディングボックスで機械的に見張る)。
  この修正に伴い、**`check_mesh.py` の検査5(内分比)は`mesh.build_surface`内部で
  オフセット適用前(marching cubes直後の生座標、整数格子点のまま)に計算した値を使う
  よう改めた** —— オフセット後の座標(半要素ずれた基準)で計算すると、整数格子点の
  前提が崩れて軸判定が丸ごと反転し、常に0.5という誤った結果になる。
  engine `marching-cubes-cell-center-half-offset`。
- **巻き順は `run_marching_cubes` で `faces[:, (0,2,1)]` へ入れ替える(生成側で直す)。**
  `skimage.measure.marching_cubes` が返す巻き順は `(v1-v0)x(v2-v0)` を外向き法線とする
  一般的な規約(STL/OCCT/three.js)に対して逆向き(実測: 単純な立方体で発散定理の
  符号付き体積が負になる)。直さずにSTLへ書き出すと `build123d.Mesher().read()` で
  読み戻した体積の**符号だけ**反転する(2026-08-30実測: 期待+3022.0が-3022.0)。
  **当初はこれをSTL書き出しの直前で直していたが、2026-09-02に取りやめた** ——
  巻き順に依存する消費者はSTLだけではなく、`server.py` の `_build_mesh_payload` が
  `mr.faces` をそのままブラウザへ送り、`web/index.html` が `computeVertexNormals()` で
  巻き順から法線を導いている。書き出し1箇所で直す形だと**ブラウザ表示だけが内向き法線の
  まま残り**(実測: 面の100%が内向き)、`MeshLambertMaterial` の既定 `side: FrontSide` が
  手前の面を間引くので奥の内壁が見えていた。生成側で直せば消費者が増えても漏れない。
  engine `winding-fix-at-export-only-leaks-to-other-consumers`。
- **最小肉厚は「法線がほぼ逆向きな近傍点との距離」で近似する**(3Dプリントの薄肉検出で
  よく使われる考え方。真の肉厚計算はレイキャストが要り複雑なため)。この近似は
  marching cubes直後の階段状メッシュでは局所ノイズを厚みとして誤検出し**実際より薄く**
  出る。そのため「平滑化後 ≥ 平滑化前」に振れるのが正常(実測比4.27)——
  閾値50%はこの前提で「著しい縮退(パラメータ誤り等)だけを検出する」ための安全側の値で、
  `|μ|>λ` を破るような致命的な劣化(実測: 反復1000回で比0.945まで低下)は検出できる。
- **要素サイズ=1mmと仮定する**(`mesh.DEFAULT_SPACING=(1,1,1)`)。SIMP側に他の物理スケールの
  定義が無く、既存のボクセル描画(`BoxGeometry(1,1,1)`)も1要素=1単位の規約なので、それに
  合わせた。実寸を変えたいときはこの1点(`spacing`)を差し替えればよい。

- **格子を決めるための bbox は `BRepBndLib.Add_s(shape, box, useTriangulation=False)` で取る。**
  `True` にすると、形状に**既に付いている三角形分割**があればそれを使う。OCCT は
  三角形分割を形状に貼り付けたままにするので、同じ形状オブジェクトに2回ボクセル化をかけると
  「1回目=素の幾何の bbox / 2回目以降=前回の三角形分割の bbox」と値が変わり、
  そこから決まる要素サイズ・分割の細かさ・三角形群まで変わる。2026-08-31に実測で発見:
  実物STEPで三角形数が呼ぶたびに 62,264 → 62,168 → 62,138 と動いた(`Cylinder(10,30)` でも
  1回目312枚・2回目以降308枚)。**BRepMesh 自体は deviation を固定すれば決定的**なので、
  非決定性の源は分割器ではなく bbox の取り方だった。`False` は実物STEP(231面)で0.003秒。
- **占有判定は偶奇ではなく巻き数で数え、そのうえでレイをずらし、縮退したらずらし幅を
  変えてやり直す。** 3つとも要る。巻き数だけだと円錐の頂点(三角形が数十枚集まる点)を
  レイが貫いたときに守れず、ずらしだけだと共有辺の二重計上で列がまるごと反転し、
  ずらし幅が**固定**だとその値に合わせた格子を作られたときに守れない(2026-08-31のQAが
  実際に再現した)。やり直しは決定的な列(素数倍の6通り)で、乱数は使わない。
- **最近傍点は7候補の最小値で求める(領域分けの優先順位では求めない)。** 教科書の
  領域分けは分岐が排他であることを前提にしていて、退化した三角形では複数の領域が同時に
  真になり、後から上書きしたほうが勝って誤った距離を返す。**退化三角形はOCCTの三角形分割に
  実際に現れる**(円錐の頂点まわりで実測1枚)ので、入力で弾くのではなくここで正しく扱う。
  stage2 は面へ戻る経路をこの関数に頼るので、ここの誤りはそのまま伝播する。
- **符号付き体積は基準点(bboxの中心)を引いてから三重積を取る。** 絶対座標のまま足すと
  原点から遠いソリッドで桁落ちする(実測: 原点から 1e8 mm の 40×20×10 の箱で 8,000 が
  7,957.33 になった)。薄い形なら符号が反転して、健全な形状を「法線が内向き」と誤って
  拒否する。体積は平行移動に対して不変なので、これは数値の都合だけの操作。
  **殻ごとに測るときの基準点は、その殻自身の点から取る**(soup 全体の bbox 中心を使うと、
  離れた位置にある小さな殻で桁落ちが戻ってくる。実測: 原点の中空箱と 1e7 mm 先に置いた
  傾けた4mm角の箱の compound で、小箱の体積が 64 ではなく 3,542.34 になった。
  軸整列した箱だと三重積が偶然きれいに相殺するので、この検査には傾けた小箱を使う)。
- **向きの検査は殻(連結成分)ごとに行う。** 総符号付き体積だけを見ると、内部空洞の殻だけを
  裏返した入力が正のまま通り、空洞が材料として埋まる。連結成分ごとの符号付き体積と、
  「他の殻いくつの内側にあるか」(+z のレイの巻き数で数える)の偶奇を突き合わせる。
- **占有はセル中心の1点サンプルで、部分体積(占有率)は持たない。** SIMPは全要素が
  同形状であることに依存していて、境界の要素だけ体積を変える口が無い。境界の表現を
  細かくしたいときは解像度を上げる(所要は要素数に比例するので stage1 側は律速にならない
  —— 効くのは SIMP 側で、engine `simp-cost-scales-with-fourth-power-of-resolution`)。

  直接落ちるようにしてある。**解析解との比較だけでは von Mises の定義は守れない。**
- **M6 は [4] を落とすが [4b] の順序検査は落とさない**(閾値を外しても
  代表値 <= max の順序は保たれる)。ρ の閾値の検出力は、階段状境界の板(空要素が材料に
  隣接する形)と、SIMP 出力での「閾値を外すと代表値が 1.346倍になる」の2本で押さえている。

## 変異検査の記録(2026-09-04・題材を縮めたあとの検出力)

## 変異検査の記録(2026-09-04・案5の受入検査[11])

`design_space.py` を1点ずつ壊して、検査[11]が実際に落ちることを確認した(手で戻して確認済み。
変異なしでは不合格0件)。

| 変異 | 壊したもの | 落ちた検査 |
|---|---|---|
| M1 | `mask = (grown \| conditions_mask) & fine.mask` → `grown & fine.mask`(条件の無条件 OR を外す) | 「膨張0でも条件の要素は塊に入る」(**アンカー要素が9個はみ出す**。保持は膨張が届くので0のまま —— **保持だけを見ていたら素通りしていた**) |
| M2 | 再サンプルを添字の割り算にする | 「再サンプルが物理座標で対応する」/「粗い格子の外へ出た本番セルは塊に入らない」(さらに導出そのものが `DesignSpaceDisconnectedError` で落ちる = **塊が3成分に割れる**) |
| M3 | `assert_faces_connected` の呼び出しを外す | 「連結性を確認してから返している」/「閾値0.99・膨張0で切れると落ちる」(**例外が上がらなくなる**) |
| M4 | `grow_by_mm` を mm でなく層数で数える | 「膨張は mm で効く」(要素2mm でも4層になる)/「案5の塊が案1より小さい」/「膨張を増やすと単調に増える」(**8mm も 12mm も箱を埋め尽くして 1,250 要素**) |
| M5 | `& fine.mask` を外す(除外を引かない) | 「除外ソリッドの領域に塊の要素が1つも無い」(**10要素が除外の中に入る**) |

**M1 が示していること**: 「4条件が塊に入る」を保持ソリッドだけで見ていると素通りする。
落ちたのは**拘束・荷重のアンカー要素**のほうで、条件の OR を外しても保持は膨張で拾われていた。

## 制限(承知のうえで残しているもの)

- **画面から面を選べない。** `?debug=anchors` は合成ブラケットの決め打ちで、
  「クリックした面を固定面にする」UIは入っていない。境界条件UIと非同期ジョブ化は
  「難しいが解決可能」として本タスクの範囲外(2026-08-29のスコープ確定)。
  ただし**面添字を受け取る側の口は全部揃っている**(`fixed_dofs` / `load_vector` /
  `pressure_vector` / `element_mask`)ので、残るのは verb の配線だけ。
- **ブラウザで回せる条件は `demo_conditions()` の決め打ち1組だけ。** 2026-09-04に
  「最適化を実行」ボタンは `design_space.run_topopt()`(4条件から塊を導出して面アンカーで
  境界条件を入れる経路)へ繋がったので、**画面と計算は同じ `DesignSpace` を見ている**。
  残っているのは「画面で条件を作る/差し替える」ほうで、条件そのものはサーバ側の
  決め打ちのままである。
- **要素サイズより小さい面には節点が付かない**(稜線の規則の帰結)。実物STEPを
  要素サイズ 1.54mm で割ると 231面中22面が空になる。`table.empty_faces()` で見えるが、
  「その面を指定したいなら解像度を上げる」以外の逃げ道は用意していない。
- **担当面積は真の面積より数%小さい**(稜線で隣の面に取られたぶんを再正規化しない設計)。
  `load_vector` の総和は正規化で、`pressure_vector` の合力は `cad_area` から出すことで、
  どちらもこの差から独立にしてある。**残るのは「担当面積を『面の面積』としてそのまま
  使ったとき数%低く出る」ことだけ**で、面の面積が要るなら `FaceAnchor.cad_area` を使うこと。
- **案1(外接直方体+余白)は「塊が答えを含む」ことを保証できない。** 余白は自由パラメータで、
  最適化が置いた材料は既定の 0.25 でも 8.9% が塊の壁に接している(0.50 でも 3.3%)。姿勢を
  変えると塊が 1.2〜1.4 倍に膨らみ、相対体積制約のままだと材料の量まで変わる。**後続の案5
  (粗く1回回して膨らませる)と比べるためのベースライン**であって、これで確定ではない。
- **体積目標の絶対量(mm^3)は口だけで、画面はまだ分率で回している。** `server.py` の
  `DEMO_VOLFRAC=0.3` は変えていない —— 利用者の入力(安全率)から材料の量を作る外側のループは
  別タスク。**画面を絶対量へ倒すときは `shot.mjs` の反復数の期待値と `screenshots/` の
  撮り直しが付いてくる。**
- **達成可能区間の端ちょうどは解けない。** 体積の口は「容量と等しい絶対量」を通すが、
  OC の二分探索が退化して `ZeroDivisionError` になる(`volfrac=1.0` / `0.0` でも同じで、
  絶対量の口が入る前からある性質)。区間の内側を渡すこと(容量の 99.9% は通る)。
- **つながり検査は入った**(2026-09-04・`20260903-2235`。上の「塊の中で拘束と荷重がひと続きかを
  検査する」)。ただし見るのは**拘束↔荷重の道が有るか無いか**だけで、**道の細さは見ない** ——
  幅1要素の糸でつながっている塊も通る。
- **反復ごとの配信は間引いていない**(60反復 × 約35KB で足りている)。
- 60反復では収束判定(change < 1%)に届かず、反復上限で止まる。コンプライアンスは
  終盤10反復で 0.161%(縮める前は 0.113%)しか動いていないので、実用上は収束しているとみなしてよい。
- **解像度は上げていない**(2026-09-04以降は 20×8×8。むしろ下げた。上の「受入検査の通し時間」)。ボクセル描画の
  階段状の見た目は描画方法が原因で解像度が原因ではないことは今回のmarching cubes導入で
  実証できたので、解像度を上げる要否は別途判断できる状態になっている
  (engine `simp-cost-scales-with-fourth-power-of-resolution`: 線形解像度を2倍にすると
  SIMP側の所要が16倍になる)。
