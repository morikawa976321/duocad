# probe_topopt — 3D SIMP トポロジー最適化のプローブ

## 起動(これ1本)

```powershell
& C:\Users\tm976\mf\duocad\.venv\Scripts\python.exe C:\Users\tm976\mf\duocad\probe_topopt\server.py
```

**ブラウザは自動で開く。** 開いた画面の左上のボタン「最適化を実行」を押すと最適化が走り、
反復ごとに形が更新される。終わるとボタンが `完了 60反復 · C=15.38 (もう一度)` になる。
**約2分かかる**(下記の実測値)。止めるのはターミナルで Ctrl-C。

- ブラウザが開かなければ手で <http://127.0.0.1:8775/> を開く。
- **ポートは 8775 / 8776**。duocad 本体(8765 = WS / 8766 = 静的配信)と**ぶつからないように
  ずらしてある**ので、本体を動かしたままこのプローブを立ててよい。
- ポートを変えるときは `PROBE_HTTP_PORT` / `PROBE_WS_PORT`。
  **WSポートを変えたら URL に `?ws=<番号>` を付ける**(画面側の既定は8776)。
- マウスドラッグで回転、ホイールでズーム(OrbitControls)。

## これは何か

duocad 本体に一切手を入れずに、**3Dのトポロジー最適化(SIMP法)が正しく動くことを実証する**
ための隔離フォルダ。本体への統合はこのフォルダの範囲外。

出力は**ボクセル(占有要素)止まり**でよい。滑らかなメッシュ化や B-rep 化は統合フェーズの話で、
そもそも「メッシュ → 編集可能な B-rep」の汎用変換は OSS に存在しない
(engine `no-oss-mesh-to-editable-brep`)。だからここでは `rho > 0.5` の要素を立方体で描くだけにし、
marching cubes(scikit-image が要る)はやらない。

## 検査の走らせ方

```powershell
# 数値の正しさ(完了条件1)。約2分半
Set-Location C:\Users\tm976\mf\duocad\probe_topopt
& ..\.venv\Scripts\python.exe check_simp.py

# 実機確認(完了条件2・3)。約2分。server.py は自分で起こして自分で落とす
node shot.mjs
```

どちらも最後の行が `OK:` で、終了コードが 0 なら合格。

`check_simp.py` が見ているもの:

1. **要素剛性行列** — 対称 / 半正定値 / 剛体モードがちょうど6本 / **パッチ試験**
   (一様ひずみ・せん断のひずみエネルギーが弾性論の値と 1e-10 相対で一致、剛体運動のエネルギーが0)。
   B行列・D行列・ヤコビアン・局所節点順のどれが狂っても落ちる。
2. **全体系** — `K U = F` の残差 / 拘束DOFが0 / **コンプライアンス = F・U** / 荷重と拘束がz対称。
   要素→全体のDOF写像の誤りを捕まえる。
3. **(a)** 体積分率が目標の ±1% 以内 /
   **(b)** コンプライアンスが減少し(最終 < 初期)、終盤10反復の変動が1%未満 /
   **(c)** 密度場がz対称(CG解法で 1e-6 以内、直接解法で 1e-9 以内)。

## 設計上の決定(実測に基づく)

- **線形方程式は CG(Jacobi前処理・前回解でウォームスタート)で解く。** 直接解法は
  40×16×16 で 1回 7.1秒(`spsolve`) / 6.3秒(`splu` + MMD_AT_PLUS_A)かかり、60反復で7分を超える。
  CG は同じ格子で 1.9〜2.1秒/反復。**タスク既定の格子 40×16×16 を落とさずに済んだのはこのため。**
- **CG の許容は `rtol = 1e-9`。** 1e-6 だと z対称性の相対誤差が 60反復で 1.7e-07 まで育ち、
  完了条件(c)の 1e-6 に対して余裕が6倍しかない。1e-9 にすると 1.0e-09 まで下がり、
  **所要は13%しか増えない**。合否が丸め誤差の積み上がりで揺れる状態にしない。
- **体積の二分探索は「フィルタ後の密度」の総和で判定する。** 設計変数 `x` の総和で判定すると
  境界付近で目標からずれる。これで最終体積分率が 0.300000 に乗る。
- **カメラは外接球の半径と視野角から距離を出す。** 「最大辺 × 係数」の目分量だと
  40×16×16 が画面の1/6にしか映らなかった。

## 制限(承知のうえで残しているもの)

- **境界条件・荷重はコード内固定**でUIから変えられない。境界条件UIと非同期ジョブ化は
  「難しいが解決可能」として本タスクの範囲外(2026-08-29のスコープ確定)。
- **反復ごとの配信は間引いていない**(60反復 × 約35KB で足りている)。
- **形状はボクセルのまま**。滑らかにするのは統合フェーズの仕事。
- 60反復では収束判定(change < 1%)に届かず、反復上限で止まる。コンプライアンスは
  終盤10反復で 0.113% しか動いていないので、実用上は収束しているとみなしてよい。
