# 密度フィルタ半径と平滑化の既定値 — 前後比較スクリーンショット(2026-09-05・撮り直し)

**2026-09-05の2回目の撮影。** 1回目(`20260904-1650`)は「密度場側のガウシアン平滑化を
入れる前 / 入れた後」の比較だったが、そこで見えた `tilted_side.png` の**1要素幅の筋**の
ほうが本題だと分かったので、**既定値を選び直したうえで撮り直した**
(`docs/TOPOPT.md`「1要素幅のフィラメントを消す既定値を選び直した」節)。

## 見方

**各PNGは3面**が1枚に並んでいる(画像の上に焼いてあるラベルが正)。左から:

| 面 | 設定 | 何のためにあるか |
|---|---|---|
| **LEFT `old(shipped)`** | `rmin`=**1.5**要素 / σ=**1.0** / Taubin **12** | 2026-09-05午前まで実際に出ていた形 |
| **MID `old(no gaussian)`** | `rmin`=**1.5**要素 / σ=**0** / Taubin **30** | 同じ最適化からガウシアンだけ外したもの = **証拠** |
| **RIGHT `new`** | `rmin`=**2.5**要素 / σ=**0** / Taubin **30** | 選び直したあとの既定 |

**MID があるのが今回の要点である。** LEFT と RIGHT だけを並べると「どちらも滑らかで差が
分からない」—— **σ=1 が1要素幅の筋を溶かして隠していたから**である。MID を挟むと、
LEFT が隠していたものが見える。

**LEFT/MID と RIGHT は別々の最適化の結果である**(`rmin` は最適化そのものを変えるので、
1つの密度場から切り分けられない)。**LEFT と MID は同じ密度場**から σ だけ変えて切った
2本である(最適化は1回しか回していない)。

**塊(設計空間)の導出は3面で同じ**にしてある —— 案5の粗い段は既定の `rmin` で回るので
条件を揃えないと「塊が違うから形が違う」が混ざる。撮影時の `simp.DEFAULT_RMIN` は
**まだ 1.5 だった**ので、粗い段はどの面も 1.5 で回っている。**変えているのは本番の `rmin` と
メッシュ化の設定だけ**で、`docs/TOPOPT.md` の段1〜段3の表と同じ土俵である
(粗い段も新しい既定で回した場合の数字は同節「端から端まで通した検証」にある)。

**カメラ・光源・画角は3面で完全に一致**している(`compare_shots.mjs` が題材ごとに
3面すべての頂点から共通の中心とカメラ距離を決める)。

## 題材と方向

題材は `design_space.CASES`: `bracket` / `plate` / `branching` / `tilted`。各題材4枚:

| サフィックス | 内容 |
|---|---|
| `_iso` | 3/4俯瞰。向き `(-0.75, 0.5, 0.6)` = `probe_topopt/web/index.html` の既定視点と同じ |
| `_side` | ほぼ真横 `(-0.06, -1.0, 0.08)`(輪郭のシルエットが見える角度。本人が問題に気づいたのが輪郭線だったため) |
| `_threeq` | 反対側からの3/4 `(0.62, 0.66, 0.42)` |
| `_zoom` | iso と同じ向きで距離を 0.45倍に詰めた拡大 |

各最適化は `derive_default`(案5)・`volfrac=0.3`・`max_iter=40`・長辺40要素。

## 撮り直し方(**今回は道具をコミットしてある**)

1回目は使い捨てスクリプトで撮ったので手順が散文でしか残らず、書き直しが要った
(`20260904-1650` の契約④)。今回は `probe_topopt/` に置いた:

```powershell
cd C:\Users\tm976\mf\duocad
& .\.venv\Scripts\python.exe -m probe_topopt.compare_shots export `
    --left  "old(shipped):rmin=1.5,sigma=1.0,iters=12" `
    --mid   "old(no gaussian):rmin=1.5,sigma=0,iters=30" `
    --right "new:rmin=2.5,sigma=0,iters=30"
node probe_topopt\compare_shots.mjs
& .\.venv\Scripts\python.exe -m probe_topopt.compare_shots join
```

`export` が4題材を面ごとに最適化する段(重い。**4題材×2回の最適化で合計10分前後**。
`rmin` が同じ面は最適化を1回しか回さない)、
`compare_shots.mjs` が固定カメラで描画する段、`join` が3面を1枚に並べる段。
`_data/` は中間ファイル(頂点・面のJSONと面ごとのPNG)で `.gitignore` 対象。

**光源は index.html の2灯に加えて、カメラ追従の弱い光を1つ足してある** —— index.html は
視点が1つなので (2,3,1) の1灯で足りるが、ここは4方向から撮るので背面側の視点が
真っ黒になる。3面で同一なので比較には影響しない。

## 見えること(2026-09-05時点の観測。数値の根拠は `docs/TOPOPT.md` の段1〜段3)

- **`tilted_side.png`**: **MID の除外トンネルの中に、迷路状の1要素幅の筋がはっきり出ている。**
  LEFT ではそれが溶けて消えており、RIGHT では**ガウシアンを掛けずに**穴が1つの滑らかな
  輪郭になっている。**この3枚がこのタスクの結論そのものである。**
- **`plate_iso.png`**: LEFT で傾斜面のリブ群が複数の細い枝へ裂けて穴が空いているのは
  「形が良くなった」のではなく、**σ=1 が薄い板を両側から食って割った**結果である
  (MID には割れが無く、1枚のうねった楔になっている)。RIGHT はうねりも消えた1枚の楔。
- **`bracket` / `branching`**: 3面ともほとんど差が無い。**この2題材は `rmin`=1.5要素でも
  1要素幅の筋を出していない**(壁厚が1要素未満の頂点が 0.00%)ので、これが正しい見え方である。
- `_zoom` は iso と同じ向きで距離を 0.62倍に詰めたもの。**`bracket` のように塊状の題材では
  面だけで画面が埋まる** —— 筋を見るのは `_side` のほうである。
